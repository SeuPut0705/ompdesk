## Remote devices

### Tailscale only, transport, routing
- Code: `src/main/remote/`. OMPdesk on a host (B) runs tabs for client computers (A). **The user's rule (19 Oct 2026): computers share over Tailscale only, with no pairing code**: like Mobile web, any computer signed in to an allowed Tailscale account on the same tailnet sees this computer and can use it. No LAN listener, no UDP discovery, no code field; computers without Tailscale do not share (no fallback).
- Host: `RemoteHost` (`host-server.ts`) listens on this computer's tailnet addresses only (`status --json` `TailscaleIPs`, `bindHosts` in `devices.ts`; never 0.0.0.0, `::` or a LAN address), rebinding every 15 s and on a status change.
  - Port: the first free one of `remotePortCandidates()` (`OMP_GUI_REMOTE_PORT`, default 47821, and its four successors, `REMOTE_PORT_SPAN`; for the default port then `FALLBACK_REMOTE_PORTS`, one port in each of five other thousand-blocks below the dynamic range) on the address devices dial (its IPv4 tailnet address), then the same port on its other addresses where they take it (one that refuses is logged `listen-skipped` and left out, never a reason to listen nowhere).
  - A port taken (EADDRINUSE) or reserved by the system (EACCES: Windows reserves port blocks for Hyper-V, WSL and Docker) is skipped, and the `port` log line names each skipped port with its code. Every candidate unavailable: it listens nowhere and `RemoteHostState.listenError` is `{code: "port_in_use", ports}` (Settings lists them), since a device only probes that list.
  - A device probes the same list, its last good port first, dialing the ports `DIAL_STAGGER_MS` (250 ms) apart and the next at once when one fails (`firstToConnect` in client.ts, used by the link's attempts and the tailnet probe `probeAny`), so a silent port costs a quarter second, never its timeout, and never hides a later port that answers. The earliest port that connects in time wins; the rest are closed. A computer that answers on no port fails after the last dial's timeout. Pinned by the listening and "one of them silent" cases of `transport.test.ts` and the candidate case of `crypto.test.ts`.
- Gate, per connection (`RemoteDevices.#gate`): the peer's address must be a tailnet address (100.64.0.0/10, fd7a:115c:a1e0::/48; `isTailnetAddress`) else `not_tailnet`; `tailscale whois` (`Tailnet`, `src/main/tailscale/tailnet.ts`, answers cached 60 s, status 3 s; works whether or not Mobile web is on) must name a node with a login (`no_identity`) on the allowed list (`not_allowed`; Mobile web's `mobileWeb.allowedUsers`, one list for both, default this computer's login) that Mobile web's blocks (`WebBlocks`, by node) do not hold (`blocked`). "Approve new devices on this computer" (Mobile web's pref `mobileWeb.confirmNewDevices`, default off: one switch for phones and computers, `ConfirmNewDevicesRow`, shown in sharing's section while sharing is on and in Mobile web's otherwise) asks through Mobile web's `PairingConfirmations` (`kind: "computer"`, no access tiers) before a new device is recorded (`declined`). Refusals travel as `auth-fail`/probe `error` codes (`REFUSAL_CODES`, `protocol.ts`) and reach the renderer as `remote_<code>`.
- Trust: handshake v2 (`HANDSHAKE_VERSION` 2; a v1 code-pairing peer gets `protocol`). Each side sends its static key; the session keys mix DH(eA,eB) ‖ DH(sA,eB) ‖ DH(eA,sB) and run AES-256-GCM frames over TCP, so only the pinned keys read the link. The host pins TOFU per Tailscale node (`PeerInfo.nodeId`/`login`, `#bindDevice`): a node holds one device and one key; another device id or key from that node, or that device from another node, is `key_mismatch` until the person removes the record (so a new key never earns a fresh PeerQuota record). The client pins the host's key per node (`PairedHost.nodeId`, `connectFirst`); a changed key is `key_mismatch`.
- **A paired device's tabs here never get this computer's control socket** (see control-tools › Control socket and the `ompdesk` CLI, **Env, per spawn**): `LocalHostServices` spawns them with an `origin`, so a device's agent acts on this host only through its link. Residual: such a session runs as this host's user and could read the token file deliberately, as any of the user's files. Pinned by `sidecar-factory.test.ts`.
- Client: Settings watches the tailnet's computers (`remote:watch-tailnet`, every 5 s while shown; `TailnetComputer`): each online non-phone node of `status --json` is probed on the candidate ports (`probe` → `probe-ok {deviceId, name}` or the refusal; this computer itself is skipped). Connect (`remote:connect {nodeId}`) pins and links it. Connect on a host already linked makes a new client and moves the host's open tabs onto it (`RemoteSidecar.relink`), so they never read offline while the host shows online (pinned by "connecting again to a host already paired" in `devices.test.ts`). A `RemoteClient` dials only what `#hostAddresses` resolves on each attempt: the node's current tailnet address on the port it answered on in this run, then every candidate port. Stored addresses and ports are never dialed (a reboot moves the port).
- **A link that went silent or dropped comes back on a signal, not on a timer**. Otherwise a dead path is noticed only by the ping timer (`PING_INTERVAL_MS` 10 s, `DEAD_AFTER_MS` 30 s) and retried 1, 2, 4, 8, 16, 30 s apart; those constants stay as the guard for the case no signal covers.
  - `RemoteClient.wake(trigger)` (`WakeTrigger`: `resume`, `unlock`, `online`, `tailnet`, `focus`, `peer`) is called by `RemoteDevices.wake` from `index.ts` for powerMonitor `resume` and `unlock-screen`, the `ConnectivityMonitor` going online, and `browser-window-focus`, and by the tailnet poll when a known host's node was offline in the last poll and is online now or Tailscale just became ready (`#wakeReturnedHosts`, `#poll`).
  - Offline or waiting out a backoff: the backoff starts over at 1 s and an attempt runs now (`connect()` still retries now without resetting it). Online: `Link.check(WAKE_CHECK_MS)` pings and drops the link (`dead`) when no frame arrives within 3 s, then the client attempts at once; a frame in time leaves it alone.
  - An attempt already running is the one trying now, except on `peer`: this computer's own host accepted a link from that host's computer (`RemoteHostOptions.peerOpened`), so it is up, and a dial that has waited on an address for `STALE_STEP_MS` (1 s; a younger one is left to finish, at once or when it turns 1 s old) is ended and run again. The 1 s gate keeps two computers that use each other as hosts from ending each other's handshakes (pinned by "two computers that use each other as hosts" in `devices.test.ts`).
- **A host whose app is restarting is dialed every second, not on a growing backoff**. A dial that ends `ECONNREFUSED`/`ECONNRESET` on every address (`RemoteError.refused`, set in `dial`) means the computer answered and nothing listens. `#scheduleRetry(refused)` then keeps the delay at `RECONNECT_MIN_MS` and the backoff at its first step, for `REFUSED_RETRY_WINDOW_MS` (60 s) from the loss of the link; after that, and for any timeout, unknown host or refusal code, the backoff grows. No quit-time event from the host is used: a crash, a kill and a shutdown would send none, while a refusal reaches the client whenever the computer is up.
- **Log** (`gui-runtime.jsonl`, source `remote-link`, transitions only apart from the host's `traffic` summary below, never a line per ping, no address, key or token): on the client `down` {deviceId, name, reason: `closed` | `dead` | `protocol` | `local` (`Link.closeReason`) or the failed attempt's code (`unreachable`, `key_mismatch`, … when a launch never got online), wasOnlineMs}, `attempt` {deviceId, n, delayMs, trigger: `start` | `connect` | `backoff` | a wake trigger} (backoff attempts past the 6th are not written) and `up` {deviceId, outageMs, attempts, appVersion: the host's build}; on the host `open` {deviceId, ms: accept to authenticated, appVersion: the device's build, slim: the hello capabilities `slimOf` turned on, by their log names in `SLIM_LOG_NAMES` order (`protocol.ts`), for a current device `events,progress,autopilot,ends,reads,tools,fields,status,lists,shift,settings,roster,jobs,outputs,args,deflate,context,sessions`, or `none`} and `closed` {deviceId, reason, ms: how long it was open} per device connection (`RemoteHostOptions.logLink`, `RemoteClientOptions.log`, both from `RemoteDevicesDeps.logLink`). Pinned by `transport.test.ts` ("a link that dropped or went silent"), `wire.test.ts` (`Link.check`, `closeReason`) and `devices.test.ts` ("a host link after the computer wakes").
- **What the link carries is logged, and a harness measures it**. `remote-link` `traffic` {deviceId, ms, tx, rx, top: JSON text of [{kind, frames, bytes} ×5], events: JSON text of {omp event type: count ×5}} (text because the runtime log keeps only primitive details): the host writes it once a minute for each device connection that moved at least `TRAFFIC_LOG_MIN_BYTES` (256 KiB) and once more when such a connection closes.
  - `kind` is `tx`/`rx` plus the frame (`evt tab.event events`, `evt tab.event subagentFrame/subagent_progress`, `req tab.command/get_jobs` (a tab command with its RPC command's type), `res sessions.list` sized under its request's method, `ping`), in wire bytes (frame header, nonce and tag included); `events` counts the omp events inside `events` batches and `eventBytes` weighs each type by its own JSON; `wholeEnds` (only when any) weighs by role the messages of an `agent_end` that crossed whole instead of as a `~sent` reference. Never a payload, address or key.
  - Code: `Link.onTraffic` (`wire.ts`) feeds a `LinkTraffic` per connection (`link-traffic.ts`, at most 128 kinds), started in `RemoteHost.#auth`. Pinned by `link-traffic.test.ts`, "the host's traffic line" in `transport.test.ts` and the real-pipeline case of `link-traffic-report.test.ts`.
- **Measured link traffic (20 Oct 2026; `OMP_GUI_LINK_TRAFFIC=1 bunx vitest run src/main/remote/link-traffic-report.test.ts`, idle seconds `OMP_GUI_LINK_TRAFFIC_IDLE_S`)**: two `RemoteDevices` over real loopback sockets, a real `LocalHostServices` and `SidecarManager` over the scripted fake omp `test-traffic-omp.ts` (stock frame shapes and the 150 ms subagent progress coalescing of omp's `task/executor.ts`). The harness counts every `Link.send` itself, independent of the production counter. Its rig is `link-traffic-test-rig.ts`; a subagent's progress cases sit in `link-traffic-progress.test.ts` (subscription off and `progress`) and `link-traffic-progress-events.test.ts` (`events`), split so their subagent runs go side by side.
  - The link is quiet when nothing runs (an idle tab sends ping and pong only), so streaming is not changed for idle (the requester's rule: only if idle is clearly above near-zero). Running work is what costs: an older device still gets each stock `message_update` whole, twice (`message` and `assistantMessageEvent.partial`), O(K²) in the reply.
  - **Done for `message_update` (20 Oct 2026, the same harness, `link-events.ts`)**: the device's hello carries `slimEvents: true` (`ClientHello`, `HostConnection.slim.events`; every capability is read from the hello in one place, `slimOf` in `protocol.ts`, a later one counting only with those it builds on). For such a connection the host sends `events` as the local pool sends a window's (`createMessageUpdateSlimmer`: the first update of each message whole, the rest reduced) and each subagent `message_update` through `slimSubagentFrame`, and drops a `usage` that repeats the last one of its message (`createLinkEventEncoder`, one per tab and connection, in `LocalHostServices.#emit`). The device (`RemoteSidecar.handleEvent`, `createLinkEventDecoder`) puts the usage back and rebuilds the text/thinking blocks and the tool call from the deltas, so every window receives what a local tab's would, including one that attaches mid-message; a whole update (an older host) passes through. **`PROTOCOL_VERSION` stays 1 on purpose**: host and device must agree on it exactly (`protocol` refusal), so a bump would lock every older device out. An older device sends no `slimEvents` and gets whole frames; an older host ignores it. Never make the capability required, and never send a slim frame to a connection that did not ask.
  - **After**: the stream is linear in the reply; pinned by `link-traffic-report.test.ts` below.
  - **The page asks for a brief `get_state`**: stock's `get_state` carries `systemPrompt` and every tool's wire schema (`dumpTools`), which the page never reads. Every renderer `get_state`, and the OMPdesk control tools' reads of a session's state, sends `brief: true`, and main's local handler (`briefState`, `local/composer.ts`) leaves the two out; a call without it (e2e specs, agent tools) gets the whole state. An older host ignores the flag. Pinned by `local/composer.test.ts`.
  - **A transcript page starts at the run it belongs to, not at the last typed prompt** (`transcriptRunStart`, `resources/gui-bridge/transcript-page.ts`): a page may also open right after an assistant message that stopped on anything but a tool call, because Goal and Autopilot runs continue with custom messages, never a typed prompt. Pinned by `local/sessions.test.ts`. A page read from the end weighs at most `BACKWARD_PAGE_BUDGET` (256 K JSON characters; `local/sessions.ts`): one heavier is read again with half as many messages, down to 20, and the rest comes as older pages on scroll; a single run longer than the budget comes whole, since the bridge snaps every shorter read back to its start (a read that starts where the last one did ends the loop). A page leaves out each thinking block's `thinkingSignature` (`transcriptPageMessages`; stock reads it from the journal, never from a page), and the renderer's live-to-page match ignores it (`message-identity.ts`).
  - **The model catalog leaves stock's `compat` block behind**: `catalogSnapshot` (`resources/gui-bridge/settings.ts`, behind `providers`, `models_catalog` and `model_catalog_update`) sends each model without `compat` (nothing in OMPdesk reads it). For `get_model_roles` the RPC client asks with `compact: true`, the bridge's `model_roles` then names each candidate once (`candidateModels`) and each role's candidates as indexes, and the client expands it back (`compactModelRoles`/`expandModelRoles` in `model-role-contracts.ts`); an older host ignores the flag and its plain answer passes through, an older device never asks. Pinned by `bridge-catalog-stock.test.ts` (no `compat`, under 1 KB a model, read fields kept; compact roles expand to the plain answer) and `src/shared/model-roles-wire.test.ts`.
  - **Live frames carry no request bookkeeping** (`withoutFrameBookkeeping`, `src/main/frame-bookkeeping.ts`, applied as the sidecar takes each frame): `message_end`, `turn_end`, every message of `agent_end` and a `message_update`'s `partial` leave without stock's `inputTransformations`, `requestControls` and `contextSnapshot`, to each window and over the link; nothing in main or the renderer reads them (transcript pages already drop them). A `turn_end` leaves with its type alone: its `message` and `toolResults` are each already sent by their own `message_end`, `message_start` and `tool_execution_end`, and read by nobody. A subagent's events (`subagent_event`, read only by its tools surface) leave the same way (`slimSubagentFrame`, `subagent-frames.ts`). Pinned by `frame-bookkeeping.test.ts` and `subagent-frames.test.ts`.
  - **A batch past the frame cap goes as several frames**: otherwise a burst past the link's 16 MiB `MAX_FRAME_BYTES` is dropped, `agent_end` included, and the device's tab never leaves "running". `Link.send` throws `FrameTooLargeError` (before sealing a message already past the cap) and the host's `sendTabEvent` halves such a batch until each part fits, in order; only a single event over the cap is still dropped and logged. The traffic report's slim-events tests stream unpaced, which reproduces it.
  - **Done for progress snapshots and subagent frames (21 Oct 2026, the same harness, `link-events.ts`)**: a hello capability, `slimProgress: true` (`ClientHello`, `HostConnection.slim.progress`; it counts only with `slimEvents`). It is its own flag because devices that already send `slimEvents` may read neither a delta nor an array: they keep single, whole frames.
    - For a connection that asked, the host sends a subagent's `AgentProgress` once and then as a delta against the last snapshot of that subagent id, whichever of the two copies brought it: the `subagent_progress` frame (`FieldDelta` `{"~delta": id, set, unset}`, by top-level field; the payload's fields beside the snapshot go the same way) or the parent's task `tool_execution_update` `details.progress` (also a nested subagent's, inside `subagent_event`). The device rebuilds the very frames and updates stock emitted.
    - Encoder and decoder each keep the last snapshot per id for the tab's life and mirror each other because the link is ordered, which holds only if the encoder sees items in wire order: `createLinkEventSender` (one per tab and connection, `LocalHostServices.#emit`/`#sender`) holds the subagent frames of one `BATCH_INTERVAL_MS` (32 ms), encodes them when they leave and sends them as ONE `subagentFrame` tab event whose `arg` is an array; an `events` batch, any other tab event and the sidecar's `beforeResponse` send the frames held back first.
    - A new connection gets a new encoder, which sends every id whole first, and a send that failed (over the frame cap) makes the next start over. A device with no snapshot behind a delta drops that update or frame, never delivers half of one. The traffic line names the batch `evt tab.event subagentFrame/batch` and counts its frame types in `events`. Never send a delta or an array to a connection that did not ask, and never make the capability required.
  - **After**: the scripted omp re-stamps `currentToolStartMs` and every `recentTools[].endMs` on each snapshot while stock stamps them once, so the rig's delta frames overstate stock's.
  - **A flush of subagent frames past the cap is halved like an `events` batch** (`sendTabEvent` splits `events` and `subagentFrame` arrays, in order; `#send` reports whether every part went out): the halves leave in the order they were encoded, so the device's decoder sees every delta after its base. A single frame over the cap is dropped, and the sender then starts a new encoder, so the next snapshot of each subagent goes whole and the device never sits on a delta without a base. Pinned by "tab events past the link's frame cap" in `host-services.test.ts`.
  - **An Autopilot status crosses as a delta**, because the status carries every cycle of the run and is re-sent often. A hello capability, `slimAutopilot` (with `slimEvents`; `HostConnection.slim.autopilot`): the host's encoder (`createStatusEncoder` in `link-events.ts`, one per tab and connection, reset with the rest after a send that failed) sends a tab's status whole once, then the top-level fields that changed, and of a list (the cycles) only its length and the items at an index that differ (`~items`). The device's decoder rebuilds the status the host's pool delivered; a delta with no status behind it is dropped, never delivered half. A device without it gets whole statuses; never send a delta to a connection that did not ask. Pinned by "an Autopilot run's status" in `link-events.test.ts` and "an Autopilot status on the link" in `host-services.test.ts`.
    - **A `get_autopilot` answer crosses as a delta too**: with the hello capability `slimAutopilotReads` (with `slimAutopilot`; log name `status`) the host numbers each answer (ids carry the encoder's random epoch, so a device never rebuilds from another encoder's answer; the host keeps a tab's encoders across the device's reconnects while its hello reads the same way, `HostTab.reads`, so the first read after a drop is a delta of the copy the device kept, and a device that lost it asks `fresh`) and, after the first on a connection, sends it as a delta of the last one (`createReadEncoder`, `LocalHostServices.#autopilotRead`); the device (`RemoteSidecar`, `createReadDecoder`) rebuilds it from the copy it names and, holding no such copy, asks again with `fresh` and gets it whole. A device without it gets the whole status. Pinned by "an Autopilot status a device reads" in `link-events.test.ts`, "a get_autopilot answer on the link" in `host-services.test.ts` and the `get_autopilot` case of `remote-sidecar.test.ts`.
    - **The reads a device repeats on every hydration go the same way**: with `slimListReads` (with `slimAutopilotReads`; log name `lists`) each read `encodedReadKey` names (`get_autopilot`, `get_available_commands`, a `get_transcript_page` from the end by its limit; a page by cursor goes whole) has its own numbered chain per tab and connection, on the host (`#encodedRead`) and the device (`RemoteSidecar`'s decoders by key). A device without it gets them whole. A `commandsUpdate` that repeats the list the connection last got is not sent at all (`#newCommands`, any device: the device replaces its list with each). With `slimShiftedReads` too (log name `shift`) a list in such a delta may be compared at an offset (`ItemsDelta.shift`, the first earlier item equal to the new first item, used only when it leaves fewer items to send), since a running session's tail page starts later on every read; devices without it keep index comparisons.
    - **Settings' reads go the same way**: with `slimSettingsReads` (with `slimListReads`; log name `settings`) `get_providers`, `get_settings_schema`, `get_model_roles` and `get_settings` each keep a chain per command and arguments. The subagent roster a running turn polls every 3 s (`get_subagents`) goes the same way with `slimRosterReads` (with `slimListReads`; log name `roster`), and a running agent whose progress moved crosses as its changed fields (`~fields`). The background jobs list (`get_jobs`) goes the same way with `slimJobsReads` (with `slimListReads`; log name `jobs`). A device without the flag gets each whole.
    - Pinned by "the reads a device repeats on every hydration", the two "Settings' reads" cases and the jobs case in `host-services.test.ts` and "keeps a chain per read" in `remote-sidecar.test.ts`, the offset by "compares a list that moved on at its offset" in `link-events.test.ts` and "compares a running session's tail page at the offset" in `host-services.test.ts`, and over real sockets by "a device that asks for slim list reads" in `link-traffic-report.test.ts`.
  - **A message crosses whole once**, because stock sends a prompt, tool result or custom message in its `message_start` and again in its `message_end`, and every message of a run once more in `agent_end`. A hello capability, `slimEnds` (with `slimEvents`; `HostConnection.slim.ends`): the host's encoder (`createEndsEncoder` in `link-events.ts`, per tab and connection, reset with the rest after a send that failed) remembers each message it sent whole in a `message_start` or `message_end` (key: role, timestamp, tool call id; the newest 256, evicted in the same order on both ends) and sends a `message_end` equal to it, and each `agent_end` message equal to it but for the journal `entryId`, as `{"~sent": key, entryId?}`; both ends forget them at a terminal `agent_end`. A message that differs goes whole. The device's decoder resolves the references; one it holds nothing for drops the event, never delivers half. A device without it gets every message whole; never send a reference to a connection that did not ask. Pinned by "messages a connection already carried" in `link-events.test.ts`.
  - **A reply that read files is a reference too**. The bridge adds `__ompReadGroup` to each read call of a committed `agent_end` message (`decorateMessages`, sessions.attach_entry_ids) and never to the live `message_end`. A hello capability, `slimReadGroups` (with `slimEnds`): the encoder compares the message without those groups and sends them beside the reference (`{"~sent": key, entryId?, reads: {index: group}}`); the decoder puts each back last among its call's arguments. A device without it parses a reference strictly, so it gets such replies whole; never send `reads` to a connection that did not ask. Pinned by "a committed reply whose read calls the bridge decorated" in `link-events.test.ts`.
  - **A tool result crosses once**, because stock builds a tool result's `tool_execution_end` and its `toolResult` message from the same result (`emitToolResult` in pi-agent-core's `agent-loop.ts`). A hello capability, `slimToolResults` (with `slimEnds`; `LinkSlim.toolResults`, log name `tools`): the host's encoder (`createToolResultEncoder` in `link-events.ts`, per tab and connection) remembers each call's end (the newest 256, both ends forget them at a terminal `agent_end`) and sends a `toolResult` `message_start` whose `content` and `details` equal it as `{"~tool": toolCallId, ...the rest}`; its `message_end` was already a `~sent` reference. The device's decoder puts them back; a reference to a call it never saw end drops the event. A device without it gets every result twice. Pinned by "a tool result its call's end already carried" in `link-events.test.ts` and by `link-traffic-report.test.ts` (result message as a reference, same renderer stream either way).
  - **A running tool's output crosses as what follows**, because stock's bash, eval and task tools send the call's whole output so far, or its kept tail, in every update. A hello capability, `slimToolOutputs` (with `slimEvents`; `LinkSlim.toolOutputs`, log name `outputs`): after a call's first update the host's encoder (`createOutputEncoder` in `link-events.ts`, per tab, connection and subagent) sends an update whose output is one text block that continues the last one as `content: {"~output": {from, add}}` (the last text from `from` on, then `add`; a tail that slid finds where it picks up, trying at most `CONTINUATION_TRIES` (4) places, so a log of one repeated line costs linear time), else whole; both ends forget a call at its `tool_execution_end` and every call at a terminal `agent_end`. The device (`createOutputDecoder`) rebuilds the text and drops an update that continues one it never held. A device without it gets every update whole. Pinned by "a running tool's output" in `link-events.test.ts`.
  - **A running call's arguments cross once**, because stock repeats the call's whole `args` in every update. A hello capability, `slimToolArgs` (with `slimEvents`; `LinkSlim.toolArgs`, log name `args`): the host's encoder (`createArgsEncoder`, per tab, connection and subagent) remembers the arguments a call's `tool_execution_start` or last update carried and sends an update with equal ones as `args: {"~args": true}`; changed arguments go whole; both ends forget a call at its end and every call at a terminal `agent_end`. The device (`createArgsDecoder`) puts them back (the renderer reads `args` from updates: `panel-auto-open.ts`) and drops an update naming arguments it never held. A device without it gets them in every update. Pinned by "a running call's arguments" in `link-events.test.ts`.
  - **A reply stock stamped after its `message_end` is a reference too** (stock adds fields such as `completedAt` to an `agent_end` reply). Another hello capability, `slimEndFields` (with `slimEnds`; `LinkSlim.endFields`, log name `fields`): a reference may carry `set` and `unset`, the top-level fields that changed since the copy crossed, when they are under a quarter of it (`fieldPatch` in `link-events.ts`); the decoder applies them before the read groups and `entryId`. A device without it parses a reference strictly and gets such replies whole. Pinned by `link-events-stock.test.ts` (installed omp: a run's `agent_end` all references, rebuilt equal) and "a committed reply stock stamped after its message_end" in `link-events.test.ts`.
  - **Large frames cross deflated**. A hello capability, `deflate` (independent of the slim flags; `LinkSlim.deflate`, log name `deflate`): the host calls `Link.deflateSent()` (`wire.ts`) for such a connection, and every message of `DEFLATE_MIN_BYTES` (1 KB) or more it sends then goes as `0x00 || deflate-raw(JSON)` (level 3) when that is smaller; a receiver reads both, since JSON never starts with 0x00, and inflates with `maxOutputLength` at the 16 MiB frame cap (past it the link drops, `protocol`). Each such frame is deflated on its own. The traffic line counts wire bytes. The device's requests stay JSON. A device without it gets every frame as JSON.   - **A live stream crosses deflated against the link's context**, because live frames are mostly under `DEFLATE_MIN_BYTES`. ### Per-device model limit
- A paired device's per-day model limit (`remote/peer-quota.ts`, prefs on the peer in `remote-peers.json`) covers every RPC command that calls a model on the host, plus `host.bench.run` (models × runs requests), `host.modelSetup.run`, every start of a schedule the device saved there (timed or run now; see Scheduled runs) and every `host.botDesk.answer` (one request: it wakes the host's bot; see A paired host's bot desk).

### A paired host's bot desk
- **The user's request (31 Oct 2026): a paired device sees and uses its host's bot, not only this computer's** (the bot's desk and its screen: control-tools.md › Bot and panels-sidebar.md › The bot's screen). A host method set like `host.schedules.*`, carried by `LocalHostServices` (`host-services.ts`) and `app-protocol.ts`: `host.botDesk.get {}` → `BotDeskState` (`BotDeskStateSchema`, `shared/bot-desk.ts`: duties, decisions, the bot's routines with their runs), `host.botDesk.answer {id, answer}` → null (the payload is the owner's own IPC schema, `BotDeskAnswerSchema`, so only what the owner's handler accepts crosses), and the event `host.botDesk.changed` (`BOT_DESK_EVENT`, data `BotDeskState`) sent to every connected device by `LocalHostServices.botDeskChanged` whenever the host's desk push (`pushBotDesk` in `ipc.ts`, hooked to the desk, the wakes and the bot switch) runs, through `RemoteDevices.hostBotDeskChanged`.
- **Same code as the owner's own answer.** `ipc.ts` builds one `HostedBotDesk` (`enabled`, `state`, `answer`, `edit`, `activity`, `teach`, `takeover`, `terminalSeen`; `LocalHostServices.attachBotDesk`, like `attachAutopilot`): `answer` is the function the owner's `BOT_DESK_ANSWER` handler calls (`answerBotDecision`: `agentControl.botDecisionAnswered(deskStore.answer(id, answer))`), so the decision is recorded first, an unknown or already answered one is refused by the desk, and the host's bot is told exactly once whoever answered: the owner at the host or a device. `edit` is the owner's `BOT_DESK_EDIT` path (`editBotDesk`) with its own schema, so a device can change identity, routing, voice, side chats, pause, task marks and pins, and nothing about the bot's memory or duties: there is no `host.botDesk.setDuties`, and `memory_*`, `duties` and `undo` edits are refused as invalid. Nothing here is a second path to the bot.
- **Only while the host's bot is on.** `get` answers an empty desk while it is off (the bot's row is gone there, and a stale tab must not show old decisions); `answer` and `edit` are refused with the coded error `bot_off` (`ipcError.bot_off` in both locales). A host with no desk attached (an older OMPdesk answers `unsupported` to every `host.botDesk.*`) shares none.
- **Quota.** An answer wakes the bot on the host's models, so `host.botDesk.answer` is one request of the device's day (`#metered`, refunded when the desk refuses the answer; over the limit it is `remote_limit_reached` and the decision stays open). Reading the desk and editing it are free. Permissions: there are none per method, as for `host.schedules.*`; the gate is the link's (allowed node, not blocked).
- **Device side.** `ipc.ts` `BOT_DESK_GET`/`ANSWER`/`EDIT` take an optional trailing `device` (`deviceOf`): none runs this computer's own desk as before, a host id goes to `remoteDevices.request(device, "host.botDesk.*")` (`get` is parsed with `BotDeskStateSchema`). `RemoteDevices` reads `host.botDesk.changed` into `HOST_BOT_DESK_STATE` (`IpcHostBotDesk {device, state}`, a separate channel so this computer's `BOT_DESK_CHANGED` payload and every window's listener are untouched; a state the link cannot parse is dropped) for the desktop windows, and `onHostBotDesk` lets `ipc.ts` forward it to a paired web page's windows. `window.omp.sessions.botDesk` is `get(device?)`, `answer(payload, device?)`, `edit(payload, device?)` and `onChanged(cb(state, device?))`, which listens to both channels.

### Agent browsing over the link
- **The user's order (1 Nov 2026): the Preview's robot button works for a tab that runs on a paired host** (panels-sidebar.md › Preview: agent browsing). The tab's omp is the host's, so `browser_relay_start` makes stock's relay listen on the HOST's loopback, out of the device's reach; the device's own native Preview page stays the one the agent drives. The host tunnels the relay's extension socket: `host.previewRelay.open {rtab}` (the host dials the relay and answers once the socket is open), `host.previewRelay.send {rtab, data}` (one text frame to the relay), `host.previewRelay.close {rtab}`, and the host pushes each frame the relay sends and the socket's end as the `host.previewRelay` event (`PreviewRelayEvent`: `message` or `close`, to the connection that opened it). Contract in `app-protocol.ts`; host side `preview-relay-tunnels.ts` (`PreviewRelayTunnels`, held by `LocalHostServices`), device side `link-relay-socket.ts` (`LinkRelaySocket`, from `RemoteDevices.previewRelay`).
- **The host dials only what its own bridge answered.** `LocalHostServices.#command` remembers, per tab, the `{url, token}` of a successful `browser_relay_start` after `relayExtensionUrl` vetted it (loopback `http://127.0.0.1:<port>` and a token), and forgets it on `browser_relay_stop` and when the tab closes or is adopted under a new rtab. `open` without a remembered relay is refused `relay_unavailable`; every param schema is strict, so an address or token a device sends is rejected, never read (no loopback SSRF). Another device's rtab is `unknown_tab`.
- **It ends with the link, and the relay with it.** The host closes the socket when the device does, the tab goes, the relay stops, or the connection ends (`disconnected` also sends the tab's omp `browser_relay_stop`, as Take over would, since the device cannot). A relay frame the link cannot carry (over `MAX_FRAME_BYTES`) closes the tunnel, so the agent's next command fails instead of waiting for an answer that was dropped. The device's `LinkRelaySocket` ends on a `close` event, a failed send, or the link leaving `online`.
- Free: not counted against the per-device limit (`browser_relay_start`/`_stop` are free commands, the tunnel only carries frames; `quota-commands.ts` header). An older host answers `unsupported` to `open`, which the Preview reports as a failed start. Pinned by `host-services.test.ts` ("agent browsing tunnel"), `devices.test.ts` ("agent browsing's tunnel") and `e2e/preview-agent-remote.e2e.ts`.

### Link loss: a tab never loses the user's answer
- `RemoteSidecar.sendSideChannel` throws `remote_offline` for an `extension_ui_response` while the link is down. Otherwise it returns its delivery (sent once a pending `tab.open` re-attach finished), which rejects with `remote_offline` when the link drops under it or with the host's error when the host refuses it.
- `routeSideChannel` and `EXTENSION_UI_RESPOND` await it, so the pool keeps the request route, the IPC call rejects, and the card or sign-in prompt stays open with an error toast.
- Replies to the host's tool/URI calls are queued and sent once the host tab re-attaches. A `tab.close` that could not be sent goes to `PendingTabCloses` (kept per host link in `devices.ts`, sent when the link is back).
- A remote tab's own link statuses (`starting` with `reconnecting` on link loss, `starting` on reconnect; `statusFromLink`) never drop its open asks in the pool, so a reload still gets the card back. A status the host reports (its omp exited or restarted, or its refusal of the re-attach's `tab.open`/`tab.start` over a live link) does.
- Re-attach brings what changed while the link was down. Every `tab.open` of a tab the host still holds re-sends the asks its omp has open (the `openAsks` tab event; `LocalHostServices` keeps each ask's body until the device answers it or omp withdraws it). The pool replaces the tab's open set with that list:
  - a card whose ask is gone (omp restarted or withdrew it) closes through a synthesized `cancel`;
  - each open ask is forwarded again, since the reconnect's `starting` cleared the page (`pushTabExtensionUiRequest` never doubles a card still up);
  - an ask the tab already held goes out marked `resent` (`IpcExtensionUiPayload`), so the OS "needs you" notification is not repeated; an ask raised while the link was down notifies as new;
  - an ask whose answer is still on its way (`routeSideChannel`) is left as it is.
- **Host tool calls and URI reads the hosted omp waits on come back too**, because stock's `RpcHostToolBridge` has no timeout and a call that reaches no connection would wait forever. `LocalHostServices` keeps each `hostToolCall`/`hostUriRequest` (`HostTab.hostCalls`) until the device's `host_tool_result`/`host_uri_result`, the omp's `host_tool_cancel`/`host_uri_cancel` frame, or a non-ready status (the process took them). A `tab.open` re-sends the ones no connection was handed; a relaunched device's (it adopts the tab under a new rtab, `#adopt`) gets every one, since its last process took the calls it held. A call a live device already has is not sent twice on a lost link, so no tool runs twice. Pinned by `host-services.test.ts` ("re-sends the host tool calls").
  - **A re-sent control call runs at most once.** The relaunched device may have carried a call out before it died and never answered it.
    - Every control-tool call that changes something (`mutates` in `agent-control/service.ts`: open, send, answer, stop, merge, `ompdesk_app`, schedule other than list, Autopilot other than status) is recorded in `<userData>/agent-control-calls.json` (`call-journal.ts`, atomic) under the caller's device, session file and the host call's id (stable across a relaunch, unlike tab ids): `begin` before the effect, `note` for each tab an open makes as it opens, `finish` with the result, `acknowledge` once the host took the result (a paired host's tab: `RemoteSidecar` emits `hostReplyDelivered` when `tab.sideChannel` returned, wired as `SidecarPool.hostReplyDelivered`; a local omp's at once, it never re-sends).
    - Only acknowledged records are forgotten (after 3 days, then oldest past 500): a host waits on a call with no time limit and may re-send it days later, so a pending or unacknowledged one stays. The same call made again gets the recorded result.
    - One left pending by a crash is reconciled, never run again (`#reconcile`): an open answers the sessions it made (by the noted tab ids through `formerIds`, else the caller's child opened for the brief's task), a schedule create answers the `[agent]` schedule of that name, and anything not found answers "its outcome is unknown after OMPdesk restarted" as an error.
    - **Fail closed**: the host marks a call it re-sends after an earlier connection was handed it (`HostToolCallRequest.resent`; a call made while the device was away is unmarked), and a marked call this computer has no record of is reconciled the same way instead of run. An older host marks nothing, so its re-sends count as new.
    - Pinned by the relaunch cases of `service.test.ts` (died after or before the effect; unacknowledged kept past 3 days and 500 calls; a re-sent call with no record never run) and "re-sends the host tool calls" in `host-services.test.ts` (only a call handed before is marked).
- `e2e/remote-resume.e2e.ts` cuts the link through a relay (`linkProxy` in `remote-harness.ts`) to cover both: the card comes back, and after the host's omp restarted none stays, not even after a reload.
- **A re-attach keeps the page**. Every host status names the omp process it comes from (`TabStatusArg.omp`, a new id each time the host's tab starts or restarts one, `HostTab.omp`). When the link is back, `RemoteSidecar` reports `starting` with `reconnecting: true` while it has seen an omp; the page (`use-rpc-events.ts` `handleStatus`) then keeps transcript rows (the same elements), draft, cards and state, and on the host's re-sent `ready` runs one `hydrateTabSession` (the web page's resync merge: state, transcript tail, queue, subagents, goal, plan; asks come back through `openAsks`) instead of the boot check plus a fresh load. A host that no longer held the tab (`attached: false`), re-sends another omp id, or names none (an older host) makes `RemoteSidecar` report a plain `starting` first, so the page starts over as for any new omp.
  - The reader's place holds: a commit that changes rows in view while the reader is away from the live edge holds the topmost unchanged row fully in view until those rows are measured (`content-anchor.ts`; ChatStream's measurement microtask and hold loop; rows compared by content, since a rebuild hands a split reply's rows new objects; a gesture lets go), because TanStack compensates only rows entirely above the fold and a re-read can relabel prompts on screen (`labelPromptOrigins`).
  - Pinned by "a re-attach after a lost link" in `remote-sidecar.test.ts`, the omp-id case of `host-services.test.ts`, the re-attach case of `use-rpc-events.test.tsx`, `content-anchor.test.ts` and the catch-up test of `e2e/remote-resume.e2e.ts` (no blank, no row mounted again).
- **A re-attach keeps the host's turn, a restarted omp's too**. The host sends its reading of the turn (`run`, `TabRunArg`) just before its status; `RemoteSidecar` holds it while re-attaching and hands it to the pool (`hostRun`) after the plain `starting` it reports for another omp, then the host's status, because handed over first the pool would read that `starting` as a link blip (`runAcrossLink`) and drop the run. The older-host fallback stays (`sidecar-pool.ts`: a re-attach with no `run` frame reads the run as over; the link protocol version did not change with it). Pinned by "a re-attach that finds the host's omp restarted" in `sidecar-pool.test.ts`.
- **A disconnect notice waits out a grace**. One rule, one constant, `LINK_NOTICE_GRACE_MS` = 3 s (`src/shared/link-notice.ts`): a surface that tells the person the link to the computer is down shows only once it has stayed down that long, never before the device list has loaded, and it stays for as long as the outage does. The web page retries at once (then 0.25, 0.5, 1 s, then every second) and the desktop client after `RECONNECT_MIN_MS` (1 s), so one routine drop says nothing.
- **The notice is the title bar's own status, never a layer over the window**. After the grace the bar's status turns to the `offline` tone (`TitleBar` `StatusPill`: a warning badge with `WifiOff`, `data-tone="offline"`; on a phone only the glyph, the words stay for the screen reader and the tooltip): "Reconnecting to your computer…" / "Connecting to your computer…" for a phone page's own link (`web/link-status.ts` `useWebLinkLost`, counted from when the page first saw it down; also on a destination page's bar, `WebLinkStatus`), "Reconnecting to {name}…" for a remote tab's host (`useHostLinkLost` in `stores/remote.ts`, counted from when this window first saw the host not online, `downSince` set by `apply`; a tab opened in a long outage shows it at once). It sits in the bar's flow, so it covers nothing; the title gives way.
  - Before the grace a remote tab reads the hollow `pending` "Reconnecting" (its own state, never the session's red `error`; it only waits for the device list). A removed host (`remote.tab.removed`, `RemoteTabBanner`) is a final fact and shows at once; an unpaired phone moves to `/pair` at once. The device chip's dot and screen-reader state, the sidebar's "Offline" row and Settings' `HostScoped` notice follow the link (each replaces content that cannot be shown while the host is away).
- Pinned by `DeviceChip.test.tsx` (nothing before the list or inside the grace, staying after it, no banner of its own, late-opened tab at once, removed host at once), `web/link-status.test.tsx` (phone grace, connecting, late mount, nothing on the desktop) and `e2e/phone-reconnect.e2e.ts` (healed drops show nothing and keep transcript, scroll and draft; a long one shows only the bar's status, covering no header control or the work strip at 390 and 412 px).

### Link loss: what the person sends waits (the outbox)
- **The bot's order (2 Nov 2026): a message typed while the link is down, for any length of time, is kept and sent once, in order, when the link is back**. It holds for a paired phone's page and for a desktop window's tab on a paired host alike; a tab on this computer never waits (no link).
- **What waits**: a plain message (prompt, steer or follow-up) and an answer to a question card. A slash command, a `!`/`$` line or a `->` queue list needs the computer's answer now: it stays in the field with a toast (`outbox.messagesOnly`).
- **Where**: `stores/outbox.ts`, one list in `localStorage` (`omp.outbox.v1`) shared by every window and page of the origin (`storage` events), so it outlives a reload and iOS killing the page. An item is keyed by the session it goes to (`outboxSession`: host device + session id), not the tab: a restarted computer gives its tabs new ids. A try cut off by a reload comes back `held` and `tried`.
- **Shown**: `ComposerOutbox`, one 36 px row at the top of the composer box like the paused queue: "Will send when connected", one chip per item oldest first, each with edit (back into the field, ahead of any draft) and cancel (an answer's cancel puts its card up again); a refused one says why with retry, and holds back the ones after it. While its link is down the tab's Send stays enabled (`useSendsHeld` in `InputArea`; a remote tab's `error` status reads as ready for it). A held answer closes its card, and `pushTabExtensionUiRequest` keeps it closed when the computer re-sends the ask (`answerHeld`).
- **Delivery** (`lib/outbox-delivery.ts`, installed by `App`): on the page's link opening, a host going online, a tab becoming ready or a new item, each session's items go one at a time to the live tab that holds the session. A message goes as `prompt` with `streamingBehavior` (the composer's steer/follow-up choice): the host decides at arrival whether it starts a turn or joins the running one, whatever happened meanwhile. Every try carries the item's id as `deliveryId`; the computer running the tab hands it to omp once (`main/delivery-ledger.ts`, wired in `ipc.ts` `dispatchRpcCommand` for its own tabs and in `LocalHostServices.#command` for a device's; a device passes it on), so a try whose answer the link lost and its retry never make two messages. Not-now answers (`remote_offline`, `rpc_delivery_unknown`, not ready) wait for the next change or 2 s; any other refusal marks the item failed.
- **An answer goes only where it was asked, only while asked**: never to another tab's omp (a restarted computer: toast `outbox.answerClosed`), only while `openRequests` still lists a blocking ask (three misses 2 s apart, so a reconnect's re-sent asks can arrive; then the same toast), and `already_answered` says it was answered on another device (`outbox.answerElsewhere`). Never dropped silently.
- Pinned by `lib/outbox-delivery.test.ts` (order, ids, reload, retry with the same id, a refusal holding the rest, closed and open questions), `main/delivery-ledger.test.ts`, `e2e/phone-offline-send.e2e.ts` (390 px WebKit and Chromium behind the fake serve: a 60 s outage, two messages and a cancelled one, a reload mid-outage, each arrives once in order) and `e2e/remote-offline-send.e2e.ts` (the same through `linkProxy` for a desktop viewing a host's tab, its own local tab sending at once meanwhile).

### A host tab never waits silently, and never fails for taking long
- Whatever the host does, a tab on it says what it waits for.
- **No deadline of the device's own** (the owner's rule: a fixed limit may never end or fail work). The tab mirrors what the host reports of its start: `starting`, `queued` (the host's start queue, or its previous omp still exiting; title bar "Waiting to start"), `slow` (the host's omp has not answered after `START_SLOW_MS`; the amber `SidecarBanner` with its stderr tail and Restart), then `ready`. A link request the host leaves unanswered (the link's own timeout, `tab.open`'s 30 s) reads `starting` with `slow` and `remote.tabUnanswered` ("{device} has not answered yet. Waiting for it; nothing was stopped."), logs `unanswered`, and the bring-up asks again (`tab.start` is idempotent). A host out of reach reads `starting` with `reconnecting` and `remote.offline` (`#markOffline`), never `error`: the page keeps what it shows and the tab comes back with the link. `error` comes only from the host's own answer (its omp exited, a refusal over a live link). Each stays a link-derived status where the device derived it (`statusFromLink`), so open asks keep their routes.
- **A tap on ☰ right after a phone page loads opens the drawer**: the first tab list moving `activeTabId` from none to a tab must not close it, so `SidebarDrawer`'s leave-the-list rule, `leftActiveSession`, counts only a pick from one listed, non-ghost tab to another; and `App.tsx` wraps the surface in `FocusedRuntimeProvider` (one element type, null runtime until the first tab), so the first tab never remounts the app and `useDrawerSidebarSync` never puts the drawer away. Pinned by `SidebarDrawer.test.ts` and `tab-runtime-provider.test.tsx`.
- **Restart keeps the session**: `SIDECAR_RESTART` restarts on the session file the caller names, else on the tab's own (`SidecarPool.tabTarget().sessionFile`), never a fresh session; the banner's Restart names none.
- **Log**: each step goes to `gui-runtime.jsonl` as source `remote-tab` (`open` {attached, viewing}, `start`, `ready`, `unanswered` {step, error}, `failed` {step, error}), with the device, rtab and `ms` since the bring-up began; Copy diagnostics carries it.
- **The banner says the reason, on every tab**: a failed, exited or restarting status's `message` and `restart` ride the tab's listing (`IpcTabInfo.message`/`restart`, kept on the pool entry as `failure`), so TAB_STATUS and GET_TABS reach every window's tab, shown or not; `applyTabFailure` (`stores/tabs.ts`) is the one writer of a tab's `sidecarError` from main's status, only when it changed (a later push keeps a dismissed banner closed), and clears it when the tab comes back up. The visible-only sidecar status and the boot read of the active tab's status do not set it.
- **The page never waits on a lost reply**: `WsConnection.#invoke` answers a result JSON cannot carry with an error `res`. A first transcript read that fails while nothing is loaded sets `pageError` (`commitHydration`): the transcript shows the failure with Retry (a fresh hydration), never an empty session's starters.
- Pinned by `remote-sidecar.test.ts` ("a start that takes long waits with the host, never an error"; "reads an unreachable host as reconnecting"), `ws-router.test.ts`, `use-rpc-events.test.tsx` ("a failed first transcript read") and `e2e/mobile-remote-session.e2e.ts` (phone → this computer → host with Windows-shaped paths, across drops, relaunches and a slow start: amber banner with Restart, no `failed` log line). `OMP_GUI_REMOTE_HOST_OUT=<built out/>` runs that host on another build (version skew).

### Host windows see the device's tabs
- **The user's rule (19 Oct 2026): the person at the host sees and can work in every session running on that computer, including one a paired device started** (e.g. with `ompdesk_session_open {device}`).
- Why: a hosted tab lives in `LocalHostServices`, not in the host's pool, so without this the host's sidebar has no tab for its session, an agent-opened session folds away as a finished helper (`foldedRootOf` → `familyChildFor` `finished` → `isShownOpened` false), and opening it spawns or switches a second omp onto the file.
- List: each tab `LocalHostServices` runs for a device is a source of this computer's session summaries (`summarySources`: path, id, title, cwd, kind, status, asks, subagents, `openFor` the device's name; panels-sidebar.md › A row is live without a click), pushed as `SESSION_SUMMARIES_CHANGED` to every window and page (renderer `stores/hosted-sessions.ts`, synced in App, read whole on a web page's resync). The sidebar counts each summary with `openFor` as held by a tab (never folded, never archived out, its project expanded), gives it a live row before the index lists it, and takes its state from that summary like any row.
- Lanes and removed worktrees: one rule for both sides, `isChatSession` (`lib/session-title.ts`): a chat, or a session in that machine's no-project workspace (`~/.omp/work`, where `ompdesk_session_open {device}` without a folder starts one), sits in that machine's Chats section. A paired host's section and a focused tab on that host ask the host's own workspace (`useHostWorkspace` in `layout/sidebar/host-workspace.ts`: `sidecar.defaultWorkspace(device)` → `workspace.default`, its last answer kept in the snapshot cache), so a row never sits among projects on the device and among chats on the host. A session whose worktree was removed leaves the list unless a tab holds it, a paired device's tab here included (`heldByTab`). Pinned by `Sidebar.test.tsx` and `e2e/remote-host-lanes.e2e.ts`.
- Open: opening it views the device's tab. `spawnTabForWindow` (dep `hosted`) asks `viewSession(path)` for a `HostedTabView` (`remote/hosted-view.ts`, a `SidecarLike` over the hosted sidecar) and `SidecarPool.acquireHostedView` makes it the window's tab (`PoolEntry.hostedView`: listed `shared`, so the host decides steer/follow-up; owns the session for F-OWN). It is never in `resumeFacts`, `tabInventory`, the saved layout, `workspaceDirs`, `restartOnNewOmp` or `applyExtensionUpdate`, which are the device tab's. `GET_SESSION_OWNER` answers `{hosted: true}` and `switch_session` refuses `session_owned_elsewhere {hosted: true}`, both routed by the renderer to a tab (`routeToSessionOwner`).
- The view forwards the omp's stream but never `hostToolCall`/`hostUriRequest` (the device answers those), journals a prompt typed here as the host's and relabels a transcript page for the host (`labelForHost`). An ask's first answer, the device's or the window's, wins (`#answer`: the other side gets a `cancel` `answered:<id>`, which the pool marks `answeredElsewhere`, and its later answer fails `already_answered`).
- Lifetime: closing the view only leaves (`CLOSE_TAB` releases the entry; the omp runs on); a viewed tab outlives the device's grace period; the device's close, delete, revoke or the grace's end ends every view first (`VIEW_ENDED_EVENT`: the pool releases the entry and the window's list drops the shared tab, no error tab). A host-side delete of a session a device's tab runs is refused (`session_running`) only while that tab runs a turn or compacts; an idle one closes and its device hears `sessionDeleted` (see Interrupted turns › The host owns the turns).
- Tests: `host-services.test.ts` ("for this computer's own windows"), the hosted-view cases of `sidecar-pool.test.ts` and `tab-spawn.test.ts`, `Sidebar.test.tsx`, and `e2e/remote-host-view.e2e.ts` (device opens on the host → listed once → a view with no second omp → prompts from both sides in the one omp → device closes → view ends with no error tab).

### Devices see the host windows' tabs
- **The other way round (the user's duplicate-tabs bug, 19 Oct 2026): a device opening a session a window of the host already has open never gets a second omp.**
- Attach: `LocalHostServices.#open` asks `localTabs.viewForDevice(path, {deviceId, name}, hostName)` first; `SidecarPool.viewForDevice` hands out a `HostedTabView` of that window's tab (`PoolEntry.deviceViews`; the same view class, its `promptOrigin` the device, its transcript localized for it with `localizePromptOrigins`). The host tab holds it as its sidecar (`HostTab.viewsWindow`: never in `resumeFacts`, `summarySources` (the window's tab is the source), `restartOnNewOmp` or `applyExtensionUpdate`; the window's open asks reach the device as `openAsks`).
- Device side: `tab.open` answers `{attached: true, viewing: true}` (`TabOpenResult.viewing`), so the device starts nothing and its `RemoteSidecar` reports `shared` (event `shared` → the pool re-lists the tab as shared: host decides steer/follow-up, closing it only leaves).
- Asks: the window's tab counts the device in `viewerCount`; the first answer, the device's (`#answerFromDevice`) or a window's (`routeSideChannel`), wins with the same `answered:<id>` cancel and `already_answered` refusal.
- Waits: the window's tab's connection wait and scheduled retry are the host's `TurnResume`'s; the device's view hears both as they change and on every `tab.open` (`awaitingConnection`, `scheduledRetry` with the time left), and its Cancel reaches the host's `TurnResume.cancelWait` for the window's tab (`SidecarPool.onCancelWait`). See Interrupted turns › The host owns the turns.
- Lifetime: the device's close only leaves; the window's close ends every device view first (`#releaseEntry` → `VIEW_ENDED_EVENT` → tab event `viewEnded` → the device's pool releases its tab quietly). The host's own delete of that session tells the device `sessionDeleted` first and closes the view, refused only while the window's tab runs a turn (see Interrupted turns › The host owns the turns); the device's delete is refused while a window here runs it live.
- **Every device views a window's session**: another device's view of a window's tab holds no omp, so `#adopt` never refuses a second device `session_open_in_tab` for it; the same connection under another rtab still is.
- **Every device views another device's tab too**. The host keeps one omp per session file and any number of viewers: its windows (`viewSession`) and every other paired device.
  - `#open` first asks the windows (`viewForDevice`), then the tab here whose own omp runs the file (`#runner`): `#viewTab` makes a `HostedTabView` of it with the opening device as `promptOrigin` (transcripts relabelled by `labelForViewer`), held in the holder's `views`, and the device's tab gets it as its sidecar with `HostTab.viewing` = the holder (`"window"` for a window's tab; one field for both).
  - A view's prompts, moves, Stop and Cancel count on the holder (`#runCommand`, the view's port), its Autopilot target is the holder's run, its replies are charged once (to the holder), and it is never in `resumeFacts`, `hostedSessions`, `liveSessions`, `restartOnNewOmp` or `applyExtensionUpdate`. Asks: `HostTab.answered` keys each party (`device`, `host`, `peer:<id>`), so the first answer of any device or window wins and every other card closes as `answered:<id>`. `#dedupe` never takes a view and its holder (one omp) for two omps on the file. `#adopt` takes over only the device's own tab; this connection under another rtab is still refused `session_open_in_tab` (naming its own tab).
  - Lifetime is the window ↔ device rule: the viewer's close only leaves (the holder's omp runs on); the holder's close ends every view first (`viewEnded`, the viewing device's tab closes quietly, no error tab); a holder whose device drops keeps its tab through the grace while views remain (`#startGrace`).
  - Pinned by "a device opening a session another device's tab runs here" in `host-services.test.ts` and `e2e/remote-device-view-device.e2e.ts` (three apps; the second device dials the host on `::1`, since macOS loopback answers only 127.0.0.1; quick clicks → one shared tab, one omp, the holder's close ends the view).
- Tests: the "device views" cases of `sidecar-pool.test.ts`, "a device opening a session a window of this computer runs" (with "a second device views the same window's session") in `host-services.test.ts`, and the second half of `e2e/remote-host-view.e2e.ts` (host opens first → device views, no new omp → prompts from both in one omp → host closes → device's view ends, no error tab).
- **A refused open never leaves an error tab**. A current host views instead (above); the refusal stays for this connection's own second rtab and for an older host. The host's `session_open_in_tab` names the holder (`TabHolder` `{device, rtab, name}` in `protocol.ts`, on the thrown error and the wire error's `holder`, and in the message for the device's `remote-tab failed` log line; a malformed or missing one from another version is ignored).
  - The device's `RemoteSidecar` emits `shownElsewhere(holder | null)` instead of an `error` status; `SidecarPool.#shownElsewhere` closes the tab and sends its window `TAB_LIST_CHANGED` with `closed` and `shown`: `{tabId}` when the holder is this computer's own tab (by its rtab or a former one; with no holder, from an older host, by the same session file), and the window switches to it; else `{host, holder?}`, and the window toasts that the session is already open on the holder, or on the host when the host named nobody (`tabs.openElsewhere`).
  - Main can answer the window's route to that tab (`false`) before the window applies that list: `focusTab` then reads main's list, and a tab main no longer lists leaves the window quietly (no "Tab … is no longer available" toast); a tab main still lists keeps the switch-failed toast.
  - Pinned by the refusal case of "a relaunched device's reopen" in `host-services.test.ts`, "hands a host's session_open_in_tab refusal" in `remote-sidecar.test.ts`, "closes a tab a paired host refused" in `sidecar-pool.test.ts` and the three refusal cases of `stores/tabs.test.tsx` ("leaves a tab main closed while the window still routed to it quietly").

### One source, every view
- **The user's reports (22 Oct to 8 Nov 2026): a session working on a paired host, in another window or on the phone showed nothing until it was tapped open**. No view derives a row: the computer that runs a session builds its summary (panels-sidebar.md › A row is live without a click) and every view shows that.
- Host: `SessionSummaries` (`src/main/session-summaries.ts`) over its windows' tabs (`SidecarPool.summarySources`) and the tabs it runs for every device (`LocalHostServices.summarySources`). `sessions.summaries {}` answers the whole set at its version (`VersionedSummariesSchema`); each change goes to every connected device as the `host.summaries` event (`SummaryDeltaSchema`: `base`, `version`, changed summaries, removed paths), one per burst (`SUMMARY_DEBOUNCE_MS`). The same change goes to this computer's windows and pages as `SESSION_SUMMARIES_CHANGED` (no device).
- Device: `RemoteDevices` reads `sessions.summaries` as the link comes up, applies a push only on the version it holds and reads the whole set again on any other (`applySummaryChange`; a push lost on the link costs one read, never a stale row), and passes each change on to its windows and pages as `SESSION_SUMMARIES_CHANGED {device}` (`SESSION_SUMMARIES(device)` reads it). The link going down empties that host's set (a row never stays lit for work nobody can see).
- Rows: a host's row reads only the host's summary of its session (`SidebarDevices.tsx` `renderRow`, `remoteFamilyChildFor` for a family child, the folded header, the bot's row), whatever tab this device holds on it: an asleep tab, a tab of another window or none at all reads the same. A phone page showing a paired host's section through this computer reads the same summaries.
- **Mixed versions** (the owner's requirement: a new device on an older host, an older device on a new host, never a crash or a wrong state; no live state is acceptable). A new device asking an older host gets `unsupported` (no handler): it holds no summaries for that host and its rows show no live state, nothing else changes. An older device asking a new host `sessions.live` gets `unsupported` (this host no longer serves it), and it drops the unknown `host.summaries` event. Pinned by "answers an older device's `sessions.live` as an unknown method" in `host-services.test.ts` and the older-host case of `devices.test.ts`.
- **An asleep tab here never keeps a host's finished session**: a tab restored asleep on a host session whose OMPdesk worktree the host lists gone does not list the row, and main closes it as the link comes up or the host's list changes, as a deleted session's tab closes; a shown one the host refuses `session_folder_missing` there closes too. The whole rule is settings-layout-look.md › Sidebar projects ("A finished worktree's session never comes back through a tab nobody uses").
- Pinned by `session-summaries.test.ts`, the summaries cases of `host-services.test.ts` and `devices.test.ts` (real sockets: read on link up, delta, gap read whole, link down empties), `e2e/remote-resume.e2e.ts` ("a host's session at work lights the device's row with no tap") and `e2e/session-summary-matrix.e2e.ts` (window, paired computer and phone page).

### A session the host deletes leaves every paired computer at once
- **The owner's report (8 Nov 2026): the host's project was deleted and no saved session was left in its folder, yet a paired computer's window still listed an asleep ("not started") tab of a deleted session.** A `tab.open` refusal (`session_deleted`) reaches only a tab that is opened and an asleep tab never asks, so the host announces deletes to every device.
- Host: the notice `deleteSession` runs once the file is gone (`LocalHostServices.closeSessionTabs`) pushes `host.sessionsDeleted {paths}` to every connected device, whether or not it holds a tab on the session, besides the `sessionDeleted` tab event to the rtabs it held. `sessions.deleted {paths}` answers which of the given session paths are tombstoned (`deletedSessions().has`), for a device that was off the link at the delete. No timer, no polling.
- Device: `RemoteDevices` hears the push (`onHostSessionsDeleted`) and, as a link comes up, `index.ts` asks `deletedOnHost(host, sidecarPool.deviceSessionFiles(host))` (an older host answers `unsupported`: ignored). Both end in `SidecarPool.closeHostDeletedSessions(host, paths)`: it records the tombstones under the host's id and closes every tab here on those sessions (asleep, ready or running: a running one stops as closing a tab does) through `#closeFinished`, the path `sessionDeleted` uses, so the windows' strips, a phone page's tab list and the saved layout drop it. One line `tab-layout` "closed tabs of sessions their host deleted" in the runtime log.
- Pinned by "announces a session deleted here to every connected device" in `host-services.test.ts`, "hears the sessions the host deletes" and "ignores a host that does not know `sessions.deleted`" in `devices.test.ts` (real sockets) and "closes every tab a paired host's deleted sessions leave here" in `sidecar-pool.test.ts`.
