## Remote devices

### Tailscale only, transport, routing
- Code: `src/main/remote/`. OMPdesk on a host (B) runs tabs for client computers (A). **The user's rule (19 Oct 2026): computers share over Tailscale only, with no pairing code** — like Mobile web, any computer signed in to an allowed Tailscale account on the same tailnet sees this computer and can use it. No LAN listener, no UDP discovery, no code field; computers without Tailscale do not share (no fallback).
- Host: `RemoteHost` (`host-server.ts`) listens on this computer's tailnet addresses only (`status --json` `TailscaleIPs`, `bindHosts` in `devices.ts`; never 0.0.0.0, `::` or a LAN address), rebinding every 15 s and on a status change. Port: the first free one of `remotePortCandidates()` (`OMP_GUI_REMOTE_PORT`, default 47821, and its four successors, `REMOTE_PORT_SPAN`; for the default port then `FALLBACK_REMOTE_PORTS`, one port in each of five other thousand-blocks below the dynamic range) on the address devices dial (its IPv4 tailnet address), then the same port on its other addresses where they take it (one that refuses is logged `listen-skipped` and left out, never a reason to listen nowhere). A port taken (EADDRINUSE) or reserved by the system (EACCES: Windows reserves 100-port blocks for Hyper-V, WSL and Docker, `netsh int ipv4 show excludedportrange`) is skipped, and the `port` log line names each skipped port with its code. Why (24 Oct 2026): a Windows PC answered connection refused on all five ports for a day while it reached this Mac fine the other way, and the Settings line said the ports were in use. Every candidate unavailable: it listens nowhere and `RemoteHostState.listenError` is `{code: "port_in_use", ports}` (Settings lists them), since a device only probes that list. A device probes the same list, its last good port first, dialing the ports `DIAL_STAGGER_MS` (250 ms) apart and the next at once when one fails (`firstToConnect` in client.ts, used by the link's attempts and the tailnet probe `probeAny`): a port that answers nothing (a firewall dropping it, a stale remembered port) costs a quarter second, never its timeout, and never hides a later port that answers; the earliest port that connects in time wins, and the rest are closed. A computer that answers on no port fails after the last dial's timeout (about 7 s for ten ports). Pinned by the listening and "one of them silent" cases of `transport.test.ts` (a remembered first port that answers nothing, then the host's port) and the candidate case of `crypto.test.ts`.
- Gate, per connection (`RemoteDevices.#gate`): the peer's address must be a tailnet address (100.64.0.0/10, fd7a:115c:a1e0::/48; `isTailnetAddress`) else `not_tailnet`; `tailscale whois` (`Tailnet`, `src/main/tailscale/tailnet.ts`, answers cached 60 s, status 3 s; works whether or not Mobile web is on) must name a node with a login (`no_identity`) on the allowed list (`not_allowed`; Mobile web's `mobileWeb.allowedUsers`, one list for both, default this computer's login) that Mobile web's blocks (`WebBlocks`, by node) do not hold (`blocked`). "Approve new devices on this computer" (Mobile web's pref `mobileWeb.confirmNewDevices`, default off: one switch for phones and computers, `ConfirmNewDevicesRow`, shown in sharing's section while sharing is on and in Mobile web's otherwise) asks through Mobile web's `PairingConfirmations` (`kind: "computer"`, no access tiers) before a new device is recorded (`declined`). Refusals travel as `auth-fail`/probe `error` codes (`REFUSAL_CODES`, `protocol.ts`) and reach the renderer as `remote_<code>`.
- Trust: handshake v2 (`HANDSHAKE_VERSION` 2; a v1 code-pairing peer gets `protocol`). Each side sends its static key; the session keys mix DH(eA,eB) ‖ DH(sA,eB) ‖ DH(eA,sB) and run AES-256-GCM frames over TCP, so only the pinned keys read the link. The host pins TOFU per Tailscale node (`PeerInfo.nodeId`/`login`, `#bindDevice`): a node holds one device and one key; another device id or key from that node, or that device from another node, is `key_mismatch` until the person removes the record (so a new key never earns a fresh PeerQuota record). The client pins the host's key per node (`PairedHost.nodeId`, `connectFirst`); a changed key is `key_mismatch`.
- **A paired device's tabs here never get this computer's control socket** (`src/main/control-socket`, see `.omp/rules/control-tools.md` › Control socket): `LocalHostServices` spawns them with an `origin`, so `controlEnvFor(true)` gives their omp and their terminals (`terminal.request`) only `OMPDESK_CONTROL_OFF=1` (main keeps the socket's address out of `process.env`), and the `ompdesk` CLI refuses there with exit 3: a device's agent acts on this host only through its link, with its grants and `PeerQuota`, never as an outside caller with this computer's front window. Residual: such a session runs as this host's user and could read the token file deliberately, as it could read any of the user's files. Pinned by `sidecar-factory.test.ts`.
- Client: Settings watches the tailnet's computers (`remote:watch-tailnet`, every 5 s while shown; `TailnetComputer`): each online non-phone node of `status --json` is probed on the candidate ports (`probe` → `probe-ok {deviceId, name}` or the refusal; this computer itself is skipped). Connect (`remote:connect {nodeId}`) pins and links it. Connect on a host already linked makes a new client and moves the host's open tabs onto it (`RemoteSidecar.relink`): left on the closed client they read "the device running this session is offline" while the host showed online (22 Oct 2026; pinned by "connecting again to a host already paired" in `devices.test.ts`). A `RemoteClient` dials only what `#hostAddresses` resolves on each attempt: the node's current tailnet address on the port it answered on in this run, then every candidate port. Stored addresses and ports are never dialed (a reboot moves the port; code pairing stored LAN addresses and old ephemeral ports, a real case that left a Mac unable to reconnect).
- **A link that went silent or dropped comes back on a signal, not on a timer** (20 Oct 2026, the Windows PC's report: "disconnected" and slow to return; its log had no line for any link event). A dead path (Wi-Fi off, the peer asleep, a NAT dropping the flow) is otherwise noticed only by the ping timer (`PING_INTERVAL_MS` 10 s, `DEAD_AFTER_MS` 30 s: 29–40 s) and then retried 1, 2, 4, 8, 16, 30 s apart. `RemoteClient.wake(trigger)` (`WakeTrigger`: `resume`, `unlock`, `online`, `tailnet`, `focus`, `peer`) is called by `RemoteDevices.wake` from `index.ts` for powerMonitor `resume` and `unlock-screen`, the `ConnectivityMonitor` going online, and `browser-window-focus`, and by the tailnet poll when a known host's node was offline in the last poll and is online now or Tailscale just became ready (`#wakeReturnedHosts`, `#poll`). Offline or waiting out a backoff: the backoff starts over at 1 s and an attempt runs now (`connect()` still retries now without resetting it). Online: `Link.check(WAKE_CHECK_MS)` pings and drops the link (`dead`) when no frame arrives within 3 s, then the client attempts at once; a frame in time leaves it alone. An attempt already running is the one trying now, except on `peer`: this computer's own host accepted a link from that host's computer (`RemoteHostOptions.peerOpened`), so it is up, and a dial that has waited on an address for `STALE_STEP_MS` (1 s; a younger one is left to finish, at once or when it turns 1 s old) is ended and run again. A live host answers in tens of ms, so two computers that use each other as hosts and reconnect at once never end each other's handshakes (pinned by "two computers that use each other as hosts" in `devices.test.ts`, which saw one ended handshake each run without the 1 s gate). Measured on this Mac after the Windows host's update restart: its five candidate ports each timed out (5 s), so the link came back 28 s after the drop while the host had connected to this Mac 16 s in. `DEAD_AFTER_MS` and the backoff constants stay as the guard for the case no signal covers. Measured on real sockets through a relay that drops for 20 s (`RemoteDevices` on both sides): restored → online 10.0 s before (the 30 s dead timer: offline at 29.0 s, then the 1 s backoff), 3.0 s with the wake at the restore; first `offline` 29.0 s after the cut before, 23.0 s after (the wake's check, when the signal arrives at the restore).
- **A host whose app is restarting is dialed every second, not on a growing backoff** (20 Oct 2026: the Windows host auto-updated 5 times in 24 h, 21 s to app-ready and 26 s to the bridge each time, and the Mac's client sat in 1, 3, 7, 15, 31 s backoff). A dial that ends `ECONNREFUSED`/`ECONNRESET` on every address (`RemoteError.refused`, set in `dial`) means the computer answered and nothing listens: one cheap round trip, never a timeout or a missing route. `#scheduleRetry(refused)` then keeps the delay at `RECONNECT_MIN_MS` and the backoff at its first step, for `REFUSED_RETRY_WINDOW_MS` (60 s, over twice the longest update restart in the log) from the loss of the link; after that, and for any timeout, unknown host or refusal code, the backoff grows as before. The Windows firewall of the host does not turn this into a timeout (read on that PC, not on a Mac client: `Tailscale-In` allows the tailnet address on Private networks and the Tailscale adapter is Private). Measured with the relay refusing for 20 s: restored → online 11.0 s before, 0.2 s after. No quit-time event from the host: a crash, a kill and a shutdown would send none, while a refusal reaches the client whenever the computer is up.
- **Log** (`gui-runtime.jsonl`, source `remote-link`, transitions only apart from the host's `traffic` summary below, never a line per ping, no address, key or token): on the client `down` {deviceId, name, reason: `closed` | `dead` | `protocol` | `local` (`Link.closeReason`) or the failed attempt's code (`unreachable`, `key_mismatch`, … when a launch never got online), wasOnlineMs}, `attempt` {deviceId, n, delayMs, trigger: `start` | `connect` | `backoff` | a wake trigger} (backoff attempts past the 6th, 30 s apart, are not written) and `up` {deviceId, outageMs, attempts, appVersion: the host's build}; on the host `open` {deviceId, ms: accept to authenticated, appVersion: the device's build, slim: the slim frames it reads, `events,progress,autopilot,ends,reads,tools,fields` or `none`} and `closed` {deviceId, reason, ms: how long it was open} per device connection (`RemoteHostOptions.logLink`, `RemoteClientOptions.log`, both from `RemoteDevicesDeps.logLink`). Pinned by `transport.test.ts` ("a link that dropped or went silent"), `wire.test.ts` (`Link.check`, `closeReason`) and `devices.test.ts` ("a host link after the computer wakes").
- **What the link carries is logged, and a harness measures it** (the user's report, 20 Oct 2026: a constant 170–350 KB/s host → Mac while the Mac showed nothing; the samples were taken while this session's own subagents streamed over the same link, so they proved nothing about idle). `remote-link` `traffic` {deviceId, ms, tx, rx, top: JSON text of [{kind, frames, bytes} ×5], events: JSON text of {omp event type: count ×5}} (text because the runtime log keeps only primitive details: until 21 Oct 2026 both were dropped from every line): the host writes it once a minute for each device connection that moved at least `TRAFFIC_LOG_MIN_BYTES` (256 KiB; an idle link sends about 1 KiB a minute in pings) and once more when such a connection closes. `kind` is `tx`/`rx` plus the frame (`evt tab.event events`, `evt tab.event subagentFrame/subagent_progress`, `req tab.command/get_jobs` (a tab command with its RPC command's type: a link moved 3 MB a minute of `tab.command` answers on 21 Oct 2026 and the line could not say which), `res sessions.list` sized under its request's method, `ping`), in wire bytes (frame header, nonce and tag included); `events` counts the omp events inside `events` batches and `eventBytes` weighs each type by its own JSON (a batch's wire bytes are one figure for all its types, so a busy minute could not say whether its bytes were many small updates or a few whole messages); `wholeEnds` (only when any) weighs by role the messages of an `agent_end` that crossed whole instead of as a `~sent` reference (two computers on 0.57.0 still sent a 49 KB `agent_end` the line could not explain). Never a payload, address or key. Code: `Link.onTraffic` (`wire.ts`) feeds a `LinkTraffic` per connection (`link-traffic.ts`, at most 128 kinds), started in `RemoteHost.#auth`. Pinned by `link-traffic.test.ts`, "the host's traffic line" in `transport.test.ts` (a minute passes: one line for a busy link, none for a link that only pinged, one on close inside the minute) and the real-pipeline case of `link-traffic-report.test.ts`.

The harness counts every `Link.send` itself, independent of the production counter. Its rig is `link-traffic-test-rig.ts`; a subagent's progress cases sit in `link-traffic-progress.test.ts` (subscription off and `progress`) and `link-traffic-progress-events.test.ts` (`events`), so their 3 s subagent runs go side by side (the one file was the Windows platform job's longest, 40 s; split, 13 s at most here).
  - An idle open tab sends 17.6 B/s (ping and pong only, no `tab.event`, 120 s). A turn waiting 30 s on a silent bash tool sends one 18 KB burst at its start and nothing after (640 B/s over the 30 s). The link is quiet when nothing runs, so streaming was not changed (the requester's rule: only if idle is clearly above near-zero).
  - Running work is what costs. Before `slimEvents` the host forwarded each stock `message_update` whole, twice (`message` and `assistantMessageEvent.partial`; `message-update-slim.ts` slimmed it only on the local pool's way to a window), so a reply of K tokens cost O(K²): 450 tokens (150 thinking + 300 text) 1.88 MB at 324 KB/s, 900 tokens 6.66 MB at 573 KB/s, 1800 tokens 24.9 MB at 1.07 MB/s (twice the tokens, 3.5–3.7 times the bytes). An older device still gets that.
  - A task tool's subagent for 20 s: 21 KB/s with the `off` subscription (the parent's `tool_execution_update` carries every `AgentProgress` snapshot in `details.progress`, about 3 KB each at most every 150 ms), 49 KB/s with `progress` (the same snapshots again as `subagent_progress`), 284 KB/s with `events` (WorkMap open: each `subagent_event` `message_update` carries the subagent's whole message twice). The 170–350 KB/s of the report is that order.
  - **Done for `message_update` (20 Oct 2026, the same harness, `link-events.ts`)**: the device's hello carries `slimEvents: true` (`ClientHello`, `HostConnection.slim.events`; every capability is read from the hello in one place, `slimOf` in `protocol.ts`, a later one counting only with those it builds on); for such a connection the host sends `events` as the local pool sends a window's (`createMessageUpdateSlimmer`: the first update of each message whole, the rest reduced) and each subagent `message_update` through `slimSubagentFrame`, and drops a `usage` that repeats the last one of its message (`createLinkEventEncoder`, one per tab and connection, in `LocalHostServices.#emit`). The device (`RemoteSidecar.handleEvent`, `createLinkEventDecoder`) puts the usage back and rebuilds the text/thinking blocks and the tool call from the deltas, so the pool's per-window slimmer still gives a window that attaches mid-message the snapshot it needs and every window receives what a local tab's would; a whole update (an older host) passes through. **`PROTOCOL_VERSION` stays 1 on purpose**: host and device must agree on it exactly (`protocol` refusal), so a bump would lock every older device out. An older device sends no `slimEvents` and gets whole frames (pinned by `link-traffic-report.test.ts`, which strips the field from the hello); an older host ignores it. Never make the capability required, and never send a slim frame to a connection that did not ask.

Subagent `events` subscription: `subagent_event/message_update` 225.5 → 16.4 KB/s (13.7x); the whole case 284 → 74.7 KB/s (3.8x), because the rest was never `message_update`: `subagent_progress` 27.7 KB/s, the parent's `tool_execution_update` progress copies 19.3 KB/s and one `tab.event` envelope per subagent frame (1,686 in 20 s, 9.1 KB/s). `off` (20.6 KB/s) and `progress` (49.3 KB/s) are unchanged.
  - **The page asks for a brief `get_state`** (21 Oct 2026): v0.52.2's per-command traffic line showed a paired device viewing one host tab got 3 MB a minute of `tab.command/get_state` answers, ~750 KB each: stock's `get_state` carries `systemPrompt` and every tool's wire schema (`dumpTools`), and the page asks for it every 15 s (the liveness probe) and at every turn's re-sync, reading neither. Every renderer `get_state`, and the OMPdesk control tools' reads of a session's state (a paired device's tab answers over the link), sends `brief: true`, and main's local handler (`briefState`, `local/composer.ts`) leaves the two out; a call without it (e2e specs, agent tools) gets the whole state. A host older than this ignores the flag. Pinned by `local/composer.test.ts`.
  - **A transcript page starts at the run it belongs to, not at the last typed prompt** (`transcriptRunStart`, `resources/gui-bridge/transcript-page.ts`): a page may also open right after an assistant message that stopped on anything but a tool call. Goal and Autopilot runs continue with custom messages, never a typed prompt, so the page snapped back to a prompt hours old: one tail page of this repository's Autopilot session was 1754 messages and 4.6 MB on every hydrate and every reconnect of a paired device (21 Oct 2026; 215 messages, 464 KB after). Pinned by `local/sessions.test.ts`. A page read from the end also weighs at most `BACKWARD_PAGE_BUDGET` (256 K JSON characters; `local/sessions.ts`): one heavier is read again with half as many messages, down to 20, and the rest comes as older pages on scroll; a single run longer than the budget comes whole, since the bridge snaps every shorter read back to its start (a read that starts where the last one did ends the loop) (the 200 messages a window asks for were 961 KB on this repository's Autopilot session's tail, sent to a phone on every open, 22 Oct 2026). A page also leaves out each thinking block's `thinkingSignature` (`transcriptPageMessages`; about a fifth of that page, read by stock from the journal, never from a page), and the renderer's live-to-page match ignores it (`message-identity.ts`).
  - **The model catalog leaves stock's `compat` block behind** (22 Oct 2026, the v0.53.0 traffic line: one `get_providers` to a paired device was 1.73 MB, `get_model_roles` 882 KB): `catalogSnapshot` (`resources/gui-bridge/settings.ts`, behind `providers`, `models_catalog` and `model_catalog_update`) sends each model without `compat` (the provider API's request quirks, about 1.9 KB of a 2.5 KB model on OpenAI's catalog; nothing in OMPdesk reads it). `get_model_roles` repeated each role's candidate list (most roles take the same chat models): the RPC client asks with `compact: true`, the bridge's `model_roles` then names each candidate once (`candidateModels`) and each role's candidates as indexes, and the client expands it back (`compactModelRoles`/`expandModelRoles` in `model-role-contracts.ts`; 78 KB → 19 KB on OpenAI's catalog); an older host ignores the flag and its plain answer passes through, an older device never asks. Pinned by `bridge-catalog-stock.test.ts` (installed omp: no model carries `compat`, under 1 KB a model, the fields the windows read stay; the compact roles expand to exactly the plain answer at under a third of its size) and `src/shared/model-roles-wire.test.ts`.
  - **Live frames carry no request bookkeeping** (`withoutFrameBookkeeping`, `src/main/frame-bookkeeping.ts`, applied as the sidecar takes each frame): stock records `inputTransformations`, `requestControls` and `contextSnapshot` on every assistant message, and in a long Anthropic session `inputTransformations` lists every earlier thinking block the API dropped (21 KB of a 26 KB message on 21 Oct 2026). `message_end`, `turn_end`, every message of `agent_end` and a `message_update`'s `partial` leave without them, to each window and over the link; nothing in main or the renderer reads them (transcript pages already drop them). A `turn_end` leaves with its type alone: its `message` and `toolResults` (each already sent by its own `message_end`, `message_start` and `tool_execution_end`) are read by nobody, and over this repository's Autopilot session they added up to about 30 MB per window and per device. A subagent's events (`subagent_event`, read only by its tools surface) leave the same way (`slimSubagentFrame`, `subagent-frames.ts`). Pinned by `frame-bookkeeping.test.ts` and `subagent-frames.test.ts`.
  - **A batch past the frame cap goes as several frames** (21 Oct 2026): an older device gets every `message_update` whole, so a burst of a long reply (an omp catching up, a fast provider) packed 24.9 MB into one 32 ms `events` batch, past the link's 16 MiB `MAX_FRAME_BYTES`; the host dropped it, `agent_end` included, and the device's tab never left "running". `Link.send` throws `FrameTooLargeError` (before sealing a message already past the cap) and the host's `sendTabEvent` halves such a batch until each part fits, in order; only a single event over the cap is still dropped and logged. The traffic report's slim-events tests stream unpaced, which reproduces it (the 1800-token case hung at its timeout without the split) and takes 0.4 s instead of 9.5 s.
  - **Done for progress snapshots and subagent frames (21 Oct 2026, the same harness, `link-events.ts`)**: a second hello capability, `slimProgress: true` (`ClientHello`, `HostConnection.slim.progress`; it counts only with `slimEvents`). It is its own flag because v0.46.0 devices already send `slimEvents` and can read neither a delta nor an array: they keep single, whole frames. For a connection that asked, the host sends a subagent's `AgentProgress` once and then as a delta against the last snapshot of that subagent id, whichever of the two copies brought it: the `subagent_progress` frame (`FieldDelta` `{"~delta": id, set, unset}`, by top-level field; the payload's fields beside the snapshot, where stock repeats the assignment, go the same way) or the parent's task `tool_execution_update` `details.progress` (also a nested subagent's, inside `subagent_event`). The device rebuilds the very frames and updates stock emitted. Encoder and decoder each keep the last snapshot per id for the tab's life (the renderer's roster does the same) and mirror each other because the link is ordered, which holds only if the encoder sees items in wire order: `createLinkEventSender` (one per tab and connection, `LocalHostServices.#emit`/`#sender`) holds the subagent frames of one `BATCH_INTERVAL_MS` (32 ms), encodes them when they leave and sends them as ONE `subagentFrame` tab event whose `arg` is an array; an `events` batch, any other tab event and the sidecar's `beforeResponse` (the pool's own rule for a response) send the frames held back first. A new connection gets a new encoder, which sends every id whole first, and a send that failed (over the frame cap) makes the next start over. A device with no snapshot behind a delta (not in normal running) drops that update or frame, never delivers half of one. The traffic line names the batch `evt tab.event subagentFrame/batch` and counts its frame types in `events`. Never send a delta or an array to a connection that did not ask, and never make the capability required.

  - **A flush of subagent frames past the cap is halved like an `events` batch** (`sendTabEvent` splits `events` and `subagentFrame` arrays, in order; `#send` reports whether every part went out): the halves leave in the order they were encoded, so the device's decoder sees every delta after its base. A single frame over the cap is dropped, and the sender then starts a new encoder, so the next snapshot of each subagent goes whole and the device never sits on a delta without a base. Pinned by "tab events past the link's frame cap" in `host-services.test.ts` (a capped connection: 40 frames in several tab events rebuild equal; the frame after an oversized one arrives whole).
  - **An Autopilot status crosses as a delta** (21 Oct 2026; the v0.52.7 host's traffic lines: 10 `autopilot_update` frames a minute of 97 KB each, ~1 MB of the 1.3 MB minutes, because the status carries every cycle of the run and the board's run, ship and landing steps each re-send it). A third hello capability, `slimAutopilot` (with `slimEvents`; `HostConnection.slim.autopilot`): the host's encoder (`createStatusEncoder` in `link-events.ts`, one per tab and connection, reset with the rest after a send that failed) sends a tab's status whole once, then the top-level fields that changed, and of a list (the cycles) only its length and the items at an index that differ (`~items`). The device's decoder rebuilds the status the host's pool delivered; a delta with no status behind it is dropped, never delivered half. Measured on this repository's own run (87 cycles): a new cycle's update 96.8 KB → 1.4 KB, an update that changes one field 61 B. A device without it (v0.52.7 and older) gets whole statuses; never send a delta to a connection that did not ask. ### Link loss: a tab never loses the user's answer
- `RemoteSidecar.sendSideChannel` throws `remote_offline` for an `extension_ui_response` while the link is down. Otherwise it returns its delivery (sent once a pending `tab.open` re-attach finished), which rejects with `remote_offline` when the link drops under it or with the host's error when the host refuses it.
- `routeSideChannel` and `EXTENSION_UI_RESPOND` await it, so the pool keeps the request route, the IPC call rejects, and the card or sign-in prompt stays open with an error toast.
- Replies to the host's tool/URI calls are queued and sent once the host tab re-attaches. A `tab.close` that could not be sent goes to `PendingTabCloses` (kept per host link in `devices.ts`, sent when the link is back).
- A remote tab's own link statuses (`error` on link loss, `starting` on reconnect; `statusFromLink`) never drop its open asks in the pool, so a reload still gets the card back. A status the host reports (its omp exited or restarted, or its refusal of the re-attach's `tab.open`/`tab.start` over a live link) does.
- Re-attach brings what changed while the link was down. Every `tab.open` of a tab the host still holds re-sends the asks its omp has open (the `openAsks` tab event; `LocalHostServices` keeps each ask's body until the device answers it or omp withdraws it). The pool replaces the tab's open set with that list:
  - a card whose ask is gone (omp restarted or withdrew it) closes through a synthesized `cancel`;
  - each open ask is forwarded again, since the reconnect's `starting` cleared the page (`pushTabExtensionUiRequest` never doubles a card still up);
  - an ask the tab already held goes out marked `resent` (`IpcExtensionUiPayload`), so the OS "needs you" notification is not repeated; an ask raised while the link was down notifies as new;
  - an ask whose answer is still on its way (`routeSideChannel`) is left as it is.
- **Host tool calls and URI reads the hosted omp waits on come back too** (21 Oct 2026, the v0.49.0 → v0.50.0 update restart: two agent-opened children on paired hosts called `ompdesk_report` 3–7 s after their device quit; the call reached no connection, nothing ever answered it, and stock's `RpcHostToolBridge` has no timeout, so both turns waited for good with their omps alive). `LocalHostServices` keeps each `hostToolCall`/`hostUriRequest` (`HostTab.hostCalls`) until the device's `host_tool_result`/`host_uri_result`, the omp's `host_tool_cancel`/`host_uri_cancel` frame, or a non-ready status (the process took them). A `tab.open` re-sends the ones no connection was handed; a relaunched device's (it adopts the tab under a new rtab, `#adopt`) gets every one, since its last process took the calls it held. A call a live device already has is not sent twice on a lost link, so no tool runs twice. Pinned by `host-services.test.ts` ("re-sends the host tool calls").
  - **A re-sent control call runs at most once.** The relaunched device may have carried a call out before it died (a session opened, a schedule saved) and never answered it. Every control-tool call that changes something (`mutates` in `agent-control/service.ts`: open, send, answer, stop, merge, `ompdesk_app`, schedule other than list, Autopilot other than status) is recorded in `<userData>/agent-control-calls.json` (`call-journal.ts`, atomic) under the caller's device, session file and the host call's id (stable across a relaunch, unlike tab ids): `begin` before the effect, `note` for each tab an open makes as it opens, `finish` with the result, `acknowledge` once the host took the result (a paired host's tab: `RemoteSidecar` emits `hostReplyDelivered` when `tab.sideChannel` returned, wired as `SidecarPool.hostReplyDelivered`; a local omp's at once, it never re-sends). Only acknowledged records are forgotten (after 3 days, then oldest past 500): a host waits on a call with no time limit and may re-send it days later, so a pending or unacknowledged one stays. The same call made again gets the recorded result. One left pending by a crash is reconciled, never run again (`#reconcile`): an open answers the sessions it made (by the noted tab ids through `formerIds`, else the caller's child opened for the brief's task), a schedule create answers the `[agent]` schedule of that name, and anything not found answers "its outcome is unknown after OMPdesk restarted" as an error. **Fail closed**: the host marks a call it re-sends after an earlier connection was handed it (`HostToolCallRequest.resent`; a call made while the device was away is new to it and unmarked), and a marked call this computer has no record of (forgotten, a new profile) is reconciled the same way instead of run. An older host marks nothing, so its re-sends count as new. Pinned by the relaunch cases of `service.test.ts` (died between the effect and the result: one session, one schedule; died before the effect: unknown, nothing opened; unacknowledged kept past 3 days and 500 newer calls; a re-sent call with no record found or unknown, never run) and "re-sends the host tool calls" in `host-services.test.ts` (only a call handed before is marked).
- `e2e/remote-resume.e2e.ts` cuts the link through a relay (`linkProxy` in `remote-harness.ts`) to cover both: the card comes back, and after the host's omp restarted none stays, not even after a reload.
- **A re-attach keeps the page** (the user's report, 20 Oct 2026: a long session went blank and loaded again from scratch each time a paired computer's link came back). ### A host tab never waits forever to come up
- Reported on v0.40.0: a phone opening a session of a paired Windows host showed the transcript skeleton forever, no toast, nothing logged. Whatever the host does, a tab on it now either comes up or says why.
- **Deadline**: every bring-up (`RemoteSidecar.#bringUp`: start, restart, the link coming back) has `REMOTE_START_TIMEOUT_MS` (60 s; env `OMP_GUI_REMOTE_START_TIMEOUT_MS` for tests) to see the host report the tab running. Past it a tab still `starting` (the link never connecting, `tab.open`/`tab.start` unanswered, or the host's omp never ready) turns `error` with `remote.tabStalled` ("{device} has not started this session after {seconds} s. Restart to try again."), shown by `SidecarBanner` with Restart; a link request that times out (`tab.open`'s 30 s) says the same instead of the raw timeout. It stays a link-derived status (`statusFromLink`), so open asks keep their routes, and a host that reports ready later still brings the tab up.
- **A tap on ☰ right after a phone page loads opens the drawer** (the "host never starts" e2e failed 3 of 10 under a locked parallel run with the drawer never showing; instrumented close reasons named two): the first tab list moving `activeTabId` from none to a tab closed it through `SidebarDrawer`'s leave-the-list rule, now `leftActiveSession` (a pick from one listed, non-ghost tab to another only); and the app surface's wrapper changed type with the first tab (`activeTabId ? <TabRuntimeProvider> : surface`), remounting the whole app, whose `useDrawerSidebarSync` put the drawer away again. `App.tsx` wraps the surface in `FocusedRuntimeProvider` (one element type, null runtime until the first tab). Pinned by `SidebarDrawer.test.ts` and `tab-runtime-provider.test.tsx`; 30 of 30 under the same load after.
- **Restart keeps the session**: `SIDECAR_RESTART` restarts on the session file the caller names, else on the tab's own (`SidecarPool.tabTarget().sessionFile`), never a fresh session; the banner's Restart names none. Before this, a host tab whose omp never reported its session forgot the stored session on Restart (`RemoteSidecar.restart` reset its resume path) and the host later started an empty one (the "host never starts" e2e failed whenever its Restart click landed: 7 of 15 runs under load, 3 of 3 with the click made certain).
- **Log**: each step goes to `gui-runtime.jsonl` as source `remote-tab` (`open` {attached, viewing}, `start`, `ready`, `stalled` {step: link | open | start | ready}, `failed` {step, error}), with the device, rtab and `ms` since the bring-up began; Copy diagnostics carries it.
- **The page never waits on a lost reply**: `WsConnection.#invoke` answers a result JSON cannot carry with an error `res` (it was dropped, and the page's call waited forever). A first transcript read that fails while nothing is loaded sets `pageError` (`commitHydration`): the transcript shows the failure with Retry (a fresh hydration), never an empty session's starters.
- Pinned by `remote-sidecar.test.ts` ("a start the host never finishes"), `ws-router.test.ts`, `use-rpc-events.test.tsx` ("a failed first transcript read") and `e2e/mobile-remote-session.e2e.ts` (phone → this computer → host with Windows-shaped paths: stored, large, link drop, agent-opened, desktop-held, host-held, asleep on a relaunched host, after this computer relaunches; and a host whose omp never starts: banner naming it, `remote-tab` log lines, up once the host can). `OMP_GUI_REMOTE_HOST_OUT=<built out/>` runs that host on another build (version skew; passes against v0.39.0).

### Host windows see the device's tabs
- **The user's rule (19 Oct 2026): the person at the host sees and can work in every session running on that computer, including one a paired device started** (e.g. with `ompdesk_session_open {device}`).
- Why: a hosted tab lives in `LocalHostServices`, not in the host's pool, so the host's sidebar had no tab for its session, and an agent-opened session (its first prompt an `<ompdesk-agent-message>` brief whose opener is on the device) folded away as a finished helper (`foldedRootOf` → `familyChildFor` `finished` → `isShownOpened` false); opening it spawned or switched a second omp onto the file.
- List: `LocalHostServices.hostedSessions()` (`IpcHostedSession`: path, id, title, cwd, kind, status with `running`, `awaitingInput`, the device's name; `onHostedSessionsChange` fires only on a real change) is `HOSTED_SESSIONS`, pushed as `HOSTED_SESSIONS_CHANGED` to every window (renderer `stores/hosted-sessions.ts`, synced in App, re-read on a web page's resync). The sidebar counts each as held by a tab (never folded, never archived out, its project expanded), gives it a live row before the index lists it, and takes its signal (running, needs input) from that state.
- Lanes and removed worktrees (the user's report, 20 Oct 2026: sessions the Mac opened on a Windows host were "missing" there and the Mac listed host rows the host did not show). One rule for both sides, `isChatSession` (`lib/session-title.ts`): a chat, or a session in that machine's no-project workspace (`~/.omp/work`, where `ompdesk_session_open {device}` without a folder starts one), sits in that machine's Chats section. A paired host's section and a focused tab on that host ask the host's own workspace (`useHostWorkspace` in `layout/sidebar/host-workspace.ts`: `sidecar.defaultWorkspace(device)` → `workspace.default`, its last answer kept in the snapshot cache), so a row never sits among projects on the device and among chats on the host. A session whose worktree was removed leaves the list unless a tab holds it, a paired device's tab here included (`heldByTab`). Pinned by `Sidebar.test.tsx` and `e2e/remote-host-lanes.e2e.ts`.
- Open: opening it views the device's tab. `spawnTabForWindow` (dep `hosted`) asks `viewSession(path)` for a `HostedTabView` (`remote/hosted-view.ts`, a `SidecarLike` over the hosted sidecar) and `SidecarPool.acquireHostedView` makes it the window's tab (`PoolEntry.hostedView`: listed `shared`, so the host decides steer/follow-up; owns the session for F-OWN). It is never in `resumeFacts`, `tabInventory`, the saved layout, `workspaceDirs`, `restartOnNewOmp` or `applyExtensionUpdate`, which are the device tab's. `GET_SESSION_OWNER` answers `{hosted: true}` and `switch_session` refuses `session_owned_elsewhere {hosted: true}`, both routed by the renderer to a tab (`routeToSessionOwner`).
- The view forwards the omp's stream but never `hostToolCall`/`hostUriRequest` (the device answers those), journals a prompt typed here as the host's and relabels a transcript page for the host (`labelForHost`). An ask's first answer, the device's or the window's, wins (`#answer`: the other side gets a `cancel` `answered:<id>`, which the pool marks `answeredElsewhere`, and its later answer fails `already_answered`).
- Lifetime: closing the view only leaves (`CLOSE_TAB` releases the entry; the omp runs on); a viewed tab outlives the device's grace period; the device's close, delete, revoke or the grace's end ends every view first (`VIEW_ENDED_EVENT`: the pool releases the entry and the window's list drops the shared tab, no error tab). A host-side delete of a session a device's tab runs is refused (`session_running`) only while that tab runs a turn or compacts; an idle one closes and its device hears `sessionDeleted` (see Interrupted turns › The host owns the turns).
- Tests: `host-services.test.ts` ("for this computer's own windows"), the hosted-view cases of `sidecar-pool.test.ts` and `tab-spawn.test.ts`, `Sidebar.test.tsx`, and `e2e/remote-host-view.e2e.ts` (device opens a session on the host → the host lists it once in its project → opens it as a view with no second omp launched → a prompt from each side reaches the one omp and shows on both → the device closes its tab → the host's view ends with no error tab).

### Devices see the host windows' tabs
- **The other way round (the user's duplicate-tabs bug, 19 Oct 2026): a device opening a session a window of the host already has open never gets a second omp.**
- Attach: `LocalHostServices.#open` asks `localTabs.viewForDevice(path, {deviceId, name}, hostName)` first; `SidecarPool.viewForDevice` hands out a `HostedTabView` of that window's tab (`PoolEntry.deviceViews`; the same view class, its `promptOrigin` the device, its transcript localized for it with `localizePromptOrigins`). The host tab holds it as its sidecar (`HostTab.viewsWindow`: never in `resumeFacts`, `hostedSessions`, `restartOnNewOmp` or `applyExtensionUpdate`; the window's open asks reach the device as `openAsks`).
- Device side: `tab.open` answers `{attached: true, viewing: true}` (`TabOpenResult.viewing`), so the device starts nothing and its `RemoteSidecar` reports `shared` (event `shared` → the pool re-lists the tab as shared: host decides steer/follow-up, closing it only leaves).
- Asks: the window's tab counts the device in `viewerCount`; the first answer, the device's (`#answerFromDevice`) or a window's (`routeSideChannel`), wins with the same `answered:<id>` cancel and `already_answered` refusal.
- Waits: the window's tab's connection wait and scheduled retry are the host's `TurnResume`'s; the device's view hears both as they change and on every `tab.open` (`awaitingConnection`, `scheduledRetry` with the time left), and its Cancel reaches the host's `TurnResume.cancelWait` for the window's tab (`SidecarPool.onCancelWait`). See Interrupted turns › The host owns the turns.
- Lifetime: the device's close only leaves; the window's close ends every device view first (`#releaseEntry` → `VIEW_ENDED_EVENT` → tab event `viewEnded` → the device's pool releases its tab quietly). The host's own delete of that session tells the device `sessionDeleted` first and closes the view, refused only while the window's tab runs a turn (see Interrupted turns › The host owns the turns); the device's delete is refused while a window here runs it live.
- **Every device views a window's session**: another device's view of a window's tab holds no omp, so `#adopt` never refuses a second device `session_open_in_tab` for it (the user's report, 23 Oct 2026: a second paired computer opening this Mac's Autopilot session got "Session is already open in another tab on the host"); the same connection under another rtab still is.
- Tests: the "device views" cases of `sidecar-pool.test.ts`, "a device opening a session a window of this computer runs" (with "a second device views the same window's session") in `host-services.test.ts`, and the second half of `e2e/remote-host-view.e2e.ts` (host opens first → device opens it, no new omp launched → prompts from both reach the one omp and show on both → the host closes → the device's view ends, no error tab).

### Devices see what the host works on
- **The user's report (22 Oct 2026): a session working on a paired host showed nothing on the device until it was tapped open** (a row's light and working arc read only this device's own tabs).
- Host: `LocalHostServices.liveSessions()` lists every session this computer works on now (`HostLiveSession`: `turn`, `background` while stock's background work keeps it unsettled, `waiting` while an ask is open; waiting beats a turn, a turn beats background), from its windows' tabs (`SidecarPool.liveSessions`, wired as `windowLiveSessions`; a tab on another host and a view of a device's tab are left out) and the tabs it runs for every device. `sessions.live {}` answers it; every change (`#hostedChanged`, the pool's `onRunningChange` and its ask activity) pushes it to every connected device as the `host.liveSessions` event, one push per burst (`LIVE_SESSIONS_DEBOUNCE_MS`, 250 ms) and only when it differs.
- Device: `RemoteDevices` reads `sessions.live` as the link comes up, takes each push, and puts the list on the host's `HostView.live` (only while online; cleared when the link drops, so a row never stays lit for work nobody can see). An older host answers `unsupported` and sends no push: no `live`, rows as before. An older device drops the event name.
- Renderer: a host's row no tab here holds wears the working cue from `host.live` (`SidebarDevices.tsx`, the same `TabLiveTitle`/`TabLiveAge` and words as a tab's state); a row with a tab here keeps its tab's own state, unless that tab is `asleep`.
- **An asleep tab here knows nothing of the host's run** (the user's report, 27 Oct 2026: after an update or a restart of either computer, a host's session at work lit nothing on the device until tapped). A relaunch restores this computer's tabs asleep (no omp attached until shown). Only the tabs `tabs.kept` names come back attached, and those are this device's own turns on the host, never its view of a host window's session or of another device's, so such a row read a tab that never heard of the run. The row (`renderRow`) and a family child (`familyChildFor`) take the host's `live` state over an `asleep` tab's; the tab still opens, closes and dumps as before, and a tab once attached keeps its own state. A phone page showing a paired host's section through this computer reads the same rows. Pinned by "lights a host's session at work whose tab here is asleep" and "says a child at work on the host is running when its tab here is asleep" in `Sidebar.test.tsx`, and by "a host's session at work lights the device's row with no tap" in `e2e/remote-resume.e2e.ts` (two apps: B's window works on a session A opened; A relaunches with that tab asleep and its row lit; B is killed mid-turn, its relaunch continues the turn, and B's next run lights A's row again, still asleep).
- **An asleep tab here never keeps a host's finished session** (29 Oct 2026): a tab restored asleep on a host session whose OMPdesk worktree the host lists gone (disk care removed it once its work landed) does not list the row, and main closes it as the link comes up or the host's list changes, as a deleted session's tab closes; a shown one the host refuses `session_folder_missing` there closes too. The whole rule is settings-layout-look.md › Sidebar projects ("A finished worktree's session never comes back through a tab nobody uses").
- **This computer's own list has the same gap** (the user's phone, 26 Oct 2026: three sessions worked in the computer's window and their rows under "This device" showed only an age until each was tapped; a second desktop window is the same): a window's sidebar knew only its own tabs and the sessions it hosts for devices. Every window now also hears `LocalHostServices.liveSessions()` (`LIVE_SESSIONS` read at boot and on a web page's resync, `LIVE_SESSIONS_CHANGED` pushed by the same debounced `liveSessionsChanged`, `onLiveSessionsChange`; `useHostedSessionsStore.live`), and a row of this device's list that no tab of the window holds and no hosted session names takes its working cue, ask and background state from it (`sessionRowState` in `Sidebar.tsx`); `isSessionBusy` counts it too. Pinned by "lights a row another window of this computer works on" in `Sidebar.test.tsx` and the window listener of "tells every device and every window" in `host-services.test.ts`.
