## Multi-viewer and mobile web

### Multi-viewer
- **Ownership** (`sidecar-pool.ts`): a tab has one owner window and may have viewer windows (`attachViewer`). Only a paired web device's window (negative ids) views another window's tab: `tab-spawn.ts` attaches instead of refusing an owned session. Env `OMP_GUI_TEST_VIEWER_WINDOWS=1` lets any window (`e2e/multi-viewer.e2e.ts`). Each window keeps its own active/visible/split view; the full channel is wired once per tab and fans out to every window showing it; the light channel reaches owner and viewers.
  - A window of a host also shows the tabs its `LocalHostServices` runs for paired devices, as hosted views over the same multi-viewer rules (`acquireHostedView`, one omp, first answer wins with the device); see Remote devices (Host windows see the device's tabs).
- A viewer closing the tab only leaves it (`detachViewer`); the owner's close releases it for all. `TAB_LIST_CHANGED` → viewers apply `applyTabList` (`shared`/`viewerCount` drive behaviour only). The user's rule (19 Oct 2026): **nothing on screen says a tab is shared** — no title-bar chip, no line under the composer.
- **Asks**: the first window to answer wins; the others get a synthetic `cancel` (`answeredElsewhere`, toast "Answered on another device"); a later answer fails `already_answered` (toast, card closes).
- Aggregation: draft-empty per window (`noteDraft`); subagent stream level = highest any window asked (`noteSubagentLevel`); a mode toggle makes others re-read (`noteModeChanged` → `config_update {modes: true}`); a shared tab's notification is deduped across windows; its terminals are keyed by the owner window; `PREFS_SET` pushes `PREFS_CHANGED` to the other windows.
- **Renderer rules for a shared tab** (`stores/messages.ts`, `composer-submit.ts`): on a shared tab or web page a plain message goes as `prompt(streamingBehavior)` and the host decides steer/follow-up (`hostDecides`). An optimistic echo is claimed only by the delivery with its own text (`sharedTab`, `ownSends`); any other user delivery is another viewer's (`fromOtherViewer`, "from another device"). The dequeue's `omp:fill-composer` names the asking `tabId`. Quota resume runs in the owner window only. A web page keeps its own done marks (`lib/unread-marks.ts`).
- **What an extension shows outlives the page that saw it set**: main keeps each tab's latest `setStatus` per key, `setWidget` per key and `setTitle` (`PoolEntry.uiState`, dropped with its omp) and gives them to a page that loads later (`EXTENSION_UI_STATE` = `ui.shownState()`, read at the page's start and in a web page's resync beside `openRequests`). No frame repeats them: a reload, a new window or a phone lost them for good, and a page whose listener came up 24 ms after the first status lost that one (nightly 39539556435, extension-ui-rpc). Pinned by `sidecar-pool.test.ts` ("keeps a tab's status texts") and the reload step of `e2e/extension-ui-rpc.e2e.ts`.
- **Prompt origins**: before a prompt/steer/follow-up from a paired web device (every window under the test hook) reaches the omp, main sends the bridge `prompt_origin_set {origin, text}`; `resources/gui-bridge/prompt-origin.ts` journals that device for the message with that text; `labelPromptOrigins(…, null)` marks every prompt of a local transcript with `promptFromId`; `ipc.ts` localizes each `get_transcript_page` per window (`localizePromptOrigins`: own prompts plain, the host's named with the computer's name). A live delivery on another window says only "from another device" until the transcript is re-read.
- **A paired web device's tabs survive this computer's relaunch** (`main/web/web-tab-layouts.ts`, pref `webTabLayouts`: device id → `PersistedTabLayout`). Its `WebClientWindow` id is new every launch, so `SidecarPool.onWindowTabsChanged` files the layout under `deviceId` (never while `quitApproved()`; a window with no tab left forgets it). At launch, after desktop windows and before `turnResume.launch()`, `restoreLayout` puts each still-paired device's layout into `webHost.windows.windowFor(deviceId)` (deferred tabs). A revoked/blocked/expired device's layout is dropped (`devices.onRevoked`); one for a device no longer listed is pruned. Desktop `tabLayouts` are untouched.
- **One session, one tab, one omp on its file**: a web window's layout also names the stored sessions it views (saved again when it starts/stops viewing one or their owner closes it); its restore views a session a desktop window already holds (`attachViewer`) instead of opening a second tab; a desktop window's restore skips a session another desktop window holds. A page whose spawn is refused `owned` by a tab of its own window it has not listed yet reads the tab list and switches to it (`openTab`); a web page never answers a refusal with "open in a new window".
- **An agent closes a web page's tab in main** (`ompdesk_session_stop {close}`, auto-close): the window's `AGENT_CONTROL_VIEW` would be dropped while the device has no socket, so main releases the tab through `closeWindowTab` (`tab-release.ts`, shared with the `tabs.close` handler) and announces it in `TAB_LIST_CHANGED {closed}`; the layout above then forgets it. It does so only for a tab no live connection of the page reported dirty: the page's `FileEditReporter` sends `tabs.reportFileEdits(dirtyTabId)` (`FILE_EDIT_REPORT`) on every Files editor change and every `open` connection, main keeps the latest per connection (a device's up to four connections share one window: `web/file-edit-reports.ts`, `IpcCaller.connId`, dropped on `WsRouter` `onConnectionEnded`), and a window with no live reporting connection is `unreported`, never assumed clean (details under OMPdesk control tools › Beyond the caller's window).
- Pinned by `web-tab-layouts.test.ts`, `sidecar-pool.test.ts`, `tabs.test.tsx`, `e2e/mobile-autopilot-rows.e2e.ts` (`e2e/fixture/phone-serve.ts` plays `tailscale serve` for a Chromium page on `http://localhost`).

### Server and auth
- **Server** (`src/main/web/`; `WebHost` in `web-host.ts`, created in `index.ts`): HTTP + WebSocket on `127.0.0.1:47831` only (when free); `tailscale serve` publishes it (see Tailscale). `server.ts` serves the built renderer from an allowlist (`/` and `/pair` → `web.html`; `STATIC_DIRS` `/assets/ /cmaps/ /standard_fonts/ /wasm/ /icons/ /screenshots/`; manifest; `sw.js`; traversal refused), plus `POST /api/pair`, `POST /api/session` (device signs a server nonce with its WebCrypto key → 30 s single-use ticket, `TICKET_TTL_MS`), `/ws`, `/blob/<token>` (Range; HTML/SVG download only), `POST /upload` (25 MiB a file, 200 MiB a device per 24 h, deleted after 24 h: `uploads.ts`).
- **`auth.ts` checks every request in this order**: loopback peer; any `Tailscale-Funnel-Request` refused; **secret path prefix** (`stripServePrefix`, constant-time; without it, or before serve is published, a bare 404 and no header is read; stripped so the page never sees it); `Host`, `Origin`, `Sec-Fetch-Site`; `Tailscale-User-Login` (RFC 2047-decoded) against the allowed logins. A login not allowed, or none (tagged node), gets `refusal-page.ts`'s HTML (`Accept-Language` ko/en; JSON `tailscale_user_not_allowed` / `no_tailscale_user` for an API call).
  - **A relaunched host answers its own secret 503 until serve is confirmed** (`RequestPolicy.pendingPrefix`, set by `WebHost.start`): serve keeps forwarding while the app restarts, and the new process listens a few seconds before Mobile web reads serve's status and configures `servePrefix`. A 404 in that window made the worker give up a chunk the new build has (nightly 39474605589: Settings' idle preload landed there and Settings opened empty in Chromium and WebKit); 503 is an outage the worker retries (`ASSET_OUTAGE_MS`). Without the secret it is still the bare 404. Pinned by `auth.test.ts` and `server.test.ts` ("answers 503 under its own secret").
- **Identity is Tailscale's**; the device cookie serves later calls (`__Host-ompdesk` over HTTPS; `devices-store.ts`: `web-devices.json` 0600, only the secret's SHA-256, 14 days sliding / 90 absolute, record keeps the Tailscale `nodeId`).
- **`POST /api/pair`** (no code: an allowed login's first visit makes the device and cookie) asks `tailscale whois` about serve's `X-Forwarded-For` address (injected `whois`, cached 60 s); the device is named after the node. Refused: a login whois does not put behind that address (`identity_mismatch`), a blocked node (`blocked`), > 10 tries a minute per address (30 overall) or 20 new devices an hour (`PairingGuard`, `NEW_DEVICES_PER_HOUR`).
- **Approval**: with "Approve new devices on this computer" (pref `mobileWeb.confirmNewDevices`, default **off**; the one switch for phones and computers alike, see Remote devices › Gate) `PairingConfirmations` (`pairing.ts`) holds the visit until the desktop approves (`WEB_PAIRING_REQUEST`, desktop windows only, 60 s); otherwise the desktop is told once after the fact (`WEB_DEVICE_CONNECTED`, desktop windows only; toast with Block).
- **Block** (`WEB_DEVICES_REVOKE`, `WebHost.block`) is a revoke that sticks: `blocks-store.ts` (`web-blocked.json` 0600) keeps the node's stable ID — never the login (one login has many devices); every record of that node is revoked (sockets close 4401, virtual window destroyed). A cookie-less page load while a block exists, and `/api/pair`, look the visitor up (`whois`) → "this device is blocked" page / `blocked`. A visitor whose node cannot be told while its login has a blocked node is held back (`unidentified`, fail closed). A device with no node identity is blocked by its login (`WebDeviceInfo.blockScope`; the confirm and Blocked list say every device of that login). `WEB_BLOCKS_LIST`/`WEB_BLOCKS_REMOVE` list/lift. Expiry only deletes the record. A revoked device that returns is refused, not re-enrolled, until Unblock.
- **`ws-router.ts`** turns `inv`/`snd` frames into `IpcRegistry.invoke/send` with the device's `WebClientWindow` (`web-client-window.ts`, negative id, parked while no socket) as caller once `IPC_POLICY` and the device's grants allow the channel (`web_forbidden` otherwise; `pairing-admin` never served; a web device cannot write `mobileWeb.*` prefs). Model commands metered through `PeerQuota` (`remote/peer-quota.ts`); pushes batched every 75 ms (slim `message_update` deltas joined); streams stop while the page reports itself hidden; ping every 20 s (three quiet ticks end a socket). **A call's answer goes after every event pushed before it** (`#reply` flushes the batch first), the order the desktop's IPC keeps: an answer that overtook the batch let a page read a tab list naming the tab's session file and then a stale status saying "no file yet", and the page replaced the tab's runtime with the draft being typed in it (`e2e/web-no-reload.e2e.ts`, about 1 in 4 under load; pinned by `ws-router.test.ts` "ahead of it").
- **Web-only calls** (`web:host.*` browse/save/open/reveal/blob; `web:models.config.read/write` = models.yml as text via `readModelsText`/`writeModelsText`: parser + schema check, atomic, refuses a file changed since read; `web:device.uiPrefs.*`; `shared/web-host.ts`, `host-actions.ts`) are a table in the router, not `IPC_POLICY`. `FS_READ_BINARY` answers `{dataBase64}` ≤ 512 KiB, else `{blobUrl}`; `FS_MEDIA_STREAM` answers a `/blob` URL from `MediaStreams`.
- **Tests** use injected clocks/`Timers`; `server.test.ts` runs the real server on an ephemeral port behind the prefix with serve's headers (stubbed `fetch`), faking only the IPC registry, desktop window and `whois`.
- **Pictures never ride the socket**: a frame holds 1 MB (`MAX_FRAME_BYTES`; the page refuses a bigger request) and a phone photo exceeds it even after the composer scales to `IMAGE_MAX_SIDE`. `shim.ts` sends any call holding an inline `{type:"image", data, mimeType}` through `upload.ts` `liftInlineImages` first (bytes to `POST /upload`; the block becomes `WebUploadedImage {type, mimeType, upload: <host path>}` from `shared/web-protocol.ts`; a refused/lost upload fails the call with `web.upload.image*`, nothing sent); `ws-router.ts` `#landUploads` reads each back into `data` before the call (`UploadStore.take`: only this device's `<device>/<uuid>/<name>`, deleted once read; missing → `file_not_found`). Calls without such a block stay synchronous. Pinned by `shim.test.ts`, `ws-router.test.ts`, `uploads.test.ts`, `e2e/mobile-attach.e2e.ts`.
- **A browser without `OffscreenCanvas` sends a photo as taken**: `fileToImage` (`composer/input-area-utils.ts`) scales a PNG/JPEG/WebP past `IMAGE_MAX_SIDE` with `OffscreenCanvas` and returns the file itself where that, `createImageBitmap` or the decode is missing (Playwright's WebKit on Windows has no `OffscreenCanvas`). `e2e/mobile-attach.e2e.ts` asks the phone's page which it is, then expects a smaller JPEG or the same bytes; a HEIC the browser cannot draw is the photo chip, so that test asks the page whether it draws one too.
- **Attaching on a phone**: on touch the composer's + menu has **Photos** (`accept="image/*"`: Android offers gallery and camera only then) and **Attach files** (no `accept`). A phone's picker is another app, so the page goes hidden and `change` arrives just after it returns — the moment a resync/update `resume` used to reload and drop every pick. Every pick is tracked from the input's click until its files landed (`lib/file-pick.ts` `trackFilePick`/`filePickInProgress`; `cancel` ends it, or 3 s back in front without `change`); `safeToReload` waits for it and the last-resort reload goes through `sw-update.ts` `reloadWhenUnused`. A non-image file goes up through `fs.pathForFile` (composer shows a `[data-upload-chip]` "Sending … to your computer", then mentions its host path); a failed upload rejects with its worded reason (`web.upload.*`, 25 MB cap checked on the phone), shown as a composer error, nothing inserted. Pinned by `file-pick.test.ts`, `sw-update.test.ts`, `safe-moment.test.ts`, `composer-files.test.ts`, `InputArea.queue-shorthand.test.tsx`, `e2e/mobile-attach.e2e.ts`.
- **Coming back is cheap** (`ws-router.ts`, `ws-transport.ts`): the page's return to foreground sends `hello` again only when the host dropped stream pushes while hidden (resync in place, no reload). A reconnect offers `resume.<connId>` as a subprotocol; `WsRouter.attach` answers `resumed: true` when that connection ended with every event acknowledged, nothing queued/dropped, no push since (`#pushes`; ended connections kept 10 min, `RESUME_WINDOW_MS` in `ws-router.ts`); `server.ts` first retires a still-open old connection of that id. A call the drop failed makes the page resync anyway. Perf audit: `e2e/web-perf.e2e.ts`, opt-in `OMP_GUI_WEB_PERF=<dir>` (fake serve plays a phone link; `_SUBJECTS=before=<checkout>,after=<checkout>`, `_PHASES`, `_RUNS`, `_MINUTES`, `_PROFILE=1`).
- **Web host sheets** (`src/renderer/web/host-ui/`, `<WebHostUi />` in `App.tsx`, nothing on the desktop): the web page has no native dialogs, so `shim.ts` calls `web/host-hooks.ts` hooks that `WebHostUi` registers, one sheet at a time (`host-ui-store.ts`): `PathActionsSheet`, `SaveImageSheet`, `HostBrowserSheet` (the computer's folder/file/save browser over `web:host.listDirs`; also replaces the project picker), `EditorSheet`, `ModelsConfigSheet`, `ConfirmSheet` (restart for update, quit; names running turns). A link opens on the device at once with a toast to open it on the computer. A device without `desktop-control` gets `hostUi.computerOff`. Every sheet has a test in `host-ui.test.tsx`. A sidebar session row's actions are one ⋯ button (`data-sidebar-row-menu`, label "Session actions"/"세션 메뉴") on every input, never separate rename/archive/delete buttons, so the title keeps its width (the user's call, 20 Oct 2026): at rest on touch (`data-input=touch`, opening an action sheet; `mobile-shell.e2e.ts`), on hover or keyboard focus on the desktop (the roving tab stop's ⋯ is the next Tab stop, Enter opens, Escape closes back to it). It opens the row's menu in `rowMenuItems` order (`Sidebar.tsx`: rename, pin, move, archive/restore, delete, then the right-click menu's rest without Open), the same list a right click shows in its own order. On hover the ⋯ takes the age's place (`ListRow` `actionsOnHover`: the meta steps aside and the title runs on under the fade to the ⋯): at the default width the hovered title's clear width went 146 → 167 px (dev harness, 1280 px window).

### Threat model
- The user's rule: no pairing code — copy the tailnet URL, open it on any device signed in to the same Tailscale account, and it works. No pairing-code step anywhere.
- **Who may connect**: a request through `tailscale serve` with a `Tailscale-User-Login` in `allowedUsers` (default: this computer's own login; Settings › Mobile web), over a tailnet only. Serve, never Funnel: `service.ts` has no Funnel command, an `AllowFunnel` flag on our port (`funnelExposed`) stops the server, `Tailscale-Funnel-Request` is refused. Anyone who can sign in to an allowed account on a tailnet device, and anyone the user shared the computer's node with while that account is allowed, can make a device and gets `DEFAULT_WEB_GRANTS` (never `pairing-admin`). The user's tools: the approval setting, the notice's Block, the Devices list.
- **Forged headers**: a local process can write `Tailscale-User-Login`/`X-Forwarded-For` to `127.0.0.1:47831`. Serve joins its target's path to every request's path, so `service.ts` publishes `serve --bg --https=<port> http://127.0.0.1:<local>/<secret>` (256 random bits; `serve-secret.ts`, `web-serve-secret.json` 0600, made on first use). Only traffic through serve carries it; without it nothing is served (404) and no header is read (`auth.test.ts`, `server.test.ts` "headers forged on the loopback"). The secret is never in prefs (`mobileWeb.serve` holds the local address only) and never logged.
- **Residual risk**: the secret is in `tailscale serve status` and the 0600 file, so a same-user process can read it and forge a login (and an `X-Forwarded-For` whois accepts; whois' cross-check only catches a self-contradicting forgery). Such a process already reads the cookie store, prefs and user files, so a single-user Mac is not defended against it (another OS user reads neither file). `Host`/`Origin`/`Sec-Fetch-Site` stop a browser page reaching the loopback port.
- **Not defended**: a compromised allowed account or tailnet device (use Block and approval), Tailscale's control plane. **Block** is by node, not login.
- **UI** (`settings/MobileWebSection.tsx`): once ready, the link in a monospace line with a big **Copy link** button and one QR (`MobileWebConnect.tsx`: install Tailscale, same account, open link, iOS Home Screen note); the approval switch (`set-confirm-new-devices`); connected devices with **Block** (`MobileWebDevices.tsx`; confirm names `revokeBodyLogin` when `blockScope` is `login`); the **Blocked** list with Unblock (`MobileWebBlocked`, `stores/mobile-web.ts` `blocked`, re-read when the device list pushes); allowed accounts. The desktop shows a new device as one toast with Block (`dialogs/WebDeviceNotice.tsx`, `mobileWeb.devices.onConnected`) or, with approval on, `WebPairingDialog`.
- **`/pair`** (`web/PairScreen.tsx`) has no form: a browser whose session is refused makes the device key, calls `POST /api/pair` (`pairing.ts` `pairFailureOf`: blocked / account not allowed / declined / rate limited) and enters, or shows the reason with Try again; a browser that can already get a ticket just goes on. `e2e/mobile-web.e2e.ts` plays the phone with the fake Tailscale's headers through the prefix.
- **Computer sharing** (OMPdesk to OMPdesk, `src/main/remote/`; see Remote devices) has the same identity and no code: a connection is let in only from a tailnet address (`not_tailnet` otherwise; a loopback or LAN peer, or a forged source, gets nothing: the host does not even listen off the tailnet), when `tailscale whois` (cached 60 s) names a node of an allowed login (Mobile web's list) that Mobile web's blocks do not hold. Tailscale's WireGuard makes the source address the node's, so the address is the identity; the static keys pinned per node on first contact add end-to-end encryption and catch a reinstall or a stolen node record (`key_mismatch`). No Funnel (the host never publishes through serve). Block is by node and shared with Mobile web; PeerQuota, grants and `host.*` routes are unchanged. **Not defended**: a compromised allowed account or node (it connects like the user's own computer until blocked; approval of new devices narrows the first contact), Tailscale's control plane. `OMP_GUI_TEST_REMOTE_LOOPBACK` (tests, unpackaged builds only) is the one way loopback counts as the tailnet.

### Reloads
- Phones once reloaded or crashed by themselves (v0.36.1–v0.38.1); these rules keep that fixed (`src/renderer/web/`).
- **Every reload says why**: `reload-reason.ts` notes `{reason, at, details}` in `localStorage` just before it (`update`, `outdated`, `resync-failed`, `chunk-load-failed`, `error-boundary`); `web-boot.ts` sends kept reasons as `web-reload` runtime-log lines on each connect. Renderer code reloads only through `lib/page-reload.ts` `reloadPage(reason)` (`WebRuntime.reload`).
- **Missed events never reload**: `ws-transport.ts` `onResync(cause)` (`missed-events`, `lost-calls`) runs `resync.ts` `PageResync` (one pass at a time, a reconnect during a pass reruns it, a failed pass retried after 2 s × failures) over `resync-page.ts`: `reconcileTabs({dropUnlisted: true})` (the host's list is the whole truth: a restarted host gives new tab ids, and a tab known only from the list takes its status into its runtime, else Send stays disabled); `hydrateTabSession` of each visible ready/running tab (merges while a reply streams); `settleTabExtensionUiRequests` (shows missed asks, drops blocking asks answered meanwhile); `loadRemoteState`; `refreshHeldSessionLists`; then `WebRuntime.onResynced` listeners. A streaming reply gets missed deltas back: every hello sending the page to resync (`resumed: false`) makes the host resend each tab's next `message_update` whole (`WsRouter` `onResync` → `SidecarPool.resnapshotWindow`), and the messages store snapshots the message it streams when longer than its buffer. Only after three failed passes in a row does it reload, via `reloadWhenUnused` (hidden, or a launch/return moment that is `safeToReload`).
- **Updates only while unused**: `sw-update.ts` `ResumeGate` is open at launch and on a return after ≥ 30 s hidden (`RESUME_AFTER_HIDDEN_MS`) for 15 s (`RESUME_WINDOW_MS` in `sw-update.ts`) or until the first `pointerdown`/`keydown`/`wheel`/`touchstart` (a scroll alone does not count); `applyUpdate` resumes a waiting worker only then. An `outdated` page (host's `minClient` newer) cannot talk to the host and waits only for `safeToReload`; before the app loaded it purges at once.
- **Chunks of an old build** (a page left open, or booted from its worker's stale-while-revalidate shell, asks for hashed lazy chunks the new build lacks; v0.38.1 crashed because `BenchmarkDialog` was mounted at every launch — mount dialogs from their first open). Three layers:
  - Host: `main/web/asset-archive.ts` copies each build once at `WebHost.start` into `<userData>/web-assets/<build>/` (build = hash of `web.html`; replaced builds kept 7 days, at most 2: `ARCHIVE_RETAIN_MS`, `ARCHIVE_MAX_PREVIOUS`); `server.ts` serves a missing `/assets/` file from them by name only.
  - Worker: `sw-core.ts` keeps every hashed `/assets/` file of its build it fetched (`omp-assets-<build>`, `RUNTIME_LIMITS` 24 MB / 150, oldest out), retries a failed fetch once after `ASSET_RETRY_MS` (400 ms), then takes another build's copy of the same name. While the host does not answer or answers a 5xx it keeps retrying, each wait doubling, for up to `ASSET_OUTAGE_MS` (30 s); a 404 gives up after the one retry. WHY: a browser keeps a failed module import for the page's life, so a 502 during the idle preload (the host restarting for an update, a phone between networks) left Settings, Agents, Insights and the panel views empty until a reload (`e2e/web-no-reload.e2e.ts`, about 1 in 10 under load; a 3 s outage injected at the preload reproduced it every time in Chromium; pinned by `sw-core.test.ts` "short outage").
  - Page: lazy views go through `lib/chunk-load.ts` `lazyChunk`/`loadChunk` (one retry, then the view renders nothing); other failing Vite dynamic imports count via `vite:preloadError` unless a retry recovered within 3 s. A failure for good **never asks the user anything** (updates are automatic: no banner, no button — the user's rule): it marks the build stale (`useChunkFailureStore`), `web-boot.ts` marks the page outdated (`markOutdated()`; `chunkStale`), and the update gate reloads at the next unused, safe moment, reason `chunk-load-failed`; a page without a worker purges through the same gate.
  - A reload for a chunk never repeats at launch: `purgeNow` records it (`sessionStorage` `CHUNK_RELOAD_KEY`), and a page whose chunk fails again within `CHUNK_RELOAD_LOOP_MS` (30 s) of one skips its launch moment (`chunkReloadRepeats` → `gate.used()`), so a chunk no build or archive has waits for a return after ≥ 30 s hidden instead of reloading the page four times a second (pinned by `sw-update.test.ts`).
  - On a web page `RootErrorBoundary` shows a quiet empty screen for a chunk error (`data-app-stale`, no text/button), marks the app gone (`appGone`) and reloads via `reloadWhenUnused` over `appGoneMoment`. Typed text does not hold it (the composer saves its draft as it unmounts, `InputArea.draft-unmount.test.tsx`); a picture, unsaved edit, pick, upload and (visible) an open question still do. A desktop window keeps the ordinary crash screen. A failed locale chunk is forgotten so the next use retries.
- **Muted errors**: every script tag carries `crossorigin`; a "Script error." with no file/line is logged with `details.muted` and the user agent.
- `session-tree-layout.ts` (`panels/`) is iterative in both passes (v0.36.1 stack overflow; `session-tree-layout.test.ts`, 100,000-entry chain).
- Pinned by `reload-reason`/`resync.test.ts`, `resync-page.test.ts`, `sw-update.test.ts`, `sw-core.test.ts`, `ws-transport.test.ts`, `chunk-load.test.tsx`, `RootErrorBoundary.test.tsx`, `tabs.test.tsx`, `asset-archive.test.ts`, `server.test.ts`, `ws-router.test.ts`, `messages.test.ts`; on the built app by `e2e/web-no-reload.e2e.ts` (Chromium and WebKit: a drop mid-reply catches up in place, no page load, no gap; after the host restarts on a build without the Agents chunk the view opens from kept assets and the draft survives; a view whose chunk neither build nor archive has stays empty with no prompt and no reload while in use, then reloads by itself on a return after ≥ 30 s hidden with the reason in the host's log), `e2e/mobile-autopilot-rows.e2e.ts`, `e2e/mobile-attach.e2e.ts`. Agents, Stats, Settings and the side panel's views are preloaded once the page idles, so only the feedback, model setup, debug console, theme picker and import dialogs are lazy-on-demand (the debug console and the theme picker stay mounted from their first open, so the console's request and result outlive a close; the theme picker and the SSH question dialog, `settings/SshPromptDialog.tsx` apart from Settings' SSH rows, came out of the phone's first screen, 3.288 → 3.267 MB). A page load in those specs is `domcontentloaded` (or a `window` marker), never `framenavigated`.

### PWA and push
- **Web Push, host side** (`shared/web-push.ts`; `main/web/{vapid-store,push,web-push-notifier}.ts`): `VapidStore` keeps the VAPID keypair in `<userData>/web-push.json` (0600, atomic; a missing/corrupt file makes a new pair and `WebHost` then drops every stored subscription). `PushSender` = the `web-push` package behind an injectable `PushTransport` (tests inject a fake): one attempt; TTL asks 6 h / news 1 h / `clear` 2 min; urgency `high` for asks; 404/410 → `forgetPushSubscription` (only while still the refused endpoint); else logged.
- `GET|POST /api/push` (device cookie, `device-self`, JSON, Origin like every POST, 20 a minute a device) stores `WebDevice.push` (removed with the device on revoke; a damaged block costs only push settings). An endpoint must be a push service's `https` DNS name on the default port (`isPushEndpoint`: loopback, LAN, tailnet, IP literals refused).
- `WebPushNotifier` is driven by `SidecarPool.observeTabs` (`TabActivity`; `tabFacts`; a provider sign-in's requests are never asks) through `WebHost.tabActivity` only while the server runs. A settle is announced 1.5 s later (`COMPLETION_DEBOUNCE_MS`) unless the tab ran again, was Stopped, waits for the connection or stock's retry, or that run was already announced. It reuses `NotificationBatcher` unchanged in rules (one extra batcher whose "windows" are paired devices, fed only the categories each device switched on; `retract` for an answered ask): ask > error > completion, first event at once, one summary after 4 s replacing the first banner (same tag, `silent`).
- A device with a visible socket (`WsRouter.isDeviceVisible`, the page's `presence`) is never pushed, not even a `clear` (its page toasts and closes its own notice). `hideContent` sends generic titles, no body. Text is the host's UI language (`push.*`, `batch.*` in `i18n-text.ts`). Tags are `tab:<tabId>` (a one-tab summary keeps its `tabId`, several has none).
- **Service worker** (`src/renderer/web/sw.ts` at `/sw.js`, scope `/`; built by `pwaPlugin` in `electron.vite.config.ts` with the precache list and a build id; `scripts/pwa-plugin.ts` is a `BUILD_SCRIPTS` input of `build-cache.ts`). Logic in `sw-core.ts` (browser objects injected, unit-tested with fakes): `push` parses a `WebPushPayload` (unknown `v` ignored) and shows it (`tag`, `silent`, `data{tabId,url}`); `clear` closes its tag's notifications and shows nothing; `notificationclick` focuses an open page (posting `{type:"notification-click",payload:{tabId}}`, routed by `notify.ts`) or opens `notificationOpenUrl`.
- **Caches**: `PRECACHE_LIMITS` 8 MB / 80 (eager chunks plus the static closure, never lazy chunks). Cache-first for those hashed `/assets/` files and (`omp-assets-<build>`) every hashed `/assets/` file of its build the page fetched; stale-while-revalidate for `/` (network when nothing cached); never touches `/api /ws /blob /upload /healthz`; one `omp-shell-<build>` and one `omp-assets-<build>` per build, older deleted on activate. The page registers the worker only after the app (`../main`) loaded, and the install takes hashed assets from the HTTP cache (`cache: "default"`), so a first visit downloads its shell once.
- **Updates apply by themselves, no banner, no strings** (the user's rule): a new worker waits; `UpdateWatcher.resume(moment)` (only while `ResumeGate` is open, see Reloads) sends `skip-waiting` and reloads once it controls the page. Only a worker waiting behind a different controller is an update: WebKit dispatches a first install's `installed` with the registration still naming that worker `waiting` and the page's controller already that same worker, which read as an update and reloaded a phone right after pairing (reason `update`, nightly 39533946034's mobile-attach). An `outdated` host is marked by `markOutdated()` and waits only for `safeToReload`, using `purgeAndReload` (unregister the worker, clear caches, load from the network; cleanup bounded by `PURGE_CLEANUP_MS` 3 s because WebKit has left a cache delete unsettled; the safe moment is re-checked right before the reload). One reload per watcher (`#applying`). `sw-update.test.ts`.
- **`safeToReload(SafeMoment)`**: page visible, composer draft and attachments empty, no ask/approval/plan card open, no upload in flight (`uploadsInFlight()`), no unsaved Files editor change (`fileEditDirty`/`pendingFileSwitch`), no host sheet/dialog on screen (host editor and models-config drafts live there); `safe-moment.ts` `pageSafeMoment` reads it from the stores. The draft is persisted per session anyway.
- **Static assets**: `/manifest.webmanifest` and icons (`icons/icon-192|512|maskable-512.png`, root `apple-touch-icon.png`) in `src/renderer/public/`; PNGs from `bun run gen:icons` (`scripts/pwa-icons.ts` from `PWA_ICON_SVGS` in `brand-svgs.ts`). Static files and the manifest need only the serve walls, never the device cookie.
- **Page side**: `push-client.ts` (`PushClient` over `GET|POST /api/push`; the permission prompt is the first await of `enable()` so it keeps the click's user gesture; a changed VAPID key resubscribes), `pwa.ts` (`webPwa()`, non-null only on the web page). On the web page Settings › Mobile web renders `WebNotificationsSection` (this device: on/off, hide content, categories, why it cannot work, install guidance) instead of the computer's panels; the desktop section keeps its own iOS step (`mobileWeb.step4`).
- **First screen stays small**: the side panel's views are a lazy chunk (`layout/PanelViews.tsx`; `PanelContainer` loads it at once on the desktop; AppShell's idle preload fetches it, with Settings, 5 s after a web page's start). `scripts/check-main-bundle.ts` fails a build whose first-screen JavaScript (`web.html`'s entry, `../main`, their static imports) exceeds `WEB_FIRST_SCREEN_JS_BYTES` (3,311,000 raw; includes the composer's question asked while the user types (`useAutoModePrefetch`), a paired host's rows and focused tab taking its own lane (`useHostWorkspace`), the transcript's hold on a scrolled-up reader's row (`contentAnchor`), the hosted sessions' sidebar rows, the family rows of sessions opened on a paired device, the phone strip's opened-session rows, the approval card's "Ask and remember" answers, the work board's strip fallback and capped sections, the composer's one Send/Stop button with its Stop menu and the sidebar's own project list (empty and missing projects, Remove from sidebar); the board's session rows are a lazy chunk) or holds the panel views. Parallel sessions each measure against their own base, so their sum can pass the budget on main although none did alone: measure the merged main before raising it.
- **A phone's page never zooms** (the user's report, 23 Oct 2026: a pinch zoomed the whole app, bars and composer off screen). `web.html` (and the dev harness) set `maximum-scale=1, user-scalable=no` in the viewport meta, `mobile.css` gives the shell's body `touch-action: pan-x pan-y` (no pinch, no double-tap zoom), and since iOS Safari ignores both for a pinch, and Chrome's "Force enable zoom" and Samsung Internet's website zoom override them, `web-boot.ts` installs `lib/no-page-zoom.ts` `blockPageZoom`, which refuses WebKit's `gesturestart`/`gesturechange`/`gestureend` and cancels every touchmove of two or more fingers (the user's second report, 23 Oct 2026: the page still zoomed everywhere on a phone). A view that pinches by itself keeps its own `touch-action: none` and pointer handling: the preview stream, and the picture viewer (`ZoomableImage` over `common/use-pinch-view.ts`, math in `lib/pinch-view.ts`: two fingers zoom the fitted picture up to 8× around the point between them, one finger moves a zoomed one within its edges, a tap zooms to 2.5× around the finger or back to the fit; touch pointers only, so a mouse click keeps actual size; reset on close and on a gallery step) and an opened file (the Files viewer's kinds but rendered HTML, `FileViewer` inside `common/PinchZoomArea.tsx`: two fingers scale the view by a transform so the views keep their own layout and scrollers, one finger moves a zoomed view to its edge and then scrolls what is under the finger (`panWithin`), an unzoomed one scrolls natively; touch events only, own non-passive listeners since React's are passive; a new file starts unzoomed; rendered HTML sits in a `sandbox=""` iframe whose touches never reach the area or the page's guard, so it does not zoom (its Source view does) and a pinch inside it is held off the page only by the viewport meta and the area's `touch-action`, which reach into the frame) (the user's call, 23 Oct 2026: pictures and opened files zoom, the page never). Text size is the in-app setting. Pinned by `no-page-zoom.test.ts`, `pinch-view.test.ts` and `e2e/mobile-no-zoom.e2e.ts` (an iPhone in Chromium: a pinch over the transcript and the composer and a double tap leave `visualViewport.scale` at 1, it read 3 before; a pinch over the viewer's picture scales it, not the page, a drag moves it, a tap zooms in and back; a pinch over an opened file zooms it, not the page, and a drag moves it; a pinch that starts inside a rendered HTML file leaves the page at 1, it read 3 with the meta and both `touch-action` rules removed).
- **The manifest sets no `orientation`** (pinned by `manifest.test.ts`): Chromium's WebAPK maps `"any"` to a full-sensor lock overriding the user's rotation lock, and `natural`/`portrait` would stop tablets rotating; never call `screen.orientation.lock`. An installed app picks up a manifest change only after Chrome's WebAPK update check (~1 day) or a reinstall. The manifest (`id`/`start_url`/`scope` `/`, standalone, 192/512/maskable icons, `screenshots/`, a New session shortcut `/#/open?new=1`) and `web.html`'s iOS metas are pinned by `manifest.test.ts`.
- **Installing** (`install.ts` pure decision, `install-ui.ts`, `install-hint.ts`, `host-ui/InstallSheet.tsx`; en/ko `web.install.*`): `installGuidance(env, {promptAvailable, installed})` → `installed` (`display-mode: standalone` / iOS `navigator.standalone` / `appinstalled`), else `ios-share` (every iOS/iPadOS browser; iOS has push only for Home Screen apps), `prompt` (kept `beforeinstallprompt`, used once), `samsung-menu` / `firefox-menu`, or `none`. ### Tailscale
- **Side** (`src/main/tailscale/`; contract `src/shared/mobile-web.ts`; created in `index.ts`; pushes `mobile-web:state` to desktop windows only; handlers `mobile-web:get-state` / `mobile-web:command` on the `IpcRegistry`). `MobileWebService` (`service.ts`) derives `MobileWebPhase` from the world each poll tick (15 s `POLL_MS`; 2 s `FAST_POLL_MS` while Settings watches or a step waits on the user/OS) from `tailscale status --json` and `serve status --json`, never the human text (only a `login.tailscale.com` link is taken from stderr; `openExternal` gets only that host or the control server's).
- `locate.ts` finds the CLI: env `OMP_GUI_TAILSCALE` (never falls through to a real install), pref `mobileWeb.tailscaleBin`, the macOS app binary run with `TAILSCALE_BE_CLI=1`, `/usr/local/bin`, Homebrew, login-shell PATH; Windows Program Files, PATH. `cli.ts` runs it through an injectable executor over `src/main/spawn.ts` (arg arrays, 10 s `CLI_TIMEOUT_MS`); `status.ts`/`serve.ts`/`whois.ts` parse with zod keeping only needed keys.
- **Publishing** is only `serve --bg --https=<port> http://127.0.0.1:<local>/<secret>` (secret path of `web/serve-secret.ts`; see Threat model), from 47831 up to the first unused port, recorded in pref `mobileWeb.serve` (`{host, port, target}`, `target` without the secret). Turning off runs `serve --https=<port> off` only when that record and the handler still match exactly (`ownProxy`: one `/` proxy to the current secret path on any loopback port, or to the bare recorded target an earlier release published; any other path on that address is the user's own handler, never overwritten or removed), then checks the user's other handlers are unchanged, else only the record is dropped. A secret-less handler of ours is republished over itself on the same port (`planPublish` reuses a port only when the handler already proxies to exactly the new target).
- No `serve reset` and no Funnel command in the source (`service.test.ts` greps for both). **The real Mac's own `tailscale serve` (443 → 3010) must stay untouched.**
- Prefs: `mobileWeb.allowedUsers` (default this computer's login; `allowedUsers()`); `mobileWeb.confirmNewDevices` (default **off**; request `set-confirm-new-devices`, `MobileWebState.confirmNewDevices`; `confirmNewDevices()`). `whois(address)` (`tailscale whois --json <ip>`: only ever given an IP, read-only, 4 s `WHOIS_TIMEOUT_MS`; `parseWhois` keeps stable ID, node name, owner login) answers the server's lookups while Mobile web is on.
- **Setup item**: `tailscale` is optional (`setupItemAutomatic` false: never installed at launch or in the background pass, no once-per-launch rule, no back-off ledger; only `installForConnection` and Retry). macOS = the Standalone zip from `pkgs.tailscale.com/stable/?mode=json` plus `.sha256`, then `codesign --verify --deep --strict`, bundle id and team `W5364U7YZB` (`TAILSCALE_TEAM_ID`, `setup/plans.ts`) before `ditto` to /Applications; Windows = winget, else the arch's MSI plus `.sha256` plus a Valid `Tailscale Inc.` Authenticode signature, then elevated `msiexec /qn`.
- **Tests never touch a real daemon**: vitest `fakeTailscaleExecutor` (`test-fake-tailscale.ts`; peers carry `ip`/`stableId`); e2e the fake CLI `e2e/fixture/fake-tailscale.ts` (`fixtureTailscale(dir)` in `fake-tailscale-install.ts`; env `OMP_GUI_TAILSCALE`, `OMP_GUI_TEST_TAILSCALE_OPEN` = stand-in for "start the Tailscale app", `FAKE_TAILSCALE_STATE` scenario JSON, `FAKE_TAILSCALE_LOG` call log).

### Phone preview/terminal
- Web viewers only; desktop paths unchanged.
- **Preview**: a paired web window has no native view, so `preview/host.ts` gives each of its tabs an offscreen `BrowserWindow` (`offscreen: true`, sandbox, contextIsolation; sessions `preview-web-<winId>` / `preview-visual-web-<winId>` with every desktop-page rule: non-persistent, http(s) only, permissions/downloads/new windows refused, remote-tab loopback blocked, the visual session's CSP and egress block). `main/web/preview-stream.ts` (`PageStream`) turns paints into JPEG frames. The viewer's `preview.stream.poll({ack})` is the only transport (`PREVIEW_STREAM_*` in `shared/preview.ts`, all classified in `ipc-policy.ts`); the next frame goes out only after the last was acknowledged (`preview-pacer.ts`: ≤ 12 fps, DPR ≤ 2 phone / 1.5 tablet, `toJPEG` only when sending, nothing for a still page; a page nobody polls for 15 s stops painting, `IDLE_PAUSE_MS`). The renderer's `layout` request carries the surface's `dpr`; `PreviewPanel` mounts `PreviewStreamView` where the desktop leaves a hole for the native view, with no cover-detection layouts.
- **Input** is `webContents.sendInputEvent` (`preview-input.ts`, never a debugger, so `isTrusted` holds and `choose` stays allowed): `lib/preview-gestures.ts` (tap, double tap, swipe/fling → wheel, long press → context, long press+move → drag, pinch → zoom); `lib/preview-keyboard.ts` maps the hidden `textarea`'s `keydown`/`beforeinput`/composition (a composition is sent once, committed, as `insertText`).

- **Terminal**: for a web caller `terminal:request list` is a long poll in the terminals worker (`waitMs` ≤ 1 s `TERMINAL_POLL_MAX_WAIT_MS`: held until a listed session has output past its offset or exited; answers cut to a 64 KB `budget`, `TERMINAL_OUTPUT_BUDGET`); `lib/terminal-poll.ts` sends the next request only after xterm parsed the last output (the request is the ack; an idle shell costs nothing). A desktop window sends neither field and keeps its 80 ms poll.
- **PTY size lease** (`main/terminal/lease.ts`, the S11 decision): a PTY has one size, so one viewer sizes it. A lone viewer holds it implicitly; the first `resize` or an explicit `claim` takes it; typing takes it only when the holder has been idle 15 s (`HOLDER_IDLE_MS`); a holder with no request for 10 s has let go (`PRESENCE_MS`). Every snapshot carries `lease: you | other | free` and the PTY's `cols`/`rows`; an `other` viewer draws the PTY at those cols × rows (xterm `resize`, sideways scroll) and neither fits nor sends `resize`; `TerminalPanel` shows a banner (ko "다른 기기가 크기를 정하고 있어요 · 여기서 맞추기") whose button sends `claim`.

Its keys sit 10 px apart, bounded at 10, so each fills the bar's height and reaches 36 across; the phone's panel tab bar under it keeps its reach inside its 40 px buttons (`--hit-gap-y: 0px`), leaving the keys their bottom edge.
- A phone's Changes view shows the unified diff only (no split toggle); Changes and Files are a list first, then one item; both poll only while mounted and the page is visible.
- Pinned by `e2e/preview-stream.e2e.ts` (real Electron OSR page + fake WS client; 0 frames idle) and `e2e/mobile-panels.e2e.ts` (iPhone and iPad × Chromium and WebKit; `OMP_GUI_MOBILE_PANELS=<dir>` writes captures).
- **A fling through the transcript is never pulled back** (the user's phone, 26 Oct 2026: flinging a long session jumped down and up by thousands of pixels). Three rules in `chat-stream-utils.ts`, wired in `ChatStream.tsx`: `transcriptScrollTo` is the virtualizer's `scrollToFn` and sets its `scrollOffset` at each write (the virtualizer learns a written offset only from the next scroll event, so a row measured in the same frame was compensated from the fling's stale offset and threw the view back by a whole page of older history, 2636 → 275); the page-of-history restore and the changed-row hold let go once `readerMoved` (the view is neither where the hold left it nor where a write since put it: the fling goes on after the finger lifts, past the gesture that used to release them); `compensateRowsAbove` (the virtualizer's `shouldAdjustScrollPositionOnItemSizeChange`) compensates a re-measured row wholly above the view in either scroll direction (stock skips it while the view moves up: 431 px in one frame). Measured on a real 16 MB session through the phone page (Pixel 7 with an Android platform): 4-6 painted jumps of 300-3,500 px per run before, none after. **iPhone and iPad keep stock's iOS rule** (WebKit cancels momentum on a scroll write, so the virtualizer defers its compensations until the fling stops and applies them at once): a jump of the deferred amount at the fling's end remains there. Pinned by `chat-stream-utils.scroll-write.test.ts`.

### Per-device prefs
- On a paired web page (`src/shared/device-prefs.ts`, routed by `src/renderer/web/shim.ts`; desktop unchanged) these belong to the device (`DEVICE_LOCAL_PREF_KEYS`, `isDeviceLocalPref`): theme (`theme`, `themeName`, `systemLightTheme`, `systemDarkTheme`, `followAgentTheme`, `colorBlindMode`), text/density (`fontSize`, `compactDensity`), conversation rendering (`transcriptDetail`, `thinkingExpanded`, `codeLineNumbers`, every `displayPreferences.*`), layout (`sidebarWidth`, `sidebarVisible`, `sidebarFolds`, `sidebarFamilies`, `gui.panelWidth`, `panelSide`, `defaultPanelTab`).
- Kept in the device's own `WebDevice.uiPrefs` record on the host (`web:device.uiPrefs.get/set`, `WEB_DEVICE_CHANNELS` in `shared/web-host.ts`, permission `device-self`, 64 KiB `DEVICE_UI_PREFS_MAX_BYTES`). Agent behaviour, models, accounts, notification policy, the keymap, the sidebar's pins/archive and every other key stay the host's.
- The shim overrides `PREFS_GET`/`PREFS_SET`: a whole-store read is the host's prefs minus device-local keys plus the device's values (`overlayDevicePrefs`; dotted keys nest as the host's store does; a keyed read of a local key reads only the record). A write of a local key goes only to `uiPrefs.set` (serialized, each from the latest copy; a refused write rejects so `saveGuiPreference` toasts), never to the host's prefs, so it cannot reach desktop windows or `nativeTheme`; `PREFS_CHANGED` for a local key is dropped on the page.
- A phone with nothing set follows the system theme (`getPersistedThemeSelection` falls back to `system`) and stock text size; phone sizes come from CSS (`mobile.css`), no phone-only size pref.
- A new appearance/layout pref that should differ per device MUST be added to `DEVICE_LOCAL_PREF_KEYS` (and the list in `device-prefs.test.ts`). Settings › Appearance shows the "This device" note (`settings.appearance.thisDevice*`) on the web page only.
- Pinned by `shared/device-prefs.test.ts`, `web/device-prefs.test.ts`, `e2e/device-prefs.e2e.ts`.
