## Multi-viewer and mobile web

### Multi-viewer
- **Ownership** (`sidecar-pool.ts`, whose rules are the core's `native/ompdesk/crates/core/src/pool/` since batch H2, native-rust › 9d, 9e): a tab has one owner window and may have viewer windows (`attachViewer`). Only a paired web device's window (negative ids) views another window's tab: `tab-spawn.ts` attaches instead of refusing an owned session. Env `OMP_GUI_TEST_VIEWER_WINDOWS=1` lets any window (`e2e/multi-viewer.e2e.ts`). Each window keeps its own active/visible/split view; the full channel is wired once per tab and fans out to every window showing it; the light channel reaches owner and viewers.
  - A host's window also shows the tabs its `LocalHostServices` runs for paired devices as hosted views (see remote-devices › Host windows see the device's tabs).
  - **One encoding per batch for every window**: each window keeps its own `message_update` slimmer (a window that joined mid-message needs the whole snapshot), but slimmers at the same message get the same array the first one made (`createMessageUpdateSlimmer` keeps each batch's result per starting message; a paired computer's link encoder uses it too), and `#wireFull` hands those windows one push object. A web page's frame text is made once for every page and connection (`WsRouter.dataText`, under Server and auth). Measured by `src/main/remote/fanout-cpu-report.test.ts`; bytes to each receiver unchanged.
- A viewer closing the tab only leaves it (`detachViewer`); the owner's close releases it for all. `TAB_LIST_CHANGED` → viewers apply `applyTabList` (`shared`/`viewerCount` drive behaviour only). The user's rule: **nothing on screen says a tab is shared** (no title-bar chip, no line under the composer).
- **Asks**: the first window to answer wins; the others get a synthetic `cancel` (`answeredElsewhere`, toast "Answered on another device"); a later answer fails `already_answered` (toast, card closes).
- Aggregation: draft-empty per window (`noteDraft`); subagent stream level = highest any viewer asked (`noteSubagentLevel` for windows; a paired device viewing a window's tab counts too through its `HostedTabView`'s port `subagentLevel`, and any viewer leaving recomputes the level so the device keeps its stream; pinned by "keeps the device's subagent stream" in `sidecar-pool.test.ts`); a mode toggle makes others re-read (`noteModeChanged` → `config_update {modes: true}`); a shared tab's notification is deduped across windows; its terminals are keyed by the owner window; `PREFS_SET` pushes `PREFS_CHANGED` to the other windows.
- **Renderer rules for a shared tab** (`stores/messages.ts`, `composer-submit.ts`): on a shared tab or web page a plain message goes as `prompt(streamingBehavior)` and the host decides steer/follow-up (`hostDecides`). An optimistic echo is claimed only by the delivery with its own text (`sharedTab`, `ownSends`); any other user delivery is another viewer's (`fromOtherViewer`, "from another device"). The dequeue's `omp:fill-composer` names the asking `tabId`. Quota resume runs in the owner window only. A web page keeps its own done marks (`lib/unread-marks.ts`).
- **What an extension shows outlives the page that saw it set**: main keeps each tab's latest `setStatus` per key, `setWidget` per key and `setTitle` (`PoolEntry.uiState`, dropped with its omp) and gives them to a page that loads later (`EXTENSION_UI_STATE` = `ui.shownState()`, read at the page's start and in a web page's resync beside `openRequests`), because no frame repeats them. Pinned by `sidecar-pool.test.ts` ("keeps a tab's status texts") and the reload step of `e2e/extension-ui-rpc.e2e.ts`.
- **Prompt origins**: before a prompt/steer/follow-up from a paired web device (every window under the test hook) reaches the omp, main sends the bridge `prompt_origin_set {origin, text}`; `resources/gui-bridge/prompt-origin.ts` journals that device for the message with that text; `labelPromptOrigins(…, null)` marks every prompt of a local transcript with `promptFromId`; `ipc.ts` localizes each `get_transcript_page` per window (`localizePromptOrigins`: own prompts plain, the host's named with the computer's name). A live delivery on another window says only "from another device" until the transcript is re-read.
- **A paired web device's tabs survive this computer's relaunch** (`main/web/web-tab-layouts.ts`, pref `webTabLayouts`: device id → `PersistedTabLayout`). Its `WebClientWindow` id is new every launch, so `SidecarPool.onWindowTabsChanged` files the layout under `deviceId` (never while `quitApproved()`; a window with no tab left forgets it). At launch, after desktop windows and before `turnResume.launch()`, `restoreLayout` puts each still-paired device's layout into `webHost.windows.windowFor(deviceId)` (deferred tabs). A revoked/blocked/expired device's layout is dropped (`devices.onRevoked`); one for a device no longer listed is pruned. Desktop `tabLayouts` are untouched.
- **One session, one tab, one omp on its file**: a web window's layout also names the stored sessions it views (saved again when it starts/stops viewing one or their owner closes it); its restore views a session a desktop window already holds (`attachViewer`) instead of opening a second tab; a desktop window's restore skips a session another desktop window holds. A page whose spawn is refused `owned` by a tab of its own window it has not listed yet reads the tab list and switches to it (`openTab`); a web page never answers a refusal with "open in a new window".
- **An agent closes a web page's tab in main**: the close decision (`closeWindowTab`, `tabCloseStep`, `unreported`) is control-tools' (see control-tools › Beyond the caller's window); the layout above then forgets the tab. The page side: its `FileEditReporter` sends `tabs.reportFileEdits(dirtyTabId)` (`FILE_EDIT_REPORT`) on every Files editor change and every `open` connection, and main keeps the latest per connection (`web/file-edit-reports.ts`).
- Pinned by `web-tab-layouts.test.ts`, `sidecar-pool.test.ts`, `tabs.test.tsx`, `e2e/mobile-autopilot-rows.e2e.ts` (`e2e/fixture/phone-serve.ts` plays `tailscale serve` for a Chromium page on `http://localhost`).

### Server and auth
- **Server** (`src/main/web/`; `WebHost` in `web-host.ts`, created in `index.ts`): HTTP + WebSocket on `127.0.0.1:47831` only (when free); `tailscale serve` publishes it (see Tailscale). `server.ts` serves the built renderer from an allowlist (`/` and `/pair` → `web.html`; `STATIC_DIRS` `/assets/ /cmaps/ /standard_fonts/ /wasm/ /icons/ /screenshots/`; manifest; `sw.js`; traversal refused), plus `POST /api/pair`, `POST /api/session` (device signs a server nonce with its WebCrypto key → 30 s single-use ticket, `TICKET_TTL_MS`), `/ws`, `/blob/<token>` (Range; HTML/SVG download only), `POST /upload` (25 MiB a file, 200 MiB a device per 24 h, deleted after 24 h: `uploads.ts`).
  - **Brotli comes from the build**: `scripts/precompress-plugin.ts` writes `<file>.br` at quality 11 beside every compressible file over 1 KB the page loads (`assets/`, `web.html`, `sw.js`), and `server.ts` `#brotliOf` sends it to a browser that accepts br; a file without one (e.g. an older build's archived chunk) is compressed once at quality 9; both kept in memory. Quality 11 never runs per request, because it is ~40× slower than 9. Pinned by `server.test.ts` ("the build's own brotli").
- **`auth.ts` checks every request in this order**: loopback peer; any `Tailscale-Funnel-Request` refused; **secret path prefix** (`stripServePrefix`, constant-time; without it, or before serve is published, a bare 404 and no header is read; stripped so the page never sees it); `Host`, `Origin`, `Sec-Fetch-Site`; `Tailscale-User-Login` (RFC 2047-decoded) against the allowed logins. A login not allowed, or none (tagged node), gets `refusal-page.ts`'s HTML (`Accept-Language` ko/en; JSON `tailscale_user_not_allowed` / `no_tailscale_user` for an API call).
  - **A relaunched host answers its own secret 503 until serve is confirmed** (`RequestPolicy.pendingPrefix`, set by `WebHost.start`): serve keeps forwarding while the app restarts, before Mobile web has read serve's status and configured `servePrefix`; a 404 there made the worker give up a chunk the new build has, while 503 is an outage the worker retries (`ASSET_OUTAGE_MS`). Without the secret it is still the bare 404. Pinned by `auth.test.ts` and `server.test.ts` ("answers 503 under its own secret").
- **Identity is Tailscale's**; the device cookie serves later calls (`__Host-ompdesk` over HTTPS; `devices-store.ts`: `web-devices.json` 0600, only the secret's SHA-256, 14 days sliding / 90 absolute, record keeps the Tailscale `nodeId`).
- **`POST /api/pair`** (no code: an allowed login's first visit makes the device and cookie) asks `tailscale whois` about serve's `X-Forwarded-For` address (injected `whois`, cached 60 s); the device is named after the node. Refused: a login whois does not put behind that address (`identity_mismatch`), a blocked node (`blocked`), > 10 tries a minute per address (30 overall) or 20 new devices an hour (`PairingGuard`, `NEW_DEVICES_PER_HOUR`).
- **Approval**: with "Approve new devices on this computer" (pref `mobileWeb.confirmNewDevices`, default **off**; the one switch for phones and computers alike, see Remote devices › Gate) `PairingConfirmations` (`pairing.ts`) holds the visit until the desktop approves (`WEB_PAIRING_REQUEST`, desktop windows only, 60 s); otherwise the desktop is told once after the fact (`WEB_DEVICE_CONNECTED`, desktop windows only; toast with Block).
- **Block** (`WEB_DEVICES_REVOKE`, `WebHost.block`) is a revoke that sticks: `blocks-store.ts` (`web-blocked.json` 0600) keeps the node's stable ID, never the login (one login has many devices); every record of that node is revoked (sockets close 4401, virtual window destroyed). A cookie-less page load while a block exists, and `/api/pair`, look the visitor up (`whois`) → "this device is blocked" page / `blocked`. A visitor whose node cannot be told while its login has a blocked node is held back (`unidentified`, fail closed). A device with no node identity is blocked by its login (`WebDeviceInfo.blockScope`; the confirm and Blocked list say every device of that login). `WEB_BLOCKS_LIST`/`WEB_BLOCKS_REMOVE` list/lift. Expiry only deletes the record. A revoked device that returns is refused, not re-enrolled, until Unblock.
- **`ws-router.ts`** turns `inv`/`snd` frames into `IpcRegistry.invoke/send` with the device's `WebClientWindow` (`web-client-window.ts`, negative id, parked while no socket) as caller once `IPC_POLICY` and the device's grants allow the channel (`web_forbidden` otherwise; `pairing-admin` never served; a web device cannot write `mobileWeb.*` prefs). Model commands metered through `PeerQuota` (`remote/peer-quota.ts`); pushes batched every 75 ms (slim `message_update` deltas joined); streams stop while the page reports itself hidden; ping every 20 s (three quiet ticks end a socket). **A call's answer goes after every event pushed before it** (`#reply` flushes the batch first), the order the desktop's IPC keeps, so a page never reads an answer older than the events it has not yet applied (pinned by `ws-router.test.ts` "ahead of it").
  - **A streamed push's data is written once** (`WsRouter.dataText`): `coalesceEvents` names the queued pushes each frame was made of (`from`), and the router keeps the data's JSON per first push, so every connection whose batch joined the same pool pushes splices the same text into its own `{"t":"evt","seq":N,...}`. Only `STREAM_CHANNELS` (fresh objects from the pool, never changed); another channel's data may be an object a handler changes and pushes again, so it is written each time. Pinned by "writes a streamed push's data once" in `ws-router.test.ts`.
- **Web-only calls** (`web:host.*` browse/save/open/reveal/blob; `web:models.config.read/write` = models.yml as text via `readModelsText`/`writeModelsText`: parser + schema check, atomic, refuses a file changed since read; `web:device.uiPrefs.*`; `shared/web-host.ts`, `host-actions.ts`) are a table in the router, not `IPC_POLICY`. `FS_READ_BINARY` answers `{dataBase64}` ≤ 512 KiB, else `{blobUrl}`; `FS_MEDIA_STREAM` answers a `/blob` URL from `MediaStreams`.
- **Tests** use injected clocks/`Timers`; `server.test.ts` runs the real server on an ephemeral port behind the prefix with serve's headers (stubbed `fetch`), faking only the IPC registry, desktop window and `whois`.
- **Pictures never ride the socket**: a frame holds 1 MB (`MAX_FRAME_BYTES`; the page refuses a bigger request) and a phone photo exceeds it even after the composer scales to `IMAGE_MAX_SIDE`. `shim.ts` sends any call holding an inline `{type:"image", data, mimeType}` through `upload.ts` `liftInlineImages` first (bytes to `POST /upload`; the block becomes `WebUploadedImage {type, mimeType, upload: <host path>}` from `shared/web-protocol.ts`; a refused/lost upload fails the call with `web.upload.image*`, nothing sent); `ws-router.ts` `#landUploads` reads each back into `data` before the call (`UploadStore.take`: only this device's `<device>/<uuid>/<name>`, deleted once read; missing → `file_not_found`). Calls without such a block stay synchronous. Pinned by `shim.test.ts`, `ws-router.test.ts`, `uploads.test.ts`, `e2e/mobile-attach.e2e.ts`.
- **A browser without `OffscreenCanvas` sends a photo as taken**: `fileToImage` (`composer/input-area-utils.ts`) scales a PNG/JPEG/WebP past `IMAGE_MAX_SIDE` with `OffscreenCanvas` and returns the file itself where that, `createImageBitmap` or the decode is missing (Playwright's WebKit on Windows has no `OffscreenCanvas`). `e2e/mobile-attach.e2e.ts` asks the phone's page which it is, then expects a smaller JPEG or the same bytes; a HEIC the browser cannot draw is the photo chip, so that test asks the page whether it draws one too.
- **Attaching on a phone**: on touch the composer's + menu has **Photos** (`accept="image/*"`: Android offers gallery and camera only then) and **Attach files** (no `accept`). A phone's picker is another app, so the page goes hidden and `change` arrives just after it returns; a reload then would drop every pick. Every pick is tracked from the input's click until its files landed (`lib/file-pick.ts` `trackFilePick`/`filePickInProgress`; `cancel` ends it, or 3 s back in front without `change`); `safeToReload` waits for it and the last-resort reload goes through `sw-update.ts` `reloadWhenUnused`. A non-image file goes up through `fs.pathForFile` (composer shows a `[data-upload-chip]` "Sending … to your computer", then mentions its host path); a failed upload rejects with its worded reason (`web.upload.*`, 25 MB cap checked on the phone), shown as a composer error, nothing inserted. Pinned by `file-pick.test.ts`, `sw-update.test.ts`, `safe-moment.test.ts`, `composer-files.test.ts`, `InputArea.queue-shorthand.test.tsx`, `e2e/mobile-attach.e2e.ts`.
- **Coming back is cheap** (`ws-router.ts`, `ws-transport.ts`): the page's return to foreground sends `hello` again only when the host dropped stream pushes while hidden (resync in place, no reload). A reconnect offers `resume.<connId>` as a subprotocol; `WsRouter.attach` answers `resumed: true` when that connection ended with every event acknowledged, nothing queued/dropped, no push since (`#pushes`; ended connections kept 10 min, `RESUME_WINDOW_MS` in `ws-router.ts`); `server.ts` first retires a still-open old connection of that id. A call the drop failed makes the page resync anyway. Perf audit: `e2e/web-perf.e2e.ts`, opt-in `OMP_GUI_WEB_PERF=<dir>` (fake serve plays a phone link; `_SUBJECTS=before=<checkout>,after=<checkout>`, `_PHASES`, `_RUNS`, `_MINUTES`, `_PROFILE=1`).
- **A dead link is noticed in seconds and left at once** (the owner's rule). `ws-transport.ts`: a drop retries at once, then after 0.25, 0.5 and 1 s and every second while the page is seen (doubling to 8 s while hidden), jitter only shortening a wait; an attempt gives up on its ticket after 4 s (`fetchTicket`'s `AbortSignal`, because a request sent on a dead route is never answered) and on `hello` after 5 s; `wake()` (visible, online, pageshow) abandons an attempt older than 1 s for a fresh one. While seen, 5 s without a frame makes the page ask (`ping`) and 2.5 s without an answer drops the link (a silent socket otherwise looks open for the host's heartbeat); hidden, it judges nothing and asks on its return. Each drop catches up in place (`resumed` is false while a reply streams), keeping the same transcript element, reading position and draft. Measured by `e2e/phone-reconnect.e2e.ts` (fake serve playing cut, refused and black-holed links).
- **Web host sheets** (`src/renderer/web/host-ui/`, `<WebHostUi />` in `App.tsx`, nothing on the desktop): the web page has no native dialogs, so `shim.ts` calls `web/host-hooks.ts` hooks that `WebHostUi` registers, one sheet at a time (`host-ui-store.ts`): `PathActionsSheet`, `SaveImageSheet`, `HostBrowserSheet` (the computer's folder/file/save browser over `web:host.listDirs`; also replaces the project picker), `EditorSheet`, `ModelsConfigSheet`, `ConfirmSheet` (restart for update, quit; names running turns). A link opens on the device at once with a toast to open it on the computer. A device without `desktop-control` gets `hostUi.computerOff`. Every sheet has a test in `host-ui.test.tsx`. `ConfirmSheet` keeps its sentence and the running turns in the body, so a confirm with no running turn has no empty band, and has no header ✕ beside its footer's Cancel (`closeButton={false}`; Escape, the scrim and the handle still cancel).
  - A sidebar session row's actions are one ⋯ button (`data-sidebar-row-menu`, label "Session actions"/"세션 메뉴") on every input, never separate rename/archive/delete buttons, so the title keeps its width (the user's call): at rest on touch (`data-input=touch`, opening an action sheet; `mobile-shell.e2e.ts`), on hover or keyboard focus on the desktop (the roving tab stop's ⋯ is the next Tab stop, Enter opens, Escape closes back to it). It opens the row's menu in `rowMenuItems` order (`Sidebar.tsx`: rename, pin, move, archive/restore, delete, then the right-click menu's rest without Open), the same list a right click shows in its own order. On hover the ⋯ takes the age's place (`ListRow` `actionsOnHover`: the meta steps aside and the title runs on under the fade to the ⋯).

### Threat model
- The user's rule: no pairing code. Copy the tailnet URL, open it on any device signed in to the same Tailscale account, and it works. No pairing-code step anywhere.
- **Who may connect**: a request through `tailscale serve` with a `Tailscale-User-Login` in `allowedUsers` (default: this computer's own login; Settings › Mobile web), over a tailnet only. Serve, never Funnel: `service.ts` has no Funnel command, an `AllowFunnel` flag on our port (`funnelExposed`) stops the server, `Tailscale-Funnel-Request` is refused. Anyone who can sign in to an allowed account on a tailnet device, and anyone the user shared the computer's node with while that account is allowed, can make a device and gets `DEFAULT_WEB_GRANTS` (never `pairing-admin`). The user's tools: the approval setting, the notice's Block, the Devices list.
- **Forged headers**: a local process can write `Tailscale-User-Login`/`X-Forwarded-For` to `127.0.0.1:47831`. Serve joins its target's path to every request's path, so `service.ts` publishes `serve --bg --https=<port> http://127.0.0.1:<local>/<secret>` (256 random bits; `serve-secret.ts`, `web-serve-secret.json` 0600, made on first use). Only traffic through serve carries it; without it nothing is served (404) and no header is read (`auth.test.ts`, `server.test.ts` "headers forged on the loopback"). The secret is never in prefs (`mobileWeb.serve` holds the local address only) and never logged.
- **Residual risk**: the secret is in `tailscale serve status` and the 0600 file, so a same-user process can read it and forge a login (and an `X-Forwarded-For` whois accepts; whois' cross-check only catches a self-contradicting forgery). Such a process already reads the cookie store, prefs and user files, so a single-user Mac is not defended against it (another OS user reads neither file). `Host`/`Origin`/`Sec-Fetch-Site` stop a browser page reaching the loopback port.
- **Not defended**: a compromised allowed account or tailnet device (use Block and approval), Tailscale's control plane. **Block** is by node, not login.
- **The control socket is this computer's, never the page's**: a tab the phone page owns and its Terminal panel get only `OMPDESK_CONTROL_OFF=1` (see control-tools › Control socket and the `ompdesk` CLI, **Env, per spawn**). Residual: it runs as this user and can read `<userData>/control/token` like any same-user process (see Residual risk above); the marker stops accidental use, not a session bent on reading the user's files. A desktop window's tab a phone views keeps what its owner gave it at spawn. Pinned by `sidecar-factory.test.ts` and `control-socket/cli.test.ts`.
- **UI** (`settings/MobileWebSection.tsx`): once ready, the link in a monospace line with a big **Copy link** button and one QR (`MobileWebConnect.tsx`: install Tailscale, same account, open link, iOS Home Screen note); the approval switch (`set-confirm-new-devices`); connected devices with **Block** (`MobileWebDevices.tsx`; confirm names `revokeBodyLogin` when `blockScope` is `login`); the **Blocked** list with Unblock (`MobileWebBlocked`, `stores/mobile-web.ts` `blocked`, re-read when the device list pushes); allowed accounts. The desktop shows a new device as one toast with Block (`dialogs/WebDeviceNotice.tsx`, `mobileWeb.devices.onConnected`) or, with approval on, `WebPairingDialog`.
- **`/pair`** (`web/PairScreen.tsx`) has no form: a browser whose session is refused makes the device key, calls `POST /api/pair` (`pairing.ts` `pairFailureOf`: blocked / account not allowed / declined / rate limited) and enters, or shows the reason with Try again; a browser that can already get a ticket just goes on. `e2e/mobile-web.e2e.ts` plays the phone with the fake Tailscale's headers through the prefix.
- **Computer sharing** (OMPdesk to OMPdesk) has the same identity and no code; its gate (`not_tailnet`, whois, allowed logins, Mobile web's blocks), key pinning (`key_mismatch`) and `OMP_GUI_TEST_REMOTE_LOOPBACK` are remote-devices' (see remote-devices › Tailscale only, transport, routing). Threat-model facts it adds: the host does not even listen off the tailnet, so a loopback, LAN or forged source gets nothing; WireGuard makes the source address the node's identity; no Funnel (the host never publishes through serve); Block is by node and shared with Mobile web; PeerQuota, grants and `host.*` routes are unchanged. **Not defended**: a compromised allowed account or node (it connects like the user's own computer until blocked; approval of new devices narrows the first contact), Tailscale's control plane.

### Reloads
- A phone's page never reloads or crashes by itself; these rules keep it so (`src/renderer/web/`).
- **Every reload says why**: `reload-reason.ts` notes `{reason, at, details}` in `localStorage` just before it (`update`, `outdated`, `resync-failed`, `chunk-load-failed`, `error-boundary`); `web-boot.ts` sends kept reasons as `web-reload` runtime-log lines on each connect. Renderer code reloads only through `lib/page-reload.ts` `reloadPage(reason)` (`WebRuntime.reload`).
- **Missed events never reload**: `ws-transport.ts` `onResync(cause)` (`missed-events`, `lost-calls`) runs `resync.ts` `PageResync` (one pass at a time, a reconnect during a pass reruns it, a failed pass retried after 2 s × failures) over `resync-page.ts`: `reconcileTabs({resync: true})` (the host's list is the whole truth: a restarted host gives new tab ids, and a tab known only from the list takes its status into its runtime, else Send stays disabled; each hidden tab that runs or still counts a live subagent reads its roster again, panels-sidebar.md › Pushes this page missed); `hydrateTabSession` of each visible ready/running tab (merges while a reply streams); `settleTabExtensionUiRequests` (shows missed asks, drops blocking asks answered meanwhile); `loadRemoteState`; `refreshHeldSessionLists`; then `WebRuntime.onResynced` listeners. A streaming reply gets missed deltas back: every hello sending the page to resync (`resumed: false`) makes the host resend each tab's next `message_update` whole (`WsRouter` `onResync` → `SidecarPool.resnapshotWindow`), and the messages store snapshots the message it streams when longer than its buffer. Only after three failed passes in a row does it reload, via `reloadWhenUnused` (hidden, or a launch/return moment that is `safeToReload`).
- **A call the outage failed counts as lost, even before the first connection**: a call that waited `connectWaitMs` (15 s) for a link that never came fails and marks the transport's `lostCalls`, so the next `hello` resyncs (`lost-calls`) though the page never connected before; otherwise a page booted offline keeps its ghost tabs and the outbox cannot send (remote-devices.md › Link loss: what the person sends waits). Pinned by `ws-transport.test.ts` and `e2e/phone-offline-send.e2e.ts`.
- **Updates only while unused**: `sw-update.ts` `ResumeGate` is open at launch and on a return after ≥ 30 s hidden (`RESUME_AFTER_HIDDEN_MS`) for 15 s (`RESUME_WINDOW_MS` in `sw-update.ts`) or until the first `pointerdown`/`keydown`/`wheel`/`touchstart` (a scroll alone does not count); `applyUpdate` resumes a waiting worker only then. An `outdated` page (host's `minClient` newer) cannot talk to the host and waits only for `safeToReload`; before the app loaded it purges at once.
- **The host's build**: `web.html` names its page build (`<meta name="omp-build">`, `WEB_BUILD_META`, the id its worker carries too, `scripts/pwa-plugin.ts`); the host reads it at `WebHost.start` and says it in every `hello` (`build`). A page whose build differs is behind its host: at the next safe launch or return moment it drops its worker and caches and loads from the host (`applyUpdate` in `web-boot.ts` over `HostBuildMove` in `sw-update.ts`), instead of waiting for its worker's update, which a first touch outruns (`e2e/phone-host-rows.e2e.ts`).
  - The move is recorded (`BUILD_MOVE_KEY`, `sessionStorage`) only as the reload happens, never before the purge (a move cancelled during cleanup must not trap the page on its old build): one reload per host build per browser session, and a page that reloaded and still differs is left to its worker's update (no loop). Pinned by `sw-update.test.ts` "HostBuildMove".
  - One move at a time: a moment during a move's cleanup starts no second one.
  - Every `web-reload` line carries `build` (the build the reload landed on) and `from` (the one it left), so a real phone's build can be read from the host's log.
  - A change an older page cannot follow MUST bump `WEB_PROTOCOL_VERSION`.
- **Chunks of an old build** (a page left open, or booted from its worker's stale-while-revalidate shell, asks for hashed lazy chunks the new build lacks; mount dialogs from their first open, never at every launch). Three layers:
  - Host: `main/web/asset-archive.ts` copies each build once at `WebHost.start` into `<userData>/web-assets/<build>/` (build = hash of `web.html`; replaced builds kept 7 days, at most 2: `ARCHIVE_RETAIN_MS`, `ARCHIVE_MAX_PREVIOUS`); `server.ts` serves a missing `/assets/` file from them by name only. Each asset is read and written, never `copyFile`d: in a packaged app the renderer is inside `app.asar`, and Electron serves a copy, `open` or read stream of a file there by first copying it to a temp file of its own that it never removes (`.com.seuput.ompdesk.XXXXXX` on macOS); one `copyFile` per asset left a build's 218 assets, 15.6 MB, in the owner's temp folder at every update (12 Nov 2026; proved on Electron with an asar of three files: `copyFile` left three temp files after quit, read and write none). Pinned by "main's code over the app's own files" in `user-folder-fs.test.ts`.
  - Worker: `sw-core.ts` keeps every hashed `/assets/` file of its build it fetched (`omp-assets-<build>`, `RUNTIME_LIMITS` 24 MB / 150, oldest out), retries a failed fetch once after `ASSET_RETRY_MS` (400 ms), then takes another build's copy of the same name. While the host does not answer or answers a 5xx it keeps retrying, each wait doubling, for up to `ASSET_OUTAGE_MS` (30 s); a 404 gives up after the one retry. WHY: a browser keeps a failed module import for the page's life, so a short outage during the idle preload would leave views empty until a reload (pinned by `sw-core.test.ts` "short outage").
  - Page: lazy views go through `lib/chunk-load.ts` `lazyChunk`/`loadChunk` (one retry, then the view renders nothing); other failing Vite dynamic imports count via `vite:preloadError` unless a retry recovered within 3 s. A failure for good **never asks the user anything** (updates are automatic: no banner, no button; the user's rule): it marks the build stale (`useChunkFailureStore`), `web-boot.ts` marks the page outdated (`markOutdated()`; `chunkStale`), and the update gate reloads at the next unused, safe moment, reason `chunk-load-failed`; a page without a worker purges through the same gate.
  - The idle preload starts only right after the computer was heard (AppShell, `WebRuntime.linkAnswered` → `WsTransport.answered`: on an open link the page asks with a `ping` and any frame answers; a link that is down, or dropped because the question went unanswered, answers with the next `hello`), because a link that reads open can be a dead route and a module load cannot be aborted: a preload sent there holds the browser's connections and blocks the reconnect. Pinned by `ws-transport.test.ts` and `e2e/phone-reconnect.e2e.ts`.
  - A reload for a chunk never repeats at launch: `purgeNow` records it (`sessionStorage` `CHUNK_RELOAD_KEY`), and a page whose chunk fails again within `CHUNK_RELOAD_LOOP_MS` (30 s) of one skips its launch moment (`chunkReloadRepeats` → `gate.used()`), so a chunk no build or archive has waits for a return after ≥ 30 s hidden instead of reloading in a loop (pinned by `sw-update.test.ts`).
  - On a web page `RootErrorBoundary` shows a quiet empty screen for a chunk error (`data-app-stale`, no text/button), marks the app gone (`appGone`) and reloads via `reloadWhenUnused` over `appGoneMoment`. Typed text does not hold it (the composer saves its draft as it unmounts, `InputArea.draft-unmount.test.tsx`); a picture, unsaved edit, pick, upload and (visible) an open question still do. A desktop window keeps the ordinary crash screen. A failed locale chunk is forgotten so the next use retries.
- **Muted errors**: every script tag carries `crossorigin`; a "Script error." with no file/line is logged with `details.muted` and the user agent.
- `session-tree-layout.ts` (`panels/`) is iterative in both passes, so it cannot overflow the stack (`session-tree-layout.test.ts`, 100,000-entry chain).
- Agents, Stats, Settings and the side panel's views are preloaded once the page idles, so only the feedback, model setup, debug console, theme picker and import dialogs are lazy-on-demand (the debug console and the theme picker stay mounted from their first open, so the console's request and result outlive a close; the theme picker and the SSH question dialog, `settings/SshPromptDialog.tsx`, stay off the phone's first screen).
- Pinned by `reload-reason`/`resync.test.ts`, `resync-page.test.ts`, `sw-update.test.ts`, `sw-core.test.ts`, `ws-transport.test.ts`, `chunk-load.test.tsx`, `RootErrorBoundary.test.tsx`, `tabs.test.tsx`, `asset-archive.test.ts`, `server.test.ts`, `ws-router.test.ts`, `messages.test.ts`; on the built app by `e2e/web-no-reload.e2e.ts` (Chromium and WebKit: drop mid-reply caught up in place; old-build chunk served from kept assets; a missing chunk reloads only on a later return), `e2e/mobile-autopilot-rows.e2e.ts`, `e2e/mobile-attach.e2e.ts`. A page load in those specs is `domcontentloaded` (or a `window` marker), never `framenavigated`.

### PWA and push
- **Web Push, host side** (`shared/web-push.ts`; `main/web/{vapid-store,push,web-push-notifier}.ts`): `VapidStore` keeps the VAPID keypair in `<userData>/web-push.json` (0600, atomic; a missing/corrupt file makes a new pair and `WebHost` then drops every stored subscription). `PushSender` = the `web-push` package behind an injectable `PushTransport` (tests inject a fake): one attempt; TTL asks 6 h / news 1 h / `clear` 2 min; urgency `high` for asks; 404/410 → `forgetPushSubscription` (only while still the refused endpoint); else logged.

An endpoint must be a push service's `https` DNS name on the default port (`isPushEndpoint`: loopback, LAN, tailnet, IP literals refused).
- `WebPushNotifier` is driven by `SidecarPool.observeTabs` (`TabActivity`; `tabFacts`; a provider sign-in's requests are never asks) through `WebHost.tabActivity` only while the server runs. A settle is announced 1.5 s later (`COMPLETION_DEBOUNCE_MS`) unless the tab ran again, was Stopped, waits for the connection or stock's retry, or that run was already announced. It reuses `NotificationBatcher` unchanged in rules (one extra batcher whose "windows" are paired devices, fed only the categories each device switched on; `retract` for an answered ask): ask > error > completion, first event at once, one summary after 4 s replacing the first banner (same tag, `silent`).

Text is the host's UI language (`push.*`, `batch.*` in `i18n-text.ts`). Tags are `tab:<tabId>` (a one-tab summary keeps its `tabId`, several has none).
- **Service worker** (`src/renderer/web/sw.ts` at `/sw.js`, scope `/`; built by `pwaPlugin` in `electron.vite.config.ts` with the precache list and a build id; `scripts/pwa-plugin.ts` is a `BUILD_SCRIPTS` input of `build-cache.ts`). Logic in `sw-core.ts` (browser objects injected, unit-tested with fakes): `push` parses a `WebPushPayload` (unknown `v` ignored) and shows it (`tag`, `silent`, `data{tabId,url}`); `clear` closes its tag's notifications and shows nothing; `notificationclick` focuses an open page (posting `{type:"notification-click",payload:{tabId}}`, routed by `notify.ts`) or opens `notificationOpenUrl`.
- **Caches**: `PRECACHE_LIMITS` 8 MB / 80 (eager chunks plus the static closure, never lazy chunks). Cache-first for those hashed `/assets/` files and (`omp-assets-<build>`) every hashed `/assets/` file of its build the page fetched; stale-while-revalidate for `/` (network when nothing cached); never touches `/api /ws /blob /upload /healthz`; one `omp-shell-<build>` and one `omp-assets-<build>` per build, older deleted on activate. The page registers the worker only after the app (`../main`) loaded, and the install takes hashed assets from the HTTP cache (`cache: "default"`), so a first visit downloads its shell once.
- **The head's un-hashed files are shell files** (`SHELL_FILES` in `sw-core.ts`: the blocking `/pre-paint.js` and `/manifest.webmanifest`): fetched at install (`cache: "reload"`) into `omp-shell-<build>` and answered stale-while-revalidate, never from the network first, so a reload while the host refuses connections still gets `load`. Pinned by the shell-file case in `sw-core.test.ts`; the unhashed icons are not kept.
- **Updates apply by themselves, no banner, no strings** (the user's rule): a new worker waits; `UpdateWatcher.resume(moment)` (only while `ResumeGate` is open, see Reloads) sends `skip-waiting` and reloads once it controls the page. Only a worker waiting behind a different controller is an update (WebKit reports a first install's worker as `waiting` while it already controls the page). An `outdated` host is marked by `markOutdated()` and waits only for `safeToReload`, using `purgeAndReload` (unregister the worker, clear caches, load from the network; cleanup bounded by `PURGE_CLEANUP_MS` 3 s because WebKit has left a cache delete unsettled; the safe moment is re-checked right before the reload). One reload per watcher (`#applying`). `sw-update.test.ts`.
- **`safeToReload(SafeMoment)`**: page visible, composer draft and attachments empty, no ask/approval/plan card open, no upload in flight (`uploadsInFlight()`), no unsaved Files editor change (`fileEditDirty`/`pendingFileSwitch`), no host sheet/dialog on screen (host editor and models-config drafts live there); `safe-moment.ts` `pageSafeMoment` reads it from the stores. The draft is persisted per session anyway.
- **Static assets**: `/manifest.webmanifest` and icons (`icons/icon-192|512|maskable-512.png`, root `apple-touch-icon.png`) in `src/renderer/public/`; PNGs from `bun run gen:icons` (`scripts/pwa-icons.ts` from `PWA_ICON_SVGS` in `brand-svgs.ts`). Static files and the manifest need only the serve walls, never the device cookie.
- **Page side**: `push-client.ts` (`PushClient` over `GET|POST /api/push`; the permission prompt is the first await of `enable()` so it keeps the click's user gesture; a changed VAPID key resubscribes), `pwa.ts` (`webPwa()`, non-null only on the web page). - **First screen stays small**: the side panel's views are a lazy chunk (`layout/PanelViews.tsx`; `PanelContainer` loads it at once on the desktop; AppShell's idle preload fetches it, with Settings, 5 s after a web page's start).

### Tailscale
- **Side** (`src/main/tailscale/`; contract `src/shared/mobile-web.ts`; created in `index.ts`; pushes `mobile-web:state` to desktop windows only; handlers `mobile-web:get-state` / `mobile-web:command` on the `IpcRegistry`). `MobileWebService` (`service.ts`) derives `MobileWebPhase` from the world each poll tick (15 s `POLL_MS`; 2 s `FAST_POLL_MS` while Settings watches or a step waits on the user/OS) from `tailscale status --json` and `serve status --json`, never the human text (only a `login.tailscale.com` link is taken from stderr; `openExternal` gets only that host or the control server's).
- The CLI is the core process's (`native/ompdesk/crates/core/src/tailscale/`, native-rust › 4a): `locate.rs` finds it (env `OMP_GUI_TAILSCALE`, which never falls through to a real install, pref `mobileWeb.tailscaleBin`, the macOS app binary run with `TAILSCALE_BE_CLI=1`, `/usr/local/bin`, Homebrew, login-shell PATH; Windows Program Files, PATH), `mod.rs` runs it (arg arrays, main's environment, 10 s `CLI_TIMEOUT_MS`, a call past it ended and waited for) and `status.rs`/`serve.rs`/`whois.rs` read what it prints, keeping only needed keys. `cli.ts` and `locate.ts` are the typed clients; `service.ts` keeps Mobile web's phases, prefs, server and poll, `tailnet.ts` computer sharing's brief caches.

Turning off runs `serve --https=<port> off` only when that record and the handler still match exactly (`own_proxy` in the core's `serve.rs`: one `/` proxy to the current secret path on any loopback port, or to the bare recorded target an earlier release published; any other path on that address is the user's own handler, never overwritten or removed), then checks the user's other handlers are unchanged, else only the record is dropped. A secret-less handler of ours is republished over itself on the same port (`plan` reuses a port only when the handler already proxies to exactly the new target). The service asks for each as one request (`tailscale.publish`, then `tailscale.confirm` once the record is saved; `tailscale.unpublish`).
- No `serve reset` and no Funnel command in the source, main's and the core's (`service.test.ts` greps `src/main/tailscale` and `crates/core/src/tailscale` for both). **The real Mac's own `tailscale serve` (443 → 3010) must stay untouched.**
- Prefs: `mobileWeb.allowedUsers` (default this computer's login; `allowedUsers()`); `mobileWeb.confirmNewDevices` (default **off**; request `set-confirm-new-devices`, `MobileWebState.confirmNewDevices`; `confirmNewDevices()`). `whois(address)` (`tailscale whois --json <ip>`: only ever given an IP, read-only, 4 s `WHOIS_TIMEOUT_MS`; the core's `whois.rs` keeps stable ID, node name, owner login) answers the server's lookups while Mobile web is on.
- **Setup item**: `tailscale` is optional (`setupItemAutomatic` false: never installed at launch or in the background pass, no once-per-launch rule, no back-off ledger; only `installForConnection` and Retry). macOS = the Standalone zip from `pkgs.tailscale.com/stable/?mode=json` plus `.sha256`, then `codesign --verify --deep --strict`, bundle id and team `W5364U7YZB` (`TAILSCALE_TEAM_ID`, `setup/plans.ts`) before `ditto` to /Applications; Windows = winget, else the arch's MSI plus `.sha256` plus a Valid `Tailscale Inc.` Authenticode signature, then elevated `msiexec /qn`.
- **Tests never touch a real daemon**: vitest `fakeTailscaleCli` (`test-fake-tailscale.ts`: an executable the core process runs, a `.cmd` on Windows, which asks the test's own process for each answer, so a test changes its scenario in place; peers carry `ip`/`stableId`); e2e the fake CLI `e2e/fixture/fake-tailscale.ts` (`fixtureTailscale(dir)` in `fake-tailscale-install.ts`; env `OMP_GUI_TAILSCALE`, `OMP_GUI_TEST_TAILSCALE_OPEN` = stand-in for "start the Tailscale app", `FAKE_TAILSCALE_STATE` scenario JSON, `FAKE_TAILSCALE_LOG` call log).

Its keys sit 10 px apart, bounded at 10, so each fills the bar's height and reaches 36 across; the phone's panel tab bar under it keeps its reach inside its 40 px buttons (`--hit-gap-y: 0px`), leaving the keys their bottom edge.
- A phone's Changes view shows the unified diff only (no split toggle); Changes and Files are a list first, then one item; both poll only while mounted and the page is visible.
- Pinned by `e2e/preview-stream.e2e.ts` (real Electron OSR page + fake WS client; 0 frames idle) and `e2e/mobile-panels.e2e.ts` (iPhone and iPad × Chromium and WebKit; `OMP_GUI_MOBILE_PANELS=<dir>` writes captures).
- **A fling through the transcript is never pulled back** (the user's rule). Three rules in `chat-stream-utils.ts`, wired in `ChatStream.tsx`:
  - `transcriptScrollTo` is the virtualizer's `scrollToFn` and sets its `scrollOffset` at each write, because the virtualizer otherwise learns a written offset only from the next scroll event and compensates a row from a stale offset;
  - the page-of-history restore and the changed-row hold let go once `readerMoved` (the view is neither where the hold left it nor where a write since put it), so a fling that goes on after the finger lifts releases them;
  - `compensateRowsAbove` (the virtualizer's `shouldAdjustScrollPositionOnItemSizeChange`) compensates a re-measured row wholly above the view in either scroll direction (stock skips it while the view moves up).
  - **iPhone and iPad keep stock's iOS rule** (WebKit cancels momentum on a scroll write, so the virtualizer defers its compensations until the fling stops and applies them at once): a jump of the deferred amount at the fling's end remains there. Pinned by `chat-stream-utils.scroll-write.test.ts`.

### Per-device prefs
- On a paired web page (`src/shared/device-prefs.ts`, routed by `src/renderer/web/shim.ts`; desktop unchanged) these belong to the device (`DEVICE_LOCAL_PREF_KEYS`, `isDeviceLocalPref`): theme (`theme`, `themeName`, `systemLightTheme`, `systemDarkTheme`, `followAgentTheme`, `colorBlindMode`), text/density (`fontSize`, `compactDensity`), conversation rendering (`transcriptDetail`, `thinkingExpanded`, `codeLineNumbers`, every `displayPreferences.*`), layout (`sidebarWidth`, `sidebarVisible`, `sidebarFolds`, `sidebarFamilies`, `gui.panelWidth`, `panelSide`, `defaultPanelTab`).
- Kept in the device's own `WebDevice.uiPrefs` record on the host (`web:device.uiPrefs.get/set`, `WEB_DEVICE_CHANNELS` in `shared/web-host.ts`, permission `device-self`, 64 KiB `DEVICE_UI_PREFS_MAX_BYTES`). Agent behaviour, models, accounts, notification policy, the keymap, the sidebar's pins/archive and every other key stay the host's.
- The shim overrides `PREFS_GET`/`PREFS_SET`: a whole-store read is the host's prefs minus device-local keys plus the device's values (`overlayDevicePrefs`; dotted keys nest as the host's store does; a keyed read of a local key reads only the record). A write of a local key goes only to `uiPrefs.set` (serialized, each from the latest copy; a refused write rejects so `saveGuiPreference` toasts), never to the host's prefs, so it cannot reach desktop windows or `nativeTheme`; `PREFS_CHANGED` for a local key is dropped on the page.
- A phone with nothing set follows the system theme (`getPersistedThemeSelection` falls back to `system`) and stock text size; phone sizes come from CSS (`mobile.css`), no phone-only size pref.
- A new appearance/layout pref that should differ per device MUST be added to `DEVICE_LOCAL_PREF_KEYS` (and the list in `device-prefs.test.ts`). Settings › Appearance shows the "This device" note (`settings.appearance.thisDevice*`) on the web page only.
- Pinned by `shared/device-prefs.test.ts`, `web/device-prefs.test.ts`, `e2e/device-prefs.e2e.ts`.
