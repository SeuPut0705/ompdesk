## Check control

Design: `docs/design/check-control.md` (the owner approved P0 to P4, 13 Nov 2026). Each part adds its own section below; this file starts with what every part shares.

### The contract
- **One source**: `native/ompdesk/crates/core/src/checks/contract.rs` holds every shape that crosses a boundary (the design's §3 types, the tool's requests and replies, `Snapshot`, the wire names, the tool name and its operations, the wait bounds). `src/shared/checks-contract.ts` mirrors it as strict zod schemas, the TypeScript types inferred from them. JSON: camelCase fields, a union tagged by `kind`, a time in milliseconds since the epoch; a field §3 marks `?` is left out when absent, one typed `| null` is always written.
- **Pinned both ways** by `checks/contract-samples.json`: the Rust test `the_samples_file_holds_the_contract_as_these_types_write_it` writes one value of every shape with every optional field, every variant and every enum word from the Rust types and fails when the file differs (`OMPDESK_WRITE_CONTRACT=1 cargo test -p ompdesk-core --lib checks::contract` rewrites it); `src/shared/checks-contract.test.ts` parses each sample with its strict schema (a field Rust writes and the mirror lacks fails) and walks each schema for a field or variant no sample holds (the reverse). A contract change is the Rust type, its sample in `samples::all`, the rewritten file and the mirror, in one commit. A new shape goes into `samples::all` and `CHECKS_SCHEMAS`.
- **Where it lives**: the hub is the core process's (`crates/core/src/checks/`, new, nothing moved from TypeScript), as the design's §4 chose. The agent tool's body also runs in the core (`agentctl`) and asks the hub in-process (`checks::hub(id)`); main reaches it through its typed client `src/main/checks/client.ts` (`CoreChecksHub`). The CLI twin `ompdesk checks` goes through the control socket like every tool, so without a running OMPdesk it can answer only this computer's own pool.
- **`ChecksHub`** (`hub.rs`; `ChecksHub` in `checks-contract.ts` is the same interface for TypeScript): `start`, `wait`, `status`, the read-only streams `watch` (the whole `Snapshot`, now and at each change) and `results` (every `RunResult` as it arrives, whoever waits: main wakes the session that started the run), and the owner's one control `pause`. A refusal is an answer (`decision: refused` with its reason), never a fault. A wait that runs out answers `verdict: unknown, next: wait`, never an error, and a cancelled request ends its wait. `origin` (who asks) is main's word in every call, never an argument a caller wrote: a session by its saved id (the id in its session file's name; its tab id while it has no file) and its computer (`local` for the hub's own, else the paired device's id); `goal` is the goal's own short text, shown as written, never an id to look up.
- **What main tells the hub**, because the hub cannot read it: `told(MainFact)` (`repos`: the repos of the open sessions' checkouts; `devicePool` and `deviceOffline`: a paired computer's pool as it answered over the link, or that the link is lost; `sessions`: whose each session tag is, so a local check run names its session) and `runners` (how gh and git run: main's `ghRunner` and `gitRunner`, sent after the open and again when the login shell's environment changed). The runners hold the environment, tokens included: they are in no serializable shape, no sample, no log and no answer, and the fake hub keeps only which of the two came (`client.test.ts`).
- **The wire** (`mod.rs`, names in `contract::wire` and `CHECKS_WIRE`): requests `checks.open {hub, fake?}`, `checks.close`, `checks.start|wait|status {hub, origin, request}`, `checks.watch {hub, on}` (answers the snapshot now), `checks.pause {hub, paused}`, `checks.facts {hub, fact}`, `checks.runners {hub, gh, git, home}`, `checks.fake {hub, op}`; events `checks.snapshot {hub, snapshot}` while a watch is on and `checks.result {hub, result}` always. `hub` is main's id for the hub it opened; a hub whose connection ended is closed (`close_all` in `server.rs`).
- **Ids**: a run the hub started keeps the id the hub gave it at `start` (a held run has one before any GitHub run exists); a GitHub run nobody started through the hub is `gh-<GitHub's run id>` with `origin: person`, a local check run `local-<journal id>`. Pools are `github-macos|windows|linux` and `device-<device id>`.
- **Fact adapters** (`sources.rs`): `GithubSource` (runs, jobs, a job's log, a run's artifacts and an artifact's zip, a repository variable, a ref's head, a folder's checkout, whether a repo is private, and the only writes a policy makes: dispatch, cancel, rerun the failed jobs) and `LocalSource` (each computer's heavy pool and disk, the `ompdesk check` journals and their flaky record). Their shapes are the sources' own facts and decide nothing. `FakeGithub` and `FakeLocal` answer facts a test sets (`with`), fail every call while `down` is set, and `FakeGithub` records its writes and counts its reads (what a budget test asserts).
- **Fakes of the hub**: `fake.rs` `FakeHub` (opened with `checks.open {fake: true}`, scripted by `checks.fake`: set the snapshot, queue a start reply, hand in a result, read the calls it got) and its in-memory twin `createFakeChecksHub` with made-up screen data `sampleSnapshot`/`sampleAnswer` (`src/shared/checks-fixture.ts`, for the page's dev harness and component tests). `src/main/checks/client.test.ts` runs the same cases over both, the core's through the real process.
- **What is not built**: the real `Hub` answers `not_built` for every call and `checks.open` without `fake` is refused the same way, until its parts land. Each part is its owner's file under `checks/`, and `mod.rs` declares every one from the start (an empty file until its part lands), so no part edits `mod.rs`: `admission.rs` (what a start decides) and `answer.rs` (a run's result as an agent reads it), the contract owner's; `poller.rs` (the one reader of GitHub and the pools, and the real sources); `queue.rs` (the merge queue); `results.rs`, `trends.rs` and `place.rs` (test results, flaky tests and cost, local or runner). `contract.rs` and `hub.rs` change through the contract's owner only.
- **Admission to the merge queue** (`hub.rs`): a `start {purpose: land}` is resolved by admission (repo, branch, its head, the base, past the pause) and handed to `Hub.queue` as `LandQueue::enqueue(origin, LandRequest)`, whose reply's `runId` names the queue entry; the queue shows itself through `LandQueue::entries` (the snapshot's `queue`). The queue asks the hub through `QueueHost`: `start_batch` (a batch's run on its temporary branch goes through the same admission as every run, lane `land`), `batch_answer`, and `finished(RunResult)` for each entry, which ends that entry's waits and wakes its session. Until `queue.rs` is built `Hub::new` holds a queue that lands nothing.

### The poller and the pools (`poller.rs`, `poller/`)
- **One reader for every session** (design §4, §9.2): `Poller` reads GitHub's Actions runs and jobs of the watched repositories and every computer's pool on the hub's clock, and writes `Snapshot.pools` and `Snapshot.runs` (only those two fields) at each change and at least once a minute. `Engine` is the schedule as a state machine (`plan`, `apply`, no clock, no I/O). Per repository: its runs every 15 s while one is unfinished, 30 s otherwise; each unfinished run's jobs every 20 s (60 s while it waits) and once more after it ended; the limits variable every 10 min. Pools and check journals every 10 s. What is due is read oldest first, so a short quota delays every run a little and starves none. A fact not confirmed within three of its periods reads `stale` with its last `asOf`, never as current (§9.3); `confirmed(repo, run)` says the same per run, so an answer never reads green from old data.
- **GitHub through the person's own gh** (`poller/github.rs`): `gh api --include --jq <projection>`, with the runner main hands over (`checks.runners`); the core holds no token, and gh's words are scrubbed of the token variables' values. Every read is conditional on the entity tag of its last `200`; measured on this repository (13 Nov 2026, gh 2.104.0) a `304` leaves `x-ratelimit-remaining` unchanged, and GitHub answers the `304` with the strong tag where the `200` gave the weak one (the weak one is sent back). Budget (`poller/budget.rs`): about 2 000 requests an hour, spread evenly, a `304` and a gh that never asked refunded; a quarter pace under 25 % of the account's quota, nothing under 5 % until its reset; a secondary limit pauses for its `retry-after` (else a minute). A gh missing, signed out or offline backs off from 15 s to 5 min; `runners` and `retry_now` end that wait, never one GitHub asked for. The recorded answers of this repository are the tests' fixtures (`checks/fixtures/*.http`, recorded with `gh api --include`, less four token-describing headers).
- **Who started a run** (`poller/provenance.rs`): the hub's own record, never a run's title, actor or any text. Admission calls `expect` before it dispatches; the first dispatched run of that workflow on that ref GitHub then shows takes the claim, decided once at the run's first sight (a run seen before anything expected it stays a person's for good; a dispatch whose run did not show in 10 min claims nothing later). A local check is the hub's own start (`claim_local`) or the session whose process tag main names (`MainFact::Sessions`); today's journals record no tag, so a check started outside the hub reads `person`.
- **GitHub's pools**: `github-macos|windows|linux` count the unfinished jobs of every watched repository by their `runs-on` label (`self-hosted` and unknown labels count in none). Limits: `RUNNER_LIMITS` of `scripts/ci-run.ts` (a test pins the two equal), widened by a repository variable `CHECKS_RUNNER_LIMITS` (`{"jobs":40,"macos":5}`) and by the most jobs ever seen running at once. Windows and Linux share the account's whole allowance; other repositories of the account are not watched, so their jobs are not in the count until main names them (design §11).
- **A computer's pool**: its own `ompdesk heavy status --json` (the binary beside the core), the waiters' ages from their tickets' times, and each paired computer's pool as that computer answered over the link (`MainFact::DevicePool`); a lost link keeps the last pool with `limit` 0 and `offline`, never an empty one.
- **Heavy work outside the pool is foreign load** (`poller/foreign.rs`; the owner's need, 14 Nov 2026: other projects count heavy work under their own locks, yuyu's `heavy-run` with `~/.cache/yuyu-heavy*.lock`, RNGAN's `tools/godot_slot.sh` with `/tmp/rng_godot_hslot.N`, which OMPdesk's pool cannot see). Every read of this computer's pool lists its processes (`ps -A -ww` on macOS and Linux, a Toolhelp snapshot on Windows) and counts, as one piece of work per topmost process of a kind: `cargo` (`cargo`, `rustc`, `cargo-clippy`, `clippy-driver`), `godot` run unattended (`--headless`, `--export-…`, `--script`; an open editor is no heavy work), `playwright` (a node, bun or deno process naming it, and its downloaded browsers) and `vitest` (its workers are `node (vitest N)`). Work under a slot's holder is the pool's own and not counted: the holder of `ompdesk run --heavy` and `ompdesk check` is its ancestor, and a script that took `ompdesk heavy hold` is the hold's parent; the core's own children are not counted either. It is `LocalPool.foreign` and `Pool.foreign` (`ForeignLoad {kind, pid, command, processes}`; a paired computer sends its own with its pool), so a pool's load is `running + foreign.len()` against `limit`; GitHub's pools carry none. Foreign load is shown and counted, never signalled, queued or judged; a listing that fails keeps what the last one saw.
- **The contract a project's script takes the slot by** (`ompdesk run --heavy`, shipping in 0.128.0; the clean path, which also takes its work out of the foreign count): `ompdesk run --heavy [--all] -- CMD ARG…` waits its turn (first come first served; `--all` takes every slot; also while a volume it writes to is under `min_free`), runs CMD holding one slot, passes SIGTERM and SIGHUP on to it, stops CMD's tree when the disk falls under the danger line, and exits with CMD's own code (128 + the signal when a signal ended it); it exits 1 when no slot could be taken, 2 on a usage error and 127 when CMD could not start. Inside a command already holding a slot (`OMPDESK_HEAVY_HELD` names a live holder) it takes no second one, so a wrapper and its inner call never deadlock. A shell script that cannot exec through it holds a slot for its own life with `ompdesk heavy hold [--all]`: start it in the background as a simple command (so the script is its parent, which is what keeps the script's work out of the foreign count), its stdin a pipe the script keeps open, wait for its one line `held <slots>` (exit 1: no slot, 2: usage), do the work; the slot is given back when that pipe closes, which the script's exit does by itself, a crash or a kill included. `OMPDESK_HEAVY_LABEL` names the hold in `ompdesk heavy status`. In any POSIX sh (macOS's bash 3.2 has no `coproc`; checked with sh, bash 3.2 and zsh on 14 Nov 2026 against a stand-in hold):
  ```sh
  dir=$(mktemp -d) && mkfifo "$dir/in" "$dir/out" || exit 1
  OMPDESK_HEAVY_LABEL="godot tests" ompdesk heavy hold < "$dir/in" > "$dir/out" &
  exec 3> "$dir/in"                       # the hold's stdin, open for this script's life
  read -r held < "$dir/out" || exit 1     # "held 0": the slot is taken
  rm -r "$dir"
  godot --headless -s tests/run.gd        # the slot goes back when this script exits
  ```
  A script for a computer without OMPdesk keeps its old lock behind `command -v ompdesk`. Both commands are answered by the CLI alone: no running OMPdesk, no token (control-tools › Heavy slots).
- **What admission takes from the poller**: `expect` (before a dispatch), `github_of(run)` (GitHub's run behind a hub id or `gh-<id>`, for cancel and rerun), `confirmed(repo, run)`, `ended(run)` (ends once the run has a verdict and its jobs were read after its end; it polls nothing and never ends for a run that never shows, so it is selected against the caller's timeout and cancel), `changes()` (grows after every round that changed a fact) and `nudge(repo)`. `status` is `poller::status`: the snapshot cut to `mine` (the same session on the same computer, whatever its goal), `repo` (named, else the caller's folder read with git) or `all`, with no GitHub request.
