## Check control

Design: `docs/design/check-control.md` (the owner approved P0 to P4, 13 Nov 2026). Each part adds its own section below; this file starts with what every part shares.

### The contract
- **One source**: `native/ompdesk/crates/core/src/checks/contract.rs` holds every shape that crosses a boundary (the design's §3 types, the tool's requests and replies, `Snapshot`, the wire names, the tool name and its operations, the wait bounds). `src/shared/checks-contract.ts` mirrors it as strict zod schemas, the TypeScript types inferred from them. JSON: camelCase fields, a union tagged by `kind`, a time in milliseconds since the epoch; a field §3 marks `?` is left out when absent, one typed `| null` is always written.
- **Pinned both ways** by `checks/contract-samples.json`: the Rust test `the_samples_file_holds_the_contract_as_these_types_write_it` writes one value of every shape with every optional field, every variant and every enum word from the Rust types and fails when the file differs (`OMPDESK_WRITE_CONTRACT=1 cargo test -p ompdesk-core --lib checks::contract` rewrites it); `src/shared/checks-contract.test.ts` parses each sample with its strict schema (a field Rust writes and the mirror lacks fails) and walks each schema for a field or variant no sample holds (the reverse). A contract change is the Rust type, its sample in `samples::all`, the rewritten file and the mirror, in one commit. A new shape goes into `samples::all` and `CHECKS_SCHEMAS`.
- **Words a person reads are codes, not English**: a `Decision` carries `reason` (English, for agents and logs) and `why` (`DecisionWhy`, a union tagged by `code` with that code's numbers and ids); a screen shows `why` through its en/ko keys, never `reason`. In Rust `DecisionWhy` is a flat struct (`DecisionWhy::new(code)` plus that code's fields), because an internally tagged enum read from text loses its numbers in a workspace build (serde_json's `arbitrary_precision`; every tagged request main sends is read through a plain wire struct for the same reason).
- **Where it lives**: the hub is the core process's (`crates/core/src/checks/`, new, nothing moved from TypeScript), as the design's §4 chose. The agent tool's body also runs in the core (`agentctl`) and asks the hub in-process (`checks::hub(id)`); main reaches it through its typed client `src/main/checks/client.ts` (`CoreChecksHub`). The CLI twin `ompdesk checks` goes through the control socket like every tool, so without a running OMPdesk it can answer only this computer's own pool.
- **`ChecksHub`** (`hub.rs`; `ChecksHub` in `checks-contract.ts` is the same interface for TypeScript): `start`, `wait`, `status`, the read-only streams `watch` (the whole `Snapshot`, now and at each change) and `results` (every `RunResult` as it arrives, whoever waits: main wakes the session that started the run), and the owner's one control `pause`. A refusal is an answer (`decision: refused` with its reason), never a fault. A wait that runs out answers `verdict: unknown, next: wait`, never an error, and a cancelled request ends its wait. `origin` (who asks) is main's word in every call, never an argument a caller wrote: a session by its saved id (the id in its session file's name; its tab id while it has no file) and its computer (`local` for the hub's own, else the paired device's id); `goal` is the goal's own short text, shown as written, never an id to look up.
- **What main tells the hub**, because the hub cannot read it: `told(MainFact)` (`repos`: the repos of the open sessions' checkouts; `devicePool` and `deviceOffline`: a paired computer's pool as it answered over the link, or that the link is lost; `sessions`: whose each session tag is, so a local check run names its session) and `runners` (how gh and git run: main's `ghRunner` and `gitRunner`, sent after the open and again when the login shell's environment changed). The runners hold the environment, tokens included: they are in no serializable shape, no sample, no log and no answer, and the fake hub keeps only which of the two came (`client.test.ts`).
- **The wire** (`mod.rs`, names in `contract::wire` and `CHECKS_WIRE`): requests `checks.open {hub, fake?}`, `checks.close`, `checks.start|wait|status {hub, origin, request}`, `checks.watch {hub, on}` (answers the snapshot now), `checks.pause {hub, paused}`, `checks.facts {hub, fact}`, `checks.runners {hub, gh, git, home}`, `checks.localPool {hub}` (this computer's own `LocalPool` as its poller reads it: a paired computer's link forwards it to the other hub as `devicePool` with its own device id, so `ompdesk heavy status` is mapped in one place, `poller::local::pool_of`), `checks.fake {hub, op}`; events `checks.snapshot {hub, snapshot}` while a watch is on and `checks.result {hub, result}` always. `hub` is main's id for the hub it opened; a hub whose connection ended is closed (`close_all` in `server.rs`).
- **Ids**: a run the hub started keeps the id the hub gave it at `start` (a held run has one before any GitHub run exists); a GitHub run nobody started through the hub is `gh-<GitHub's run id>` with `origin: person`, a local check run `local-<journal id>`. Pools are `github-macos|windows|linux` and `device-<device id>`.
- **Fact adapters** (`sources.rs`): `GithubSource` (runs, jobs, a job's log, a run's artifacts and an artifact's zip, a repository variable, a ref's head, a folder's checkout, whether a repo is private, and the only writes a policy makes: dispatch, cancel, rerun the failed jobs) and `LocalSource` (each computer's heavy pool and disk, the `ompdesk check` journals and their flaky record). Their shapes are the sources' own facts and decide nothing. `FakeGithub` and `FakeLocal` answer facts a test sets (`with`), fail every call while `down` is set, and `FakeGithub` records its writes and counts its reads (what a budget test asserts).
- **Fakes of the hub**: `fake.rs` `FakeHub` (opened with `checks.open {fake: true}`, scripted by `checks.fake`: set the snapshot, queue a start reply, hand in a result, read the calls it got) and its in-memory twin `createFakeChecksHub` with made-up screen data `sampleSnapshot`/`sampleAnswer` (`src/shared/checks-fixture.ts`, for the page's dev harness and component tests). `src/main/checks/client.test.ts` runs the same cases over both, the core's through the real process.
- **The parts**: each is its owner's file under `checks/`: `admission.rs`, `policy.rs`, `ticket.rs`, `answer.rs` and `hub.rs` (the contract owner's); `poller.rs` (the one reader of GitHub and the pools, and the real sources); `queue.rs` (the merge queue); `results.rs`, `trends.rs` and `place.rs` (test results, flaky tests and cost, local or runner). `contract.rs` and `hub.rs` change through the contract's owner only. Until `queue.rs` lands a `start {purpose: land}` answers `not_built`.

### Starting, waiting and the answer (P2: `hub.rs`, `policy.rs`, `admission.rs`, `ticket.rs`, `answer.rs`)
- **One way in**: the agent tool `ompdesk_checks` (start, wait, status), its CLI twin `ompdesk checks`, and `scripts/ci-run.ts`, which is a thin client (`ompdesk checks start --workflow <file> --input k=v … [--macos] --ref <branch>`). When OMPdesk does not answer, ci-run dispatches a run that asks for no macOS directly with `gh workflow run` (an app restart never stops every CI dispatch) and refuses a macOS one with "open OMPdesk".
- **What a start dispatches** (`policy.rs`, pure): a repo may say it in `.ompdesk/checks.json` (`{"branch": {"workflow": "ci.yml", "inputs": {…}, "macos"?: bool}, "release": {…}}`, read at the commit being checked); without it `branch` runs `ci.yml` with `batch=true` and `release` with `batch=true mac=true`. Only the inputs the workflow's `on.workflow_dispatch.inputs` declares are sent (`dispatch_inputs` reads the shapes workflows are written in), so a repo whose `ci.yml` has no `mac` input decides its own systems; a workflow without `workflow_dispatch` is refused "ci.yml cannot be dispatched". macOS (`mac=true` sent, or the file's `macos`) is admitted only from `main` or a `MAC_REFS` branch (`policy::listed`, read like queue-gate.yml). The lane is the purpose's; a named workflow is `release` when it asks for macOS from a listed ref, else `branch`. The reuse digest is commit + the workflow file's hash + the inputs (`policy::digest`), never the sha alone.
- **When it runs** (`admission.rs`, the model `formal/checks-admission`; each code action carries its `@code` line range there): one `Admission` behind one lock, never held across an await. `start` refuses while paused, answers `reused` from a green run of the same digest, else holds the entry with a 30 min lease (each `wait` renews it every minute) and supersedes older governed branch runs of the same repo, ref and workflow (a waiting one leaves, a dispatched one is cancelled at GitHub and keeps its place until the poller sees it end). The pump admits the first live entry in line (release, land, branch, local; then arrival) whose pool and the account have room, writes its place before it awaits the dispatch, and never queues a failed dispatch again. A held release entry on a full account pool holds one account place from those behind it (F1). Places are runs: `github-macos` has 1 (GitHub's `mac-dispatch` lane runs one dispatched unit), `github-linux` has the account's job limit ÷ 10; runs nobody started through the hub count against them from the poller's snapshot.
- **The loop** (`Hub::run`, started by `Hub::real`): at each poller change, each start and every 30 s it frees the places of runs that ended, answers them, reaps lapsed leases (their owners get `unknown`, "start it again") and pumps. Before a dispatch the hub gives the poller its claim (`expect`), so the run GitHub shows is known by the hub's id (`chk-…`).
- **The answer** (`answer.rs`): a completed run's jobs and each job's `test-report-<job id>` artifact are read once, taken into the repository's ledger (`results::take_in`, P4's; saved under `<cache>/ompdesk/checks/hub/results`) and written as the `Answer`. It is `unknown` while the poller's facts about the run are stale (`confirmed`, with its `trouble`), for a cancelled run, a failed dispatch, a superseded entry and a lapsed lease; never green from old data. `blocksRelease` names the run's gate when a release run is not green or a quarantined test failed in it. Every answer goes once to `results()` (main wakes the session that started it), into `Snapshot.answers` (the newest 50) and to every `wait` on it; `rerun: failed` reruns only the failed jobs of the caller's last red run on that commit whose answer said `rerun-failed`.
- **The owner's pause** is kept in `<cache>/ompdesk/checks/hub/admission.json` (`write_kept`) and read when the hub opens.
- **The admission ticket** (`ticket.rs`, design §7.1): `v1.<expiry ms>.<hex HMAC-SHA256>` over `ompdesk-checks-ticket-v1\n<repo>\n<ref>\n<sha>\n<expiry>` under the owner's key, 30 min valid. The hub adds it as the `ticket` input to a macOS dispatch of a workflow that declares `ticket`, when main handed it the key (`checks.open {key}`); queue-gate.yml checks it (e2e-ci-windows › CI › The check queue). The key never enters a session's environment, a log or a serializable shape (`AdmissionKey` prints as `AdmissionKey(..)`). Off until the owner sets the Actions secret `CHECKS_ADMISSION_KEY`.
- Pinned by the Rust tests of `admission.rs` (one per model property), `policy.rs` (this repo's workflows read, every trigger shape, the repo file, the lane, the digest), `ticket.rs` (RFC 4231 vectors, the pinned `VECTOR`), `hub_tests.rs` (the real hub over fake GitHub: declared inputs only, supersede, MAC_REFS and the macOS unit, the ticket, the pause across a restart, the wait's judgment heard once), `agentctl::service::tests` (the tool's body), `scripts/ci-run.test.ts` (the route) and `src/main/ci-queue.test.ts` (the gate's step on the vector).
- **Admission to the merge queue** (`hub.rs`): a `start {purpose: land}` is resolved by admission (repo, branch, its head, the base, past the pause) and handed to `Hub.queue` as `LandQueue::enqueue(origin, LandRequest)`, whose reply's `runId` names the queue entry; the queue shows itself through `LandQueue::entries` (the snapshot's `queue`). The queue asks the hub through `QueueHost`: `start_batch` (a batch's run on its temporary branch goes through the same admission as every run, lane `land`), `batch_answer`, and `finished(RunResult)` for each entry, which ends that entry's waits and wakes its session. Until `queue.rs` is built `Hub::new` holds a queue that lands nothing.

### Merge queue (lane `land`, P3)
- **OMPdesk's own queue** (`checks/queue.rs` `LandQueue`, one per base branch of a repository; the design's §5 policy 3): GitHub's merge queue is not offered to a repository a user owns and does not combine builds. Branches wait in a line, each pinned to the commit it was queued with. A batch is the oldest waiting entry and the later ones of its goal, oldest first, at most `BATCH_SIZE` (4); it forms when it is full or its oldest entry waited `BATCH_WINDOW_MS` (5 min). One batch is worked on at a time.
- **The rules run nothing**: every method takes what happened and returns `Effect`s (`Build` the first entries of the batch on the base tip as one commit on the queue's own branch `omp/queue/<candidate>`, `Test` that commit, `Land` it, `Drop` a candidate, `Tell` an entry's owner), and whoever runs the queue answers through `built`, `verdict`, `lost`, `landed`, `moved`, `refused`, `base_read`. No git, no GitHub and no clock in the file, so the unit tests, the model and a real remote drive the same code. The queue is saved as it is (`Serialize`); `resume` asks again for what a restart interrupted, each safe to do twice.
- **What lands is what was tested**: `Land` pushes the very commit the check passed on, as a fast-forward of the base, never forced (the user's rule for every push OMPdesk makes). A base that moved (`moved`, or `base_read` with a tip the queue did not know) drops the trial and everything known, and the batch starts over on the new tip. A base read while the queue's own push is under way changes nothing: that push's answer decides.
- **A red batch bisects over prefixes**, with what the check said kept per base tip and entries (`memo`): the longest prefix known green lands; the first entry fails once it alone is known red on the tip; otherwise the middle of the shortest prefix known red is tested. After a landing, red knowledge of longer combinations is carried onto the new tip only when the base is exactly the landed commit, so a combination already known red is never built again and an entry is never failed on a tip it was not tested on. A branch that cannot be built onto the tip and the entries before it (`built` with `Unbuilt`: a conflict, a commit the remote lacks) is a red result for the prefix it ends. A failed entry's result is the `Answer` of the run that was red with it alone on the tip (its failed tests), or the build's words when no run says it.
- **A result is taken only for the commit under test now** (`verdict` compares the commit; `built`, `lost`, `landed`, `moved`, `refused` the candidate): the late answer of a trial dropped meanwhile changes nothing. An entry is withdrawn any time except while the commit that holds it is being pushed (`Refusal::Landing`); a withdrawal drops the trial whose commit holds the entry and no other. A branch queued again keeps its place while waiting; out of a batch under test it leaves and waits again.
- **Model-checked before it was written**: `formal/checks-queue` (TLC; read `skill://checks-queue-verify` before changing `queue.rs`). Pinned by `queue_tests.rs`: one case per rule above, and the model's properties over 3,000 generated orders of arrivals, withdrawals, results (also of dropped trials), others' pushes and base reads.
- **The runner** (`checks/queue_run.rs`, a child module of `queue.rs`; `queue::open(host)` is what `Hub.queue` holds, its git and folder the hub's `QueueHost::git` and `queue_dir`): one task per base branch of a repository (a lane) owns that base's `LandQueue` and is the only one to call it, one message at a time. `Build` reads the base's tip first and tells the queue a tip it did not know instead of building on an old one; `Test` is one run through `QueueHost::start_batch` on the candidate's branch and its `batch_answer` (`unknown` is asked again after `UNKNOWN_AGAIN_MS`, never taken as a verdict); `Land` reads the push's answer (a base that moved on but already holds the commit, a push that went through before a restart, reads as landed); `Drop` cancels the candidate's work and deletes its branch; `Tell` is `QueueHost::finished` with the entry's id as `runId` (`enqueue` answers `held` with that id, also for an entry that went straight into a batch). A git or GitHub that fails for a while (no network, git not handed over yet, the owner's pause) is tried again from `RETRY_FIRST_MS` (5 s) doubling to `RETRY_MAX_MS` (5 min) and never reaches the queue as a result. The lane is saved after every step and started again from the save.
- **`GitHands`**, the real git: a bare clone the queue owns per repository (`<dir>/repos/<owner>__<name>.git`, remote `origin`), never anyone's checkout. A build fetches each part's branch, takes a branch that already holds what is built so far as it is (it lands as a fast-forward), else merges with `merge-tree` and `commit-tree` (`git/land.rs`, Autopilot's landing git) dated the later of the two commits, so the same parts on the same tip build the same commit; then pushes it to `omp/queue/<name>/<base>-c<n>` (`<name>`: this computer's random part, `<dir>/name`). Saves go through `write_kept` (`<dir>/lanes/<owner>__<name>__<base>.json`).
- **Pinned** by `queue_run_tests.rs` against real git with a bare repository as the remote and a fake hub: a batch lands as exactly the commit its one run passed; a red batch lands the good branch and fails the bad one with its own run's tests; a conflicting branch is failed with the file named and starts no run; a push to main during the run is kept and the branch tested again on it; a queue opened again shows what it had.
- **How the hub holds it**: `Hub::build` makes its core with `Arc::new_cyclic` and `queue: queue::open(Arc::new(Host(core.clone())))`. `open` asks `Host` nothing then (its `Weak` cannot reach the hub yet): the folder is read on use, the saved lanes start at the first `enqueue` or from a task of the queue's own. An `enqueue` is answered once the step that queued the entry is saved. Not built yet: a target batch size from history.

### The poller and the pools (`poller.rs`, `poller/`)
- **One reader for every session** (design §4, §9.2): `Poller` reads GitHub's Actions runs and jobs of the watched repositories and every computer's pool on the hub's clock, and writes `Snapshot.pools` and `Snapshot.runs` (only those two fields) at each change and at least once a minute. `Engine` is the schedule as a state machine (`plan`, `apply`, no clock, no I/O). Per repository: its runs every 15 s while one is unfinished, 30 s otherwise; each unfinished run's jobs every 20 s (60 s while it waits) and once more after it ended; the limits variable every 10 min. Pools and check journals every 10 s. What is due is read oldest first, so a short quota delays every run a little and starves none. A fact not confirmed within three of its periods reads `stale` with its last `asOf`, never as current (§9.3); `confirmed(repo, run)` says the same per run, so an answer never reads green from old data.
- **GitHub through the person's own gh** (`poller/github.rs`): `gh api --include --jq <projection>`, with the runner main hands over (`checks.runners`); the core holds no token, and gh's words are scrubbed of the token variables' values. Every read is conditional on the entity tag of its last `200`; measured on this repository (13 Nov 2026, gh 2.104.0) a `304` leaves `x-ratelimit-remaining` unchanged, and GitHub answers the `304` with the strong tag where the `200` gave the weak one (the weak one is sent back). Budget (`poller/budget.rs`): about 2 000 requests an hour, spread evenly, a `304` and a gh that never asked refunded; a quarter pace under 25 % of the account's quota, nothing under 5 % until its reset; a secondary limit pauses for its `retry-after` (else a minute). A gh missing, signed out or offline backs off from 15 s to 5 min; `runners` and `retry_now` end that wait, never one GitHub asked for. The recorded answers of this repository are the tests' fixtures (`checks/fixtures/*.http`, recorded with `gh api --include`, less four token-describing headers).
- **Who started a run** (`poller/provenance.rs`): the hub's own record, never a run's title, actor or any text. Admission calls `expect` before it dispatches; the first dispatched run of that workflow on that ref GitHub then shows takes the claim, decided once at the run's first sight (a run seen before anything expected it stays a person's for good; a dispatch whose run did not show in 10 min claims nothing later). A local check is the hub's own start (`claim_local`) or the session whose process tag main names (`MainFact::Sessions`); today's journals record no tag, so a check started outside the hub reads `person`.
- **GitHub's pools**: `github-macos|windows|linux` count the unfinished jobs of every watched repository by their `runs-on` label (`self-hosted` and unknown labels count in none). Limits: `RUNNER_LIMITS` of `scripts/ci-run.ts` (a test pins the two equal), widened by a repository variable `CHECKS_RUNNER_LIMITS` (`{"jobs":40,"macos":5}`) and by the most jobs ever seen running at once. Windows and Linux share the account's whole allowance; other repositories of the account are not watched, so their jobs are not in the count until main names them (design §11).
- **A computer's pool**: its own `ompdesk heavy status --json` (the binary beside the core), the waiters' ages from their tickets' times, and each paired computer's pool as that computer answered over the link (`MainFact::DevicePool`); a lost link keeps the last pool with `limit` 0 and `offline`, never an empty one.
- **Heavy work outside the pool is foreign load** (`poller/foreign.rs`; the owner's need, 14 Nov 2026: other projects count heavy work under their own locks, yuyu's `heavy-run` with `~/.cache/yuyu-heavy*.lock`, RNGAN's `tools/godot_slot.sh` with `/tmp/rng_godot_hslot.N`, which OMPdesk's pool cannot see). Every read of this computer's pool lists its processes (`ps -A -ww` on macOS and Linux, a Toolhelp snapshot on Windows) and counts, as one piece of work per topmost process of a kind: `cargo` (`cargo`, `rustc`, `cargo-clippy`, `clippy-driver`), `godot` run unattended (`--headless`, `--export-…`, `--script`; an open editor is no heavy work), `playwright` (a node, bun or deno process naming it, and its downloaded browsers) and `vitest` (its workers are `node (vitest N)`). Work under a slot's holder is the pool's own and not counted: the holder of `ompdesk run --heavy` and `ompdesk check` is its ancestor, and a script that took `ompdesk heavy hold` is the hold's parent; the core's own children are not counted either. It is `LocalPool.foreign` and `Pool.foreign` (`ForeignLoad {kind, pid, command, processes}`; a paired computer sends its own with its pool), so a pool's load is `running + foreign.len()` against `limit`; GitHub's pools carry none. Foreign load is shown and counted, never signalled, queued or judged; a listing that fails keeps what the last one saw.
- **The contract a project's script takes the slot by** (`ompdesk run --heavy`, shipping in 0.128.0; the clean path, which also takes its work out of the foreign count): `ompdesk run --heavy [--all] -- CMD ARG…` waits its turn (first come first served; `--all` takes every slot; also while a volume it writes to is under `min_free`), runs CMD holding one slot, passes SIGTERM and SIGHUP on to it, stops CMD's tree when the disk falls under the danger line, and exits with CMD's own code (128 + the signal when a signal ended it); it exits 1 when no slot could be taken, 2 on a usage error and 127 when CMD could not start. Inside a command already holding a slot (`OMPDESK_HEAVY_HELD` names a live holder) it takes no second one, so a wrapper and its inner call never deadlock. A shell script that cannot exec through it holds a slot for its own life with `ompdesk heavy hold [--all]`: start it in the background as a simple command (so the script is its parent, which is what keeps the script's work out of the foreign count), its stdin a pipe the script keeps open, wait for its one line `held <slots>` (exit 1: no slot, 2: usage), do the work; the slot is given back when that pipe closes, which the script's exit does by itself, a crash or a kill included. `OMPDESK_HEAVY_LABEL` names the hold in `ompdesk heavy status`. In any POSIX sh (macOS's bash 3.2 has no `coproc`; checked with sh, bash 3.2 and zsh on 14 Nov 2026 against a stand-in hold):
  ```sh
  dir=$(mktemp -d) && mkfifo "$dir/in" "$dir/out" || exit 1
  OMPDESK_HEAVY_LABEL="godot tests" ompdesk heavy hold < "$dir/in" > "$dir/out" &
  exec 3> "$dir/in"                       # the hold's stdin, open for this script's life
  read -r held < "$dir/out" || exit 1     # "held 0": the slot is taken
  rm -r "$dir"
  godot --headless -s tests/run.gd        # the slot goes back when this script exits
  ```
  A script for a computer without OMPdesk keeps its old lock behind `command -v ompdesk`. Both commands are answered by the CLI alone: no running OMPdesk, no token (control-tools › Heavy slots).
- **What admission takes from the poller**: `expect` (before a dispatch), `github_of(run)` (GitHub's run behind a hub id or `gh-<id>`, for cancel and rerun), `confirmed(repo, run)`, `ended(run)` (ends once the run has a verdict and its jobs were read after its end; it polls nothing and never ends for a run that never shows, so it is selected against the caller's timeout and cancel), `changes()` (grows after every round that changed a fact) and `nudge(repo)`. `status` is `poller::status`: the snapshot cut to `mine` (the same session on the same computer, whatever its goal), `repo` (named, else the caller's folder read with git) or `all`, with no GitHub request.

### Test results, the flaky quarantine and reruns (P4)
- **Where a job's tests come from**: a test job writes its runner's own report (Vitest's `--reporter=json`) and uploads it as the artifact `test-report-<job id>` (the id is the job context's `check_run_id`, which is the job's id in `actions/runs/<id>/jobs`, so a report finds its job and a job that ran again uploads another; uploaded with `if: !cancelled()`, so a failed run still reports; the artifact holds only report files). The workflows' side of this seam is the CI rules' (e2e-ci-windows › CI). `results::cases_of(zip, repo)` reads the artifact (`results/zip.rs`: stored and deflated entries, bounded, no zip64) and every `.json`/`.xml` in it (`results/reports.rs`: Vitest's and Jest's JSON, Playwright's JSON with one attempt per retry, JUnit XML) as `Case`s named like `ompdesk check` names a test (`[project] file › title`, the file relative to the repository). cargo's tests write no report; a job without one is judged by its conclusion alone. No job name or matrix shape is read.
- **One quarantine rule** (`ompdesk_checks::flaky`, control-tools › Heavy slots and `ompdesk check`): `results/ledger.rs` keeps a `flaky::Book` per repository and feeds it from the runs, keyed `<os>|<test>` (the same test is another program on each system). A job's rerun on the same commit and inputs is the same digest, a runner's retried pass is `flaky`. The book records a pass only of a test it already knows (thousands of passing tests would be megabytes rewritten per run); a test's first failure in a rerun after it passed in the same run is still seen through `Ledger::seen` (the tests that failed per run and job: a report lists every test of its job, so one not named there passed; per run, because another run of the same inputs may deal its tests to other jobs). Whether a run passes is `flaky::Failures::passes(exit_ok, release)`, the same function `ompdesk check` uses: a failed job whose every failed test is quarantined is forgiven, never for a release gate, where a quarantined test that failed or flaked in that run fails it (`Verdict::blocks_release`, design §9.5).
- **`results::take_in(ledger, Finished)`** is the hub's one call per completed run attempt (the answer's builder and `wait` are the hub's own): it answers `Verdict` (green, red or cancelled; test counts; the failed tests with first error, `knownFlaky` and their record in words, the ones that fail the run first; the jobs that failed outside their tests; `blocks_release`; the rerun budget; `next`; notes). An attempt is counted once: taking it in again answers None, so the caller keeps the first answer. `results/store.rs` saves a repository's ledger as `<dir>/<owner>__<name>.json` through `write_kept`; a file that cannot be read starts an empty ledger.
- **Reruns** (`results/rerun.rs`, design §9.6): only the failed jobs run again (`GithubSource::rerun_failed`; one test alone can only be rerun by `ompdesk check`). The cap is per run and shrinks with the failed jobs' time: 3 up to 5 min, 2 up to 20 min, else 1; every red answer carries it. `next` is `rerun-failed` while the cap has room and a rerun can still tell something (a test failed once on these inputs, a job failed outside its tests, a release gate's quarantined test has to pass in the deciding run), `fix` for a test that failed twice on the same inputs without passing there or a spent cap, `land` when green. The hub makes the write and logs the `Decision`.
- Pinned by the Rust tests of `results.rs`, `results/{ledger,reports,rerun,zip,store}.rs` and `flaky.rs` (`only_quarantined_failures_are_forgiven_and_never_for_a_release`).

### Tests and cost (P4)
- **`trends::tab::build(ledgers, local, now)`** fills `contract::Trends`: `tests` (every test in quarantine and each that left it within 7 days, per system; a test a computer's own `ompdesk check` quarantined is listed unless a runner's row names it, with its all-time local counts), `slowdowns`, `minutes`, `queueDepth` (a pool's highest waiting count per day, the last 7 days; the poller reports it with `Ledger::note_queue`), the week's time lost to flaky tests and the week before (a job that failed on quarantined tests alone counts whole, a retried test by its failed attempts), what reruns of only the failed jobs saved (jobs not run again) and what reuse saved (`Ledger::note_reuse`, admission's), and `storeBytes` (the computers' `checkStoreBytes` summed).
- **Slowdown** (`trends/slow.rs`): a test or test file over 1.3 times its 30-day median 3 runs in a row. The median is of the passing runs before those three and needs 5 of them; a median under 200 ms raises none (the runner's jitter is larger than 30 %). `sinceSha` is the first run of the streak. The alert ends when a run is back under the line or the slower pace has become the median. A test has a duration track once it took 1 s or failed; every file has one (the sum of its tests, while all passed).
- **Runner minutes and cost are an estimate** (`trends/cost.rs`; the tab says so): each job's duration rounded up to a whole minute, times GitHub's published per-minute rate for its runner label (read 13 Nov 2026), kept per day and system for 186 days. GitHub's billing usage report was checked the same day and is not used: the user endpoint answers 404 to gh's default token (it needs the `user` scope), an organization's needs an administrator, and `actions/runs/<id>/timing` reports 0 billable milliseconds for a public repository. A public repository's standard runners are free, so its figure is a list price; a self-hosted runner uses no minutes.

### Placement (P4)
- `place::place(Ask { os, private, runner, pools })` (design §5 policy 5; `start` has no placement argument): a private repository goes to the least loaded local computer of the job's system that has a free slot, a public one to a GitHub runner, macOS work to a local Mac first whatever the repository and to a runner only when none has a slot. A computer with waiters has no free slot and one whose link is lost has no capacity.
- **Disk**: nothing starts on a computer with a volume under `min_free`. The number is the heavy pool's (`ompdesk_checks::heavy::min_free`, read as `LocalVolume::low`); placement never computes it. Making room is disk care's (machine-setup-updates › Disk care): the answer names the short volume (`Placement::short`, and the reason's words) and the job goes to a runner where one may take it, else it is held. Disk care does not clean `<cache>/ompdesk/checks` today (its own `Store::prune` keeps 10 runs per check); the tab shows its size.
