## Check control

Design: `docs/design/check-control.md` (the owner approved P0 to P4, 13 Nov 2026). Each part adds its own section below; this file starts with what every part shares.

### The contract
- **One source**: `native/ompdesk/crates/core/src/checks/contract.rs` holds every shape that crosses a boundary (the design's §3 types, the tool's requests and replies, `Snapshot`, the wire names, the tool name and its operations, the wait bounds). `src/shared/checks-contract.ts` mirrors it as strict zod schemas, the TypeScript types inferred from them. JSON: camelCase fields, a union tagged by `kind`, a time in milliseconds since the epoch; a field §3 marks `?` is left out when absent, one typed `| null` is always written.
- **Pinned both ways** by `checks/contract-samples.json`: the Rust test `the_samples_file_holds_the_contract_as_these_types_write_it` writes one value of every shape with every optional field, every variant and every enum word from the Rust types and fails when the file differs (`OMPDESK_WRITE_CONTRACT=1 cargo test -p ompdesk-core --lib checks::contract` rewrites it); `src/shared/checks-contract.test.ts` parses each sample with its strict schema (a field Rust writes and the mirror lacks fails) and walks each schema for a field or variant no sample holds (the reverse). A contract change is the Rust type, its sample in `samples::all`, the rewritten file and the mirror, in one commit. A new shape goes into `samples::all` and `CHECKS_SCHEMAS`.
- **Where it lives**: the hub is the core process's (`crates/core/src/checks/`, new, nothing moved from TypeScript), as the design's §4 chose. The agent tool's body also runs in the core (`agentctl`) and asks the hub in-process (`checks::hub(id)`); main reaches it through its typed client `src/main/checks/client.ts` (`CoreChecksHub`). The CLI twin `ompdesk checks` goes through the control socket like every tool, so without a running OMPdesk it can answer only this computer's own pool.
- **`ChecksHub`** (`hub.rs`; `ChecksHub` in `checks-contract.ts` is the same interface for TypeScript): `start`, `wait`, `status`, the read-only streams `watch` (the whole `Snapshot`, now and at each change) and `results` (every `RunResult` as it arrives, whoever waits: main wakes the session that started the run), and the owner's one control `pause`. A refusal is an answer (`decision: refused` with its reason), never a fault. A wait that runs out answers `verdict: unknown, next: wait`, never an error, and a cancelled request ends its wait. `origin` (who asks) is main's word in every call, never an argument a caller wrote.
- **The wire** (`mod.rs`, names in `contract::wire` and `CHECKS_WIRE`): requests `checks.open {hub, fake?}`, `checks.close`, `checks.start|wait|status {hub, origin, request}`, `checks.watch {hub, on}` (answers the snapshot now), `checks.pause {hub, paused}`, `checks.fake {hub, op}`; events `checks.snapshot {hub, snapshot}` while a watch is on and `checks.result {hub, result}` always. `hub` is main's id for the hub it opened; a hub whose connection ended is closed (`close_all` in `server.rs`).
- **Fact adapters** (`sources.rs`): `GithubSource` (runs, jobs, a job's log, a repository variable, a ref's head, a folder's checkout, and the only writes a policy makes: dispatch, cancel, rerun the failed jobs) and `LocalSource` (each computer's heavy pool and disk, the `ompdesk check` journals and their flaky record). Their shapes are the sources' own facts and decide nothing. `FakeGithub` and `FakeLocal` answer facts a test sets (`with`), fail every call while `down` is set, and `FakeGithub` records its writes and counts its reads (what a budget test asserts).
- **Fakes of the hub**: `fake.rs` `FakeHub` (opened with `checks.open {fake: true}`, scripted by `checks.fake`: set the snapshot, queue a start reply, hand in a result, read the calls it got) and its in-memory twin `createFakeChecksHub` with made-up screen data `sampleSnapshot`/`sampleAnswer` (`src/shared/checks-fixture.ts`, for the page's dev harness and component tests). `src/main/checks/client.test.ts` runs the same cases over both, the core's through the real process.
- **What is not built**: the real `Hub` answers `not_built` for every call and `checks.open` without `fake` is refused the same way, until its parts land. The parts are separate files under `checks/` so they are built side by side: admission (`start`), the poller and pools, results (`wait` and the `Answer`), the merge queue, tests and trends.

### Merge queue (lane `land`, P3)
- **OMPdesk's own queue** (`checks/queue.rs` `LandQueue`, one per base branch of a repository; the design's §5 policy 3): GitHub's merge queue is not offered to a repository a user owns and does not combine builds. Branches wait in a line, each pinned to the commit it was queued with. A batch is the oldest waiting entry and the later ones of its goal, oldest first, at most `BATCH_SIZE` (4); it forms when it is full or its oldest entry waited `BATCH_WINDOW_MS` (5 min). One batch is worked on at a time.
- **The rules run nothing**: every method takes what happened and returns `Effect`s (`Build` the first entries of the batch on the base tip as one commit on the queue's own branch `omp/queue/<candidate>`, `Test` that commit, `Land` it, `Drop` a candidate, `Tell` an entry's owner), and whoever runs the queue answers through `built`, `verdict`, `lost`, `landed`, `moved`, `refused`, `base_read`. No git, no GitHub and no clock in the file, so the unit tests, the model and a real remote drive the same code. The queue is saved as it is (`Serialize`); `resume` asks again for what a restart interrupted, each safe to do twice.
- **What lands is what was tested**: `Land` pushes the very commit the check passed on, as a fast-forward of the base, never forced (the user's rule for every push OMPdesk makes). A base that moved (`moved`, or `base_read` with a tip the queue did not know) drops the trial and everything known, and the batch starts over on the new tip. A base read while the queue's own push is under way changes nothing: that push's answer decides.
- **A red batch bisects over prefixes**, with what the check said kept per base tip and entries (`memo`): the longest prefix known green lands; the first entry fails once it alone is known red on the tip; otherwise the middle of the shortest prefix known red is tested. After a landing, red knowledge of longer combinations is carried onto the new tip only when the base is exactly the landed commit, so a combination already known red is never built again and an entry is never failed on a tip it was not tested on. A branch that does not merge (`built` with a `Conflict`) is a red result for the prefix it ends.
- **A result is taken only for the commit under test now** (`verdict` compares the commit; `built`, `lost`, `landed`, `moved`, `refused` the candidate): the late answer of a trial dropped meanwhile changes nothing. An entry is withdrawn any time except while the commit that holds it is being pushed (`Refusal::Landing`); a withdrawal drops the trial whose commit holds the entry and no other. A branch queued again keeps its place while waiting; out of a batch under test it leaves and waits again.
- **Model-checked before it was written**: `formal/checks-queue` (TLC; read `skill://checks-queue-verify` before changing `queue.rs`). Pinned by `queue_tests.rs`: one case per rule above, and the model's properties over 3,000 generated orders of arrivals, withdrawals, results (also of dropped trials), others' pushes and base reads.
- **Not built yet**: the runner (git for `Build` and `Land`, the dispatch and the poller's result for `Test`), the seam to `Hub` (`start {purpose: land}`, `Snapshot.queue`), and target batch size from history.
