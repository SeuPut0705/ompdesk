## Check control

Design: `docs/design/check-control.md` (the owner approved P0 to P4, 13 Nov 2026). Each part adds its own section below; this file starts with what every part shares.

### The contract
- **One source**: `native/ompdesk/crates/core/src/checks/contract.rs` holds every shape that crosses a boundary (the design's §3 types, the tool's requests and replies, `Snapshot`, the wire names, the tool name and its operations, the wait bounds). `src/shared/checks-contract.ts` mirrors it as strict zod schemas, the TypeScript types inferred from them. JSON: camelCase fields, a union tagged by `kind`, a time in milliseconds since the epoch; a field §3 marks `?` is left out when absent, one typed `| null` is always written.
- **Pinned both ways** by `checks/contract-samples.json`: the Rust test `the_samples_file_holds_the_contract_as_these_types_write_it` writes one value of every shape with every optional field, every variant and every enum word from the Rust types and fails when the file differs (`OMPDESK_WRITE_CONTRACT=1 cargo test -p ompdesk-core --lib checks::contract` rewrites it); `src/shared/checks-contract.test.ts` parses each sample with its strict schema (a field Rust writes and the mirror lacks fails) and walks each schema for a field or variant no sample holds (the reverse). A contract change is the Rust type, its sample in `samples::all`, the rewritten file and the mirror, in one commit. A new shape goes into `samples::all` and `CHECKS_SCHEMAS`.
- **Words a person reads are codes, not English**: a `Decision` carries `reason` (English, for agents and logs) and `why` (`DecisionWhy`, a union tagged by `code` with that code's numbers and ids); a screen shows `why` through its en/ko keys, never `reason`. In Rust `DecisionWhy` is a flat struct (`DecisionWhy::new(code)` plus that code's fields), because an internally tagged enum read from text loses its numbers in a workspace build (serde_json's `arbitrary_precision`; every tagged request main sends is read through a plain wire struct for the same reason).
- **Where it lives**: the hub is the core process's (`crates/core/src/checks/`, new, nothing moved from TypeScript), as the design's §4 chose. The agent tool's body also runs in the core (`agentctl`) and asks the hub in-process (`checks::hub(id)`); main reaches it through its typed client `src/main/checks/client.ts` (`CoreChecksHub`). The CLI twin `ompdesk checks` goes through the control socket like every tool, so without a running OMPdesk it can answer only this computer's own pool.
- **`ChecksHub`** (`hub.rs`; `ChecksHub` in `checks-contract.ts` is the same interface for TypeScript): `start`, `wait`, `status`, the read-only streams `watch` (the whole `Snapshot`, now and at each change) and `results` (every `RunResult` as it arrives, whoever waits: main wakes the session that started the run), and the owner's one control `pause`. A refusal is an answer (`decision: refused` with its reason), never a fault. A wait that runs out answers `verdict: unknown, next: wait`, never an error, and a cancelled request ends its wait. `origin` (who asks) is main's word in every call, never an argument a caller wrote: a session by its saved id (the id in its session file's name; its tab id while it has no file) and its computer (`local` for the hub's own, else the paired device's id); `goal` is the goal's own short text, shown as written, never an id to look up.
- **What main tells the hub**, because the hub cannot read it: `told(MainFact)` (`repos`: the repos of the open sessions' checkouts; `devicePool` and `deviceOffline`: a paired computer's pool as it answered over the link, or that the link is lost; `sessions`: whose each session tag is, so a local check run names its session) and `runners` (how gh and git run: main's `ghRunner` and `gitRunner`, sent after the open and again when the login shell's environment changed). The runners hold the environment, tokens included: they are in no serializable shape, no sample, no log and no answer, and the fake hub keeps only which of the two came (`client.test.ts`).
- **The wire** (`mod.rs`, names in `contract::wire` and `CHECKS_WIRE`): requests `checks.open {hub, fake?}`, `checks.close`, `checks.start|wait|status {hub, origin, request}`, `checks.watch {hub, on}` (answers the snapshot now), `checks.pause {hub, paused}`, `checks.facts {hub, fact}`, `checks.runners {hub, gh, git, home}`, `checks.localPool {hub}` (this computer's own `LocalPool` as its poller reads it: a paired computer's link forwards it to the other hub as `devicePool` with its own device id, so `ompdesk heavy status` is mapped in one place, `poller::local::pool_of`), `checks.fake {hub, op}`; events `checks.snapshot {hub, snapshot}` while a watch is on and `checks.result {hub, result}` always. `hub` is main's id for the hub it opened; a hub whose connection ended is closed (`close_all` in `server.rs`).
- **Ids**: a run the hub started keeps the id the hub gave it at `start` (a held run has one before any GitHub run exists); a GitHub run nobody started through the hub is `gh-<GitHub's run id>` with `origin: person`, a local check run `local-<journal id>`. Pools are `github-macos|windows|linux` and `device-<device id>`.
- **Fact adapters** (`sources.rs`): `GithubSource` (runs, jobs, a job's log, a run's artifacts and an artifact's zip, a repository variable, a ref's head, a folder's checkout, whether a repo is private, and the only writes a policy makes: dispatch, cancel, rerun the failed jobs) and `LocalSource` (each computer's heavy pool and disk, the `ompdesk check` journals and their flaky record). Their shapes are the sources' own facts and decide nothing. `FakeGithub` and `FakeLocal` answer facts a test sets (`with`), fail every call while `down` is set, and `FakeGithub` records its writes and counts its reads (what a budget test asserts).
- **Fakes of the hub**: `fake.rs` `FakeHub` (opened with `checks.open {fake: true}`, scripted by `checks.fake`: set the snapshot, queue a start reply, hand in a result, read the calls it got) and its in-memory twin `createFakeChecksHub` with made-up screen data `sampleSnapshot`/`sampleAnswer` (`src/shared/checks-fixture.ts`, for the page's dev harness and component tests). `src/main/checks/client.test.ts` runs the same cases over both, the core's through the real process.
- **What is not built**: the real `Hub` answers `not_built` for every call and `checks.open` without `fake` is refused the same way, until its parts land. Each part is its owner's file under `checks/`, and `mod.rs` declares every one from the start (an empty file until its part lands), so no part edits `mod.rs`: `admission.rs` (what a start decides) and `answer.rs` (a run's result as an agent reads it), the contract owner's; `poller.rs` (the one reader of GitHub and the pools, and the real sources); `queue.rs` (the merge queue); `results.rs`, `trends.rs` and `place.rs` (test results, flaky tests and cost, local or runner). `contract.rs` and `hub.rs` change through the contract's owner only.
- **Admission to the merge queue** (`hub.rs`): a `start {purpose: land}` is resolved by admission (repo, branch, its head, the base, past the pause) and handed to `Hub.queue` as `LandQueue::enqueue(origin, LandRequest)`, whose reply's `runId` names the queue entry; the queue shows itself through `LandQueue::entries` (the snapshot's `queue`). The queue asks the hub through `QueueHost`: `start_batch` (a batch's run on its temporary branch goes through the same admission as every run, lane `land`), `batch_answer`, and `finished(RunResult)` for each entry, which ends that entry's waits and wakes its session. Until `queue.rs` is built `Hub::new` holds a queue that lands nothing.

### The screens and main's relay
- **Watching, not operating** (design §8, the owner's approval of 13 Nov 2026): the person's one control is **Pause admission** on the Checks page. Nothing else there, in the sidebar block or on the work board's row is a button that acts on a run, a test or the queue; a new control needs the owner.
- **One frame, one copy** (`src/shared/checks-frame.ts` `ChecksFrame`): main's relay (`src/main/checks/relay.ts`, wired in `index.ts`) watches the hub through `CoreChecksHub` and sends `{snapshot, names, hub}` to every window and paired phone's page (`CHECKS_FRAME` push, `CHECKS_GET` for a window that mounts later, `CHECKS_SET_PAUSED` → `hub.pause`, permission `host-admin`; agents have no action for any of the three, `channels.rs`). The snapshot is the contract's, untouched. `names` are the names main knows for the ids in it (`namesFor`: `local` is this computer, a paired one by its device id, a session by its saved id from the session index; a goal is its own text and needs none), read when the frame is sent, because the contract carries ids only and a title changes without the hub hearing of it; an id main cannot name is absent and the page says "A session". `hub: "lost"` marks the last frame once the core ended, until the next snapshot. The renderer keeps the frame in `stores/checks.ts` (`subscribeChecks` from `App.tsx`; a push that lands before the boot read wins). No frame (the real hub answers nothing until its parts land) means nothing of check control draws anywhere.
  - **It is this computer's hub, not the focused tab's host's**: the hub already pools every paired computer and the GitHub account, so the page does not follow `useFocusedHost` as Settings and Stats do. A phone's page shows its host's frame.
  - **Nothing old reads as current** (design §9.3): `freshness(frame)` (`lib/checks/view.ts`) is `lost` while main cannot reach the hub and `stale` once the hub itself reads no pool as live; the page then says so above everything and the sidebar block's waiting count gives way to a muted word. Staleness is the hub's word (`Pool.state`), never a clock in the renderer.
- **Every figure has one owner**: `src/renderer/lib/checks/view.ts` (pure, pinned by `view.test.ts`) says which pools have work and in what order, a pool's load (`poolLoad`: OMPdesk's running jobs plus `Pool.foreign`, heavy work outside it that takes the machine without a slot; shown and counted, never managed), how full a pool is (`full` once its load fills its slots: the warning fill, never danger, since a full pool is busy, not broken), a release's gates (`gateJobs`: a gate's jobs of its run by `Job.name`) and what its runs wait on (`releaseWaits`), a run's one word (`runState`), its jobs per OS, the run a session waits on (`waitedRun`: by its saved id or its tab's id, on its computer). A screen that needs another reading adds it there.
- **Sidebar block** (`layout/sidebar/SidebarChecks.tsx`, mounted in `SidebarFooter` above the usage block; styles in `sidebar.css`): draws nothing with no frame or no pool at work. One `Gauge` per pool with work (GitHub's first, then this computer; four at most, the rest one "+N more pools" line), the jobs waiting as a warning badge, the first release's gate line. The whole block is ONE button that opens the page (its accessible name says the block in a sentence). It is not a rail pin and has no setting, fold or menu. `Gauge` (`components/common`) is the bar `UsageGauges` draws, lifted out for a value that is no percent.
- **Checks page** (`components/checks/`, destination `checks`: `useUiStore.openChecks(tab?, run?)`, palette command `checks`; tabs Now, Merge queue, Tests and cost): Now is capacity by device, runner and OS (with the work outside OMPdesk on each computer), each release's gates with where their jobs run, runs under their lane with the session, goal and computer behind each (a person's, an outside caller's and another repository's run are listed and say so: shown and counted, never governed), the last answer an agent received, the merge queue and the Decided-automatically log (one translated sentence per `PolicyAction`). The other tabs draw what the snapshot holds and an empty state otherwise. The page lays itself out by its own width (`@container omp-checks`, `styles/checks.css`, loaded with the page's chunk), so a paired computer's narrow window and the phone get one column by the same rule; a phone's tabs are a segmented bar.
- **Work board row** (`WorkBoardSession.tsx` `HubCheckRow`, row kind `hub-check` after the shell check row): the newest live hub run whose origin is the board's session (`waitedRun`) reads "Check · release gate · 21m"; its tooltip says the session is woken when the result arrives; a tap opens the page on that run (`checksRun`: the row is marked `aria-current` and scrolled into view). It is no attention kind.
- **Fakes for screens**: component tests and the dev harness (`?checks=busy|idle`, `dev-harness/fixture-checks.ts`) use `sampleSnapshot` with `sampleNames` (`src/shared/checks-frame-fixture.ts`). An unpackaged launch with `OMP_GUI_TEST_CHECKS=busy` opens the core's scripted hub and shows the same sample (anything else: an empty hub); the parity surfaces `sidebar-checks` and `checks-page` need it (ui-parity.md).
