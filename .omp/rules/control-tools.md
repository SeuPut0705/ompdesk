## OMPdesk control tools

### Overview and safety
- Switch: Settings › Tools & extensions › OMPdesk control tools, pref `agentControl`, default **on**. Contract `src/shared/agent-control.ts`, rules `src/main/agent-control/service.ts`, schemas `tools.ts`, app seam `host.ts`, skill `resources/omp-builtin/skills/ompdesk/SKILL.md`.
- **Full control** (the user's decision, 19 Oct 2026): Settings › Tools & extensions, first row "Give agents full control of OMPdesk" / "에이전트에게 OMPdesk 모든 권한", pref `agentControlFull` (`AGENT_CONTROL_FULL_PREF`), default **on** for every install (`agentControlFullEnabled`: only a stored `false` is off). While on, **no control tool or app action raises an `[OMPdesk]` card**: the `always` set (deletes, MCP/plugin install, sign-in starts, proxy, mobile web on, pairing, update apply, quit), a foreign session delete, Autopilot release or main targets, every power pref; it implies `agentControlApprove` and `agentControlManage` (`host.ts` resolves both as `full || stored`; the Settings rows show them checked and disabled as covered), and the catalog action `agent_power.set` (`fullOnly`; `FULL_CONTROL_PREFS`/`FULL_CONTROL_SETTINGS` in `app-guard.ts`, the two memory switches through ai-memory's own channels) lets an agent change the agent-power switches, this one included. Every action is still journaled and toasted with undo where one exists. Kept whatever it says: an agent never answers an `[OMPdesk]` card (and with the switch on none is raised), secrets/tokens/passwords are never readable, git safety (no force push, Autopilot's guard bans destructive git), and OS security prompts (UAC, TCC). Its tooltip names the risk: prompt-injected content can then make an agent delete data or install code unasked. **Every card rule below applies only while full control is off.** Pinned by `shared/agent-control.test.ts`, `app-control.test.ts` (each `always` action runs card-free when on, `agent_power.set` refused when off), `service.test.ts`, `host.test.ts`, `AgentControlRow.test.tsx`, and the on/off cases of `e2e/agent-app-control.e2e.ts`, `e2e/agent-control.e2e.ts`, `e2e/agent-review.e2e.ts`.
- Host tools (like `gui_terminal_read`) are registered with stock `set_host_tools` on every ready local sidecar (`SidecarManager.syncHostTools`, re-sent when the switch changes) and answered in `ipc.ts` (`hostToolExecutor` → `AgentControlRuntime.run`). The skill's root `resources/omp-builtin` is a `-e` directory only while the switch is on, so skill and tools come and go with the pref.
- Tools (`AGENT_CONTROL_TOOLS`): `ompdesk_sessions`, `_session_open` (one or `sessions: […]`, optional `worktree: true | {branch, base: HEAD|default}`), `_session_send` (steer or follow-up), `_session_result` (several ids, `wait`, `until all|any`), `_session_read` (pages via `get_transcript_page`), `_session_answer`, `ompdesk_tab_focus` (renderer pick/split via `AGENT_CONTROL_VIEW`), `ompdesk_notify`, `_session_stop` (`close`, `delete`), `ompdesk_compare`, `ompdesk_merge`, `ompdesk_schedule`, `ompdesk_autopilot`, `ompdesk_app_list`, `ompdesk_app`, `ompdesk_report`.
- Everything runs through existing GUI paths: prompts/steers through `dispatchRpcCommand` (a paired host's tab goes over the link, so the host's grants and the per-device quota apply; `src/main/remote/quota-commands.ts` lists `agent_control_confirm`/`agent_control_note` as free), `spawnTabForWindow` to open, the renderer's own close, `deleteSession` for delete.
- **Subagents have no control tools** (stock registers host tools on the RPC session only; `host_tool_call` carries no caller id). `e2e/real-agent-control.e2e.ts` checks it: a subagent answers `NO_TOOL` and no tab opens.
- **No count or rate caps** (the user's rule, 19 Oct 2026; none exist in `src/main/agent-control`): any number of sessions opened, messages sent, schedules and Autopilot runs. Only a self-send is refused. Provenance ("opened by you") is main-owned state, never read from text or tool args; it survives a relaunch (`#openedBy` adds every tab whose `host.parentOf` is the caller: the pool's `openedBy`, else the tab holding `openedBySession`).
- Session tools touch no accounts, settings or permissions. **Deleting a saved session the caller did not open** (`ompdesk_session_stop delete:true`) always raises one confirmation card (stock extension-UI `confirm` via the calling tab's omp, bridge `agent_control.confirm`, title prefix `[OMPdesk]`, so it survives a reload and reaches a paired device), whatever "Let agents manage other sessions" says: a delete cannot be undone. Stopping or closing a session it did not open raises the same card only while that switch (`agentControlManage`, **default on**: `agentControlManageEnabled` in `shared/agent-control.ts` treats an unset pref as on and only a stored `false` as off) is off. Sessions it opened itself need none, delete included.
- Closing a resting session's tab (not busy, no open ask, not in the person's view, no draft or prompt of theirs since: `ControlTab.looked`/`userTouched`) raises no card whoever opened it; a session in view or typed into is never closed (re-checked right before the close). Each close is journaled as one quiet `ompdesk.mail` note in both sessions, **only once the tab is confirmed gone** (`#journalClose` runs after `#closeTab`/`#deleteWhenIdle` returned): a close the window kept or main held back sends no note, so the caller never reads "Closed" beside a failed close. The closed session's own line is best effort: its omp has exited by then, so it lands only where something still answers for that tab (it used to be sent before the close, which told a session that stayed open it had been closed).
- `_answer` answers asks (select, confirm, input, ask); the answered session journals `ompdesk.agent-answer` and toasts "에이전트가 답함 (title)" (bridge `agent_control.note`). A **tool approval** ("Allow tool: …") is approved only when "Let agents approve for other sessions" (`agentControlApprove`, **default off** on purpose: an agent approving another session's tool bypasses the user's own approval policy, so it stays the user's explicit choice; `agentControlApproveEnabled` is true only for a stored `true`) is on, else "사용자 승인이 필요해요" (deny always works). Stock's "Approve <tool> for this session" option needs the same leave. A card titled `[OMPdesk] …` is never answerable.
- **Stock's tool approval shape** is one rule, `src/shared/tool-approval.ts` (`approvalChoices`, `isApprovalSelect`; the renderer's `isApprovalRequest` narrows it; `APPROVAL_MODES` lists stock's `tools.approvalMode` values for the composer, tray and agent catalog): an RPC host has no `approve` UI, so stock `requestApproval` sends a `select` titled "Allow tool: <name>" whose options are stock's `approvalChoiceLabels`: under "Ask and remember" (`always-ask-cached`, omp ≥ 18.12.3) the grants first ("Approve Directory: <folder>", "Approve File" or "Approve" for a target that is no file: remembered for this session), then the same with "Always " in front (every session), then this call only ("Approve", or "Approve Once" beside grants), "Approve <subject> for this session" when the approval mode raised it, and "Deny" last. `ApprovalDialog` shows every choice in stock's order with words that name what is remembered and for how long (`approval.grant.*`); an agent's `approve: true` and Autopilot's approver answer stock's this-call option only (`ApprovalChoices.once`), so every later call still meets its guard, and every approving answer needs the approve leave. Before this a "Ask and remember" prompt read as a plain select. Pinned to the installed omp by `src/main/tool-approval-stock.test.ts` (a command, a file, a folder and a web address, with and without a session subject), the card by `ApprovalDialog.test.tsx`.
- **A plan awaiting approval is a waiting state.** The bridge (`modes/plan.ts` `settlePending`) emits `plan_proposal_resolved {planFilePath}` whenever a shown proposal stops waiting: approved or rejected from any window, device or agent, a turn starting while it waits (a prompt replies to it as feedback, as the card's refine does), plan mode left, a session switch. The pool holds `PoolEntry.planProposal` from `plan_proposal` to that frame (`SidecarPool.pendingPlan`; an omp exit drops it) and forwards both to hidden tabs; every window's `use-plan-approval.ts` clears the card unless its own answer is in flight (that keeps its outcome notice). `ControlTab.plan` makes the session waiting everywhere asks do (`waits()` in `service.ts`: listing `waiting for plan approval: "<title>" (<path>)`, `ompdesk_session_result` wait, no auto-close, no merge, review item `waiting`). `_answer` on it sends the card's own `plan_approval`: `approve: true` with `choice` `execute` (default) / `compact` / `keep_context` (approving follows the tool-approval rule, `approveEnabled`, implied by full control), or `approve: false` with `text` as feedback (always allowed); `save` stays the person's. Pinned by `service.test.ts` (plan cases), `sidecar-pool.test.ts`, `PlanApprovalDialog.test.tsx` and the plan tests of `e2e/agent-control.e2e.ts` (the fake omp mirrors `settlePending`).
- A message another session's agent sends arrives as a stock prompt wrapped in `<ompdesk-agent-message from="…">` (`wrapAgentMessage`; a body cannot forge or close it), shown as "에이전트가 보냄 · title" (`MessageBubble`/`promptDisplayText`).
- The user can hide a session from agents (Sidebar session menu › "다른 에이전트가 이 세션을 보지 못하게", `agentHidden` in the `sidebar` prefs blob, this computer's sessions): it lists as hidden and refuses read, send, wait, answer, show and stop.
- Autopilot hooks (optional host deps `isStopping`, `beforeFirstPrompt`; `AgentControl.childrenOf`, `clearQueue`, `openSessions(caller, sessions, tag)`) keep `src/main/autopilot*.ts` out of this module.
- Tests: `agent-control/*.test.ts`, `shared/agent-control.test.ts` (default resolution: unset → manage on, approve off; stored `false`/`true` honoured), `AgentControlRow.test.tsx`, `e2e/agent-control.e2e.ts` (fake omp: create → send → wait → read, the delete card for a foreign session, an approval), `e2e/agent-app-control.e2e.ts` (no card by default, the card with the switch stored off, a deleting action asks either way), opt-in `e2e/real-agent-control.e2e.ts`. The fake omp implements `get_last_assistant_text`, `agent_control.confirm` and `agent_control.note`.

### App control (`ompdesk_app_list`, `ompdesk_app`)
- Changes the app itself in main; arguments are validated against the action's schema. `app-catalog.ts` actions, `app-settings.ts` one `settings.<row>` action per Settings row, `app-control.ts` the one dispatch point, `app-guard.ts` and `app-channels.ts` the agent's own default-deny risk tables. `AGENT_CHANNELS` is typed over every `IpcChannel`: a new channel does not compile until it is `never` with a reason or lists the actions that call it. `IPC_POLICY` is the web device's table, not the agent's.
- `read`/`change` are free; a change is journaled in the caller's session (`agent_control_note`) and shown as a quiet toast with one-step undo when a previous value exists (`AGENT_CONTROL_APP` → `lib/agent-app.ts`, applied live).
- `sensitive` raises no card while full control is on. With it off, it raises the same `[OMPdesk]` card only while `agentControlManage` (default on) is off, **except the actions whose `manage` rule is `always`** (`ManageRule` in `app-settings.ts`, a field of `AppAction` and of a Settings row): every `sensitive` action must decide `{ lifts: reason }` or `{ always: reason, when? }`; `app-catalog.test.ts` fails on one that does not, and `app-control.test.ts` pins the `always` list (`agent_power.set`, `fullOnly`, is pinned on its own). `always` asks whatever the manage switch says because the action erases data (`sessions.delete`, `memory.purge`, `memory.delete_page`, `memory.sweep`), runs code (`extensions.install_plugin`, `extensions.install_mcp`, `extensions.mcp_use`), touches credentials or traffic (`accounts.github_sign_in`, `accounts.provider_sign_in`, `extensions.mcp_sign_in`, `settings.proxy`), exposes or connects the computer (`mobile_web.set_enabled` when turning it on, `remote.connect`, `remote.unblock`, `remote.set_allowed_users`) or ends running work (`updates.apply`, `app.quit`). The rest lift (`updates.check`, the four auto-update switches, `builtinRea`, `rotation`, `remote.block`); an `undo` of a setting asks by its row's rule. `remote.list_tailnet` (read) lists the tailnet's computers for `remote.connect`. MCP servers: see Panels, sidebar and work views › MCP servers.
- **Which computer.** A caller tab that runs on a paired host (`AppPorts.device(tabId)` = its sidecar's `device`; `ActionContext.device`) gets what the Settings page gives that tab, so no action is local-only where a host route exists. Already the host's through the tab's own RPC: every stock setting, models, usage, plugins, MCP. Routed by device: `HOST_PREFS` (`app-settings.ts`) sends `settings.rotation` and `settings.builtinRea` (read, write and undo) through `ACCOUNT_ROTATION_*`/`BUILTIN_REA_*` with the device (`machine-services.ts` `RemoteMachine`), never into this computer's prefs; `sessions.saved|search|rename|delete` put the device in the `sessions:*` payload; `updates.status|check|apply` take `host: true` for `HOST_DESKTOP_*` (the host's OMPdesk; a session on this computer refuses it, and the host refuses an install while any work runs). Tiers, cards and the channel table are unchanged (`AGENT_CHANNELS` lists the routed channels per action). This device's own, in the Settings UI too, so they stay here: every other pref row (a paired host's tab follows the host's own pref), this app's updater switches, memory, remote devices, Mobile web, GitHub, `ui.*`, `app.quit`.
- `autopilot.*` actions call `ompdesk_autopilot` (its card and folder rules); `get_autopilot`/`set_autopilot` are `never` for app actions.
- `never` refuses, whatever the switches say: secrets and tokens, answering a card, `RPC_COMMAND_FOR_TAB` and any raw RPC passthrough. While full control is off it also refuses the agent-power switches (the control tools switch, `agentControlFull`/`agentControlManage`/`agentControlApprove`, `tools.approvalMode` and every approval, memory and computer-use switch), which `agent_power.set` reaches only under full control. It holds whether reached as a pref, a stock setting, an RPC command or one command inside another (`ActionContext` re-checks every primitive with the current full-control state; a nested RPC command is `never`).

### The `ompdesk` skill
- Kernel plus references: `SKILL.md` (at most 60 lines: tools, when to open a session, definition of done, the brief template with Ownership and Observable acceptance, handoff vs supervise, reuse a finished child, "silence is a checkpoint, not failure") links `skill://ompdesk/references/<file>.md` (`orchestration`, `worktrees-review`, `schedules`, `across`, `autopilot`, `app-control`), resolved against the skill's own `baseDir` inside an extension root (`internal-urls/skill-protocol.ts`). Each rule sits where it is used (e.g. never follow an absolute path in a child's answer into the main checkout: in the collect and compare steps). The kernel teaches the opener's loop (dispatch, end the turn, be woken, judge with `ompdesk_compare`, merge) instead of polling.
- `skill-drift.test.ts` fails when a tool or parameter in `tools.ts` and the skill disagree (renamed, added, or a word on a kernel tool line that is no parameter or enum value of it), when a `skill://` link names a missing file, or when the kernel passes 60 lines.
- There is no "remember" control tool: an agent saves durable learnings with ai-memory's own MCP tools (the skill points at `ai-memory-durable-pages`).

### Worker contract
- `#openOne` sends each child `agent_control_worker {from}` (local handler → bridge `agent_control.worker`, free in `quota-commands.ts`) once ready and before its first prompt. The child journals one `ompdesk.worker` custom entry; `resources/gui-bridge/agent-control.ts` registers the `ompdesk-worker` prompt section (`registerPromptSection`), appending `WORKER_CONTRACT` for the main agent of a session whose branch holds that entry.
- `WORKER_CONTRACT`: stay in your folder and the named scope; done = the message's acceptance checked; the final answer names changes, the check run and what is left, and ends with `Result: ok` or `Result: problem — <reason>`, and is delivered to the opener as the done report (main sends it, below); `ompdesk_report` stays for question/blocked (decisions), progress at real milestones and a note to a sibling.
- **The done report is main's job** (measured 24 Oct 2026: every worker dispatch spent 2 extra model requests, reading the `xd://ompdesk_report` docs and writing a `done`, before an answer its opener gets anyway; OMPdesk's prompt already weighed ~23.6k tokens over stock). `AgentControl.#autoDone` (`service.ts`, run in `autoClose`'s pass before the close decision) sends the opener a `done` report through `#report` (custody line, MailOutbox, dedupe id, pickup, `aside` + turn) when an agent-opened child's turn ended `ok`, idle and settled, its last answer ends with a `Result` line (`ok` or `problem`), it has no `done` or `review` to the opener on its current dispatch (a progress or note before the finish does not count), and no question or blocker of its waits for the opener's answer (`Mailbox` `waiting`, cleared by the opener's next send, the new dispatch; a done would read the decision gate as settled). `#autoDoneFor` keeps a failed post from being retried. Text is the final answer cut at `MESSAGE_MAX_CHARS`. Never a failed or stopped turn, a child the person typed into, one a relaunch restored, or a dispatch already reported (a child that still calls `ompdesk_report` done itself yields one report); a turn with no verdict line keeps `#nudgeSilent`. Pinned by "the done report main sends for a child" in `service.test.ts` (progress or note then finish → one done; an unanswered question or blocker → none, the opener's answer then the finish → one).
- Journal-based, so a relaunched child keeps it; a session the user opened, the parent and a worker's own subagents never get it. Pinned by `bridge-agent-worker.test.ts` and `service.test.ts` (fan-out); the fake omp answers `agent_control.worker`.
- **A host tool description opens with one short line** (measured 25 Oct 2026: stock lists a mounted host tool as `xd://<name> — <first non-empty line of its description>` cut at 200 bytes (`promptCatalogSummary`, `xdev.ts`), so the one-paragraph descriptions put ~72 tokens each of mid-sentence text in the prompt: the 18 `ompdesk_*`/`gui_*` lines were 1,331 tokens, 629 with a lead line; the worker-session first request fell 704 tokens). Each `description` in `AGENT_CONTROL_DEFINITIONS`, `TERMINAL_READ_DEFINITION` and `VISUALIZE_DEFINITION` starts with a sentence of about 80 characters saying when to use the tool, then `\n`, then the full docs (read on `xd://<name>`). A new host tool follows it; the rest of the text is unchanged, so no fact is lost. `tools.test.ts` pins only the shape, not the wording.

### Worktrees and the review list
- `ompdesk_session_open` with `worktree` makes each child's checkout and branch through `worktree_create` (`omp/agent/<slug>`, base `HEAD` or `default`). Files: `branches.ts`, `stores/agent-review.ts`.
- **An open never leaves half** (v0.46.0 left a worktree and branch behind when a busy omp's first command passed 8 s): the child's first command (`agent_control_worker`, which waits for the local handler's `get_state`, the bridge connect and the bridge's module load) gets `FIRST_COMMAND_TIMEOUT_MS` (60 s, `service.ts`); an open that still fails, or a spawn that never started, closes the tab and, once the tab is gone from the pool (`CLOSE_WAIT_MS`; a tab the window keeps keeps its worktree, named in the error), takes back the worktree it made through `discardOpenedWorktree` (`disk/saved-worktrees.ts` over `discardNewWorktree` in `branches.ts`; `host.git.discardWorktree` on a paired host): under `withRemovalClaim` with every open folder of this computer (`sessionOpenFolders`; no tab starts there meanwhile), once the closed tab's omp has exited (`omp-exits.ts`: `SidecarPool` and `LocalHostServices` note every released omp's exit by folder; up to 5 s, else kept) and, where process folders can be read (not on Windows), no other process works in it, `archiveBeforeRemove` first, as before every removal (ignored files a seeding or setup hook made or someone edited are archived and listed under Saved worktrees; a refusal keeps the worktree), then `worktree remove` without `--force`, then `update-ref -d` of the branch against the commit it was created at, only while its reflog holds that one entry. A branch cut from the default branch is ahead of an unpulled parent checkout, so `removeSafeWorktree`'s `branch -d` would keep it. What git keeps is named in the error. Pinned by the "8 s", "takes back the worktree" and "tab is still open" cases of `service.test.ts` and `discardNewWorktree` in `branches-worktrees.test.ts` (an edited ignored `.env` archived and restored; the claim held while it archives; a worktree in use or with a process in it kept).
- **On every computer alike** (the user's rule: every agent tool works on a paired device's sessions exactly as on local ones): the git of a session's worktree runs on the computer the session runs on. `AgentControlHost.branchFacts`/`mergeBranch`/`landing`/`removeSafeWorktree` take the session's `device`; for a paired host `host.ts` asks it `host.git.facts|evidence|landing|merge|removeWorktree` (`GIT_METHODS` in `remote/app-protocol.ts`, params zod-checked in `host-services.ts`, `GIT_REQUEST_TIMEOUT_MS`), which run the same `branches.ts` on the host's checkout and answer the same shapes; a `BranchError` reaches the agent as its message. A child opened on another computer than the caller's (`device` ≠ the caller's) gets its worktree there: `host.git.worktreeCreate {baseCwd, name, branchPrefix, baseRef}` runs the same `createWorktree` (seeding and setup hook included) on the host, or locally for a remote caller opening here; it needs that device's absolute `folder`. No session of that computer has to run: the location comes from the stock helper's `git.worktree_location` (`stock-helper/worktrees.ts`: stock `worktree.base` read-only for the repository, applied with pi-utils `setWorktreesDir` as stock's effect does, then `getWorktreesDir`/`hashPath`; `tablessWorktreeBridge` in `local/git/worktree.ts`; internals under `worktreeLifecycle` in `capabilities.ts`), the answer a session's bridge gives. A caller on the target computer keeps the `worktree_create` command through its own tab. Git ops are free (no `PeerQuota`). Pinned by the paired-host cases of `service.test.ts` and `host.test.ts`, the `host.git.*` tests of `remote/host-services.test.ts` (real temp repos, no session running), `stock-helper-worktrees.test.ts` (real omp: config's `worktree.base`, `OMP_WORKTREE_DIR` over it, stock's hash) and `e2e/agent-control-across.e2e.ts` (two apps: worktree session on the host, compare, merge into the host's checkout; the fake install's stock modules are `e2e/worktree-location-fixture.ts`).
- `ompdesk_compare` reads each child's branch (`git merge-base`, `diff --numstat`, commits ahead, uncommitted and untracked counts), a merge prediction and its final answer; it **runs no tests** (a child reports them). The prediction (`predictMerge`, `branches.ts`) is `git merge-tree --write-tree --name-only` of the parent's HEAD and the branch tip with a quarantined object store (`GIT_OBJECT_DIRECTORY` a scratch dir, the repo's store as alternate, deleted after; idea from Orca's `conflict-summary.ts`, MIT, re-implemented), so no checkout, index, ref or object of the repo changes; the line reads `merge: would conflict in <files>`, `no conflict with <base>` or `not predicted (<reason>)` (git < 2.38), and a predicted conflict marks the child's review item `conflict`.
- **Where a branch lands** (`branchFacts`/`landingFacts`, one rule): the parent checkout's HEAD and the upstream its branch tracks (`<branch>@{upstream}`, else `refs/remotes/origin/HEAD`; refs as last fetched, never fetches, never touches the parent checkout). Agents push their own work (`git push origin HEAD:main`) while the parent's local main stays behind, so a tip in either has **landed** (`BranchFacts.merged`) and its diff is measured from that tip (only uncommitted work is left). An unlanded branch is measured from its merge-base with the upstream when the upstream holds the parent's HEAD, else with the parent's HEAD, so a stale local main never lends a child the upstream's newer commits (it once showed every pushed child as "200 files · +40520 −425").
- `ompdesk_merge` merges into the parent checkout's current branch with `git merge --no-ff` (never a push, no remote command in the module). It refuses a detached parent, uncommitted work in child or parent, and a branch with nothing to merge (`mergeProblem`); asks one `[OMPdesk]` card only while `agentControlManage` (default on) is off; refuses a merge `predictMerge` says would conflict before running `git merge` (`MergeOutcome.predicted`, the files named, the parent untouched), and still aborts a conflict it did not predict (`git merge --abort`) naming the files.
- **The work board has no review section** (the user's decision): the agent that opened a child reviews and lands it itself with `ompdesk_compare`, `ompdesk_merge` and `ompdesk_session_stop`; nobody clicks Approve, Discard or Dismiss on a board (desktop or phone strip), and `agent_control_review` only lists. `AgentControl.reviewItems` stays: pushed as `AGENT_CONTROL_REVIEW` after a 400 ms settle on child activity and asked once on mount via the `agent_control_review` command `dispatchRpcCommand` answers itself, it feeds the "Child sessions" rows (title, status, step, clock, report, waiting) and the opener's next-prompt children. A child that needs the person (a question, a blocker, a plan waiting for approval: `AgentReviewItem.waiting`) shows as a waiting row and a notification. No item when nothing is left: idle (no turn, no open ask), branch landed, no uncommitted or untracked file, not failed, not waiting on an answer (its opened row reads merged). A landed branch with leftovers lists only those.
  - The review list follows the world, not only tab activity: besides the pushes after a child's activity and after `ompdesk_session_open`/`_merge`/`_stop`/`_autopilot`, `AgentControlRuntime.#sweepAll` (the 10 s timer that also runs the auto-close pass; `OMP_GUI_TEST_AGENT_SWEEP_MS` in e2e) re-reads each opener's `reviewItems` and sends `AGENT_CONTROL_REVIEW` only when the list differs from the one last sent (`#reviewSent`), so a commit, push or merge made outside the app moves a child's row without tab activity: an idle child whose branch has landed (an untouched branch counts: its tip is in the parent's HEAD) and has no uncommitted or untracked file has no item. `e2e/agent-review.e2e.ts` commits into each child's checkout from outside the app and waits for the board to list all three as opened rows, with no review section or button; `host.test.ts` pins the timer push (changed → sent, unchanged → silent).
  - A child's release always reaches the board that listed it. A child restored by a relaunch has its opener only in the pool (`openedBySession`), which forgets it with the tab, so its `released` found no opener and the board kept the stale item beside the closed record: one finished child read "2 done" (`e2e/opened-close-relaunch.e2e.ts`, 7 of 8 runs). `#listedIn` remembers, per child tab, the opener whose list (a push or the board's own read) last named it, and a release with no opener left pushes that opener's list. A report's id defaults to a hash of both session files, kind, dispatch and text, so a call stock re-runs after a relaunch has the same id; the receiver's bridge drops an id its branch already holds (`hasMailEntry` over stock's `custom_message` entries) or this process already handed to stock, and answers `{duplicate: true, journaled}` (`journaled` false = only queued by this omp). A report counts as delivered (`#seen`) only after delivery succeeded; a failed one is retried by the sender with the same id (progress `MAIL_PROGRESS_RETRIES` = 3). After a relaunch main reads dispatch and request ids back from the child's transcript (`journalMarks`), so fencing and `request_id` idempotency of `ompdesk_session_send` hold. Concurrent sends with one `request_id` (keyed by both session files) join one in-flight delivery.
- **A report survives its receiver's omp ending** (21 Oct 2026: a child's `done`, then a `followUp`, to a parent inside a long tool call vanished across an update restart). Measured on the installed omp (`bridge-agent-mail-restart-stock.test.ts`): an aside queued during a model request or a tool call is journaled when a quit disposes the session (stdin closed the way `SidecarManager` closes an omp), for every kind, but a SIGKILL before the next step boundary (a crash, a force-quit of OMPdesk) loses it. So `AgentControlRuntime` keeps every accepted report in `MailOutbox` (`mail-outbox.ts`, `<userData>/mail-outbox.json`, atomic write at accept time and never in a quit hook, newest `MAIL_OUTBOX_MAX` = 100, none older than `MAIL_OUTBOX_TTL_MS` = 3 days; an earlier build's `followUp` entry is read as an aside) per receiver session file and paired device, unless the first answer already says journaled. On the sweep timer (`sweepMs`, 10 s) `redeliverMail` sends each entry again, with its id, to the tab that holds the receiver's session now (`SidecarPool.sessionOwner`; a relaunch gives it a new tab id; a closed tab waits until the session is reopened): the bridge delivers an id it never saw (the omp that replaced the killed one), answers `{duplicate, journaled: false}` for one it still queues (left alone), and `{duplicate, journaled: true}` settles the entry. Never delivered twice: the receiver's journal and `queuedMail` dedupe by id. A report journaled but never answered by a turn counts as delivered: the model reads it with the journal when the interrupted turn continues.
- Receipts: a send answers `accepted` plus `turn started` when the target is seen running within `TURN_START_WAIT_MS` (1.5 s). No count or rate cap; only a self-send is refused.
- **A child's question card tells its opener** (20 Oct 2026: a child opened on a paired Windows device raised a stock `ask`, and its opener learned of it only by polling `ompdesk_session_result`; a local child's card woke nobody either). The pool's `ask` activity (`SidecarPool.#announceAsk`, from a local omp's frame or a paired host's `extensionUi`/`openAsks` alike) reaches `AgentControlRuntime`, which calls `AgentControl.childAsked(opener, child, requestId)` for a session the opener opened: one `question` mail (`aside`, wakes an idle opener) whose text is the card (`cardText`: title, options as written, the `ompdesk_session_answer` field that answers it) and `Mail.card` the request id, so `mailText` points at `ompdesk_session_answer` instead of `ompdesk_session_send`. Id `ask-<child>-<request>`, told once per card (`#cardsTold`; the bridge drops a repeat by id). Never OMPdesk's own `[OMPdesk]` card, a session hidden from agents, or an Autopilot run's children (its approver answers them). While the card is open the child's review item is `waiting` (board row, sidebar, next-prompt children). `ompdesk_session_answer` on a choice card with no `choice` says which field to pass (`No choice given: pass \`choice\` …`, and how to type an answer of one's own through `Other (type your own)`) instead of calling the value wrong. Pinned by the question-card cases of `service.test.ts` and `host.test.ts` and the question-card test of `e2e/agent-control-across.e2e.ts` (two apps).
- **A send never starts a turn under the person's hands** (`#untilDraftSent`, after OpenRig's draft-aware delivery): while the target's composer holds the person's draft in any window or on a paired device (`ControlTab.drafting`, `SidecarPool.hasDraft`), `ompdesk_session_send` waits for the draft to be sent or cleared, up to `DRAFT_WAIT_MS` (60 s), then fails with nothing sent, saying the person is typing. A repeat of a request already delivered (`request_id` in the receipts or the target's journal) answers at once without waiting. Pinned by "waits while the person types into the target" in `service.test.ts`.
- **A queued follow-up is never invisible** (v0.45.0: children reported done or asked, then waited in the same turn while the opener's follow-up sat in stock's queue, which the model never sees, and said "d5/d6 has not arrived"). A send to a session that reported done, review, question or blocked to the caller since its current turn started (`#reportedAt`, against `ControlTab.busySince`) goes as `steer` whatever `delivery` says, and the receipt says why. A follow-up that is queued behind a busy child's turn is remembered (`#queuedFollowUp`: its dispatch); when that child reports before its transcript holds the dispatch (`journalMarks`), the report's answer says the message waits and to end the turn now (`#queuedNote`, also on a stale or repeated report). Pinned by the "after a relaunch" cases of `service.test.ts` and the busy-child test of `e2e/relaunch-child-ids.e2e.ts`.

### Sessions sharing a checkout
- The user's rule (20 Oct 2026): sessions working in the same project folder at the same time know of each other and talk instead of breaking each other's work. Measured first (stock omp, two `omp -p` sessions on the smol role, no OMPdesk): in 3 of 9 same-checkout runs one session's work landed in the other's commit (a plain `git commit` after the other's `git add`, a `git add -A`, a formatter plus `add -A`); `checkout --`/`restore`/`reset --hard`/`clean` never came up; a shared formatter rewrote the other session's files every time; stash was used by 5 of 6 sessions in two worktrees of one repository with no swap in 3 runs (the swap is real, it happened that day). Stock has no cross-process channel to reuse: `src/irc` is one process's bus (subagents), `collab` shares one session with browsers. With the guard (real omp in OMPdesk, two tabs, 3 runs each of guard alone and guard plus messaging): separate files 0 of 6 wrong commits (8 refusals, 3 `add -A` and 5 commits without paths, each redone by name); the same files, guard alone ended right 1 of 3 (the refusal said "ask the user", nobody answered, one lost change), guard plus messaging 6 of 6 in about 40 s, one conflict settled by a question and its answer; what remained was each session overwriting the shared file's uncommitted lines with `echo >`/heredocs, hence the overwrite rule below.
- Two scopes, as git keeps them: the worktree (`git rev-parse --show-toplevel`: files, index, HEAD, build output) and the repository (`--git-common-dir`: stash, branches, refs, shared by every worktree). Main's `CheckoutPeerCoordinator` (`src/main/checkout-peers.ts`, wired in `ipc.ts`) groups this computer's live omps (the tabs of its windows and `LocalHostServices.checkoutMembers()`, the tabs it runs for paired devices; a paired host's tab is that host's to coordinate) by both, on tab activity and every `CHECKOUT_PEERS_SWEEP_MS` (10 s; `OMP_GUI_TEST_CHECKOUT_PEERS_MS`), reads each same-worktree member's changed files from its bridge (`checkout_touched`) and pushes each member `checkout_peers_set` (`CheckoutPeers`, `resources/gui-bridge/modes/checkout-peers-contracts.ts`) only on a change; a session never told of company starts alone and one left alone is told once. A session hidden from agents is a peer with no id, title or files; one run for a paired device has no id (its control tools answer on the device).
- The bridge (`modes/checkout-peers.ts`, rules `checkout-peers-core.ts`, capability `checkoutPeers`) adds the `<shared-checkout>` section through `registerPromptSection` (names and ids of both groups, stage and commit by name, change a shared file with the edit tool, formatters on own files only, one `ompdesk_report` note before a commit, install, rebuild or dev-server restart, a question to have a peer commit or hold); it carries no files, so it stays the same text turn after turn and the prompt cache holds. A `tool_call` guard reads `bash` with Autopilot's own parser (`shellEffects` in `autopilot-guard-core.ts`, a collect mode of its walk: git runs and output redirects) and judges each git run by one table (`GIT_RULES`): stash (not list/show) and deleting, moving or force-setting a branch while any session works in any worktree of the repository; `commit -a`, a commit without paths (the index is shared), `checkout`/`switch` of a branch, `reset --hard` or a reset without paths, `clean -f` while one works in the same worktree; `add`, `commit --`, `checkout --`, `restore`, `reset --`, `rm`, `mv` of a path that is a glob, pathspec magic, the top level or above, or holds a file a peer changed. Writing a file a peer changed whole (a shell `>`/`>>`, the `write` tool: `writeRefusal`) is refused with the edit tool as the way (it applies only its own lines and refuses an edit whose lines moved). A git run in another repository is not judged; a session alone is never judged. Paths are compared in main's spelling: the bridge resolves its cwd, its writes and each git run's cwd to the native real path of the nearest existing folder (`canonicalPath`; macOS `/var` is `/private/var`, Windows temp dirs have 8.3 names). The refusal names the command, why, each peer (id, title, files changed lately), the files this session changed and the exact `ompdesk_report {"to": …, "kind": "question"}` to agree who goes first (or "ask the user" without the control tools). A session's own files are what its file tools (`fileToolPaths`) and its shell redirects (`shellWrites`, devices left out) wrote, recorded whether or not it has company yet.
- `ompdesk_report {to: <peer>}` works from any session (no opener needed): a question or blocker reaches a busy peer between its steps and wakes an idle one; every other kind is a note that reaches a busy peer between its steps and never wakes it. Hidden peers refuse it like every control tool.
- The work board's "Same checkout" row reads the peers back: `CheckoutPeersState` (`checkout-peers-core.ts`) keeps what `checkout_peers_set` carried, and the bridge emits a `checkout_peers` frame (`{peers: CheckoutPeers | null}`, `CHECKOUT_PEERS_EVENT`) only when it changed; `checkout_peers.get` → main `get_checkout_peers` (free in `quota-commands.ts`) hydrates it like `get_goal`, into the session store's `checkoutPeers` (a paired host's tab carries its host's frame). The row (`work-board/WorkBoardSession.tsx`) counts the worktree's peers, else the repository's, and never shows on a session alone; a hidden peer counts and reads "a hidden session". Test: `bridge-checkout-peers-frame.test.ts`.
- Tests: `bridge-checkout-peers.test.ts` (guard and section; the cross-worktree stash case first; a cwd through a symlink; shell writes counted as the session's own), `checkout-peers.test.ts` (grouping on real temp repositories), the peer case of `service.test.ts`, `e2e/shared-checkout.e2e.ts` (two tabs in one checkout: the second writes its file from the shell; the first agent's whole-file write and shell overwrite of that file and its `git add -A` are refused, it commits its own file by name, the second's edit stays unstaged and uncommitted, a note and a question reach the second; the fake plays turns through the real guard, `fixture checkout:` in `e2e/fixture/checkout-peers.ts`), opt-in `e2e/real-shared-checkout.e2e.ts` (`OMP_GUI_REAL_WORK=1`: two real sessions, guard alone vs guard plus messaging, on separate and on the same files; results appended to `/tmp/shared-checkout-measure/real-runs.jsonl`).

### Schedules and Autopilot
- `ompdesk_schedule` `create`/`list`/`cancel` (`service.ts`; `AgentControlHost.schedules(device?)` in `host.ts`: no device → this computer's `ScheduleService` via dep `schedules` ← `IpcDeps.schedules` ← `scheduleService` in `index.ts`; a paired host → `host.schedules.*` over the link, served by that host's own `ScheduleService`) goes through `command({action:"get"|"delete"})` and `create(draft)`, so the Schedules page, its log and its one-run-per-schedule rule apply on the computer that runs it. `create` (`host.schedules.create` on a host) answers the id its own save made (`ScheduleCreated`): never a diff against an earlier read, which handed one of two concurrent creates the other's schedule.
  - `device` (name or id, `"local"` = this computer) picks the computer; default the device the caller's session runs on, so a session on a paired host schedules on that host. A device whose link is down is waited for (`#reach`, see Beyond the caller's window), then refused; a create on another device than the caller's needs `folder` (the caller's folder is not a path there).
  - A create raises one `[OMPdesk]` card only while `agentControlManage` (default on) is off; names the schedule `[agent] <name>` (`AGENT_SCHEDULE_PREFIX`; main-owned provenance shown in that computer's Settings › Schedules; only such schedules can be cancelled by an agent); never sets `autoApprove` (a print-mode run cannot ask, so tools needing approval are denied); leaves the interval to the service's own minimum; refuses a relative folder. These agent rules live in the caller's `service.ts`, the one place that knows an agent asked; the host checks the request's shape (`SchedulesCommandParams`, `SchedulesCreateParams`) and its service the draft.
  - `SCHEDULE_RUNS_KEPT` 200 (`shared/schedules.ts`) bounds the service's run log, and a start while the previous run goes is recorded as skipped; neither limits how many schedules an agent creates.
  - Tests: `service.test.ts`, `host.test.ts` (local and remote source), `remote/host-services.test.ts` (`host.schedules.*`), `e2e/agent-control-across.e2e.ts` "on a paired device" (create, list and cancel on the host; the host's own `schedules.json`; the device-routed Settings read and the host's push).
- `ompdesk_autopilot` (`action` start | status | stop; `AutopilotSource` in `service.ts`, adapted by `host.ts` over `Autopilot.handleCommand` through the optional dep `autopilot`, wired in `ipc.ts`; skill reference `references/autopilot.md`): a start goes through the one `#start` path from a tab of the folder's computer that has the folder open (default the caller's own folder on the caller's own device; `device` names another, `local` = this computer). On this computer the folder must be open in a tab of the caller's window; on a paired host a session is opened there to start from when none has it and closed once the run started. `ship` commit/push/release maps to the sheet presets and is always sent (omitted: commit), so an agent's start always names a level and never gets Automatic, and the card says what it will do. `branch`/`advanced` map 1:1 onto `AutopilotStartOptions`. It raises one `[OMPdesk]` card only while `agentControlManage` (default on) is off, and always for ship release and for the default branch, `main` or `master`, whatever the switch says (a push to main is never loosened; push and release from Autopilot keep the card the ship level needs). The default branch comes from the folder's idle `get_autopilot` on the computer that holds it (`plan` in `host.ts`, local and paired alike). No cap on agent-started runs. `stop` = End, `abort` = Stop now (pauses).
  - **A paired host's folder is the host's run** (19 Oct 2026, the user's rule: every agent tool works on a device's sessions as on local ones). `host.ts` sends `get_autopilot`/`set_autopilot` of a paired host's tab through its link (`dispatch`; a start gets `MAX_RPC_COMMAND_TIMEOUT_MS`), and the plan reads the host's default branch from its idle `get_autopilot`. On the host `LocalHostServices` answers both through its own coordinator, never the omp (`attachAutopilot`, `src/main/remote/hosted-autopilot.ts`; a start counts one of the device's requests in `PeerQuota`): the coordinator's pool reads the device's tab by its resume id as the source, and the run is a tab of the host's front window (`getTargetWindow`; see Autopilot › Overview, Ownership). So worktree, guard, ShipRunner, notifications and restart resume are the host's. The answer names the run's session file; the device opens it (`spawnTab {device, sessionPath}`), the host attaches that as a view of the run's tab (one omp), and the device tab counts as the caller's opened run, so status and stop go through it to the window tab that runs it. The run is charged to the device until it ends (`chargeRun` with its root and session; `ipc.ts` feeds every reply of a pool tab whose `Autopilot.runRootOf` names a charged run to `runEvents`; `runEnded` → `endRun`), whether or not the device still views it. Pinned by `service.test.ts`, `host.test.ts`, `host-services.test.ts`, `hosted-autopilot.test.ts`, `autopilot.test.ts` and `e2e/agent-control-remote.e2e.ts` (closing the device's view leaves the run going and its next cycle still counts).

### New worktree preparation
- `src/main/local/git/worktree-seed.ts`, run by `createWorktree` after `worktree add`, so the worktree dialog, Autopilot and `ompdesk_session_open` worktrees all get it (stock omp 18.12.1 has no `worktreeinclude` and no worktree hook).
- `.worktreeinclude` at the main checkout's root lists paths or globs (`*`, `?`, `**`; `#` comments) copied from the main checkout only when `git check-ignore` reports them ignored (a tracked file never is). Refused: absolute paths, `..`, `.git`, `!`, any match whose real parent leaves the checkout. A symlink inside a copied folder is recreated only when it points inside; one written with an absolute path into the main checkout points at the worktree's own copy once the worktree has one (a tracked file, or one the seed copied; `pointLinksAtWorktree`), else keeps the main checkout's (a shared store); **on Windows a file link is copied (a file symlink there needs Developer Mode or admin, and OMPdesk never requires one) and a folder link becomes a junction** (`worktree-seed.test.ts` "copies an ignored file link on Windows"; tests that make a file symlink use `itWithFileSymlinks` from `src/main/test-symlinks.ts`, skipped where the OS refuses). Budget `SEED_MAX_BYTES` 50 MB / `SEED_MAX_FILES` 10,000; existing files never overwritten; every skip reported (`WorktreeSeedReport.skipped`).
- Then `.ompdesk/worktree-setup` (`.cmd` on Windows), only when it exists in the new worktree or the main checkout, runs in the worktree under the setup supervisor (`/bin/sh <file>`, env `OMPDESK_ROOT_PATH`/`OMPDESK_WORKTREE_PATH`, `SETUP_TIMEOUT_MS` 120 s, process tree killed at the timeout and its exit code then ignored, output in `<worktree git dir>/ompdesk-worktree-setup.log`). A failure is reported in `RpcWorktreeCreateResult.setup`, never fatal.
- The dialog toasts both (`announcePreparation`, `worktree.seed*`/`worktree.setup*`); `ompdesk_session_open` adds `describePreparation` to its notes. `worktree_create`'s budget includes it (`WORKTREE_PREPARE_BUDGET_MS`; renderer, agent-control and Autopilot wait 960 s). Pinned by `worktree-seed.test.ts` (real temp repos).

### Worktree names
- Files: `shared/project-origin.ts` (rules), `main/local/git/origin.ts` (git reads), `renderer/lib/project-origin.ts` (`useProjectNames`), `stores/project-origins.ts`, channel `project-origin:get` = `window.omp.projectOrigins.get(cwds)`. A linked worktree's folder (`~/.omp/wt/gui-<name>-<hash7>`) never shows as a project name.
- Git alone says what it is: `--git-common-dir` names the main checkout (`<main>/.git`, else the first `git worktree list` entry for a bare or relocated dir); `--git-dir` ≠ common dir marks a linked worktree; the branch gives its kind (`autopilot/…` → "오토파일럿"/Autopilot, `omp/agent/…` → "병렬 작업"/Parallel work, or the child's title where a one-line `project · title` is shown; any other branch shows as itself).
- No new store: main caches each cwd for 30 s (5 s when git cannot place it); the renderer asks once per cwd and retries an unknown one after 10 s. A lookup that fails (no answer: the computer restarting, a dropped link) is no unknown: the folder keeps what was known and the store asks again by itself every 2 s until one answers (`stores/project-origins.ts` `RETRY_FAILED_MS`; a null would hide a worktree's rows as a removed folder until the folder list changed; `project-origins.test.ts`). A folder git cannot place (removed worktree, not a repository, a paired host's path) shows its own name with the `gui-…-<hash7>` dressing stripped.
- Surfaces: in the sidebar a linked worktree's sessions are **rows of their project's own group, never a group of their own** (the user's report, 21 Oct 2026: an Autopilot run showed as its own "⑂ 오토파일럿" group with its own +): in the project's order (pins, then recency), each marked at the row's end by what it is for (`data-sidebar-worktree`: `Rocket` for `autopilot`, `GitBranch` for `agent` and a user's own branch), the kind's word (`Autopilot`/`Parallel work`, else the branch) in the row's tooltip and screen-reader text. A project whose own folder has no session gets its group from its worktrees' sessions, keyed and named by the main checkout (its `+` starts there), never by the worktree. The group header and its `+` are the project's only; phone and tablet the same. Title bar and pane header breadcrumb `acme-web › Autopilot › <title>` (`data-titlebar-worktree`, `data-pane-worktree`; an Autopilot run shows the rocket alone, its word for screen readers); work board head `acme-web · Parallel work` (`data-board-project`; a run's is `acme-web` and the rocket, the word for screen readers); window title `<name> — acme-web · Autopilot`; an untitled worktree tab chip reads from `IpcTabWorktree` (`baseCwd` + branch, no git); session and workspace pickers. **A new surface that shows a cwd's folder name goes through `useProjectNames`, never `basename`.**
- An Autopilot run's children (`autopilot/<run>-c<N>-<area>`, `autopilotRunOf`) are no rows of the project's list of their own: they sit right under the run's row, newest first, one step in and with no mark (`data-session-run-child`; `runParentOf` in `Sidebar.tsx`, from the branch git reports or, while git cannot place a new child worktree, the child tab's `worktree.baseCwd`). Parallel work sessions nest under their opener as family rows when the opener is listed (see Sidebar families), else are plain marked rows of the project.
- A session another agent opened (`ompdesk_session_open`, an Autopilot child) reads as its task until stock names it: `agentTaskTitle` (`shared/agent-control.ts`: the body's `Title:` line by `assignmentTitle`, else its first line) of the indexed first message in `sessionDisplayTitle`, and before the index lists it the tab's `task` (`IpcTabInfo.task`), never "New session". The task rides the spawn (`SpawnRequest.task` → `IpcSpawnTabPayload.task` → `SidecarPool.acquire`), so the tab's first status already carries it: set after the spawn, the first `TAB_STATUS` went out without it and a phone's row read "New session" for a frame (`e2e/mobile-autopilot-rows.e2e.ts` caught it 1 in 60). Only a tab that already exists (one a relaunch restored, named from its saved session by `#nameUntitled`) gets its task afterwards (`SidecarPool.setTabTask`). Pinned by `sidecar-pool.test.ts` ("from the first status any window hears") and `agent-control/host.test.ts`.
