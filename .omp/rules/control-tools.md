## OMPdesk control tools

### Overview and safety
- Switch: Settings › Tools & extensions › OMPdesk control tools, pref `agentControl`, default **on**. Contract `src/shared/agent-control.ts`, rules `src/main/agent-control/service.ts`, schemas `tools.ts`, app seam `host.ts`, skill `resources/omp-builtin/skills/ompdesk/SKILL.md`.
- **Full control** (the user's decision, 19 Oct 2026): Settings › Tools & extensions, first row "Give agents full control of OMPdesk" / "에이전트에게 OMPdesk 모든 권한", pref `agentControlFull` (`AGENT_CONTROL_FULL_PREF`), default **on** for every install (`agentControlFullEnabled`: only a stored `false` is off). While on, **no control tool or app action raises an `[OMPdesk]` card**: the `always` set (deletes, MCP/plugin install, sign-in starts, proxy, mobile web on, pairing, update apply, quit), a foreign session delete, Autopilot release or main targets, every power pref; it implies `agentControlApprove` and `agentControlManage` (`host.ts` resolves both as `full || stored`; the Settings rows show them checked and disabled as covered), and the catalog action `agent_power.set` (`fullOnly`; `FULL_CONTROL_PREFS`/`FULL_CONTROL_SETTINGS` in `app-guard.ts`, the terminal-omp wiring through ai-memory's own channel; memory and learning have no switch since 29 Oct 2026) lets an agent change the agent-power switches, this one included. Every action is still journaled and toasted with undo where one exists. Kept whatever it says: an agent never answers an `[OMPdesk]` card (and with the switch on none is raised), secrets/tokens/passwords are never readable, git safety (no force push, Autopilot's guard bans destructive git), and OS security prompts (UAC, TCC). Its tooltip names the risk: prompt-injected content can then make an agent delete data or install code unasked. **Every card rule below applies only while full control is off.** Pinned by `shared/agent-control.test.ts`, `app-control.test.ts` (each `always` action runs card-free when on, `agent_power.set` refused when off), `service.test.ts`, `host.test.ts`, `AgentControlRow.test.tsx`, and the on/off cases of `e2e/agent-app-control.e2e.ts`, `e2e/agent-control.e2e.ts`, `e2e/agent-review.e2e.ts`.
- **Every power on by default, no setup** (the user's decision, 29 Oct 2026: "By default agents must have every power; it must not need separate setup."). The switches `agent_power.set` exposes all resolve on while unset: `agentControl`, `agentControlFull`, `agentControlManage`, `agentControlApprove` (it used to default off), `pstack`, `ecc`, stock `computer.enabled` (OMPdesk's held default on, `.omp/rules/models-accounts.md` Held stock defaults) and stock `tools.approvalMode` (stock's own default is `yolo`, so no approval card by default; no held default is needed and Autopilot's own `yolo` override would clear one). Only a stored `false` (or another mode) is off, so a person who turns one off keeps it off.
  - **One-time migration for existing installs** (`src/main/agent-power-migration.ts`, run from `prefsStore()` in `index.ts` right after `migrateRetiredPrefs`, before any window or omp starts): pref `agentPowersMigrated` holds the version that ran (`AGENT_POWERS_MIGRATION_VERSION`, 1). The first launch drops every stored `false` of those prefs and removes `computer.enabled` unless `true` and `tools.approvalMode` unless `yolo` from the agent dir's config.yml (`parseDocument`, comments and other keys kept, atomic rename, file mode kept; a config.yml that is unreadable or not YAML is left alone and reported in `gui-runtime.jsonl` as `agent-powers-migrated`, the prefs part still runs). The version is stored after that, so no later launch touches a switch: it stays the person's opt-out. A project's own `.omp` config and the user's per-tool `tools.approval` rules are never edited. A fresh profile stores only the version. Bump the version only for another all-on decision. Pinned by `agent-power-migration.test.ts` (fresh profile, old explicit off turned on once, a later off kept, config.yml cases).
  - **No first-use grant card exists** (checked: no onboarding step, intro card or consent dialog grants these powers; first run is provider setup only). Cards that confirm a consequential action per call stay when full control is off (the `always` set, a foreign delete, release or main targets); `credentials.read` and `cards.answer` stay `never`.
  - **macOS Accessibility and Screen Recording** cannot be granted by an app. `askMacPermissionsOnce` (`src/main/mac-permissions.ts`, called from `index.ts` after the first tab is up; packaged, non-headless macOS only) calls `systemPreferences.isTrustedAccessibilityClient(true)` and, while Screen Recording is `not-determined`, one `desktopCapturer.getSources` for the system prompt, once ever: pref `macPermissionsAsked` is stored before the prompts show, so a decline is never repeated. The person still flips the switch in System Settings; without it the `computer` prelude fails as stock says. Pinned by `mac-permissions.test.ts`.
- Host tools (like `gui_terminal_read`) are registered with stock `set_host_tools` on every ready local sidecar (`SidecarManager.syncHostTools`, re-sent when the switch changes) and answered in `ipc.ts` (`hostToolExecutor` → `AgentControlRuntime.run`). The skill's root `resources/omp-builtin` is a `-e` directory only while the switch is on, so skill and tools come and go with the pref.

- **Subagents have no control tools** (stock registers host tools on the RPC session only; `host_tool_call` carries no caller id). `e2e/real-agent-control.e2e.ts` checks it: a subagent answers `NO_TOOL` and no tab opens. Since the control socket (below) a subagent, like any process on this computer, can run the `ompdesk` CLI through bash: it then acts as an outside caller, under the same rules and cards.
- **No count or rate caps** (the user's rule, 19 Oct 2026; none exist in `src/main/agent-control`): any number of sessions opened, messages sent, schedules and Autopilot runs. Only a self-send is refused. Provenance ("opened by you") is main-owned state, never read from text or tool args; it survives a relaunch (`#openedBy` adds every tab whose `host.parentOf` is the caller: the pool's `openedBy`, else the tab holding `openedBySession`).
- Session tools touch no accounts, settings or permissions. **Deleting a saved session the caller did not open** (`ompdesk_session_stop delete:true`) always raises one confirmation card (stock extension-UI `confirm` via the calling tab's omp, bridge `agent_control.confirm`, title prefix `[OMPdesk]`, so it survives a reload and reaches a paired device), whatever "Let agents manage other sessions" says: a delete cannot be undone. Stopping or closing a session it did not open raises the same card only while that switch (`agentControlManage`, **default on**: `agentControlManageEnabled` in `shared/agent-control.ts` treats an unset pref as on and only a stored `false` as off) is off. Sessions it opened itself need none, delete included.
- Closing a resting session's tab (not busy, no open ask, not in the person's view, no draft or prompt of theirs since: `ControlTab.looked`/`userTouched`) raises no card whoever opened it; a session in view or typed into is never closed (re-checked right before the close). Each close is journaled as one quiet `ompdesk.mail` note in both sessions, **only once the tab is confirmed gone** (`#journalClose` runs after `#closeTab`/`#deleteWhenIdle` returned): a close the window kept or main held back sends no note, so the caller never reads "Closed" beside a failed close. The closed session's own line is best effort: its omp has exited by then, so it lands only where something still answers for that tab (it used to be sent before the close, which told a session that stayed open it had been closed).
- `_answer` answers asks (select, confirm, input, ask); the answered session journals `ompdesk.agent-answer` and toasts "에이전트가 답함 (title)" (bridge `agent_control.note`). A **tool approval** ("Allow tool: …") is approved only when "Let agents approve for other sessions" (`agentControlApprove`, **default on** since the user's decision of 29 Oct 2026, see Full control; `agentControlApproveEnabled`: only a stored `false` is off) is on or full control covers it, else "사용자 승인이 필요해요" (deny always works). Stock's "Approve <tool> for this session" option needs the same leave. A card titled `[OMPdesk] …` is never answerable.
- **Stock's tool approval shape** is one rule, `src/shared/tool-approval.ts` (`approvalChoices`, `isApprovalSelect`; the renderer's `isApprovalRequest` narrows it; `APPROVAL_MODES` lists stock's `tools.approvalMode` values for the composer and agent catalog): an RPC host has no `approve` UI, so stock `requestApproval` sends a `select` titled "Allow tool: <name>" whose options are stock's `approvalChoiceLabels`: under "Ask and remember" (`always-ask-cached`, omp ≥ 18.12.3) the grants first ("Approve Directory: <folder>", "Approve File" or "Approve" for a target that is no file: remembered for this session), then the same with "Always " in front (every session), then this call only ("Approve", or "Approve Once" beside grants), "Approve <subject> for this session" when the approval mode raised it, and "Deny" last. `ApprovalDialog` shows every choice in stock's order with words that name what is remembered and for how long (`approval.grant.*`); an agent's `approve: true` and Autopilot's approver answer stock's this-call option only (`ApprovalChoices.once`), so every later call still meets its guard, and every approving answer needs the approve leave. Before this a "Ask and remember" prompt read as a plain select. Pinned to the installed omp by `src/main/tool-approval-stock.test.ts` (a command, a file, a folder and a web address, with and without a session subject), the card by `ApprovalDialog.test.tsx`.

Pinned by `service.test.ts` (plan cases), `sidecar-pool.test.ts`, `PlanApprovalDialog.test.tsx` and the plan tests of `e2e/agent-control.e2e.ts` (the fake omp mirrors `settlePending`).

### Control socket and the `ompdesk` CLI
- **The user's decision (30 Oct 2026)**: anything running on this computer (a terminal omp, a shell script, another agent CLI such as Claude Code or Codex, a subagent through bash) drives OMPdesk the way OMPdesk's own agents do with the `ompdesk_*` tools. Inspired by Herdr's external control surface (https://herdr.dev, github.com/herdrdev/herdr, Apache-2.0): JSON lines on a per-user socket, server-owned waits, `agent_blocked`, `events_lost`. No Herdr code is copied, so `THIRD_PARTY_NOTICES.txt` is unchanged; copying any would need its Apache-2.0 attribution there (`bun run gen:licenses`).
- Files: wire contract `resources/cli/protocol.ts` (shared by main and the CLI, dependency-free), CLI `resources/cli/ompdesk.ts` (shipped as `extraResources` `cli`, run by bun), main `src/main/control-socket/` (`endpoint.ts` paths, folder and token; `server.ts` transport and auth; `router.ts` methods and waits; `events.ts` event ring; `backend.ts` the seam to `AgentControlRuntime`; `index.ts` `startControlSocket`, called from `ipc.ts`; `cli-install.ts` the launchers; `env.ts`).
- **One service**: a `tool` request is `AgentControlRuntime.runOutside(caller, tool, args)` → `AgentControl.run`, the same rules, tiers and cards as a host tool call; `credentials.read` and `cards.answer` stay `never`. Pinned by "a caller outside OMPdesk" in `host.test.ts` (the same request through the socket's backend and through the host tool answers the same; never tier; the card).
- **The outside caller** (`OutsideCaller`, `host.ts`): id `outside:<name>#<connection>`, one per socket connection (the name comes from hello `caller`, `OMPDESK_CALLER`, `--caller`, `[a-z0-9_-]{1,32}`, default `cli`, and is the process's own claim, never an identity: another process that claims the same name owns none of the first's sessions or reports); title `outside process "<name>" (self-declared)`; cwd the CLI's folder. It has no tab: `AgentControlHost.outsideCaller` gives the service a stand-in `ControlTab` (never listed), it acts through the front desktop window (`outsideWindow` = `windowManager.getTargetWindow()`; none open refuses), and the sessions it opens are its own (`#parents`, so stop/close need no card and their `ompdesk_report`s reach it as `report` events) but get no pool opener (they sit in the sidebar like the person's), no review list, no auto-close and no provenance after a relaunch (ids starting `outside:` are excluded wherever a tab opener is expected). A closed connection releases its caller (`releaseOutside`); its sessions stay open. Its cards are native `dialog.showMessageBox` over that window (`confirmOutside`, `[OMPdesk]` title, detail "Outside process: <name> (self-declared)" / "외부 프로세스: <name> (자체 표기)", `CARD_TIMEOUT_MS`, no answer = no), one at a time per caller (`#outsideCards`: the next waits until the shown one is answered). Whatever goes through the caller's own omp (stock settings, models, usage, MCP app actions, the app action journal note) answers that an outside caller has none (`#hostCommand`).
- **Endpoint** (`endpoint.ts`): `<userData>/control/` (mode 0700, a real folder owned by this uid, else refused) holds `token` (64 hex, 0600) and `endpoint.json` (`{version, socket, pid}`, 0600, removed on quit only while it names this socket). The token is replaced, not only re-moded, whenever someone else could have read it: the folder or the file had group or other bits, or the file is another user's (`prepareControlDir` reports a repair, `readOrCreateToken({exposed})`). macOS/Linux socket `<dir>/control.sock`, made under `umask 0177` and chmodded 0600; past `sun_path` (103 bytes) only the socket moves to `<tmpdir>/ompdesk-<uid>-<hash>/` (same checks). A socket file already at the path is replaced only when nothing answers on it (`ECONNREFUSED`); a live listener or a non-socket fails the start (`SocketInUse`). Close removes only the socket file this server made (dev/inode at listen; a newer one at the path is moved aside while libuv unlinks the path, then put back). Nothing ever listens on TCP.
- **Windows pipe (decided 30 Oct 2026, S2 of the review)**: `\\.\pipe\ompdesk-<32 random hex>`, new each launch, published only in `endpoint.json` under the user's `%APPDATA%`, so another user can neither guess nor squat it. Node's `net` (libuv) cannot set a pipe's DACL beyond `readableAll`/`writableAll` (both off here) nor `PIPE_REJECT_REMOTE_CLIENTS`; a native helper for that is not worth a native module. The default pipe DACL gives other accounts (and a network logon) read access at most, so none of them can write the hello, and nothing is answered before the token. The control folder's ACL is not checked on Windows (it inherits the user profile's: the user, SYSTEM, Administrators); the CLI cannot identify the pipe's server process from Node either. Revisit if OMPdesk ever ships a native module.
- **Auth and limits** (`server.ts`): the first line must be `hello {token, protocol}` within 10 s and at most 64 KiB; a wrong or missing token, any other first request or another protocol is answered `unauthorized`/`protocol_mismatch` and the connection ends. At most 64 connections (the next is answered `unavailable` and closed) and 16 running requests per connection; past that, or while the connection's answers or events back up (`write` returned false), the server stops reading it until a request answers or the socket drains. The CLI sends the token only to a socket that is this user's alone: on POSIX the socket, its folder and the token file must belong to its uid with no group or other bits, else it refuses with exit 3 before any byte (`ownerOnly`, `resources/cli/ompdesk.ts`).
- **Env, per spawn** (`env.ts`): main never puts the socket's address in `process.env`. `controlEnvFor(foreign)` gives this computer's own tabs (`SidecarOptions.controlEnv`, read per spawn) and their terminals (`terminalRequest`'s `env`, merged by the terminals worker) `OMPDESK_SOCKET` and `OMPDESK_CONTROL_DIR`; a tab run for a paired device (`origin`) or owned by the phone page (the pool factory's `web` flag) and its terminals get only `OMPDESK_CONTROL_OFF=1`, which the CLI refuses on (exit 3), so neither acts as an outside caller with this computer's front window outside its device's grants and `PeerQuota` (threat models in `multi-viewer-web.md` and `remote-devices.md`). `withoutControlEnv` strips what a login shell or a parent OMPdesk passed on, for omp spawns and the stock helper workers.
- **Waits** (`router.ts`, Herdr's `prompt_agent` mechanics from `src/api/wait.rs` at bc8c28988, re-implemented): `state` is `SessionState` from `sessionState` (`backend.ts`): `blocked` = the tools' `waits` (an ask or approval that is no sign-in, or a plan up for review: the same rule `lib/attention.ts` `pendingAsks` applies in the renderer) over `working` (busy or resuming), `starting`, `stopped`, `idle`. Each request subscribes to the pool's activity before it resolves the name and numbers every lifecycle step of the tab (`TabWatch`: working = `busy`, blocked = `ask`, ended = `idle`, released). `wait --until idle|blocked|done|any`; no `until` = settled (idle, blocked or stopped). `done` and `any` are edges: a turn end (any step for `any`) after the mark satisfies them, replayed. `idle`, `blocked` and settled are states: a step only makes the wait look at the session now, and only its current state matches (Herdr's final wait runs with `accept_transient_status: false` and re-probes), so a turn that ended before another started does not end them. `send` refuses a blocked session with `agent_blocked` unless `force`. With `wait` it takes the step sequence just before the send (Herdr's `last_event_sequence`); the activity gate passes when the session was working already or a step after that mark (or the state now: a plan proposal raises no step) shows working, blocked or a turn end, within `START_WAIT_MS` (5 s) or the remaining total timeout if nearer, else `agent_prompt_stalled`; the final wait then counts from that same pre-send mark, so a turn end the gate consumed still ends `done`. When the session was already working as the message went, the final wait counts from the receipt instead (a turn end heard while the send was in flight is the older turn's, review W1), and an idle seen right after such an end is held for `START_WAIT_MS` unless a new step comes (the gap before a queued follow-up's own turn); a follow-up folded into the turn that ended settles after that hold. One total timeout covers the send, the gate and the wait (`timeout`). Known limit (as Herdr's): a message steered into a turn still running at the receipt settles at that turn's end.
- **Events** (`events.ts`): `subscribe` starts live; `session_state`, `ask`, `turn_finished`, `session_closed`, and `report` only to the caller it is addressed to; never a hidden session. A ring of 1 024 events, one cursor per subscriber; one that falls behind the oldest retained event gets one `events_lost` frame (how many, and the resync hint: subscribe again and resync with `ompdesk sessions`/`state`) and its subscription ends, never a silent skip.
- **CLI and PATH** (`cli-install.ts`, called from `index.ts`): every launch writes `<userData>/bin/ompdesk` (and `ompdesk.cmd` on Windows) running `bun <resources>/cli/ompdesk.ts` and appends that folder to `process.env.PATH`, the way setup puts its managed tools on PATH for everything OMPdesk spawns; a packaged, non-headless app also writes it into Bun's global bin (where `omp` is, so a terminal outside OMPdesk finds it), only over a missing file or one with its marker line. The Windows launchers run `<Bun>\bin\bun.exe` by its absolute path (cmd.exe searches the current folder before PATH). Exit codes 0 ok, 1 failed, 2 usage, 3 OMPdesk not running or refused; `--json` prints the raw result.
- Tests: `control-socket/server.test.ts` (auth refusals, modes, owner check, stale socket, env; the named pipe on Windows in `test:platform`), `router.test.ts` (fast finish, `agent_blocked`, `force`, stalled, until, gone, timeout), `events.test.ts` (`events_lost`, report routing, hidden), `cli.test.ts`, `cli-install.test.ts`, "a caller outside OMPdesk" in `host.test.ts`, and `e2e/control-cli.e2e.ts` (the launcher from `/bin/sh` against the built app and the fake omp: open, send `--wait --until idle`, state, read, exit 3 after quit).

### App control (`ompdesk_app_list`, `ompdesk_app`)
- Changes the app itself in main; arguments are validated against the action's schema. `app-catalog.ts` actions, `app-settings.ts` one `settings.<row>` action per Settings row, `app-control.ts` the one dispatch point, `app-guard.ts` and `app-channels.ts` the agent's own default-deny risk tables. `AGENT_CHANNELS` is typed over every `IpcChannel`: a new channel does not compile until it is `never` with a reason or lists the actions that call it. `IPC_POLICY` is the web device's table, not the agent's.
- `read`/`change` are free; a change is journaled in the caller's session (`agent_control_note`) and shown as a quiet toast with one-step undo when a previous value exists (`AGENT_CONTROL_APP` → `lib/agent-app.ts`, applied live).
- `sensitive` raises no card while full control is on. With it off, it raises the same `[OMPdesk]` card only while `agentControlManage` (default on) is off, **except the actions whose `manage` rule is `always`** (`ManageRule` in `app-settings.ts`, a field of `AppAction` and of a Settings row): every `sensitive` action must decide `{ lifts: reason }` or `{ always: reason, when? }`; `app-catalog.test.ts` fails on one that does not, and `app-control.test.ts` pins the `always` list (`agent_power.set`, `fullOnly`, is pinned on its own). `always` asks whatever the manage switch says because the action erases data (`sessions.delete`, `memory.purge`, `memory.delete_page`, `memory.sweep`), runs code (`extensions.install_plugin`, `extensions.install_mcp`, `extensions.mcp_use`), touches credentials or traffic (`accounts.github_sign_in`, `accounts.provider_sign_in`, `extensions.mcp_sign_in`, `settings.proxy`), exposes or connects the computer (`mobile_web.set_enabled` when turning it on, `remote.connect`, `remote.unblock`, `remote.set_allowed_users`) or ends running work (`updates.apply`, `app.quit`). The rest lift (`updates.check`, the four auto-update switches, `builtinRea`, `rotation`, `remote.block`); an `undo` of a setting asks by its row's rule. `remote.list_tailnet` (read) lists the tailnet's computers for `remote.connect`. MCP servers: see Panels, sidebar and work views › MCP servers.
- **Which computer.** A caller tab that runs on a paired host (`AppPorts.device(tabId)` = its sidecar's `device`; `ActionContext.device`) gets what the Settings page gives that tab, so no action is local-only where a host route exists. Already the host's through the tab's own RPC: every stock setting, models, usage, plugins, MCP. Routed by device: `HOST_PREFS` (`app-settings.ts`) sends `settings.rotation` and `settings.builtinRea` (read, write and undo) through `ACCOUNT_ROTATION_*`/`BUILTIN_REA_*` with the device (`machine-services.ts` `RemoteMachine`), never into this computer's prefs; `sessions.saved|search|rename|delete` put the device in the `sessions:*` payload; `sidebar.projects|add_project|remove_project` pass it as `SIDEBAR_PROJECTS_COMMAND`'s second argument (the host's own list over `host.projects.command`); `updates.status|check|apply` take `host: true` for `HOST_DESKTOP_*` (the host's OMPdesk; a session on this computer refuses it, and the host refuses an install while any work runs). - `ompdesk_compare` reads each child's branch (`git merge-base`, `diff --numstat`, commits ahead, uncommitted and untracked counts), a merge prediction and its final answer; it **runs no tests** (a child reports them). The prediction (`predictMerge`, `branches.ts`) is `git merge-tree --write-tree --name-only` of the parent's HEAD and the branch tip with a quarantined object store (`GIT_OBJECT_DIRECTORY` a scratch dir, the repo's store as alternate, deleted after; idea from Orca's `conflict-summary.ts`, MIT, re-implemented), so no checkout, index, ref or object of the repo changes; the line reads `merge: would conflict in <files>`, `no conflict with <base>` or `not predicted (<reason>)` (git < 2.38), and a predicted conflict marks the child's review item `conflict`.
- **Where a branch lands** (`branchFacts`/`landingFacts`, one rule): the parent checkout's HEAD and the upstream its branch tracks (`<branch>@{upstream}`, else `refs/remotes/origin/HEAD`; refs as last fetched, never fetches, never touches the parent checkout). Agents push their own work (`git push origin HEAD:main`) while the parent's local main stays behind, so a tip in either has **landed** (`BranchFacts.merged`) and its diff is measured from that tip (only uncommitted work is left). An unlanded branch is measured from its merge-base with the upstream when the upstream holds the parent's HEAD, else with the parent's HEAD, so a stale local main never lends a child the upstream's newer commits (it once showed every pushed child as "200 files · +40520 −425").
- `ompdesk_merge` merges into the parent checkout's current branch with `git merge --no-ff` (never a push, no remote command in the module). It refuses a detached parent, uncommitted work in child or parent, and a branch with nothing to merge (`mergeProblem`); asks one `[OMPdesk]` card only while `agentControlManage` (default on) is off; refuses a merge `predictMerge` says would conflict before running `git merge` (`MergeOutcome.predicted`, the files named, the parent untouched), and still aborts a conflict it did not predict (`git merge --abort`) naming the files.

A symlink inside a copied folder is recreated only when it points inside; one written with an absolute path into the main checkout points at the worktree's own copy once the worktree has one (a tracked file, or one the seed copied; `pointLinksAtWorktree`), else keeps the main checkout's (a shared store); **on Windows a file link is copied (a file symlink there needs Developer Mode or admin, and OMPdesk never requires one) and a folder link becomes a junction** (`worktree-seed.test.ts` "copies an ignored file link on Windows"; tests that make a file symlink use `itWithFileSymlinks` from `src/main/test-symlinks.ts`, skipped where the OS refuses). Budget `SEED_MAX_BYTES` 50 MB / `SEED_MAX_FILES` 10,000; existing files never overwritten; every skip reported (`WorktreeSeedReport.skipped`).
- Then `.ompdesk/worktree-setup` (`.cmd` on Windows), only when it exists in the new worktree or the main checkout, runs in the worktree under the setup supervisor (`/bin/sh <file>`, env `OMPDESK_ROOT_PATH`/`OMPDESK_WORKTREE_PATH`, `SETUP_TIMEOUT_MS` 120 s, process tree killed at the timeout and its exit code then ignored, output in `<worktree git dir>/ompdesk-worktree-setup.log`). A failure is reported in `RpcWorktreeCreateResult.setup`, never fatal.
- The dialog toasts both (`announcePreparation`, `worktree.seed*`/`worktree.setup*`); `ompdesk_session_open` adds `describePreparation` to its notes. `worktree_create`'s budget includes it (`WORKTREE_PREPARE_BUDGET_MS`; renderer, agent-control and Autopilot wait 960 s). Pinned by `worktree-seed.test.ts` (real temp repos).

### Worktree names
- Files: `shared/project-origin.ts` (rules), `main/local/git/origin.ts` (git reads), `renderer/lib/project-origin.ts` (`useProjectNames`), `stores/project-origins.ts`, channel `project-origin:get` = `window.omp.projectOrigins.get(cwds)`. A linked worktree's folder (`~/.omp/wt/gui-<name>-<hash7>`) never shows as a project name.
- Git alone says what it is: `--git-common-dir` names the main checkout (`<main>/.git`, else the first `git worktree list` entry for a bare or relocated dir); `--git-dir` ≠ common dir marks a linked worktree; the branch gives its kind (`autopilot/…` → "오토파일럿"/Autopilot, `omp/agent/…` → "병렬 작업"/Parallel work, or the child's title where a one-line `project · title` is shown; any other branch shows as itself).
- No new store: main caches each cwd for 30 s (5 s when git cannot place it); the renderer asks once per cwd and retries an unknown one after 10 s. A lookup that fails (no answer: the computer restarting, a dropped link) is no unknown: the folder keeps what was known and the store asks again by itself every 2 s until one answers (`stores/project-origins.ts` `RETRY_FAILED_MS`; a null would hide a worktree's rows as a removed folder until the folder list changed; `project-origins.test.ts`). A folder git cannot place (removed worktree, not a repository, a paired host's path) shows its own name with the `gui-…-<hash7>` dressing stripped.
- Surfaces: in the sidebar a linked worktree's sessions are **rows of their project's own group, never a group of their own** (the user's report, 21 Oct 2026: an Autopilot run showed as its own "⑂ 오토파일럿" group with its own +): in the project's order (pins, then recency), each marked at the row's end by what it is for (`data-sidebar-worktree`: `Rocket` for `autopilot`, `GitBranch` for `agent` and a user's own branch), the kind's word (`Autopilot`/`Parallel work`, else the branch) in the row's tooltip and screen-reader text. A project whose own folder has no session gets its group from its worktrees' sessions, keyed and named by the main checkout (its `+` starts there), never by the worktree. The group header and its `+` are the project's only; phone and tablet the same. Title bar and pane header breadcrumb `acme-web › Autopilot › <title>` (`data-titlebar-worktree`, `data-pane-worktree`; an Autopilot run shows the rocket alone, its word for screen readers); work board head `acme-web · Parallel work` (`data-board-project`; a run's is `acme-web` and the rocket, the word for screen readers); window title `<name> — acme-web · Autopilot`; an untitled worktree tab chip reads from `IpcTabWorktree` (`baseCwd` + branch, no git); session and workspace pickers. **A new surface that shows a cwd's folder name goes through `useProjectNames`, never `basename`.**
- An Autopilot run's children (`autopilot/<run>-c<N>-<area>`, `autopilotRunOf`) are no rows of the project's list of their own: they sit right under the run's row, newest first, one step in and with no mark (`data-session-run-child`; `runParentOf` in `Sidebar.tsx`, from the branch git reports or, while git cannot place a new child worktree, the child tab's `worktree.baseCwd`). Parallel work sessions nest under their opener as family rows when the opener is listed (see Sidebar families), else are plain marked rows of the project.
- A session another agent opened (`ompdesk_session_open`, an Autopilot child) reads as its task until stock names it: `agentTaskTitle` (`shared/agent-control.ts`: the body's `Title:` line by `assignmentTitle`, else its first line) of the indexed first message in `sessionDisplayTitle`, and before the index lists it the tab's `task` (`IpcTabInfo.task`), never "New session". The task rides the spawn (`SpawnRequest.task` → `IpcSpawnTabPayload.task` → `SidecarPool.acquire`), so the tab's first status already carries it: set after the spawn, the first `TAB_STATUS` went out without it and a phone's row read "New session" for a frame (`e2e/mobile-autopilot-rows.e2e.ts` caught it 1 in 60). Only a tab that already exists (one a relaunch restored, named from its saved session by `#nameUntitled`) gets its task afterwards (`SidecarPool.setTabTask`). Pinned by `sidecar-pool.test.ts` ("from the first status any window hears") and `agent-control/host.test.ts`.
