## Waste guards (`resources/gui-bridge/waste-guards.ts`, rules and text `waste-guards-core.ts`, capability `wasteGuards`)

- **Why** (the bot's measurement of 4 Nov 2026 over 667 sessions on three computers, `scripts/session-pace.ts --days 14`): SeuPut's 14 days were 86,003 min of wall = 40% idle, 38% tools, 22% model; 5,533 of 124,593 tool calls failed (4.4%) and 2,364 were polls. The largest session ran `bash` 2,373 times: `sleep` 127, `gh run` 100, `read proc://` 11 (another: 87 polls, 21 `proc://` reads). Five `bash` service starts gave `ready: {log: /Running \d+ tests/, timeout: 600 to 900}` to a command that sent its stdout to a file (`… > file 2>&1`): each waited the whole timeout, 55 min in one session, and returned `NOT ready — readiness timed out after 600s; process state: starting` as a success. The agent-side rule that says it in prose is the light-brief item of the bot (`.omp/rules/control-tools.md`); the guards make the two cases that repeat impossible or visible. Both use only the public hooks (`tool_call`, `tool_result`), so `wasteGuards: {}` in `capabilities.ts` needs no internal. Stock omp is not forked and nothing is installed.
- **Guard 1: a `ready.log` that can never match is refused** (`tool_call`, `{block: true, reason}`, before the command runs). It applies to a `bash` call with a non-blank `ready.log` **and a non-blank `name`** (stock `bash.ts` `normalizeReady`/`execute`: `ready` without a service `name` is ignored with a notice, the call does not wait, so refusing it would be wrong) whose command's **last command, in its last pipeline stage,** sends stdout to a file. `readyLogCannotMatch` reads the command with a small scanner (`scan`: quotes, escapes, `$(…)`, backticks, comments, heredocs, `;` `&&` `||` `&` newline, pipes), not a shell: anything it cannot place (a subshell's contents, an expansion) reads as "no redirect" and passes.
  - Refused: `> f`, `>> f`, `&> f`, `&>> f`, `1> f`, `>| f`, `>& f`, `>f 2>&1`, `2>&1 > f`, `2> e > o`, a target of `/dev/null` or a quoted `"$VAR"`, `>&-`, the last command of `a && b > f` or `a; b > f`, the last stage of `a | b > f`, a trailing `&`, a redirect after a line continuation, `cat <<EOF > f` (the redirect on the heredoc's own line).
  - Passes: no redirect, `| tee f`, `2> f` alone, `> f 1>&2`, `> /dev/stdout`, `/dev/stderr`, `/dev/tty`, `/dev/fd/N`, `> >(tee f)`, a redirect in an earlier command of a chain or an earlier pipeline stage, a `>` in quotes or a comment, a redirect only in a heredoc body (bodies are cut before judging), a redirect only inside `( … )`, `< f`, `3> f`.
  - Known cost: `bun test > f` (stdout only, stderr still shown) is refused too, as the owner's brief asked; the reason names the two ways out. The reason: `OMPdesk: ready.log can never match — the command sends its stdout to a file, so the log line is never seen and the call would wait the whole ready.timeout (measured 55 min lost in one session). Run it with async: true and `wait`, or keep stdout visible (`| tee file`).` (`READY_LOG_REASON`).
- **Guard 2: one hint at a poll** (`tool_result`, `{content}`: the hint is a second text part appended to the call's own content; never a block, `details` and `isError` stay). `pollKinds` names the kind of a call: `sleep` (`sleep N` followed by another command, or `while … sleep`), `gh-run` (`gh run list|view|watch`), `pgrep`, `tail-f` (`tail … -f`/`-F`/`--follow`), and `proc` (`read` of a `proc://` path, which also covers the `read proc://` right after bash's automatic 60 s move to the background). Heredoc bodies are cut first. `gh run watch` with `async: true` is the recommended way, not a poll. `wait` is never touched. `createPollHints()` keeps the kinds already told in one module-level set: **once per kind, per omp process** (one omp is one session; the main agent and every subagent rebinding share it), quiet from the second call of the kind on; a call that carries several kinds marks them all told. Text (`POLL_HINT`): `OMPdesk: this polled. A backgrounded job (async: true, or a bash that outlives 60 s) delivers its result by itself; `wait` blocks until then; for a CI run `gh run watch` under async, or ompdesk_schedule {on: github}. Each look costs a model call.`
  - **Can the hook change the result? Yes, so the hint is appended to it** (the owner's brief: append to the result when the hook may; `sendCustomMessage` only otherwise). Stock's `ToolResultEventResult` (`extensibility/shared-events.ts`, merged by `extensions/runner.ts` `emitToolResult`) takes a replacement `content` array (text and images), `details` and `isError`, and the changed result is what the model, the transcript and the work board get. The hook returns `{content: [...event.content, {type: "text", text: "\n" + hint}]}` only for a fresh kind; nothing else of the result changes. `additionalContext` (a line for the next request that stays out of the result, as `todo-compact.ts` uses it) was the first version and was withdrawn before release: the result the agent reads then carried no hint.
- **Measured** (5 Nov 2026, omp 18.16.0, scripted provider, no spend, captures in `~/motion-shots/waste-guards/`): a service start `sleep 30 > x.log 2>&1` with `ready: {log, timeout: 8}`. Before (bridge at HEAD): the call returned after 8.8 s with `NOT ready — readiness timed out after 8s; process state: starting.`, no hint anywhere. After: refused in the same turn's first 0.4 s with the reason above, `x.log` never created; of two `sleep 0.1; echo POLLRESULT` calls the first result ends with `OMPdesk: this polled.` and the second is `POLLRESULT` alone.
- **Pinned by** `src/main/bridge-waste-guards.test.ts` (rule: "ready.log that can never match" 20 refused and 15 passing fixtures, "looks only at a call stock would hold for ready.log", "polling kinds", "poll hints": once per kind, several kinds in one call, per instance) and `src/main/bridge-waste-guards-stock.test.ts` (installed omp: "refuses a ready.log that cannot match at once, without running the command" fails by timeout without the guard; "hints at the first poll of a kind only": the first call's result ends with the hint, the second call's result is the command's output alone, and the request after the second still holds one hint), plus the `never poll` clause in `bridge-agent-bot.test.ts`.
- **Guard 3: one hint at a refused edit** (same `tool_result` hook and once-per-process set as the poll hint, kind `edit-misuse`). Measured over the 18 local journals of the last 14 days (the bot, 5 Nov 2026): all 36 `edit` errors were agent misuse the tool caught, none a tool defect: 27 anchored to lines the latest `read` never displayed (edited after a declarations-only or elided read, or straight from a grep hit), 8 used a hash the session never received (`#0000`, "not from this session"), 1 restated neighbour lines; each a wasted model round trip plus a re-read. `editMisuse(toolName, outcome)` is true for an `edit` result with `isError` whose text matches `anchors to lines` or `not from this session` (stock's two refusals; the stale-tag refusal "file changed between read and edit" and the restated-neighbour case already name their own fix and get no hint). Text (`EDIT_HINT`): `OMPdesk: this edit was refused. Edit only lines shown by the latest read of that file; after a grep hit or an elided or declarations-only read, read the exact range first. Copy the `[FILE#TAG]` from that read or the last edit's response, never invent one; after each edit use the tags and line numbers its response returns.` Appended to the failed result's content; stock keeps the call an error (`runner.ts` `emitToolResult` returns `isError` as it was, `wrapper.ts` returns the modified result with `isError: true` instead of rethrowing). The hook fits because the refusal text is the only signal needed and the same `content` path serves failed calls.
- **Guard 3 pinned by** `bridge-waste-guards.test.ts` ("hint on a refused edit": once per process, the two refusal texts, not a success, another refusal or another tool) and the stock test "hints once at an edit anchored to lines the session never read" (installed omp, scripted provider: an `edit` with tag `#0000` on a file never read is refused by stock and its result ends with the hint, still an error with `errorKind: unknown_tag`; the second identical edit gets none). Captured in `~/motion-shots/waste-guards/edit-hint-results.txt`.

## Edits

The rule the third guard repeats, for any agent working in this repository:
- Edit only lines shown in the latest `read` of that file. After a grep hit, or an elided or declarations-only read, read the exact range first.
- Copy the `[FILE#TAG]` header from that read or from the last edit's response; never invent one (`#0000`) or reuse one from another session.
- After each edit use the tags and line numbers the edit's response returns, not the ones before it.
- Do not re-audit an edit: the edit response already shows the result. Measured over the same 18 journals: 37 `git status`/`git diff` calls within 3 calls after an edit. `git diff --cached --stat` right before a commit is fine.
- Do not `read` a file again right after editing it: 27 `read`s of a file came within 3 calls after an edit of it. Use the lines and tags the edit's response returns.
- Change files with `edit`, never `sed -i`, `perl` or `python` through `bash`.
