## Waste guards (`resources/gui-bridge/waste-guards.ts`, rules and text `waste-guards-core.ts`, capability `wasteGuards`)

- **Why**: measured sessions (`scripts/session-pace.ts`) lose much of their time to failed tool calls, polls and `ready.log` waits that can never match (a service start whose stdout goes to a file waits its whole timeout and returns `NOT ready` as a success). The agent-side prose rule is the light-brief guidance in `resources/omp-builtin/skills/ompdesk/references/orchestration.md`; the guards make the repeating cases impossible or visible. They use only public hooks (`tool_call`, `tool_result`) and a re-registered built-in, so `wasteGuards: {}` in `capabilities.ts` needs no internal. Stock omp is not forked and nothing is installed.
- **Guard 1: a `ready.log` that can never match is refused** (`tool_call`, `{block: true, reason}`, before the command runs). It applies to a `bash` call with a non-blank `ready.log` **and a non-blank `name`** (stock `bash.ts` `normalizeReady`/`execute` ignores `ready` without a service `name`, so refusing it would be wrong) whose command's **last command, in its last pipeline stage,** sends stdout to a file. `readyLogCannotMatch` reads the command with a small scanner (`scan`: quotes, escapes, `$(…)`, backticks, comments, heredocs, `;` `&&` `||` `&` newline, pipes), not a shell: anything it cannot place (a subshell's contents, an expansion) reads as "no redirect" and passes.
  - Refused: `> f`, `>> f`, `&> f`, `&>> f`, `1> f`, `>| f`, `>& f`, `>f 2>&1`, `2>&1 > f`, `2> e > o`, a target of `/dev/null` or a quoted `"$VAR"`, `>&-`, the last command of `a && b > f` or `a; b > f`, the last stage of `a | b > f`, a trailing `&`, a redirect after a line continuation, `cat <<EOF > f` (the redirect on the heredoc's own line).
  - Passes: no redirect, `| tee f`, `2> f` alone, `> f 1>&2`, `> /dev/stdout`, `/dev/stderr`, `/dev/tty`, `/dev/fd/N`, `> >(tee f)`, a redirect in an earlier command of a chain or an earlier pipeline stage, a `>` in quotes or a comment, a redirect only in a heredoc body (bodies are cut before judging), a redirect only inside `( … )`, `< f`, `3> f`.
  - Known cost, as the owner asked: `bun test > f` (stdout only) is refused too; the reason (`READY_LOG_REASON`) names the two ways out (async: true and `wait`, or `| tee file`).
- **Guard 2: one hint at a poll** (`tool_result`, `{content}`: the hint is a second text part appended to the call's own content; never a block, `details` and `isError` stay). **A poll is a repeated status look at the same thing, not a look** (the owner's rule, so a lone failure diagnosis is never hinted or counted). `pollLooks` names the looks of a call, each with a `kind` and, where there is a target, a `key`; `createPollTracker().observe` (the one classifier: the bridge's `createHints` and `src/main/session-pace.ts` `pace()` each keep one tracker per session and import it, no second copy) returns the kinds that are polls. No key = a poll at first sight: `sleep` (`sleep N` followed by another command, or `while … sleep`), `tail-f` (`tail … -f`/`-F`/`--follow`), and a foreground `gh run watch`. A key = a poll from the second look at the same key: `gh-run` (`gh run view`, key = run id, plus `--job` id, or the arguments when there is no id; `gh run list`, key = its normalized arguments), `pgrep` (key = its arguments), `proc` (`read` of a `proc://` path, key = the process id, the first segment after `proc://`: `proc://bg_1`, `proc://bg_1/streams/0` and `proc://bg_1:1-20` are all looks at bg_1). Never a look: `gh run view` with `--log` or `--log-failed` (diagnosis), a heredoc body (cut first), a quoted mention (`gh run` and `pgrep` are found among the command's words), and **anything in a bash with `async: true`** (it runs without the model and delivers once, so a background `gh run list` + `sleep` + `gh run watch` loop is the recommended way). Commands are cut at `; & | newline` outside quotes, so a jq filter's `|` stays in its argument. `createHints()` keeps the kinds already told in one set: **once per kind, per omp process** (one omp is one session; the main agent and every subagent share it); a call that carries several kinds marks them all told. Pace counts one poll per call that is one (the same diagnosis twice counts 1, a lone `sleep 30` counts 0) and each `wait` that came back with nothing (Guard 4). Text: `POLL_HINT`.
  - **Can the hook change the result? Yes, so the hint is appended to it** (the owner's rule: append to the result when the hook may; `sendCustomMessage` only otherwise). Stock's `ToolResultEventResult` (`extensibility/shared-events.ts`, merged by `extensions/runner.ts` `emitToolResult`) takes a replacement `content`, `details` and `isError`, and the changed result is what the model, the transcript and the work board get. The hook returns `{content: [...event.content, {type: "text", text: "\n" + hint}]}` only for a fresh kind; nothing else changes. Not `additionalContext`, because the result the agent reads would then carry no hint.
- **Measured**: with the guards, a service start redirecting to a file is refused at once with `x.log` never created, and of two polling calls only the first result carries the hint.
- **Pinned by** `src/main/bridge-waste-guards.test.ts` ("ready.log that can never match" fixtures, "looks only at a call stock would hold for ready.log", "polling kinds", "poll hints": once per kind, several kinds per call, per instance) and `src/main/bridge-waste-guards-stock.test.ts` (installed omp: "refuses a ready.log that cannot match at once, without running the command"; "hints at the first poll of a kind only"), `src/main/session-pace.test.ts` ("polls are repeated looks": the same tracker counts Pace's `polled ×N`).
- **Guard 3: one hint at a refused edit** (same `tool_result` hook and once-per-process set as the poll hint, kind `edit-misuse`), because refused edits are agent misuse that costs a round trip and a re-read. `editMisuse(toolName, outcome)` is true for an `edit` result with `isError` whose text matches `anchors to lines` or `not from this session` (stock's two refusals; the stale-tag refusal "file changed between read and edit" and the restated-neighbour case name their own fix and get no hint). Text: `EDIT_HINT`, appended to the failed result's content; stock keeps the call an error (`runner.ts` `emitToolResult` returns `isError` as it was, `wrapper.ts` returns the modified result with `isError: true` instead of rethrowing).
- **Guard 3 pinned by** `bridge-waste-guards.test.ts` ("hint on a refused edit": once per process, the two refusal texts, not a success, another refusal or another tool) and the stock test "hints once at an edit anchored to lines the session never read" (a `#0000` edit is refused, still an error with `errorKind: unknown_tag`, ends with the hint; the second gets none).
- **What the `tool_result` hook costs**: stock awaits its handler runner for every tool result once any extension subscribes, which can lose an aborted result in the journal at a quit. A hook added here, or anywhere in the bridge, relies on `quit-journal.ts` (`.omp/rules/interrupted-work.md` › "A quit during a tool keeps the tool's aborted result in the journal"), which holds the quit until started calls have their results; never remove it while a `tool_result` handler exists.
- **Guard 4: `wait` returns only with news**. Stock's `wait` (`tools/wait.ts`) gives each call a window from a ladder (`WAIT_LADDER_MS` 5 s, 10 s, 30 s, 60 s, 300 s; a back-to-back wait climbs one rung, news or a 60 s gap restarts at 5 s) and returns when it runs out with every watched job still running (`## Still Running`, `useless: true`, `details.jobs` all `running`), a model call that only waits again. The bridge re-registers `wait` (public `registerTool` over a built-in) and calls stock's own through the same-tool `ctx.invokeTool` again while `waitWindowElapsed(result)` holds (core: `useless`, `op: "wait"`, at least one job, every job `running`). Anything else is returned as stock built it: a job settled, a service ended, a message or reply, nothing to wait for, an interrupt. A wait on a service alone or for a reply lists no job, so it still returns at stock's window. No limit of its own (the owner's rule): the job's own timeout, a message and the user's stop end it. The definition carries `interruptible` and `handlesToolInterrupt` as stock's tool does (not in `ToolDefinition`'s type; `RegisteredToolAdapter` passes every key through `applyToolProxy`), or a steer would no longer cut the wait short. `invokeTool`, `useless` and the ladder are the same at the 18.18.2 floor. Pinned by `bridge-waste-guards.test.ts` ("a wait that came back with nothing"), `session-pace.test.ts` (an empty wait is a poll, a wait with news is not; nothing in an async bash is) and the stock tests "blocks a wait until the job it watches finishes, past stock's first windows" and "still ends a blocked wait at once when a message comes in".
- **Measured and not guarded**: repeat reads (nearly all distinct ranges or follow-ups stock's declarations-first reads require; a guard cannot save them since the model call is spent when the read is asked) and edits refused for a tag never received (`#0000`, after seeing the file only through `bash` or a `:raw` read, which give no tag; Guard 3's hint covers it). Turning bare code reads into whole-file reads (`tool_call` `input`) was rejected, to keep stock's declarations-first design.

## Edits

The rule the third guard repeats, for any agent working in this repository:
- Edit only lines shown in the latest `read` of that file. After a grep hit, or an elided or declarations-only read, read the exact range first.
- Copy the `[FILE#TAG]` header from that read or from the last edit's response; never invent one (`#0000`) or reuse one from another session.
- After each edit use the tags and line numbers the edit's response returns, not the ones before it.
- Do not re-check that one edit applied: its response already shows the edited lines and the new tag, so a `git diff` of that same hunk or a `read` of lines the response just displayed adds nothing. What a single edit response cannot show stays a normal check: `git status` for unexpected or untracked files, the whole diff before a commit (`git diff`, `git diff --cached`), the combined change across several edits or files, and a `read` of lines outside the displayed range (the next spot to edit).
- Change files with `edit`, never `sed -i`, `perl` or `python` through `bash`.
