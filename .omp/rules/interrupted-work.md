## Interrupted work, quit and diagnostics

### Interrupted turns continue by themselves
- `src/main/turn-resume.ts`, `src/main/connectivity.ts`. Settings › General › Continue interrupted work after relaunch, pref `resumeInterrupted`, **default on** (main reads `!== false`).
- **Two paths, one coordinator (`TurnResume`), driven by `SidecarPool.onRunningChange` (`resumeFacts()`).**
- **① Relaunch.** Eligibility is a marker file `<userData>/interrupted-turns.json` ({window, tab, peer, sessionPath, cwd, kind, startedAt, reason}) rewritten atomically on every run-state transition. NEVER write it in a quit hook: SIGKILL/crash runs none. `InterruptedTurnStore` writes through `writeFileAtomicDeferred` (one attempt now, retries on a timer) because on Windows the rename fails (`EPERM`) while any process reads the file and a running turn has no later transition to rewrite it; it logs `markers not saved` (source `turn-resume`) only when every try failed.
  - Present while a turn runs (`running`); cleared on normal completion and on the user's Stop (`SidecarPool.noteStopped`, called by the RPC dispatcher for `STOP_COMMANDS` `abort`/`abort_and_prompt`/`abort_and_restore_queue`, so a kill before the run's end event leaves none); kept as `asking` while blocked on an ask/approval (the relaunch re-runs the cut-off call, the card reopens; not "continuing"). An omp that exits or restarts takes its open asks with it (the pool forgets owners on any non-ready status).
  - A quit (`quitApproved()`) freezes writes: tearing tabs down must not read as turns ending. Closing the last shown window on Windows with close-to-tray off is such a quit, asked for before the window goes (`lastWindowCloseAction`, `quit-guard.ts`).
  - A marker whose session the user deleted (`deletedSessions()` tombstone) is dropped at launch, never continued, not even into a fresh tab. A never-written session has no tombstone and still continues.
  - `TurnResume.launch()` (after saved windows exist): each marker finds its tab by session path (deferred tab: `SidecarPool.startTab`; missing from the layout: opened) and continues through stock: `restore_interrupted` (local handler → bridge `composer.restore_interrupted` → stock `restoreSession`, what `omp --restore` runs) for a cut-off turn, `retry` (`/retry`) for a failed one (a turn that waited for the connection, `network`, or for a provider's limit, `limit`: see Limit wait). A killed OMPdesk's omp usually closes the turn itself on stdin EOF, so `restoreSession` finds nothing; the relaunch then runs stock `retry`, which replays the failed tool batch or aborted reply and does nothing for a turn that really ended.
  - **A turn cut before its next model call**: stock records a closed stdin as a `normal` `session_exit` (with `pendingToolCalls` only while a tool runs) and may never journal the abort, so `findUnfinishedTurn` reads the turn as ended and `/retry` finds nothing. The bridge's restore (only for a marker of a running turn) checks `requestCutAtExit` (`restart-core.ts`: the replaced process's clean exit record, nothing after it, a prompt or tool result before it that nothing answered) and appends stock's own interrupted-turn record (`session/exit-diagnostics` `createInterruptedTurnAbortMessage` over the branch without that exit) before stock `restoreSession`, which continues from the recorded tail: no tool reruns, no prompt sent twice. A prompt journaled only as its process ends lands after the exit record and needs nothing. Pinned by `bridge-restart.test.ts`, `src/main/bridge-restore-request-stock.test.ts` (installed omp) and `e2e/interrupted-resume.e2e.ts` (the fake omp records stock's exit record on stdin EOF).
  - **An aborted turn with a note after it**: a custom message journaled after an aborted reply hides it from stock's `retry` (`turn-recovery.ts` `conversationEnd` skips eval snapshots only). The bridge's restore (`turnCutBehindNotes` in `restart-core.ts`: last message an aborted or failed reply of the replaced process, a non-eval custom message after it, nothing typed since) continues it with the relaunch's one follow-up (`ompdesk-restart-turn`, or folded into the jobs/subagents one; details `turn: true`; the transcript's muted line "Continuing the work the restart cut off", `data-restart-turn`) and reports `followUp`/`turnCut`; `TurnResume` counts `followUp` as continuing and sends no `retry` on top (log `restored: "turn-behind-notes"`). It reads the journal only. Pinned by `bridge-restart.test.ts`, `turn-resume.test.ts`, `MessageBubble.test.tsx` and the note case of `bridge-restore-request-stock.test.ts`.
  - **A quit during a tool keeps the tool's aborted result in the journal**: with more than one stock `tool_result` handler the aborted result lost the race against `#doDispose` sealing the journal, and stock cannot skip a handler (`ExtensionToolWrapper` emits whenever any extension subscribes). So `quit-journal.ts`' `session_shutdown` handler (after `session_exit` is recorded, before dispose's `agent.abort()`) aborts the loop and waits, at most `QUIT_TOOL_SETTLE_MS` (1.5 s), until every call that started (`tool_execution_start`) has its result message (`message_end`, role `toolResult`); with nothing running it returns at once.
  - **The relaunch runs the cut-off bash again, with or without that handler**: stock's documented replay (`restoreInterruptedTurn` closes the turn with "outcome unknown" results, then `retry` reruns a fully cut batch). OMPdesk does not change that; a side-effecting command cut by a quit runs twice. Only the journaled result's text differs ("Command aborted" vs "Previous OMP process exited before this tool returned; its outcome is unknown.").
  - **The hold leaves `wait` alone**: a `wait` cut by a graceful quit never reaches the journal with a result, so stock's restore reruns it silently (`turn: true`); holding for it made stock read the turn as ended and the parent got the revived-subagents follow-up as a new turn. `quit-journal.ts` (`LEFT_PENDING_TOOL`) does not hold the quit for a `wait`. Pinned by `bridge-restore-subagents-stock.test.ts` ("while the parent waited on it").
  - **From omp 18.18.2 the dying turn's own aborted records reach the journal after `session_exit`, a `wait` and a first-request prompt included**: the journal ends `session_exit`, the prompt or aborted `wait` result, then an `aborted` reply "Request was aborted", which stock's `findUnfinishedTurn` reads as ended. `requestCutAtExit` returns `{ exit, abort }` when the last message after the replaced process's clean exit is such a reply (not stock's own interrupted-turn record, not one journaled after this process started, not one a custom note follows: `turnCutBehindNotes` owns that), builds stock's interrupted-turn record without the exit and that reply, and stock continues the turn: the tool's aborted result stands (a cut `wait` does not rerun; the parent still gets the revived-subagents follow-up as a steer, once). Pinned by `bridge-restart.test.ts` (`requestCutAtExit`), `bridge-restore-subagents-stock.test.ts` and `bridge-restore-request-stock.test.ts`. `[sidecar] stock stream metadata unavailable: unknown method stream_metadata.start` in a ci log is a fake omp in `link-traffic-relaunch.test.ts`, not this.
  - Pinned by `bridge-restore-request-stock.test.ts` ("a quit that aborted a tool, with a note journaled after the abort": the journal ends on the aborted reply or tool result, never the call) and `bridge-quit-journal.test.ts` (nothing pending goes at once; every started call has its result; a tool that never returns is waited for no longer than the bound).
  - A continuation waits for its tab's omp with no deadline (the owner's rule: no time limit ends or blocks work). `TurnResume.#whenReady` ends only when the tab reads `ready`, its omp fails (`error`, not a held session) or exits, the tab closes or the continuation is called off. `SidecarManager.dispose` drops listeners without emitting a status, so `sync()` ends the waits of tabs no longer in the pool's facts (`#endReadyWaits`), and a Stop, Cancel, new prompt or a superseding omp exit (`#dropWait`, `#exited`) ends them with the generation bump: no status listener outlives its continuation. The resuming row's Stop, the waiting row's Cancel and a new prompt on a held tab call it off even during the wait (a per-tab generation checked before every command). Pinned by `turn-resume.test.ts` (a day of fake time, no failed try; a closed tab and Stop leave no listener).
  - **A failed continuation keeps its marker** (its omp failed or exited before ready, or every command it sent threw or had no connection: "GUI bridge closed", an RPC timeout): the marker stays in `#pending` and in `interrupted-turns.json`, and `#run` goes again, under the same `stale()`/`HOLD_ENDS` checks, when the tab's sidecar next emits `status: ready` (a listener, never a poll), at most `LAUNCH_CONTINUATION_ATTEMPTS` (3) failed tries per marker; past that nothing more is sent this launch, the "continuing" row goes and Autopilot's `goalSettled` hears `none` (once per continuation, at its end, never per failed try). An omp that answered with nothing to continue is no failure: the marker goes, and it still leaves when the turn runs, on Stop/Cancel, a new prompt, a move, a closed tab or the setting off.
  - `restore_interrupted` and `retry` get `RESUME_COMMAND_TIMEOUT_MS` (2 min), not the RPC client's 8 s default, because stock's restore reads every subagent transcript first.
  - No toast: each resuming tab shows its own calm row ("Continuing where it left off…", `data-resuming`, one per tab, `setResuming` → tab `resuming` → `TurnStatusRow`; not for a reopened card) with the Stop on it (`resume.stop(tabId)` → `TurnResume.stopResumed(tabId)`: that tab only, noted as the user's Stop so its marker goes and Autopilot's goal resume ends `cancelled`). The only resume indicator.
  - Rank order: focused tab, other panes of its split, then background tabs (`ResumePool.resumeRank` ← `SidecarPool.resumeRank`).
  - Setting on: a quit (⌘Q, tray, last window on Windows) and "Restart to update" ask nothing (`quitNeedsConfirmation(risk, resumes)` in `quit-guard.ts`, `confirmQuit()` in `app-quit.ts`, the updater's `UPDATER_APPLY`); off, they ask before stopping running work. Exception, a person's update restart (`confirmUpdateRestart`, `updateRestartConfirmation`): running background subagents and jobs start over after a relaunch, so it names them first (`app-updater.md`, "Running background work holds the restart too"); the automatic install waits for them instead.
  - **A run whose turn had ended is never retried** (marker `background: true`, `deriveMarkers` from `ResumeFact.settling` = `runSettling`: only background subagents or async jobs kept the run on). Its continuation is `revive` (`launchAction`): stock's restore alone, which revives the subagents and lets the bridge name the stopped jobs; stock `retry` is never sent. A marker without the field (an older app's) reads as before.
- **An omp that dies while the app runs is a relaunch for its tab**: `SidecarPool` and `LocalHostServices` count each `restarting` of a tab's own omp (`ResumeFact.exits`; a paired host's link status is no exit, nor Windows ending the session), and `TurnResume.#exited` turns the marker the tab had before that sync (running, asking or background; never `network`, whose wait and marker outlive the omp) into a launch marker in `#pending` and runs it as `launch()` would once the next omp is up: the resuming row, the person's Stop, prompt or move ending it, the setting off taking none, Autopilot's `relaunchContinuation` reading `after_restore`, the log's `marker` line with `via: "exit"`. A continuation already on its way when the omp dies again is superseded (its marker in `#superseded`, the tab's generation bumped): it sends nothing more (no `retry` into the next omp) and leaves the marker and the goal report to the new one. Pinned by `sidecar-pool.test.ts` ("an omp that ends under its work continues on the next one"), `turn-resume.test.ts` ("TurnResume after the omp died under its tab"), `host-services.test.ts` ("a device tab's omp dies under its background work") and `e2e/interrupted-resume.e2e.ts` ("goes on when its omp dies under it").
- **One conversation stays one session across a relaunch**: a tab whose session file exists starts on it (`--session`), the continuation answers into that file, the sidebar lists it once.
  - A start on a stored session first waits (up to `SESSION_FREE_WAIT_MS`, 60 s) until no other live omp holds stock's ownership lease on it (asked every 250 ms for 5 s, then every 2 s) (stock helper `sessions.owned`, `tryAcquireSessionLease` keyed by the header's id, read past stock's title slot with `parseTitleSlotFromContent` as stock's `readSessionHeaderIdSync` does; `src/main/session-free.ts`, SidecarOptions `sessionFree`), because an omp that opens a session owned elsewhere moves it to a new file (stock `"open-elsewhere"`).
  - Still owned when the wait runs out (an omp run in a terminal): the start opens nothing; the tab is `error` with `omp.sessionOwned` ("still open in another omp … Close the other one: it opens here by itself then, or press Restart"), Restart waits again, and the tab keeps waiting by itself and opens the session the moment the owner lets go (`#whenSessionLetGo`).
  - Its status carries `sessionHeld`, shown everywhere as a wait (warning, "Waiting for the session", `sidecar.heldTitle`), never a failure: the pane's `SidecarBanner`, an opener's child row (`IpcTabInfo.sessionHeld`), the title bar (`SessionSummary.sessionHeld`, `sessionRun`, panels-sidebar.md › A row is live; `titlebar.status.sessionHeld`, the hollow pending dot), the tray (`trayStatusOf`: not an error), every split pane header (a spinner), the Work tree (`work-tree.ts`), every sidebar row of the session (a paired device's tab here included), a paired device's pane (`TabStatusArg.statusPayload.sessionHeld`, kept by `RemoteSidecar`). A relaunch's continuation keeps waiting for that `ready` (`TurnResume.#whenReady`, no deadline) instead of dropping the cut-off turn; pinned by `turn-resume.test.ts`.
  - The lease is an OS lock, so a dead owner never holds it; a helper that cannot tell lets the start go on (the two stock internals are the `sessionOwner` feature in `capabilities.ts` and `health.ts` `LOADERS`, reported like any missing internal). A wait over 1 s, or one that runs out, is a `session-owner` line in `gui-runtime.jsonl`.
  - Pinned by `session-free.test.ts`, `session-free-stock.test.ts` (installed omp), the two start cases of `sidecar.test.ts`, `e2e/interrupted-resume.e2e.ts` (no second file, one indexed row, after kill and normal quit), `e2e/real-update-restart.e2e.ts` (a)/(a2) and the SIGKILL test of `e2e/real-resume.e2e.ts`. Two rows in the README resume clip were the fake omp writing a second journal (see the fake omp under Build, test), never OMPdesk.
- **Every spawn of a tab launches one bundle on the tab's own session** (`src/main/omp-launch.ts`: `sessionOpen`, `ompArgs`, `sessionEnv`; `SidecarManager.#spawn` gathers the facts). A new tab, a stored session, a relaunch's saved tab started later, an interrupted turn's tab, an omp update's restart, a paired device's tab and that tab revived get the same extensions and OMPdesk settings; only the session flag, the bridge socket and a device tab's `OMP_GUI_PROMPT_ORIGIN` differ.
  - The tab keeps the session it is on (the file it opened, then what `get_state` reports), so a restart that names none (a crash, machine setup starting a tab that waited for omp, the desktop slot's stop) reopens it.
  - A session stock never wrote starts a new one in the folder (`--config fresh-launch.yml`), never omp's `autoResume`; a tab stays new (`#isNew`) until `get_state` names its session, not merely until `ready` (formal/tab-session F1).
  - A `switch_session` or `new_session` inside the omp is taken from its own response (`#observeResponse`: the requested file; a new session not yet named), because stock names no file there (F2); a fork, branch or handoff keeps its parent until `get_state` (formal/tab-session A5).
  - Only the person's move to another folder (`restart(cwd)`) leaves the choice to omp; the start gate's move into a worktree stays new.
  - Model-checked by `formal/tab-session` (TLC; `skill://tab-session-verify`); pinned by `session-launch-parity.test.ts` (every path through the real pool, host services and factory; every three-event sequence of crash, restart, turn, move and open) and `omp-launch.test.ts`.
- **The host owns the turns it runs for a paired device.**
  - On the device (A) a remote tab (`device`) is skipped entirely: no marker, no judging, no takeover by A's connectivity.
  - On the host (B) `index.ts` composes `TurnResume`'s pool from `SidecarPool` and `LocalHostServices` (`resumeFacts`/`startTab`/`setAwaitingConnection`/`noteStopped`/`tabForSession`, ids `peer:<deviceId>:<rtab>` kept when re-keyed; run bookkeeping via `trackRunEvent` in `sidecar-run-state.ts`; asks from the tab's `extensionUi` and the device's `extension_ui_response`; the device's Stop through `tab.command`). B writes the marker (with `peer`), continues after its own crash or quit (the marker revives the hosted tab, unstarted, waiting for its device in the grace period: `RemoteDevices.reviveHostTab`, only while hosting is on) and judges network failure by B's connectivity.
  - Grace (`HOST_TAB_GRACE_MS`, 10 min from link loss, `LocalHostServices.#startGrace`) closes only an idle hosted tab; one that runs out while the tab runs a turn (revived included) or holds it for B's connection starts another. A turn blocked on an ask waiting for the device keeps its omp until the device answers or B quits; no overall cap.
  - A only mirrors the wait (`awaitingConnection` tab event, emitted ahead of the failing events and re-sent on every `tab.open`; "Waiting for {device}'s internet connection…") and sends its Cancel to B (`RemoteSidecar.cancelHostWait` → `tab.cancelWait`).
  - **A device viewing a window's tab of B sees B's wait and scheduled retry too**. The window's tab is B's own (`viewForDevice`, never in `LocalHostServices.resumeFacts`), so B's `TurnResume` holds it under the window tab's id. `SidecarPool.setAwaitingConnection`/`setScheduledRetry` emit on the entry's `deviceViews` as they change (a view that joins gets what holds from its snapshot); `LocalHostServices` forwards a view's `awaitingConnection` and `scheduledRetry` to the device (`#createTab`; a device's own tab still takes only the coordinator's) and re-sends both on every `tab.open`. `scheduledRetry` (`TabScheduledRetryArg`: `{remainingMs, attempt, max}` or null) carries time left, never B's clock; `RemoteSidecar` sets A's `at` = A's now + `remainingMs` and A's pool shows it (`setScheduledRetry`, `TurnErrorNotice`'s "Retrying in 0:30…"); A's `TurnResume` never arms one for a remote tab (`#mayRetry`, `fact.device`). A's Cancel on either reaches B's `TurnResume.cancelWait(<window tab id>)` (`tab.cancelWait` → the view's `cancelHostWait` → `SidecarPool.onCancelWait`, set in `index.ts`), which drops the scheduled retry with the wait. An older host never sends `scheduledRetry`; an older device drops the name. Pinned by the device-view cases of `sidecar-pool.test.ts`, "tells the viewing device the window's connection wait and scheduled retry" and "sends the device's Cancel to the window's tab" in `host-services.test.ts`, and `remote-sidecar.test.ts`.
  - A relaunched device reopens tabs under new rtabs: `tab.open` with a session path takes over the tab an earlier connection left (`#adopt`), so no second omp starts on the session.
  - **A device's quit leaves its host tabs running**: during an approved quit with Continue interrupted work on, `RemoteSidecar.dispose` sends no `tab.close` and defers none (`keepOnHost`, `RemoteDevicesDeps.keepHostTabsOnQuit` = `quitApproved()` and the pref, wired in `index.ts`), so B keeps the tab through its grace and the relaunch adopts it. With the setting off the quit dialog promised to stop those turns, so they close; a user's own tab close always closes. Pinned by `remote-sidecar.test.ts` and the quit test of `e2e/remote-resume.e2e.ts`.
  - **A device whose saved layout lost a running host tab gets it back**: every time a host's link comes up (`RemoteDevices.onHostOnline`) the device sends `tabs.kept` (`KEPT_TABS_METHOD`, `app-protocol.ts`). The host's `LocalHostServices.#keptTabs` answers, for the asking device, the tabs in their grace period (no live connection) with a session file that run a turn, settle, wait on an ask, or are held for the host's connection (`state`: `running` | `settling` | `asking` | `waiting`), each with `rtab`, `formerRtabs` (`HostTab.formerRtabs`, ≤ `MAX_FORMER_TAB_IDS`), `sessionPath`, `cwd`, `kind`, `title`. An idle grace tab is left to its grace. `readoptHostTabs` (`remote/readopt.ts`) leaves a session a local tab already holds to that tab (`SidecarPool.sessionOwner`, which a deferred layout tab holds too) and opens the rest in the front window through `SidecarPool.acquire(…, formerIds)` (wired in `index.ts`): adopted by session path (`#adopt`), with `[rtab, ...formerRtabs]` as its `former` ids so an id an agent was given before the relaunch resolves (`ControlTab.formerIds`). One runtime-log line per tab, source `remote-tab`, message `readopt` {device, rtab, formerRtabs, session, state, tab}; `readopt-failed` {device, error} when the answer fails for any reason but being away. A host that answers `unsupported` opens nothing. **A v0.49.0 host is not covered**: none of its routes names the orphaned tab, so a device updated before its host is protected only once the host updates too. Pinned by `host-services.test.ts` ("lists the working tabs a device's last connection left"), `readopt.test.ts`, `devices.test.ts` ("the tabs a host keeps for this device", `unsupported`), the former-ids case of `sidecar-pool.test.ts` and `e2e/remote-resume.e2e.ts` ("a host's running tab the saved layout lost").
  - **A host tab the saved layout kept comes back attached, not deferred.** The same `tabs.kept` answer starts the tab here that holds a kept session (`readoptHostTabs` → `holder`/`start` → `SidecarPool.startTab` on an `asleep` tab, whose `tab.open` adopts the host's tab; its `readopt` line adds `held: true`), so the host's running turn is visible on the device. Pinned by `readopt.test.ts` and the background test of `e2e/remote-resume.e2e.ts`.
  - **Both computers relaunching together: a host tab its own relaunch is about to continue counts as running**: `#keptTabs` also names as `running` a tab whose launch continuation is still owed (`TurnResume.relaunchContinuation(resumeId) === "after_restore"`: marker pending from the relaunch through the restore until the turn is seen running or nothing went on), because between the restore's answer and stock starting the restored turn the tab reads idle. `running` is the state every device version reads. Pinned by "lists a revived tab whose relaunch continuation has not started its turn yet" in `host-services.test.ts`.
  - One session file = one host tab = one omp. An open of a file this connection shows under another rtab, or another device's tab holds, is refused `session_open_in_tab`; `#open` re-checks the holder after its awaits; a tab whose omp moves onto a file another host tab holds (`#dedupe`, on its `session` identity) stops the other (keeping one that runs a turn) and tells its device `exited` (`host-services.test.ts`).
  - A host's session closes and deletes like a local one: its sidebar row (`SidebarDevices.tsx`) has Close (the tab; session stays on the host) and Delete (confirm names the host, `remote.sidebar.deleteMessage`; tab closes first, then `sessions.delete` on the host), both behind the row's one ⋯ (`data-sidebar-row-menu`; an action sheet on touch). `#deleteSession` takes the host's own delete path (`session-mutations.ts` `deleteSession` with `LocalHostServices` as `deviceTabs`): every idle tab on the file closes (the asking device's own, including one from an earlier connection; another device's, which hears `sessionDeleted` once the file is gone; a window's tab on the host), the omps are waited for, and it is refused (`session_running`) only while one of them runs a turn or compacts. Pinned by `host-services.test.ts`, `Sidebar.test.tsx`, the delete tests of `e2e/remote-resume.e2e.ts` and the touch ⋯ in `e2e/mobile-shell.e2e.ts`.
  - **The host's own delete closes the devices' tabs on the session** as another window's tab (`deleteSession`'s `deviceTabs`, `LocalHostServices.closeSessionTabs`): refused (`session_running`) only while one of them, or the window's own tab (`SidecarPool.sessionRunning`), runs a turn or compacts; otherwise their tabs end (`exited`, "closed on the host"), their omps exit, the file goes, and only then (the notice `closeSessionTabs` resolves to, run after the stored delete succeeded and the tombstone is written) each device hears the tab event `sessionDeleted` (its pool records the tombstone, drops the tab and its saved layout entry). A failed stored delete tells no device, because a tombstone for a file still there would refuse it forever. An older device drops the event and keeps an exited tab. A device viewing a window's session (`viewsWindow`) is told the same; a device off the link learns it at its next `tab.open` (`session_deleted`). Pinned by `session-mutations.test.ts`, `host-services.test.ts` and the host-delete test of `e2e/remote-resume.e2e.ts`.
  - **Stop and delete** (the user's rule: one action, no second confirmation). A delete a running turn refused, here (`Sidebar.tsx`: this window's tab, another window's, a paired device's tab this computer runs) or on a host (`SidebarDevices.tsx`), is a toast "This session is running…" with one action, "Stop and delete" / "멈추고 삭제" (`sidebar.stopAndDelete`). It calls `sessions:stop` (`window.omp.sessions.stop(path, device)`): main stops every turn on the file (`LocalHostServices.stopSessionTurns`: `SidecarPool.stopSession` for a window's tab in any window, and the device tabs it runs; with `device`, the host's `sessions.stop` does the same there) with `abort_and_restore_queue` (logged by `session-delete`), and answers once each run has ended (the tab's `idle` activity / run events, never a timer; `session_running` after `STOP_SESSION_WAIT_MS` if one does not). Then the same delete runs again. An older host has no `sessions.stop`: the action fails with its message. Pinned by "Stop and delete" in `sidecar-pool.test.ts` and `host-services.test.ts`, `Sidebar.test.tsx` and the host-window delete test of `e2e/remote-resume.e2e.ts`.
  - Every delete, here or asked by a device, writes one `gui-runtime.jsonl` line (source `session-delete`, `recordSessionDelete` in `session-mutations.ts`): `device` (the machine the file is on, `local`), `by` (the asking device), the file's name, and `deleted`, `refused` with the code or `failed` with the message.
- **② Connectivity.** `ConnectivityMonitor` (net.isOnline() sampled by edge, windows' `online`/`offline` via `resume.reportOnline`, `powerMonitor` suspend/resume with a DNS probe until the wake is real, then `RESUME_WINDOW_MS` = 60 s) decides `shouldWait()`. A turn ending in a network-class error (`isNetworkError`, subset of stock's retryable pattern) while `shouldWait()` holds is not failed: the tab shows `awaitingConnection` (`TurnStatusRow`'s "Waiting for the internet connection…", Cancel → `resume.cancelWait`; `TurnErrorNotice` hidden), keeps a `network` marker and runs stock `retry` once online. A new run on the held tab (a prompt sent meanwhile, not the taken-over retry saga still ending) replaces the wait.
  - **One table says what ends a hold** (`src/main/turn-resume-ends.ts`), so end conditions are never copied into each path. `HOLD_ENDS` has one row per end condition (the person's run or prompt, Stop, a move, another outcome, not retryable, busy, a closed tab, the quit), with the checks it applies at; `HOLD_CHECKS` names each place `TurnResume` looks (`wait`, `probe`, `probeAnswer`, `armed`, `firing`, `continuing`) by the model action that looks. Every place calls `holdEnd` and decides only what the end does there. `TurnResume.tla` mirrors it by name (row `x` = `End_x`, check `y` = `Ends_y` built from exactly that check's rows), so a new end condition is one row and one `End_` operator; `turn-resume-ends.test.ts` pins every hold × condition pair, replays random event orders against the model's properties, and fails on any row or row-at-a-check one side lacks (rows the model keeps constant are its fixed `OUT_OF_MODEL` list); `src/main/turn-resume-test-rig.ts` is the one-tab world it drives.
  - **The marker says `network` the moment any wait holds**: every `#hold` outside `sync()` (the probe's answer, the scheduled retry firing offline) calls `sync()` right after, so a crash during the wait still retries (formal/turn-resume F1).
  - **Another session or branch ends the wait** like Cancel (`#dropWait`: the row goes, nothing retries into what the tab shows now), as it ends a probe and a scheduled retry. Every wait records what it holds for (`HeldWait.since`: the session file and `touched`); `#judge` ends it when `touched` moved or the tab's file is another one (`#movedSince`; a file stock writes after the hold, a first turn not saved yet, is the same conversation). The continuation re-checks with `#movedSince`: `flush()` hands each wait's `since` to `#run`, which drops a moved one before it starts the omp and again once the omp is up (a fired scheduled retry's `#run` carries the armed session too).     - **Autopilot hears every call-off.** A held launch continuation (the wait and its marker in `#pending`) that Cancel, the resuming row's Stop, a new prompt or a session/branch move drops tells `ResumeDeps.goalSettled(tab, "cancelled")` from `#dropWait`, so Autopilot's `#awaitingResume` never waits forever.     - **A move is in flight before it is counted.** `touched` counts a `TOUCH_COMMANDS` move at its answer, so `trackMove` (`ipc.ts` for a window's tab, `LocalHostServices.#command` for a device's; through a view the window tab's pool entry) marks the move in `MovesInFlight` (`SidecarPool.beginMove`/`movesSettled`, host `movesSettled`, composed as `ResumePool.movesSettled` in `index.ts`) until its answer was counted; `#fire` and `#run` wait for it before they look. ### What a relaunch continues beyond the cut-off turn
Measured on the real omp by `e2e/real-update-restart.e2e.ts` (opt-in `OMP_GUI_REAL_WORK=1`; "Restart to update" = an approved quit while work runs).
- Stock: a foreground bash call is journaled "outcome unknown" and runs again; subagents (awaited or background) are revived by `restoreSession` (the parent gets the result, a waiting `wait` included, when stock continues its turn); an open ask/approval reopens.
- OMPdesk handles five things stock leaves behind:
  - **Background bash jobs** (`async: true`) started by the last process and never settled are named to the agent in one follow-up (`ompdesk-restart-jobs`; bridge `composer.restore_interrupted` → `resources/gui-bridge/restart-core.ts` `interruptedJobs`, reported as `jobs`). The model gets `restartFollowUp`'s text (each job `- <id>: <intent> — \`command\``, intent = the call's own `i` argument, then "start again only the jobs the work still needs, say nothing about the restart or this notice, carry on"). The transcript gets one muted line ("Re-running N background task(s) the restart stopped", `RestartNote`, `data-restart-jobs`, intents as hover title): `details` hold only job ids and intents, never a user bubble, never a raw command. Jobs are read from entries journaled before this process started, from after the second-to-last `session_exit`, never cut at a `session_exit` alone; a job an earlier relaunch already named counts as settled. Pinned on stock by the SIGKILL test of `bridge-autopilot-stock.test.ts`.
  - **Subagents revived for a session whose own turn did not go on**: same follow-up (next subsection).
  - **Background subagents stock could not revive** (stock's `restoreSession` skips an isolated one or one without `session_init`). `stoppedSubagents` (`restart-core.ts`) reads the last life's backgrounded `task` results (`details.async` `{state: "running", type: "task"}`, the spawns of `details.progress` still `pending` or `running`; the job id is the agent id) minus what settled them (stock's delivery, a `wait` report, an earlier notice) and minus what the restore revived; the same follow-up names them (`- <id>: <intent>`, "they did not come back and their results will not arrive … check what each one already did, then start again only the ones the work still needs"), customType `ompdesk-restart-jobs`, counted with the jobs in `details.jobs` (ids and intents) so the one muted line covers them; reported as `stopped`. Pinned by `bridge-restart.test.ts` (`stoppedSubagents`).
  - **A goal active until the last process ended** (`goalActiveAtExit`: the last `mode_change` journaled before this process started, `performance.timeOrigin`, is `goal`; NEVER read it from a `session_exit`, which stock does not journal for SIGKILL/crash nor always when stdin closes mid-turn) that stock paused at startup comes back as `goalPausedByExit`. `TurnResume` resumes it once after the restore (`resumeGoal`, injectable; default local `set_goal` `resume`; `goalSettled` tells Autopilot `resumed`, `none` or `cancelled`).
  - **A new session's first turn cut off before stock wrote its file** (at the first assistant message): the pool keeps the prompt (`unsavedPrompt`, marker `prompt`) and the relaunch sends it again when restore and retry find nothing; it leaves the marker before sending, so once. The saved layout drops the missing path (`tab-layout.ts`), so the tab returns as a fresh session in the same folder and `TurnResume.launch` takes it for the marker (`#unwrittenSessionTab`: a local tab in the marker's folder with no session file, one per marker), never a hidden second one; only without such a tab does `openTab` open one. A spawn whose `--session` file does not exist starts fresh in its folder (`#spawn` in `sidecar.ts`, fresh-launch config so no older session auto-resumes; stock exits "Session not found" on it; also covers an omp restart of a never-used tab).
- Pinned by `turn-resume.test.ts`, `sidecar.test.ts`, `bridge-restart.test.ts` (intent, notice wording, details without a command), `MessageBubble.test.tsx` (muted line, not a bubble), `ChatStream.turn-status.test.tsx` (row's Stop), `quit-guard.test.ts`, `e2e/interrupted-resume.e2e.ts` (background-job relaunch: no toast, one resuming row, one muted line, no bubble, transcript at the bottom; idle session with a working background subagent: one muted subagents line and a turn; setting off: the quit asks, "Quit anyway" leaves no marker). Real omp (`(b2)`) records `ui` and `saidAfterNotice`: no restart narration from the model.

### Revived subagents
- **Seen**: the bridge's `composer.restore_interrupted` hands stock `restoreSession` the buses a live `task` run reports on (the task tool's `ToolSession` `eventBus`/`subagentEventBus`; TaskTool keeps it in a TS-private `session` field, `getToolByName("task")` in `capabilities.ts`), as `omp --restore` passes main.ts's own, so omp's RPC registry (`get_subagents`, the `subagent_*` frames the work board, dock and composer cue read) hears of a revived subagent. Pinned by `src/main/bridge-restore-subagents-stock.test.ts` (installed omp: a SIGKILL-cut background subagent is listed `running` after restore).
- **Told, every time**: stock's restore leaves the session unaware of the subagents it revived (the turn had ended, stock declined to continue, or it restored the turn but the subagents' first answers take minutes).
  - The bridge adds them to the relaunch's one follow-up (`restartFollowUp(jobs, revivedSubagents(branch, outcome.subagents), "restored" | "cut" | "idle")`; customType `ompdesk-restart-subagents`, or `ompdesk-restart-jobs` when jobs come too: one message). The model gets `- <id>: <intent>` (intent = the `task` assignment's `Title:` line, else its first line, `assignmentHeadline`, cut at 120 chars). Idle session: check them, tell the user in a sentence or two, keep supervising, a `followUp` prompt (one turn). Restored turn: each one's first answer can take several minutes, not a stall, keep supervising; queued as a steer at that turn's first `turn_start` (`session.subscribe`), because a steer queued before the turn is held behind the rerun calls (a rerun `wait` would run for minutes), while one queued after interrupts the `wait`. Both say nothing about the restart.
  - The transcript shows one muted line ("Continuing N background task(s) after the restart" / "재시작 뒤 백그라운드 작업 N개를 이어서 진행해요", `RestartNote`, `data-restart-subagents`, intents as hover title) from `details.subagents`.
  - **Seen while it resumes**: omp's registry lists a revived subagent `running` with no `parentToolCallId`. `mergeRunAgents` (`chat/work/work-run.ts`) gives such a running row the lane its spawn named (index, call, title), never "Work interrupted". Until it reports back (`resumedAgents`: the newest restart note's `details.subagents` minus a later `async-result` naming the job) a lane with no call yet says "Resuming after the restart" / "재시작 뒤 이어서 진행 중" (`chat.work.resuming`), and so does the board row's tooltip step (`WorkBoard.tsx` `AgentRow`).
  - **A subagent the revive ended at once reads "Interrupted by the restart", never failed, on every surface**. One rule, `restartCuts` (`src/shared/restart-cuts.ts`, pure and import-light, indexed once per transcript list; `restartCutsOf(committed, live)` joins the live messages only when one can be a delivery; main's session summaries run it over the restart notes and deliveries each omp writes, so a sidebar row never lists such an agent): an `async-result` job of type `task` with status `failed` whose output is only stock's empty-message warning, `(no output)` or nothing (`endedWithoutMessage`; any real `<error>` text, abort reason or preview keeps it a failure) and whose agent id the newest restart note before it names (`details.subagents[].id`). One applier, `markCut`: a `failed` node of a named agent takes the status `restart-cut` (`RESTART_CUT_STATUS`; stock's own in `stockStatus`, the note's `{intent, doing}` in `restartCut`; `restartCutNote` = `doing`, else `intent`). An agent that runs again keeps running.
    - **Applied once, at ingestion, in the tab's subagents store** (`stores/subagents.ts`): `createTabRuntime` calls `bindRestartCuts` (`tab-runtime.ts`), which hands the store `setRestartCuts(restartCutsOf(messages, liveMessages).agents)` whenever the tab's messages change (a no-op while the map is equal). ### Scheduled retry
- `TurnResume`, follows stock's `retry.enabled` (Settings › Agent behavior › Retry; the `scheduledRetry` pref is retired, `src/main/retired-prefs.ts`). Once stock's own auto-retries are spent and a turn ends in a transient error (`isTransientError`: stock's retryable pattern with word-bounded 5xx codes, minus auth, quota/rate limit, bad request, context overflow, certificates), main arms stock `retry` after 30 s, 2 min, 10 min (`SCHEDULED_RETRY_DELAYS_MS`; `OMP_GUI_RETRY_DELAYS_MS`, comma-separated ms, shortens them for e2e), then **again every 10 min, with no limit, for as long as the failure stays transient and nothing calls it off** (the owner's rule: never hold agent work back). The attempt number counts on and nothing says "of N" or "gave up": `IpcScheduledRetry` is `{at, attempt}`, the card reads "Retrying in 10:00… · Attempt 12" (`turnError.scheduled.attempt`, en/ko). A failure that is not transient ends the chain (red card, Retry). `TurnErrorNotice` shows it ("Retrying in 0:30…", Cancel through `RESUME_CANCEL_WAIT`, Retry now) from `scheduledRetry` on the pool entry (`IpcTabInfo`, so a renderer reload re-reads it).
- Guards: never a hosted/peer tab, a tab without a session file, after Stop, unless stock's `retry.enabled` reads `true` (`get_settings`), or for a network error the connection wait already holds. Called off by any run that is not its own retry, Cancel, a session change or a `TOUCH_COMMANDS` move (`touched` on the pool entry, counted only once the command worked and was not cancelled: `movesTab`), stock's `retry.enabled` reading off at fire, tab close, quit; a fired retry whose omp is still coming up is called off by a move made meanwhile (`#run` looks again once the omp is up). "Branch from here" (`fork_from`) is no move: it writes a new session for another window and leaves the tab on its own. A retry due while offline goes to the connection wait. The attempt count resets when a retry ends in anything but a transient error or the user runs something new.
- **A continuation held for the connection is shown the whole time and released within a minute of the network returning**. The wait has no timer of its own, so the offline state must never outlive the outage: besides the events and the wake's probe loop, an offline state nothing is recovering asks the resolver every `REPROBE_INTERVAL_MS` (15 s, `ConnectivityMonitor#reprobe`; a probe times out at `PROBE_TIMEOUT_MS`) and goes online the moment it answers, whatever the link flag says, so `flush()` runs. Every surface shows the wait while `awaitingConnection` holds: the pane's row, the tab strip and sidebar signal (`tabSignalPresentation`, "Waiting for the internet connection", `titlebar.status.connectionWait`, below a question, a run and the tab's own down state), and the sidebar row of a paired device's tab on this computer (`SessionSummary.awaitingConnection`, pushed as it changes). Pinned by `connectivity.test.ts`, `turn-resume.test.ts` ("a continuation held for the connection"), `tab-signal.test.ts`, `host-services.test.ts`; model `formal/turn-resume` (`WaitEnds` with `LinkUpMissed`/`Reprobe`, `NoGiveUp`).
- A paired device viewing the window's tab shows the same countdown and its Cancel calls it off here (tab event `scheduledRetry`, time left rather than this computer's clock; see The host owns the turns). A device never arms one for a host's tab.
- Pinned by `turn-resume.test.ts`, `TurnErrorNotice.test.tsx`, `e2e/scheduled-retry.e2e.ts`.

### Limit wait
- **A turn that ended at a provider's limit waits for the limit and goes on by itself** (the owner's report, 12 Nov 2026: a tab his MacBook hosted for the paired desktop ended three turns with `429 … rate_limit_error … retry-after-ms=319918000`, the model's weekly limit, and sat for 37 minutes until another session wrote to it). Stock ends such a turn at once: a wait past `retry.maxDelayMs` (5 min) with no credential or model to switch to (`turn-recovery.ts` `exceedsDelayCap`; its chain walk skips a fallback model whose window cannot hold the conversation, `contextFitsModel`). `TurnResume` takes it up with the scheduled retry's machinery (one armed retry per tab, `#scheduled`), under the same `retry.enabled`, with another rule for when it fires.
- **What**: `isLimitError` (`turn-resume.ts`): a limit by its wording (`isLimitWording`, `src/shared/quota-reset.ts`: 429, rate limit, quota, usage limit) that is no account out of money (`isBillingCap`: the wordings of stock's `isBillingCapUsageLimit` and HTTP 402; a copy because main judges the text with no omp to ask, held against stock's function by `quota-reset-stock.test.ts`) and none of sign-in, a rejected request, a context that does not fit or certificates (`NEVER_RETRIED`). Never while stock's own saga runs (the run has not ended), and never for a live Autopilot run's session (`ResumeDeps.limitHeldElsewhere` = `Autopilot.holdsLimitWait`: the run's own `waiting_quota`, autopilot.md).
- **When**: the wait the failed reply carries (`retryAfterMs`: stock's ` retry-after-ms=<n>`, counted from the failure), else the provider's first reset over stock's usage reports, else `QUOTA_FALLBACK_MS` (15 min): `quotaWaitUntil`, the one rule Autopilot's wait reads too.
- **Earlier once it lifts**: every `LIMIT_LOOK_MS` (10 min, never more often per tab; `OMP_GUI_LIMIT_LOOK_MS` shortens it for e2e) the wait looks (`#look` → `#readLimit`): `get_settings` (`retry.enabled`, `retry.fallbackChains`), `get_state` and `get_usage` on the tab's own omp. **A look sends no request to a model**: `get_usage` answers stock's cached reports, which stock reads again from the provider's usage endpoint only once they are older than its 5 min. The retry fires early when the reports no longer say every account of the provider is limited (a reset pass was spent, another account is free; a provider with no report at all counts as well, since nothing then says the limit holds) or when the session's model or the fallback chains differ from when the wait began (a chain that now holds a model the conversation fits). A read that fails changes nothing. A try the provider refuses again is a new failure and a new wait, so a tab sends at most one request per look.
- **Shown and called off as the scheduled retry**: `IpcScheduledRetry.limit` on the pool entry; the card reads "Tries again by itself at {time} · in {countdown}, or sooner once the limit lifts." (`turnError.limitWait`, `data-limit-wait`) with Retry now and Cancel. The end table is the scheduled retry's (`turn-resume-ends.ts`, check `armed`/`firing`); a look syncs first, so a session file that moved on an idle tab ends the wait at the next look. **There is no booking** (the windows' click-to-book resume, `use-quota-resume.ts` and pref `quotaResume`, is gone and the pref retired): a limit nobody waits for (after Cancel, with stock's retry off, on an Autopilot run) still names the provider's reset on its card (`turnError.resume.resetsAt`).
- **A hosted tab too**: `notRetryable` lets a limit wait hold for a `peer` tab; the backoff retry still never does. What the exclusion guarded against was a retry nobody at either computer sees, so `index.ts` hands a hosted tab's wait to `LocalHostServices.setScheduledRetry`: the device gets the tab event `scheduledRetry` (`limit: true`, time left) on its own tab, shows the same card, and its Cancel is `tab.cancelWait`. The grace period keeps a waiting tab while its device is away (`#startGrace`) and `tabs.kept` names it `waiting`.
- **Across a relaunch**: a tab with an armed limit wait keeps a `limit` marker (`deriveMarkers`' `limited`; written when the wait is armed, gone with it, a running turn's `running` comes first), and the launch continues it with stock `retry` as it does a `network` one: one request per waiting tab per relaunch, and a provider that still refuses starts the wait again. An omp that dies under an armed wait changes nothing (`#exited`: the timer is main's).
- **Log**: source `turn-resume`, message `limit`: `{tab, session, wait: "armed", by: retry-after | usage | fallback, ms, peer}` when the wait starts, `{wait: "due"}` or `{wait: "lifted", by: usage | setup}` when it tries (the `continue` line follows).
- **Background work does not end the wait**: a look that finds the tab still running (the failed turn's background jobs or subagents) fires nothing and looks again a pace later, where the backoff retry is dropped at `busy`; a result of that work starts a turn of its own, which ends the wait as any new run does, and a tab whose jobs end quietly is tried at the next look.
- Known limits: stock's report marks an account limited while any of its windows is exhausted (`usageResetAtMs` over every limit, not the model's own), so without a `retry-after-ms` a short limit on an account whose other model's weekly window is spent waits for that window; stock trusts a model's own weekly row only at full exhaustion (`usage/claude.ts`), so a row that reads short of it makes each look a try.
- Pinned by `turn-resume-limit.test.ts`, `turn-resume-ends.test.ts` ("an armed limit wait"), `shared/quota-reset.test.ts`, `quota-reset-stock.test.ts`, `remote/host-services.test.ts` ("a hosted tab's wait for a provider's limit"), `TurnErrorNotice.test.tsx`, `e2e/usage-resume.e2e.ts`, `e2e/scheduled-retry.e2e.ts`, `e2e/remote-resume.e2e.ts`; model: formal/turn-resume's armed retry (`SCOPE.md` › The limit wait).

### Close to tray
- Closing the last shown window hides it instead of ending the app (`lastWindowCloseAction` in `quit-guard.ts`, the `close` handler in `window.ts`, pref `closeToTray`, default **on**: only an explicit `false` keeps the Windows quit, via `closeToTrayEnabled`).

  - macOS hides regardless of the pref (it has no Settings row): window, tabs and omp keep running; `app.on("activate")` shows the same hidden window (spawns one only if none exists).
  - **After `quitApproved()` nothing rebuilds a window**: `activate` (`activateAction`, `quit-guard.ts`) and every `spawnWindow`/`spawnWindowWithLayout` path (tray, menu, deep link, second instance) do nothing, and the saved desktop session is never rewritten (`layoutsToSave`, `saved-layouts.ts`, used by `persistTabLayouts` for both the tab-change and the window-closed hook; the web layouts and the resume markers are frozen too), because the teardown closes tabs and windows one by one and a stalled quit would otherwise save the session smaller or rebuild it on disposed services. A window the user closes before any quit still leaves the saved set. Pinned by `quit-guard.test.ts`, `saved-layouts.test.ts`.
  - A non-last window closes as before and ends its tabs: hiding it would leave no Dock or tray way back.
  - A hidden window stays in `getAllWindows()`, so tab inventory, notifications (a click shows it), keep-awake, badge and tray counts keep working.
  - Real quits (menu, ⌘Q, tray, logout/update restart) still go through the quit guard; once `quitApproved()` every window closes.

### Keep awake, lid closed while charging
- The user's rule: closing the lid of a laptop that is charging never stops OMPdesk's running work; on battery the OS sleeps on a lid close as usual. No setting of its own: it is part of General's one "Keep this computer awake while it is used" (pref `keepAwakeWhileWorking`, `KEEP_AWAKE_WORKING_PREF`, default **on**: only a stored `false` turns it off), which covers both the work blocker and the host role's (devices connected or running a session here). The host's old `remote.keepAwake` is merged into it once (`MERGES` in `retired-prefs.ts`) and retired: a choice the person stored decides (a stored host `true` turns a stored-off work switch on), and a work switch stored off beside a host switch never touched stays off, because the old key is deleted after the merge and a later launch could not tell that state from a person turning the one switch off; Devices & connections shows only a "Keeping awake now" row while devices hold it.
- Electron's `powerSaveBlocker` `prevent-app-suspension` (`KeepAwakePolicy`, `remote/keep-awake.ts`) is an idle-sleep assertion a lid close ignores. So `LidAwake` (`src/main/power/lid-awake.ts`, pure, injected backend) wraps both keep-awake blockers (`wrap(blocker, "work" | "host")` in `index.ts`) and, while any is held, holds a platform `LidBackend` as long as the computer is a laptop (has a battery, asked once) on AC (`powerMonitor.isOnBatteryPower()` at start, `on-ac`/`on-battery` flip it at once). It converges one step at a time, logs one `gui-runtime.jsonl` line per change (source `keep-awake`: `held`/`released` with `reason` `work` | `charging` | `work-ended` | `on-battery` | `quit`, plus `skipped` no battery, `recovered`, `failed`), retries a failed step only on the next input change, and releases synchronously at quit (`lid-awake` teardown step). Never in a test launch (`OMP_GUI_HEADLESS=1`: a killed test app would leave the setting changed) or a second instance.
- **macOS** (`lid-backend-mac.ts`): stock `/usr/bin/caffeinate -s -w <main pid>`, a PreventSystemSleep assertion macOS honours on AC only (verified to keep a closed-lid Mac awake on AC); `-w` ends it with the app, so a crash holds nothing. No admin, no `pmset disablesleep`.
- **Windows** (`lid-backend-windows.ts`): the active scheme's AC "lid close action" (`SUB_BUTTONS`/`LIDACTION` by GUID) goes to 0 (do nothing) with `powercfg /setacvalueindex` + `/setactive SCHEME_CURRENT` (no admin), and back to the user's value when work stops. The DC (battery) value is never touched; a user who already chose "do nothing" is left alone; a value the user changed while it was held stays theirs. The original is written to `<userData>/lid-awake.json` before the change and put back at the next launch (`recover`), so a crash or kill is undone. `powercfg /query` labels are localized, so the AC value is the first of its two `0x` lines. A desktop (no `Win32_Battery`) does nothing.
- **A powercfg failure never loses the user's value**: the backend keeps the original (`#held` and the marker) until a restore succeeded, so a failed release is retried on the next change, at quit (`dispose` always asks the backend) or at the next launch; a hold made while a restore is still owed reuses that original instead of reading the 0 it left; a hold that fails after changing the value rolls itself back.
- Pinned by `power/lid-awake.test.ts` and `power/lid-backend-windows.test.ts` (fake powercfg, English and Korean output, crash recovery, injected failures); `e2e/desktop-tabs.e2e.ts` (default on: the blocker is held during a turn, the switch turns it off).

### One stop, one start at a time
- Why: many omps started at once can stall, stuck omps that outlive a quit stall the next launch, and a second omp on a tab whose first still runs breaks its session; OMPdesk must survive a stock stall.
- **One stop** (`stopOmp`, `src/main/omp-stop.ts`) for every path (tab close, restart, sleep, a revive, the quit): SIGTERM (Windows: its stdin ends), so stock journals `session_exit`; still running `STOP_GRACE_MS` (5 s) later, SIGKILL to its process group (every omp spawns `detached` on POSIX, `OMP_SPAWN_GROUP`; Windows keeps `taskkill /T /F`). **An omp that says it waits to save is not killed meanwhile**: stock's exit writes "<what it waits for> (up to N s)…" to stderr when it holds on one thing (`EXIT_HOLD`; the login refresh, up to 125 s, because the provider already swapped the refresh token and a kill before the save leaves a spent token in the store every omp shares, so the account drops off the list at its next refresh), and the kill then waits for the time named plus 2 s, at most `STOP_HOLD_MAX_MS` (130 s) from the stop; each chunk is searched together with the unread end kept from before (bounded only after the search), because the pipe may cut the line anywhere or bury it in other output, and the longest wait printed counts (`omp-stop.test.ts`). **An omp that ends because its stdin closed waits for that save too** (`resources/gui-bridge/exit-drain.ts`, `exit-drain-core.ts`): stock ends such an omp with `process.exit` right after it disposed the session (rpc-mode.ts `disposeAndExit`) and does not await the cleanup pass the `exit` event starts, so the save was dropped on every stop that closes stdin (Windows, and everywhere with the ai-memory grace) while a signal's exit awaited it. The main agent's `session_shutdown` therefore replaces `process.exit` with one that runs stock's awaited pass first (`postmortem.quit`, then `postmortem.exitProcess`); the pass then prints the same line, which holds the kill. An idle omp ends as fast as before (measured, 3 runs each: 44 to 76 ms with it, 40 to 83 ms without). Pinned by `bridge-exit-drain.test.ts` and, on the installed omp, `bridge-exit-drain-stock.test.ts` (a cleanup shaped as the refresh's is finished and announced; without the hook the omp ended 36 ms after its stdin closed and the save never ran). The quit's own bound (the app then exits and the omp finishes alone) and a later launch's reap of a leftover pid (`stopOmpPid`, which sees no stderr) do not wait for it. It resolves only once the process exited (or 2 s after the kill) and is shared by every caller of the same child. The ai-memory grace (`gracefulStopMs`) is its `stdinGraceMs`: stdin first, then the same steps.
- **A replacement waits for its predecessor**: `SidecarManager` keeps the exits of the omps it stopped (`#exiting`), and `#spawn` starts the next only once all of them exited; `whenExited()` covers them too.
- **One start queue** (`OmpStartQueue`, `src/main/omp-start-queue.ts`, one per app, handed to every local `SidecarManager` by `sidecar-factory.ts`): at most `OMP_STARTS_AT_ONCE` (2) omps starting; a place goes to the next start once the omp answered, ended or was stopped, after `START_SLOT_CAP_MS` (15 s), or once the omp is slow (`START_SLOW_MS`). A tab that waits for a place, for the launch's reap (`holdUntil`) or for its previous omp to exit reads `starting` with `queued: true` (`acquire(onWait)`, `#spawn`), shown as "Waiting to start" on the title bar's status in every view (the session summary's `queued`, read by `session-run.ts`) and passed over the link (`TabStatusArg.statusPayload.queued`); no deadline: it starts when its place comes.
- **A tab reads `ready` only once its omp answered** (`#answered`: stock `get_state` after `ready` and the protocol negotiation, before the start gate; no deadline, `RpcClient.stock(…, Number.POSITIVE_INFINITY)`). Until then it reads `starting`. **A live omp is never stopped or failed for being slow** (the owner's rule: a limit that stalls work is worse than what it guards).
  - Past `START_SLOW_MS` (20 s) without an answer (`#startIsSlow`) its start-queue place goes to the next tab, and an `omp-slow-start` runtime-log line keeps its stderr tail, its own log's tail (`ompLog`: `ompLogTail`, `src/main/omp-log-tail.ts`, the last 8 lines of stock's `<logs>/omp.<local day>.<pid>.log`, compacted), `ready` (omp printed `ready`, so it is past its startup; stock's startup watchdog prints "Still starting after Ns" to stderr every 10 s only before that) and `unanswered` (`RpcClient.unanswered()`: the stock commands it holds, oldest first).
  - The tab reads `starting` with `slow: true` and `message` = the stderr tail, or the log tail when stderr is empty, re-sent as stderr grows (`SidecarStatusPayload.slow`; pool `startWait` → `IpcTabInfo.slow`; over the link `TabStatusArg.statusPayload.slow`; a slow or queued re-send keeps the host tab's `omp` id and the page's state). Every view (this window, a paired computer, the phone) shows the amber `SidecarBanner` "omp is taking long to start" with the tail and Restart; Restart is the person's call, and `error` comes only from the omp exiting or failing to spawn.
  - A paired computer has no start deadline of its own (`.omp/rules/remote-devices.md` › A host tab never waits silently), and an agent's `ompdesk_session_open` waits for a starting child however long (`#whenReady`: only closed, exited or a non-held `error` fail it). `OMP_GUI_START_SLOW_MS` shortens the bound for e2e. There is no ready-time health check. `dispatchRpcCommand` (`ipc.ts`) waits for a tab that reads `starting` or `restarting` (`START_WAIT_MS`, 60 s) instead of answering `sidecar_not_ready`; the omp is not stopped when that wait ends.
- **A hung network does not hold the first answer**: stock defers MCP, model discovery (`refreshInBackground`), credential usage (`prefetchCredentialUsage`) and connection prewarm past the `get_state` answer, and OMPdesk's extensions do nothing on the network at `session_start` (verified with every outbound request hung, proxies, a black-holed route, a hung project MCP server and a cold models cache). Find the next slow start's cause from its `omp-slow-start` line, not from network errors of the same minutes.
- **The quit waits for every omp** (`OmpProcesses`, `src/main/omp-processes.ts`; `installQuitGuard`'s `ompsExited`): `will-quit` is held (every `will-quit` listener, the relaunch swap included, has run by then) until `stopAll()` saw every omp exit and the core took each exit out of the file, or `QUIT_OMP_STOP_MS` (12 s: the longest one stop, ai-memory's stdin grace included) passed, then `app.exit(0)`. An update's relaunch quits the same way. The stop of each omp and the wait stay main's (`stopOmp`): they need the child process it spawned, for the stdin whose end asks an omp on Windows and the stderr on which an omp asks to be left to save a login. The teardown has stopped the core by then; an exit told afterwards starts it again (the memory watch's next reading does the same), and it ends with the app.
- **A launch reaps what an earlier one left** (a crash, a forced quit): the core (`native/ompdesk/crates/core/src/omp`, native-rust › 5a) keeps every running omp named in `<userData>/omp-pids.json` (`{omps: [{pid, started?}]}`, 0600; `omp.track` at each spawn and `omp.exited` at each exit rewrite it, requests nothing awaits), and `reapLeftovers()` (`omp.reap`) stops every listed omp that is still this app's, with what it started.
  - POSIX: the pid's command line holds this app's gui-bridge path, read again before each signal; SIGTERM, `STOP_GRACE_MS`, SIGKILL to its group.
  - Windows: the recorded pid is the shim omp runs behind (`omp.cmd`, bun's `omp.exe`), told by its creation time (`GetProcessTimes` in ms equals `started` exactly, because Windows reuses a freed pid within a fraction of a second and a slack would kill another program; read by the core when the spawn is recorded: no PowerShell, no WMI, no retries). Windows ends the shim with the app, however the app ended (node keeps its children in a job closed with it), and the real omp runs on (measured on the built app, 12 Nov 2026: 16 of 16 kills). So when the recorded process is gone the reap looks for what it left: a process whose parent id is the recorded pid, started no earlier than the shim, that no later holder of the pid started, and whose command line holds this app's gui-bridge path. Its stdin ended with the app, so it gets `STOP_GRACE_MS` to end by itself and is then ended with its tree through handles opened on those processes (no `taskkill`). A shim that still runs is ended at once with its tree. An entry with no `started` (a file an older OMPdesk wrote, a process the core could not read) is left running.
  - An entry leaves the file when its pid is gone and it left nothing, is another program's, or what was stopped for it is gone; one that cannot be told, or whose stop something survived, stays for the next launch. The start queue holds every start until the reap is over (`holdUntil`), at most 15 s when the core does not answer (logged as a warning); a reap that stopped something writes an `omp-reap` line. A session the launch does not bring back has its processes ended by the session sweep as well (control-tools › Session processes), whichever comes first; only the reap ends the stuck omp of a session that does come back.
  - A leftover that was still saving a login when the app quit past its bound (`STOP_HOLD_MAX_MS`) is ended by a launch within that time, on every system: the dead app's stderr, where the omp asked to be left, is gone.
- Pinned by `sidecar.test.ts` ("one stop, one start at a time": SIGTERM ignored → killed at the bound; replacement after predecessor's exit; queue limit; a slow omp is never stopped or failed, gives its place away and reads ready once it answers; empty stderr shows its own log and logs `ready` and `unanswered`), `omp-log-tail.test.ts`, `sidecar-pool.test.ts`, `remote/remote-sidecar.test.ts`, `stores/tabs.test.tsx` and `SidecarBanner.test.tsx` (the slow start reaches every banner as a wait), the `session-slow-start` parity surface, `omp-processes.test.ts` (a quit's stop leaves none; a launch reaps its leftover and spares another program) and `app-quit.test.ts` (the exit waits in `will-quit`). ### Watchdogs
- **Quit watchdog** (`src/main/quit-watchdog.ts`, electron-free, injected clock/log/exit; wired in `app-quit.ts`): once a quit is committed (`before-quit` lets the teardown run, after `finalize`, which may still be asking the user; or `before-quit-for-update` fires) the process force-exits (`app.exit(0)`, a runtime-log line `source: "background-task"`, `details.watchdog: "quit"`) if still alive after `QUIT_EXIT_TIMEOUT_MS` (30 s), because a wedged teardown otherwise strands the updater's swap helper or installer waiting for this pid. `app.exit` skips `will-quit`, so the relaunch swap registers `onQuitForcedExit` and starts through one once-only call (`updater.ts` `launchStagedSwap`). A failed `quitAndInstall()` (autoUpdater `error`) disarms the update countdown (`disarmQuitWatchdog("update")`). Idea: Orca's `update-install-exit-watchdog.ts` (MIT), reimplemented. Pinned by `quit-watchdog.test.ts`.
- **Main-thread hang watchdog** (`src/main/hang-watchdog.ts` wiring, `hang-watchdog-core.ts` pure rules, `hang-watchdog-worker.ts` the worker, its own `electron.vite.config.ts` main input `out/main/hang-watchdog-worker.js`; wired in `index.ts` right after `app-ready`; packaged builds or `OMP_GUI_HANG_WATCHDOG=1`, never under vitest or in a second instance): main posts a heartbeat to an in-process, unref'd `worker_threads` Worker every `HANG_HEARTBEAT_INTERVAL_MS` (1 s); the worker checks every `HANG_CHECK_INTERVAL_MS` (1 s) and records a stall after more than `HANG_TIMEOUT_MS` (5 s) without a heartbeat, in `<userData>/logs/main-thread-hang.json` ({detectedAt, pid, unresponsiveMs, selfRecovered, phase, steps}), rewritten with `selfRecovered: true` when heartbeats resume (`detectedAt` is then the moment main answered again, so the stall began `unresponsiveMs` earlier). A tick gap over `SLEEP_GAP_FACTOR` (3×) is a system suspend, not a hang (the wait restarts); `powerMonitor` `resume` resets it too. **Observation only**: nothing kills or restarts main. `markMainStep(phase, step)` names what main is about to run (startup marks, quit teardown steps, the update's quit); the worker keeps the last `HANG_STEP_HISTORY` (8). The next launch consumes the marker and writes one `gui-runtime.jsonl` line (`source: "main-thread-hang"`, `details` {unresponsiveMs, selfRecovered, detectedAt, previousPid, phase, steps}); `steps` is text, oldest first joined with ` > `, because the runtime log keeps only primitive details and drops an array. Idea: Orca's hang watchdog (MIT), reimplemented. Pinned by `hang-watchdog-core.test.ts` and `hang-watchdog.test.ts`.
- **GPU fallback and crash-loop guard**: `src/main/gpu-fallback.ts` relaunches into software rendering after a GPU process crash (`gpu-fallback.json` marker, read before ready), but **never from a launch that already renders in software** (marker, `--disable-gpu`, safe mode), **never from a test launch** (`OMP_GUI_HEADLESS=1`: the relaunched app would run on unwatched; Chromium restarts the GPU process itself, logged `no relaunch (test-launch)`) and at most once per `GPU_RELAUNCH_COOLDOWN_MS` (10 min) across processes, because with hardware acceleration off Chromium still runs and restarts a GPU process itself, and a per-process guard let each software launch relaunch forever.
  - Rules in `launch-guard-core.ts` (`gpuRelaunchDecision`, `crashLoopDetected`), history in `launch-guard.ts` (`<userData>/launch-history.json`, newest 10). Every launch holding the instance lock is recorded before ready and marked stable after `STABLE_AFTER_MS` (20 s) or a clean quit (`will-quit`); a crash, a kill or the GPU relaunch's `app.exit` leave it unstable. When the last `CRASH_LOOP_LAUNCHES` (3) were all unstable within 10 minutes, the launch starts in **safe mode**: software rendering whatever the switches say, no automatic GPU relaunch, machine setup and memory setup paused (`automatic: false`; Retry still installs), one `gui-runtime.jsonl` line `source: "launch-guard"`. Packaged runs outside `OMP_GUI_HEADLESS=1` only (a dev run restarts main on every edit, e2e kills apps on purpose); `OMP_GUI_LAUNCH_GUARD=1` forces it.
  - **A crash in a settled launch is Chromium's to recover**: `gpuRelaunchDecision` answers `settled` for the first crash of a hardware launch up `GPU_CRASH_SETTLED_MS` (5 min): no marker, no relaunch, one `gpu-fallback` line ("Chromium restarts it, hardware acceleration stays"), hardware on the next launch too. A second crash within `GPU_RELAUNCH_COOLDOWN_MS` of it takes the marker path. Markers carry `policy` (`MARKER_POLICY` 2); one without it came from a build that wrote a marker for every crash, so the next launch tries hardware once (`trial: "policy"`). Pinned by `gpu-fallback-loop.test.ts` "a crash in a launch that has run for a while".
  - **Hardware comes back by itself** (`gpu-fallback-core.ts`): the marker records the GPU the crash happened on (`app.getGPUInfo("basic")`'s active adapter: vendor and device ids, driver version and date; `complete` names SwiftShader in a software launch, `basic` the real adapter), a software launch records the GPU it sees (`seen`), and a launch under the marker tries hardware once when the GPU or its driver changed or `HARDWARE_RETRY_AFTER_MS` (7 days) passed since the crash or the last trial. The trial is written into the marker before it runs (`markerForTrial`: `trialAt`, the tried GPU becomes the crash GPU), so it happens once; after 20 s without a GPU crash it clears the marker (`confirmHardwareTrial`); a crash in it writes a fresh marker and relaunches only within the 10-minute cap. Each step is a `gpu-fallback` log line. `--enable-gpu` still clears the marker by hand.
  - Pinned by `gpu-fallback-loop.test.ts`, `launch-guard.test.ts` and ci.yml's `installer_check` (`windows-installer-check.ps1` `Assert-StaysUp`: one main process for 60 s, no relaunch or safe mode in the log; `Assert-NoGpuRelaunchLoop`: a GPU process ended with 0xC0000005 relaunches a hardware launch once, and the software launch survives further GPU crashes).
- **omp ended by the Windows session is no crash**: logoff and shutdown end omp's tree with DBG_TERMINATE_PROCESS (`WINDOWS_SESSION_END_EXIT_CODE` 0x40010004, `restart-policy.ts`) while main lives on for seconds. `SidecarManager`'s `exit` handler treats that code like exit 0: status `exited` ("The Windows session ended"), no `restarting` banner, no `reportFailure`, no respawn (a respawn fails with the session gone). The status carries `sessionEnded: true` and nothing else about the turn changes: `SidecarPool` and `LocalHostServices` skip their "a non-ready status ends the run and its asks" reset for it, so `TurnResume.sync()` keeps the cut-off turn's marker for the reboot. A marker already in `interrupted-turns.json` stays, as after a killed main. The exit code is the signal, not BrowserWindow's `query-session-end`/`session-end` (only while a window exists, unordered against omp's death) or `powerMonitor` `shutdown` (linux/darwin only). `taskkill /f` (`terminate`) ends a process with 1 and a POSIX exit code is ≤ 255, so a user kill or a real crash still restarts. Pinned by `sidecar-os-shutdown.test.ts`, and in `sidecar-pool.test.ts` and `remote/host-services.test.ts` (resume facts keep the running turn and its ask after that status, and lose them after `restarting`). The stats server (`stats-server.ts`) shares the ladder and does not check the code.
- **Settle diagnostic** (`src/main/settle-watch.ts`, installed on the pool by `index.ts`; log only, changes nothing): a local tab whose turn ended but that still reads running (settling: stock reported background work, no `session_settled` since) for `SETTLE_DIAGNOSTIC_MS` (60 s) writes one `gui-runtime.jsonl` line (source `settle-watch`, "still settling") with stock's `get_state` (`isSettled`, `isStreaming`, `isCompacting`, `queuedMessageCount`, `hasPendingAsyncWork`, queue lengths, `messageCount`), main's run flags and the last `prompt_result`/`session_settled` main applied with its age, so a stuck settle tells stock unsettled apart from a settle frame main missed. Pinned by `settle-watch.test.ts`.
- **A refused todo call no longer leaves a turn running** (`resources/gui-bridge/todo-reminder.ts`, rule `todo-reminder-core.ts`, capability `todoReminder`): stock answers a refused `todo` call with a hidden `todo-error-reminder` sent `deliverAs: "nextTurn"`; during a turn it waits for the next explicit prompt and its count keeps `isRpcSessionSettled` false, so `session_settled` never comes. The bridge wraps the session class's `sendCustomMessage` once and sends only that reminder, only while a turn streams and never one with `triggerTurn`, as stock's `aside`: the model reads it at the next step of the same turn and the session settles when it ends.
