## Interrupted work, quit and diagnostics

### Interrupted turns continue by themselves
- `src/main/turn-resume.ts`, `src/main/connectivity.ts`. Settings › General › Continue interrupted work after relaunch, pref `resumeInterrupted`, **default on** (main reads `!== false`).
- **Two paths, one coordinator (`TurnResume`), driven by `SidecarPool.onRunningChange` (`resumeFacts()`).**
- **① Relaunch.** Eligibility is a marker file `<userData>/interrupted-turns.json` ({window, tab, peer, sessionPath, cwd, kind, startedAt, reason}) rewritten atomically on every run-state transition. NEVER write it in a quit hook: SIGKILL/crash runs none. On Windows the rename over the file fails (`EPERM`) while any process has it open for reading (a poll, a virus scan, a backup), and a running turn has no later transition that writes it again: `InterruptedTurnStore` writes through `writeFileAtomicDeferred` (one attempt now, the retries on a timer) and logs `markers not saved` (source `turn-resume`) only when every try failed. Measured: a second process reading the file in a loop failed 2918 of 4000 renames in a bare Node loop, and 11 of 16 e2e runs lost the `running` marker (0 of 16 with the retry).
  - Present while a turn runs (`running`); cleared on normal completion and on the user's Stop (`SidecarPool.noteStopped`, called by the RPC dispatcher for `STOP_COMMANDS` `abort`/`abort_and_prompt`/`abort_and_restore_queue`, so a kill before the run's end event leaves none); kept as `asking` while blocked on an ask/approval (the relaunch re-runs the cut-off call, the card reopens; not "continuing"). An omp that exits or restarts takes its open asks with it (the pool forgets owners on any non-ready status).
  - A quit (`quitApproved()`) freezes writes: tearing tabs down must not read as turns ending. Closing the last shown window on Windows with close-to-tray off is such a quit, asked for before the window goes (`lastWindowCloseAction`, `quit-guard.ts`).
  - A marker whose session the user deleted (`deletedSessions()` tombstone) is dropped at launch, never continued, not even into a fresh tab. A never-written session has no tombstone and still continues.
  - `TurnResume.launch()` (after saved windows exist): each marker finds its tab by session path (deferred tab: `SidecarPool.startTab`; missing from the layout: opened) and continues through stock: `restore_interrupted` (local handler → bridge `composer.restore_interrupted` → stock `restoreSession`, what `omp --restore` runs) for a cut-off turn, `retry` (`/retry`, the quota-resume path) for a failed one. A killed OMPdesk's omp usually closes the turn itself on stdin EOF (pending ask fails "RPC client disconnected before extension UI response completed", run journaled aborted), so `restoreSession` finds nothing; the relaunch then runs stock `retry`, which replays the failed tool batch or aborted reply and does nothing for a turn that really ended.
  - **A turn cut before its next model call** (v0.41.0 update restart: `restored: nothing, retried: false`): stock records a closed stdin as a `normal` `session_exit` with `pendingToolCalls` only while a tool runs, and the abort record that would follow never reaches the journal when the cut lands before the model call (the agent loop stops there with no message) or omp's graceful EPIPE quit ends the process first. Stock's `findUnfinishedTurn` then reads the turn as ended and `/retry` finds no failed reply. The bridge's restore (only ever called for a marker of a running turn) checks `requestCutAtExit` (`restart-core.ts`: the replaced process's clean exit record, nothing after it, a prompt or tool result before it that nothing answered) and appends stock's own interrupted-turn record (`session/exit-diagnostics` `createInterruptedTurnAbortMessage` over the branch without that exit) before stock `restoreSession`, which then continues from the recorded tail: no tool reruns, no prompt sent twice. A prompt stock journals only as its process ends lands after the exit record and needs nothing. Pinned by `bridge-restart.test.ts`, `src/main/bridge-restore-request-stock.test.ts` (installed omp: a `context` handler holds the request preparation) and `e2e/interrupted-resume.e2e.ts` (the fake omp records stock's exit record on stdin EOF).
  - **An aborted turn with a note after it** (v0.48.0 → v0.49.0 update restart, 21 Oct 2026: two running sessions logged `restored: nothing, retried: false, journal "assistant/aborted, …"` and sat idle): the quit aborted them mid-tool and stock journaled the aborted result and reply, then a custom message landed after the reply (a report the bridge handed the session once the abort left it idle; a follow-up stock had queued since an earlier relaunch, journaled at the abort with its old timestamp). Stock's `retry` reads the conversation's end past eval snapshots only (`turn-recovery.ts` `conversationEnd`), so the note hid the aborted reply. The bridge's restore (`turnCutBehindNotes` in `restart-core.ts`: last message an aborted or failed reply of the replaced process, a non-eval custom message after it, nothing typed since) continues it with the relaunch's one follow-up (`ompdesk-restart-turn`, or folded into the jobs/subagents one; details `turn: true`; the transcript's muted line "Continuing the work the restart cut off", `data-restart-turn`) and reports `followUp`/`turnCut`; `TurnResume` counts `followUp` as continuing and sends no `retry` on top (log `restored: "turn-behind-notes"`). It reads the journal only, so state v0.49.0 wrote at its quit is continued too. Pinned by `bridge-restart.test.ts`, `turn-resume.test.ts`, `MessageBubble.test.tsx` and the note case of `bridge-restore-request-stock.test.ts` (installed omp: a bash cut by the quit, an `ompdesk.mail` line appended as v0.49.0 wrote it, the relaunch continues).
  - A continuation waits for its tab's omp (`RESUME_READY_TIMEOUT_MS`, 5 min; an omp that already failed drops the marker at once). The resuming row's Stop, the waiting row's Cancel and a new prompt on a held tab call it off even during the wait (a per-tab generation checked before every command).
  - `restore_interrupted` and `retry` get `RESUME_COMMAND_TIMEOUT_MS` (2 min), not the RPC client's 8 s default: stock's restore reads every subagent transcript first (v0.37.0, 577 transcripts: reply cut, logged `failed`, stock kept reviving).
  - No toast: each resuming tab shows its own calm row ("Continuing where it left off…", `data-resuming`, one per tab, `setResuming` → tab `resuming` → `TurnStatusRow`; not for a reopened card) with the Stop on it (`resume.stop(tabId)` → `TurnResume.stopResumed(tabId)`: that tab only, noted as the user's Stop so its marker goes and Autopilot's goal resume ends `cancelled`). The only resume indicator.
  - Rank order: focused tab, other panes of its split, then background tabs (`ResumePool.resumeRank` ← `SidecarPool.resumeRank`).
  - Setting on: a quit (⌘Q, tray, last window on Windows) and "Restart to update" ask nothing (`quitNeedsConfirmation(risk, resumes)` in `quit-guard.ts`, `confirmQuit()` in `app-quit.ts`, the updater's `UPDATER_APPLY`); off, they ask before stopping running work.
- **One conversation stays one session across a relaunch**: a tab whose session file exists starts on it (`--session`), the continuation answers into that file, the sidebar lists it once. A start on a stored session first waits (up to `SESSION_FREE_WAIT_MS`, 60 s) until no other live omp holds stock's ownership lease on it (asked every 250 ms for 5 s, then every 2 s) (stock helper `sessions.owned`, `tryAcquireSessionLease` keyed by the header's id, read past stock's title slot with `parseTitleSlotFromContent` as stock's own `readSessionHeaderIdSync` does; `src/main/session-free.ts`, SidecarOptions `sessionFree`), since an omp that opens a session owned elsewhere moves it to a new file (stock `"open-elsewhere"`): on 23 Oct 2026 an update's relaunch opened this repository's Autopilot run while the last launch's omp still held it, and the run went on in a second file. Still owned when the wait runs out (an omp the person runs in a terminal), the start opens nothing: the tab is `error` with `omp.sessionOwned` ("still open in another omp … Close the other one: it opens here by itself then, or press Restart") and Restart waits again (the tab also keeps waiting by itself and opens the session the moment the owner lets go: `#whenSessionLetGo`; its status carries `sessionHeld`, which the pane's `SidecarBanner`, the title bar's status (`titlebar.status.sessionHeld`, the hollow pending dot), the tray (`trayStatusOf`: not an error), and through `IpcTabInfo.sessionHeld` every other window's sidebar row (`tabSignalPresentation`), split pane header (a spinner, not the failure mark), an opener's child row, the Work tree (`work-tree.ts`) and, through `IpcHostedSession.sessionHeld`, the host's own row of a session a paired device runs there show as a wait (warning, "Waiting for the session", `sidecar.heldTitle`), never as a failure (a paired device's pane too: `TabStatusArg.statusPayload.sessionHeld`, kept by `RemoteSidecar`), and so a relaunch's continuation keeps waiting for that `ready` (`whenReady` in `turn-resume.ts`, up to `RESUME_READY_TIMEOUT_MS`) instead of dropping the cut-off turn; pinned by `turn-resume.test.ts`); the lease is an OS lock, so a dead owner never holds it, and a helper that cannot tell lets the start go on (the two stock internals are the `sessionOwner` feature in `capabilities.ts` and `health.ts` `LOADERS`, so an omp that lacks one is reported like any missing internal). A wait over 1 s, or one that runs out, is a `session-owner` line in `gui-runtime.jsonl`. Pinned by `session-free.test.ts`, `session-free-stock.test.ts` (installed omp: a titled journal stock wrote, owned while another process holds the lease, free once it is gone) and the two start cases of `sidecar.test.ts` (no omp before the owner lets go; none while it keeps the session, then the session opened by itself once it lets go). Pinned by `e2e/interrupted-resume.e2e.ts` (no second file, one indexed row, after kill and normal quit), `e2e/real-update-restart.e2e.ts` (a)/(a2) and the SIGKILL test of `e2e/real-resume.e2e.ts`. Two rows once seen in the README resume clip were the fake omp writing a second journal (see the fake omp under Build, test), never OMPdesk.
- **The host owns the turns it runs for a paired device.**
  - On the device (A) a remote tab (`device`) is skipped entirely: no marker, no judging, no takeover by A's connectivity.
  - On the host (B) `index.ts` composes `TurnResume`'s pool from `SidecarPool` and `LocalHostServices` (`resumeFacts`/`startTab`/`setAwaitingConnection`/`noteStopped`/`tabForSession`, ids `peer:<deviceId>:<rtab>` kept when re-keyed; run bookkeeping via `trackRunEvent` in `sidecar-run-state.ts`; asks from the tab's `extensionUi` and the device's `extension_ui_response`; the device's Stop through `tab.command`). B writes the marker (with `peer`), continues after its own crash or quit (the marker revives the hosted tab, unstarted, waiting for its device in the grace period: `RemoteDevices.reviveHostTab`, only while hosting is on) and judges network failure by B's connectivity.
  - Grace (`HOST_TAB_GRACE_MS`, 10 min from link loss, `LocalHostServices.#startGrace`) closes only an idle hosted tab; one that runs out while the tab runs a turn (revived included) or holds it for B's connection starts another. A turn blocked on an ask waiting for the device keeps its omp until the device answers or B quits; no overall cap.
  - A only mirrors the wait (`awaitingConnection` tab event, emitted ahead of the failing events and re-sent on every `tab.open`; "Waiting for {device}'s internet connection…") and sends its Cancel to B (`RemoteSidecar.cancelHostWait` → `tab.cancelWait`).
  - A relaunched device reopens tabs under new rtabs: `tab.open` with a session path takes over the tab an earlier connection left (`#adopt`), so no second omp starts on the session.
  - **A device's quit leaves its host tabs running** (v0.46.0's update restart journaled the host's turn `aborted` 146 ms after the swap helper started: every disposed `RemoteSidecar` sent `tab.close`). During an approved quit with Continue interrupted work on, `RemoteSidecar.dispose` sends no `tab.close` and defers none (`keepOnHost`, `RemoteDevicesDeps.keepHostTabsOnQuit` = `quitApproved()` and the pref, wired in `index.ts`), so B keeps the tab through its grace and the relaunch adopts it. With the setting off the quit dialog counted those turns and promised to stop them, so they close as before; a user's own tab close always closes. Pinned by `remote-sidecar.test.ts` and the quit test of `e2e/remote-resume.e2e.ts`.
  - **A device whose saved layout lost a running host tab gets it back** (21 Oct 2026, the v0.48.0 → v0.49.0 update restart: the first quit tore the services down and stalled, a Dock click restored the layout again on a disposed `RemoteDevices`, the host's tab got no tab there, and the layout rewrite without it was what the relaunch read; the host's turn sat in its grace until reopened by hand). Every time a host's link comes up (`RemoteDevices.onHostOnline`) the device sends the request `tabs.kept` (`KEPT_TABS_METHOD`, `app-protocol.ts`). The host's `LocalHostServices.#keptTabs` answers, for the asking device, the tabs in their grace period (no live connection) with a session file that run a turn, settle (background work), wait on an ask, or are held for the host's connection (`state`: `running` | `settling` | `asking` | `waiting`), each with `rtab`, `formerRtabs` (the rtabs it had before an adoption re-keyed it, `HostTab.formerRtabs`, ≤ `MAX_FORMER_TAB_IDS`), `sessionPath`, `cwd`, `kind`, `title`. An idle grace tab is left to its grace. `readoptHostTabs` (`remote/readopt.ts`) leaves a session a local tab already holds to that tab (`SidecarPool.sessionOwner`, which a deferred layout tab holds too; next bullet) and opens the rest in the front window through `SidecarPool.acquire(…, formerIds)` (wired in `index.ts`): the tab's omp is the host's own, adopted by session path (`#adopt`), and `[rtab, ...formerRtabs]` are its `former` ids, so an id an agent was given before the relaunch resolves (`ControlTab.formerIds`). One runtime-log line per tab, source `remote-tab`, message `readopt` {device, rtab, formerRtabs, session, state, tab}; `readopt-failed` {device, error} when the host's answer fails for any reason but being away. A host that answers `unsupported` opens nothing. **A v0.49.0 host is not covered**: none of its existing routes names the orphaned tab (`sessions.list` rows carry no live state and no rtab, `HOSTED_SESSIONS` goes only to the host's own windows, `tab.open` needs the path first), so a device updated before its host is protected only once the host updates too. Pinned by `host-services.test.ts` ("lists the working tabs a device's last connection left"), `readopt.test.ts`, `devices.test.ts` ("the tabs a host keeps for this device", the `unsupported` host), the former-ids case of `sidecar-pool.test.ts` and `e2e/remote-resume.e2e.ts` ("a host's running tab the saved layout lost").
  - **A host tab the saved layout kept comes back attached, not deferred.** The same `tabs.kept` answer starts the tab here that holds a kept session (`readoptHostTabs` → `holder`/`start` → `SidecarPool.startTab` on an `asleep` tab, whose `tab.open` adopts the host's tab; its `readopt` log line adds `held: true`). Before, a background host tab came back "not started" and attached only when shown, so the host's running turn was invisible on the device (the v0.49.0 → v0.50.0 restart of the same day). Pinned by `readopt.test.ts` and the background test of `e2e/remote-resume.e2e.ts`.
  - One session file = one host tab = one omp. An open of a file this connection shows under another rtab, or another device's tab holds, is refused `session_open_in_tab`; `#open` re-checks the holder after its awaits; a tab whose omp moves onto a file another host tab holds (`#dedupe`, on its `session` identity) stops the other (keeping one that runs a turn) and tells its device `exited` (`host-services.test.ts`, three fail-first cases).
  - A host's session closes and deletes like a local one: its sidebar row (`SidebarDevices.tsx`) has Close (the tab; session stays on the host) and Delete (confirm names the host, `remote.sidebar.deleteMessage`; tab closes first, then `sessions.delete` on the host), both behind the row's one ⋯ (`data-sidebar-row-menu`; an action sheet on touch) like a local row's. `#deleteSession` takes the host's own delete path (`session-mutations.ts` `deleteSession` with `LocalHostServices` as `deviceTabs`): every idle tab on the file closes (the asking device's own, including one left from an earlier connection; another device's, which hears `sessionDeleted` once the file is gone; a window's tab on the host, as closing a tab does), the omps are waited for, and it is refused (`session_running`) only while one of them runs a turn or compacts. Until 21 Oct 2026 a host window or another device holding the session idle refused it for good ("Session is open on the host"), and the device had no tab there to close (`host-services.test.ts`, `Sidebar.test.tsx`, the delete tests of `e2e/remote-resume.e2e.ts`: gone on the host and after both apps relaunch, and a session the host's own window holds; the touch ⋯ in `e2e/mobile-shell.e2e.ts`).
  - **The host's own delete closes the devices' tabs on the session** as another window's tab (`deleteSession`'s `deviceTabs`, `LocalHostServices.closeSessionTabs`): refused (`session_running`) only while one of them, or the window's own tab (`SidecarPool.sessionRunning`), runs a turn or compacts; otherwise their tabs end (`exited`, "closed on the host"), their omps exit, the file goes, and only then (the notice `closeSessionTabs` resolves to, run after the stored delete succeeded and the tombstone is written) each device hears the tab event `sessionDeleted` (its pool records the tombstone, drops the tab and its saved layout entry). A failed stored delete tells no device: a tombstone for a file still there would refuse it forever. An older device drops the event name and keeps an exited tab. A device viewing a window's session (`viewsWindow`) is told the same. A device off the link learns it at its next `tab.open` (`session_deleted`). Pinned by `session-mutations.test.ts`, `host-services.test.ts` and the host-delete test of `e2e/remote-resume.e2e.ts`.
  - **Stop and delete** (21 Oct 2026, the user's call: one action, no second confirmation). A delete a running turn refused, here (`Sidebar.tsx`: this window's tab, another window's, a paired device's tab this computer runs) or on a host (`SidebarDevices.tsx`), is a toast "This session is running…" with one action, "Stop and delete" / "멈추고 삭제" (`sidebar.stopAndDelete`). It calls `sessions:stop` (`window.omp.sessions.stop(path, device)`): main stops every turn on the file (`LocalHostServices.stopSessionTurns`: `SidecarPool.stopSession` for a window's tab in any window, and the device tabs it runs; with `device`, the host's `sessions.stop` does the same there) with `abort_and_restore_queue` (logged by `session-delete`), and answers once each of those runs has ended (the tab's `idle` activity / run events, never a timer; `session_running` after `STOP_SESSION_WAIT_MS` if one does not). Then the same delete runs again. Pinned by "Stop and delete" in `sidecar-pool.test.ts` and `host-services.test.ts`, `Sidebar.test.tsx` ("a delete refused because a turn runs offers Stop and delete") and the host-window delete test of `e2e/remote-resume.e2e.ts`. An older host has no `sessions.stop`: the action then fails with its message.
  - Every delete, here or asked by a device, writes one `gui-runtime.jsonl` line (source `session-delete`, `recordSessionDelete` in `session-mutations.ts`): `device` (the machine the file is on, `local`), `by` (the asking device), the file's name, and `deleted`, `refused` with the code or `failed` with the message.
- **② Connectivity.** `ConnectivityMonitor` (net.isOnline() sampled by edge, windows' `online`/`offline` via `resume.reportOnline`, `powerMonitor` suspend/resume with a DNS probe until the wake is real, then `RESUME_WINDOW_MS` = 60 s) decides `shouldWait()`. A turn ending in a network-class error (`isNetworkError`, subset of stock's retryable pattern) while `shouldWait()` holds is not failed: the tab shows `awaitingConnection` (`TurnStatusRow`'s "Waiting for the internet connection…", Cancel → `resume.cancelWait`; `TurnErrorNotice` hidden), keeps a `network` marker and runs stock `retry` once online. A new run on the held tab (a prompt sent meanwhile, not the taken-over retry saga still ending) replaces the wait.
- **Stock's own retry comes first.** A dropped connection (Bun's "The socket connection was closed unexpectedly before the response completed", which both patterns already match) starts stock's auto-retry saga; the saga is one run, so its failed attempts are live messages (`liveMessages`) until its terminal end. While it retries (`retryInfo`) the latest failure shows no card, only the status row's "Retrying (n/m)…" with its Stop (`TurnErrorNotice` reads the live tail for `latest` and `retried`); the card comes once stock gives up, with main's countdown. Why (20 Oct 2026, this Mac, a socket error at 21:35 KST; the Wi-Fi drops airportd logged came after, 21:37–21:45): stock had already scheduled its retry (omp log `agent.continue scheduled source automatic-retry`) while a red "Response failed" card with Try again sat beside the retry row; 4 s into the attempt an abort of the user-interrupt class (errorId `UserInterrupt`, which stock gives RPC `abort`/`abort_and_restore_queue`/`abort_and_prompt`) ended it, and a turn ended by a stop is never continued. Who sent that abort was not recorded anywhere; that the card prompted it is an inference (hence the stop log under Relaunch log). Other sessions that day rode the same drops out on stock's retries alone. The fake omp's `fixture socket drop` plays stock's saga (`auto_retry_start`, backoff, non-terminal `agent_end`, `agent_start`; `abort_retry` → "Retry cancelled"). Pinned by `TurnErrorNotice.test.tsx`, the socket tests of `e2e/scheduled-retry.e2e.ts` (online all along: no card during the saga, then main's countdown and the turn going on) and `e2e/interrupted-resume.e2e.ts` (offline: the wait takes the saga over).

### What a relaunch continues beyond the cut-off turn
Measured on the real omp by `e2e/real-update-restart.e2e.ts` (opt-in `OMP_GUI_REAL_WORK=1`; "Restart to update" = an approved quit while work runs).
- Stock: a foreground bash call is journaled "outcome unknown" and runs again; subagents (awaited or background) are revived by `restoreSession` (the parent gets the result, a waiting `wait` included, when stock continues its turn); an open ask/approval reopens.
- OMPdesk handles four things stock leaves behind:
  - **Background bash jobs** (`async: true`) started by the last process and never settled are named to the agent in one follow-up (`ompdesk-restart-jobs`; bridge `composer.restore_interrupted` → `resources/gui-bridge/restart-core.ts` `interruptedJobs`, reported as `jobs`). The model gets `restartFollowUp`'s text (each job `- <id>: <intent> — \`command\``, intent = the call's own `i` argument, then "start again only the jobs the work still needs, say nothing about the restart or this notice, carry on"). The transcript gets one muted line ("Re-running N background task(s) the restart stopped", `RestartNote`, `data-restart-jobs`, intents as hover title): `details` hold only job ids and intents, never a user bubble, never a raw command (a hidden `display: false` message left that to chance). Jobs are read from entries journaled before this process started, from after the second-to-last `session_exit`, never cut at a `session_exit` alone; a job an earlier relaunch already named counts as settled. Pinned on stock by the SIGKILL test of `bridge-autopilot-stock.test.ts` (no `session_exit` in its journal).
  - **Subagents revived for a session whose own turn did not go on**: same follow-up (next subsection).
  - **A goal active until the last process ended** (`goalActiveAtExit`: the last `mode_change` journaled before this process started, `performance.timeOrigin`, is `goal`; NEVER read it from a `session_exit`, which stock does not journal for SIGKILL/crash nor always when stdin closes mid-turn: omp 18.11.3 journaled only the aborted turn and an Autopilot run came back paused `app_closed`) that stock paused at startup comes back as `goalPausedByExit`. `TurnResume` resumes it once after the restore (`resumeGoal`, injectable; default local `set_goal` `resume`; `goalSettled` tells Autopilot `resumed`, `none` or `cancelled`).
  - **A new session's first turn cut off before stock wrote its file** (at the first assistant message): the pool keeps the prompt (`unsavedPrompt`, marker `prompt`) and the relaunch sends it again when restore and retry find nothing; it leaves the marker before sending, so once. The saved layout drops the missing path (`tab-layout.ts`), so the tab returns as a fresh session in the same folder and `TurnResume.launch` takes it for the marker (`#unwrittenSessionTab`: a local tab in the marker's folder with no session file, one per marker), never a hidden second one; only without such a tab does `openTab` open one. A spawn whose `--session` file does not exist starts fresh in its folder (`#spawn` in `sidecar.ts`, fresh-launch config so no older session auto-resumes; stock exits "Session not found" on it; also covers an omp restart of a never-used tab).
- Pinned by `turn-resume.test.ts`, `sidecar.test.ts`, `bridge-restart.test.ts` (intent, notice wording, details without a command), `MessageBubble.test.tsx` (muted line, not a bubble), `ChatStream.turn-status.test.tsx` (row's Stop), `quit-guard.test.ts`, `e2e/interrupted-resume.e2e.ts` (background-job relaunch: no toast, one resuming row, one muted line, no bubble, transcript at the bottom; idle session with a working background subagent: one muted subagents line and a turn; setting off: the quit asks, "Quit anyway" leaves no marker). Real omp (`(b2)`, 18 Oct 2026) records `ui` and `saidAfterNotice`: no restart narration from the model.

### Revived subagents
- **Seen**: the bridge's `composer.restore_interrupted` hands stock `restoreSession` the buses a live `task` run reports on (the task tool's `ToolSession` `eventBus`/`subagentEventBus`; TaskTool keeps it in a TS-private `session` field, `getToolByName("task")` in `capabilities.ts`), as `omp --restore` passes main.ts's own. Without them a revived subagent delivered its result but omp's RPC registry (`get_subagents`, the `subagent_*` frames the work board, dock and composer cue read) never heard of it (v0.35.1). Pinned by `src/main/bridge-restore-subagents-stock.test.ts` (installed omp, scripted loopback provider, no spend: a SIGKILL-cut background subagent is listed `running` after restore).
- **Told, when the session is idle**: if stock revived subagents but `turn` is false, the session would sit silent until an async result arrives (maybe hours). ### Keep awake, lid closed while charging
- The user's rule (21 Oct 2026): closing the lid of a laptop that is charging never stops OMPdesk's running work; on battery the OS sleeps on a lid close as usual. No setting of its own: it is part of "Keep this computer awake while working" (pref `keepAwakeWhileWorking`, `KEEP_AWAKE_WORKING_PREF`, default **on** since this change: only a stored `false` turns it off) and of the host role's `remote.keepAwake` (default on).
- Electron's `powerSaveBlocker` `prevent-app-suspension` (`KeepAwakePolicy`, `remote/keep-awake.ts`) is an idle-sleep assertion a lid close ignores. So `LidAwake` (`src/main/power/lid-awake.ts`, pure, injected backend) wraps both keep-awake blockers (`wrap(blocker, "work" | "host")` in `index.ts`) and, while any is held, holds a platform `LidBackend` as long as the computer is a laptop (has a battery, asked once) on AC (`powerMonitor.isOnBatteryPower()` at start, `on-ac`/`on-battery` flip it at once). It converges one step at a time, logs one `gui-runtime.jsonl` line per change (source `keep-awake`: `held`/`released` with `reason` `work` | `charging` | `work-ended` | `on-battery` | `quit`, plus `skipped` no battery, `recovered`, `failed`), retries a failed step only on the next input change, and releases synchronously at quit (`lid-awake` teardown step). Never in a test launch (`OMP_GUI_HEADLESS=1`: a killed test app would leave the setting changed) or a second instance.
- **macOS** (`lid-backend-mac.ts`): stock `/usr/bin/caffeinate -s -w <main pid>`, a PreventSystemSleep assertion macOS honours on AC only; `-w` ends it with the app, so a crash holds nothing. No admin, no `pmset disablesleep`. Measured on the user's MacBook (21 Oct 2026, AC 95 %, no external display): with only that assertion held, the lid closed at 07:32:37 local (`ioreg -r -k AppleClamshellState`: `AppleClamshellState = Yes`, `AppleClamshellCausesSleep = Yes`) and the Mac stayed awake: a 1 s ping to the router had no gap and lost nothing while closed, and the user kept talking to this Mac's session from a phone. On battery the same assertion is ignored and the lid sleeps the Mac as usual.
- **Windows** (`lid-backend-windows.ts`): the active scheme's AC "lid close action" (`SUB_BUTTONS`/`LIDACTION` by GUID) goes to 0 (do nothing) with `powercfg /setacvalueindex` + `/setactive SCHEME_CURRENT` (no admin), and back to the user's value when work stops. The DC (battery) value is never touched; a user who already chose "do nothing" is left alone; a value the user changed while it was held stays theirs. The original is written to `<userData>/lid-awake.json` before the change and put back at the next launch (`recover`), so a crash or kill is undone. `powercfg /query` labels are localized, so the AC value is the first of its two `0x` lines. A desktop (no `Win32_Battery`) does nothing.
- **A powercfg failure never loses the user's value**: the backend keeps the original (`#held` and the marker) until a restore succeeded, so a failed release is retried on the next change, at quit (`dispose` always asks the backend) or at the next launch; a hold made while a restore is still owed reuses that original instead of reading the 0 it left; a hold that fails after changing the value rolls itself back.
- Pinned by `power/lid-awake.test.ts` and `power/lid-backend-windows.test.ts` (fake powercfg, English and Korean output, crash recovery, injected failures after `setacvalueindex`, during rollback and during release); `e2e/desktop-tabs.e2e.ts` (default on: the blocker is held during a turn, the switch turns it off).

### Watchdogs
- **Quit watchdog** (`src/main/quit-watchdog.ts`, electron-free, injected clock/log/exit; wired in `app-quit.ts`): once a quit is committed (`before-quit` lets the teardown run, after `finalize`, which may still be asking the user; or `before-quit-for-update` fires) the process force-exits (`app.exit(0)`, a runtime-log line `source: "background-task"`, `details.watchdog: "quit"`) if still alive after `QUIT_EXIT_TIMEOUT_MS` (30 s), because a wedged teardown otherwise strands the updater's swap helper or installer waiting for this pid. `app.exit` skips `will-quit`, so the relaunch swap registers `onQuitForcedExit` and starts through one once-only call (`updater.ts` `launchStagedSwap`). A failed `quitAndInstall()` (autoUpdater `error`) disarms the update countdown (`disarmQuitWatchdog("update")`). Idea: Orca's `update-install-exit-watchdog.ts` (MIT), reimplemented. Pinned by `quit-watchdog.test.ts`.
- **Main-thread hang watchdog** (`src/main/hang-watchdog.ts` wiring, `hang-watchdog-core.ts` pure rules, `hang-watchdog-worker.ts` the worker, its own `electron.vite.config.ts` main input `out/main/hang-watchdog-worker.js`; wired in `index.ts` right after `app-ready`; packaged builds or `OMP_GUI_HANG_WATCHDOG=1`, never under vitest or in a second instance): main posts a heartbeat to an in-process, unref'd `worker_threads` Worker every `HANG_HEARTBEAT_INTERVAL_MS` (1 s); the worker checks every `HANG_CHECK_INTERVAL_MS` (1 s) and records a stall after more than `HANG_TIMEOUT_MS` (5 s) without a heartbeat, in `<userData>/logs/main-thread-hang.json` ({detectedAt, pid, unresponsiveMs, selfRecovered, phase, steps}), rewritten with `selfRecovered: true` when heartbeats resume (`detectedAt` is then the moment main answered again, so the stall began `unresponsiveMs` earlier). A tick gap over `SLEEP_GAP_FACTOR` (3×) is a system suspend, not a hang (the wait restarts); `powerMonitor` `resume` resets it too. **Observation only**: nothing kills or restarts main. `markMainStep(phase, step)` names what main is about to run (startup marks, quit teardown steps, the update's quit); the worker keeps the last `HANG_STEP_HISTORY` (8). ### Copy diagnostics

### Diagnostic bundle
- "Save diagnostic bundle" ("진단 묶음 저장") in a session row's context menu and touch action sheet (a paired host's rows too) and in Settings › Updates & about beside the diagnostics Preview (focused tab). The plain item is stock `/dump all`; holding Option/Alt or the "(anonymized)" item is stock `/dump anon`. A stored session no tab holds has the item disabled (stock's dump runs inside the tab's omp).
- Over stock RPC `/dump all|anon` only prints the archive path in a `command_output` prose frame and rides the prompt queue, so bridge `session_dump` (`resources/gui-bridge/session-dump.ts`, feature `sessionDump`) calls the same `dumpSessionArchiveToTmpDir()` / `dumpAnonymizedArchiveToTmpDir()` and returns stock's `SessionDumpArchive`; local handlers `dump_session_archive` / `discard_session_archive` (`src/main/local/session-dump.ts`, both quota-free; discard deletes only archives this process produced).
- **Every member is redacted, both variants** (the UI promises it). Stock's `/dump all` zip holds the raw transcript (`session.md`), the LLM request (`llm-request.json`) and `subagents/**`; stock says it "may contain raw context/secrets". `dump_session_archive` never hands stock's file on: it repacks it into `ompdesk-dump-<uuid>.zip` beside it, every UTF-8 member through `redactDiagnosticsFile` (`redactor.ts`: `.json`/`.jsonl` value by value so they still parse, a field naming a secret blanked; anything else as `redactDiagnosticsText`), a member that is not text dropped and named in `dropped`, then deletes stock's file whatever happened. `/dump anon` keeps stock's anonymizer and then gets the same pass. The handler runs on the machine whose omp wrote the archive, so a host redacts before a paired device reads a byte; the answer carries `redacted: true` and main refuses an archive without it (an older host: `remote_protocol`, never saved, still discarded). A new redaction need goes into `redactor.ts`, never a second pass elsewhere.
- Main's `sessions:dump-bundle` (`src/main/diagnostic-bundle.ts`): save dialog first (cancel makes nothing), then the dump on the tab's omp, then `ompdesk-diagnostics.txt` (the Copy diagnostics text) added as a zip member (jszip is in `MAIN_BUNDLED_DEPS`), written, and the temp archive deleted even on failure. A paired host's tab dumps on the host through `tab.command` and reads the bytes back with `host.fs.readBinary` (`FS_BINARY_REMOTE_MAX_BYTES` 11 MB, else `file_too_large`); the host's temp zip is discarded. A web page picks the path on the computer through the host browser's save mode (`destination: {kind: "path"}`).
- Agents: `ompdesk_app` `sessions.dump_bundle {session?, anonymized? = true, path?}` (tier `change`, no card): anonymized unless asked otherwise, written to the absolute `path` or Downloads (never overwriting), refused for a session hidden from agents.
