## Panels, sidebar and work views

### MCP servers: why one is off, sign-in, every live session

- Files: bridge `extensions/mcp.ts` (rules `mcp-core.ts`, contract `mcp-contracts.ts`), main `mcp-live.ts`, card `panels/mcp/McpServerCard.tsx`. An MCP server an agent installs must be usable after sign-in in the session that asked, without a terminal `omp`, and Settings must say why a server is off.
- **Why off** (`RpcMcpServerInfo.offReason`, `offReasonOf`), in stock's dashboard order (`resolveState` in pi-coding-agent `modes/components/extensions/state-manager.ts`): turned off by the person (denylist, or `enabled: false` in omp's own mcp.json) → `disabled`; the provider off as a whole (`isProviderEnabled`) → `toolOff`; declared only in another tool's user config whose `~/` omp has not opted in (`isUserSourceEnabled`, stock's `FOREIGN_USER_PROVIDERS`: Codex, Claude Code, Cursor, Gemini, Windsurf, OpenCode, GitHub) → `otherTool`; turned off in the other tool's own file → `offInTool`; a project server while `mcp.enableProjectConfig` is off → `projectConfigOff`. The row shows one muted line and its fix inline (`otherTool`: "omp에서 쓰기"/"Use in omp"; `disabled`/`offInTool`: "켜기"/"Turn on"). A server declared by omp's config and another tool's reads "{tool} 설정에서 가져옴" (`alsoIn`). Pinned against stock's dashboard by `bridge-mcp-stock.test.ts`.
- **Use in omp** (`mcp_action` `adopt`, `adoptServer`): copies that one server's definition (as stock discovered it, without the other tool's `enabled: false`) into omp's user `~/.omp/agent/mcp.json` with stock's `addMCPServer`, then connects it. Never stock's provider-wide `enabledProviders` (it would also bring the tool's other servers, skills and rules) nor `enabledServers` (it overrides `enabled: false`, never a source not opted in). A value the other tool forwards from the environment (Codex `env_vars`, `bearer_token_env_var`) goes in as `${NAME}`, never the secret (`adoptedEntry`).
- **Needs a sign-in** (`authState: required`): also when the server answered the last connect with an OAuth challenge (stock `analyzeAuthError`) though its config says nothing about auth. The failure is stock's own (`MCPManager.waitForStartup(1)`'s `failed`, kept from the first connect on; `lastError`), never a bridge listener (it would have to attach before a fast 401). The row shows "로그인이 필요해요" with a Sign in button (`mcp_reauth`).
- **A server that does not connect never fails the change that saved it**: stock's reload (`MCPCommandController.reloadServers`) presents failed servers as one warning; `mcp_add` and `mcp_reload` return it as `warning` instead of rejecting, so the change answers and its broadcast goes out.
- **Every live session follows** (`mcp-live.ts`): a successful `mcp_add`, `mcp_action` (adopt, enable, disable, remove, reconnect), `mcp_reauth` and `mcp_reload` (local handlers in `local/extensions.ts`) call `noteMcpChange`; index.ts sends it as `ExtensionApplyPlan.mcp` to every local tab and every tab this computer hosts: a ready tab at once, a tab in a turn when the turn ends. The tab's bridge runs `mcp_sync`: clears stock's fs cache, reloads the credential store, and per named server disconnects one no longer configured, connects one configured but not connected, reconnects one whose config changed, and leaves one connected with the same config alone (stock's `/mcp reload` would drop every server). A paired host's tab runs its handlers on the host, so the host's sessions follow.
- **An MCP sign-in is no model account**: stock keeps managed MCP OAuth tokens in the model credential store under the credential id (`mcp_oauth:profile:<profile>:<server url>`, agent.db `auth_credentials`). Every list of stored providers drops those rows with stock's `isManagedMCPOAuthCredentialId` (`mcp/oauth-flow`), never a string match: the Settings provider list (bridge `buildProviders`), the stock helper's `accounts.providers` and `accounts.signedIn` (only an MCP sign-in is not signed in). Per-provider reads take a model provider's id and never see them. Pinned by `bridge-mcp-credentials-stock.test.ts` and `stock-helper-accounts.test.ts`.
- **Composer `/mcp`**: stock's headless `/mcp reauth` opens the browser on omp's computer and cannot reconnect in RPC mode, and its `reload` only refreshes commands, so a typed `/mcp <verb>` whose registry item is an action or window runs in the GUI (`composer-submit.ts`): `/mcp reauth <name>` signs in from the composer, `/mcp reload` is `mcp_reload` (this session, then every live one); `/mcp list` still goes to stock (`typedAsPrompt`).
- **The sign-in is stock's** (`mcp_reauth`, bridge `runReauth`): stock `mcp/oauth-reauth` `findMcpServerForAuth` + `reauthorizeMcpServer` do the flow (endpoints, client credentials, browser, credential row, config write-back, clearing a stale `Authorization` header); the GUI only presents it: the URL as an `extension_ui_request` `open_url` frame (a paired device opens it on its own screen), progress as `notify`, the code paste-back as the session's `input` dialog (dismissing cancels, `MCPOAuthCancelledError` → `cancelled`), then the live session's servers reload. Pinned by "signs a server in over a stale bearer header" and "ends a sign-in the person dismisses or the GUI cancels" (`mcp_reauth_cancel` closes the open paste-back dialog) in `bridge-mcp-stock.test.ts`.
- **Agents** (`agentctl/app/catalog.rs`): `extensions.mcp_servers` (read: state, tools, sign-in, why off; never a url or command), `extensions.mcp_sign_in` (sensitive, always: starts the OAuth sign-in in the caller's session, answers once under way), `extensions.mcp_use` (sensitive, always: the adopt); `extensions.install_mcp` says whether the new server needs a sign-in and that open sessions pick it up. The skill (`references/app-control.md`) tells an agent never to start a terminal omp for MCP work.
- Pinned by `bridge-mcp-stock.test.ts` (installed omp: 401 server needs sign-in, `mcp_sync` after another omp's credential, real `mcp_add`/`mcp_reauth` against a fake OAuth server, adopting one Codex server), `bridge-mcp-core.test.ts`, `local/mcp-live-changes.test.ts`, `extension-reload.test.ts`, `app-control.test.ts`, `McpServerCard.test.tsx`, `composer-submit.test.ts`; captures `OMP_GUI_MCP_SETTINGS_SHOTS=<dir>` with `e2e/mcp-settings-captures.e2e.ts` (fixture `fixture-mcp.ts`; `OMP_GUI_MCP_SETTINGS_PREFIX` names the set).

### Built-in MCP (REA)

- `resources/omp-builtin/rea/.mcp.json` declares `rea` as an http server of **OMPdesk's MCP hub** (url `${OMP_GUI_MCP_HUB}/rea?cwd=${OMP_GUI_MCP_CWD}`, header `Authorization: ${OMP_GUI_MCP_AUTH}`, `REA_HUB_ENTRY` in `mcp-hub-contracts.ts`, pinned by `packaging-config.test.ts`), loaded as a directory `-e` on every eligible spawn (REA root = `resources/omp-builtin/rea/`; `resources/omp-builtin/` itself is OMPdesk's own root, see OMPdesk control tools). The hub runs pinned REA (`rea/rea-config.json` is the sole version pin), mounts `analyze_javascript_application` and `open_binary` with their original descriptors (`curatedTools`) plus `rea_catalog` / `rea_call`, and keeps every upstream tool reachable through discovery and invocation. Each omp is its own MCP session with its own REA, started in that omp's folder (`?cwd=`).
- **One MCP hub per app, not helpers per session**, because per-session relays froze the machine with a few sessions. `resources/gui-bridge/mcp-hub.ts` (REA `mcp-hub-rea.ts`, memory `mcp-hub-memory.ts`, env names `mcp-hub-contracts.ts`) is ONE Bun process started by main (`src/main/mcp-hub.ts` `McpHub`, before the first omp; a spawn waits for its first listening line, at most 10 s), never main's own event loop. Streamable HTTP on 127.0.0.1; every request needs the per-launch secret (`OMP_GUI_MCP_AUTH`, `Bearer <hex>`; the hub's copy `OMP_GUI_MCP_HUB_SECRET` is never passed to REA). Main gives every omp that mounts REA or memory `OMP_GUI_MCP_HUB`/`OMP_GUI_MCP_AUTH`/`OMP_GUI_MCP_CWD` (`sidecar-factory.ts`, scheduled runs through `ompRunLauncher` `extensionEnv`; all three in `SESSION_OWNED_ENV`) and stock expands them in `.mcp.json` (`expandEnvVarsDeep`), so the files never change between launches. Known cost: the secret is in every omp's and its tools' environment; it grants only these two servers. The port is kept across restarts (`RestartBudget`, revived by the next spawn once spent), stdin EOF stops it with every REA, and it runs at the agents' priority. Sessions: `initialize` mints `Mcp-Session-Id`; answers are the POST's JSON; REA's own notifications and requests go on the session's GET event stream (held, at most 1000, until omp opens it; the stream opens with a `: open` comment because Bun holds headers until the first bytes and omp gives a stream one second). The stream ending or a DELETE stops that session's REA; a session whose REA never started is kept (a call to a gone session is a 404, which omp answers by reconnecting). Every caller is served at once, nothing queues.
- **REA starts at first use**, because an idle REA costs hundreds of MB per omp. The hub keeps what a started REA answered omp's startup with (`initialize`, the whole catalog, `prompts/list`) in `<userData>/rea/rea-<version>.json` (`OMP_GUI_REA_CACHE`), keyed by the pinned version and omp's exact handshake, read once per hub and shared by every session (`ReaCacheStore`). With that file a session answers `initialize`, `tools/list`, `prompts/list`, `ping` and `rea_catalog` itself and spawns REA at the first call that needs it (a curated tool, `rea_call`, any other method): the same handshake and `initialized`, then the notifications held since (none reaches REA before its handshake is answered; a call omp cancelled meanwhile is answered `-32800` and never reaches REA), then a catalog check that sends `tools/list_changed` (and `prompts/list_changed`) when REA's answers differ and rewrites the file. No file, an unreadable one, or another handshake: REA starts with the session and the file is written once its catalog is read. **A REA that cannot start late** (no `npx`, offline, a refused handshake): the waiting calls get the JSON-RPC error, the file is deleted (so the next session fails at connect instead of a cached "healthy" REA failing every call), and the session's stream ends after those answers (any REA exit answers its waiting calls first), so omp reconnects. Tests: `src/main/mcp-hub-rea.test.ts`, `src/main/mcp-hub-memory.test.ts`.
- `rea_catalog` search returns concise tool summaries. A named lookup returns the complete upstream descriptor, including the full description, input and output schemas, annotations and metadata. `rea_call` invokes the named upstream tool with its original arguments and preserves its result.
- REA's upstream server instructions remain enabled for every connected session, including target-content prompt-injection handling and `close_binary` guidance. They do not depend on reading the optional skill. Never set `instructions: false` or maintain an OMPdesk copy of those instructions in the skill.
- The same root carries REA's `reverse-engineer-anything` skill in `rea/skills/` (stock loads an extension root's `skills/`), so it comes and goes with the server. It is vendored from the pinned release plus an OMPdesk section (mounted vs `rea_call` tools, no `rea setup`) by `bun run sync:rea-skill`, which every version bump runs (`packaging-config.test.ts` fails on a stale copy). The pin moves by itself: see Built-in skill packs stay current (`skills-bump.yml`; a new release must still list every `curatedTools` entry in its catalog).
- Node/npx must satisfy REA's engines. Pref `builtinMcp.rea` (default on) governs tabs this machine spawns or hosts; while it is off a spawn runs no node/npx probe. A tab's spawn (`spawnReaState`, `src/main/builtin-mcp.ts`) takes the last launch's available answer from `<userData>/rea-runtime.json` while the `node` and `npx` first on the spawn PATH keep the same identity (`toolIdentity`: PATH entry, resolved file, its size and mtime, read before the probe runs it), so a restored tab's omp need not wait for the probe; this launch's probe runs behind it and replaces the file (an unavailable answer deletes it; it is not cached while Node is missing). A changed binary behind the same PATH entry misses the stored answer and waits for the probe. **Known limit**: a version manager's shim (mise, asdf, volta) stays put while its config picks another Node, so the first spawns after such a switch still take the stored answer; the probe behind them corrects later spawns. Settings and machine setup ask the live probe (`builtinReaState`). stdin EOF kills the child process tree. Never write the user's MCP config.

### Computer use engine (agent-desktop)

- **The owner's rule**: the computer-use engine of every omp session OMPdesk spawns is [vercel-labs/agent-desktop](https://github.com/vercel-labs/agent-desktop) (Apache-2.0, native Rust CLI, `agent-desktop mcp` = stdio MCP server, v1.2.0 and newer), not stock's eval `computer` prelude, and it updates itself. Machine setup's updates keep it current in the managed tools dir (item `agent-desktop`, `machine-setup-updates.md`; `managedAgentDesktop` in `src/main/setup/paths.ts`).
- **Shipped in the app** (the owner's rule), so no session runs on the built-in prelude because a launch-time download had not finished. `scripts/agent-desktop-pin.json` pins one upstream release (version, per target the archive and its SHA-256 from upstream's `checksums.txt`, and the files it must hold) for `darwin-arm64` and `win32-x64`. `bun run build:agent-desktop` (`scripts/build-agent-desktop.ts`; `-- --all` both targets, `-- --pin-latest` moves the pin to upstream's newest release) downloads with the app's own downloader, refuses the archive unless the SHA-256 matches and it holds exactly the pinned regular files (own tar reader, no `tar` program), runs the CLI's `--version` on its own platform, and unpacks into the gitignored `resources/agent-desktop-bin/<platform>-<arch>/` with upstream's license (`LICENSES/agent-desktop-LICENSE`, as `LICENSE`) and `agent-desktop.build.json` (version, target, archive hash, each binary's SHA-256); a matching folder is kept. Both builder configs ship it as `agent-desktop-bin` (`extraResources`); `scripts/after-pack.cjs` `checkAgentDesktop` fails the package unless the record names the pinned version, target and archive hash, every pinned binary is byte-identical to the record (executable on macOS) and the LICENSE is beside it. On macOS `mac.sign` (`@electron/osx-sign`) signs both Mach-O binaries; release.yml's mac `Verify bundle` checks `codesign --verify --strict` on both and runs `--version`, its win `Verify package` and `scripts/windows-installer-check.ps1` run the `.exe`'s. release.yml's mac and win jobs and ci.yml's two Windows packaging jobs run `bun run build:agent-desktop` before packaging (no cache). The pin moves by hand (`--pin-latest`); newer releases reach users through the CLI updater.
- **Setting**: Settings › Agent behavior, right after Default browser, pref `computerUse` = `agent-desktop` (default; absent or unknown reads as it) | `builtin` (`src/shared/computer-use.ts`, row `settings/ComputerUseRow.tsx`, catalog id `computerUse`). The note under the row follows the setup item: not detected yet shows nothing, missing/installing/failed says sessions use the built-in computer use until it is installed, present shows its version. **Spawn-time only**: the MCP root is mounted when omp starts, so a change applies from a session's next start and nothing is pushed to live ones (`ipc.ts` validates with `isComputerUseEngine`). Agents never read or write it: `computerUse` matches `POWER_PREF` (`agentctl/app/guard.rs`) and is `ROW_NOT_WRITTEN` in `agentctl/app/settings.rs` (pinned by `app-control.test.ts`).
- **Spawn** (`computerUseSpawn`, `src/main/agent-desktop.ts`, called from `sidecar-factory.ts` `builtinMcp` with `deps.computerUse = {pref, toolsDir, bundleDir, platform}`, so local and hosted tabs take the same path): `builtin` → env `OMP_GUI_COMPUTER_USE=builtin`; `agent-desktop` with a copy to run → args `-e <omp-builtin>/agent-desktop`, env `OMP_GUI_COMPUTER_USE=agent-desktop` and `OMP_GUI_AGENT_DESKTOP=<executable>`; neither copy → `OMP_GUI_COMPUTER_USE=missing`, nothing mounted (a dev run without `bun run build:agent-desktop` and no managed copy, or a damaged install). **Which copy** (`agentDesktopToRun` → `pickAgentDesktop`, one rule for the spawn, machine setup's detection and the CLI updater): the managed copy when its `--version` is at least `AGENT_DESKTOP_MIN_VERSION` and the bundled version, else the bundled one (`bundledAgentDesktop`: `<resources>/agent-desktop-bin` packaged, `resources/agent-desktop-bin/<platform>-<arch>` dev; version from the build record, no process run). So an update applies from a session's next start and a stale managed copy never shadows a newer app. The managed copy's `--version` runs once per installed file (`agentDesktopVersion` keys by size, mtime and inode; a failure is not kept); a session never waits for a download. Both env names are in `SESSION_OWNED_ENV` (`omp-launch.ts`), so a shell-inherited one never leaks. Scheduled runs (`ompRunLauncher`) load no bridge and no root of this table, so stock's `computer.enabled` stays off there. Contracts: `resources/gui-bridge/modes/computer-use-contracts.ts`.
- **Root** `resources/omp-builtin/agent-desktop/.mcp.json`: one stdio server `agent-desktop`, `command` `${OMP_GUI_AGENT_DESKTOP}`, `args` `["mcp"]`, `timeout` `120000` (stock expands `${…}` from the omp's env, `discovery/omp-plugins.ts` `expandEnvVarsDeep`). The `timeout` is each request's deadline; stock's 30 s default equals agent-desktop's own waits (and Windows `launch notepad` takes ~30 s), so calls that succeeded failed as "timed out". It ships with the existing `omp-builtin` extraResources; `packaging-config.test.ts` pins the server and root list, `bridge-computer-use-mcp-stock.test.ts` the deadline stock takes. Stock mints its tools as `mcp__agent_desktop_<tool>` (`desktop_snapshot`, `desktop_click`, …); with `tools.xdev` they are `write` calls to `xd://mcp__agent_desktop_<tool>`.
- **Held default** (`thinking-default-core.ts` `defaultValueOf`): `computer.enabled` is held **off** while this omp's `OMP_GUI_COMPUTER_USE` is `agent-desktop` and it has not fallen back, on otherwise (`GUI_THINKING_DEFAULTS` keeps the built-in engine's `true`). A user's own value (config.yml, project config, `/computer on|off`, a Settings write) still wins; a person who turned `computer.enabled` on by hand has both engines.
- **Startup check and fallback** (`modes/computer-use.ts`, rules `computer-use-core.ts`, capability `computerUse`, installed first in `index.ts` `AREAS` so its `before_agent_start` hook runs before the sections hook): for an `agent-desktop` launch the bridge waits for stock's MCP startup of `agent-desktop` (`MCPManager.waitForStartup`, at most 10 s from the bridge's start; a server stock reports failed fails at once with stock's error; one still connecting or never listed at the bound fails with "did not start in time"/"the server was not loaded"), and the first turn's `before_agent_start` awaits that promise. On failure `holdBuiltinComputerPrelude` (`thinking-default.ts`) puts the held value on for this omp only, and stock's `cfgComputerEnabled.listen` reconciles the live prelude (an empty transcript rebuilds the prompt, a running one gets stock's hidden prelude notice). `missing` keeps the held value on from the start.
- **The fallback is visible, once**: the first turn of a session whose journal does not yet carry it returns a displayed `ompdesk-computer-use` custom message (`COMPUTER_USE_NOTICE_TYPE`, details `{v: 1, reason: "missing" | "failed", error?}`; one English line telling the model it uses the built-in prelude, or has no computer use when the person's setting keeps it off) plus one warning `ctx.ui.notify` toast per session id (the GUI toasts every `notify` warning, `rpc-types.ts`). The journal is the record, not a flag, because stock re-prepares a turn whose prompt changed under a handler and drops the first attempt's message; a relaunch falling back the same way adds nothing. The transcript renders it as one muted note line, `chat/ComputerUseNote.tsx` (`ui-parity.md`).
- **Prompt section `computer-use`** (`registerPromptSection`, static text, main agent and subagents alike since they share the omp's MCP manager; only while the engine is agent-desktop and has not fallen back): operate the desktop with the `agent-desktop` server's `desktop_*` tools, the built-in prelude is off, read `desktop_skills_get` "desktop" then "platform" before the first desktop action, observe → act on a qualified ref → observe again, retry only when `disposition.retry` is `safe`, actions are headless (no pointer movement, no focus change) and physical `--headed` input is unavailable (say so, do not work around it). Then the safety block **copied from stock's `src/prompts/system/computer-use.md`** (the `<critical>` bullets and the three paragraphs after it) plus one OMPdesk bullet: never change security or privacy settings (System Settings › Privacy & Security, permissions, accounts, passwords) yourself, tell the user what to change. `bridge-computer-use-stock.test.ts` fails when a stock bullet or paragraph is missing (skips without an omp).
- **The desktop slot is not involved**: agent-desktop is headless (`--headed` is a server-start flag OMPdesk never passes), so its input never takes the foreground, like a `backgroundFallback: refuse` run of the built-in prelude (`models-accounts.md` › Desktop slot); several sessions drive the desktop side by side. On Windows a `launch`ed app comes to the front, and `type` needs `--headed`, so a session writes a text field with `set-value` (read back with `get`). macOS Accessibility is attributed to OMPdesk as the responsible app. **Autopilot**: an unattended run has no person to confirm a consequential desktop action, so the Autopilot guard refuses every `mcp__agent_desktop_*` call, direct or as an `xd://` device (`autopilot-guard-core.ts` `evaluateToolCall`; pinned by `bridge-autopilot-guard.test.ts`).
- Tests: `src/main/agent-desktop.test.ts` (which copy runs), `src/main/bridge-computer-use.test.ts` (section gating, safety lines, server check, note once, held value and fallback), `bridge-computer-use-stock.test.ts`, `bridge-computer-use-mcp-stock.test.ts`, `sidecar-factory.test.ts` (root and env for local and hosted tabs), `setup/detect-agent-desktop.test.ts` and `cli-tools/detect.test.ts` (bundle counts as installed), `omp-launch.test.ts`, `packaging-config.test.ts` (extraResources, after-pack refusals, release steps), `scripts/setup-assets-health.test.ts` (pinned archives in the weekly download check), `app-control.test.ts`, `ComputerUseRow.test.tsx`, `bridge-thinking-default.test.ts`. Opt-in live run: `e2e/real-agent-desktop.e2e.ts` (`OMP_GUI_REAL_AGENT_DESKTOP=1`, after `bun run build:agent-desktop`; first launch runs the bundled copy, no fallback, nothing downloaded; Windows points `LOCALAPPDATA` into the profile). Not covered without a real omp and agent-desktop: the live fallback reconciling stock's prelude mid-session.

### Built-in pstack engineering mode

- Settings › Agent behavior › Smart automation, pref `pstack` (`PSTACK_PREF`), default **on**; contract `src/shared/pstack.ts`, row `settings/PstackRow.tsx`. `resources/omp-builtin/pstack/` is a translated copy of [pstack](https://github.com/cursor/plugins/tree/main/pstack) (MIT, Lauren Tan; pin `pstack-config.json`: upstream commit and pstack version, moved by `skills-bump.yml`) loaded as a directory `-e` beside the REA root only while the switch is on (`sidecar-factory.ts` `builtinMcp`, from the next spawn).
- Content: `skills/` (principles, playbooks under `poteto-mode/playbooks/`, workflow skills; every one `disable-model-invocation`, so hidden from the model's skill list and read as `skill://<name>`), `agents/` (`pstack-agent`, the wrapper every playbook delegate uses, and `comment-sicko`), the hand-written `adapter.md` (Cursor/Claude names → omp `task`/`ask`/`todo`, `ompdesk_session_open`/`compare`/`merge`, model roles `@task`/`@slow`/`@smol`, `~/.omp/agent/sessions` transcripts, the routing gate) and `pstack-manifest.json`.
- **Never add a `plugin.json` there**: omp would class the folder an Agent Plugins root and drop most skills for their frontmatter. `tdd`/`teach` are `pstack-tdd`/`pstack-teach`, so no stock or user skill is shadowed. Left out as Cursor-only: `setup-pstack`, `poteto-help`, `make-bot-ui`, Bugbot triage, the `orchestrate` playbook, the `watch-pr`/`orch` tools. Left out because they are folded into the built-in `ompdesk-formal-verify` skill: `create-formal-verification-skill`, `maintain-formal-verification-skill`, `statechart` (`SKIPPED_SKILLS` in `sync-pstack.ts`, so a sync never brings them back).
- **One formal-verification routing line**: `adapter.md` (Routing gate, and one Autopilot bullet) sends a race, ordering, retry, lease or state-machine bug, or an "are we sure this can never happen" question, to `skill://ompdesk-formal-verify` before the fix; the bug-fix playbook gets the same pointer through the sync rule `bugfix-formal`. `pack-drift.test.ts` resolves that `skill://` path in `resources/omp-builtin/formal/skills/`, not in the pstack pack.
- Everything except `pstack-config.json`, `adapter.md`, `agents/pstack-agent.md` and `README.md` is generated by `bun run sync:pstack` (`scripts/sync-pstack.ts`: clone at the pin or `PSTACK_SRC=<clone>`, copy, a rule table in which every rule must match at least once, so a reworded upstream line fails the sync; `-- --check` compares the pin with the newest upstream past the 3-day hold) and pinned by `src/main/pstack/pack-drift.test.ts` (sha256 manifest, no `plugin.json`, names and links, no leftover Cursor term, section size cap, tool names). The pin moves by itself: see Built-in skill packs stay current (`skills-bump.yml`).
- The always-on part is one `registerPromptSection` section (`resources/gui-bridge/modes/pstack.ts` + `pstack-core.ts`; texts generated into `pstack-text.ts` from `adapter.md` and the translated `poteto-mode` skill): static text for the prompt cache, main agent only, opening with the precedence repo rules > user settings > a skill the user invoked > the pack, then a routing gate (a trivial request gets a plain answer; anything else reads the matching playbook first and copies its steps into `todo`).
- Off for subagents (they get `pstack-agent`), Plan mode, a chat session without a project (`OMP_GUI_PSTACK=0` at spawn) and the switch off. A waiter polls every `pollMs` up to `maxWaitMs` (2 h) and is Unavailable after that; a slow, stopped (SIGSTOP) or asleep holder keeps the lock, a killed one frees it at once. The file holds an owner note (pid, host, start) that only the waiting log line reads, never a decision. A runtime without `bun:ffi`, a lock file that cannot be opened and a full or read-only disk are Unavailable (exit 3). The lock file is never removed or replaced (an unlinked lock file lets the next opener lock a new inode while the old one is held), so it has a name of its own and the old protocol's `.lock-<name>` folder is left alone (test "never deletes the folder the hand-made protocol left as its lock"); running a skill of the old protocol at the same time is not supported. `flock` failing with `EINTR` is retried like a busy lock. ### Built-in skill packs stay current

- pstack, ECC and REA bump themselves (the user's rule). `scripts/skill-packs.ts` is the one table and rule: `check [<name>]` compares each pin with the newest upstream release that has been public for bunfig.toml's `minimumReleaseAge` (3 days, read from that file: one hold for dependencies and skill packs); `bump <name>` moves the pin's `commit`/`version` lines to it, runs the pack's sync, regenerates `THIRD_PARTY_NOTICES.txt` (`gen:licenses`), checks REA's new catalog still lists every `curatedTools` entry (its real MCP server's `tools/list`), runs the pack's drift, stock and packaging tests and `licenses:check`. `sync:pstack -- --check` and `sync:ecc -- --check` call its `check`.
- **The hold**: a git pack takes the newest commit touching its folder (`pstack`, `pi/core`) whose committer date is at least 3 days old and descends from the pin; REA takes the highest stable `rea-agents` whose npm publish time is. Known gap: a commit pushed rather than merged on GitHub carries its author's own date, so a compromised upstream could backdate one; npm publish times are the registry's.
- **`.github/workflows/skills-bump.yml`** runs daily (05:41 UTC) and on dispatch (`gh workflow run skills-bump.yml`). `bump` (macOS, read-only token, no stored credentials, installs omp for ECC's stock test) tries each pack behind on top of the last one that passed and keeps each passing one as a commit `chore(skills): bump <name> to <version>`; `push` (ubuntu, `contents: write` and `actions: write`, runs no third-party code) applies them with `git am` onto main, pushes (fetch and rebase on a rejection, never force) and dispatches ci.yml on main (`-f win_platform=true`), because a push made with `GITHUB_TOKEN` starts no workflow. A pack whose sync rule stopped matching or whose test failed commits nothing: `report` (`issues: write`, waits for `bump` and `push`) opens or updates one issue "Skill pack bump failed" with the log's tail, also when a bump passed but `push` did not end `success` or `skipped` (`push.outputs.pushed` tells a failed push from a failed dispatch); only a run where every pack is current or bumped and pushed closes it. Fix the rule in the pack's sync script (adapt it, never silence it). The ordinary release cadence ships a bump; these commits never touch `.github/workflows`.
