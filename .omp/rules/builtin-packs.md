## Panels, sidebar and work views

### MCP servers: why one is off, sign-in, every live session

- The user's report (21 Oct 2026): MCP servers an agent installed (Higgsfield, Mobbin: OAuth over http) were unusable after the sign-in in the session that asked (`No such tool: xd://mcp__…`), the agent drove a terminal `omp` to sign in, and Settings listed several servers as off with no reason. Bridge `extensions/mcp.ts` (rules `mcp-core.ts`, contract `mcp-contracts.ts`), main `mcp-live.ts`, card `panels/mcp/McpServerCard.tsx`.
- **Why off** (`RpcMcpServerInfo.offReason`, `offReasonOf`): stock's dashboard order (`resolveState` in pi-coding-agent `modes/components/extensions/state-manager.ts`): turned off by the person (denylist, or `enabled: false` in omp's own mcp.json) → `disabled`; the provider turned off as a whole (`isProviderEnabled`) → `toolOff`; only another tool's user config declares it and omp has not opted that tool's `~/` in (`isUserSourceEnabled`, stock's `FOREIGN_USER_PROVIDERS`: Codex, Claude Code, Cursor, Gemini, Windsurf, OpenCode, GitHub) → `otherTool`; the other tool's own file turns it off → `offInTool`; a project server while `mcp.enableProjectConfig` is off → `projectConfigOff`. The row shows one muted line and its fix inline (`otherTool`: "omp에서 쓰기"/"Use in omp"; `disabled`/`offInTool`: "켜기"/"Turn on"). A server omp's own config declares that another tool's does too reads "{tool} 설정에서 가져옴" (`alsoIn`). Pinned against stock's dashboard by `bridge-mcp-stock.test.ts`.
- **Use in omp** (`mcp_action` `adopt`, `adoptServer`): copies that one server's definition (as stock discovered it, without the other tool's `enabled: false`) into omp's user `~/.omp/agent/mcp.json` with stock's `addMCPServer`, then connects it. Not stock's provider-wide opt-in (`enabledProviders`: it would also bring the tool's other servers, skills and rules) and not `enabledServers` (it overrides an `enabled: false`, never a foreign source that is not opted in). A value the other tool forwards from the environment (Codex `env_vars`, `bearer_token_env_var`) goes in as `${NAME}`, never the secret (`adoptedEntry`).
- **Needs a sign-in** (`authState: required`): also when the server answered the last connect with an OAuth challenge (stock `analyzeAuthError`), though its config says nothing about auth (an http server added by url alone). The failure is stock's own (`MCPManager.waitForStartup(1)`'s `failed`, the TUI status line's source, kept from the first connect on; `lastError`), never a listener the bridge would have to attach before a fast 401. The row shows "로그인이 필요해요" with a Sign in button (the existing `mcp_reauth` flow).
- **A server that does not connect never fails the change that saved it**: stock's reload (`MCPCommandController.reloadServers`) presents every server that failed to connect as one warning; the bridge keeps that text (`mcp_add` and `mcp_reload` return it as `warning`) instead of rejecting, so an add of a 401 server, or a sign-in while another server still refuses, answers, and its broadcast goes out.
- **Every live session follows** (`mcp-live.ts`): a successful `mcp_add`, `mcp_action` (adopt, enable, disable, remove, reconnect), `mcp_reauth` and `mcp_reload` (local handlers in `local/extensions.ts`) call `noteMcpChange`; index.ts sends it as an extension apply plan (`ExtensionApplyPlan.mcp`) to every local tab and every tab this computer hosts: a ready tab at once, a tab in a turn when its turn ends. The tab's bridge runs `mcp_sync`: it clears stock's fs cache, reloads the credential store (another omp wrote the row), and per named server disconnects one no longer configured, connects one configured but not connected, reconnects one whose config changed, and leaves one connected with the same config alone (so the tab that made the change does nothing twice; stock's `/mcp reload` would drop every server). A paired host's tab runs its handlers on the host, so the host's sessions follow.
- **An MCP sign-in is no model account**: stock keeps a managed MCP OAuth token in the same credential store as model accounts, its provider column the credential id (`mcp_oauth:profile:<profile>:<server url>`, agent.db `auth_credentials`). Every place that lists stored providers leaves those rows out with stock's own `isManagedMCPOAuthCredentialId` (`mcp/oauth-flow`), never a string match: the Settings provider list (bridge `buildProviders`), the stock helper's `accounts.providers` (the tool CLIs of connected accounts) and `accounts.signedIn` (a first run holding only an MCP sign-in is not signed in). Per-provider reads (account rotation, model setup facts, usage) take a model provider's id and never see them. Pinned by `bridge-mcp-credentials-stock.test.ts` and `stock-helper-accounts.test.ts` (installed omp, a seeded MCP credential row).
- **Composer `/mcp`**: stock's headless `/mcp reauth` (omp ≥ 18.12.6) opens the browser on the computer omp runs on (a paired host's tab: the host's screen) and in RPC mode has no live manager to reconnect, telling the person to restart the session; its `reload` only refreshes commands. So a typed `/mcp <verb>` whose registry item is an action or window runs in the GUI (`composer-submit.ts`): `/mcp reauth <name>` signs in from the composer, `/mcp reload` is `mcp_reload` (this session, then every live one); `/mcp list` still goes to stock (`typedAsPrompt`).
- **The sign-in is stock's** (`mcp_reauth`, bridge `runReauth`): stock `mcp/oauth-reauth` `findMcpServerForAuth` + `reauthorizeMcpServer` (endpoints, client credentials, the browser flow, the credential row, the config write-back), with the GUI's presentation only: the browser URL as an `extension_ui_request` `open_url` frame (so a paired device opens it on its own screen), progress as `notify`, the code paste-back as the session's `input` dialog (dismissing it cancels, `MCPOAuthCancelledError` → `cancelled`), then the live session's servers reload. An earlier OMPdesk copy of that flow left a config's `Authorization` header in place, so the next omp kept sending the stale bearer; stock clears it. Pinned by "signs a server in over a stale bearer header" and "ends a sign-in the person dismisses or the GUI cancels" (`mcp_reauth_cancel` closes the open paste-back dialog) in `bridge-mcp-stock.test.ts`.
- **Agents** (`app-catalog.ts`): `extensions.mcp_servers` (read: state, tools, sign-in, why off; never a url or command), `extensions.mcp_sign_in` (sensitive, always: starts the OAuth sign-in in the caller's session, answers once it is under way), `extensions.mcp_use` (sensitive, always: the adopt), and `extensions.install_mcp` says whether the new server needs a sign-in and that open sessions pick it up. The skill (`references/app-control.md`) tells an agent never to start a terminal omp for MCP work.
- Pinned by `bridge-mcp-stock.test.ts` (installed omp: a 401 server lists as needing a sign-in; another omp stores its credential and `mcp_sync` connects it and its tool joins the live session; the real `mcp_add` of a server answering 401 at once, then the real `mcp_reauth` against a fake OAuth server (metadata, client registration, authorize, token; the `open_url` followed as a browser would) while another server still refuses; a temp HOME's Codex config with two servers: adopting one makes only it active, the other stays `otherTool`, no Codex skill appears), `bridge-mcp-core.test.ts`, `local/mcp-live-changes.test.ts`, `extension-reload.test.ts`, `app-control.test.ts`, `McpServerCard.test.tsx`, `composer-submit.test.ts`; captures `OMP_GUI_MCP_SETTINGS_SHOTS=<dir>` with `e2e/mcp-settings-captures.e2e.ts` (dev harness fixture `fixture-mcp.ts`; `OMP_GUI_MCP_SETTINGS_PREFIX` names the set).

### Built-in MCP (REA)

- `resources/omp-builtin/rea/.mcp.json` starts the dependency-free Node `rea-relay.mjs` via stock's `${OMP_PLUGIN_ROOT}` substitution, outside asar, as a directory `-e` on every eligible spawn (REA root = `resources/omp-builtin/rea/`; `resources/omp-builtin/` itself is OMPdesk's own root, see OMPdesk control tools). The relay runs pinned REA (`rea/rea-config.json` is the sole version pin), mounts `analyze_javascript_application` and `open_binary` with their original descriptors (`curatedTools`) plus `rea_catalog` / `rea_call`, and keeps every upstream tool accessible through discovery and invocation.
- **REA starts at first use** (28 Oct 2026; an idle REA was ~400 MB of physical footprint in every omp: `npm exec` ~75 MB plus `rea mcp` ~340 MB, on a machine with ten omps). The relay keeps what a started REA answered omp's startup with (`initialize`, the whole catalog, `prompts/list`) in `<userData>/rea/rea-<version>.json` (`OMP_GUI_REA_CACHE`, set by `sidecar-factory.ts` only while REA is mounted; session-owned in `sidecar.ts`), keyed by the pinned version and omp's exact handshake. With that file it answers `initialize`, `tools/list`, `prompts/list`, `ping` and `rea_catalog` itself and spawns REA at the first call that needs it (a curated tool, `rea_call`, any other method): the same handshake and `initialized`, then the notifications held since (none reaches REA before its handshake is answered; a call omp cancelled meanwhile never reaches REA and is answered `-32800`), then a catalog check that sends `tools/list_changed` (and `prompts/list_changed`) when REA's answers differ and rewrites the file. No file, an unreadable one, or another handshake: REA starts with omp as before and the file is written once its catalog is read. **A REA that cannot start late** (no `npx`, offline, a refused handshake): the waiting calls get the JSON-RPC error, the file is deleted (the next omp starts REA with its startup and fails at connect, as without a cache, instead of a cached "healthy" REA failing at every call), and the relay exits only after stdout drained (any child exit answers its waiting calls first). Measured with the real omp and the installed app's extension set (`full:fresh` vs this relay, 5 interleaved runs each, footprint of omp's whole process tree after 25 s): median 774 → 367 MB, 6 → 4 processes; the relay's startup answer 2.7 s → 0.1 s; the cost moves to the first REA call of a session (median 3.3 s, 2.3–19 s under load 10). Tests: `src/main/rea-relay.test.ts` "REA relay with a startup cache".
- `rea_catalog` search returns concise tool summaries. A named lookup returns the complete upstream descriptor, including the full description, input and output schemas, annotations and metadata. `rea_call` invokes the named upstream tool with its original arguments and preserves its result.
- REA's upstream server instructions remain enabled for every connected session, including target-content prompt-injection handling and `close_binary` guidance. They do not depend on reading the optional skill. Never set `instructions: false` or maintain an OMPdesk copy of those instructions in the skill.
- The same root carries REA's `reverse-engineer-anything` skill in `rea/skills/` (stock loads an extension root's `skills/`), so it comes and goes with the server. It is vendored from the pinned release plus an OMPdesk section (mounted vs `rea_call` tools, no `rea setup`) by `bun run sync:rea-skill`, which every version bump runs (`packaging-config.test.ts` fails on a stale copy). The pin moves by itself: see Built-in skill packs stay current (`skills-bump.yml`; a new release must still list every `curatedTools` entry in its catalog).
- Node/npx must satisfy REA's engines. Pref `builtinMcp.rea` (default on) governs tabs this machine spawns or hosts; while it is off a spawn runs no node/npx probe (the probe is not cached while Node is missing, and costs seconds on Windows). A tab's spawn (`spawnReaState`, `src/main/builtin-mcp.ts`) takes the last launch's available answer from `<userData>/rea-runtime.json` while the `node` and `npx` first on the spawn PATH have the same identity (`toolIdentity`: the PATH entry, the file it resolves to, that file's size and mtime, each read before the probe runs it), and this launch's probe runs behind it and replaces the file (an unavailable answer deletes it): `node --version` plus `npx --version` through mise's shims took 0.25 to 1 s on the user's Mac, all of it before a restored tab's omp could start. A Homebrew or nvm upgrade behind the same PATH entry (a relinked keg, a binary replaced in place) misses the stored answer and waits for the probe. **Known limit**: a version manager's shim (mise, asdf, volta) is a script that stays put while its config (`.tool-versions`, `mise.toml`, a pinned project) picks another Node, so the first spawns after such a switch still take the stored answer and mount REA; the probe behind them corrects every later spawn. Settings and machine setup still ask the live probe (`builtinReaState`). stdin EOF kills the child process tree. Never write the user's MCP config.

### Built-in pstack engineering mode

- Settings › Agent behavior › Smart automation, pref `pstack` (`PSTACK_PREF`), default **on**; contract `src/shared/pstack.ts`, row `settings/PstackRow.tsx`. `resources/omp-builtin/pstack/` is a translated copy of [pstack](https://github.com/cursor/plugins/tree/main/pstack) (MIT, Lauren Tan; pin `pstack-config.json`: upstream commit and pstack version, moved by `skills-bump.yml`) loaded as a directory `-e` beside the REA root only while the switch is on (`sidecar-factory.ts` `builtinMcp`, from the next spawn).
- Content: `skills/` (principles, playbooks under `poteto-mode/playbooks/`, workflow skills; every one `disable-model-invocation`, so hidden from the model's skill list and read as `skill://<name>`), `agents/` (`pstack-agent`, the wrapper every playbook delegate uses, and `comment-sicko`), the hand-written `adapter.md` (Cursor/Claude names → omp `task`/`ask`/`todo`, `ompdesk_session_open`/`compare`/`merge`, model roles `@task`/`@slow`/`@smol`, `~/.omp/agent/sessions` transcripts, the routing gate) and `pstack-manifest.json`.
- **Never add a `plugin.json` there**: omp would class the folder an Agent Plugins root and drop 54 of the skills for their frontmatter. `tdd`/`teach` are `pstack-tdd`/`pstack-teach`, so no stock or user skill is shadowed. Left out as Cursor-only: `setup-pstack`, `poteto-help`, `make-bot-ui`, Bugbot triage, the `orchestrate` playbook, the `watch-pr`/`orch` tools. Left out because they are folded into the built-in `ompdesk-formal-verify` skill (see its section): `create-formal-verification-skill`, `maintain-formal-verification-skill`, `statechart` (`SKIPPED_SKILLS` in `sync-pstack.ts`, so a sync never brings them back).
- **One formal-verification routing line**: `adapter.md` (Routing gate, and one Autopilot bullet) sends a race, ordering, retry, lease or state-machine bug, or an "are we sure this can never happen" question, to `skill://ompdesk-formal-verify` before the fix; the bug-fix playbook gets the same pointer through the sync rule `bugfix-formal`. `pack-drift.test.ts` resolves that one `skill://` path in `resources/omp-builtin/formal/skills/`, not in the pstack pack.
- Everything except `pstack-config.json`, `adapter.md`, `agents/pstack-agent.md` and `README.md` is generated by `bun run sync:pstack` (`scripts/sync-pstack.ts`: clone at the pin or `PSTACK_SRC=<clone>`, copy, a rule table in which every rule must match at least once, so a reworded upstream line fails the sync; `-- --check` compares the pin with the newest upstream past the 3-day hold) and pinned by `src/main/pstack/pack-drift.test.ts` (sha256 manifest, no `plugin.json`, names and links, no leftover Cursor term, section size cap, tool names). The pin moves by itself: see Built-in skill packs stay current (`skills-bump.yml`).
- The always-on part is one `registerPromptSection` section (`resources/gui-bridge/modes/pstack.ts` + `pstack-core.ts`; texts generated into `pstack-text.ts` from `adapter.md` and the translated `poteto-mode` skill: about 20 KB / 7.3k tokens): static text for the prompt cache, main agent only, opening with the precedence repo rules > user settings > a skill the user invoked > the pack, then a routing gate (a trivial request gets a plain answer; anything else reads the matching playbook first and copies its steps into `todo`).
- Off for subagents (they get `pstack-agent`), Plan mode, a chat session without a project (`OMP_GUI_PSTACK=0` at spawn) and the switch off. An Autopilot run gets the 2 KB `PSTACK_AUTOPILOT_SECTION` instead (its protocol and HARD LIMITS win; bug-fix, hillclimb, autonomous-run, session-pickup, pause-safely and prove-it-works, no shipping or PR playbooks). Solo delegation swaps the delegation paragraph.
- **Copied steps follow the todo language.** Every instruction in the pack to copy a playbook's steps into `todo` (the routing gate and adapter in `adapter.md`; `poteto-mode/SKILL.md` and each playbook's OMPdesk note through `sync-pstack.ts`'s rules `mode-todolist`, `mode-todolist-copy` and `insertPlaybookNote`) says: one item per step in order, written in the todo language the `<reply-language>` section sets, word for word only without one, skill, tool and file names kept. "Copied in verbatim" beat that section (real omp 18.12.3 on `smol`, Korean reply language, bridge and pack on `omp -p`, a bug prompt typed in Korean and an English agent brief, three runs each: 0 of 36 todo items in Korean before, 40 of 40 after, still one item per step in order). Pinned by `bridge-pstack.test.ts`, `pack-drift.test.ts` and the session-kind case of `bridge-reply-language.test.ts`; `e2e/real-pstack.e2e.ts` runs with reply language off, so its match of the playbook's English words still holds.
- **No ritual round trips, delegation only when faster** (20 Oct 2026, the user's rule: wall-clock speed matters, no feature switched off). The routing gate still reads the playbook first, but its `todo` init travels with the first step's own call, the list is kept current next to real work (never a response holding only `todo`), every finished step is marked done in the response with the last check (so stock's todo reminder has nothing to wake), and a failure the request already names is not reproduced again by a whole suite. Delegation sizes each item first: a few small edits are parallel tool calls in one response, subagents are for items of minutes each (`adapter.md` Delegation; `sync-pstack.ts` rules `feature-delegate-speed`, `swarm-size`, `mode-fanout-size`). Measured on six tasks (nanoid copies, 26 runs per build and model, real omp): GPT-6.1 todo-only responses 44 → 12 and their time 246 s → 77 s; Sonnet 5.5 todo-reminder turns 9 → 4; pass rate unchanged. **Known gap**: GPT-6.1 still fans three small edits out to three subagents when the request suggests subagents (11 of 11 runs, median 103 s against 50 s for Codex solo); Sonnet does it in 1 of 11.
  - **The playbook read goes out with the first look** (20 Oct 2026): the routing gate's first response reads the matching playbook and, as parallel calls beside it, lists the folder, reads the files the request names and runs the failing command it names; the `todo` list opens in the next response with the first step's own call. Measured on the clean harness (4 tasks × 3 runs, base vs this, all passing, answer time from prompt to final answer): GPT-6.1 381 → 341 s, Sonnet 5.5 103 → 93 s; requests that only read a skill or playbook per GPT run 1.2 → 0.2. A broader "fill each round trip" section (batch every read and edit, no lone skill read, one sentence between calls) helped GPT alone (339 s) but slowed Sonnet (t5 5 → 9 requests, 124 → 142 s with both), so it was dropped.
- Tests: `bridge-pstack.test.ts` (gating table and `install` on a fake `pi`), `e2e/pstack.e2e.ts` (fake omp whose `get_skills` and context inspector read the `-e` roots, real gating under `OMP_GUI_TEST_PSTACK=1`), opt-in `e2e/real-pstack.e2e.ts` (`OMP_GUI_REAL_WORK=1`, `smol` role: a bug-fix prompt must read `bug-fix.md` and copy its steps into `todo`, a greeting stays plain, the switch-off control never reads the playbook; a small model sometimes skips the playbook on a one-line bug, so it asks one follow in three runs).

No other skill or command name clashes with stock, pstack, REA, OMPdesk or this Mac's user skills. Pinned by `src/main/ecc/pack-drift.test.ts` (sha256 manifest, hidden skills, index coverage, drops and their `leads`, names), `src/main/ecc/ecc-stock.test.ts` (installed omp through `stock-probe.ts`: cost, every skill loads and reads through `skill://`, every command offered as itself and none named like a stock command), the ECC case of `command-registry-coverage.test.ts` (no OMPdesk command name) and `packaging-config.test.ts`. ### Built-in formal verification skill

- **One skill, `ompdesk-formal-verify`** (28 Oct 2026; the user's request: one OMPdesk-native skill instead of juggling three sources). It replaces proof-skills' four skills ([opum-ai/proof-skills](https://github.com/opum-ai/proof-skills), MIT, written for Claude with bash and python scripts) and pstack's `create-formal-verification-skill`, `maintain-formal-verification-skill` and `statechart`, which no longer ship in `resources/omp-builtin/pstack/` (left out by `sync-pstack.ts`'s `SKIPPED_SKILLS`, so a sync never brings them back). Nothing was copied from michael-denyer/agent-formal-verify (GPL-3.0); its ideas (a mutation runner) were written from scratch.
- **Root and mounting**: `resources/omp-builtin/formal/` (only `skills/ompdesk-formal-verify/`; **no `plugin.json`**, as for pstack and ECC) is a directory `-e` on **every** spawn, agent and chat (`sidecar-factory.ts` `builtinMcp`, after the pstack and ECC roots), independent of the agentControl, pstack and ECC switches. No setting (minimal-settings rule). It ships inside the existing `omp-builtin` extraResources, outside the asar, because the scripts run from disk. Cost: 77 estimated prompt tokens on omp 18.13.2 (stock lists the skill with a 100-character preview, so the description's first sentence carries the triggers); `formal-stock.test.ts` holds it under 200.
- **Name**: stock dedups skills by name (`capability/skill.ts` key, then `resolveCollision`: the later same-named skill becomes `<namespace>/<name>`), so a user's own `formal-verify` (proof-skills, agent-formal-verify) would shadow or rename ours. Hence `ompdesk-formal-verify`; `formal-stock.test.ts` runs a user `formal-verify` beside it on the installed omp. A download is checked before it appears under its final name; a refused, failed, stalled (no data for 60 s) or mismatching one is UNAVAILABLE. **Installs hold an OS lock** (30 Oct 2026; `withLock` in `lib/toolchain.ts`): `<cache>/.oslock-<name>` is locked with `bun:ffi`, which the kernel releases when the holder's process dies, however it dies. macOS (and Linux, for CI): `flock(fd, LOCK_EX | LOCK_NB)` on an fd opened by the call and kept open for the hold (BSD flock belongs to the open file description, so two calls in one process exclude each other too); Windows: `CreateFileW` read/write with a sharing mode that admits only readers and `OPEN_ALWAYS` (a second opener is refused on the sharing mode = busy, `CloseHandle` releases; a refused open is told busy from an environmental failure by a plain `fs.openSync(file, 'r')` probe, which libuv opens with full sharing, never by `GetLastError`, which the runtime can reset between the FFI call and the read; chosen over `LockFileEx`, which needs a HANDLE while Bun gives `fs.openSync` only a CRT fd, and the reader-only share keeps the note readable). A waiter polls every `pollMs` up to `maxWaitMs` (2 h) and is Unavailable after that; a holder that is slow, stopped (SIGSTOP) or asleep keeps the lock, one that is killed frees it at once. The file holds an owner note (pid, host, start) that only the waiting log line reads, never a decision. A runtime without `bun:ffi` (the scripts always run under Bun), a lock file that cannot be opened and a full or read-only disk are Unavailable (exit 3); the lock file is never removed or replaced (an unlinked lock file lets the next opener lock a new inode while the old one is held), so it has a name of its own and the old protocol's `.lock-<name>` folder is left alone: removing that folder by name raced between two new installers (one removed it and locked its file there, the other's late recursive remove unlinked that locked file; test "never deletes the folder the hand-made protocol left as its lock"); running a skill of the old protocol at the same time as this one is not supported (they ignore each other's lock). `flock` that fails with `EINTR` is tried again like a busy lock. After acquiring, it deletes `*.part-<host>-<pid>` and `*.tmp-<host>-<pid>` leftovers of dead pids (up to gigabytes). **Why this replaced the hand-made lock** (a `mkdir` lock folder with a second `mkdir` guard, stale reclaim, heartbeat, owner tokens and re-checks): four rounds of check-then-mutate fixes (release run 40891943183, two holders at once on a loaded Linux runner; the gone-lock, owner-identity, guard-token and stalled-holder fixes, model `formal/toolchain-lock`, verify skill `toolchain-lock-verify`, both retired) each closed one interleaving and left another that needed no stall: `takeGuardAside` renamed a guard aside before it checked its token, so a late reclaimer could move a fresh holder B's guard right after B's `guardStillMine`, a third process C made a new guard, the put-back failed and B's folder was deleted, and B and C both changed the lock (reproduced with real processes by a test, commit 08c6d2a94, that failed on the old code; it was dropped with the guard, since it pauses at the old guard's fs calls and can no longer mean anything). A mutex made of `mkdir` and time can always be passed by a holder that stalls between a check and the call after it, so the premise went, not the next check: nothing judges a holder alive or dead, nothing times out, and there is no guard, token, heartbeat or takeover. Nothing aborts `work` any more either (a signal ends the process, and the kernel frees the lock), so `work` takes no `AbortSignal` and `download`, `extractInto` and `run` carry none; `unpackArchive` and its shared-archive rule went with it (the two callers unpack and delete the archive themselves). **A cache on a network drive shared by several computers is not supported**: flock and sharing modes are not promised to hold across NFS or SMB (some grant silently), so two computers could both hold the lock; the cache is per computer (leftovers with another host's name are still never deleted). Tests: real child processes under Bun (no overlap across 2 and 8 processes, a SIGKILLed holder frees the lock at once, a SIGSTOPped holder is not taken over and the waiter gets in after SIGCONT and its release, two calls in one process, `maxWaitMs`); a test that takes the lock in vitest's Node runs the code in a Bun child instead (`src/main/formal/in-bun.ts`), since Node has no `bun:ffi`. A 16 process by 1000 round stress on macOS showed no overlap. The Windows path is covered by those tests on the Windows CI job only; it was not run by hand. **Every child process (java, lake) is tracked and killed with its process group (`taskkill /T /F` on Windows) on SIGINT, SIGTERM, SIGHUP and exit** (`lib/proc.ts`), so an interrupted script leaves no orphan TLC. `OMPDESK_FORMAL_OFFLINE=1`, `OMPDESK_FORMAL_JAVA`, `OMPDESK_FORMAL_NO_SYSTEM_JAVA=1`, `OMPDESK_FORMAL_SYSTEM_LEAN=1` and `OMPDESK_FORMAL_TOOLCHAIN=<pin file>` exist for tests and air-gapped machines. ### Built-in skill packs stay current

- pstack, ECC and REA bump themselves (the user's rule, 20 Oct 2026). `scripts/skill-packs.ts` is the one table and rule: `check [<name>]` compares each pin with the newest upstream release that has been public for bunfig.toml's `minimumReleaseAge` (3 days, read from that file: one hold for dependencies and skill packs); `bump <name>` moves the pin's `commit`/`version` lines to it, runs the pack's sync, regenerates `THIRD_PARTY_NOTICES.txt` (`gen:licenses`), checks REA's new catalog still lists every `curatedTools` entry (its real MCP server's `tools/list`), runs the pack's drift, stock and packaging tests and `licenses:check`. `sync:pstack -- --check` and `sync:ecc -- --check` call its `check`.
