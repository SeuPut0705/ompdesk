## Machine setup and updates

### Machine setup (`src/main/setup/`, contract `src/shared/setup.ts`)
- At launch main detects Bun, omp (through `resolveOmp`, so `MIN_OMP_VERSION` gates it), Git, GitHub CLI, Node.js (through the REA probe) and Tailscale, and installs what is missing **on its own**: no install button, no consent click. `SETUP_ITEMS` = bun, git, omp, gh, node, tailscale.
  - Required, in order: Bun (`curl -fsSL https://bun.sh/install | bash` / `irm bun.sh/install.ps1 | iex`, user-level; `<abs bun> upgrade` for a Bun below the omp package's `engines.bun`, `bun-upgrade`); on Windows Git for Windows (an existing install with `bin\bash.exe` is reused, else the PortableGit pinned in `plans.ts` with its SHA-256, extracted without admin into `%LOCALAPPDATA%\ompdesk\tools\git`; never WSL); then omp (`<abs bun> install -g @oh-my-pi/pi-coding-agent`, or `omp update` below the minimum).
  - **OMPdesk runs omp only from its package** (`resolveOmp`): the bridge's `@oh-my-pi/*` imports cannot resolve inside a compiled omp (Bun's standalone build: what stock's installer, Homebrew and mise install, and what stock's own launcher repair writes over a bun/npm launcher). `isCompiledOmp`: on POSIX any native executable (a package install launches through its `#!/usr/bin/env bun` script), on Windows a PE with Bun's `.bun` section (bun's own launcher `omp.exe` is a PE without it). A compiled omp earlier in the lookup is passed over; with none other the resolution fails `compiled`, setup calls omp broken and reinstalls the package (`bun-global`). The package's `engines.bun` gates the Bun omp's shebang would find (`bun-too-old`); setup then marks Bun `outdated` (`bunForOmp`, also from the package beside a compiled omp) and upgrades it first.
  - **The user's rule (29 Oct 2026): OMPdesk repairs every toolchain fault itself and never asks the person to run a command.** WHY: a Windows PC (데스크탑) stuck on "Couldn't install omp" after omp 18.13.3 (`engines.bun` >=1.4.4) with stock's compiled `omp.exe` in `~\.bun\bin` and no `bun` in PowerShell; the person cannot run commands there. So: a Bun that is missing or broken gets Bun's installer (`bun-script`), a too-old one `bun upgrade`, and a failed `bun upgrade` falls through to `bun-script` in the same attempt (no second back-off count); on Windows `bun-script` is `bunInstallScript` (renames a bun.exe a process runs aside, since install.ps1 deletes it first and stops with exit 0 when it cannot; verifies `bun.exe --version`, puts the old one back and fails otherwise). Before `bun-global`, a compiled omp at `<BUN_INSTALL>/bin/omp(.exe)` is renamed aside (`compiled-launcher.ts`): measured, Bun 1.4.4's `bun install -g` over a file in the launcher's place fails `failed to link …: EEXIST` on POSIX, and on Windows ignores EBUSY while that `omp.exe` runs (`bin.rs` `create_windows_shim`), exit 0, compiled omp kept. It is dropped once the package's launcher is in place and put back when the install fails. The back-off ledger records the OMPdesk version (`appVersion`); misses of another version are ignored, so a fixed release repairs at its first launch. `manualSteps` lists no commands and no page for Bun and omp, and the `omp.*` failure texts say OMPdesk is repairing it.
  - Optional, in the background once omp works: Git on macOS (`xcode-select --install`); gh and Node (Homebrew on macOS, else the official archive checked against its published SHA-256 into the managed tools dir `<userData>/tools`; `winget … --accept-source-agreements --accept-package-agreements` on Windows, else `unavailable`).
  - Tailscale (Mobile web) is never automatic (`setupItemAutomatic`): only `installForConnection` and an explicit Retry install it; the user's click is its consent.
  - Claude Code CLI and Codex CLI are never installed: omp signs in to Anthropic and OpenAI itself.
- `download.ts` fetches PortableGit and archives itself (streamed to `<tools>/.downloads`, SHA-256 checked, removed after the install) so an item's `progress` carries real bytes; running items also carry `step`/`steps` and `startedAt`. The view shows a determinate bar only for bytes, else an indeterminate one, plus "Step n of m" and the elapsed time.
- `paths.ts` appends the managed bin dirs to `process.env.PATH` and sets `GIT_INSTALL_ROOT` (stock `resolveWindowsShell` checks it after the Git for Windows roots) at startup and after each install. After an install it re-reads the login-shell PATH (macOS) or registry PATH (Windows), re-detects, and when omp became usable restarts every local tab in `error`/`exited` and the stats server. No app restart.
- Retry policy: each item once per launch automatically; after three automatic misses only once a day (`BACKOFF_MS` 24 h, `<userData>/setup-state.json`); the user's Retry always runs.
- Every install runs under `supervisor.ts` (the app binary as Node via `ELECTRON_RUN_AS_NODE`), which kills the installer's process tree when its stdin closes: Cancel (also aborts main's download), quit (`SetupService.dispose`) or a crash. POSIX ends the process group. **Windows has no group, so a PowerShell sweep ends the tree and repeats until two passes in a row find nothing new** (`TREE_SWEEP_SCRIPT`: Toolhelp's process snapshot through a dynamic assembly's P/Invoke, no WMI, no `Add-Type` compile; a process counts as a member only when born after its parent, the root only when born before the Stop; the supervisor exits after it). WHY (21 Oct 2026, `sessions-schedules` teardown `EBUSY rmdir …\project`, 1 of 40 runs under load): `taskkill /T` lists the tree and then ends it. A Stop 60 ms after the supervisor started reached the `cmd` shim before its `bun` (the fake omp's `-p` hang) existed; `bun` was born 200 ms before taskkill returned, taskkill exited 0 with the shim ended and `bun` alive, and nothing ended it. The folders of four such runs were still locked tens of minutes later, each by a live `bun.exe` whose working directory was the project (ending them freed the folders). Taskkill is now the fallback, used only when PowerShell cannot run the sweep. Pinned by `runner.test.ts` ("a child started in the gap between taskkill listing the tree and ending it": a slow `taskkill` that lists, waits 800 ms and ends its list; 3 of 3 runs failed with 7 to 13 survivors before, 3 of 3 passed after).
- IPC (`setup:get-state`, `setup:retry`, `setup:cancel`, push `setup:state`) takes item ids only; no handler accepts a command.
- Automatic installs run only in a packaged app outside `OMP_GUI_HEADLESS=1`, or with `OMP_GUI_TEST_INSTALLER` (plus `OMP_GUI_TEST_DOWNLOAD`/`OMP_GUI_TEST_DOWNLOAD_SHA256`: a file every test plan downloads first). Dev and test launches otherwise only detect.
- Setup screen (`components/onboarding/SetupTakeover.tsx`, shown by `App.tsx` from `useMachineSetupNeeded()`): while a local tab's omp is unusable and a required item is missing or installing, one modal dialog covers the whole window (sidebar and title bar included; drag strip and OS window controls stay live). Everything beneath is `inert`; menu actions, omp:// links, shortcuts and drops are no-ops through `useMachineSetupStore.takeover`; Tab is trapped, and focus opens on the dialog itself, never on its first control. Each required item is one row with its phase and progress; the exact command, install location and output sit in one closed "Show details" disclosure (an OS prompt it will raise stays visible), and a failure adds the banner with the reason, manual steps and Retry. When required setup finishes it fades out (reduced motion skips the fade) into the first-run flow (`FirstRunGate` → provider step). Optional items and remote tabs never show it. Every item stays listed in Settings › Updates & about › This computer (`MachineSetupSection.tsx`).
- `.github/workflows/setup-assets-health.yml` downloads every pinned setup file weekly through `download.ts` (`scripts/setup-assets-health.ts`; `gh workflow run setup-assets-health.yml` runs it now) and keeps one issue open while any fails.

### Connect installs its tool
- `SetupService.installForConnection`: a connection the user starts that needs a missing optional item installs it right then, as the user's own action: past the daily back-off and the once-per-launch rule, queued behind any running install, only in a launch that installs on its own (else it only detects). The connection carries on when the tool lands. Callers: gh (GitHub sign-in), node (`LocalMachine.setBuiltinRea` turning the built-in REA on while Node is missing or too old), tailscale (`tailscale/service.ts`).
- Connect GitHub (Settings › General, the PR center's signed-out card; `onboarding/GithubSignIn.tsx`) calls `GithubAuthService.startLogin`: with gh missing the flow is `installing`, awaits `installGh`, then starts `gh auth login`. No gh after the install → `gh_install_failed`; nothing able to install it here → `gh_missing`; Cancel stops it (`cancelGhInstall`).
- `onboarding/SetupInstallInline.tsx` shows the item inline (step, bytes, clock; the reason plus Retry after a failure; the download page when nothing can install it), also for setup's own background gh install. A paired host's tab: the host's own UI and setup install on the host.
- git/gh lookups (`local/git/exec.ts` `resolveBin`, `execBin`) read the spawn PATH on every call (`spawnPath` shares the cached login-shell probe, which `refreshPath` drops after an install), so a fresh gh is found without a relaunch. Never keep a copy of PATH from the first git call.
- No stock omp provider login shells out to a CLI (github-copilot, gemini-cli, google-antigravity, cursor, anthropic, openai-codex are OAuth/device-code flows in pi-ai's `registry/oauth/`; perplexity only reads its macOS app's token), so no provider sign-in installs anything.
- `e2e/github-cli-install.e2e.ts` (fake installer) covers gh off PATH and in back-off, the click downloading (held at half), failing offline with Retry, installing into the managed tools dir and reaching the device code and signed-in account (en/ko captures).

### omp updates itself (`src/main/omp-updater.ts`, contract `src/shared/omp-update.ts`)
- OMPdesk's own update is `updater.ts`, installed by itself unless the user turns `appAutoUpdate` (default on) off.
- Main asks stock `omp update --check` (`SetupService.latestOmp`) at launch (after machine setup's first pass) and every 4 h, doubling the wait per failure in a row up to 24 h; while omp is missing nothing is checked. When the answer is newer than the installed omp (`compareVersions`) it runs stock `omp update` through `SetupService.updateOmp` (the omp item's `omp-update` plan under the setup supervisor): background, no click, queued behind any install, **never waiting for a turn to end** (the user's rule: a running omp keeps the code it loaded).
- **Bun first, package always** (28 Oct 2026, this Mac): OMPdesk ran `omp update` to 18.13.3, whose `engines.bun` is `>=1.4.4`, on Bun 1.4.2. Stock installed the package, its verify (`omp --version` on the new launcher) hit "Bun runtime must be >= 1.4.4", and `updateViaManager` "repaired" `~/.bun/bin/omp` with the 217 MB compiled omp; OMPdesk read 18.13.3 from it and restarted every tab on it, so every bridge feature read "Unavailable with omp 18.13.3". Now, before the installer, `updateOmp` reads the target's manifest (`bun pm view <pkg>@<v> --json` in the update's environment, `SetupServiceDeps.ompRelease`): a failed lookup is a `check` failure and nothing runs; `omp.dist` "binary" (a release stock never installs as a package) is not installed; a Bun below `engines.bun` is upgraded through the bun item (`bun upgrade`) and an upgrade that falls short stops the update. After it, an omp that is not usable (a compiled omp from stock's repair for any other reason, such as a Windows lock) is put back by setup's required pipeline at once (`#runRequired(true, false)`: no `onOmpReady`; the updater's `resume` restarts the tabs).
- Check and update share one environment (`ompUpdateEnv` in `omp-runtime.ts`): the detected omp's folder first on PATH (stock updates the first `omp` on PATH, `resolveOmpPath` = `$which("omp")`) and, for a `bun install -g` launcher, `BUN_INSTALL=<its Bun root>` (stock calls it a Bun install only inside `bun pm bin -g`). So both follow the user's registry (.npmrc, bunfig, `npm_config_registry`), channel and install method (Bun, npm, Homebrew, mise, standalone), agree, and land in the omp OMPdesk runs, never another `omp` earlier on PATH. `get_omp_update` (a paired host's check, `local/misc.ts`) uses it too.
- Why it is safe: `bun install -g` replaces package files by new inodes, and the bridge's literal `@oh-my-pi/*` imports resolve to the running omp's bundled singletons (`health.ts`). Processes that read omp's files from disk (stats server, stock helper: `import(variable)`) are stopped before the installer and started after it. Known limit: the old process's lazy hashed assets in `dist/` (HTML export template, highlight/marked chunks) vanish, so those can fail in a tab until it restarts. Windows locks files a running omp holds: stock's EBUSY/launcher repair applies; a failed install is kept in `OmpUpdateState.failure` and retried at the next check.
- After success main re-detects omp (`refreshSystemOmp`), starts the stats server on it, restarts every idle local tab and every idle tab it hosts for paired devices on their own session file, and restarts a busy tab one tick after its turn ends (`src/main/omp-restart.ts`; `SidecarPool.restartOnNewOmp`, `LocalHostServices.restartOnNewOmp`; `asleep` tabs need nothing). Composer drafts survive. The restarts re-ask each bridge's `capabilities` (`BridgeHealth` is keyed by omp version), so a feature the new omp lacks shows the existing `unsupported_omp` warning toast. Success shows one quiet "omp updated to X" toast in one window.
- One switch, "Keep tools up to date" (pref `toolsAutoUpdate`, `TOOLS_AUTO_UPDATE_PREF`; default on; a stored `false` turns it off), covers omp, the tool CLIs and extensions; it and omp's manual "Update now" live in Settings › Updates & about › This computer (`OmpUpdateRows.tsx`). IPC (`omp-update:get-state`, `omp-update:now`, push `omp-update:state`, `omp-update:updated`) carries no version, command or path.
- Each computer updates its own omp under its own pref, always through its own `OmpUpdater`. On a paired host's tab Settings › Updates & about shows the host's row (`HostOmpUpdateRow`); its button only asks the host to run its updater (`host.ompUpdate.now` / `host-omp-update:now`; state `host.ompUpdate.get` / `host-omp-update:get`; the host pushes every change as the `host.ompUpdate.changed` event, forwarded as `host-omp-update:state`), so the host's helpers, supervisor, re-detection and tab restarts run, and it never overlaps its own scheduled update. There is no `omp_update` RPC and no second `omp update` path.
- Scheduled checks run only in a packaged app outside `OMP_GUI_HEADLESS=1`, or in a test launch with both `OMP_GUI_TEST_INSTALLER` and `OMP_GUI_TEST_OMP_UPDATES=1` (installer called `<installer> omp omp-update`).
- Tests: `e2e/omp-auto-update.e2e.ts` with `OMP_GUI_TEST_LATEST_OMP` (what `update --check` reports), `OMP_GUI_TEST_UPDATE_CHECK_LOG` (each check's first PATH entry), `OMP_GUI_TEST_VERSION_FILE`, `OMP_GUI_TEST_BOOT_LOG`, `OMP_GUI_TEST_UNAVAILABLE_AFTER_UPDATE`; `src/main/setup/omp-update-install.test.ts` runs the real `bun install -g` against a fake registry (`src/main/test-omp-registry.ts`) in a temp HOME and BUN_INSTALL, a second omp first on PATH staying untouched.

### `UpdateScheduler` (`src/main/update-scheduler.ts`)
- The omp, tool CLI and extension updaters share one loop: it ticks at start in a scheduled launch, re-arms its timer from the end of each tick (a rejected tick does not end the schedule), queues passes one at a time (`enqueue`, dropped once disposed) and owns the back-off (`nextCheckDelay`, per item `settleBackoff`; `CHECK_INTERVAL_MS` 4 h, `MAX_CHECK_INTERVAL_MS` 24 h).
- omp backs off its timer by its own failure count and joins a running check instead of queueing a second; CLI and extension updaters back off per tool or row (a cancel is no failure). `updater.ts` (its own 5-minute check) is not on it.

### Tool CLIs of connected accounts (`src/main/cli-tools/`, contract `src/shared/cli-update.ts`)
- Follows "Keep tools up to date" (`toolsAutoUpdate`, default on; a user may pin a vendor CLI; OMPdesk needs no minimum version of one). Runs at launch (after setup's first pass) and every 4 h with omp's per-tool back-off (`CliUpdater`).
- Main reads providers with a stored credential from stock's own store (stock-helper `accounts.providers` = `discoverAuthStorage().credentials.list()`, ids only; `sdk` is listed under `providers` in `capabilities.ts`) and maps them to CLIs (`catalog.ts`: anthropic → `claude`, openai-codex/openai → `codex`, google-gemini-cli/google → `gemini`, cursor → `cursor-agent`, github-copilot → `copilot`, `gh` and its `gh-copilot` extension), plus what setup installs (gh, and Node in the managed tools dir only).
- It **never installs** a vendor CLI: only an installed one is listed and updated, by the owner found from its resolved executable path (`detect.ts classifyInstall`): Homebrew (`brew upgrade [--cask] <name>`), a global npm (`npm install -g --prefix <that prefix>`) or Bun package (`bun install -g` under that `BUN_INSTALL`), winget (`winget upgrade --id`), the vendor's updater (`claude update`, which also owns a Claude Code in npm/Bun; `cursor-agent update`; `gh extension upgrade gh-copilot`), or setup's verified archive for the managed gh/Node. System (`/usr/bin`, Xcode CLT, `C:\Windows`), app-bundled (the Codex in ChatGPT.app) and admin-only installs are listed with their reason and never touched; no sudo.
- The check asks the owner first (`npm view`, `bun pm view`, `brew outdated --json=v2`, `winget list --upgrade-available`, the release feed), updates only when newer (`compareVersions`), runs `SetupService.runToolUpdate` under the setup supervisor (queued behind installs, never touching setup items' state) and detects again (`updated` or `not-updated`).
- Running-process rule: npm and Bun replace the whole package dir (a running process keeps its open files, but a later `require` reads the new version and a file only the old version had is gone); Homebrew removes the old keg. So on macOS an npm/Bun/Homebrew update of a Node CLI waits while a process of it runs (`ps`, `plans.ts waitsForIdle`/`runningIn`; result `deferred`, no back-off, retried next check). A native binary (gh), vendor updaters and managed copies update at once. On Windows a file a running tool holds just fails the update, which is recorded and retried. A failure backs off like omp's.
- IPC `cliUpdate.getState/now(id?)/onState` carries tool ids only (an unknown id throws; no command, path or version crosses it); opening Settings rescans. Each computer, and each paired host, updates its own tools.
- Homebrew prefixes (`/opt/homebrew/bin`, `/usr/local/bin`) are also searched when the login-shell PATH omits them (`resolveBin` for gh/git, setup's gh detection, `cli-tools/detect.ts`). The PR and GitHub centers show the connect card (install, then sign in) instead of a download link for a missing gh on this computer; a paired host's tab keeps the link (that gh is the host's).
- Tests: a test launch checks on its own only with `OMP_GUI_TEST_INSTALLER` plus `OMP_GUI_TEST_CLI_UPDATES=1` (runs `<installer> cli-<tool> <method> check|update`; `e2e/cli-update.e2e.ts`). `OMP_GUI_TEST_BREW_DIRS` (PATH-style list, empty = none) replaces Homebrew's prefixes so the developer's brew never answers a test.
- Windows: a tool is found only as `<bin>.exe` or `<bin>.cmd` (npm's bare `<bin>` and `npm` are POSIX scripts Windows cannot start). A `.cmd` runs through cmd.exe with the omp shim's quoting (`src/main/spawn.ts`: `launcherNames`, `findOnPath`, `spawnCommand`/`spawnArgs`/`needsShell`: the one PATH lookup and Windows spawn rule every external tool uses). npm writes a global bin there as a cmd-shim, so `detect.ts cmdShimTarget` reads the package file the shim runs (`"%dp0%\node_modules\<package>\<bin>"`) to find its npm prefix. A Bun global is a copy of Bun's shim `.exe` beside a `<bin>.bunx`, whose start names the target in UTF-16LE up to a `"`, relative to the folder above the shim's (`detect.ts bunxShimTarget`, bun's `BinLinkingShim.zig`; `install\global\node_modules\<package>\…` from `.bun\bin`), so Bun's install owns it.

### Extensions of connected omp (`src/main/ext-update/`, contract `src/shared/extension-update.ts`, helper contract `resources/gui-bridge/stock-helper/extensions-contracts.ts`)
- Follows "Keep tools up to date" (`toolsAutoUpdate`, default on); rows in Settings › Updates & about › This computer › Extensions. Marketplaces, plugins, skills and MCP servers, on `CliUpdater`'s schedule (after setup's first pass, every 4 h, per-row back-off `nextCheckDelay`, failures recorded, deferred rows retried; `omp` being installed defers without back-off). `ExtensionUpdater` reads the inventory in the extensions worker (local files, no network) and works marketplaces → plugins → skills → MCP, one row at a time.
- Marketplaces: stock `updateMarketplace` (what `marketplace_action update` runs).
- Plugins: marketplace installs by stock `checkForUpdates`/`upgradePlugin`, npm and git plugins by `PluginManager.upgrade`. Stock has no user pin for a marketplace plugin (the catalog's `ref`/`sha`/`version` is the author's; upgrade follows it).
  - `upgrade(name)` reinstalls an npm plugin at the registry's latest whatever its spec says, so OMPdesk reads `plugins/package.json` and calls upgrade only when the spec is what a bare install writes (bun 1.4.2: `pkg`/`pkg@latest` → `^x.y.z`, `pkg@beta` → `^<tagged>`, exact and range specs verbatim; `^<installed>`, `latest`, `*` follow latest) and latest is strictly newer.
  - An exact or ranged npm spec and a git commit/version-tag ref are pinned: checked, shown as "update available", never moved, not even by Update now. Linked plugins are skipped.
  - npm/git/linked plugins are user scope only (stock's `PluginManager` has no project scope); marketplace plugins also per project registry of the open local tabs' folders.
- Skills: stock records a source only for skills-registry installs (`skills.json`/`skills.lock.json`, `skillshare/manifest.ts`; `omp skill install|update|uninstall` take `@scope/name`; no git-source skill), so those update by `updateSkillPackages` (exact range = pinned; a version that ships scripts is never approved for the user: `needs-approval`). Plugin-provided skills follow their plugin (one grouped row); plain local files are one "local, not updated" row.
- MCP servers (the user's config is never written):
  - The built-in REA is listed as pinned to the OMPdesk release; URL servers are skipped (`remote`).
  - An unpinned `npx`/`bunx`/`uvx` package is "follows latest at start" and its cache is not touched (npm 11.17: a bare `npx -y pkg` after a new publish starts the new version; warming a cache would execute the server). A pinned `pkg@1.2.3` is checked against the registry and shown as an available update, config untouched.
  - A global binary is updated by its owner (`cli-tools/detect.ts classifyInstall` plus pipx `/pipx/venvs/<pkg>/`, uv tool `/uv/tools/<pkg>/`, pip via the shebang python's `importlib.metadata`) through `SetupService.runToolUpdate` under the supervisor (system, bundled and admin-only installs listed and skipped, no sudo).
  - Running rule: a script (shebang) whose owner replaces package files in place (npm/Bun, Homebrew, pipx/uv/pip) waits while a `ps`-visible process of it runs (`deferred running`, retried); a native binary updates at once; Windows has no scan, a held file fails and is retried.
- Applying to live tabs (`src/main/extension-reload.ts`, `SidecarPool.applyExtensionUpdate`, `LocalHostServices.applyExtensionUpdate`): one `ExtensionApplyPlan` per pass. An idle ready tab reloads now (bridge `extension_update.reload` = stock `reloadPluginState`, what `/reload-plugins` does); a plugin that ships extensions/tools/hooks (`activation: restart-required`, `extensions/activation-core.ts`) restarts the tab on its session file (`omp-restart.ts` pattern); an updated MCP package is reconnected (`extension_update.reconnect` = stock `MCPManager.reconnectServer`); a busy tab waits and applies one tick after its turn ends; `asleep` tabs need nothing.
- Every stock internal the worker uses is in `capabilities.ts` and `health.ts` `LOADERS`. IPC `extensionUpdate.getState/now(key?)/onState` carries row keys only. Each computer, and each paired host, updates its own.
- Tests: a test launch checks only with `OMP_GUI_TEST_INSTALLER` plus `OMP_GUI_TEST_EXT_UPDATES=1` (MCP binary checks/updates run `<installer> cli-mcp-<name> <method> check|update`; `e2e/extension-update.e2e.ts`).

### Disk care (`src/main/disk/`, contract `src/shared/disk-care.ts`)
- The user's rule (20 Oct 2026): OMPdesk keeps the disk it fills in check by itself, **zero settings, nothing lost**. `DiskCare` runs once 2 min after launch (skipped when a run ended within 20 h; the daily timer comes due instead), then daily, one at a time; the Settings button and the agent's `disk.clean` join a running one. Every action is one `disk-care` line in gui-runtime.jsonl (`run` summary, `artifacts`, `worktree-landed`, `worktree-saved` with its `git worktree add …` restore line, `kept` with the reason, `http-cache`, `bun-cache`, `failed`). State (last run, last measurement) in `<userData>/disk-care/state.json`.
- **Measured on the user's Mac (20 Oct 2026)**: `~/.omp/wt` 54 GB in 24 worktrees; read-only classification of its 18 orphans by the rules below: 41.8 GB, of which 97.3 % regenerable (Cargo `target/` with `CACHEDIR.TAG` 24.4 GB, lockfile `node_modules` 15.2 GB allocated, `.gitignore` build sections 1.1 GB), 14 MB for the archive; none was yet idle 3 days. `node_modules` is mostly copy-on-write clones of Bun's cache: deleting a fresh one freed 276 MB of its 925 MB. Sessions 1.9 GB, userData 1.3 GB (1.2 GB Chromium HTTP cache, 111 × ~100 MB update installers), Bun cache 1.1 GB, stats.db 110 MB, omp logs 45 MB.
- **Idle thresholds by evidence**: stock session files by cwd (Oct 7–20): a worktree was resumed at most 8.3 h after its last write; across every project p99 2.9 days, max 6.7 days. So build output goes after `DISK_CARE_ARTIFACT_IDLE_DAYS` 3 (the cost of a wrong guess is a reinstall or rebuild) and a worktree with unlanded work after `DISK_CARE_REMOVE_IDLE_DAYS` 14 (twice the longest gap seen). Idle = no open tab on any device (`openFolders`), no running process with its cwd inside (`lsof -d cwd` on macOS, `/proc` on Linux; Windows cannot tell, so these two steps keep everything there), and nothing changed for N days: HEAD commit, git dir HEAD/index/reflog, every tracked and untracked file, every ignored entry no tool makes again, and stock's newest session file for that cwd (`lastActivity`).
- **Every step keeps a worktree whole** (build output included) while an open tab on any device holds it, git lists it locked, a known process works in it, or a rebase, merge, cherry-pick, revert or bisect is half done (`inProgressOperation`; checked under the removal claim in the artifact step, in `archiveBeforeRemove` for the landed sweep and the person's Remove, and before a save).
- **A save never rewrites bytes**: a worktree whose restore could write other bytes than it holds is kept, not saved: `core.autocrlf` true/input (Git for Windows' default), `core.eol`, or any `text`/`eol`/`crlf`/`filter`/`working-tree-encoding`/`ident` attribute (`-text` excepted) on a file the save carries (`rewritesBytes` in `saved-worktrees.ts`: `git ls-files --cached --others --exclude-standard` with `:(attr:…)` pathspecs, so git itself reads tracked and untracked `.gitattributes`, the common dir's `info/attributes`, `core.attributesFile` and the system file; never a parsed or lower-cased path). Pinned by the attribute-source cases and the CRLF/LF/mixed save → restore sha256 round trip of `disk/disk-care.test.ts`, which run in `test:platform` on Windows too.
- **Regenerable by evidence, never by name** (`disk/regenerable.ts`, one rule table): a `CACHEDIR.TAG` with the standard signature; `node_modules/` beside a tracked `package.json` with a tracked lockfile at or above it; `__pycache__/` holding only `.pyc`; the output folder of a build tool the package depends on and **builds with** in a script (`vite build`, `electron-vite build`, `next build` → `.next/`, `next export` → `out/`, `astro build`, `parcel build`, `nuxt build|generate`, `tsc` without `--noEmit`; a bare `vite` or `next dev` proves nothing), or a `--outDir` a script passes; a tool's config file's literal `outDir`/`output` replaces the default, and one that sets it any other way (`outDir: resolve(…)`) leaves the output unknown, so nothing counts; an ignored path whose `.gitignore` line sits under a comment naming build output, artifacts, generated files, caches or dependencies. Anything else (a hand-made `dist/`, `tmp/`, `.env`, a local database) is data.
- Steps: (1) drop regenerable entries of idle orphans; (2) the landed sweep (Work tree › Swept by themselves) with the archive first; (3) an idle orphan with unlanded or uncommitted work, not locked, no half-done rebase/merge/cherry-pick/revert/bisect: what is staged becomes one commit (from a copy of the index) and the working tree's tracked changes and untracked files one more on top (scratch index), `commit-tree --no-gpg-sign`, no hook, on a new `ompdesk/saved/<folder>-<date>` branch (HEAD → staged → working; never its own branch, never main; a detached HEAD's commits get the branch too). **No secret enters a commit** (`secretIn`): a file whose name says secret (`.env*`, keys, `credentials*`), whose whole content holds a credential by the central redactor's rules (`resources/gui-bridge/redactor.ts`: a `<secret>` or `<token>` appears, so a `"password": "…"`, a Bearer value, a JWT or a vendor token; a lockfile's long hashes count too, which only archives it), or that cannot be read whole (over `SECRET_SCAN_MAX_BYTES` 16 MB, unreadable) goes to the archive instead; a staged one keeps the worktree. Everything git does not keep and no tool makes again plus those files is copied to `<userData>/disk-care/saved/<id>/` (0700/0600, copy-on-write, verified by a walk; never in git, never synced, never uploaded). Only when nothing moved since the save read the worktree (no process inside, no half-done operation, the same HEAD and status, and no tracked, untracked or archived ignored file, index, reflog or session written since: its `lastActivity` stamp, which the status alone misses for a second edit of an already modified file) is the record written, and only then does `git worktree remove --force` take the folder; its own branch stays. **Once removal starts nothing is rolled back**: a removal that stops half way leaves the record, branch and archive as the only copies (a landed worktree's archive is likewise kept unless the folder still holds every archived file); a record that cannot be written rolls back and removes nothing. Kept instead: a saved commit over 256 MB or an archive over 512 MB. (4) the app's HTTP cache past 256 MB is cleared (`session.clearCache`); update installers are now fetched `cache: "no-store"`. (5) Bun's cache past 2 GB is cleared with `bun pm cache rm` (Bun has no age option) while no install runs (`ps`; skipped on Windows, which shows no arguments).

### Scheduled runs (Settings › Schedules; contract `src/shared/schedules.ts`, service `src/main/schedules.ts`)

### Serial queues never wait on a hung step (30 Oct 2026)
- Every serial queue that can wait on a child process or a network call is a `SerialChain` (`src/main/serial-chain.ts`): a step past its bound fails its own caller with `StepStalledError`, aborts its signal, runs `onStall` (ends what it runs), writes a `chain-stall` runtime-log line and the next step starts at once. Bounds: `withRepoLock` (git `exec.ts`, also `disk/care.ts`) `REPO_LOCK_HOLD_MS` 20 min, and the git children of a stopped hold end and later ones never start; setup `#enqueue` `SETUP_STEP_MAX_MS` 30 min (download aborted, runner cancelled); ai-memory `#enqueue` `AI_MEMORY_STEP_MAX_MS` 30 min (runner cancelled); Tailscale `#serial` `TAILSCALE_STEP_MAX_MS` 10 min; `UpdateScheduler.enqueue` (omp, CLI and extension updaters) `UPDATE_STEP_MAX_MS` 30 min. Read-only git commands take no lock. Pinned by `repo-lock.test.ts` and each service's "never ends" case.
- **A stopped step is fenced, not just left behind** (30 Oct 2026, review): a stopped step's promise can still settle later. Every chain step runs in an `AsyncLocalStorage` scope (`serial-chain.ts`: `stepStalled()`, `throwIfStepStalled()`, `fencedCall(fn)`, `currentStepSignal()`); each await that leads to a side effect (a spawn, a write, a state change, an emit) is followed by `throwIfStepStalled()`, and a `catch` or `finally` that writes state is skipped once stalled. Setup, ai-memory: fences inside the pipelines (`#detect`, `#ensure`, `#fetch`, `#settle`, `#updateOmp`, `#enable`, `#purgeData`, …); Tailscale, the CLI and extension updaters: their outside calls (`exec`, `locate`, server, `runUpdate`, `helper`, …) are `fencedCall`s, `#set`/`#emit` ignore a stopped step, and a pass left a row "checking" or "updating" is put back to idle (`UpdateScheduler` `onStall`); git: `execBin` refuses to start and ends its child for a stopped repository-lock holder. A caller that did `void` an enqueue catches the `StepStalledError` (it is in the chain-stall log). A new serial chain follows the same rule. Pinned by each chain's "resumes later" test (the stopped step answers after the next one ran; no spawn, no call, no state change).
- **The whole `withRepoLock` callback is fenced** (30 Oct 2026): git calls were refused for a stopped holder, but a plain `fs.rm` after a late `realpath` was not. Every module whose code runs under the lock imports `fs` from `src/main/fenced-fs.ts` (a Proxy over `original-fs` promises where each call is a `fencedCall`: refused before it starts and again as it returns), never `original-fs`/`node:fs` directly: `scm.ts` (discard's `realpath`+`rm`, the reorder todo file), `worktree.ts` (create's `mkdir`, remove's `realpath`), `session-worktree.ts`, `worktree-orphans.ts` (listing), `disk/saved-worktrees.ts` (archive copy, `rm` rollbacks, the saved record, whose `writeFileAtomic` also has `commitIf: () => !stepStalled()`), `disk/worktree-facts.ts` and `agent-control/branches.ts`. **A call the OS already has is waited for** (30 Oct 2026, review): fencing only before and after a call is not enough, an `fs.rm`/`rename`/`writeFile`/`copyFile` already dispatched (or a git/`lsof` child still exiting) finishes against the next holder's files. `fenced-fs` and `execBin`/`run` record every call in flight per step (`trackEffect`/`fencedEffect` in `serial-chain.ts`), and a `SerialChain` step stopped with calls still running becomes a hold on its chain: the caller fails at once, the next step starts only when those calls ended and waits for them at most `STALLED_DRAIN_MAX_MS` (60 s) counted from the stop; after that every step on that chain (queued or new) fails at once with a `ChainBusyError` (the repository lock turns it into a `repo_busy` `LocalCommandError`) naming what still runs, with a `chain-stall` log line, and the chain is usable the moment they ended, no restart. The lock is never handed on while such a call runs: no fallback that releases it anyway. Read-only git takes no lock and is not held. A non-git child started under the lock (`worktree-facts.ts` `run`: `lsof`, `ps`) never starts for a stopped step and is killed when it stops. New code under the lock uses `fenced-fs` and `execBin`/`run`-style fenced children; `prepareWorktree` (seed and setup hook) runs outside the lock. Test: `src/main/repo-lock-fence.test.ts` (a call not yet started is refused; a dispatched rm/rename/writeFile/copyFile/symlink ends before the next holder starts; past the 60 s bound mutations fail busy and run again after release; a git child that ignores SIGTERM).
- **A nested step is fenced to the step that called it** (30 Oct 2026): `SerialChain.run` made inside another chain's step (a git `withRepoLock` from a setup, updater or Autopilot step; `ShipRunner.drain` from an Autopilot `#settled`) composes its signal with the caller's: when the caller's step is stopped, the nested step's signal aborts (`throwIfStepStalled` and `fencedCall` inside see it), the nested `run` rejects with the caller's reason and frees its chain, a step still waiting for its turn is skipped, and a `run` from a caller already stopped rejects without queueing. The listener on the caller's signal is removed when the nested step ends. A new chain needs nothing extra; a nested step started from a callback outside the caller's `AsyncLocalStorage` scope is not fenced. Pinned by `serial-chain.test.ts` ("nested across chains") and `autopilot-late-step.test.ts` (settle stalls while the ship queue drains).
