## Machine setup and updates

### Machine setup (`src/main/setup/`, contract `src/shared/setup.ts`)
- At launch main detects Bun, omp (through `resolveOmp`, gated by `MIN_OMP_VERSION`), Git, GitHub CLI, Node.js (through the REA probe), agent-desktop (managed or bundled copy) and Tailscale, and installs what is missing **on its own**: no install button, no consent click. `SETUP_ITEMS` = bun, git, omp, gh, node, agent-desktop, tailscale.
  - Required, in order: Bun (`curl -fsSL https://bun.sh/install | bash` / `irm bun.sh/install.ps1 | iex`, user-level; `<abs bun> upgrade` (`bun-upgrade`) for a Bun below the omp package's `engines.bun`); on Windows Git for Windows (an existing install with `bin\bash.exe` is reused, else the PortableGit pinned in `plans.ts` with its SHA-256, extracted without admin into `%LOCALAPPDATA%\ompdesk\tools\git`; never WSL); then omp (`<abs bun> install -g @oh-my-pi/pi-coding-agent`, or `omp update` below the minimum).
  - **OMPdesk runs omp only from its package** (`resolveOmp`), because the bridge's `@oh-my-pi/*` imports cannot resolve inside a compiled omp (Bun standalone build, as installed by stock's installer, Homebrew, mise or stock's launcher repair). `isCompiledOmp`: on POSIX any native executable (a package launches through `#!/usr/bin/env bun`), on Windows a PE with Bun's `.bun` section (bun's own launcher `omp.exe` is a PE without it). A compiled omp earlier in the lookup is passed over; with no other, resolution fails `compiled`, setup calls omp broken and reinstalls the package (`bun-global`). The package's `engines.bun` gates the Bun omp's shebang finds (`bun-too-old`); setup then marks Bun `outdated` (`bunForOmp`, also from the package beside a compiled omp) and upgrades it first.
  - **The user's rule (29 Oct 2026): OMPdesk repairs every toolchain fault itself and never asks the person to run a command.** Because the person often cannot run commands. A missing or broken Bun gets Bun's installer (`bun-script`), a too-old one `bun upgrade`, and a failed `bun upgrade` falls through to `bun-script` in the same attempt (no second back-off count). On Windows `bun-script` is `bunInstallScript`: it renames a running bun.exe aside (install.ps1 deletes it first and exits 0 when it cannot), verifies `bun.exe --version`, puts the old one back and fails otherwise. Before `bun-global`, a compiled omp at `<BUN_INSTALL>/bin/omp(.exe)` is renamed aside (`compiled-launcher.ts`), because `bun install -g` over it fails `EEXIST` on POSIX and silently keeps it on Windows; the aside is dropped once the package's launcher is in place and put back when the install fails. The back-off ledger records the OMPdesk version (`appVersion`); misses of another version are ignored, so a fixed release repairs at its first launch. `manualSteps` lists no commands and no page for Bun and omp, and the `omp.*` failure texts say OMPdesk is repairing it.
  - Optional, in the background once omp works: Git on macOS (`xcode-select --install`); gh and Node (Homebrew on macOS, else the official archive checked against its published SHA-256 into the managed tools dir `<userData>/tools`; `winget … --accept-source-agreements --accept-package-agreements` on Windows, else `unavailable`).
  - **agent-desktop** (`agent-desktop mcp` is the stdio MCP server of the default computer-use engine, `src/shared/computer-use.ts`) **ships in the app** (`<resources>/agent-desktop-bin`, the pinned release; `builtin-packs.md` › Computer use engine), so a first, offline or failed-download launch runs it without installing. Machine setup and the CLI updater install newer releases on macOS **and** Windows (`agent-desktop-archive`, never a package manager) into `<tools>/agent-desktop/` (`managedAgentDesktopDir`; executable `managedAgentDesktop`; `managedBinDirs` puts it on PATH); sessions run that copy once it is at least the bundled version (`pickAgentDesktop`, `src/main/agent-desktop.ts`):
    - Source: `resolveAgentDesktopRelease` (`archives.ts`) reads `releases/latest` of `vercel-labs/agent-desktop` (tag must match `vX.Y.Z`), takes `agent-desktop-v<X.Y.Z>-<target>.tar.gz` (`aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc`; any other CPU is `unavailable`) and its SHA-256 from `checksums.txt`; no checksum, no install. main verifies it (`download.ts`), the script verifies it again.
    - **No release-age hold**, like gh and Node: the newest stable release, checked against the publisher's checksum (`agent-desktop mcp` exists only since `AGENT_DESKTOP_MIN_VERSION` 1.2.0).
    - **Managed or bundled** (`detectAgentDesktop`): only `<tools>/agent-desktop/agent-desktop[.exe]` and the app's copy count; a user's npm/Homebrew copy is ignored, so the engine never runs a version OMPdesk did not verify. The copy a session would run (`pickAgentDesktop`) is `present`, so setup never downloads a version equal to or older than the bundled one: with the bundle intact, a missing, broken (fails or prints no version), outdated (below 1.2.0) or older managed copy reads `present` at the bundled version and is left for the next update. Without a bundle (dev run before `bun run build:agent-desktop`) the managed copy's own state stands and `outdated`/`broken` are reinstalled. The Tool CLI updater looks in the managed folder first (`cli-tools/detect.ts`, `managedOnly`) so a user's copy on PATH never hides it, and lists the bundled copy (owner `managed`) while no managed copy is at least as new; the 4 h check installs a newer release into the managed dir, picked up at the next session start.
    - macOS script (`agentDesktopArchiveScript`): SHA-256 again; `tar -tzf` must list exactly `agent-desktop` and `agent-desktop-macos-helper` (helper beside the CLI), both regular files; the staged CLI must print `agent-desktop <version>`; the old folder is **moved aside and the new one moved in** (never copied over, so a running `agent-desktop mcp` keeps its inode) and `<dest>/agent-desktop --version` runs again (also stops an older command host, as upstream's postinstall does); a failure puts the old folder back.
    - Windows script (`agentDesktopWindowsScript`, modelled on `bunInstallScript`): `Get-FileHash`; `System32\tar.exe -tzf` must list exactly `agent-desktop.exe`, extracted to `agent-desktop.partial`; since Windows can rename but not delete a running exe, an existing exe is moved to `agent-desktop.exe.ompdesk-<ticks>` (older asides dropped first), the new one moved in and `--version` checked, the old one moved back on failure, the aside removed SilentlyContinue.
  - Tailscale (Mobile web) is never automatic (`setupItemAutomatic`): only `installForConnection` and an explicit Retry install it; the user's click is its consent.
  - Claude Code CLI and Codex CLI are never installed: omp signs in to Anthropic and OpenAI itself.
- `download.ts` fetches PortableGit and archives itself (streamed to `<tools>/.downloads`, SHA-256 checked, removed after install) so an item's `progress` carries real bytes; running items also carry `step`/`steps` and `startedAt`. The view shows a determinate bar only for bytes, else an indeterminate one, plus "Step n of m" and elapsed time.
- `paths.ts` appends the managed bin dirs to `process.env.PATH` and sets `GIT_INSTALL_ROOT` (stock `resolveWindowsShell` checks it after the Git for Windows roots) at startup and after each install. After an install it re-reads the login-shell PATH (macOS) or registry PATH (Windows), re-detects, and when omp became usable restarts every local tab in `error`/`exited` and the stats server. No app restart.
- Retry policy: each item once per launch automatically; after three automatic misses only once a day (`BACKOFF_MS` 24 h, `<userData>/setup-state.json`); the user's Retry always runs.
- Every install runs under the setup supervisor (`spawnSupervised`, `setup/supervisor.ts`: OMPdesk's core binary started as `ompdesk-core --supervise`, `native/ompdesk/crates/core/src/supervise.rs`, no running core needed), which ends the installer's whole process tree when its stdin closes: Cancel (also aborts main's download), quit (`SetupService.dispose`) or a crash; it answers `SUPERVISOR_STOPPED_CODE` 130 then. POSIX: the installer leads a session and process group of its own (`setsid`), which a stop signals (SIGTERM, SIGKILL 2 s later) and which is killed once the installer exited. **Windows has no group: the installer starts suspended and runs only once it is in a job object of its own, which every process it starts joins**; a stop ends the job at once and the supervisor exits only once the job is empty (at most 15 s), so a child born while the tree is being ended (a `.cmd` shim's `bun`, which `taskkill /T` once missed with the folder held) never lives on. The job does not end with the supervisor: a descendant of an installer that exited by itself stays, as ai-memory's service host must. Pinned by `runner.test.ts` ("kills what the installer starts while it is being stopped", "kills the installer's whole tree when its stdin closes").
- IPC (`setup:get-state`, `setup:retry`, `setup:cancel`, push `setup:state`) takes item ids only; no handler accepts a command.
- Automatic installs run only in a packaged app outside `OMP_GUI_HEADLESS=1`, or with `OMP_GUI_TEST_INSTALLER` (plus `OMP_GUI_TEST_DOWNLOAD`/`OMP_GUI_TEST_DOWNLOAD_SHA256`: a file every test plan downloads first). Dev and test launches otherwise only detect.
- Setup screen (`components/onboarding/SetupTakeover.tsx`, shown by `App.tsx` from `useMachineSetupNeeded()`): while a local tab's omp is unusable and a required item is missing or installing, one modal dialog covers the whole window (sidebar and title bar included; drag strip and OS window controls stay live). Everything beneath is `inert`; menu actions, omp:// links, shortcuts and drops are no-ops through `useMachineSetupStore.takeover`; Tab is trapped, and focus opens on the dialog itself, never its first control. Each required item is one row with phase and progress; command, install location and output sit in one closed "Show details" disclosure (an OS prompt it will raise stays visible); a failure adds the banner with reason, manual steps and Retry. When required setup finishes it fades out (reduced motion skips the fade) into the first-run flow (`FirstRunGate` → provider step). Optional items and remote tabs never show it. Every item stays listed in Settings › Updates & about › This computer (`MachineSetupSection.tsx`).
- `.github/workflows/setup-assets-health.yml` downloads every pinned setup file weekly through `download.ts` (`scripts/setup-assets-health.ts`; `gh workflow run setup-assets-health.yml` runs it now) and keeps one issue open while any fails.

### Connect installs its tool
- `SetupService.installForConnection`: a connection the user starts that needs a missing optional item installs it right then, as the user's own action: past the daily back-off and the once-per-launch rule, queued behind any running install, only in a launch that installs on its own (else it only detects). The connection carries on when the tool lands. Callers: gh (GitHub sign-in), node (`LocalMachine.setBuiltinRea` turning the built-in REA on while Node is missing or too old), tailscale (`tailscale/service.ts`).
- Connect GitHub (Settings › General, the PR center's signed-out card; `onboarding/GithubSignIn.tsx`) calls `GithubAuthService.startLogin`: with gh missing the flow is `installing`, awaits `installGh`, then starts `gh auth login`. No gh after the install → `gh_install_failed`; nothing able to install it → `gh_missing`; Cancel stops it (`cancelGhInstall`).
- `onboarding/SetupInstallInline.tsx` shows the item inline (step, bytes, clock; reason plus Retry after a failure; the download page when nothing can install it), also for setup's own background gh install. A paired host's tab: the host's UI and setup install on the host.
- git/gh lookups (`local/git/exec.ts` `resolveBin`, `execBin`) read the spawn PATH on every call (`spawnPath` shares the cached login-shell probe, which `refreshPath` drops after an install), so a fresh gh is found without a relaunch. Never keep a copy of PATH from the first git call.
- No stock omp provider login shells out to a CLI (they are OAuth/device-code flows in pi-ai's `registry/oauth/`; perplexity only reads its macOS app's token), so no provider sign-in installs anything.
- `e2e/github-cli-install.e2e.ts` (fake installer) covers gh off PATH and in back-off, download progress, offline failure with Retry, install into the managed tools dir and sign-in.

### omp updates itself (`src/main/omp-updater.ts`, contract `src/shared/omp-update.ts`)
- OMPdesk's own update is `updater.ts`, installed by itself unless the user turns `appAutoUpdate` (default on) off.
- Main asks stock `omp update --check` (`SetupService.latestOmp`) at launch (after machine setup's first pass) and every 4 h, doubling the wait per failure in a row up to 24 h; while omp is missing nothing is checked. When the answer is newer than the installed omp (`compareVersions`) it runs stock `omp update` through `SetupService.updateOmp` (the omp item's `omp-update` plan under the setup supervisor): background, no click, queued behind any install, **never waiting for a turn to end** (the user's rule: a running omp keeps the code it loaded).
- **Bun first, package always**: because stock's update on a too-old Bun "repairs" the launcher with a compiled omp the bridge cannot run. Before the installer, `updateOmp` reads the target's manifest (`bun pm view <pkg>@<v> --json` in the update's environment, `SetupServiceDeps.ompRelease`): a failed lookup is a `check` failure and nothing runs; `omp.dist` "binary" is not installed; a Bun below `engines.bun` is upgraded through the bun item (`bun upgrade`) and an upgrade that falls short stops the update. After it, an omp that is not usable is put back by setup's required pipeline at once (`#runRequired(true, false)`: no `onOmpReady`; the updater's `resume` restarts the tabs).
- Check and update share one environment (`ompUpdateEnv` in `omp-runtime.ts`): the detected omp's folder first on PATH (stock updates the first `omp` on PATH) and, for a `bun install -g` launcher, `BUN_INSTALL=<its Bun root>`. So both follow the user's registry (.npmrc, bunfig, `npm_config_registry`), channel and install method, agree, and land in the omp OMPdesk runs, never another `omp` earlier on PATH. `get_omp_update` (a paired host's check, `local/misc.ts`) uses it too.
- Why it is safe: `bun install -g` replaces package files by new inodes, and the bridge's literal `@oh-my-pi/*` imports resolve to the running omp's bundled singletons (`health.ts`). Processes that read omp's files from disk (stats server, stock helper) are stopped before the installer and started after it. **An install OMPdesk did not run** (a terminal's `omp update` or `bun install -g`) stops nothing, so the stock and extensions workers check omp's `package.json` (time and size) at every request they are idle for, and one started on another install is let go and started fresh (`StockHelper.#outlivedItsOmp`; never while a request is on its way to it, never the terminals worker, whose shells would go with it), because a worker that outlived a reinstall imports new files into an old module graph ("Export named … not found" on every worktree create, 12 Nov 2026). Pinned by the two omp-change cases of `stock-helper.test.ts`. Known limit: the old process's lazy hashed assets in `dist/` vanish, so those can fail in a tab until it restarts. On Windows locked files fall to stock's EBUSY/launcher repair; a failed install is kept in `OmpUpdateState.failure` and retried at the next check.
- After success main re-detects omp (`refreshSystemOmp`), starts the stats server on it, restarts every idle local tab and every idle tab it hosts for paired devices on their own session file, and restarts a busy tab one tick after its turn ends (`src/main/omp-restart.ts`; `SidecarPool.restartOnNewOmp`, `LocalHostServices.restartOnNewOmp`; `asleep` tabs need nothing). Composer drafts survive. The restarts re-ask each bridge's `capabilities` (`BridgeHealth` is keyed by omp version), so a feature the new omp lacks shows the `unsupported_omp` warning toast. Success shows one quiet "omp updated to X" toast in one window.
- One switch, "Keep tools up to date" (pref `toolsAutoUpdate`, `TOOLS_AUTO_UPDATE_PREF`; default on; a stored `false` turns it off), covers omp, the tool CLIs and extensions; it and omp's manual "Update now" live in Settings › Updates & about › This computer (`OmpUpdateRows.tsx`). IPC (`omp-update:get-state`, `omp-update:now`, push `omp-update:state`, `omp-update:updated`) carries no version, command or path.
- Each computer updates its own omp under its own pref, always through its own `OmpUpdater`. On a paired host's tab Settings › Updates & about shows the host's row (`HostOmpUpdateRow`); its button only asks the host to run its updater (`host.ompUpdate.now` / `host-omp-update:now`; state `host.ompUpdate.get` / `host-omp-update:get`; the host pushes changes as `host.ompUpdate.changed`, forwarded as `host-omp-update:state`), so it never overlaps the host's scheduled update. There is no `omp_update` RPC and no second `omp update` path.
- Scheduled checks run only in a packaged app outside `OMP_GUI_HEADLESS=1`, or in a test launch with both `OMP_GUI_TEST_INSTALLER` and `OMP_GUI_TEST_OMP_UPDATES=1` (installer called `<installer> omp omp-update`).
- Tests: `e2e/omp-auto-update.e2e.ts` with `OMP_GUI_TEST_LATEST_OMP` (what `update --check` reports), `OMP_GUI_TEST_UPDATE_CHECK_LOG` (each check's first PATH entry), `OMP_GUI_TEST_VERSION_FILE`, `OMP_GUI_TEST_BOOT_LOG`, `OMP_GUI_TEST_UNAVAILABLE_AFTER_UPDATE`; `src/main/setup/omp-update-install.test.ts` runs the real `bun install -g` against a fake registry (`src/main/test-omp-registry.ts`) in a temp HOME and BUN_INSTALL, a second omp first on PATH staying untouched.
- **Bun's transpiler cache is off for a session's omp on Windows** (`ompBunDefaults` in `src/main/omp-runtime.ts`, `BUN_RUNTIME_TRANSPILER_CACHE_PATH=0`, set under the user's own environment at `SidecarManager` spawn), because there the cache made omp's start slower. macOS keeps bun's default until it is measured there.

### `UpdateScheduler` (`src/main/update-scheduler.ts`)
- The omp, tool CLI and extension updaters share one loop: it ticks at start in a scheduled launch, re-arms its timer from the end of each tick (a rejected tick does not end the schedule), queues passes one at a time (`enqueue`, dropped once disposed) and owns the back-off (`nextCheckDelay`, per item `settleBackoff`; `CHECK_INTERVAL_MS` 4 h, `MAX_CHECK_INTERVAL_MS` 24 h).
- omp backs off its timer by its own failure count and joins a running check instead of queueing a second; CLI and extension updaters back off per tool or row (a cancel is no failure). `updater.ts` (its own 5-minute check) is not on it.

### Tool CLIs of connected accounts (`src/main/cli-tools/`, contract `src/shared/cli-update.ts`)
- Follows "Keep tools up to date" (`toolsAutoUpdate`, default on; a user may pin a vendor CLI; OMPdesk needs no minimum version of one). Runs at launch (after setup's first pass) and every 4 h with per-tool back-off (`CliUpdater`).
- Main reads providers with a stored credential from stock's store (stock-helper `accounts.providers` = `discoverAuthStorage().credentials.list()`, ids only; `sdk` is listed under `providers` in `capabilities.ts`) and maps them to CLIs (`catalog.ts`: anthropic → `claude`, openai-codex/openai → `codex`, google-gemini-cli/google → `gemini`, cursor → `cursor-agent`, github-copilot → `copilot`, `gh` and its `gh-copilot` extension), plus what setup installs (gh, and Node and agent-desktop in the managed tools dir only; agent-desktop also as the bundled copy until a managed one is at least as new). Setup's tools are one row each in Settings › Updates & about › This computer (`MachineSetupSection`, with update method and "Update now"), not in `CliUpdateRows`; "Keep tools up to date" covers them.
- It **never installs** a vendor CLI: only an installed one is listed and updated, by the owner found from its resolved executable path (`detect.ts classifyInstall`): Homebrew (`brew upgrade [--cask] <name>`), a global npm (`npm install -g --prefix <that prefix>`) or Bun package (`bun install -g` under that `BUN_INSTALL`), winget (`winget upgrade --id`), the vendor's updater (`claude update`, which also owns a Claude Code in npm/Bun; `cursor-agent update`; `gh extension upgrade gh-copilot`), or setup's verified archive for the managed gh, Node and agent-desktop (the latter's release from `resolveAgentDesktopRelease`). System (`/usr/bin`, Xcode CLT, `C:\Windows`), app-bundled and admin-only installs are listed with their reason and never touched; no sudo.
- The check asks the owner first (`npm view`, `bun pm view`, `brew outdated --json=v2`, `winget list --upgrade-available`, the release feed), updates only when newer (`compareVersions`), runs `SetupService.runToolUpdate` under the setup supervisor (queued behind installs, never touching setup items' state) and detects again (`updated` or `not-updated`).
- Running-process rule: npm and Bun replace the whole package dir and Homebrew removes the old keg, so a running Node CLI would load mixed versions. So on macOS an npm/Bun/Homebrew update of a Node CLI waits while a process of it runs (`ps`, `plans.ts waitsForIdle`/`runningIn`; result `deferred`, no back-off, retried next check). A native binary (gh, agent-desktop), vendor updaters and managed copies update at once. On Windows a file a running tool holds fails the update, which is recorded and retried. A failure backs off like omp's.
- IPC `cliUpdate.getState/now(id?)/onState` carries tool ids only (an unknown id throws; no command, path or version crosses it); opening Settings rescans. Each computer, and each paired host, updates its own tools.
- Homebrew prefixes (`/opt/homebrew/bin`, `/usr/local/bin`) are also searched when the login-shell PATH omits them (`resolveBin` for gh/git, setup's gh detection, `cli-tools/detect.ts`). The PR and GitHub centers show the connect card (install, then sign in) instead of a download link for a missing gh on this computer; a paired host's tab keeps the link.
- Tests: a test launch checks on its own only with `OMP_GUI_TEST_INSTALLER` plus `OMP_GUI_TEST_CLI_UPDATES=1` (runs `<installer> cli-<tool> <method> check|update`; `e2e/cli-update.e2e.ts`). `OMP_GUI_TEST_BREW_DIRS` (PATH-style list, empty = none) replaces Homebrew's prefixes so the developer's brew never answers a test.
- Windows: a tool is found only as `<bin>.exe` or `<bin>.cmd` (npm's bare `<bin>` is a POSIX script). A `.cmd` runs through cmd.exe with the omp shim's quoting (`src/main/spawn.ts`: `launcherNames`, `findOnPath`, `spawnCommand`/`spawnArgs`/`needsShell`: the one PATH lookup and Windows spawn rule every external tool uses). `detect.ts cmdShimTarget` reads the package file an npm cmd-shim runs (`"%dp0%\node_modules\<package>\<bin>"`) to find its npm prefix. A Bun global is Bun's shim `.exe` beside a `<bin>.bunx` naming the target in UTF-16LE up to a `"`, relative to the folder above the shim's (`detect.ts bunxShimTarget`), so Bun's install owns it.

### Extensions of connected omp (`src/main/ext-update/`, contract `src/shared/extension-update.ts`, helper contract `resources/gui-bridge/stock-helper/extensions-contracts.ts`)
- Follows "Keep tools up to date" (`toolsAutoUpdate`, default on); rows in Settings › Updates & about › This computer › Extensions. Marketplaces, plugins, skills and MCP servers, on `CliUpdater`'s schedule (after setup's first pass, every 4 h, per-row back-off `nextCheckDelay`, failures recorded, deferred rows retried; `omp` being installed defers without back-off). `ExtensionUpdater` reads the inventory in the extensions worker (local files, no network) and works marketplaces → plugins → skills → MCP, one row at a time.
- Marketplaces: stock `updateMarketplace` (what `marketplace_action update` runs).
- Plugins: marketplace installs by stock `checkForUpdates`/`upgradePlugin`, npm and git plugins by `PluginManager.upgrade`. Stock has no user pin for a marketplace plugin (the catalog's `ref`/`sha`/`version` is the author's; upgrade follows it).
  - `upgrade(name)` reinstalls an npm plugin at the registry's latest whatever its spec says, so OMPdesk reads `plugins/package.json` and calls upgrade only when the spec is what a bare install writes (`pkg`/`pkg@latest` → `^x.y.z`, `pkg@beta` → `^<tagged>`, exact and range specs verbatim; `^<installed>`, `latest`, `*` follow latest) and latest is strictly newer.
  - An exact or ranged npm spec and a git commit/version-tag ref are pinned: checked, shown as "update available", never moved, not even by Update now. Linked plugins are skipped.
  - npm/git/linked plugins are user scope only (stock's `PluginManager` has no project scope); marketplace plugins also per project registry of the open local tabs' folders.
- Skills: stock records a source only for skills-registry installs (`skills.json`/`skills.lock.json`, `skillshare/manifest.ts`; `omp skill install|update|uninstall` take `@scope/name`; no git-source skill), so those update by `updateSkillPackages` (exact range = pinned; a version that ships scripts is never approved for the user: `needs-approval`). Plugin-provided skills follow their plugin (one grouped row); plain local files are one "local, not updated" row.
- MCP servers (the user's config is never written):
  - The built-in REA is listed as pinned to the OMPdesk release; URL servers are skipped (`remote`).
  - An unpinned `npx`/`bunx`/`uvx` package is "follows latest at start" and its cache is not touched (a bare `npx -y pkg` already starts the new version; warming a cache would execute the server). A pinned `pkg@1.2.3` is checked against the registry and shown as an available update, config untouched.
  - A global binary is updated by its owner (`cli-tools/detect.ts classifyInstall` plus pipx `/pipx/venvs/<pkg>/`, uv tool `/uv/tools/<pkg>/`, pip via the shebang python's `importlib.metadata`) through `SetupService.runToolUpdate` under the supervisor (system, bundled and admin-only installs listed and skipped, no sudo).
  - Running rule: a script (shebang) whose owner replaces package files in place (npm/Bun, Homebrew, pipx/uv/pip) waits while a `ps`-visible process of it runs (`deferred running`, retried); a native binary updates at once; Windows has no scan, a held file fails and is retried.
- Applying to live tabs (`src/main/extension-reload.ts`, `SidecarPool.applyExtensionUpdate`, `LocalHostServices.applyExtensionUpdate`): one `ExtensionApplyPlan` per pass. An idle ready tab reloads now (bridge `extension_update.reload` = stock `reloadPluginState`, what `/reload-plugins` does); a plugin that ships extensions/tools/hooks (`activation: restart-required`, `extensions/activation-core.ts`) restarts the tab on its session file (`omp-restart.ts` pattern); an updated MCP package is reconnected (`extension_update.reconnect` = stock `MCPManager.reconnectServer`); a busy tab applies one tick after its turn ends; `asleep` tabs need nothing.
- Every stock internal the worker uses is in `capabilities.ts` and `health.ts` `LOADERS`. IPC `extensionUpdate.getState/now(key?)/onState` carries row keys only. Each computer, and each paired host, updates its own.
- Where the rules are: what a server's launch is, the rows, the running rule, what a binary's file says and the lookups' parsers are the core process's (`native/ompdesk/crates/core/src/ext/`, native-rust › 4c). `src/main/ext-update` keeps the updater, the PATH lookup and the package managers' ownership and commands it shares with cli-tools.
- Tests: a test launch checks only with `OMP_GUI_TEST_INSTALLER` plus `OMP_GUI_TEST_EXT_UPDATES=1` (MCP binary checks/updates run `<installer> cli-mcp-<name> <method> check|update`; `e2e/extension-update.e2e.ts`).

### Disk care (`src/main/disk/`, contract `src/shared/disk-care.ts`)
- The user's rule: OMPdesk keeps the disk it fills in check by itself, **zero settings, nothing lost**. `DiskCare` runs once 2 min after launch (skipped when a run ended within 20 h; the daily timer comes due instead), then daily, one at a time; the Settings button and the agent's `disk.clean` join a running one. Every action is one `disk-care` line in gui-runtime.jsonl (`run` summary, `artifacts`, `worktree-landed`, `worktree-saved` with its `git worktree add …` restore line, `kept` with the reason, `http-cache`, `bun-cache`, `failed`). State (last run, last measurement) in `<userData>/disk-care/state.json`.
- **Measured on the user's Mac (20 Oct 2026)**: worktrees under `~/.omp/wt` are the bulk of the disk use, and almost all of it is regenerable build output and dependencies; that is why the steps below target them.
- **Idle thresholds by evidence**: build output goes after `DISK_CARE_ARTIFACT_IDLE_DAYS` 3 (a wrong guess costs only a reinstall or rebuild) and a worktree with unlanded work after `DISK_CARE_REMOVE_IDLE_DAYS` 14 (twice the longest resume gap seen in session files). Idle = no open tab on any device (`openFolders`), no running process with its cwd inside (`lsof -d cwd` on macOS, `/proc` on Linux; Windows cannot tell, so these two steps keep everything there), and nothing changed for N days: HEAD commit, git dir HEAD/index/reflog, every tracked and untracked file, every ignored entry no tool makes again, and stock's newest session file for that cwd (`lastActivity`).
- **Every step keeps a worktree whole** (build output included) while an open tab on any device holds it, git lists it locked, a known process works in it, or a rebase, merge, cherry-pick, revert or bisect is half done (`inProgressOperation`; checked under the removal claim in the artifact step, in `archiveBeforeRemove` for the landed sweep and the person's Remove, and before a save).
- **A save never rewrites bytes**: a worktree whose restore could write other bytes than it holds is kept, not saved: `core.autocrlf` true/input, `core.eol`, or any `text`/`eol`/`crlf`/`filter`/`working-tree-encoding`/`ident` attribute (`-text` excepted) on a file the save carries (`rewrites_bytes` in `crates/core/src/disk/saved.rs`: `git ls-files --cached --others --exclude-standard` with `:(attr:…)` pathspecs, so git itself reads every attributes source; never a parsed or lower-cased path). Pinned by the attribute-source cases and the CRLF/LF/mixed save → restore sha256 round trip of `disk/disk-care.test.ts`, which run in `test:platform` on Windows too.
- **Regenerable by evidence, never by name** (`crates/core/src/disk/regenerable.rs`, one rule table): a `CACHEDIR.TAG` with the standard signature; `node_modules/` beside a tracked `package.json` with a tracked lockfile at or above it; `__pycache__/` holding only `.pyc`; the output folder of a build tool the package depends on and **builds with** in a script (`vite build`, `electron-vite build`, `next build` → `.next/`, `next export` → `out/`, `astro build`, `parcel build`, `nuxt build|generate`, `tsc` without `--noEmit`; a bare `vite` or `next dev` proves nothing), or a `--outDir` a script passes; a tool's config file's literal `outDir`/`output` replaces the default, and one set any other way (`outDir: resolve(…)`) leaves the output unknown, so nothing counts; an ignored path whose `.gitignore` line sits under a comment naming build output, artifacts, generated files, caches or dependencies. Anything else (a hand-made `dist/`, `tmp/`, `.env`, a local database) is data.
- Steps: (1) drop regenerable entries of idle orphans; (2) the landed sweep (Work tree › Swept by themselves) with the archive first; (3) an idle orphan with unlanded or uncommitted work, not locked, no half-done operation: what is staged becomes one commit (from a copy of the index) and the working tree's tracked changes and untracked files one more on top (scratch index), `commit-tree --no-gpg-sign`, no hook, on a new `ompdesk/saved/<folder>-<date>` branch (HEAD → staged → working; never its own branch, never main; a detached HEAD's commits get the branch too). **No secret enters a commit** (`secretIn`): a file whose name says secret (`.env*`, keys, `credentials*`), whose whole content holds a credential by the central redactor's rules (`resources/gui-bridge/redactor.ts`: a `<secret>` or `<token>` appears; a lockfile's long hashes count too, which only archives it), or that cannot be read whole (over `SECRET_SCAN_MAX_BYTES` 16 MB, unreadable) goes to the archive instead; a staged one keeps the worktree. Everything git does not keep and no tool makes again plus those files is copied to `<userData>/disk-care/saved/<id>/` (0700/0600, copy-on-write, verified by a walk; never in git, never synced, never uploaded). Only when nothing moved since the save read the worktree (no process inside, no half-done operation, the same HEAD and status, and no tracked, untracked or archived ignored file, index, reflog or session written since: its `lastActivity` stamp, which the status alone misses for a second edit of an already modified file) is the record written, and only then does `git worktree remove --force` take the folder; its own branch stays. **Once removal starts nothing is rolled back**: a removal that stops half way leaves the record, branch and archive as the only copies (a landed worktree's archive is likewise kept unless the folder still holds every archived file); a record that cannot be written rolls back and removes nothing. Kept instead: a saved commit over 256 MB or an archive over 512 MB. (4) the app's HTTP cache past 256 MB is cleared (`session.clearCache`); update installers are fetched `cache: "no-store"`. (5) Bun's cache past 2 GB is cleared with `bun pm cache rm` (Bun has no age option) while no install runs (`ps`; skipped on Windows, which shows no arguments).
- **Left alone, by measurement**: omp logs (stock `pi-utils` `pruneStaleProcessLogs` already bounds them), sessions (never deleted; stock has no compressed form), `stats.db` (stock omp-stats has no retention), `~/.omp/puppeteer` (stock's browser).
- **Measuring is cheap** (the walk is the core process's, `crates/core/src/disk/sizes.rs`; `disk/tree-sizes.ts` is its client): every run ends with the Disk row's parts, and the HTTP and Bun cache checks measure too, without reading every file each time. `TreeSizes` keeps, per folder, its mtime, inode, the bytes of its direct files and its child folders in `<userData>/disk-care/sizes.json`, and reuses a folder while both are unchanged and its mtime is more than `RACY_MS` (2 s) older than the reading that saw it (git's racy rule, for coarse filesystem timestamps). Only the write-once parts reuse (`REUSED_PARTS`: worktrees, Bun cache); sessions, logs, stats and userData are appended to in place and are read in full. A full walk at least every 7 days (`FULL_WALK_EVERY_MS`) bounds what a reused folder cannot see (a file rewritten in place, a second link to a file in an unchanged folder). 4 file calls at once across the core process; allocated blocks on macOS (equal to `du -sk`), sizes on Windows; a hard-linked file counts once per part, as `du` counts it. Each run logs `usage` {ms, reused, lstat, readdir}. Pinned by `tree-sizes.test.ts` (each change kind vs a full walk, changed folders only, hard links, the bounded misses, racy rule, unreadable file) and the first case of `disk-care.test.ts`.
- Surfaces: Settings › Updates & about › This computer one Disk row (`DiskCareRow.tsx`: total, last freed, breakdown in (i), Clean up); the Work tree's Saved worktrees with Restore; agent actions `disk.status` (read) and `disk.clean` (change, no card). IPC `disk-care:get-state`, `disk-care:run`, push `disk-care:state`. Each computer, and each paired host, cares for its own disk.
- **One listing per run**: the artifact step walks the orphans' paths alone (`orphanWorktreePaths`, one `git worktree list`) and keeps what it read of each before any claim; after it, one `listAllOrphans` reading of every orphan's state serves the landed sweep (`sweepLandedWorktrees`' `listed`) and the save step (minus what the sweep removed), whose idle pre-filter reuses the artifact step's read (its idle days only when nothing was dropped: a drop writes the worktree's folder). A read of a worktree (`readWorktreeFiles`, `lastActivity`) runs `ls-files` once (`WorktreeFiles.tracked`), and the git dir comes from the worktree's `.git` (`git_dir` in `crates/core/src/disk/facts.rs`). The claimed reads and `stillSame` are unchanged, so fewer git processes run without weakening any check.
- Tests: `disk/disk-care*.test.ts` (six files on one fixture, `disk-care-fixture.ts`, so they run side by side; real temp repos covering: regenerable vs data folders, `.gitignore` sections, dev-only build scripts and computed `outDir`, save/remove/restore with no secret in git, staged vs working placement, a staged secret, edits during the save, changes after the shared listing (`disk-care-shared-listing.test.ts`), each keep reason, unknown processes, landed `.env` archive, a half-way removal, a failed record write), `DiskCareRow.test.tsx`, `WorkTreePanel.test.tsx`, `app-control.test.ts`.
- **Windows: Electron's `fs` holds the `.asar` files disk care walks** (Code conventions has the mechanism), which kept worktrees from being removed and folders from being deleted while the app ran. What of `src/main/disk/` still touches a user's folder does it through `original-fs` (or `fenced-fs` over it); the walks, copies and removals are the core process's since unit 2g, which has no asar at all. Pinned by `e2e/disk-care-asar.e2e.ts` (real app and git, `.asar` archives in worktrees and the Bun cache; the run has no failure and the folders delete while the app runs).

### Scheduled runs (Settings › Schedules; contract `src/shared/schedules.ts`, service `src/main/schedules.ts`)
- Main checks every 30 s (`SCHEDULE_TICK_MS`) and starts stock `omp -p [--model] [--yolo]` in the schedule's folder, only while OMPdesk is open. Times missed while it was closed are skipped; a start due while the previous run still goes is recorded as skipped. Stock omp has no scheduler.
- Each computer keeps and runs its own schedules. A tab on a paired host shows the host's in Settings › Schedules (`SECTION_SCOPE` `host`, "Selected host"): `SCHEDULES_COMMAND`/`SCHEDULES_LOG` take the focused tab's `device` and go through `machineFor` (`MachineServices.schedules`/`scheduleLog`/`createSchedule`; `RemoteMachine` → `host.schedules.command|log|create`), the folder picker browses the host, and the host pushes each change as `host.schedules.changed` (`LocalHostServices.schedulesChanged`), forwarded to the device's windows as `host-schedules:state` (`schedules.onHostState`). Pinned by `SchedulesSection.test.tsx`, `SettingsDeviceScope.test.tsx`, `machine-services.test.ts`, `schedules.test.ts` (concurrent creates).
- A schedule a paired device saves on a host (its Settings or its agent's `ompdesk_schedule`; `host.schedules.command` passes the peer as `origin`) is that device's: `Schedule.device`, cleared when someone saves it on the host itself. Every start of it, timed or run now from the device, takes one of that device's daily model requests through `ScheduleServiceOptions.reserve` (`RemoteDevices.reserveModelRequest` → `PeerQuota`): past the limit a timed start is recorded `skipped` with the reason and omp never launches, and a device's run now fails `remote_limit_reached`; a run that could not start gives the request back. The host's own run now of it is not charged. Pinned by `schedules.test.ts`, `host-services.test.ts`.
- Each run goes through the setup supervisor (`spawnSupervised`, the prompt file as omp's stdin), so a Stop, a quit or a crash kills omp's whole tree.
- A schedule with `wakeSession` (a session's own wake-up, `ompdesk_schedule {target: "self"}`; details under Schedules and Autopilot in `control-tools.md`) starts no omp: `#startRun` calls the option `wake(schedule, runId)`, which delivers the prompt into that session and returns a `RunProcess` that follows the turn it started (agent-control `wakeSession`): the run ends with that turn (succeeded, failed with the turn's error, stopped when the turn was aborted), fails when the tab closes first or no turn starts within 2 min (`WAKE_TURN_START_MS`), and its Stop aborts the turn (`TurnStopBy` `schedule`). `ScheduleService` takes `tickMs` and `minuteMs` options (`nextRunAt` also takes `minuteMs`); only a test launch sets them, through `OMP_GUI_TEST_SCHEDULE_TICK_MS` and `OMP_GUI_TEST_SCHEDULE_MINUTE_MS` (`index.ts`). Pinned end to end by `e2e/routines.e2e.ts` ("a check a session schedules for itself wakes its own turn in its own tab").
- **Routines** (the owner's order; contract `ScheduleFrequency` in `shared/schedules.ts`, zod in `shared/schedules-schema.ts`). Besides `interval`/`daily` a schedule starts `once` or on an `event`.
  - `once` (`at`): its timed start turns it off, which is what spends it. `nextRunAt` reads only its moment (null once passed, as after the app was closed), never its runs, so a Test before the moment keeps the start, and moving a spent one to a new moment and turning it on schedules it again. A save of a moment already past is refused. Spent ones past `SCHEDULE_ONCE_DONE_KEPT` 20 are deleted; an agent's (`[agent] …`) spent once is deleted as soon as its run succeeded and a day after a failed run, and an agent schedule's runs go after 7 days (`ScheduleService.prune`).
  - `event` (`ScheduleEvent`: `webhook {key}`, `github {repo, events}`, `files {path}`, `git {repo, branch}`, `session {events, folder?}`; no clock, `nextRuns` null). `ScheduleService.fire(id, detail)` starts an event run whose prompt gets "What fired this run:" and the detail lines (`ScheduleRun.trigger` `event`, `detail`); events while it runs are kept (`#pending`, newest 20 lines) and start exactly one more run after it with all of them.
  - **Loop guard**: a routine whose every run is asked for again before it ends is turned off after `ROUTINE_CHAIN_LIMIT` (10) such runs in a row, recorded as a `skipped` run whose reason says so; it guards against a routine firing itself, not a rate cap (the user's no-cap rule, AGENTS.md), so no count or rate limit exists.
  - A webhook key is made by the service when a draft carries `key: ""` and kept through every later save (`cleanFrequency`); `webhook(id, bearer, detail)` compares it in constant time (`fired`/`unknown`/`denied`/`off`). A run now of an event routine is its Test (`manual`, "A test run: no event fired"); `e2e/routines.e2e.ts` pins it from Settings › Schedules: Run now on a session's own routine wakes that session, the run row reads "run by hand" and `ompdesk_schedule runs` "succeeded (test)". The sources that call `fire` live in `src/main/routines/` (see that folder's module docs).
- **Email trigger** (the owner's order: no inbound mail server, no Funnel): `{source: "email", account, from?, subject?, to?}` polls a mailbox the owner added in Settings › Schedules › Email accounts every `EMAIL_POLL_MINUTES` (2) with the small IMAP client in `routines/imap.ts` (LOGIN, read-only EXAMINE, UID SEARCH past a UIDVALIDITY+UID cursor, UID FETCH of headers and the first 6 KB of text with BODY.PEEK so nothing is marked read; no package; tested against `routines/fake-imap.ts`).
  - The first read, or one after the mailbox was recreated, is a baseline; each new mail passing the filters (text contained, case aside; `to` in To/Cc/Delivered-To, so a plus-address works) fires once with sender, recipients, subject, date and up to 600 characters of its plain text (a multipart's text/plain part, quoted-printable and base64 decoded).
  - Loop guards: `Auto-Submitted` other than `no`, and a reply sent from the account's own address (`In-Reply-To`), never fire.
  - Accounts (`src/main/mail-accounts.ts`, contract `shared/mail-accounts.ts`): `<userData>/mail-accounts.json` without passwords; each password is base64 of `safeStorage.encryptString` in `<userData>/mail-accounts/<id>.bin` (0600), decrypted only to log in and then kept in memory. IPC `MAIL_ACCOUNTS_COMMAND` (list, save, remove, test) never returns a password, is `never(CREDENTIALS)` for agents (`app-channels.ts`) and serves this computer only (a paired host's accounts are set on the host).
  - TLS checks the server's certificate against its host; a test launch uses plain TCP to the fake server (`OMP_GUI_TEST_IMAP_PLAIN`, `plainImapConnect` in `mail-accounts.ts`) and a short poll (`OMP_GUI_TEST_EMAIL_POLL_MS`). Pinned by `imap.test.ts`, `email.test.ts`, `mail-accounts.test.ts`, `MailAccounts.test.tsx` and `e2e/routines.e2e.ts` ("an email routine").
  - macOS Mail.app's local store is not read, because it needs Full Disk Access and an undocumented layout while IMAP covers every provider.
- **Triggers across a relaunch and their failures** (the owner's order): where each git, GitHub, files and email trigger stood is kept in `<userData>/routine-marks.json` (`routines/marks.ts` `FileMarks`, 0600, written after each change and at quit; keyed by routine id and its trigger as set).
  - A source started with its mark fires once for what changed while OMPdesk was closed (git: commits since the kept head; GitHub: ids not seen and commits since the kept head, within what the endpoints still list; email: mail past the kept UID; files: a listing of up to `FILES_LISTING_MAX` (2,000) files with modified time and size, compared added/changed/removed, taken at start and two seconds after each burst, the routine's own writes too) and saves the new mark before it fires, so nothing fires twice.
  - A routine turned off, edited, deleted or everything paused loses its mark (`RoutineTriggers` drops it), so what happens then never fires later.
  - Sources start once the first window has loaded (`ready`, `firstWindowLoaded` in `index.ts`), so a run a relaunch fires can open its session.
  - A source's failure (told once per distinct message, `failureReporter`) is a runtime-log line and `ScheduleService.triggerFailed`: a `failed` run with trigger `event` and the reason ("Its trigger failed: …"), which nothing ran, in the routine's history.
  - Pinned by `triggers.test.ts` (relaunch, off drops the mark, ready, failure), each source's "across a relaunch" tests, `marks.test.ts`, `schedules.test.ts` ("records a trigger's failure") and `e2e/routines.e2e.ts` ("a git routine fires once after a relaunch").
- Schedules and their runs live in `<userData>/schedules.json` (the newest `SCHEDULE_RUNS_PER_SCHEDULE` 20 per schedule, `SCHEDULE_RUNS_KEPT` 200 in all, so one busy routine never pushes out another's history); run output in `<userData>/schedule-runs/<runId>.log`. Pinned by `schedules.test.ts` ("routines: …").

### Serial queues never wait on a hung step (30 Oct 2026)
- Every serial queue that can wait on a child process or a network call is a `SerialChain` (`src/main/serial-chain.ts`): a step past its bound fails its own caller with `StepStalledError`, aborts its signal, runs `onStall` (ends what it runs), writes a `chain-stall` runtime-log line and the next step starts at once. Bounds: `withRepoLock` (git `exec.ts`, also `disk/care.ts`) `REPO_LOCK_HOLD_MS` 20 min, and the git children of a stopped hold end and later ones never start; setup `#enqueue` `SETUP_STEP_MAX_MS` 30 min (download aborted, runner cancelled); ai-memory `#enqueue` `AI_MEMORY_STEP_MAX_MS` 30 min (runner cancelled); Tailscale `#serial` `TAILSCALE_STEP_MAX_MS` 10 min; `UpdateScheduler.enqueue` (omp, CLI and extension updaters) `UPDATE_STEP_MAX_MS` 30 min. Read-only git commands take no lock. Pinned by `repo-lock.test.ts` and each service's "never ends" case.
- **A stopped step is fenced, not just left behind**, because its promise can still settle later. Every chain step runs in an `AsyncLocalStorage` scope (`serial-chain.ts`: `stepStalled()`, `throwIfStepStalled()`, `fencedCall(fn)`, `currentStepSignal()`); each await that leads to a side effect (spawn, write, state change, emit) is followed by `throwIfStepStalled()`, and a `catch` or `finally` that writes state is skipped once stalled. Setup, ai-memory: fences inside the pipelines (`#detect`, `#ensure`, `#fetch`, `#settle`, `#updateOmp`, `#enable`, `#purgeData`, …); Tailscale, the CLI and extension updaters: their outside calls (`exec`, `locate`, server, `runUpdate`, `helper`, …) are `fencedCall`s, `#set`/`#emit` ignore a stopped step, and a row left "checking" or "updating" is put back to idle (`UpdateScheduler` `onStall`); git: `execBin` refuses to start and ends its child for a stopped repository-lock holder. A caller that did `void` an enqueue catches the `StepStalledError`. A new serial chain follows the same rule. Pinned by each chain's "resumes later" test.
- **The whole `withRepoLock` callback is fenced**, not just its git calls. Every module whose code runs under the lock imports `fs` from `src/main/fenced-fs.ts` (a Proxy over `original-fs` promises where each call is a `fencedCall`: refused before it starts and again as it returns), never `original-fs`/`node:fs` directly: `scm.ts`, `worktree.ts`, `worktree-orphans.ts`, `disk/saved-worktrees.ts` (whose saved record's `writeFileAtomic` also has `commitIf: () => !stepStalled()`), and `disk/worktree-facts.ts`. Disk work a core request does itself (a merge prediction's scratch object store, gh's body file) is covered by the request's cancel: the core answers only after it is gone (`formal/repo-lock-core` `NoScratchAfterStop`). **A call the OS already has is waited for**, because an `fs.rm`/`rename`/`writeFile`/`copyFile` already dispatched (or a git/`lsof` child still exiting) would finish against the next holder's files. `fenced-fs` and `execBin`/`run` record every call in flight per step (`trackEffect`/`fencedEffect` in `serial-chain.ts`), and a `SerialChain` step stopped with calls still running becomes a hold on its chain: the caller fails at once, the next step starts only when those calls ended, waiting at most `STALLED_DRAIN_MAX_MS` (60 s) from the stop; after that every step on that chain (queued or new) fails at once with a `ChainBusyError` (the repository lock turns it into a `repo_busy` `LocalCommandError`) naming what still runs, with a `chain-stall` log line, and the chain is usable the moment they ended, no restart. The lock is never handed on while such a call runs: no fallback that releases it anyway. Read-only git takes no lock and is not held. A non-git child started under the lock (`worktree-facts.ts` `run`: `lsof`, `ps`) never starts for a stopped step and is killed when it stops. New code under the lock uses `fenced-fs` and `execBin`/`run`-style fenced children; `prepareWorktree` (seed and setup hook) runs outside the lock. Test: `src/main/repo-lock-fence.test.ts`.
- **A nested step is fenced to the step that called it**: `SerialChain.run` made inside another chain's step (a git `withRepoLock` from a setup, updater or Autopilot step; `ShipRunner.drain` from an Autopilot `#settled`) composes its signal with the caller's: when the caller's step is stopped, the nested step's signal aborts (`throwIfStepStalled` and `fencedCall` inside see it), the nested `run` rejects with the caller's reason and frees its chain, a step still waiting for its turn is skipped, and a `run` from a caller already stopped rejects without queueing. The listener on the caller's signal is removed when the nested step ends. A new chain needs nothing extra; a nested step started from a callback outside the caller's `AsyncLocalStorage` scope is not fenced. Pinned by `serial-chain.test.ts` ("nested across chains") and `autopilot-late-step.test.ts`.
