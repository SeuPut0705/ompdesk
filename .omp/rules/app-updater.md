## Release

### Updater

- **Where it lives** (batch SX4, native-rust › Ledger › SX). The work is the shell's `updater.*` (`native/ompdesk/crates/shell/src/modules/updater/`: `service.rs` the check, downloads and installs, `token.rs` the token, `platform.rs` staging, the swap helper and the installer, `fetch.rs` its requests through `net.rs`; the pure rules in `src/updater_core/`, replayed against `captured.json` from the deleted TypeScript). Node keeps the client `src/main/shell-host/modules/updater.ts` (the mirror of the shell's state, the scheduler, the restart confirm, the quit, the window presence, the next launch's report, the log writer). Wire: `crates/shell/PROTOCOL.md` §15.8.
- **Auth** (`modules/updater/token.rs`). The repo is public: release lookup and asset download carry no Authorization header. A token is optional (`GH_TOKEN`/`GITHUB_TOKEN` → `gh auth token` → a token from Settings › Updates & about, encrypted with `safeStorage`'s key (OSCrypt `v10`, byte-identical to Electron's) by the shell itself, which never hands the token to Node, whose row shows only while the updater is `auth-required` or a token is stored); it raises the rate limit and keeps updates working if the repo goes private. Never bundle a token.
  - A token answered 401 is dropped and the check retried anonymously. Only an anonymous "not found" ends in `auth-required`; a 403 with `x-ratelimit-remaining: 0` is a failed request, not missing access.
- **Release lookup.** Each check reads `/releases/latest` (or `/releases` with pre-releases on) through the API. `updater_core/release.rs` validates the metadata comment against the release (tag = version, asset present with that size), identically with or without a token. A missing, malformed or contradicting comment means no update and the error "no valid update information"; a release without this platform's file reports a missing installer. Both platforms download the API asset endpoint's signed redirect taken by hand (no Authorization to the CDN), into a `.partial` that resumes with `Range`, SHA-512 checked before use; the version rule is node-semver's `gt` (`updater_core/semver.rs`). Requests go through Chromium's network (`net.rs` `fetch_in_shell`: system proxy, PAC, certificate store).
- **One check at a time** (`run_check`/`check_once` in `service.rs`). A Check for Updates (menu, Settings, a paired device) arriving while the 5-minute background check runs joins it, and that check settles as asked: its failure or "no result" reaches the banner, so the card never spins on "Checking for updates…". Pinned by `shell-host/modules/updater-shell.test.ts` (against the real shell).
- **Dev seams** (unpackaged only; the version is `package.json`'s). `OMP_DEV_UPDATE_API=<url>` replaces the release repository's API root (the parity suite's stand-in server). `OMP_DEV_UPDATE_CHECK=1 OMP_DEV_UPDATE_MODE=manual` (+ `OMP_DEV_UPDATE_PRERELEASE=1` for a throwaway pre-release). `OMP_DEV_UPDATE_MODE=relaunch OMP_DEV_UPDATE_BUNDLE=<writable copy of OMPdesk.app>` runs the relaunch path against that stand-in and swaps it on quit.
- **Install modes** (`service.rs` `install`/`quit`). Windows: the NSIS installer, downloaded in the background into electron-updater's cache (`%LOCALAPPDATA%\ompdesk-updater\pending\`, `update-info.json`; a cached installer whose SHA-512 matches is reused), applied on restart (`--updated --force-run`) or quit (`--updated /S`). On a restart the installer starts on a thread of the shell and Node's quit (`before-quit-for-update`, `app.quit()`) follows once that attempt ended, started or not (`CreateProcess` on the fresh unsigned setup waits for Defender's scan). The install at app quit (any end with code 0: an approved quit or a forced `exit(0)`, the shim's `quit` event) starts silently on a thread the shell's `shutdown` joins, so it exists before the shell is gone. macOS, ad-hoc or signed, avoids Squirrel (it would need the ZIP the release no longer ships):
  - **relaunch** (writable bundle): download `ompdesk-mac-arm64.dmg` into `<userData>/updates/ompdesk-X.Y.Z-arm64.dmg`, verify SHA-512, `hdiutil attach -nobrowse -readonly`, copy the `.app` out with `ditto`, detach, check `codesign --verify --deep --strict`, bundle id and version (`platform.rs` `stage_bundle`). On "Restart & install" or any approved quit a detached `/bin/bash` helper (`rules.rs` `SWAP_SCRIPT`) waits for the shell's exit, swaps with rollback, and reopens on restart.
    - **A start-checked swap** (13 Nov 2026; the last Electron release must carry it so its swap into the Rust shell can roll back). Main writes `<userData>/app-started.json` `{version, pid, at}` (`noteAppStarted` in `shell-host/modules/updater.ts`, `writeFileAtomicSync`, once per launch) when the first window's page finished loading, and only then reports the previous install (`swap result`, reading `update-install.json`), so a new app that dies before its first page leaves that marker for the old app the helper restores (it reports `rolled back`). On a restart (relaunch=1) `SWAP_SCRIPT` (the shell passes it the mark's path and the staged version) keeps the old bundle as `<dest>.previous`, removes a stale mark, reopens the app, logs `waiting for the new app to start` and polls up to 120 s (`OMPDESK_SWAP_START_WAIT_S`, the tests' and the e2e's shortcut) for a mark with the staged update's version. Seen: `.previous` goes, `started`. Not seen: every process under `<dest>/Contents/` ends (TERM, KILL after 5 s), `.previous` moves back and is reopened, `start failed; previous app restored` (`start failed; previous app lost` when it cannot move back or there was none, leaving what is there). No dialog anywhere. `lastSwapEntry` takes the last outcome line of the entry. The new app may read `swap.log` before the helper's next 0.2 s poll, so its `swapOutcome` can still read `installed`; `swap result.outcome` (the versions) is what decides. Pinned by `updater_core/swap_tests.rs` (the script run under bash with an `open` stand-in on the PATH: started, never started, a wrong version, a stale mark, a late mark, leftover processes, nothing to restore), `update-log-core.test.ts`, `shell-host/modules/updater.test.ts` ("the start mark") and the two stand-in tests of `e2e/app-auto-update.e2e.ts`.
    - **A version whose start failed is not installed automatically again** (the owner's rule, 13 Nov 2026: no install/fail/roll-back loop at every safe point). When the first launch after an install is not the expected version and `swap.log`'s last outcome is `start failed; …` (the helper's, or the new shell's launcher, which appends the same lines), main writes compact `{"version":"X","count":N,"at":<epoch ms>}` (`count` = failed starts of that version, one more each time; the Rust shell's NSIS setup reads the same file) to `<userData>/update-start-failed.json` (`startFailureOf`, `rememberStartFailure`). `AutoInstallFacts.startFailedBefore` is true while the downloaded version is that one: the scheduler decides nothing, logs `scheduler withdrawn {reason: "start failed before"}` once, and starts over when the update goes or another one comes. A person's "Restart & install" (and the tray) still installs it, with the start check (relaunch=1); a different downloaded version (a newer release) deletes the file. **Only the click installs it.** The shell reads that file (`held_start_failed` in `service.rs`; Node stays its only writer): while the downloaded version is the held one and no install started, an ordinary quit and the quit watchdog's forced exit start no swap for it on macOS (log `swap skipped {reason: "start failed before"}`; a relaunch=0 helper would delete `.previous` at once and check nothing) and no `/S` installer on Windows. **A newer release supersedes it**: a manual check and the 5-minute background check still look while it is held (no "checking" status, no `not-available` or error status over the held download; a failed look logs `check error {kind: "held"}`), the held version found again is kept and fetched nothing, and a different version found is downloaded (Windows) or staged (macOS) as usual, after which the scheduler counts down for it. The remaining relaunch=0 install (a quit with a staged version that is not held) keeps the accepted gap below. Pinned by `app-auto-update.test.ts`, `update-log-core.test.ts`, `shell-host/modules/updater.test.ts` and `shell-host/modules/updater-shell.test.ts` (held: no install at quit, a check keeps it, a newer one is downloaded).
    - **Gaps, accepted by the owner (13 Nov 2026).** The install at an approved quit (relaunch=0) reopens nothing, so it has no start check: `.previous` is removed at once. A Mac that skips this release (v0.127.0 straight to the Rust shell) has no rollback: its helper is the old one.
  - **manual** (read-only: DMG, App Translocation): the same DMG, verified and opened in Finder from Downloads.
- **Install updates automatically** (Settings › Updates & about; pref `appAutoUpdate`, `APP_AUTO_UPDATE_PREF`, `AppAutoUpdateRow.tsx`). **Default on** (the user's rule, so an unattended Mac running Autopilot updates itself): only a stored `false` turns it off. Off: check, background download, "Restart & install", applied on the click or any approved quit.
  - On, once a verified update is downloaded and `restartableUpdate()` holds (relaunch or NSIS; never the manual DMG, whose switch is disabled with the reason, `updater:installMode`), `AutoInstallScheduler` (`src/main/app-auto-update.ts`, electron-free, injected clock, ticked every second by the client `shell-host/modules/updater.ts`) decides when.
  - **With Continue interrupted work (`resumeInterrupted`) on: the next safe point.** No ask, approval or plan-proposal card open (`asking`: the pool's and hosted tabs' open asks, `SidecarPool.restartHolds().planWaiting`) and no compaction under way (`compacting`: `restartHolds().compacting`, `LocalHostServices.compacting()`; a cut compaction does not resume). Nothing else holds it back (a running turn, background subagents and jobs, a focused window, typing, Autopilot runs, hosted tabs), because the relaunch continues the turn and restarts the subagents and cut commands (see Interrupted turns; `bridge-restore-subagents`, `turn-resume`). At the countdown's end it waits for a safe point again (log `held`, `open ask` | `compaction`) instead of installing over a card. Log `safe {waitedMs, running, resume}`. A compaction and a plan proposal have no cap (they hold past the 30 min max wait too); an ask or approval card holds only while someone is there (next point).
  - **A card nobody answers gives way** (the owner's rule, 12 Nov 2026, his pick when asked: a question card left open overnight held a verified update from 06:12 until he clicked the restart himself at 08:02). With resume on, an open ask or approval card holds the restart only while someone may answer it: once a card has held it for 10 min (`AUTO_INSTALL_CARD_HOLD_MS`; counted from the first tick, once a second, that saw a card open with the update ready, so a card closed and another opened between two ticks counts as one) and nobody gave this computer input for 10 min (`idleMs`, `powerMonitor.getSystemIdleTime`, the quiet-moment rule's fact), the scheduler logs `unattended` and starts the usual 60 s countdown (Now / Later here, on a paired computer and the phone); at its end it installs over the card, and the relaunch reruns the cut-off call so the same card comes back (`bridge-restore-card-stock.test.ts`: the ask and the approval, after SIGTERM and after stdin's end, without a new model request). While someone gives input it keeps waiting: input during the hold or the countdown holds it (`held` at the countdown's end), and it gives way again only after 10 more minutes without input, through a fresh countdown. A card that came up during a countdown holds at its end until it has held 10 min. It never gives way to a plan proposal (`planWaiting`, `restartHolds().planWaiting`: the proposal lives only in the bridge of the omp that made it, `modes/plan.ts`, so a relaunch would lose it), to a compaction (beside a card too), or with resume off. Input on a phone or a paired computer is not input on this computer. Do not bring the uncapped card hold back, or change the 10 min, without the owner.
  - **Background work never holds the automatic restart** (the owner's rule). `AutoInstallFacts` has no background-work fact; there is no background-work wait, log reason, `overdue`, waiting notice or frozen countdown, and the update card has two states, the countdown and installing. Do not bring a hold, a wait or a notice for background work back without the owner.
  - **A person's restart asks** (`confirmUpdateRestart` in `app-quit.ts`, decided by `updateRestartConfirmation` in `quit-guard.ts`; "Restart & install", the countdown's "Now", the tray: all `applyUpdate`). With resume on and background work running, one native confirm names it (up to 3 names, subagents first; Restart / Cancel, Cancel default); with nothing running it asks nothing. With resume off the existing quit confirm covers running work. The scheduler's own install never asks. The only reader of background work is `askBackgroundWork` (`src/main/background-work.ts`, electron-free): the bridge's `composer.jobs` of every omp whose run is on, this computer's tabs and the tabs it hosts (`SidecarPool.runningBridges()`, `LocalHostServices.runningBridges()`), asked fresh at the click, one request per running tab. **It fails closed**: a tab whose request fails or takes over 3 s (or a pool that cannot be listed) is `unknown` work, named in the confirm; it never throws. **A paired page asks on the page** (`applyUpdate("device")` for a caller with a `connId`): its `ConfirmSheet` names the running work, and this computer shows no dialog. **A paired computer** asks in its own `ConfirmDialog` with the same sentence, then sends `host.desktop.update {action: "restart-now"}`, which the host runs while work runs only when its countdown shows; otherwise it is `install` (`host_busy` while work runs). `postpone` is the countdown's Later. Actions: `HOST_UPDATE_ACTIONS` (`src/shared/ipc-types.ts`). Pinned by `machine-services.test.ts` (paired device on the countdown) and `background-work.test.ts`.
  - A check while an update is downloaded answers with it and changes nothing (`checkForUpdate`), so a check (Settings › Updates checks as it opens) never drops the countdown. Pinned by `shell-host/modules/updater.test.ts` ("a check while the countdown shows keeps the countdown").
  - **With it off, or after the user's "Later" that round:** a quiet moment: no tab running a turn or compacting, no ask open (`resumeFacts`/`tabInventory`, this computer's and hosted tabs), and every window unfocused or no input for 2 min (`AUTO_INSTALL_IDLE_MS`, `powerMonitor.getSystemIdleTime`). Not quiet after 30 min (`AUTO_INSTALL_MAX_WAIT_MS`): with resume on it proceeds anyway (`forced`); with it off it never forces and keeps waiting for idle.
  - Then it announces: `UpdateStatus.downloaded.restartAt` (epoch ms, 60 s ahead, `AUTO_INSTALL_COUNTDOWN_MS`) shows one quiet line with a countdown and "Now / Later" in the sidebar update card and Settings › Updates & about, never a modal. "Later" (`updater:postpone`) postpones to the quiet-moment rule and restarts the 30 min wait.
  - At the deadline `restartIntoUpdate()` runs the existing quit path (`requestQuit`/`quitAndInstall`, so drafts, layout and resume markers survive); with resume off and work started during the countdown it withdraws the notice instead of asking. It first sets `UpdateStatus.downloaded.installing` (optional, also in the remote host schema): card and Settings row read "Installing update X…" with no button, even for a version put off with Later, and `current.installing` guards `restartIntoUpdate` and `updater:apply`, so a second click, a second "Now" or the deadline starts nothing. The scheduler is done once any install began (`installStarted`, which `beginInstall` calls for every trigger: its own, a click here or on a paired device, a quit): it logs `install` once and decides nothing more (12 Nov 2026: a click left it deciding, and one second later it logged `safe` and `countdown`). It announces and installs again only after the update stops being installable (install failed) or the pref goes off.
  - Dev seams: `OMP_DEV_UPDATE_STAGED` (+ `OMP_DEV_UPDATE_STAGED_VERSION`) treats a bundle as the verified staged update (with `OMP_DEV_UPDATE_MODE=relaunch`, `OMP_DEV_UPDATE_BUNDLE`; `e2e/fixture/stand-in-bundle.ts`); on Windows it is a pretend NSIS update whose install only quits (`devDryInstall`: every decision before it runs as shipped). `OMP_DEV_UPDATE_AUTO_COUNTDOWN_MS` shortens the countdown, `OMP_DEV_UPDATE_AUTO_MAX_WAIT_MS` the max wait after "Later" (unpackaged only). `e2e/app-auto-update.e2e.ts` (macOS) covers the default (installs unclicked), a stored off (waits) and a running background subagent (`OMP_GUI_TEST_BACKGROUND_JOB=1`, finished by `fixture:finish-background`; log `safe` → `countdown` → `install`); `e2e/app-auto-update-parity.e2e.ts` is the parity spec (this computer, a paired computer, the phone at 390 px); the second test of `e2e/autopilot-restart.e2e.ts` installs during an Autopilot cycle and the relaunch continues it. No e2e installs over an open card. Pinned by `app-auto-update.test.ts` (resume on/off cases; a card nobody answers: gives way, input holds, a fresh countdown after input, never a compaction, a plan proposal or resume off; every sequence of seven steps of time, cards, compaction and input installs over no compaction, no plan proposal and no card held under 10 min or with input within 10 min), `bridge-restore-card-stock.test.ts` (the card comes back), `background-work.test.ts` (the ask, the naming), `quit-guard.test.ts`, `app-quit.test.ts` and `shell-host/modules/updater.test.ts` (installs while background work runs, no confirm; installs over a question nobody answered for 10 min, never over a plan proposal).
- **The relaunch comes back as the app sat** (the user's rule). When an install begins (`beginInstall`, before the quit tears the windows down) `windowPresenceOf` reads every window: none shown → `hidden` (closed to the tray, or macOS with no window shown), all shown ones minimized → `minimized`, none focused → `behind`, else nothing. The install marker (`update-install.json`, `PendingInstall.presence`) carries it, and the next launch reads it before its first window (`readRelaunchPresence`, only within `RELAUNCH_PRESENCE_MS` of the helper's start, never with an argv folder): `WindowManager.launchPresence` keeps restored windows hidden, minimized or shown without focus (`showInactive`), and a hidden relaunch on macOS gives the focus back (`app.hide()`). The tray, the Dock and a notification bring them back as always. Pinned by "relaunch presence" in `update-log-core.test.ts` and "records how the windows sat" in `shell-host/modules/updater.test.ts`.
- **Update log.** Every decision goes to `<userData>/logs/gui-runtime.jsonl` (source `app-update`, `details.level: "info"`; the shell's lines arrive as `log.runtime` and Node's relay scrubs their `reason` with `scrubUpdateReport` before writing, the scheduler's are the client's own), so an unclicked restart is explained from the log (Copy diagnostics carries the last 100 entries, repeats folded, redacted). Never the token or a URL: failure reasons pass `scrubUpdateText` (`update-log-core.ts`: drops URLs and the token, runs the diagnostics redactor). `message` is the area, `details.event` the step:
  - `check` (every check, background one every 5 min): `no-update` | `found` {version, current, mode} | `error` {kind: a release-metadata code, `auth-required:<reason>`, `check-failed` or `no-result`, reason}.
  - `download`: `started` {version, mode, bytes} | `verified` {…, ms} | `failed` {version, mode, reason}; `mode` = relaunch, manual or nsis.
  - `scheduler` (transitions only, never one line per tick): `waiting` {reason: `busy turn` | `open ask` | `compaction` | `focused+active input`, waitedMs} once per reason, and again in a new round (pref off and on, the update gone and back); `safe` {waitedMs, running, resume} (resume on); `unattended` {heldMs, idleMs} (resume on: an ask or approval card held the restart 10 min with no input for as long; a countdown or the install follows); `quiet`; `forced` {waitedMs, maxWaitMs, resume, reason} (30 min, resume on, after Later, a busy turn); `countdown` {restartAt}; `held` {reason} (a card or a compaction at the countdown's end, resume on; an ask or approval only while it has held under 10 min or input came within the last 10 min); `postponed` {by: user}; `withdrawn` {reason: `pref off` | `update not ready` | `work started, resume off`}; `install` {trigger: `auto` | `user click` (incl. a paired device's) | `quit`} once per install, whoever started it, and nothing from the scheduler after it.
  - `swap`: `helper` {mode: `relaunch` | `nsis`, from, to, trigger} when the helper starts (it also writes `<userData>/update-install.json`); next launch, once its first window's page loaded (after the start mark), one `result` {outcome: `installed` | `rolled back` | `changed`, previous, expected, current, mode, trigger, launchedAt; on macOS swapAt + swapOutcome from `swap.log`'s last entry, e.g. `install failed; previous app restored`, `start failed; previous app restored`}.
  - Pinned by `app-auto-update.test.ts` (transitions, no duplicate lines, `unattended`, a new round's wait reason, done after any install) and `update-log-core.test.ts`; `shell-host/modules/updater.test.ts` (double click installs once, "installing" before the installer starts, no second countdown after a stall, no scheduler line after a click's install; `quit-for-update`: the quit follows the installer's start, failed or not) and `updater-shell.test.ts` (the shell's check, download, resume and auth against a stand-in API; on Windows the installer as a real process: a recorder the suite compiles with the runner's rustc, served as the setup, writes the arguments it got, `--updated --force-run` on Restart & install and `--updated /S` at an approved quit; a non-program setup fails with `updates.failed` and still quits), `updater_core/spawn.rs` (a real process gets the installer's arguments; a missing or non-program file is an error); the installing row in `SidebarUpdateCard.test.tsx`.
