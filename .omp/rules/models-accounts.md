## Models, accounts and held stock defaults

### Desktop slot
- One session at a time drives the desktop. Files: contract `resources/gui-bridge/desktop-slot-contracts.ts`; bridge `desktop-slot.ts` + `desktop-slot-core.ts`; main `src/main/desktop-slot.ts` + `desktop-slot-host.ts` + `local/desktop-slot.ts`; renderer `stores/desktop-slot.ts`, `DesktopSlotIndicator.tsx`, the waiting line in `ToolCard.tsx`; capability `desktopSlot`.
- WHY: each omp has its own `ComputerSupervisor`; stock only refuses input while another operation owns focus, never queues, never spans observe → act → verify, and nothing crosses processes. So **main** owns one slot per computer and the bridge patches `ComputerSupervisor.prototype.run` once (feature-detected; without `run`/`revokeControl` the slot is `unavailable` in capabilities/health and stock behaviour stays).
- A `snapshot.readOnly` run (screenshots, `capabilities`) never waits, nor does a run under stock's `computer.backgroundFallback: "refuse"` (`needsSlot` in `desktop-slot-core.ts`), because stock then refuses anything that would take the foreground (`worker.ts` `refuseForeground`), so such runs of several sessions go side by side (`runBackground`: with no slot held it runs at once; while the session holds the slot, lets go of it or failed to revoke, it is an acting run, so a revoke aborts it and a failed revoke blocks it). Under the default `takeover` an acting run takes the slot.
- The first acting run takes the slot (`desktop_slot_acquire` → `desktop_slot_bridge`) and keeps it until `agent_end`, `DESKTOP_SLOT_IDLE_MS` (20 s) without a computer run, Stop, abort, tab close/crash, or lease expiry (`DESKTOP_SLOT_LEASE_MS` 120 s without `desktop_slot_touch`).
- Waiters queue FIFO. An acting run that had to wait does **not** run once granted: it returns `DESKTOP_SLOT_STALE_NOTICE` so the agent re-screenshots and repeats.
- **Handoff**: abort the holder's in-flight input run, await stock `ComputerController.revokeControl()` on every controller the bridge saw, only then grant the next session.
- **Never handed on unconfirmed.** A `revokeControl()` that rejects (holder's acting runs get "input is blocked") or is silent for `DESKTOP_SLOT_REVOKE_TIMEOUT_MS` (10 s) leaves the holder `revoke-failed` (`DesktopSlotState.holder.revokeFailed`): nobody is granted, main retries every `DESKTOP_SLOT_REVOKE_RETRY_MS` (5 s; a late answer counts), the indicator offers "다시 시도" (`desktop_slot_retry`) and "그 세션 중지" (`desktop_slot_kill`: abort + `restart()` of its omp, SIGTERM only).
- Freed only by a confirmed revoke, a confirmed exit of the holder's process (host re-reads `whenExited()` while the sidecar is ready; a failed grant is not a crash), or a kill whose process exited within `KILL_CONFIRM_MS` (5 s). A bridge `desktop_slot_release` follows only a confirmed revoke.
- UI: app-wide "화면 사용 중: <title> · 대기 N" with Stop (`desktop_slot_stop`: aborts the holder's turn, hands off); a waiting `eval` card says "화면 차례를 기다리는 중 (N번째)".
- Hosted tabs for a paired device join this slot; tabs on a remote host use that host's slot (main skips `sidecar.device` tabs). Autopilot never takes it (its `eval` is off). No "run marked done" release (stock has no marker).
- Tests: `desktop-slot.test.ts`, `desktop-slot-host.test.ts`, `bridge-desktop-slot.test.ts` (rejecting/silent revoke, holder death, kill), `e2e/desktop-slot.e2e.ts`.

### Account rotation
- Settings › Models & accounts pref `accountRotation` (`quota` default = stock's usage ranking | `even`; `src/shared/account-rotation.ts`, `providers/RotationModeControl.tsx`). Each spawn gets `OMP_GUI_ACCOUNT_ROTATION` and the shared ledger `<userData>/account-rotation.json` (`OMP_GUI_ACCOUNT_ROTATION_STATE`); a change or bridge connect pushes `account_rotation_set {mode}` to every live local sidecar and every tab this machine hosts (`LocalMachine.setAccountRotation`, `src/main/account-rotation.ts`). A paired host's tabs follow the host's pref (`host.accountRotation.get|set`).
- **Even**: the bridge's `account-rotation.ts` (`before_agent_start`) gives an account-less session the unblocked account handed out least recently across all local omps, as an automatic warm pin (`authStorage.sessions.pin(…, {restoredAtMs})`). A session keeps it until blocked (idle pin renewed, not re-ranked); stock's 429 blocking/failover is untouched.
- **Quota re-ranks at turn start.** Because stock re-ranks an automatic pin only when cold, blocked or spent and every request refreshes last-use, so a busy session never left its first account. `rerankBeforePrompt` (`account-rotation-core.ts`) runs in the same hook for the main agent only (`ctx.agent.kind === "main"`; subagents keep the spawn copy via `sessions.inherit`); mid-turn checks are below.
- It asks stock, not our own policy: the account stock's selector would give a pinless session now (`authStorage.keys.getWithCredential(provider, <stand-in id>, {…, recordAffinity: false})`). It moves the pin (automatic warm pin, `restoredAtMs: now`) only when ALL hold, else stock decides: >1 account; pin exists and is warm; pin is automatic (read via the `include(provider, explicit)` callback of `sessions.inherit` with a stand-in target returning `false`; no provenance = left alone); session unrestricted (`sessions.permits`) and no account has a stock policy (`oauth.policy`), because pools/policies are the user's choice; pin not blocked; both accounts measured and stock's comparator (`orderUsageRankedCandidates` over `RankedOAuthCandidate` rows from both `usage.report`s, mirroring `#rankOAuthSelections`) still ranks the other first after the pin's required drain is multiplied by `RERANK_DRAIN_MARGIN` (2).
- The margin is OMPdesk's only addition, because every switch rewrites the provider's per-account prompt cache. Only the plain drain order gets it; stock tiers (blocked, spent, 85% 5h demotion, unmeasured) move a pin at once. Proper fix belongs in stock.
- **Between two model calls of a long turn** (`after_provider_response`, main agent only; capability `accountRotation` lists the session member `extensionRunner.emitAfterProviderResponse()` and `AgentRegistry.prototype.list|isRunning`; a module probe of the runner would be a second module graph): the same decision runs again (`rerankMidTurn`) because a main session here runs turns for hours and only moved after a 429 otherwise. Why this hook: it fires after every response and before the next request's key is resolved, so a pin written there serves the next call and the stream in flight keeps its account; stock holds the response body until extension handlers return, so the check is **not awaited** (single-flight per session, at most once per `MID_TURN_CHECK_MS` = 60 s, reading only stock's cached reports). A `context` hook would also reach the next request but makes stock clone the whole context on every request (`context-hook.ts`), and `turn_start`/`tool_execution_end` are pushed on an event stream the loop does not wait for. **The move rule is one pure function, `decideMove` (`account-rotation-core.ts`), with a table test**:

  | phase | usage read | pin / top pick | answer |
  | --- | --- | --- | --- |
  | either | one account unread | - | stay `usage-unreadable` (never "unmeasured, so the sibling wins") |
  | either | both read | the top pick's window for the session's model is spent or full (`limited`) | stay `target-limited` |
  | either | both read | pin near limit (5h window at stock's 85% demotion step, `HOT_PRIMARY_FRACTION`, or allowance spent), top not | move `near-limit` |
  | turn start | both read | stock ranks top first after the 2x drain margin | move `better` |
  | turn start | both read | otherwise | stay `within-margin` |
  | mid-turn | both read | top near limit too | stay `no-better` |
  | mid-turn | both read | top's required drain >= `MID_TURN_DRAIN_MARGIN` (8x) the pin's, on the first window both are measured in (stock compares the 7d one first) | move `much-better` |
  | mid-turn | both read | otherwise | stay `mid-turn` |

  The other stays are `rerankSession`'s cheap checks (`mode`, `no-model`, `single-account`, `no-pin`, `cold`, `unknown-provenance`, `explicit` = pinned by the person, `restricted`, `policy`, `blocked`, `subagents`, `no-choice`, `same`, `pin-refused`). **A session never moves mid-turn while one of its subagents runs** (`subagents`): a subagent holds the account it was spawned on, so a parent that moved would split the task over two accounts. 8x is a choice, not a measurement: the log of 12 Nov 2026 shows a session going 8 → 7 → 8 → 7 inside 90 minutes at turn start with the 2x margin, so mid-turn moves on plain drain are made rare. **A target whose window for the session's model is spent or full is never moved to** (`target-limited`, `AccountFacts.limited`, the owner's top finding from the logs: a move onto an account whose Fable cap stock still read as usable was answered 429 on the first request): the bridge reads the windows stock ranks for that model (`scopeLimitsForReserve`, else `scopedUsageLimits`, so a model's own weekly row counts, unconfirmed or not) and calls the account limited when one is exhausted by stock's own predicate (`isUsageLimitExhausted`) or a non-shared row of the model is at `MODEL_WINDOW_FULL` (98%), because stock gates a Fable row only at 100% with a live reset time (pi-ai `usage/claude.ts` `isConfirmedExhaustedTierRow`). A pin that is itself limited counts as near its limit. Limits of this check: it reads the cached report, so a cap spent since that report (up to the 5 min cache) is not seen. **Measured on 18.20.0** (`bridge-account-rotation-stock.test.ts`, first CI run of the case): with the sibling's Fable row at exactly 100% and no reset time, stock's selector kept the pin on the account at the 85% step instead of picking the sibling [INFERENCE: `remainingUsageFraction` 0 reads as `allowanceSpent`, which ranks above the 85% demotion]. So the case this check adds is a row short of 100% that stock neither gates nor counts as spent, and the real-omp case puts it at 99% with no reset time on the account stock picks (the pin's account at the 85% step): the pin stays, and with the row at 50% it moves.
- **Every decision leaves a log line** (`gui-bridge: quota re-rank moved|kept the session's account`, fields `phase`, `why`, `from`/`to`, both accounts' facts `pin`/`top` (5h used fraction, spent, required drains) and `topFirstWithMargin`; info at turn start and for a move, debug for a mid-turn stay), because before 13 Nov 2026 only a move was logged (and a throwing hook), so "why did it not switch" could not be answered. **The usage view says why**: the core keeps the last decision per session (`recordDecision`/`lastDecision`, 64 sessions), the bridge's `usage` answer carries it as `UsageReport.rotation {why, moved, phase, at}` on the in-use account's report, and Stats › Usage renders one muted line under that card's header (`rotationReason`, keys `usage.rotation.<why>` in en and ko; codes without a line: `single-account`, `no-pin`, `no-model`). The renderer only renders.
- **A person's Refresh is answered at once.** `get_usage`/`get_provider_accounts` with `refresh` drop stock's cache for every provider with a report whatever the report's age (the 60 s `REFRESH_FRESH_MS` suppression stays only for the credits-only ChatGPT fetch outside a refresh); `refresh` is sent by the explicit button only, never by the poll, and it is the only read that goes through the failure backoff (`useUsageRead`, tested in `use-usage-reports.test.tsx`). **The in-use account reflects response headers as stock allows**: `usage.ingestHeaders` merges them at most once a minute per account (`USAGE_HEADER_INGEST_INTERVAL_MS`, stock; except a window that reads exhausted, which is persisted at once), so the gauge of the account in use can lag the real figure by up to that minute plus the read gap. **While reads fail, the poll keeps its doubling backoff (5, 10, 20 min) and holds the focus and turn-end reads** (`watchUsage`; the owner's call, 13 Nov 2026: a failing day reads about 73 times, as before, never more; test: a simulated day with a turn ending every two minutes, at most 720 reads healthy, 74 failing). The 22 Oct incident (313 `/usage` calls in a day on one Mac) must not come back.
- **Cases from this computer's logs and sessions (13 Nov 2026: `~/.omp/logs`, session files of 7-13 Nov; the other computers' logs were not reachable).** The log counted 29 `quota re-rank moved` lines and no line for any other decision, so only the session files (`credential_pin` entries, each assistant message's `credentialId` and 429 `errorStatus`) could show what happened next. (1) **A move into an account that answered 429 on its first request**: of the 4 pin changes at a turn start that could be followed to the next request, 3 (10→7 twice on 10 Nov 09:14-09:15, 10→8 on 11 Nov 14:05), all on `claude-fable-5-2`, with `retry-after` 3.7 h and 54 min. [INFERENCE] the move trusted the 5h/7d windows of the usage report while the provider's limit for that model was spent. (2) **Stayed on the blocked account after the 429**: the same prompt failed four times in four minutes on the account moved to (11 Nov 14:05-14:09), and one session's next prompt five minutes after its 429 went to the same account (10 Nov 09:19); the pin changed at 14:11:51 and after 09:24. Stock ends the turn with the 429 when `markReached` finds no usable sibling (`turn-recovery.ts`, "No sibling credential is usable right now"). [INFERENCE] the siblings' usage was unreadable then: the logs hold 167 `Claude usage fetch failed` 429s and 20 403s, up to 22 an hour (10 Nov 00-06 h); no log line records the failover itself. (3) **Flip-flops**: 8↔7 three or four times inside 90 minutes on 12 Nov 08:15-09:52 in three sessions, each rewriting the prompt cache; this is what the 8x mid-turn margin guards against. (4) A Fable weekly 429 (`retry-after` 6939 min) was answered by stock's model fallback to Opus, not by an account move: not a rotation failure. Not found in these files: an account with room left unused for long.
- **Why a never-used account with no 5h window is not chosen: stock working as designed, not an OMPdesk defect.** Stock ranks by required drain, headroom per hour to reset (`windowRequiredDrain`, pi-ai `auth/usage-report.ts:256-269`; order in `auth/rank.ts` `compareUsageRankedCandidatePriority`, 7d drain first): an account whose 7d window has not started (no reset clock) counts the full 168 h as remaining, so its drain is the smallest of all, and the account whose week ends soonest drains first ("use it or lose it"). It is chosen when the in-use account's 5h window reaches the 85% demotion (`rank.ts` `PRIMARY_WINDOW_HOT_FRACTION`), since a missing 5h window reads 0.5 used (`normalizeUsageFraction`) and is never hot. A 7d reading of 0% means only that the weekly usage read 0%, not that the account was never used.
- Tests: `src/main/bridge-account-rotation-stock.test.ts` on the real omp (margin thresholds, 5h tier, explicit/cold/subagent, inheritance, the mid-turn check and stock's 84.9%/85% step), rules in `bridge-account-rotation.test.ts` (the `decideMove` table, mid-turn cases, the decision record), `UsageQuotas.test.ts` (every reason has an en and ko line), `usage-reports.test.tsx` (backoff and the bounded day), `bridge-usage-live-stock.test.ts` (refresh bypass); internals in `capabilities.ts` (`accountRotation`) and `health.ts` (`auth/rank`).

### Credit use
- The owner's rule (12 Nov 2026): no money leaves an account because OMPdesk kept working past the plan, unless he turned that on. Settings › Models & accounts › Credit use (`providers/CreditSpendRow.tsx`, under the rotation control), one switch for every account, pref `creditSpend` (`src/shared/credit-spend.ts`), **off by default**. Each spawn gets `OMP_GUI_CREDIT_SPEND` (`0`/`1`, `sessionEnv`); a change or bridge connect pushes `credit_spend_set {enabled}` to every live local omp and every tab this machine hosts (`syncCreditSpend`). A paired host's tabs follow the host's pref (`host.creditSpend.get|set`). Agents never switch it (`app-channels.ts` `SPEND`, `ROW_NOT_WRITTEN`).
- **OMPdesk never buys credits or switches a top-up.** A provider's auto top-up fires only when credits are spent; neither usage answer tells stock whether it is enabled, so OMPdesk can only avoid triggering it by not spending.
- Why stock spends: ChatGPT's plan-spent report with `credits.has_credits` reads allowed (pi-ai `usage/openai-codex.ts` `hasPlanCreditOverage`, `buildPlanMeterState`), and whatever a report says, stock's selector ends on a last-resort pass that takes a blocked account (`auth/select.ts` `resolveOAuth` passes `allowBlocked: true`) and reads no usage at all with one account (`#oauthUsagePolicy`: `credentials.length > 1`). Measured on 18.18.9: one spent ChatGPT account with credits is sent every request; with a sibling that has plan left stock already moves to it.
- **Off** (`resources/gui-bridge/credit-spend.ts`, rules `credit-spend-core.ts`): ChatGPT's usage provider is stock's own wrapped as a runtime override (`usage.providerFor` → `usage.setProvider`, its own `cacheVersion` namespace so a terminal omp's "allowed on credits" report never reaches it): `/wham/usage` reaches stock's parser without `credits`, the report's `raw` keeps the real answer for the credits figure, and `x-codex-*` headers are parsed without the 2xx verdict so 100 % reads spent. Every request key (`keys.getWithCredential`; the prompt-time probe `keys.get` stays stock) is checked after stock picked the account: plan spent by its report (`planSpentUntil`: a plan window at 100 % with its reset ahead, or Codex `limitReached`), or Claude's last answer said `overage-in-use` (`after_provider_response`, `overageUntil`), is refused with a `usage_limit_reached` error carrying stock's `retry-after-ms` hint; stock then blocks the account (`limits.markReached`), rotates, walks `retry.fallbackChains` or shows the error. **An overage answer stops only what its window covers** (`overageCoversAccount`): the whole account when the claimed window is one all its models share (`five_hour`, `seven_day`), only the model that was served (the request's `modelId`) for a model's own weekly window or a claim this build has not heard of, because a spent Fable or Opus week must not take the account's other models with it. **On**: the override is removed, the check passes everything.
- Gaps: the request that crosses 100 % is served (the report or header that says so comes with or after it); a turn already streaming finishes; Claude's usage answer can read under 100 % while extra usage serves until the first response's `overage-in-use` header, so that one request is served on extra usage; a terminal omp may heal the shared block, the key check still refuses. **ChatGPT's 2xx headers do not stop it** (measured on 18.18.9): after a 2xx whose `x-codex-*` headers put the plan at 100 %, the account's report still read the 90 % of its last usage answer, so the next request went out; the same headers handed to `usage.ingestHeaders` directly make it read spent (same cache key: model and provider base URL are both `https://chatgpt.com/backend-api`), and an ingest from `after_provider_response` changed nothing, so stock's response path does not reach the report there. Size: every request until the account's next usage report (stock's report life, about 5 minutes). Pinned as the gap case of the stock test.
- Tests: `bridge-credit-spend.test.ts` (rules), `bridge-credit-spend-stock.test.ts` (installed omp against a fake ChatGPT and Claude on 127.0.0.1; measured: stock and on send a spent ChatGPT account with credits both requests, off sends none and ends in the usage limit while the credits figure still reads 500; off with a sibling that has plan left serves from it; off with `retry.fallbackChains` goes on on the Claude fallback; Claude at 100 % off sends none; Claude served on extra usage under 100 % off sends the first request only), `omp-launch.test.ts`, `machine-services.test.ts`, `host-services.test.ts`, `CreditSpendRow.test.tsx`; capability `creditSpend`. The stock test's guard routes Claude to the fake over plain http and refuses every `node:https` request and `tls.connect`, besides the `fetch` guard: stock sends Claude requests through its `node:https` Cowork transport (pi-ai `utils/transport-fetch.ts`), which a `fetch` guard never sees (its first run sent two requests with a made-up key to the real api.anthropic.com, refused 401).

### Provider sign-in
- Settings › Models & accounts and first run (`providers/ProviderLogin.tsx`) run stock `login` on the tab's omp. While a sign-in is in flight its `open_url`, `input` and info `notify` requests (`isSignInRequest` in `shared/rpc-types.ts`) belong to the panel (`loginRequestIds` in `stores/extension-ui.ts`) and **never render as chat cards**, even after the panel unmounts, the page reloads or a paired host's link returns.
- Main counts `login` commands in flight per tab (`SidecarPool.noteSignIn`); for a paired host's tab also the host's `signIn` tab event (sent as `login` starts/ends, on every `tab.open` incl. a new tab's `{active: []}`, and ahead of `openAsks` on re-attach), because the host's login runs on when this window's `login` call fails with the link. A host status (not the link) leaving `ready` drops the host's list. Main marks each such request (`IpcSignIn`: `active`, provider, browser page) on the live `EXTENSION_UI` frame, in `EXTENSION_UI_OPEN` and in a host's re-sent `openAsks`; all reach the page through `pushTabExtensionUiRequest`: a marked request is never a card.
- While `login` runs (`active`) the page adopts the sign-in (`adoptedLogin`, counted in flight) and the panel shows it when reopened ("Sign-in in progress…", browser link, paste fallback, Cancel) until main sends `SIGN_IN_ENDED` (`endTabSignIn`: answers the leftover; panel reloads providers or shows the failure; outcome is unseen if a host's login ended while the link was down). Once `login` answered, a request is a leftover and is answered `cancelled` at once.
- Browser sign-in finishes through stock's loopback callback; stock also races a code paste and never closes it. A local desktop tab opens the launch URL automatically and keeps the paste collapsed. A web page or paired host's tab opens the provider URL only on a click and shows the paste immediately, except a paired host's tab whose browser comes back through this computer (below). The panel answers the leftover `cancelled` once `login` returns (an empty answer earlier only re-asks).
- **A paired host's browser sign-in comes back through this computer**, because the provider sends this computer's browser to the HOST's loopback `http://localhost:<port>/callback`. While the host reports the tab's `login` running (`signIn`), the device's `RemoteSidecar` reads the `open_url` that has a `launchUrl` and listens on its `redirect_uri`'s port on this computer's loopback (`src/main/remote/sign-in-relay.ts`, its listener and guards in the core's `remotebytes/signin.rs`; both families for `localhost`, as stock binds them). The browser's callback crosses as `host.signIn.callback {rtab, path, query}`; the host (`host-services.ts`) replays it only to the callback of the `open_url` its tab's running sign-in raised (`signInCallback`, read with `loopbackCallback`, `src/main/sign-in-callback.ts`, the one parser Cancel uses too), only on that path with that flow's `state`, once, and the browser gets the page stock's server answered.
  - Guards on the device: exact path, the flow's `state`, a loopback `Host` header, one use, `Connection: close`. The stand-in ends with the host's sign-in, the tab, or stock's 5-min timeout, and lets a callback already on its way finish (the host's `login` answer can cross before the page). A link down when the browser comes back gets OMPdesk's own page (`remote.signInRelay.*` in `i18n-text.ts`: paste the address, or reload once the host is back); the stand-in stays until the sign-in ends. Nothing logs the query. An older host answers `unsupported` (the device's page says to paste).
  - The panel learns the state from `SIGN_IN_RELAY` (`IpcSignInRelay`, also on the sign-in mark for a reloaded page): listening → "comes back to this computer" and the paste behind its toggle; port taken here → that port named and the paste open. A phone's browser never reaches this computer's loopback, so the web page keeps the paste with `pasteHintRemote`. Test seam `OMP_GUI_TEST_SIGN_IN_RELAY_PORT` (two apps on one computer share its loopback).
- Stock's RPC `login` has no cancel and holds omp's serial command queue (up to its 5-min callback timeout), so Cancel sends `login_cancel` (`src/main/local/settings.ts`), ending it via the callback's own denial (`error=access_denied` with the flow's `state`). A relaunched client has lost a host login's browser page (Cancel of its adopted panel then answers the paste).
- `accounts.provider_sign_in` starts the guarded RPC in main and returns without waiting for authentication. Its renderer event selects the caller tab and opens that provider in Models & accounts; the panel adopts the existing login rather than starting another. Main refuses a second login in the same tab, including one started from another viewer. Startup errors remain visible even before the panel adopts a request.
- A pasted answer is sent once per request while delivery is pending. Failed delivery allows retry, and a late answer cannot clear a newer prompt. Cancel before the first request waits for the link or input, then cancels without opening the browser. That early cancel intent belongs to the mounted panel; after unmount, the existing adoption path lets the person cancel again.
- Runtime coverage (isolated credentials and a fake provider, never a live subscription): `e2e/oauth-login.e2e.ts` (callback, reload, agent-started login, duplicate refusal), `e2e/mobile-oauth-login.e2e.ts` (phone handoff, paste, cancel, reload), `e2e/remote-resume.e2e.ts` (host link loss and recovery), `e2e/sign-in-relay.e2e.ts` (host sign-in through the device's loopback). Guards: `sign-in-relay.test.ts`, the host replay case of `host-services.test.ts`, the stand-in case of `remote-sidecar.test.ts`.

### Featured providers
- One picker for both sign-in surfaces: first run's "which provider do you use" step and Settings › Models & accounts › Add a provider (`providers/ProviderPicker.tsx`; list `FEATURED_PROVIDERS` in `providers/provider-catalog.ts`; `STARTER_PROVIDERS` holds the featured ids too so cards show before omp answers).
- Popular ones lead as their own group ("Popular providers"/"주요 프로바이더"; cards `[data-featured-provider]`: `ProviderMark` + name + one line + action, `min-h-11` = 44 px, `auto-fill minmax(15rem)` so a phone gets one column); the rest stay under "Other providers"/"다른 프로바이더". A search is the flat list of every match, no group.
- Ids and login kinds are stock's (pi-catalog `auth/*.kdl`, `/login` roster), never invented: ChatGPT = `openai-codex` OAuth; Claude = `anthropic` OAuth; OpenRouter = `openrouter` (browser sign-in or paste yields a durable API key); Gemini = `google-gemini-cli` (stock's plain `google` has no login); Grok = `xai-oauth` (device-code, primary) with `xai` API key as the card's quieter second action (`apiKeyId`; subscription first; the key action is a quiet row INSIDE the card under a hairline, never a loose row under the grid).
- **OMPdesk keeps no plan or tier wording** (the owner's rule, so plan renames follow by themselves). A name is the brand (`PROVIDER_SHORT_NAMES` in `provider-groups.ts`, one table by provider id; any other provider is stock's name without its parenthetical) plus, where a plan shows, the plan read at run time from stock's live `get_providers` name (`providerPlan`: what follows the brand in the name, else its parenthetical without a leading brand word; `providerLabel` = "Claude (Pro/Max)" from "Anthropic (Claude Pro/Max)"). A card's name is `providerLabel`, the list header's secondary text is the plan. ### Context inspector, prompt sections, prompt origins
- **Context inspector** (Insights › This session › Inspect, `components/insights/ContextInspector.tsx`): bridge `context.inspect` (`resources/gui-bridge/context-inspect.ts`, rules `context-inspect-core.ts`) keeps stock `getContextBreakdown()`'s anchored totals (instruction files `instructionFilesTokens` → `memoryFiles`, skills, system prompt and context as stock splits them, omp 18.18.9+), splits tool schemas by source (built-in / MCP / extension, per tool via stock `estimateToolSchemaTokens`) and lists each instruction file and skill where stock built it into the prompt: stock's `session.systemPromptSources` claimed by its own `claimPromptSources` (the rule its status line and `/context` count by), each source's text cut out of its block (`splitBlock`), so the rows add up to stock's totals and a prompt block counts only what is left. The composer's context ring shows stock's instruction files as their own row (`contextUsage.category.files`), as `/context` does. Pinned by `bridge-context-inspect.test.ts` (the split) and the inspector half of `bridge-input-history.test.ts` (installed omp: a context file and a skill are rows that sum to stock's totals and open to their text).

- **No device twice in a request** (`resources/gui-bridge/xdev-notice.ts`, rules `xdev-notice-core.ts`, capability `xdevNotice`): a section's `before_agent_start` result carries a `systemPrompt`, and stock then treats the base catalog as dropped (`baseXdevCatalogDelivered = result?.systemPrompt === undefined`, `agent-session.ts`), so its `xdev-mount-notice` names every dynamic device again although the prompt (catalog, `## MCP Tool Routes`) still lists it, costing thousands of tokens per first request.

Never a partly covered notice, never an edited one, because stock marks a message a `context` hook changed as per-call and Anthropic's cache breakpoints then stop before it. A different shape, or no `getSystemPrompt`, leaves the notice untouched.
  - The text is a pure function of the notice and the prompt, so the prefix is the same every turn and after a resume; a device the prompt later stops listing brings its notice back. Once stock counts an append-only `systemPrompt` as keeping the base catalog, the hook goes. Pinned by `src/main/bridge-xdev-notice.test.ts` (the rules on stock's rendering, and the installed omp's notice template matching what they parse).
- **Message filters off the request path** (`resources/gui-bridge/context-hook.ts`, capability `contextHookIdle`, used by the recap and mount-notice filters): stock's `emitContext` `structuredClone`s the whole context and `Bun.deepEquals` every message before **each** provider request whenever any extension has a `context` handler, even one that returns nothing.
  - Each filter leaves its extension's handler table (`pi.extension.handlers`, an internal read at run time; missing → the filter stays on every request) after a request whose context and branch hold none of its messages. It is put back by a session load or tree move (`session_start`/`_switch`/`_branch`/`_tree`), by the run's `agent_start`, and by the next prompt's `before_agent_start`, **from where it may not leave until `agent_start` or `turn_start`**, because stock adds a mount notice after that hook, behind `runPrePromptCompactionIfNeeded`, and the run's first request can come before `agent_start` reaches the extension (a follow-up prepared inside a running loop gets no notice and ends the hold at its `turn_start`).

A session holding a recap or a mount notice keeps its filter.

- **Background checks** (`resources/gui-bridge/modes/background-checks.ts`, text and gate in `background-checks-core.ts`, capability `backgroundChecks`): one static section (`<background-checks>`, ~120 tokens) telling the agent to run tests, builds, lints and typechecks with bash `async: true` by default, keep working on independent steps, read the result before claiming done or before a dependent edit, and keep a run in the foreground only when the very next step needs it, it must be watched, or it would fight another run for a lock, port or build directory.   - **Measured**: the section changes little when the agent knows a suite is slow and reduces foreground baseline runs when it does not; every run still read the test result before its final answer.
