## Models, accounts and held stock defaults

### Desktop slot
- One session at a time drives the desktop. Files: contract `resources/gui-bridge/desktop-slot-contracts.ts`; bridge `desktop-slot.ts` + `desktop-slot-core.ts`; main `src/main/desktop-slot.ts` + `desktop-slot-host.ts` + `local/desktop-slot.ts`; renderer `stores/desktop-slot.ts`, `DesktopSlotIndicator.tsx`, the waiting line in `ToolCard.tsx`; capability `desktopSlot`.
- WHY: each omp has its own `ComputerSupervisor`; stock's native layer only refuses input while another operation owns focus ("no input was sent"). It neither queues nor spans a session's observe → act → verify, and nothing crosses processes. So **main** owns one slot per computer and the bridge patches `ComputerSupervisor.prototype.run` once (feature-detected; without `run`/`revokeControl` the slot is `unavailable` in capabilities/health and stock behaviour stays).
- A `snapshot.readOnly` run (screenshots, `capabilities`) never waits, nor does a run under stock's `computer.backgroundFallback: "refuse"` (`needsSlot` in `desktop-slot-core.ts`; the user's question, 22 Oct 2026: control other windows while I work, like Codex). Stock sends window input in the background (no pointer moved, no app activated) and under `refuse` refuses before sending anything that would take the foreground (a takeover rerun, raise, activate, desktop-wide input, a menu; `worker.ts` `refuseForeground`), so such runs of several sessions go side by side (`runBackground`: with no slot held it runs at once; while the session holds the slot, lets go of it or failed to revoke, it is an acting run, so a revoke aborts it and a failed revoke blocks it); under the default `takeover` an acting run may take the foreground and keeps taking the slot. The first acting run takes the slot (`desktop_slot_acquire` → `desktop_slot_bridge`) and keeps it until `agent_end`, `DESKTOP_SLOT_IDLE_MS` (20 s) without a computer run, Stop, abort, tab close/crash, or lease expiry (`DESKTOP_SLOT_LEASE_MS` 120 s without `desktop_slot_touch`).
- Waiters queue FIFO. An acting run that had to wait does **not** run once granted: it returns `DESKTOP_SLOT_STALE_NOTICE` so the agent re-screenshots and repeats.
- **Handoff**: abort the holder's in-flight input run, await stock `ComputerController.revokeControl()` on every controller the bridge saw, only then grant the next session.
- **Never handed on unconfirmed.** A `revokeControl()` that rejects (holder's acting runs get "input is blocked") or is silent for `DESKTOP_SLOT_REVOKE_TIMEOUT_MS` (10 s) leaves the holder `revoke-failed` (`DesktopSlotState.holder.revokeFailed`): nobody is granted, main retries every `DESKTOP_SLOT_REVOKE_RETRY_MS` (5 s; a late answer counts), the indicator offers "다시 시도" (`desktop_slot_retry`) and "그 세션 중지" (`desktop_slot_kill`: abort + `restart()` of its omp, SIGTERM only).
- Freed only by a confirmed revoke, a confirmed exit of the holder's process (host re-reads `whenExited()` while the sidecar is ready; a failed grant is not a crash), or a kill whose process exited within `KILL_CONFIRM_MS` (5 s). A bridge `desktop_slot_release` follows only a confirmed revoke.
- UI: app-wide "화면 사용 중: <title> · 대기 N" with Stop (`desktop_slot_stop`: aborts the holder's turn, hands off); a waiting `eval` card says "화면 차례를 기다리는 중 (N번째)".
- Hosted tabs for a paired device join this slot; tabs on a remote host use that host's slot (main skips `sidecar.device` tabs). Autopilot never takes it (its `eval` is off). No "run marked done" release (stock has no marker).
- Tests: `desktop-slot.test.ts`, `desktop-slot-host.test.ts`, `bridge-desktop-slot.test.ts` (fail-first: rejecting revoke, silent revoke, holder death after failed revoke, kill), `e2e/desktop-slot.e2e.ts`.

### Account rotation
- Settings › Models & accounts pref `accountRotation` (`quota` default = stock's usage ranking | `even`; `src/shared/account-rotation.ts`, `providers/RotationModeControl.tsx`). Stock has no switch: each spawn passes `OMP_GUI_ACCOUNT_ROTATION` and the shared ledger `<userData>/account-rotation.json` (`OMP_GUI_ACCOUNT_ROTATION_STATE`); a change or bridge connect pushes `account_rotation_set {mode}` to every live local sidecar and every tab this machine hosts (`LocalMachine.setAccountRotation`, `src/main/account-rotation.ts`). A paired host's tabs follow the host's pref (`host.accountRotation.get|set`).
- **Even**: the bridge's `account-rotation.ts` (`before_agent_start`) gives an account-less session the unblocked account handed out least recently across all local omps, as an automatic warm pin (`authStorage.sessions.pin(…, {restoredAtMs})`). A session keeps it until blocked (idle pin renewed, not re-ranked); stock's 429 blocking/failover is untouched.
- **Quota re-ranks at turn start.** WHY: stock re-ranks an automatic pin only when cold (Claude: 60 min idle), blocked or spent, and `affinity.record` refreshes last-use on every request, so a session used without a 60-min gap stayed on its first account for days (subagents inherit the parent's pin via `sessions.inherit`). `rerankBeforePrompt` (`account-rotation-core.ts`) runs in the same hook for the main agent only (`ctx.agent.kind === "main"`; subagents keep the spawn copy), never mid-turn.
- It asks stock, not our own policy: the account stock's selector would give a pinless session now (`authStorage.keys.getWithCredential(provider, <stand-in id>, {…, recordAffinity: false})`). It moves the pin (automatic warm pin, `restoredAtMs: now`) only when ALL hold, else stock decides: >1 account; pin exists and is warm; pin is automatic (read via the `include(provider, explicit)` callback of `sessions.inherit` with a stand-in target returning `false`; no provenance = left alone); session unrestricted (`sessions.permits`) and no account has a stock policy (`oauth.policy`): pools/policies are the user's choice; pin not blocked; both accounts measured and stock's comparator (`orderUsageRankedCandidates` over `RankedOAuthCandidate` rows from both `usage.report`s, mirroring `#rankOAuthSelections`) still ranks the other first after the pin's required drain is multiplied by `RERANK_DRAIN_MARGIN` (2).
- The margin is OMPdesk's only addition (stock compares drain at 1e-6 and every switch rewrites the provider's per-account prompt cache). Only the plain drain order gets it; stock tiers (blocked, spent, 85% 5h demotion, unmeasured) move a pin at once; a round trip needs a 4x swing. Proper fix belongs in stock.
- Tests: `src/main/bridge-account-rotation-stock.test.ts` on the real omp (2.7x moves, 1.9x never, 2.1x does, no way back at 1.9x, hot 5h tier, explicit/cold/subagent, inheritance), rules in `bridge-account-rotation.test.ts`; internals in `capabilities.ts` (`accountRotation`) and `health.ts` (`auth/rank`).

### Provider sign-in
- Settings › Models & accounts and first run (`providers/ProviderLogin.tsx`) run stock `login` on the tab's omp. While a sign-in is in flight its `open_url`, `input` and info `notify` requests (`isSignInRequest` in `shared/rpc-types.ts`) belong to the panel (`loginRequestIds` in `stores/extension-ui.ts`) and **never render as chat cards**, even after the panel unmounts, the page reloads or a paired host's link returns.
- Main counts `login` commands in flight per tab (`SidecarPool.noteSignIn`); for a paired host's tab also the host's `signIn` tab event (sent as `login` starts/ends, on every `tab.open` incl. a new tab's `{active: []}`, and ahead of `openAsks` on re-attach), because the host's login runs on when this window's `login` call fails with the link. A host status (not the link) leaving `ready` drops the host's list. Main marks each such request (`IpcSignIn`: `active`, provider, browser page) on the live `EXTENSION_UI` frame, in `EXTENSION_UI_OPEN` and in a host's re-sent `openAsks`; all reach the page through `pushTabExtensionUiRequest`: a marked request is never a card.
- While `login` runs (`active`) the page adopts the sign-in (`adoptedLogin`, counted in flight) and the panel shows it when reopened ("Sign-in in progress…", browser link, paste fallback, Cancel) until main sends `SIGN_IN_ENDED` (`endTabSignIn`: answers the leftover; panel reloads providers or shows the failure; outcome is unseen if a host's login ended while the link was down). Once `login` answered, a request is a leftover and is answered `cancelled` at once.
- Browser sign-in finishes through stock's loopback callback; stock also races a code paste and never closes it. A local desktop tab opens the launch URL automatically and keeps the paste collapsed. A web page or paired host's tab opens the provider URL only on a click and shows the paste immediately. The panel answers the leftover `cancelled` once `login` returns (an empty answer earlier only re-asks).
- Stock's RPC `login` has no cancel and holds omp's serial command queue (up to its 5-min callback timeout), so Cancel sends `login_cancel` (`src/main/local/settings.ts`), ending it via the callback's own denial (`error=access_denied` with the flow's `state`). A relaunched client has lost a host login's browser page (Cancel of its adopted panel then answers the paste).
- `accounts.provider_sign_in` starts the guarded RPC in main and returns without waiting for authentication. Its renderer event selects the caller tab and opens that provider in Models & accounts; the panel adopts the existing login rather than starting another. Main refuses a second login in the same tab, including one started from another viewer. Startup errors remain visible even before the panel adopts a request.
- A pasted answer is sent once per request while delivery is pending. Failed delivery allows retry, and a late answer cannot clear a newer prompt. Cancel before the first request waits for the link or input, then cancels without opening the browser. That early cancel intent belongs to the mounted panel; after unmount, the existing adoption path lets the person cancel again.
- Runtime coverage: `e2e/oauth-login.e2e.ts` checks callback, reload, agent-started login and duplicate refusal; `e2e/mobile-oauth-login.e2e.ts` checks phone browser handoff, paste, cancel and reload; `e2e/remote-resume.e2e.ts` checks host link loss and recovery. These use isolated credentials and a fake provider, not a live subscription.

### Featured providers
- One picker for both sign-in surfaces: first run's "which provider do you use" step and Settings › Models & accounts › Add a provider (`providers/ProviderPicker.tsx`; list `FEATURED_PROVIDERS` in `providers/provider-catalog.ts`; `STARTER_PROVIDERS` holds the featured ids too so cards show before omp answers).
- Popular ones lead as their own group ("Popular providers"/"주요 프로바이더"; cards `[data-featured-provider]`: `ProviderMark` + name + one line + action, `min-h-11` = 44 px, `auto-fill minmax(15rem)` so a phone gets one column); the rest stay under "Other providers"/"다른 프로바이더". A search is the flat list of every match, no group.
- Ids and login kinds are stock's (pi-catalog `auth/*.kdl`, `/login` roster), never invented: ChatGPT (Plus/Pro) = `openai-codex` OAuth; Claude (Pro/Max) = `anthropic` OAuth; OpenRouter = `openrouter` (browser sign-in or paste yields a durable API key); Google (Gemini) = `google-gemini-cli` (stock's plain `google` has no login); Grok (SuperGrok) = `xai-oauth` (device-code, primary) with `xai` API key as the card's quieter second action (`apiKeyId`; subscription first; the key action is a quiet row INSIDE the card under a hairline, never a loose row under the grid).
- Card names are fixed brand labels; a card whose logins stock's catalog doesn't list is skipped. First run (`showConnectedFeatured`) shows a connected featured provider as "Connected" in place; Settings lists connected ones above and leaves them out.
- First run (`onboarding/FirstRunSetup.tsx`, opened by `FirstRunGate`) is one step: brand mark, "Set up OMPdesk", one line, the picker, a one-line custom endpoint row (its explanation behind ⓘ) and Set up later. No step list and no GitHub step (GitHub sign-in lives in Settings › General and the PR center; an old saved `firstRunStep` of `github` is cleared). A browser sign-in the person starts on a local tab opens the browser by itself (stock sent a `launchUrl`; device-code and API-key pages wait for the click) and the login panel scrolls into view. Once a provider serves, the recommended model (`pickDefaultModel`, the connected provider first) is applied and saved as `modelRoles.default`, and setup ends with one toast naming it; the model step shows only when nothing can be picked or saving fails. The provider step ends setup only for a provider signed in on it or one that starts serving after it opened (`servingAtOpen`), so Back from the model step stays on the list. Cards are clickable while the omp still starts (`useProviderCatalog().loginReady`: status ready or starting): `useProviderLogin.start` waits for the tab itself (`tabReady`) and sends no `login` for an attempt cancelled meanwhile. The composer's "suggestions are off" line stays hidden while setup is open.
- The opt-in `e2e/first-run-walk.e2e.ts` (`OMP_GUI_FIRST_RUN_WALK=<dir>`) walks it end to end: fake installer and fake omp in en/ko (install → Claude sign-in through the fake's callback → first answer), the real omp's provider step on an empty agent dir (no sign-in), and the phone page's provider step at 390 px; `walk-<lang>.json` / `real-<lang>.json` hold per-screen seconds, clicks, visible words and buttons.
- Tests: `ProviderPicker.test.tsx` (order, actions, connected, search), `e2e/first-run-no-omp.e2e.ts` (fake omp `OMP_GUI_TEST_FEATURED=1`, en/ko × light/dark), `e2e/real-core.e2e.ts` (stock's real catalog lists all five in order), `e2e/mobile-pages.e2e.ts` (`?firstrun=1`: one column, 44 px, no overflow).

OMPdesk's own model roles and the security reviewer's tier follow the same rule (see Model roles › OMPdesk roles).
- Tests: `src/main/bridge-omp-defaults-stock.test.ts` and `bridge-goal-continuation-stock.test.ts` (real omp); rules in `bridge-thinking-default.test.ts`.

### Model roles
- Settings › Models & accounts › Model roles (`ModelRolesSection.tsx`, `ModelRoleRow.tsx`; contracts in dependency-free `resources/gui-bridge/model-role-contracts.ts`). Stock owns the roles (ids, names, tags, sections, `hidden`, `accepts`, empty-role fallbacks, `@role` resolution in `config/model-roles.ts`, `config/model-resolver.ts`); the bridge reads every one at runtime (`settings.ts` `roleMetadata`: each `MODEL_ROLE_IDS` id with `getRoleInfo`, `accepts` = the `modelKind`s of the catalog models its predicate takes, `defaults` = `rolePriorityDefaults`), so a role a newer omp adds is listed with no OMPdesk change. OMPdesk adds only an ordering preference (`ROLE_GROUPS`, `ROLE_ORDER`): Conversation (default, slow, smol, plan), Agent work (task, advisor, commit, tiny, widget), Input & output (vision, image, web, speech, dictation, judge); a role not in it goes by stock's section (kind → Input & output, chat → Agent work) after these, in stock's order. Hidden roles carry their reason (`HIDDEN_ROLES`): `memory` served only stock's memory backends, replaced by ai-memory.
- **No user-made custom roles** (the user's decision, 19 Oct 2026): `get_model_roles`/`get_model_role_metadata` list stock's built-in roles (`MODEL_ROLE_IDS`, `origin: "stock"`) then OMPdesk's own (`origin: "ompdesk"`, below); no add/rename/remove and no agent-usage lines. A `modelRoles.<id>`/`modelTags.<id>` the user set elsewhere is never read, listed or rewritten; stock still resolves `@id` for an agent that names it. The agent templates (`src/shared/agent-templates.ts`) name built-in roles and OMPdesk's own (`["@review", "@slow", "@task"]` for code-reviewer, `["@slow", "@task"]`, `["@smol", "@task"]`, `["@task"]`; pinned by `agent-templates.test.ts`); a template agent whose model line an earlier release wrote (`@debug, @slow, @task`, or code-reviewer's `@slow, @task`) is offered the current line by Definitions' "Update to role-based model" (`LEGACY_TEMPLATE_MODELS`, `agent-template-migration.ts`).
- **OMPdesk roles** (the user's decision: roles beyond stock are runtime-only; contracts `resources/gui-bridge/ompdesk-role-contracts.ts`, `OMPDESK_ROLES`; rules `ompdesk-roles.ts`): `review` (cross-family code review; chain `@review → @advisor → @slow → @task`). Each is stock's own `modelRoles.<id>` held as a runtime override: merged per key (`Settings.overrideModelRoles`, so `--smol`/`--plan` runtime values stay), value = the pick then the chain (`heldRoleValue`), never written to config.yml (the omp CLI stays stock), never over a config.yml/project value for the id (`getGlobalModelRole`/`getProjectModelRole`) or a runtime value OMPdesk did not write. Stock then lists it with its custom roles and resolves `@review` for every agent and subagent (overlay settings read the parent live).
  - Picks: `set_model_role` on an OMPdesk role writes `<userData>/ompdesk-roles.json` (`OMP_GUI_OMPDESK_ROLES`, passed by `sidecar-factory.ts` to every local and hosted omp; a single model selector per id, `parseRolePicks`), always, so config.yml is never written; while the user's config sets the id that value stays in force and the pick waits. Every omp re-reads the file at bridge start, before each turn (`before_agent_start`) and around the Settings reads and writes (`settleOmpdeskRoles`), so a pick on any tab reaches every omp of this computer from its next turn; a paired host's tab uses the host's file. Row: `model` = the pick, `effective` = `@review` through stock (`effectiveOmpdeskRole`: `configured` when the pick answers, else `fallback` with `via` the chain role that did).
  - Agent tiers (`AGENT_TIERS`): stock's bundled `security-reviewer` has no `model:` line and ran on the parent's model; OMPdesk holds `task.agentModelOverrides["security-reviewer"] = "@slow,@review"` the same way (Thinking first: on the P5 eval it scored 1.000 vs the review role's cross-family model 0.933, within noise; a cheap parent model must never run a security review), only while stock's bundled agent has no model line and no config sets that key. Overrides outrank an agent file's `model:`, so a user's own `security-reviewer.md` with a model line gets it back at spawn (`before_subagent_spawn`, stock `discoverAgents`).

It returns one hidden custom message (`ompdesk-todo-stale`, `display: false`, `<system-reminder>` naming the phases and done/total, "replace the list with its steps (op init) or mark the finished items done"), never a system-prompt section: a section that comes and goes changes the prompt in front of the whole conversation and the prompt cache would miss twice. A question or a short reply never gets it (`isNewRequest`: code rule, no model call; a trailing `?`, an English interrogative first word or a Korean question ending, unless a request word such as `줄래`, `고쳐`, `can you` is in it; under 8 characters; `/ ! $`). One list gets it at most twice (`MAX_REMINDERS`), the second only after 3 more requests left it alone; the reminder is journaled with the list's entry id, so a relaunch keeps the count. Whether the items name work the conversation moved past is not read (it needs a model); the untouched-request rule stands in.
