## Smart features

All three bridge features (prompt suggestions, automatic titles, automatic mode) live in `resources/gui-bridge/modes/`, each as dependency-free `*-contracts.ts` + rules in `*-core.ts` + behaviour in `*-engine.ts`/`*.ts`, each with a capability flag. They never use the session model silently and never fall back to the main model; a missing model, credentials, refusal or offline state is a quiet `unavailable`/none, never a toast.

### Prompt suggestions
- Built in, Settings › Agent behavior. Prefs `nextPromptSuggestions` (default **on**) and sub-switch `nextPromptInline` (default on). Files: `next-prompt-contracts.ts`, `next-prompt-core.ts`, `next-prompt-engine.ts` behind `next-prompt.ts`.
- Plumbing = the reply language: `OMP_GUI_NEXT_PROMPT` JSON at spawn, `next_prompt_set` on change and on bridge connect to every live local sidecar and hosted tab; a paired host's tab follows the host's pref.
- Model: stock's `ComposerPredictionController` runs only in its TUI and `runEphemeralTurn` can only use the session model, so the engine calls stock `completeSimple` on the model stock's `smol` role resolves to (`resolveRoleChain` over `roleCandidatePool`, credentials via `modelRegistry.resolver`). Reasoning off, ≤ 512 output tokens, one retry without the cap when a transport refuses it. NEVER the main model. No model / no credentials / refused / offline → `unavailable` frames, shown as a muted `role=status` line under the composer plus a bridge debug log, never a toast.
- When: one request per finished turn (`agent_end`). Regenerated (debounced `SUGGEST_DEBOUNCE_MS` 800 ms, gated by `gateSuggestion`: enabled, idle, main agent, empty composer, a reply exists, state key moved) after a compaction, a finished user `!` command (renderer `refresh_next_prompt`), a session switch and an emptied draft. Typing (`set_next_prompt_draft`, from `use-idle-compaction-draft.ts`), a new run or the switch going off aborts the request; an answer whose moment moved meanwhile (new messages, work started/ended) is dropped and asked again.
- **Running work does NOT suppress suggestions** (a delegating session has jobs running at almost every turn end, so suppression would switch the feature off where it is used most); the model is told the work is underway and suggests waiting for, checking or steering it, or something unrelated.
- **Nothing to approve** (reported: after the assistant steered a session it opened and said so, the suggestion was "좋아 그 방향으로 가"; on a replay of that moment 2 of 7 runs showed such a line, 0 of 7 after the fix, `src/main/bridge-next-prompt-real.test.ts`, opt-in `OMP_GUI_REAL_WORK=1` with `NEXT_PROMPT_BEFORE_REF=<ref>`):
  - Sessions the main agent opened with the control tools run in their own tabs, so stock's jobs never list them. Main's `AgentControlRuntime` sends the opener's tab `set_next_prompt_children` (→ bridge `next_prompt_children`, a free command) with the running or waiting items of the work board's review list each time that list is pushed (only on a change, at most `MAX_NEXT_PROMPT_CHILDREN` 20); `<app-state>` shows them as `sessions-working-now` / `sessions-waiting-for-an-answer`.
  - `awaitsDecision` (in code, no model): an `ask` still open, the reply's final paragraph ends in a question or puts a choice (`할까요`, `골라 주세요`, `should I`, `which do you prefer` …), or its last two paragraphs offer a next step (`OFFERS_USER`: `원하시면`, `필요하시면`, `말씀해 주세요`, `알려 주시면`, `let me know`, `if you want` …; measured on 16 real moments, 5 replies ended on such an offer, often with the options as a list after it, and all 5 read as asking nothing). `<app-state>` says `last-reply: asks the user to decide …` or `… reports work done or underway; it asks the user nothing`, and the rules allow approving only in the first case.
  - With no decision pending the cleaner drops a line made only of approval words (`isApprovalOnly`, `APPROVAL_WORDS`: "좋아 그 방향으로 가", "그렇게 해", "진행해", "ㅇㅋ 고", "go ahead", "sounds good, proceed"); any line naming something ("진행 상황 알려줘") stays.
  - A `write` to `xd://…` (a tool device) is not a changed file in `<app-state>`.
- Prompt content:
  - First `<user-style>` with ONE line only: `register: 반말 …` / `register: 존댓말 …` when most of the user's last 6 typed messages (`REGISTER_MESSAGES`) end in one Korean register (`userRegister` over the first lines of `sentTexts`, which leaves out stock's `synthetic` and `attribution: "agent"` user messages, slash commands and `<…>` blocks; `koreanRegister` majority, a tie names none; `koreanRegisterOf`: polite = ends in 요/니다/니까/죠 except nouns like 필요, casual = a listed 해체/해라체/음슴체 last syllable such as 줘, 해, 래, 지, 음, 임, anything else neutral). The register is read from what the user typed in the whole session (`typedTexts`: the journal's branch, since after a compaction `session.messages` keeps only a few typed messages), over their latest 6 messages that show one (first line, else last line): one 반말 user's messages often end in a noun ("이미지는 허용", "전부 릴리즈 진행"), and 6 of 16 real moments named no register (one showed two 존댓말 candidates).
  - **NEVER include excerpts of the user's messages**: given six excerpts the small model re-asked them as new requests (v0.32.2: 9 of 16 restated with six, 0 of 16 with none, register held).
  - Then the transcript tail (the reply being followed up clipped to 1800 chars, older ones to 700) plus a compact `<app-state>` read from the live session (last failed tool/command and exit, files changed this turn, open plan/todos, a question answered this turn, the main agent's running subagents and background jobs, a subagent's own included, as `running-now` via stock `getAsyncJobTree` — a subagent with the intent of the spawning `task` call —, goal, whether tests ran/failed, the user's `!` command, compaction).
  - Rules: stock `prompts/system/composer-prediction-user.md` voice/follow-up lines (write as the user), exactly 3 different next steps (asked for "up to 3" the cheap model often wrote one, so no chips showed), each a message the user sends to the assistant (never the assistant's voice, never addressed to the user, never offering/promising work), in the user's own voice, never repeat/reword/re-ask what they sent, use the `<user-style>` register, 3–8 words within the limits below, nothing already done, started, planned or handed to a subagent.
  - **Measured, not guessed** (24 Oct 2026, the user's "프롬프트 추천하는것 제대로 개선좀"): 16 real moments of the user's own sessions (a reply, then what they typed next), the request built as the engine builds it and asked of their real `smol` model, judged blind as two lists in random order (harness kept outside the tree). A system prompt that named three kinds of candidate (an answer, a check of a claim, a next step) and required specific nouns was worse (usable lists 12 → 8 of 16, one-line answers 2 → 7) and is not used. The code-level changes above (offers, the register from the whole session, field names, openers and periods, the 48-character tolerance) with the prompt unchanged, over three blind samples (the first two also dropped "기다릴게"-style lines, a filter since removed): usable 30 → 33 of 48, the better list 17 to 12 with 19 ties. What is left: the model writes a single line on about 5 of 16 moments, and sometimes invents a detail the reply never named. Change the prompt only with such a blind comparison; one sample a moment is noisy (the same variant read 12 and 9 usable in two runs).
- **The register is enforced in code** (v0.32.1 voice rules alone still produced 존댓말 for a user who writes "배포해줘"). `cleanCandidateLine` / `cleanCandidates`, whatever the model writes:
  - a line in the assistant's voice (`isAssistantVoice`, conservative: ko `드릴게요/드릴까요/드리겠습니다`, `둘게요/두겠습니다`, `보신다면/하신다면/원하시면`, `알려 주시면`; en a leading `I'll`, `I will`, `Shall I`, `Would you like`, `Do you want me to`, `Let me` but not `Let me know`/`see`) is dropped whole;
  - `matchRegister`: for a casual user each sentence's polite end becomes its 반말 form by a fixed list (주세요 → 줘, 되나요 → 돼, 죠 → 지, and 요 after a 해체 syllable: 해요, 줄래요, 할까요, 있나요, 좋네요 …); any other polite end (니다, 세요, 예요) or a remaining honorific/humble word (주시, 하세, 드리, 제가, 저희 …) drops the line. For a polite user only 반말 ends a noun never has gain their polite form (줘 → 주세요, 돼 → 돼요, ㄹ래/ㄹ까 → +요, 지? → 죠?) and nothing is dropped: **a polite user is never pushed to 반말**. No register named → the line is left alone;
  - length: the request asks for at most `ASKED_CANDIDATE_CHARS_CJK` 40 characters in Korean, Chinese or Japanese, the cleaner keeps up to `MAX_CANDIDATE_CHARS_CJK` 48 (the model overshoots a stated limit: with 40 both asked and enforced, the most useful candidate of 3 of 32 real samples, at 41, 42 and 48 characters, was dropped) and `MAX_CANDIDATE_CHARS` 60 in other scripts; over that a line keeps its first sentence when that fits (`fitCandidateLength`), else is dropped — never cut at a comma/word (a cut sends a different, unfinished request);
  - mojibake lines are dropped (see Mojibake from the model);
  - a line naming the request's own tags or `<app-state>` field names (`PROMPT_WORDS`: "그 last-failure 어디서 난 거야?") is dropped ("I'll wait"-style lines stay: two blind judges read "기다릴게"/"확인해볼게" as a natural answer to an offer); an opener the user never uses ("좋아,", "응,", "OK,") and a final period they never write come off (`userVoice` from their typed messages, `style` in `cleanCandidates`), so a candidate that differed from another only by them is a duplicate;
  - last, a line restating a message the user already sent is dropped (`SentMessages.isCopy` over every typed message of the session): F1 of a weighted longest common subsequence of units (each Hangul/Han/kana char, each Latin/digit run; a text's first 400), weighted by rarity across the sent messages (IDF), so shared rare words count, shared endings/everyday words hardly do, and Korean rewording still matches. `COPY_SIMILARITY` 0.6 against the latest message at any length, and against ANY sent message only from `COPY_MIN_UNITS` 14 units on (short generic requests recur and stay worth suggesting).
- Display: the best of up to 3 ranked one-line candidates is the placeholder (Tab/→); the rest are chips (↓ from an empty composer enters them, ←/→, Enter/click fills; Alt+1..3 fills directly; up to `min(100%, 44em)` wide so a 48-char Korean candidate shows whole (`.omp-next-chip` `max-width: min(100%, 52em)`), wrapping to a second row, full text as tooltip). Per-session memory in `stores/next-prompt.ts`: submit or a run clears it, a deleted draft brings it back. In a field narrower than a hint fits (`fieldNarrow`, a pane of a split) the best candidate leads the chips as on touch and is no placeholder: a placeholder the field cannot hold is cut, which a suggestion kept across a relaunch showed in `e2e/split-select.e2e.ts`.
- **A suggestion never vanishes on its own** (the user's report, 24 Oct 2026: "원격이든 현재기기든 추천 프롬프트 날라가지 않도록"). Main forwards a session's frames only to windows that show its tab, so a suggestion made while the tab was in the background, before a reload, while a phone was hidden or a paired host's link was down, or by an omp a relaunch replaced, never reached the page and none showed until the next turn. The bridge keeps each session's last suggestion (`kept` in `next-prompt-engine.ts`; empty once `agent_start` makes it stale) and journals it (`NEXT_PROMPT_ENTRY` `ompdesk.next-prompt`, `{id, candidates, used, at, key}`, feature-detected `appendCustomEntry`/`getBranch`); `next_prompt_state` (`get_next_prompt`) answers it as `last` (`NextPromptLast`), an omp started on the session reading the journal's entry once, valid while no `message` entry followed it (custom messages leave it, as on screen), and seeding `lastKeys` when it was made for the moment this omp sees. Every hydration (`syncNextPrompt`: a tab shown again, a reload, a phone's resync, a host's re-attach) records it with `recordLast(key, last, since)`, which never undoes the page and orders nothing by two computers' clocks (a paired host's may be minutes off): each suggestion carries an `id` (its frame, the journal entry and `last` alike), the page drops a read during which it recorded a frame or let the session's suggestion go (`clear`: a submit, a run; both times on its own clock), and a `last` whose identity is one the page let go (its `id`, an older bridge's by its text) never comes back. An emptied draft asks the model only when the moment moved (trigger `draft`, not forced; it was `refresh` and replaced the suggestion the person saw on every typed-then-deleted draft). The tabs store clears a session's suggestion only when an idle (`ready`) tab starts running, never on a paired host's re-attach (`starting` → `running`). Pinned by the "last suggestion" cases of `bridge-next-prompt.test.ts`, `stores/next-prompt.test.ts` (`recordLast`, a host clock two minutes behind and far ahead, the re-attach), `e2e/next-prompt-keep.e2e.ts` (a tab in the background and a reload; a relaunch with no new request), `e2e/mobile-next-prompt-keep.e2e.ts` (a phone opening the session after its turn, and a reload) and the suggestion case of `e2e/remote-resume.e2e.ts` (made while the link was down).
- **Inline completion** (`complete_inline` → `next_prompt_inline`, same cheap model, ≤ 512 tokens, `InlineScheduler`): ghost text after the caret for a single-line draft of ≥ `INLINE_MIN_DRAFT_CHARS` 8 with the caret at its end, `INLINE_DEBOUNCE_MS` 600 ms after the last keystroke, at most one request start per `INLINE_MIN_INTERVAL_MS` 2 s (≤ 30 a minute, answers cached per draft; `e2e/next-prompt.e2e.ts` scripts 10 typing bursts in a minute and sees 10 requests). Aborted on every keystroke; never during IME composition, with a slash/`@` menu or paste choice open, for drafts starting `/`, `!`, `$`, `->`/`=>`, or a draft stock's `shouldSkipHistory` calls secret. Tab accepts, Esc dismisses.
  - Request carries the same register line (no excerpts); rules ask for the whole message, the draft restated character for character then continued on its own topic, one piece of the same sentence, never the assistant's words.
  - `cleanInlineReply` takes what follows the restated draft (`inlineDraftWindow`; trailing spaces of a draft ending in one are not doubled). A reply that does not start with the draft as typed shows nothing: **the user's text is never rewritten**. The ghost must be ≤ `INLINE_MAX_CHARS_CJK` 20 / `INLINE_MAX_CHARS` 50 (longer shows nothing, never cut), no role label, tag, fence or second sentence. Then the assembled message (draft + ghost) is judged — no assistant voice, no leaving the register (an opposite ending or, for a casual user, an honorific/humble word), no restatement of a sent message; each check counts only what the ghost brought. (Why the whole message is restated: asked for the continuation alone, 9 of 12 glued onto the last word.)
  - Debug log `next-prompt inline` records model, time, whether a ghost showed and the register, NEVER the text. `next_prompt_state.requests` counts both kinds.
- The user's own `next-prompt` extension is found through stock's loaded-extension list (`legacyExtension`); while the built-in is on the renderer ignores its widget; with the built-in off or unsupported the widget path works as before.
- Tests: `src/main/bridge-next-prompt-stock.test.ts` (smol resolution, legacy detection, reply cleaning vs stock's `parseComposerPrediction`), `bridge-next-prompt-core.test.ts`, `bridge-next-prompt.test.ts`; opt-in `OMP_GUI_REAL_WORK=1` `e2e/real-next-prompt.e2e.ts`. Loaders `config/model-roles`, `config/model-resolver`, `modes/controllers/input-controller`, `pi-ai` in `capabilities.ts` / `health.ts`.
- **Suggestions on touch** (`useShellInput() === "touch"`; desktop unchanged):
  - No Tab/→/↓/Alt+1..3/Esc, so `use-composer-suggestions.ts` builds the chips = best candidate FIRST, then the runner-ups (≤ `MAX_NEXT_PROMPT_CHIPS` 3), drawn by `NextPromptChips` as **one sideways-scrolling row** (`.omp-next-chips[data-touch]` in `mobile.css`: `nowrap`, `overflow-x: auto`, 32 px high, 28 px chips, scrollbar hidden, `--hit-gap-y: 4px` because an overflow container clips the global 44 px reach). The row sits just above the composer box (never inside). Nothing with no suggestion; hidden while typing, streaming or with a menu open.
  - The best candidate is **never also the placeholder** (`placeholderPrompt` undefined on touch; the placeholder stays the idle hint); no `Kbd` hints, `aria-keyshortcuts`, "to accept" chip or tooltip titles.
  - A **tap** fills the field, caret at the end, NOT sent (`pickChip` → `placeDraft`). A **long press** (the shell turns it into `contextmenu`) arms the chip and shows a "Send now" / "바로 보내기" button (`input.chips.sendNow`) that sends it through `send(text)`; any other pointer-down disarms.
  - **Inline ghost completion is OFF on touch** (`useInlineCompletion` gets `enabled: … && !touchInput`; no `complete_inline` request is ever made): the phone keyboard has its own suggestion strip, Korean IME composition keeps the draft "composing" so a ghost would shift every keystroke, and no clean accept gesture exists. The `nextPromptInline` switch still governs desktop.
  - Pinned by `InputArea.next-prompt-touch.test.tsx` (chip tap fills without sending, long press → Send now, first chip not the placeholder, no kbd/Tab hint, no `complete_inline`) and `e2e/mobile-suggestions.e2e.ts` (Pixel 8 emulation on the dev harness, which exposes `window.__stores.nextPrompt`; `OMP_GUI_SUGGEST_TOUCH=<dir>` writes the en/ko light captures).

### Mojibake from the model
- v0.33.0 showed UTF-8 read as Windows-1252 ("ì•Œê² ì–´ …" for "알겠어 …") in the placeholder and a chip. Nothing in OMPdesk decodes that text (bridge socket, omp stdout and IPC are UTF-8 end to end); the model itself wrote those characters. So OMPdesk **refuses, never repairs** (a model rarely spells every byte: Windows-1252 has no character for 0x81, 0x8D, 0x8F, 0x90, 0x9D; a no-break space 0xA0 becomes a plain space once whitespace is folded).
- `isUtf8Mojibake` (`resources/gui-bridge/mojibake.ts`, dependency-free) flags text with two or more whole UTF-8 sequences spelled in Windows-1252 characters (three- or four-byte ones, or Latin-1 letters led by Â/Ã). Real Latin-script text never forms them ("„Straße“", "café…", "ação" stay clean; pinned by `src/main/bridge-mojibake.test.ts`).
- Where applied: `cleanCandidateLine` drops the line; `cleanInlineReply` shows no ghost; automatic titles keep the current name (`concise` in `auto-title-engine.ts`, the shorter retry too); the idle recap is neither shown nor journaled (`session-recap-core.ts`, checked before `deliver`).

### Automatic session titles
- Built in, Settings › Agent behavior › Session titles. Prefs `autoTitle` and sub-switch `autoTitleEvolve` ("keep the title up to date as work changes"), both default **on**. Files `auto-title-contracts.ts`, `auto-title-core.ts`, `auto-title-engine.ts` behind `auto-title.ts`; capability `autoTitle`. Plumbing as prompt suggestions: `OMP_GUI_AUTO_TITLE` JSON at spawn, `auto_title_set` on change and on bridge connect to every live local sidecar and hosted tab; a paired host's tab follows the host's pref.
- **Stock machinery only, never the session model for a first title**: `AgentSession.generateTitle` (stock's `generateSessionTitle`, `tiny` → `commit` → `smol` role chain; the session model only as stock's own retry fallback after those failed) names the operator's first message (`operatorTitleText`); `renameTitle(title)` adds the card per `title.icons` (OMPdesk holds `boring`: no card, no card request — see Held stock defaults). A message the title model declines (a greeting) is retried from the conversation after the turn with `renameTitle()`. Main agent only; subagents are excluded.
- A brief another session's agent sent (`<ompdesk-agent-message>`, an `ompdesk_session_open` or Autopilot child) is named from its `Title:` line, else its body (`titleInput` in `auto-title-core.ts` over `memory-prompt.ts` `unwrapPrompt`), because stock's `isLowSignalTitleInput` strips the whole tag block and declined it, which left such a session untitled until its one long turn ended (pinned by `bridge-auto-title*.test.ts`).
- **Origin is stock's own record**: `SessionManager.titleSource` and the journal's `title_change` entries (`source`, `trigger`). The one case stock cannot say, "a fresh automatic title over a typed one" (`setSessionName(…,"auto")` is refused over source `user`), is written as source `user` with `trigger: "ompdesk-auto"` (`TITLE_TRIGGER`) and read back by `titleIsAuto` (`auto-title-core.ts`). Nothing lives in a GUI-only file.
- **Language, length, form**: stock's `title-system.md` is English-only and asks for 3-6 imperative words, so the model answered English and long. The engine sets the session's TITLE_SYSTEM.md slot (`setTitleSystemPrompt`, read by `generateTitle`, `renameTitle` and stock's replan refresh; the card request passes its own prompt) to stock's own `title-system.md` (`ompPrompt` + `prompt.render`, never copied) plus one line (`titleLanguageLine`): the language the user writes in first (for a non-English reply language, `currentReplyLanguage()`, that language when unclear); a plain noun-phrase summary, 2–4 words (`TITLE_MAX_WORDS`), ≤ 12 chars in Korean/Chinese/Japanese (`TITLE_MAX_CJK_CHARS`) and 30 otherwise (`TITLE_MAX_CHARS`), spaces included; subject and head noun kept, modifiers and generic words dropped; two `COMPRESSIONS` examples ("로그인 비밀번호 에러 메시지 버그 수정" → "로그인 오류 수정", "CSV export empty with filters" → "Empty CSV export"); no punctuation, quotes or emoji; identifiers and names as written. Set at attach, on `reply_language_set` (`onReplyLanguageChange`) and again before each request (stock's headless `/move` re-resolves the slot). Reply language off/unset/English → same line without the language fallback (the title stays in the user's language).
- **Over the limits** (`titleFits`), while the line is in effect: ONE retry, never more, never on the first pass, on a stronger model than the cheap chain (the cheap chain answered its own retry with the same 13–16-char titles): stock's `default` role (`roleCandidatePool` + `resolveRoleChain`), else the session's model, the first with credentials (`modelRegistry.getApiKey`/`resolver`), via stock `completeSimple`, reasoning off, `RETRY_MAX_TOKENS` 256, temperature 0, `cacheRetention: "none"` (Anthropic's 1 h cache write doubled a one-off request's cost).
  - System prompt = the slot's prompt + `titleShorterLine` (the too-long answer named, ≤ 12/30 chars, subject and head noun kept, modifiers and generic tails such as 화면, 메시지, 로직, 기능, 관련, "with …" dropped, all four `COMPRESSIONS` as examples); message = the operator's first message, or the answer itself when stock built the context for `renameTitle()` (✨, evolving). The reply's `<title>` goes through stock `normalizeGeneratedTitle`; counted in `requests`; a failed retry keeps the first answer.
  - The retry wins unless longer than the first answer (a tie goes to the retry) and is kept whole up to the hard cap (`TITLE_HARD_CJK_CHARS` 14, `TITLE_HARD_CHARS` 32, any word count). Past it `conciseTitle` cuts whole words, NEVER an ellipsis: in Korean/Chinese/Japanese generic words go first (`CJK_FILLER`: 화면, 메시지, 로직, 기능, 관련, 부분), then the leading words (the head noun comes last: a cut from the end turned "작업 현황판 화면 디자인" into "작업 현황판 화면"); otherwise the trailing ones, never ending on an English function word such as "with" or "the".
  - Every generated title is logged in omp's own log (`auto-title: title {answer, retry, retryModel, retryUsage, title}`). Cost reference (16 Oct 2026): a retry ≈ $0.005 (≈ 1.2 k input, 15–18 output tokens).
- Cards: under `title.icons: boring` a fresh title drops a card (stock's retitle keeps the current title's card through `keepTitleCard`, so ✨ and evolving on an old carded title come back plain; `cfgTitleIcons`, stock `splitCardTitle`); under another value the card is kept (`formatCardTitle`). Stored titles are never rewritten on their own. A person's own TITLE_SYSTEM.md (any slot value the engine did not set) is their whole title prompt: stays as written, uncut, never retried (`planTitlePrompt`). Setting the slot turns off stock's `title.generator: fork` path, which a GUI session never reaches (`autoTitle` is TUI-only in `main.ts`).
- **Evolving** (sub-switch): after a terminal `agent_end` while the title is automatic, `EvolveGate` (no model call; `DEFAULT_GATE_RULES`: `minTurns` 2 terminal turns and `minIntervalMs` 60 s since the title was set or last considered, and the work moved — a file edited/written 1, the todo plan changed 2, the goal changed 3, `threshold` 3 — or `forceTurns` 6 regardless) asks stock `renameTitle()` once per window. The result is applied only when not a reword of the current title (`isRewordedTitle`: normalized word overlap ≥ 0.6 `SAME_WORDS` or character-trigram overlap ≥ 0.55 `SAME_TRIGRAMS`). Every write re-checks the session id, the name and `titleRevision` it started from, so **a typed name wins over any request in flight and ends the evolving**.
- Cost: 1 title-model request for the first title (+1 for its card when `title.icons` ≠ `boring`, +1 retry on `default` when over the limits), then at most 1 per two finished turns and minute (+ its retry), only after files/plan/goal moved or six quiet turns (counted in `auto_title_set`'s `requests`).
- ✨ auto button (title bar, rename dialog, sidebar row; `hooks/use-auto-title.ts`, `common/AutoTitleButton.tsx`) sends `regenerate_session_title` → local handler → bridge `regenerate_title` (`renameTitle()` on the live session, saved as an automatic title even over a typed name; failure is one inline `role="alert"` sentence, never a toast). A stored session no tab has open has no omp to ask (origin tracking lives in that omp), so its button is aria-disabled with a tooltip. A paired host's tab answers on the host (the command is in `quota-commands.ts`' model list). A changed title eases in (`common/SwapText.tsx`, `.omp-title-swap`; the global reduced-motion rule shortens it).

### Automatic mode choice
- Settings › Agent behavior › Smart automation › Auto mode, and the "Auto mode" switch in the composer's Mode popover. Pref `autoMode`, default **on**, only `false` turns it off. Files `auto-mode-contracts.ts`, `auto-mode-core.ts`, per-session memory `auto-mode-state.ts`, behaviour `modes/auto-mode.ts`; capability `autoMode`.
- Decides **only Plan or Goal, or none**, and **uses that mode for the one request it classified, never as the session's mode** (the user's call after it put a busy work session into Plan). Other manual modes are never enabled by it.
- Classifier: stock has none (`plan.defaultOnStartup` is unconditional; `auto-thinking/classifier.ts` picks an effort), so the bridge copies its approach: stock `judgment` (`resolveJudge` over the `judge` role chain: a native System One judge first when its key exists (since omp 18.12.2 TypeSafe's Jev, `openrouter/typesafe/jev-1.14`), then `@tiny` → `@smol` → `@default`; one choice question answered in a few tokens, `sharedJudgmentCache`, `journalJudgmentUsage` with purpose `auto-mode` so session totals count it) and `preprocessTinyMessage`. The judge's state carries `previousExchange` (last user message and reply, 400 chars each); its instructions say none for anything that continues, answers or corrects that work.
- No env or sync plumbing: the composer reads the pref at send time (`lib/auto-mode-client.ts` `runAutoMode`, called from `planComposerSubmit`'s `beforePrompt` for a plain prompt only, never steer/follow-up/slash) and calls `auto_mode_decide` (a model command in `remote/quota-commands.ts`; a paired host's tab runs it on the host, with the host's quota). The bridge method decides and changes nothing; main (`local/auto-mode.ts`) applies it through stock's own commands: bridge `modes.set_plan_mode` with `auto: true` for Plan (`auto-mode-state.ts` `autoPlan` marks it), stock `goal create` with the prompt text as objective for Goal.
- After a Goal decision `planComposerSubmit` sends the prompt with `streamingBehavior: "steer"`: on an idle session stock's `goal create` admits the goal's own turn at once (`rpc-goal.ts` `#scheduleContinuation`), ahead of the prompt, and stock refuses a plain prompt while a turn runs (`AgentBusyError`; sent plain it came back as "Message not sent"); steer joins that turn or starts one.
- **One request only**: an automatic plan ends at its approval, and **nobody clicks it** (the user's call, 21 Oct 2026: Plan under Auto mode means the agent plans and goes on by itself). When the agent proposes a plan while `autoPlan` holds, the bridge (`plan.ts` `onProposalWritten`) emits no `plan_proposal` frame (so no card in any window, nothing waits on the person, no needs-you notification), aborts the planning turn as for a card, and runs its own `approve` with `keep_context`: plan mode ends and stock's approved-plan prompt (the plan inlined, as stock's own render does) starts the execution turn in the same session. A paired host's tab does it on the host (the bridge runs there). A plan mode the user turned on, or took over from an automatic one, still shows the card. An automatic plan also ends when the user sends a plain prompt before the agent proposed it (`runAutoMode` first sends `auto_mode_end` → main sends `modes.set_plan_mode {enabled: false}`); the chip's undo leaves it as before. An automatic goal ends when it completes (`goal_updated`) or the user stops the turn (`abortActiveTurn` → `endAutoGoal` → `auto_mode_end` → stock `goal drop`). Neither ending is an undo: later prompts are still classified.
- **The Mode picker never shows it** (`ComposerModes` leaves `autoMode`'s plan/goal out of its label, badges and Plan switch); only the "This request: Plan/Goal" chip (`AutoModeChip`, store field `autoMode`, clears itself when the mode ends) does, with the undo. Turning Plan on in the picker over an automatic plan makes it the user's (`set_plan_mode` without `auto` clears `autoPlan`; the store's `autoMode` goes).
- **No hijacking busy sessions**: `autoModeSkip` answers `busy` without a request when the session ran anything within `AUTO_MODE_IDLE_MS` (10 min; the last message's timestamp), has open todos (pending/in progress) or running subagents/background jobs, a subagent's own included (`getAsyncJobTree`) — so Plan only happens on a session's first message or after 10 idle minutes. Plan needs a stated probability ≥ `MIN_PLAN_PROBABILITY` 0.7, Goal ≥ `MIN_PROBABILITY` 0.6.
- Bounds: `AUTO_MODE_TIMEOUT_MS` 2000 ms in the bridge (3000 ms in the renderer; raised from 1500 because a cold first request or loaded machine often exceeded it and decided none); a timeout, failure, low probability or unknown answer is none; a message under `MIN_CLASSIFIED_CHARS` 12 is none without a request.
- **Never on the critical path longer than it must be** (20 Oct 2026; the order judge → mode → prompt stays: Plan must be on before the model can edit, a Goal's prompt joins stock's goal turn as a steer). The first request to the judge's host after an omp starts took 1.5 s and more (DNS and TLS while stock's model discovery downloads from the same host; 0.4 s afterwards), so the 2 s deadline lost every first message. So: the bridge warms a native judge once per omp as its main session starts (`warmJudge`, `install`'s `session_start` hook; one unbilled judgment of `AUTO_MODE_WARM_REQUEST`, outside the answer cache and the ledger; a prompted judge is never warmed); every typing pause (`AUTO_MODE_PREFETCH_DEBOUNCE_MS` 250 ms, `components/layout/composer/use-auto-mode-prefetch.ts`, this computer's own tabs only) sends `auto_mode_prefetch {message}` with the text the send will carry, whose answer lands in stock's judgment cache (journaled once, purpose `auto-mode`), so the decision at Enter is answered from it; a decision joins a prefetch of its own text or a warm-up still under way instead of asking again (`PrefetchSlot` in `auto-mode-core.ts`). The warmed connection also serves stock's auto-thinking classifier (held `defaultThinkingLevel: auto`). Measured (one app at a time, a new session's first message, 1.5 s between typing and Enter, 3 runs each): Enter → prompt in the journal 0.88 s before, 0.65 s after, 0.54 s with auto mode off (no judge); an Enter the moment the tab is ready takes 1.3–1.8 s in all three (stock's auto-thinking judgment on a cold host). Pinned by `bridge-auto-mode-prefetch-stock.test.ts` (installed omp, loopback native judge: one request per distinct question, the decision at Enter from the cache, a joined question, billing), the `PrefetchSlot` cases of `bridge-auto-mode-core.test.ts`, the prefetch and order cases of `auto-mode-client.test.ts` and the two prefetch tests of `e2e/auto-mode.e2e.ts` (set_plan_mode before the prompt; goal create before the steer).
- Other guards: pref off, a turn running, `/` and `!` messages, any active mode the user picked (plan or goal: **a manual mode always wins**), and per session (`auto-mode-state.ts`, keyed by transcript id) a rejected plan (no plan again, goal still allowed) and an undone decision (`auto_mode_undo`, a free command: leaves the mode, stops all auto decisions for that session). Logged at debug level (`gui-bridge: auto mode`).
- Measured (19 Oct 2026, 44 labelled prompts (plan 8 Korean + 3 English, goal 6 + 3, none 20 + 4), 3 rounds plus cold starts, 139 calls per model, the bridge's own instructions): Jev 92.4 % right (Korean 90.2 %, English 100 %), p50 412 ms warm / 467 ms cold, p95 563 ms, no timeout, ≈ $0.000027 a call; Sonnet (the `smol` judge before 18.12.2) 74.2 % because 48 % of its calls passed the 2 s deadline (97.7 % had it waited), p50 1.8 s, ≈ $0.0002 a call. Neither ever chose plan or goal for a none-labelled prompt (Jev's plan probability there ≤ 0.04, Sonnet's 0) nor plan for a goal prompt, so `MIN_PLAN_PROBABILITY` went 0.75 → 0.7 (Jev's Korean plan requests came back at 0.52–1.0; 0.7 takes the 0.73–0.74 answers, Jev plan recall 24 → 26 of 35). Pinned with those answers in `bridge-auto-mode-core.test.ts`.
- **Plan is narrow** (21 Oct 2026, the user's report: every long first message ran in Plan). The plan criterion used to read "a new feature across several files where reviewing a plan helps", which every detailed feature request matches, and a long first message is usually one: on the user's real `judge` (Jev 1.14) 2 of 10 long, concrete first messages chose plan (one of them a real session's "read docs/…, write the ADR, then scaffold apps/homepage", plan 0.97) and 3 more had 0.51-0.68 of plan's probability against the 0.7 floor. Not the cause: `preprocessTinyMessage` (none of them reaches its 2000 characters) or the threshold. Now plan is only a message that asks for a plan, design or proposal before any change, or large work (a migration, a rewrite across the codebase) whose approach the message leaves open; a concrete request is none however long, detailed or multi-step (`AUTO_MODE_INSTRUCTIONS`, `autoModeCriteria`). After: 0 of 10 long concrete messages plan (the reported one 0.39), both plan-asking messages still plan (1.0), the six short audit prompts unchanged except "refactor the whole settings module into separate stores … update every caller", concrete and now 0.5 plan (none). The 19 Oct measurement above was made with the broader criterion; its plan recall is lower now by design.

### Judge-model assists
- Small decisions asked of stock's judge, the way auto mode asks (`judgment` `resolveJudge` over the `judge` role chain, `sharedJudgmentCache()`, `journalJudgmentUsage(session.sessionManager)` so session totals count them, telemetry), but **only while stock's `hasNativeJudge(settings, registry)` is true** (the chain resolves first to a native decision model: TypeSafe's Jev 1.14 through OpenRouter on a stock install) **and** pref `judgeAssist` is on (default on; only a stored `false` is off; Settings › Agent behavior › Smart automation "Use the judge model for small decisions", `JudgeAssistRow.tsx`, deep link `agent:setting-gui-judgeAssist`; the `judge` row of Model roles links to it). The check runs on every call, because a login, key or role change moves the chain. Never a direct Jev client, never new provider code.
- **OMPdesk works fully without the judge and only gets better with it (the user's rule).** No key, a prompted fallback (Sonnet, a local model), the switch off, an omp without the feature, an error, a timeout (`JUDGE_ASSIST_TIMEOUT_MS` 2 s; the engine races its own timer, so a judge ignoring the abort never holds a caller) or an unreadable answer → the judge "did not decide" and every feature runs its previous code rule, byte-identical. Nothing in the UI mentions Jev beyond Model roles' existing one-line hint.
