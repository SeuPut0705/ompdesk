## Settings, layout and look

### Settings layout and rows
- Sections (`settings-catalog.ts` `SETTINGS_NAV`; one name per section in en/ko and the native menu): **App** General (language, notifications, profile, window, GitHub account; Advanced: window placement (default side panel, panel edge, terminal shell) and proxy), Appearance & input (an Advanced holds follow-agent-theme and the paste threshold), Keyboard shortcuts; **Agent** Models & accounts, Agent behavior (its Advanced opens with the two auto-panel rows, then the stock groups), Memory (see The Memory page), Tools & extensions, Permissions & security, Projects & launch, Schedules; **System** Devices & connections, Updates & about (versions plus This computer, the machine setup list), Other settings. Older names ("Models & providers", "General › This computer", "Settings › SSH") mean these.
- **Minimal settings, maximum automation** (the user's rule, 21 Oct 2026): a setting exists only where people really differ; what has one right answer is automatic, an action is never a setting. Merged or removed then, each with its stored value carried once by `migrateRetiredPrefs` (`src/main/retired-prefs.ts`: `MERGES` decide the new value, `RETIRED_PREFS` delete the old keys; pinned by `retired-prefs.test.ts`): Appearance's "hide thinking" and "expand thinking by default" are one choice, Thinking: hidden / collapsed / expanded (`ThinkingDisplayRow.tsx`, over the two prefs it writes, `displayPreferences.hideThinkingBlock` (⌃T, follows omp until chosen) and `thinkingExpanded`; what is stored reads as hidden if hiding was on, else expanded if expanding was on, else collapsed, and hiding keeps the open state for ⌃T); the System light/dark pair shows only while the theme is System; the run state in the window title and progress on the app icon are always on (no `titleState`/`showProgress`; across windows one waiting on the person outranks one working, as inside a window: `aggregateProgress`, `aggregateTrayStatus`); the sidebar's shortcut pins are set on the sidebar (Help › Customize sidebar… sheet `SidebarPinsSheet`, a pinned row's context menu Unpin), not in Settings; Agent behavior has no Goal/Autopilot/open-agents action rows (they are the Run chip's, the palette's and the menus'); the GitHub update token row shows only while the updater is `auth-required` or a token is stored; one "Keep tools up to date" (`toolsAutoUpdate`, on unless all three old switches were off) replaces the omp, tool-CLI and extension switches; one "Approve new devices on this computer" (`mobileWeb.confirmNewDevices`, on if either old switch was) covers phones and computers; the work board has no switch and no close (it docks whenever a pane has room, else the strip shows; the user's call, 22 Oct 2026: its ✕ hid it with no way to open it again).
- Curated rows come first. Rare rows and raw stock rows (the auto panels, window placement, non-curated schema rows, launch profile, reset passes, account pools, model overrides, the proxy) fold under one closed `SettingsAdvanced` disclosure at the section's end; `SettingsPage` opens it before scrolling to a search hit or deep link inside, so every row stays reachable and searchable.
- Models & accounts reads connection, then models: Providers & accounts (accounts, live quota, rotation), Custom endpoints, then Model (setup assistant, Model roles, Defaults, Compare models). "This device" / "Selected host" scope lines (`SECTION_SCOPE`) show only while the focused tab runs on a paired host.
- No section intros: `settings.section.*.desc` only feeds nav search. App and Agent sections (except Memory) are tip-only (`SettingsTipOnly`, `isTerse` in `SettingsPage`): every string description sits behind its info glyph; rows read icon + label + control.
- Sidebar shortcuts (prefs `sidebar.railPins`, `stores/sidebar-prefs.ts`) are off by default, including the footer's Agents and Stats (reachable through the palette, the menu, ⌥A and Settings; Settings and the help menu always stay). Only the usage block is on until a saved `railPins` array (even empty) says otherwise; it lists one line per subscription account with usage windows and renders nothing for API-key-only users. They are set on the sidebar itself, never in Settings: Help › Customize sidebar… opens `SidebarPinsSheet` (one switch per pin, a bottom sheet on a phone), and a pinned row's context menu (right click, Shift+F10, long press) has Unpin and Customize sidebar…; `toggleRailPin` is the one writer.
- Compact rows (`settings/SettingsLayout.tsx`): `SettingsRow`/`SettingsSwitchRow` are one dense line (`--sc-control-md` high): optional decorative `icon` (lucide glyph, or `ProviderMark` for a provider, model or vendor CLI), label, muted `description`, control at the right. A string description up to `INLINE_DESCRIPTION_MAX` (56) characters reads inline; a longer one sits behind a `SettingInfo` glyph (tooltip on hover/focus, text kept as `sr-only`); a node description (a cost, a warning) stays a visible small muted note. Collections (accounts, CLIs, devices, schedules, MCP servers, shortcuts) are dense list rows with secondary actions behind an overflow `MenuButton`. New rows reuse these, never a boxed card or a full-width description paragraph.
- Outside Settings (Mode popover, dialogs, run settings) `SettingInfo` and `splitDescription` (`common/SettingInfo.tsx`) are shared with `common/Switch.tsx`'s `SwitchField`: the glyph sits outside the `<label>`, so the switch is named by the label alone. A boolean row never stacks a paragraph under its label.
- The composer's Mode popover (`layout/composer/ComposerModes.tsx`, `modes/ModeConfig.tsx`, `modes/AutopilotConfig.tsx`) is built from `SettingsRow`s (`compactControl`; fixed-width `Select`/`Input`/segmented `Tabs` at the right; explanation behind `SettingInfo` in the row's `badge`; `FocusChips compact` within two rows; a one-line `GrowArea` that opens on first focus and never collapses on blur; release-procedure check as a glyph with the sentence as tooltip and name; one short warning line beside Start; no footer line) and scrolls inside `max-h-[min(36rem,calc(100dvh-6rem))]`. Nothing in it may change layout on a blur: a press blurs the focused field at mousedown, a reflow moves the control from under the pointer and its click never fires (v0.35.0: typing in the guide box and clicking Start did nothing). Pinned by `ComposerModes.autopilot.test.tsx` and the guide test of `e2e/autopilot-cycles.e2e.ts`.
- Opt-in captures: `e2e/settings-captures.e2e.ts` (`OMPDESK_SETTINGS_SHOTS=<dir>`; `OMPDESK_SETTINGS_SECTIONS` / `OMPDESK_SETTINGS_SIZES` narrow it), `e2e/mode-captures.e2e.ts` (`OMPDESK_MODE_SHOTS=<dir>`).

### Figure headers
- A box with a title and actions (code block, mermaid/svg figure, a write's figure in its tool card, the Files viewer's mode switch; `chat/FigureHeader.tsx`, `chat/Figure.tsx`) wears ONE header row on its top edge, `--sc-control-sm` high: kind or file name left, lucide icon buttons right (Preview/Code as two `aria-pressed` buttons via `FigureModeToggle`, then wrap, copy, download, enlarge), each with `IconButton`'s tooltip + `aria-label`. Never a separate text-tab row above such a box.
- `Figure` (`data-figure="mermaid|svg"`) owns the box and the Preview/Code state (`mode`/`onModeChange`); `CodeBlock` takes `title`, `headerActions`, `endActions`, `bare` for the same header. Tests: `chat/Figure.test.tsx`, `e2e/figure-header.e2e.ts` (`OMP_GUI_FIGURE_HEADER=<dir>` captures).

### Phone and tablet (web build only; an Electron window keeps the desktop layout byte for byte)
- `common/MasterDetail.tsx` is the one list-beside-detail primitive (`MasterDetail`, `useMasterDetail`, `MasterDetailBack`). Phone (`useShellMode() === "phone"`): one pane at a time, the list, then the row's detail under a back bar; the system back gesture takes a back layer while the detail is open. Tablet and desktop keep two columns. `SettingsPage` uses the hook (`data-stacked` on `.settings-page`: the section list is its own page, search results replace it, a deep link opens the detail); the GitHub center sections and the PR center use `MasterDetail` (the PR store's `deselect` is the back).
- On a phone `SettingsRow` stacks label and description above a full-width control unless `compactControl` (a switch row, or a one-button control such as push "Turn on" and install: stays at the right). Switches and `SettingInfo` glyphs are small with a 44 px hit area, except an info glyph in Settings' content on touch: it heads lines 28 px apart, so it declares `--hit-gap` 20 px (a 36 px target) and its line is 36 px tall, and it never takes the next line's taps (`mobile.css`, 34245bb5f); `ListRow` carries `omp-list-row` (40 px on touch). `e2e/mobile-pages.e2e.ts` covers it on the dev harness in Chromium and WebKit (`OMP_GUI_MOBILE_PAGES=<dir>` captures; `harness.html?rail=all` pins Agents and Stats).
- Scale (`styles/mobile.css`): a tablet and plain touch do NOT resize controls or type (`--sc-control-*` 28/32/36, `--sc-icon-*` 14/16/20, body and transcript 15 stay the desktop's). A **phone is denser**: the "Phone density" block (`html[data-shell="phone"]`) is the only place that overrides those tokens: `--phone-type-scale` 0.8667 (`applyFontSize` in `lib/theme.ts` multiplies it into `--gui-font-size` and the body size, so the type preference reads 13 px instead of 15 and still scales), `--sc-font-2xs/xs/sm` 12, `--sc-control-sm/md/lg` 24/28/32, `--sc-hit-min` 24, `--sc-icon-lg` 16, `--sc-row-touch` 36, `--sc-row-action` 44. A new phone rule goes in that block, gated on `html[data-shell="phone"]`, and never changes a ≥ 1200 px or tablet layout. Fields stay 16 px (iOS zooms into anything smaller); sheet items are `--sc-row-action`.
- A phone turned sideways (`html[data-shell="phone"]` under `(orientation: landscape)`, the last block of `mobile.css`) has the width portrait lacks: composer chips 10 px apart (each reach 5 px, the 26 px + a 36 px tap), the model chip's whole name, 12 px chip badges, a 36 px work strip, a 38 px suggestion row and a 36 px work-card "Steps" row. A work card's 24 px step chips sit 12 px apart under any finger (phone in either orientation, tablet; reach, never drawn bigger; portrait drew 26 × 28 targets until 22 Oct 2026). Portrait's 19.4 % chrome budget does not apply sideways. Pinned by the phone landscape test of `e2e/responsive-smoke.e2e.ts` (844×390, zero soft findings on the session surfaces) and the rotate step of `e2e/phone-day.e2e.ts`.
- Chrome budget at 390×844: gutters 12 px (`--omp-column-pad`), header bar 40 px, dock card head 28 px, always-open composer (see "Phone composer"), side-panel title row 36 px and tab bar 40 px; header + work chip + dock + composer stay ≤ 19.4 % of the height while idle (measured 18.4–18.5 % without suggestions, 22.6 % with them; the user prefers the always-open composer to a lower share).
- The 44 px rule is a hit area only. Under `html[data-input="touch"]` every `button`, `[role=button|switch|tab|checkbox]`, `summary`, `[data-setting-info]` and checkbox label gets an invisible `::after` reaching `--sc-touch-target` (`@layer base`, so an element's own `::after` or positioning utility wins; an element with `after:`/`before:` utilities is left alone). Never lift a switch, chip, ⋯ or icon button to 44 px visually; a field has no pseudo-element and is drawn 36 px.
- A hit area never covers a neighbour (the responsive audit's `stolen-tap`): a container of close controls sets `--hit-gap-x` / `--hit-gap-y` to the gap between them and the reach stops at half of it (title bar icons 14 px apart ≈ 40 px hit; composer toolbar, dock header, work chip, sidebar and panel top bar declare theirs); unset, the reach is the full 44 px. The bound counts from the control's own edge, so it must not be tighter than the room around it: a compact settings row resets it (`--hit-gap-y: initial`; a stacked row's own control reaches 7 px up and down on a phone, `--hit-gap-y: 14px`, under its label's 36 px info line; the stacked rows' 8 px bound left switches 32 px between rows that no tap reached), and a scroller clips every reach to its padding box (the terminal key bar's key scroller holds the bar's padding so its keys reach the panel tab bar's hit area).
- **36 px through spacing, not size** (20 Oct 2026): a 28 px control (26 inside its border) reaches 36 when its neighbours sit 10 px apart and the container declares `--hit-gap-x|y: 10px`, so on touch (`html[data-input="touch"]`, web build only) the clusters that sat 0–4 px apart are spaced 10 px: page top bars, the side panel's title row and its views' button clusters, the tablet composer row, Settings' button clusters (14 px on a phone, whose icon buttons are 24 px), Stats' section pills, the context popover's actions, a schedule's days (their rows 14 px apart, a 24 px day reaching 7 px up and down), a message's actions, a figure's header buttons (reaching 5 px out of its 28 px header; a phone's 24 px ones 14 px apart), a multi-question card's step tabs (outranking the tab bars' 4 px bound), a phone's message actions (14 px apart), the sidebar update card's Restart and dismiss (10 px apart). Rows that stack flush (tabs, sheet items, Changes rows, the Run sheet's Advanced and Model roles, a host sheet's actions, the children-at-work rows) are a row tall with `--hit-gap-y: 0` (a Changes row's stage box label and file stand as tall as the row, the label as wide; the discard icon keeps its size and reaches the row's height, 14 px from the file; the Changes view's own 24 px controls behind a 1 px border sit 14 px apart, bounded at 14, so each reaches 36); a segmented tab bar (`[data-segmented]`, its tabs 2 px apart) declares `--hit-gap-x: 2px`, and a wrapping button row or chip list gets room on touch as well as its bound, since a reach is its own box plus half the gap and a bound alone over 4-6 px left them 26-29 px (the Autopilot run's controls 10 px apart, the benchmark's models 12 px, each remote address 7 px above and below inside its row, the import dialog's search and refresh and the terminal's toolbar 10 px; a finished work card's findings and copy button 10 px apart (a wrapped line 14, the row no longer tucked under the narrative; the outcome's "Result" a touch row), the phone Run sheet's Autopilot buttons 14 px apart, the goal dock bar's Pause, Edit and Drop 10 px apart (`data-goal-dock`; an iPad held sideways handed a tap on Pause to Edit) and 14 px apart on a phone, whose buttons are 24 px (10 px left them 32 × 34 once the strip panel's summary stopped covering the bar, responsive smoke at 390), an Autopilot run's board controls (Pause, End, Stop now) 14 px apart, a section head's own buttons (the run log's copy) 8 px in from its end, and a board row's own pin or ✕ reaching the touch row (`--hit-gap-y: 10px`) and only 6 px sideways, so no reach makes a docked board scroll sideways; on a phone, whose icons draw 24 px behind a 1 px border and reach from the 22 px inside, the side panel views' clusters sit 14 px apart, bounded at 14, and a view's lone buttons (the terminal's New terminal, the Files viewer's Back, an empty state's actions, `data-terminal-head`, `data-file-viewer-head`, `data-empty-actions`) get the room around them); tabs and sheet items are `--sc-row-touch` / `--sc-row-action` rows on touch. A docked tablet sidebar's device and folder headers, starter guide and project ⋯ are 36 px boxes; on touch the always-shown project ⋯ takes its own slot beside "+" instead of overlaying the title. The drawer's left-edge strip (`EdgeSwipeZone`) owns swipes only: a tap on it is handed to the element under it (`tapThrough`).
- Pinned by `styles/touch-targets.test.ts` and, for the hit area, `hitSizes()` in `e2e/harness.ts`. The harness page takes `?stress=1` (long URL, wide table, long code line, diff, mermaid, long tool paths) for the responsive audit (`e2e/responsive-audit.ts`).

### Themes
- Ten distinct themes, five light and five dark (18 Oct 2026; replaced eleven near-identical tints). Ids, groups, schemes and the retired-id table: dependency-free `src/shared/theme-names.ts`. Light: `light` (OMPdesk Light), `github-light`, `solarized-light`, `sepia`, `hc-light`. Dark: `dark` (OMPdesk Dark), `nord`, `tokyo-night`, `gruvbox-dark`, `hc-dark`. `LEGACY_THEME_NAMES` maps titanium/nord/latte/gruvbox/paper/solarized/dawn/frost/matcha to the nearest same-scheme successor (CIE Lab distance of page and accent).
- `light` and `dark` are written token by token in `lib/themes.ts` because `theme-light.css` / `theme-dark.css` must match them (`styles/tokens.test.ts`). Every other theme is one compact `ThemePalette` in `lib/theme-palettes.ts`; `lib/theme-builder.ts` derives all 119 `--omp-*` tokens plus the terminal's ANSI 16, six chart series and the focus ring (`themeExtrasFor` writes `--omp-ansi-*`, `--omp-chart-1…6`, `--sc-focus-ring` inline). Published palettes (Solarized, Nord, Tokyo Night, Gruvbox, GitHub Primer; MIT, credited in `THIRD_PARTY_NOTICES.txt` via `scripts/generate-third-party-notices.ts`) start from their own colors; a color failing AA as text is shaded toward the text color until it passes.
- Never add a theme that is a tint of an existing one: `themes.contrast.test.ts` fails a same-scheme pair whose page, accent and three loudest syntax colors are under mean ΔE 15 apart, or whose accents are under ΔE 15.
- Contrast is a test, not a review. `lib/theme-contrast.ts` lists every text, accent, status, syntax, diff, button/badge, selection, border, focus-ring, chart and ANSI-16 pair with its floor: 4.5:1 (7:1 High Contrast), 3:1 for graphics. `themes.contrast.test.ts` fails any theme under a floor; `styles/colorblind.test.ts` holds the color-blind palette (per scheme, `--cb-*` in `global.css`) to 4.5:1 on every theme. A status color as text on its own soft wash (a badge, a chip) is `--sc-<status>-on-soft` (`tokens.css`, a third toward the text color, `STATUS_ON_SOFT_MIX`), never the bare status color (`tokens.test.ts` fails a stylesheet rule or a component class string that pairs them): 11 px warning on its wash over the sidebar's selected row read 3.64:1. After touching a palette run `bunx vitest run src/renderer/lib/themes.contrast.test.ts`.
- **System** pairs one light and one dark theme (prefs `systemLightTheme` / `systemDarkTheme`, device-local like `themeName`; default `light` / `dark`; a wrong-scheme name falls back to the default). `applyThemeByName("system")` resolves the OS scheme to the pair's theme and writes its tokens inline (not stylesheet-driven); `data-theme` carries the scheme, `data-theme-name` the theme shown (Mermaid, e2e and captures read it); `setSystemThemePair` re-applies when System is selected; the watcher in `lib/theme.ts` re-applies on an OS flip. Picker: `settings/ThemePicker.tsx` (System card with both halves previewed, a light group, a dark group, and the two pair selects only while System is chosen); `ThemePreview` is shared with `dialogs/ThemePickerDialog.tsx`.
- Migration: `migrateThemeName` maps a retired id to its successor and an unknown value to null (the caller falls back to System, never a blank theme). `getPersistedThemeSelection` stores the successor on first read (desktop prefs and a paired device's uiPrefs alike); the main process rewrites `themeName` / `systemLightTheme` / `systemDarkTheme` once in `prefsStore()`; `nativeThemeSource` (`lib/theme.ts`, used by `main/window-chrome.ts`) takes the scheme from the theme id, so a saved window opens in the right scheme before any renderer runs. A paired host's reported `themeName` goes through the same migration (`hooks/use-host-appearance.ts`).
- Every surface follows the theme through tokens, never a literal: xterm (`TerminalPanel.terminalTheme`, `--omp-ansi-*`), highlight.js (`--omp-syntax-*`), diffs (`--omp-diff-*`), Mermaid (`MermaidBlock` builds `themeVariables` from `--sc-*`, re-renders on `data-theme` / `data-theme-name`), charts (`lib/chart.ts`, `--omp-chart-*`), the Windows title-bar overlay and the phone page's `theme-color` metas (`lib/window-chrome.ts` `syncWindowControls`).
- Pre-paint: `applyThemeByName` stores `omp.themeScheme` (dark, light or system) and `omp.themePaint` (`{light?, dark?}` page backgrounds: System stores both); `public/pre-paint.js` paints it and sets the `theme-color` metas before any module runs. Static `manifest.webmanifest` colors stay the OMPdesk dark. `?theme=<any id>` works on the dev harness.

### Profile and reply language
- Profile: Settings › General › Profile stores prefs `userProfile` (`{name, experience}`; contracts and prompt text in dependency-free `resources/gui-bridge/modes/user-profile-contracts.ts`; levels beginner, vibe-coder, junior, expert). It rides the reply-language path: `OMP_GUI_USER_PROFILE` (JSON) at spawn, `user_profile_set` on change and on bridge connect to every live local sidecar and hosted tab; `modes/user-profile.ts` appends one `<user-profile>` section through `before_agent_start` (nothing for an empty profile). Stock has no such setting.
- Reply language: Settings › General › Conversation language stores prefs `replyLanguage` (`auto` default | a curated English name | `off`; `src/shared/reply-language.ts`; missing or unknown reads as `auto`). `auto` is the device language's English name (first usable `app.getPreferredSystemLanguages()` entry, then `app.getLocale()`; not the UI language). Each spawn passes it as `OMP_GUI_REPLY_LANGUAGE`; a pref change (or bridge connect) pushes it to every live local sidecar and every tab this machine hosts via the bridge's `reply_language_set {language: string | null}`. A paired host's tabs follow the host's own pref.
- `modes/reply-language.ts` keeps the value as module state and appends one instruction through `before_agent_start` from the next turn (nothing when off, unset or English, so the prompt stays stock); `currentReplyLanguage()` / `onReplyLanguageChange()` feed the session titles (see Automatic session titles).
- A second line in the same section, naming the same resolved language (never hardcoded), covers the labels a person sees: todo items and phase names, and a `Title: <short sentence>` first line in each `task` assignment, and in an Autopilot run the cycle's `title`, `summary` and `followups` the agent gives the `autopilot` tool, which the run's timeline and board show as written (the user's report, 21 Oct 2026: a Korean user's timeline was English, because tool arguments stayed in the model's language). A subagent's stock title (`generateTaskLabel`, `task/label.ts`) is always English with no hook and stock's task tool has no `description` field, so the GUI shows that `Title:` line (`assignmentTitle` in `modes/subagent-title-contracts.ts`, applied in `subagentPrimaryLabel` for sidebar rows, the Subagent panel header and the work board, and in `stores/subagents.ts` / `work-run.ts` for the work map; no line → stock's label). Thinking, the rest of every assignment, tool arguments, code and file contents stay as the model writes them (Korean costs more tokens).
- Text OMPdesk or omp writes into a session (Autopilot's cycle prompts, goal continuations, reminders, notes, other sessions' briefs) is English and never counts as the person switching language: the first line says so (an Autopilot run on a Korean computer answered in English, the user's report of 23 Oct 2026).
- Every session kind gets both lines: main, subagents (their rebind installs the hook), workers an agent opened, Autopilot runs; a paired host's tabs get the host's language (above). An instruction that would put todo items in another language yields to it: pstack's "copy the playbook's steps into `todo`" says to write them in the todo language this section sets (see Built-in pstack engineering mode).
- Pinned by `bridge-reply-language.test.ts`, `subagent-graph.test.ts` and the opt-in `e2e/real-subagent-titles.e2e.ts` (Korean and Japanese). Never inject GUI text with `--append-system-prompt`: it collides with the launch profile's flag and turns off omp's fork prompt-cache key.

### Sidebar memory
- The left side keeps what was left open or closed across a relaunch, a reload and a reopened window. Device-local prefs `sidebarVisible`, `sidebarFolds`, `sidebarFamilies` (`DEVICE_LOCAL_PREF_KEYS`: a paired web page keeps them per device, the desktop per profile). Code: `lib/sidebar-memory.ts`, `stores/sidebar-folds.ts`, `stores/sidebar-subagents.ts`, `stores/ui.ts`. Each pref has a localStorage mirror (`omp.sidebarVisible`, `omp.sidebarFolds`, `omp.sidebarFamilies`) read synchronously by the first render; the pref is read again after mount and wins when it differs, unless the user already edited.
- **Shown/hidden**: `useUiStore.sidebarVisible` starts from the mirror and every change is saved by a `useUiStore` subscription, except while the shell is a drawer (phone, portrait tablet: `AppShell` `useDrawerSidebarSync` calls `setSidebarDrawerMode`; the flag is then the drawer's open state, never saved, and the drawer always starts closed; saving resumes when the window docks). `pre-paint.js` sets `data-boot-sidebar="hidden"` from `omp.sidebarVisible` and the boot shell (`scripts/boot-shell.ts`) drops its sidebar and clears the traffic lights, so the first frame never flashes an open sidebar.
- **Folds** (`sidebarFolds`: `groups` project / folder `cwd` → folded, `devices` `local` and each paired host's deviceId, `deviceGroups` a host's folders as `deviceId\ncwd`, `chats` each device's Chats section (`local` or a host's id; an earlier build's `lane` is dropped on read), `deviceColors` each device header's chosen color, `archivedOpen`, `starterOpen` Get started, `usageCollapsed` the footer usage block, `deviceOrder` the device sections' order, `knownHosts` the last host list): a filter still shows every match.
- **Device order** (`layout/sidebar/SidebarDeviceSections.tsx`, rules `lib/device-order.ts`): once a host is paired, "This device" (`data-sidebar-local-device`) and each host's section can be reordered. The saved `deviceOrder` (ids, `local` = this computer) comes first; a device it does not name follows in the default order (this device, then the hosts as listed); `syncHosts` drops an unpaired host's id once the host list loaded. It lives in `sidebarFolds`, not the host's `sidebar` blob, so a paired web page keeps its own order. **Nothing moves after the first frame**: `knownHosts` (the hosts the last read named, `{id, name, offline?}`) draws each host's section before this launch's first read (`data-device-pending`, a still grey dot, the same body as the state it is likely to be: offline = header only, else connecting), so a host saved above This device does not push its rows down when the read lands; a host the read no longer lists leaves. While a host connects, its last-known rows (the session-list snapshot, namespace `device:<id>`) stand in, never read (`useSessionList(…, {read: false})`), so they are in place when it comes online; only with no snapshot does it show the connecting line. The list renders through the same component with or without hosts, so pairing never remounts this device's list. Only the section header is a handle (`data-device-drag-handle`; rows keep their drags): a mouse or pen drag arms after 6 px, a touch drag after a 400 ms long press (`TouchSensor`: a tap folds, a swipe scrolls, the long press's context menu is swallowed); nothing moves while dragging: an accent line (`data-device-drop-indicator`) marks the landing place and a chip with the device's name (`data-device-drag-chip`) follows the raw pointer (dnd-kit's delta includes the list's scroll), no drop animation. Keyboard: Alt+↑/↓ on a focused header (announced in a polite status region); right click or Shift+F10 opens Move up / Move down. Pinned by `device-order.test.ts`, `sidebar-folds.test.ts`, "Sidebar device sections › order" in `Sidebar.test.tsx`, `e2e/device-order.e2e.ts`.
- **Device colors** (the user's request, 22 Oct 2026: a paired host's rows were hard to tell from this computer's): every device section's header row wears its device's color, a light wash of the row and the hue on its glyph (`.omp-device-header[data-device-color]` in `components.css`; six hues drawn per scheme, never a status color). A paired host gets one by itself from its id (`autoDeviceColor`, `lib/device-color.ts`), this computer's header none; the header's gear (`data-sidebar-device-color`, `Settings2`, label `remote.sidebar.color`) chooses another, none, or automatic again (with a mouse it shows while the header is hovered or focused, or its menu is open, so at rest the name keeps that room; a finger keeps it at rest; pinned by the device header case of `e2e/responsive-smoke.e2e.ts`) (`sidebarFolds.deviceColors`, device-local, pruned with the host). The same color is on the glyph of the device chip a remote tab's title bar and pane header carry (`DeviceChip`, `data-device-color`). Pinned by `device-color.test.ts`, the color case of `Sidebar.test.tsx` and of `DeviceChip.test.tsx`.
- **Families** (`sidebarFamilies`: session paths whose family rows are open or hidden): a remembered open family keeps its entry until children have been seen and gone (`FamilyGroup`'s `hadChildren`), never at launch while they have not reported yet; a live tab's `tab:` key is never saved.
- **Bounded**: each record keeps its newest `FOLD_LIMIT` (50) entries and keys ≤ 200 characters (a paired device's whole `uiPrefs` record is capped at 64 KiB, `DEVICE_UI_PREFS_MAX_BYTES`: a write over it is refused for every pref in it). The sidebar prunes entries of folders, hosts and sessions that no longer exist (`pruneGroups`, `syncHosts`, `pruneFamilies`) only once a live read answered (`useSessionList().live`, never the last-known snapshot of the newest 150 rows) and the host list has loaded.

### Sidebar projects
- **A project is not its sessions** (the user's report, 21 Oct 2026: deleting a project's old sessions took the project off the sidebar). Each computer keeps a project list of its own, apart from its sessions, as Codex desktop keeps its saved workspace roots apart from its threads (its docs: hover a project › ⋯ › Remove, Add new project or ⌘O brings it back; an empty project's group reads "No chats"; issues openai/codex#18640 and #19615 name the stored keys). Claude desktop's Code tab (its `app.asar` read statically, never run; REA's analyzer timed out on its 6.7 MB chunk) and its docs group sessions by folder and keep folders only in saved environments; no separate project list was found there.
- Main owns it (`src/main/sidebar-projects.ts`, contract `src/shared/sidebar-projects.ts`, prefs key `sidebarProjects`: `{projects: [{path, addedAt, missing?}], removed, worktrees}`, never trimmed: a project leaves only by Remove and a removal is never forgotten). A folder enters when the person starts a new session there (`openTab` in `stores/tabs.ts`, local or a paired host's; a worktree names its main checkout) and by itself for every folder this computer's sessions ran in (`sync`, 1.5 s after the session index changes; its first pass lists the folders that had sessions before the list existed, each sorted by its newest session). Chats, the Work workspace (`~/.omp/work`), a file with no conversation yet and a folder that is gone never enter. It leaves only by the group menu's **Remove from sidebar** (`sidebar.menu.removeProject`), which deletes no file and no session: the folder goes to `removed`, its sessions list under no project (unless a tab holds one; the session picker still finds them), and only the person opening the folder again brings it back. The group menu's Delete deletes the project's sessions and the project stays, empty.
- An empty project shows its header with ⋯ and + and no row. A project whose folder is gone (`missing`, checked at every sync and read) stays, its name subtle with "Folder not found" in the tooltip and to screen readers, + disabled, Remove in its menu. Projects sort as before (pins, the dragged order, then recency), an empty one by `addedAt`. **Sessions keep the order the person sets too** (the user's request, 23 Oct 2026): a stored session row's menu (right click, Shift+F10, ⋯, the touch sheet) has Move up / Move down and Alt+↑/↓ on a focused row does the same, within its project or the Chats section; pins stay on top (a row never trades places across the pinned edge), a session never placed (new since the last move) is on top by creation as before, a live row with no file has no place to keep, and a filter turns the moves off (a move there would forget where the hidden rows were). Kept in the `sidebar` prefs as `sessionOrder` (`setSessionOrder`, per list key: the project's cwd, `CHATS_ORDER_KEY` for Chats, the newest 300 lists and 500 rows each; `orderByManual` in `lib/project-order.ts` is the one rule projects and sessions share). **A paired host's section orders the same way**: its projects drag by their header like this computer's (`SortableProject.tsx`, shared; a 6 px move arms it, so a click still folds) and its project ⋯ has Move up / Move down, its session rows' menus too, kept in this computer's prefs under the host's id (`hostOrderKey`: `<deviceId>\n<cwd>` in `groupOrder` and `sessionOrder`), so moving a host's project never moves this computer's and the order survives relaunches and reconnects. Pinned by the two "Move up and down reorder" cases of `Sidebar.test.tsx`.
- **A worktree folder never stays a project of its own** (the user's report, 23 Oct 2026: a paired Windows host's section was a column of empty `gui-agent-…` projects). A folder resolves through git, else its `.git` file (`linkedWorktreeRoot`: `gitdir: <main>/.git/worktrees/<name>` names the main checkout, no git needed), since a pass whose git could not answer (not installed yet, slow at a Windows startup) listed every agent worktree as its own project, and projects are never trimmed. Each sync also re-resolves the listed projects: one that is a linked worktree gives way to its project (`moved`, kept in `worktrees`). A listed folder named like an OMPdesk checkout (`gui-<name>-<hash7>`) whose folder is gone leaves the list (it was a worktree, never a project). Pinned by the three worktree cases of `sidebar-projects.test.ts`.
- **A host's gone session folders hide their sessions on a device too** (the user's report, 23 Oct 2026: a paired host's section on this Mac showed a column of `gui-agent-…` groups of sessions whose worktrees the host had removed): the host's `sync` names every session folder that is gone (`SidebarProjectsState.gone`), and the host section (`SidebarDevices.tsx`) leaves those sessions out unless a tab holds one, as this computer's own sidebar does with `projectName(cwd).gone`. A gone folder is asked again each pass (it may be restored). Pinned by "names the session folders that are gone" in `sidebar-projects.test.ts` and "hides a host session whose folder is gone there" in `Sidebar.test.tsx`.
- **A paired host's list is the host's own**: `MachineServices.sidebarProjects` (`host.projects.command {request}`, pushed as `host.projects.changed` → `SIDEBAR_PROJECTS_STATE` with the device) feeds the host's section (`SidebarDevices.tsx`, re-read each time its link comes up), whose group header has the same ⋯ › Remove. A device cannot ask the host's git, so the host's `sync` also sends `worktrees` (each session folder that is a linked worktree → its project) and the host section groups and removes by that project, never by the worktree's folder (an older host sends none: its sessions group by their own folder). The renderer store is `stores/sidebar-projects.ts` (`useProjectList(device, read)`, last read painted at the first frame through `lib/last-read.ts`).
- Pinned by `src/main/sidebar-projects.test.ts` (first pass lists folders with sessions and names worktree folders' projects, a deleted last session keeps the project, Remove sticks until the folder is opened, missing folders, 600 projects and removals kept across add, remove, sync and relaunch), the project-list case of `remote/host-services.test.ts`, the project cases of `Sidebar.test.tsx` (an empty project listed, delete keeps it, Remove local and on a host, a host worktree's session under its project and removed with it, a missing folder dimmed, a new session's folder added); captures `OMP_GUI_SIDEBAR_PROJECTS=<dir>` with `e2e/sidebar-projects-captures.e2e.ts` (dev harness `?projects=1`).
