## Autopilot

### Overview
- UI **Autopilot** (ko "오토파일럿"; code id `autopilot`; Mode popover tab beside Plan and Goal): an endless development run in its own new git worktree tab, built on **stock Goal continuation** (`goal.continuationModes ∋ rpc`), no scheduler of its own. States `running | stopping | paused(reason) | waiting_quota | ended`; "End" = stock `goal pause` (turn in progress finishes) then drop; "Stop now" = `abort`.
- Contracts live in the dependency-free `resources/gui-bridge/modes/autopilot-contracts.ts`: journal entries, states, settings, `set_autopilot`'s `AutopilotAction`, `AUTOPILOT_BRIDGE_METHODS`, and `AutopilotStatus` (carried by `get_autopilot` and the `autopilot_update` frame, whole on every update to every window and paired device).
  - The status carries only the newest `STATUS_CYCLES` (30) cycles plus `cycleCount` once there are more: main's overlay and its `get_autopilot`/`set_autopilot` answers cut it with `withRecentCycles`, because whole lists made every frame huge. Main keeps the bridge's whole list (`run.status`) for reverts, the PR body and the run summary.
  - The board's "+N more" and the log copy read every cycle with `get_autopilot {allCycles: true}`, read ahead on hover or focus of the copy button; a copy whose cycles are still being read starts its write inside the click with a `ClipboardItem` (`copyTextWhenRead` in `lib/format.ts`), because WebKit allows a write only inside the gesture.
  - On a device that took it as a delta over the link it is rebuilt whole (Remote devices, `slimAutopilot`): its cycles leave out `checkCommand` and `resolved` (read only by main's cycle-end frame and `begin`'s journal) and carry each summary clipped to one line of at most 400 characters (`clipCycleSummary`).
  - Pinned by "a long run's cycles on the way to a window" in `autopilot-actions.test.ts` and the older-cycles case of `AutopilotBoard.test.tsx`.
- **Bridge** (`resources/gui-bridge/modes/autopilot*.ts`): cycle ledger in the session journal, the `autopilot` tool, a static system section, and a `tool_call` guard: destructive git always blocked, no push/tag/publish for the agent, path checks, `eval`/`debug`/`ask` off the active tools. GitHub reads pass; `gh run download` too when its `-D` folder is inside the worktree or a scratch folder, so a failed release run's traces can be read.
- **Main** (`src/main/autopilot*.ts`): start, end/abort, children, approver, release detection, restart resume, `ShipRunner` (push/PR/merge/revert/land), and the post-cycle git audit (second defence, `autopilot-audit.ts`):
  - Symbolic refs such as `origin/HEAD` are not compared.
  - A ref is not the run's when a fetch moved a remote-tracking ref, another session pushed it, or it is a local branch checked out in another worktree, and it was created or moved forward holding none of the run's own commits (its branch's first-parent commits the remote default branch did not hold at the cycle's start), so pushing the run's unchanged branch is still caught.
  - Git failing to say counts as the run's; a deleted or rewound ref always counts. Pinned by `autopilot-audit*.test.ts`.
- **Renderer**: store `stores/autopilot.ts`; UI in `components/autopilot/`; pure rules in `autopilot-view.ts`; log Markdown in `src/shared/autopilot-log.ts` (the board's copy and the draft PR body).
  - **The run's home is the work board, never the side panel** (the user's rule): there is no `autopilot` panel view, no View options entry, and nothing opens by itself at a run's start.
  - In an Autopilot tab (`isAutopilotTab`, an ended run included) the board changes shape (`AutopilotBoard.tsx`, a lazy chunk so the phone's first screen stays in budget; `use-autopilot-state-text.ts` is the one small piece the strip and chip read). The head is named "Autopilot" with the run's state, active time and totals (`AutopilotBoardHead`: `data-autopilot-state`, `data-autopilot-reason`, `data-autopilot-totals`; branch ↑↓ and pace in the tooltips). The run's sections come ahead of the board's own (after a waiting question and a failed check):
  - `autopilot`: the cycle in flight (its item, or "Picking an item…" with its step), the cycle's child sessions, the red streak from two on, and where green cycles go (`ShipLandRow`: the one PR a protected branch asked for, or the shipping level; no line for a run that simply lands (the user's call); for an Automatic run also a release under way or the last release). Then one row of three controls (`AutopilotControls`, the user's layout: icon and name each, a third of the row; icons alone in the dock row and the Mode tab): Pause as a toggle (Resume while paused), **Ship, then stop**, and Stop now. There is no "End" control. The focus areas are one row of this section that opens `FocusChips` in place.
  - **Ship, then stop** (`stop_after_ship`): main notes the run's next `begin` to land its work and release when a release is due, then ends the run after the first cycle that began after the choice and shipped (`shipGap`: green, a commit, every queued push or land gone through; a land refused for a pull request counts). A cycle that did not ship leaves the choice on and the agent is told to repair it. A release run still going holds the end until it succeeds (`shipStopWaitsRelease`, read by `#checkRelease`); a failed one is owed (`releaseOwed`) and the run ends only after a later release succeeds. `AutopilotShipState.endAfterShip` lights the button; a second press cancels; a paused run resumes for it. In memory only, so a relaunch carries on running.
  - `cycles` (`AutopilotCycles.tsx`): the newest five, one line each, older ones behind "+N more"; a tap opens a cycle's commit, time, change, verify note, children and Revert in place (`data-board-expands`).
  - `followups` ("Left for later" / "남은 후속 작업", `AutopilotStatus.followups` from `openFollowups`): every follow-up the run's cycles left, however long ago (no window, so none is dropped silently), that no later cycle did or resolved. One line each, the sentence as tooltip and the cycle that last left it as `#N` (`followupCycles`, `openFollowupsLeft`); the first three and "+N more". ✕ (`data-autopilot-followup-dismiss`, action `followup_dismiss`, bridge `modes.autopilot_dismiss`) journals a `dismiss` event (`AUTOPILOT_DISMISS_ENTRY`, which keeps the removed backlog's entry name so older dismissals stay read) that closes it for the board and `begin` alike (`openFollowups`' `dismissed`, counted against the cycle that left it once that cycle ended); a cycle that lists it again reopens it, even one already running at the dismissal. Absent while there is none.
  - `ship` (`AutopilotShip.tsx`: push, PR, merge, release, automatic release, the queue), **only for a run whose start named a level** (the user's call): under Automatic shipping (`AutopilotShipPolicy.automatic`, set by main whatever it then decided: land, push of the run's branch without a known default branch, or nothing without a remote) nothing there is the person's to do.
  - **No backlog** (the user's call): a follow-up a cycle leaves is the agent's to take or close; an older journal's backlog events are ignored.
  - **no field for the next cycle's instruction and no auto-push switch** (the user's call): what the next cycle should do is typed into the tab's composer, as in any session (a steer while a turn runs); the push level is the start's. The `note` action stays for agents (`ompdesk_app autopilot.*`) and main's own notes.
  - No row of the board may widen it sideways (e.g. negative-margin rows make the docked board scroll).
  - An ended run keeps its head, reason and cycles, no controls.
  - The composer chip's button beside the Run chip, the dock row's and the Mode tab's "show the run" (`data-autopilot-chip-open`, `data-autopilot-open-screen`; `autopilot.chip.open`) call `revealWorkBoard(tabId)`: the pane's docked board unfolds the run's section and scrolls to it, else its strip expands (narrow window, split pane, side panel open, phone).
  - **A run is reachable in every layout**: the board has no close, so it is always docked or the strip.
  - Pinned by `WorkBoard.autopilot.test.tsx` (head, sections, controls, ended run, the three undockable layouts, reveal for another tab), `AutopilotBoard.test.tsx` (no shipping section for Automatic; no next-cycle field; follow-up rows and cap), `bridge-autopilot-core.test.ts` (which follow-ups the status names), `autopilot.test.ts` ("the ship level nobody chose"), `panel-auto-open.test.ts` (a start opens no panel), `ComposerModes.autopilot.test.tsx`, `GoalDockBar.autopilot.test.tsx`, `e2e/autopilot-cycles.e2e.ts`. Captures: `OMP_GUI_AUTOPILOT_BOARD_SHOTS=<dir>` with `e2e/autopilot-board-captures.e2e.ts` (dev harness; wide, narrow, split, side panel open, phone × light/dark × en/ko, before and after "show the run").
- An Autopilot tab's approval card is held back 3 s (`APPROVAL_GRACE_MS`; main's approver answers it).
- A usage-limit stop waits in main, never in a window (`#waitForQuota` in `src/main/autopilot.ts`), because a renderer booking cannot wake a run with no window open. The reset is the provider's first account to reset (`quotaResetAt` in `src/shared/quota-reset.ts`, the same rule the turn error card's booking uses; `QUOTA_FALLBACK_MS` 15 min when no report names one), journaled `waiting_quota` with `quotaResetAt` so every window, a paired device and a relaunch read it. The wake (`#armQuotaWake`) runs stock `retry`, or the restart resume after a relaunch, only if the run is still waiting.
- **A retry stock refuses is tried again**: the run goes back to `waiting_quota` with `quotaResetAt` set to the next try (30 s, doubling, never past 10 min; `QUOTA_RETRY_*`) until the retry takes or a turn is already running; no nudge is piled on it. Pinned by "a retry that fails after the wake" in `autopilot-branch.test.ts`. Windows are a view: the chip reads the state, `use-quota-resume.ts` never retries a live run's session and drops a stray booking, and the error card offers no booking on a run.
- Prefs: none (no remembered branch per repository). Shipping and notifications have no setting (`src/main/retired-prefs.ts` deletes the old prefs once); there is no `autopilotLimits` pref. A start nobody chose a level for ships Automatic (see Start sheet). A run notifies its stops, its end and release outcomes, never each cycle:
  - this computer's banner, under its own notifications switch (General › Notifications);
  - the paired device that started the run (its charge, `chargeRun`, even after it closed the run's view) and every device with a tab on the run's session, once each (`host.autopilotNotice`, `LocalHostServices.autopilotNotice`; shown on the tab of that session, else as a plain banner, under the device's own switch);
  - paired phones through Web Push (`WebPushNotifier.notice`, the categories each phone chose).
- **Ownership: a run belongs to the computer whose folder it works in, as a tab of that computer's window** (the user's decision).
  - A run a paired device starts on a host folder (`ompdesk_autopilot` with `device`, or the start sheet in a device session that runs on the host: the host answers with the run's session file and the device opens it, `use-autopilot-actions.ts`) is a tab of the host's front window, never a device tab or a hosted session (its summary names no `openFor`). It outlives the device closing its tab or going away, resumes from the host's own layout, and the host's person sees an ordinary tab.
  - The device shows it as a viewer tab of the host's run session (`viewForDevice`): closing it only leaves; status and stop go through it to the host's coordinator.
  - The run's replies and its children's count against that device's daily tokens until it ends (see control-tools › Schedules and Autopilot); the charge persists by worktree root in `<userData>/autopilot-device-runs.json`. A device tab viewing any session of a charged run, the run or a child (`attachRunLookup`: the session's owner tab → `runRootOf`), counts none of its replies, so nothing counts twice.
  - The sheet refuses only a folder that is no git repository: Plan mode or a Goal in the tab it starts from never blocks; the run is its own new tab. Details under OMPdesk control tools › Schedules and Autopilot.

### Branch choice and target
- **The start sheet shows only the folder's own branch** (the user's rule): the Branch row is one plain line, a branch glyph and the branch checked out in the folder (`AutopilotBranchInfo.current`, `readBranchInfo` in `src/main/autopilot-branches.ts`, re-read each time the sheet opens; no row while detached). No list, no other local or remote branch, no remembered or earlier run's name, no name field; the explanation is its (i). The sheet sends no `branch`, so every run from it works on a new `autopilot/<date>` cut from that branch (made free of clashes). `AutopilotBranchInfo.defaultBranch` is kept for an agent's start (`plan` in `agent-control/host.ts` asks before committing on it) and never shown.
- An agent's `ompdesk_autopilot` may still name a branch (`AutopilotStartOptions.branch`): `new` (`worktree_create` takes `branch: {name, mode: new|local|remote}` and never renames it) or `existing` (local, or only on the ship remote, checked out tracking `<remote>/<name>`), checked at the start against git's own branches (`readBranchEntries`).
- **A branch another worktree holds is never refused**: it is the run's **TARGET**. The run works on its own `autopilot/<date>` cut from the target (`branch: {name, mode: "new", from}`, `viaWorkBranch` in `src/shared/autopilot-branch.ts`), journaled as `target` (arm params, state entry, `AutopilotStatus.target`, survives restart); `ShipRunner` pushes `<sha>:refs/heads/<target>` (`ShipTarget.pushTo`), fast-forward only. The user's folder and working tree are never touched.
- **The default branch only when an agent names it**, and its start asks first whatever the switches say (see Schedules and Autopilot). A run committing on it is its own base (`baseBranch` = it, so a release's `HEAD:<default>` stays the one push the guard allows); Merge/PR refuse (`autopilot_on_base`).
- **A PR follows the push**: with a target, `ShipRunner.#pr` pushes the sha to the target (the only branch Autopilot ever pushes; the work branch never reaches the remote) and opens the PR from it. When that head is the base there is nothing to compare: Create PR is disabled with `autopilot.ship.prOnBase` and `set_autopilot ship pr` refuses with `autopilot_on_base` (Merge refuses only when the run's own branch is the base).
- Unchanged on any branch: the agent's pushes stay blocked (`ShipRunner` pushes `<sha>:refs/heads/<branch>`, never `+`); destructive git (force push, `reset`, branch delete/move, rewriting) stays banned in the guard; a non-fast-forward push is refused by git, never forced, and is a note to the agent, not a stop (`#tellAgent` → bridge `note`, handed over by the next `begin`: fetch, merge, never force; text `<remote>/<branch> has commits this run lacks (not a fast-forward); Autopilot never forces a push.`). The post-cycle audit judges the chosen branch (`AuditScope.branch`; the `autopilot/` prefix earns nothing). Run id = part after `autopilot/`, else the date.
- The choice persists in the journal as the arm's `branch` (`#adopt` reads `status.branch`). Rules are pure in `src/shared/autopilot-branch.ts`.
- Pinned by `src/shared/autopilot-branch.test.ts`, `autopilot-branches.test.ts` (the sheet gets only the folder's branch), `autopilot.test.ts` ("the branch a run is on", restart; a retired `autopilotBranch` value is never read), `autopilot-audit*.test.ts`, `autopilot-ship-push.test.ts` ("pr"), `bridge-autopilot-guard.test.ts`, `src/main/local/git/worktree.test.ts`, the Branch row tests in `ComposerModes.autopilot.test.tsx`, `AutopilotBoard.test.tsx`, and `e2e/autopilot-ship.e2e.ts` (a named existing branch moves on the remote, main does not; the sheet shows only `main`; the run pushes its own branch, never main).

### No soft stops
- **The run does not stop for soft reasons.** Red cycles, a failed check, a missing report, compaction churn, cycles without a commit, a rejected/unreachable push, a failed release run, plan mode, all todos blocked, a quiet turn, a model failing after TurnResume's retries are repaired by the next cycle.
  - `decideAfterCycle` only reports ceilings a start set.
  - `classifyStall` returns `nudge` (frame `autopilot_nudge`): main leaves plan mode and sends one follow-up "call `autopilot begin`" whose words name why the run went quiet (`NUDGE_MESSAGES` by reason: no progress, plan mode, every todo blocked (end with the blockers as follow-ups and pick another item), a failed turn; pinned by `autopilot-branch.test.ts`), at most every 20 s, 60 s after a failed turn. A nudge inside that window is never dropped: it is asked again when the window passes (a failed turn reports its failure once), so the run never sits silent while reading "running".
  - Every nudge runs from the run's cycle-end queue and checks right before it prompts (`#quietAndRunning`, again after leaving plan mode) that the run is still running and no turn, retry or connection wait holds it, so a queued nudge never resumes a run the user paused or stopped meanwhile.
  - A push's in-flight mark names no state (`setStatePatch` in `autopilot-core.ts`): the journal keeps its own, so a Pause given while a cycle's push runs stays. Pinned by `autopilot-cycle-end.test.ts`.
  - `AutopilotStatus.redStreak` is the counter: from two red in a row the timeline shows one muted line "연속 빨강 N"/"N red in a row" (`data-autopilot-red-streak`).
- Pauses left: the user's Pause/Stop/End and ■, `ban_violation` (destructive git, always), ceilings an agent's start set (`budget`/`time`/`cycles`/`cost`; none by default and none in the UI), `app_closed` (Continue interrupted work off), `repo_gone` (worktree or git dir vanished, confirmed: `probeRepo` says `gone` twice 1.5 s apart, a missing folder or git's own "not a git repository"; a git that does not answer, `unknown`, skips that cycle's audit and shipping and the next cycle end checks again). `agent_done` ends the run; a quota wait resumes itself at the reset.
- **Every step of a run's pipeline ends for real** (the owner's rule that nothing sits in front of agent work):
  - Cycle end, ship drain, nudge, stop, settle and quota wake run on one `SerialChain` per run (`Run.steps`; `#enqueue(run, work, name, maxMs)`; mechanism in machine-setup-updates › Serial queues never wait on a hung step (30 Oct 2026)).
  - Bounds: an ordinary step 15 min (`STEP_MAX_MS`), a cycle end 4 h (`CYCLE_END_MAX_MS`), the ship queue's drain 3 h (`SHIP_DRAIN_MAX_MS`; `ShipRunner` uses its own chain: the running item fails with "did not finish in …", shown on screen and in the agent's note, and the next drain starts; a stopped drain never writes its item again).
  - A stopped step is listed in `AutopilotStatus.stalls` (newest 5), shown as one muted line in the board's run section (`data-autopilot-stall`).
  - **A stopped step is fenced**: the coordinator's stock and bridge calls (`#stockResponse`, `#bridge`) and the points before a direct mutation (`#settled`, `#cycleEnd`'s audit and ship results, `#drain`) call `throwIfStepStalled()` before and after; a stopped `stop` step also clears `run.stopping`. Pinned by `autopilot-late-step.test.ts` (nudge, stop, settle, quota wake, cycle end).
  - A land check whose supervisor does not stop it 30 s after its timeout is killed and given up (`autopilot-land-check.ts`).
  - Pinned by "a step of the run's pipeline that never answers" in `autopilot-branch.test.ts`, `autopilot-ship-stall.test.ts`, "stops a check that outlives its timeout" in `autopilot-land-check.test.ts` and the stall row of `AutopilotBoard.test.tsx`.
- **The ship queue's chain is fenced to the step that awaits it** (see machine-setup-updates › Serial queues never wait on a hung step (30 Oct 2026)): this holds for `ShipRunner.drain` called from `#settled`, cycle end and `ship queue`; a stopped drain's running item fails. Pinned by `autopilot-late-step.test.ts` ("a settle that stalls while the ship queue drains").
- Defaults: fan-out is the agent's call (no cap and no setting, the owner's rule that nothing sits in front of agent work; the protocol says optional, `begin` hints: fan out only for multi-minute items; a stored `maxParallel` in an older run's journal is dropped when the run is armed again), shipping Automatic (see Start sheet), release cadence = agent decides, notifications = stops, end and releases, focus = all, remote = origin or the only remote.
- **A start waits for its new tab's omp with no deadline** (the owner's rule that no time limit ends or blocks work; `#ready` in `src/main/autopilot.ts`). The wait ends only when the tab's omp reads `ready`, fails (`error`) or exits; the pool releases the tab (`tabReleased`: "The Autopilot tab is gone."; `SidecarManager.dispose` drops the sidecar's listeners without a status, so the release is the signal); or the user's Stop arrives while the run is still `starting` (`#startWaits`: the start fails as stopped, nothing is armed). Each end removes the wait's status listener. The new tab's own status (`starting`, with the pool's `slow` state) is what the person sees; there is no extra screen for the wait. Pinned by `autopilot-start-wait.test.ts`.

### Start sheet
- `components/modes/AutopilotConfig.tsx`: visible are the full-access warning line and Start. Everything else sits in ONE closed `SettingsAdvanced` named "오토파일럿 옵션"/"Autopilot options" (`autopilot.sheet.options`; not "Advanced", because the Run popover's own "Advanced" sits below it): 내보내기/Shipping (Automatic / Commit / Push / Release; Automatic, the default, names what it will do: "lands every green cycle on the default branch of origin (a protected branch gets one pull request), and releases when the project releases" or "no remote: commits stay here"), 브랜치/Branch (one plain line: the folder's own branch, see Branch choice and target), focus areas.
  - **No guide box** (the user's decision): nobody sees or edits `AUTOPILOT.md` in the sheet; the app owns it (see Project guide).
  - The sheet sends only what the user chose: a Start on the closed sheet sends `{action: "start"}` and main decides the rest. Nothing in the popover changes layout on blur, Advanced included.
- **Automatic shipping = land** (`#start` in `src/main/autopilot.ts`, when the start names no level; the user's decision): with a remote and a known default branch the policy is `land: true` (`AutopilotShipPolicy.land`, `autoPush` off); without a known default branch the run's own branch is pushed; without a remote nothing.
  - Every **green** cycle **with a commit** (`#cycleEnd`, green by the verify rule: the turn's own tool calls show the check passed after the last edit) queues a `land` item pinned to that commit, with the command that made it green (`AutopilotCycleRecord.checkCommand`, `judgeVerify`'s `check`: the check the report names (`end.check`) when it passed after the last edit, else the last check after the last edit, exactly as it ran under the guard). A red cycle or one without a commit never lands.
  - `ShipRunner.#land` (`src/main/autopilot-ship.ts`): fetch `<remote>/<default>`, and push `<sha>:refs/heads/<default>` when the commit contains the remote tip (fast-forward, journaled first, URL pinned, never `+`, never the agent). The user's checkout is never written.
  - **Default branch moved** (so a busy main does not starve landing): `git merge-tree --write-tree` (no checkout touched) says whether a merge is clean. Clean, with a known check: the merge commit is built with `commit-tree` (the cycle's commit first parent, the fetched tip second), and **a clean textual merge is not a green one**, so the cycle's own check runs on exactly that commit before anything moves (`autopilot-land-check.ts` `checkLandCandidate`):
    - a detached `git worktree add` of the candidate in a temp folder with no hooks, `.worktreeinclude` and the setup hook as for every new worktree;
    - then HEAD `reset --soft` to the default branch's tip so the run's whole change is uncommitted, because a check of what changed against HEAD (like `check:changed`) would pass a clean checkout without checking anything;
    - the command in bash with pipefail (Git Bash on Windows) under the setup supervisor, in the environment a session's omp gets (`shellSpawnEnv`: the login shell's PATH and exports under the app's), because a Finder-launched app's own PATH is launchd's bare one; the run's worktree path in it points at the temp checkout; 30 min cap; the folder is removed every time.
    - Only that commit is pushed, as a fast-forward of the tip it merged; a default branch that moved again during the check or the push gets a new candidate, checked again, up to `LAND_ATTEMPTS` (3).
    - Landed as a merge: the run's branch is fast-forwarded to it only while its worktree still sits clean on the cycle's commit, else the agent is told to merge; either way one note says it landed.
  - A failed check (`LandOutcome` `red`), a conflict, a cycle without a known check, or a branch that kept moving lands nothing, and the next `begin` gets a note (`#landed`: "Not landed: … Run git fetch && git merge …, fix, run the check, commit; the next green cycle lands it", with what the check printed (`checkExcerpt`: its first error line and the 11 under it, then its end, within 2,000 characters, because the tail alone is only a list of failing files) or the conflicting files named). Main never merges into the worktree, because the next turn may already work in it. Never a stop.
  - A run on an existing branch ahead of the default branch lands its earlier commits with the cycle's (they are in the cycle's commit).
  - Pinned by `autopilot-ship-land*.test.ts` (moved main → checked candidate → landed; red candidate; moved again during check and push; diff-scoped check; worktree moved on; existing branch ahead), `autopilot-land-check.test.ts` (login-shell PATH tool runs under the bare PATH; first error kept) and `autopilot.test.ts`.
  - **Protected default branch** (the push refused for any reason other than moving on, the network or the account): the run's branch is pushed and ONE pull request opened into the default branch (`#landByPr`; an existing one, "already exists", is reused; once it is open a moved default branch goes to it too, unchecked, since the pull request is merged on the host); later lands update that branch. Said once: `AutopilotShipState.landing {via: "pr", url, reason}` (overlaid by main; ShipBox's `data-ship-land` line with an open button), one notification (`autopilot.land.prTitle`/`prBody`) and one note.
  - **Release** (cadence `agent`: the agent judges when, see Project guide) when the repository has a remote and a release procedure exists in the run's own checkout after Start committed its guide (`#releaseFor(made.path)`: a rules file's, else the guide's Release section, see `release-detect.ts`); the procedure runs on top of the landed default branch. A project whose guide says `Releases: no` only lands.
  - The agent's `begin.ship.land` says green cycles land. Main logs the guide's source and the decision (`autopilot: guide …; ship land on <branch>, release …`).
  - Kept: the guard (destructive git banned, agent pushes blocked), the post-cycle audit, and the sheet's Advanced levels (Commit / Push / Release) for a person who picks otherwise. An agent's `ompdesk_autopilot` start always names a level, so it never lands.
- **Every run leaves a summary** (`#summary`, `#reportStop`), so a stop reason survives a deleted session: when a run ends or pauses, one `gui-runtime.jsonl` line (source `autopilot`, message `ended` | `paused`; `details` {summary, run, root, branch, reason, detail, cycles, green, commits, landed + landTo + pr, or pushed}) and the same line as its notification body (`autopilot.summary`: "<branch>: N cycles (G green), C commits; L of C landed on main | pushed to … | kept on this computer. Stopped: <reason>"). Counts come from the journal and git (`merge-base --is-ancestor` of each cycle's commit against `<remote>/<default>`), so they hold after a relaunch. The user's own pause and stop (`SILENT_REASONS`) write the line but send no notification.
- **No caps or ceilings in the UI**: fan-out has no cap and no switch (`ompdesk_autopilot`'s `advanced` has no `parallel`), the release cadence is the agent's, the remote is detected, and ceilings exist only as `limits` an agent's start may set (`advanced.limits`).
- Settings has no Autopilot row.

### Permissions
- Held only while the run lives. Arm takes `ask`/`eval`/`debug` off, adds `autopilot`, holds `tools.approvalMode = yolo` as a runtime override on the session's settings (never written to config.yml), and journals what it took off plus which were `xd://` devices (`excludedTools`, `mountedTools`). Disarm clears the override and restores with stock `setActiveToolPresentation(names, mounted)`, because `getEnabledToolNames` also lists devices and `setActiveToolsByName` would bring a device taken off at arm (`debug`) back top level.
- Pinned by `src/main/bridge-autopilot-stock.test.ts` (tool presentation before arm = after disarm) and the real-omp yolo/tool-set test in `e2e/real-autopilot.e2e.ts` (while armed, after Stop, and across a SIGKILL relaunch where the run continues by itself, armed before it runs).

### Restart
- **The user's rule: a restart continues the run, always** (crash, SIGKILL, normal quit, omp restart). Only Settings › General › Continue interrupted work off leaves it paused `app_closed` with Resume.
- `#onReady` sees the journal say `running` and asks `TurnResume.relaunchContinuation`: with a launch marker the run waits for TurnResume's restore of the cut-off turn (`resumeGoal`; `goalSettled` `none` continues anyway, `cancelled` or the resuming row's Stop pauses); without one (kill between turns) it continues at once. A run `#start` is still arming is no restart. Every way that continuation ends must reach `goalSettled`, a call-off while it still waits offline included (Cancel, the resuming row's Stop, a new prompt, a session or branch move: `TurnResume.#dropWait` says `cancelled`), or Autopilot's `#awaitingResume` would wait for ever.
- Order: stock `goal pause`, arm with `resume`, `goal resume` (`#continueAfterRestart`). Why: stock's startup reconcile reattaches the goal paused and remembers the tool set of that moment (ask, eval, debug, no `autopilot`); its `goal resume` puts that set back and its `goal pause` restores and forgets it (`RpcGoalController` `#previousTools`). Without the pause the run loses its tool set until the next turn's `ensureTools` and every later pause gives the startup set back.
- A killed/quitting OMPdesk closes omp's stdin and stock journals the cut turn aborted, with or without a `session_exit`, so `goalPausedByExit` must not need one (see Interrupted work, quit and diagnostics).
- Pinned by `autopilot.test.ts` (restart), `bridge-autopilot-stock.test.ts` (third test: stdin EOF mid-turn on the real omp), `e2e/autopilot-restart.e2e.ts` (kill mid-cycle, normal quit, kill between turns, setting off), and the real-omp yolo/tool-set test.

### Project guide (`AUTOPILOT.md`)
- At a repo's root (`AUTOPILOT_GUIDE_*`, `AutopilotGuideParams` and `AutopilotEnsuredGuide` in `autopilot-contracts.ts`; rules in `modes/autopilot-guide.ts`, `modes/autopilot-release-core.ts` (pure), `modes/autopilot-release-facts.ts` (reads) + `boundGuide` in `autopilot-core.ts`): project-wide direction shared across sessions and computers (roadmap, area priorities, no-touch paths, done criteria, taste, release, ideas). OMPdesk's own is `AUTOPILOT.md` at this repo's root. It is **not** the run's follow-ups or notes (those stay in the session journal and return through `begin`); nothing ever writes them into it.
- Every `autopilot begin` reads it from the worktree root (`state.root`) and returns `begin.guide` (≤ 8 KB, `AUTOPILOT_GUIDE_MAX_BYTES`, cut on a character boundary with a marker; absent/blank leaves the field out), so an edit applies from the next cycle. The static system section stays byte-identical (says the guide exists, ranks below the rules files, never lifts the HARD LIMITS): rules files (AGENTS.md etc.) win over the guide.
- **The app owns it** (the user's decision): no one sees or edits it in the start sheet.
  - At Start, while the worktree is made, main asks the bridge `modes.autopilot_guide {root, procedure, text?}` (`#guideToCommit`, `GUIDE_MS` 45 s; `procedure` = the folder's rules-file procedure, `text` = an agent's `ompdesk_autopilot` guide) and `#commitGuide` writes the answer into the new worktree and commits it (`--no-verify`, no signing) as the branch's first commit when the file differs, so it never touches the user's current branch and reaches main only on merge.
  - `ensureGuide`: an existing guide (the agent's `text`, else the checkout's file) is kept byte for byte and only gets the facts' `## Release` section when it has none (no model request); never rewritten otherwise; one past `AUTOPILOT_GUIDE_COMMIT_MAX_BYTES` (256 KB) is left alone.
  - A repo without one gets one built: ONE `completeOnSmol` request (`next-prompt-engine.ts`: stock's `smol` role via `resolveRoleChain`, never the main model, usage in stock's ledger as `autopilot-guide-draft`) over a bounded prompt (rules-file excerpts, README, recent commit subjects, test/build commands) writes the other sections, then the facts' Release section goes in (replacing any the model wrote); on any failure the deterministic `templateGuide`.
  - A bridge that cannot answer means no guide commit; the run starts anyway.
- **Release facts** (`collectReleaseFacts`, read-only, no model, every read bounded, git and gh with a 10 s timeout): release/publish/deploy workflows in `.github/workflows` (triggers: a push to the default branch and its `paths`, a pushed tag, a published GitHub release, manual dispatch; what they publish (npm, crates.io, PyPI, electron-builder, GitHub release, goreleaser, …) or deploy (GitHub Pages, Vercel, Netlify, Cloudflare, Fly.io, Firebase); the secrets they read, `GITHUB_TOKEN` left out), version manifests (`package.json`, `Cargo.toml`, `pyproject.toml`, `go.mod`), local publish scripts (`package.json` scripts, `Makefile`, goreleaser), the changelog's shape (keep-a-changelog, versioned, unversioned), version tags (count, last 90 days, median gap of the latest 10, the latest tag's commit subject), GitHub releases (`gh release list`, only for a github.com remote), hosting configs whose Git integration deploys a push (`vercel.json`, `netlify.toml`, …), conventional commits (a majority of the last 30 subjects).
- **Verdict** (`releaseVerdict`): a rules-file procedure first (the section points there and adds only the cadence); else a publishing workflow (packaging alone, an electron-builder CI build, publishes nothing); else a deploy workflow or hosting config (a release is a fast-forward push of the default branch); else tags, GitHub releases or a publish script (push the release commit and a version tag; a local publish command stays the maintainer's); else **no release**.
  - The `## Release` section starts with one marker line, `Releases: yes` or `Releases: no`, and is **always `releaseSectionTemplate` over the facts, never a model's**, because the agent runs it as written and a model's procedure can get the order wrong (e.g. pushing a tag that makes the publish workflow skip).
  - A `yes` section has a numbered Procedure: version bump rule from the commit kinds; where the version lives (manifests with a version, and the files a publishing workflow's push `paths` must change); changelog section in its own shape; checks first; one release commit touching only those files and the changelog in the last release's message style; the exact push/tag/workflow; watch the run; a failed run is reported and fixed in the next cycle, never forced.
  - And a Cadence: the history line, the newest of local tags and GitHub releases, then: release when user-visible fixes or features have gathered at about that rhythm, a breaking defect at once.
  - Both stay within what the guard lets a release do: push `HEAD:<default>` fast-forward and version tags, `gh workflow run`, watch runs; never a publish command or `gh release create` (CI publishes).
- **Release detection reads it**: `detectReleaseProcedure` (`src/main/release-detect.ts`) takes a rules file's (AGENTS.md, CLAUDE.md, CONTRIBUTING.md), then `RELEASING.md`/`docs/release*.md`, then AUTOPILOT.md's Release section (`guideRelease`: a heading named Release/Releasing/Release procedure/릴리스/배포, never "Release cadence"; a section without a marker is a person's own procedure and counts) unless it says `Releases: no`. So a run started with the app's guide can release under Automatic shipping, and the agent's `begin.ship.releaseProcedure` names `AUTOPILOT.md › Release`.
  - WHEN to release is decided by the content, never the clock (the user's call; `propose_release`, cadence `agent`; `releaseReadiness` in `autopilot-core.ts`). The bridge reads what landed on the release target, never the run's own HEAD (`unreleasedOnTarget` in `autopilot-release-facts.ts`: `<ship remote>/<base branch>` fetched with its tags, the commits after the newest `v*` tag reachable from it; an unlanded run has nothing to release there, and a release made from another checkout is a tag on the remote, so its commits do not count again; pinned on real repos by `bridge-autopilot-release.test.ts`).
  - It answers due for `RELEASE_BATCH` (3) user-visible commits (`feat`/`fix`/`perf` or a breaking `!`; every commit counts in a repository without conventional commits), for one the agent calls `urgent` (with why), or for one that has waited `RELEASE_WAIT_CEILING_MS` (a day); docs, tests, refactors and CI alone never are. The answer lists the user-visible subjects (newest 20) and counts the rest; a release not due opens no release scope.
  - A user's own release request (`ship`) is never held.
- Pinned by `bridge-autopilot-guide.test.ts` (kept byte for byte, missing Release section added with no model request, a model's Release section replaced, agent's text first, too-large guide left alone), `bridge-autopilot-release.test.ts` (facts on real temp repos: npm package with tag publish, Electron app publishing on a version push, no releases, Pages and Vercel sites; `on:`-only trigger parsing, CI build publishes nothing, push `paths` as the version file, newest release in the cadence; marker and replacement), `release-detect.test.ts` (AUTOPILOT.md's Release section, `Releases: no`, a rules file wins), `autopilot.test.ts` (Start's guide request and commit, no guide call from the sheet), the sheet tests in `ComposerModes.autopilot.test.tsx`, the guide test of `e2e/autopilot-cycles.e2e.ts` (no guide box; the template guide with `Releases: no` is the branch's first commit and `begin` reads it) and the opt-in guide test of `e2e/real-autopilot.e2e.ts`.

### Cycle reports are checked, not trusted
- Why: agents' reports can miss the commit hash or repeat `end`. Pure rules in `modes/autopilot-verify.ts` (pinned by `bridge-autopilot-verify.test.ts`), wiring in `autopilot.ts`.
- **The first `end` of a turn stands**: a repeat only adds follow-ups, children, ship, commit; `shouldSteerStop` sends no stop steer once reported. Only a refused report is replaced by a second `end`.
- `observeReport` takes the commit from git (a claimed hash not in the branch history is dropped; no repo, the claim stands) and measures `change` (`AutopilotChangeStat`: files, +/−, commits, `docOnly`).
- **`end` waits for the calls beside it** (`settledBeside`), because stock runs a message's tool calls side by side and an `end` could read HEAD and the ledger before its commit or check finished. It first waits for stock's event stream to report its own start (up to 2 s; the stream lags the call, and a call listed after `end` starts after it), then until every other call of its own assistant message (stock's message list) has ended and no other call of the cycle runs (up to 5 min, `OMP_GUI_TEST_AUTOPILOT_SIBLING_WAIT_MS` in tests). A call still running then records nothing and answers `recorded: false` with the running tools, so the agent waits and calls `end` again. Pinned by "takes the commit a call beside `end` made", "takes the commit of a call listed after `end`" and "records nothing while a call beside `end` still runs" in `bridge-autopilot-stock.test.ts` (installed omp).
- **A green claim needs the turn's own tool calls to show it** (ledger of `tool_execution_*`: a check-like `bash` command, or the one named in `end.check`, that did not fail and ran after the last `edit`/`write`/`ast_edit`).
  - How each `bash` call ended is the work card's own rule (`commandStatus`, `resources/gui-bridge/command-verdict-core.ts`, read in `ledgerCall`): a check stock or the shared-checkout guard refused is no check run; a check whose own output shows failure under exit 0 failed; a backgrounded one is no failure (its result never reaches the ledger); one the user's stop cut off while `end` waited (the tool's abort signal, `LiveState.stoppedAt`, `statusAfterStop`) is no check run, as the card reads it interrupted.
  - Otherwise `verify` becomes `skipped` or `red` with `verifyNote` (`no_check` | `check_failed` | `edited_after`; timeline in en/ko and Markdown log); the `end` result tells the agent, which may run the check and `end` again.
  - A cycle with a commit and no green counts red: neither pushed nor ignored. Release cycles are exempt.
- A `pick` op names the item after the audit (`now.title`; before it `now.area` is unset and the screen says "Picking an item…", never the rotation's guess) and refuses a repeat of a recent title before the work.
- **A cycle is a batch** (the user's call): the static protocol's PICK step takes the highest-value item plus every other independent item (different files, none waiting on another) the cycle can finish and verify, worked side by side (the task tool's subagents in the worktree for small ones, child sessions for multi-minute ones), one commit per item, the batch named in one `pick`/`end` title joined by " · ". `beginHints`' cost hint points small items at subagents instead of child sessions (`bridge-autopilot-verify.test.ts`).
- `begin` carries `pick` and `hints`: a follow-up open ≥ 3 cycles asks for a decision (do it, or close it in `end.resolved` with why), counted from the cycle that left it whether or not later cycles list it again (`followupAge`); a docs-only last cycle; fan-out cost ("fan out only for items of several minutes", because small fan-outs cost about twice as much). All dynamic guidance rides in `begin`; the static section is unchanged.
- **A follow-up closes when a cycle says it did it**, so finished follow-ups do not keep sending the agent back. `openFollowups` drops a follow-up a later cycle's title names exactly or lists under `end.resolved` (begin's exact text, case, punctuation and spacing ignored; the tool schema and the defect hint say so; a repeated `end` merges it). A cycle that lists it again in its own `followups` reopens it. Pinned by `bridge-autopilot-core.test.ts` ("resolves a follow-up").
  - Because a title almost never repeats a follow-up's sentence, `pick` and `end` name the open follow-ups the cycle looks like it covers (`followupsLikeCycle`: at least 2 of the follow-up's words of two or more letters, and 40 % of them, appear in the title and summary; one the report already resolved is left out) and ask for their exact text in `resolved` (a repeated `end` merges it). Only a hint, in the tool results; the static section is unchanged. Pinned by `bridge-autopilot-core.test.ts` ("followupsLikeCycle").
- **Bugs before polish**: `BEGIN_PICK` ranks a known bug or failing behaviour first, docs and polish last, and says a fixable bug is never a limitation; `beginHints` names up to two open follow-ups whose words mark a defect (`DEFECT`); `pick` refuses a docs item right after a docs-only cycle unless it carries `reason` (`docsPickRefusal`); `end` answers a report that writes a problem off with no follow-up with `writeOff` (`writeOffNote`), and the repeated `end` merges the follow-up. Pure in `autopilot-core.ts`, pinned by `bridge-autopilot-verify.test.ts`.
- **The run's session title** (`runSessionTitle`, `#retitle` in `src/main/autopilot.ts`): stock `set_session_name` "<repo folder>" once the tab is ready, then the item of the cycle at work, renamed as each cycle's `pick` (or, for a cycle that picked nothing, its record) names it, only while the name is still the run's own (`get_state.sessionName`; renames go one after another, `Run.titling`). No "Autopilot" word in it (the user's call): the row's rocket mark, the title bar and the pane header say it is a run. A relaunch's run takes the naming over only when the name is still one a run gives (its folder, a cycle's item, an earlier build's "Autopilot · …") or none (`runOwnsTitle`); a typed one stays. Stock answers an RPC rename without `session_info_update`, so `SidecarPool.noteSessionName` tells the tab entry and the windows. Pinned by `autopilot.test.ts` ("titles the run's session") and the two title cases of `autopilot-restart-resume.test.ts` (restart).
- The run's board sections have no empty-state sentences: the run, the cycles and the follow-ups show only their rows, and the cycles section waits for the first cycle (`AutopilotBoard.test.tsx` "one-line rows").
