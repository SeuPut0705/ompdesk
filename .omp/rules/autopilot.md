## Autopilot

### Overview
- UI **Autopilot** (ko "오토파일럿"; code id `autopilot`; Mode popover tab beside Plan and Goal): an endless development run in its own new git worktree tab, built on **stock Goal continuation** (`goal.continuationModes ∋ rpc`), no scheduler of its own. States `running | stopping | paused(reason) | waiting_quota | ended`; "End" = stock `goal pause` (turn in progress finishes) then drop; "Stop now" = `abort`.
- Contracts (journal entries, states, settings, `AutopilotStatus` carried by `get_autopilot` and the `autopilot_update` frame (whole on every update to every window and paired device, with only the newest `STATUS_CYCLES` (30) cycles and `cycleCount` once there are more: main's overlay and its `get_autopilot`/`set_autopilot` answers cut it with `withRecentCycles`, since 446 cycles made every frame 505 KB (23 Oct 2026); the board's "+N more" and the log copy read every cycle with `get_autopilot {allCycles: true}`, read ahead on hover or focus of the copy button, and a copy whose cycles are still being read starts its write inside the click with a `ClipboardItem` holding the text (`copyTextWhenRead` in `lib/format.ts`; WebKit allows a write only inside the gesture, so a phone's first tap failed), and main keeps the bridge's whole list (`run.status`) for reverts, the PR body and the run summary; pinned by "a long run's cycles on the way to a window" in `autopilot-actions.test.ts` and the older-cycles case of `AutopilotBoard.test.tsx`; rebuilt whole on a device that took it as a delta over the link (Remote devices, `slimAutopilot`), so its cycles leave out `checkCommand` and `resolved`, which only main's cycle-end frame and `begin`'s journal read, and carry each summary as the Markdown log clips it, one line of at most 400 characters, `clipCycleSummary`), `set_autopilot`'s `AutopilotAction`, `AUTOPILOT_BRIDGE_METHODS`) live in the dependency-free `resources/gui-bridge/modes/autopilot-contracts.ts`.
- **Bridge** (`resources/gui-bridge/modes/autopilot*.ts`): cycle ledger in the session journal, the `autopilot` tool, a static system section, and a `tool_call` guard (destructive git always blocked, no push/tag/publish for the agent, path checks, `eval`/`debug`/`ask` off the active tools; GitHub reads pass, `gh run download` too when its `-D` folder is inside the worktree or a scratch folder, so a failed release run's traces can be read).
- **Main** (`src/main/autopilot*.ts`): start, end/abort, children, approver, post-cycle git audit (second defence, `autopilot-audit.ts`: symbolic refs such as `origin/HEAD` are not compared; a remote-tracking ref a fetch moved is not the run's, nor one another session pushed, nor a local branch checked out in another worktree (another session's, or the user's own checkout pulled forward): created or moved forward holding none of the run's own commits, i.e. its branch's first-parent commits the remote default branch did not hold at the cycle's start, so pushing the run's unchanged branch is still caught; git failing to say counts as the run's; a deleted or rewound ref always counts; pinned by `autopilot-audit*.test.ts`), `ShipRunner` (push/PR/merge/revert/land), release detection, restart resume.
- **Renderer**: store `stores/autopilot.ts`; UI in `components/autopilot/`; pure rules in `autopilot-view.ts`; log Markdown in `src/shared/autopilot-log.ts` (the board's copy and the draft PR body). **The run's home is the work board, never the side panel** (the user's rule, 21 Oct 2026: opening a panel is harder than glancing at the board; there is no `autopilot` panel view, no View options entry and nothing opens by itself at a run's start). ### Branch choice and target
- **The start sheet shows only the folder's own branch** (the user's rule, 21 Oct 2026, from a report that the list held names that were not the project's): the Branch row is one plain line, a branch glyph and the branch checked out in the folder (`AutopilotBranchInfo.current`, `readBranchInfo` in `src/main/autopilot-branches.ts`, re-read each time the sheet opens; no row while detached). No list, no other local or remote branch, no remembered or earlier run's name, no name field; the explanation is its (i). The sheet sends no `branch`, so every run from it works on a new `autopilot/<date>` cut from that branch (made free of clashes). `AutopilotBranchInfo.defaultBranch` is kept for an agent's start (`plan` in `agent-control/host.ts` asks before committing on it) and never shown.
- An agent's `ompdesk_autopilot` may still name a branch (`AutopilotStartOptions.branch`): `new` (`worktree_create` takes `branch: {name, mode: new|local|remote}` and never renames it) or `existing` (local, or only on the ship remote, checked out tracking `<remote>/<name>`), checked at the start against git's own branches (`readBranchEntries`).
- **A branch another worktree holds is never refused**: it is the run's **TARGET**. The run works on its own `autopilot/<date>` cut from the target (`branch: {name, mode: "new", from}`, `viaWorkBranch` in `src/shared/autopilot-branch.ts`), journaled as `target` (arm params, state entry, `AutopilotStatus.target`, survives restart); `ShipRunner` pushes `<sha>:refs/heads/<target>` (`ShipTarget.pushTo`), fast-forward only. The user's folder and working tree are never touched.
- **The default branch only when an agent names it**, and its start asks first whatever the switches say (see Schedules and Autopilot). A run committing on it is its own base (`baseBranch` = it, so a release's `HEAD:<default>` stays the one push the guard allows); Merge/PR refuse (`autopilot_on_base`).
- **A PR follows the push**: with a target, `ShipRunner.#pr` pushes the sha to the target (the only branch Autopilot ever pushes; the work branch never reaches the remote) and opens the PR from it. When that head is the base there is nothing to compare: Create PR is disabled with `autopilot.ship.prOnBase` and `set_autopilot ship pr` refuses with `autopilot_on_base` (Merge refuses only when the run's own branch is the base).
- Unchanged on any branch: the agent's pushes stay blocked (`ShipRunner` pushes `<sha>:refs/heads/<branch>`, never `+`); destructive git (force push, `reset`, branch delete/move, rewriting) stays banned in the guard; a non-fast-forward push is refused by git, never forced, and is a note to the agent (`#tellAgent` → bridge `note`, handed over by the next `begin`: fetch, merge, never force; text `<remote>/<branch> has commits this run lacks (not a fast-forward); Autopilot never forces a push.`), not a stop. The post-cycle audit judges the chosen branch (`AuditScope.branch`; the `autopilot/` prefix earns nothing). Run id = part after `autopilot/`, else the date.
- The choice persists in the journal as the arm's `branch` (`#adopt` reads `status.branch`). Rules are pure in `src/shared/autopilot-branch.ts`.
- Pinned by `src/shared/autopilot-branch.test.ts`, `autopilot-branches.test.ts` (the sheet gets the folder's branch and no other local, remote or earlier run's name), `autopilot.test.ts` ("the branch a run is on", restart; a retired `autopilotBranch` value is never read), `autopilot-audit*.test.ts`, `autopilot-ship-push.test.ts` ("pr"), `bridge-autopilot-guard.test.ts`, `src/main/local/git/worktree.test.ts`, the Branch row tests in `ComposerModes.autopilot.test.tsx`, `AutopilotBoard.test.tsx`, and `e2e/autopilot-ship.e2e.ts` (an existing branch an agent names moves on the remote, main does not; the sheet shows only `main` with other local, remote and earlier run's branches present, and the run pushes its own branch, never main).

### No soft stops
- **The run does not stop for soft reasons.** Red cycles, a failed check, a missing report, compaction churn, cycles without a commit, a rejected/unreachable push, a failed release run, plan mode, all todos blocked, a quiet turn, a model failing after TurnResume's retries are repaired by the next cycle. `decideAfterCycle` only reports ceilings a start set; `classifyStall` returns `nudge` (frame `autopilot_nudge`: main leaves plan mode and sends one follow-up "call `autopilot begin`" whose words name why the run went quiet (`NUDGE_MESSAGES` by reason: no progress, plan mode, every todo blocked (end with the blockers as follow-ups and pick another item), a failed turn; pinned by `autopilot-branch.test.ts`), at most every 20 s, 60 s after a failed turn). A nudge inside that window is never dropped: it is asked again when the window passes (a failed turn reports its failure once; a dropped nudge left the run silent while it read "running"). A push's in-flight mark names no state (`setStatePatch` in `autopilot-core.ts`): the journal keeps its own, so a Pause given while a cycle's push runs stays (main once wrote its last read, `running`, back over it and the run went on; pinned by `autopilot-cycle-end.test.ts`). Every nudge runs from the run's cycle-end queue and checks right before it prompts (`#quietAndRunning`, again after leaving plan mode) that the run is still running and no turn, retry or connection wait holds it, so one queued behind a slow push never resumes a run the user paused or stopped meanwhile. `AutopilotStatus.redStreak` is the counter: from two red in a row the timeline shows one muted line "연속 빨강 N"/"N red in a row" (`data-autopilot-red-streak`).
- Pauses left: the user's Pause/Stop/End and ■, `ban_violation` (destructive git, always), ceilings an agent's start set (`budget`/`time`/`cycles`/`cost`; none by default and none in the UI), `app_closed` (Continue interrupted work off), `repo_gone` (worktree or git dir vanished, confirmed: `probeRepo` says `gone` twice 1.5 s apart, a missing folder or git's own "not a git repository"; a git that does not answer, `unknown`, skips that cycle's audit and shipping and the next cycle end checks again). `agent_done` ends the run; a quota wait resumes itself at the reset.
- Defaults: fan-out is the agent's call (no cap and no setting: `maxParallel` was removed 30 Oct 2026, the owner's rule that nothing sits in front of agent work; the protocol says optional, `begin` hints: fan out only for multi-minute items; a stored value in an older run's journal is dropped when the run is armed again), shipping Automatic (see Start sheet), release cadence = agent decides, notifications = stops, end and releases, focus = all, remote = origin or the only remote.

### Start sheet
- `components/modes/AutopilotConfig.tsx`: visible are the full-access warning line and Start. Everything else sits in ONE closed `SettingsAdvanced` named "오토파일럿 옵션"/"Autopilot options" (`autopilot.sheet.options`; the Run popover's own "Advanced" sits below it, and two identical "Advanced" rows read as one control twice): 내보내기/Shipping (Automatic / Commit / Push / Release; Automatic, the default, names what it will do: "lands every green cycle on the default branch of origin (a protected branch gets one pull request), and releases when the project releases" or "no remote: commits stay here"), 브랜치/Branch (one plain line: the folder's own branch, see Branch choice and target), focus areas. **No guide box** (the user's decision, 21 Oct 2026): nobody sees or edits `AUTOPILOT.md` in the sheet, the app owns it (see Project guide). The sheet sends only what the user chose: a Start on the closed sheet sends `{action: "start"}` and main decides the rest. Nothing in the popover changes layout on blur, Advanced included.
- **Automatic shipping = land** (`#start` in `src/main/autopilot.ts`, when the start names no level; the user's decision, 21 Oct 2026): with a remote and a known default branch the policy is `land: true` (`AutopilotShipPolicy.land`, `autoPush` off; without a known default branch the run's own branch is pushed; without a remote nothing). Every **green** cycle **with a commit** (`#cycleEnd`: the existing verify rule, green only when the turn's own tool calls show the check passed after the last edit) queues a `land` item pinned to that commit, with the command that made it green (`AutopilotCycleRecord.checkCommand`, `judgeVerify`'s `check`: the check the report names (`end.check`) when it passed after the last edit, else the last check after the last edit, exactly as it ran under the guard; a narrower run after the repo's check, a few e2e specs, was what a land re-ran until 21 Oct 2026); a red cycle or one without a commit never lands. `ShipRunner.#land` (`src/main/autopilot-ship.ts`): fetch `<remote>/<default>`, and push `<sha>:refs/heads/<default>` when the commit contains the remote tip (fast-forward, journaled first, URL pinned, never `+`, never the agent). The user's checkout is never written. **Default branch moved** (21 Oct 2026: a real run had 6 green cycles and landed none, because main took ~12 commits an hour from other sessions and the agent's own merge always lost the race): `git merge-tree --write-tree` (no checkout touched) says whether a merge is clean. Clean, with a known check: the merge commit is built with `commit-tree` (the cycle's commit first parent, the fetched tip second), and **a clean textual merge is not a green one**, so the cycle's own check runs on exactly that commit before anything moves (`autopilot-land-check.ts` `checkLandCandidate`: a detached `git worktree add` of the candidate in a temp folder with no hooks, `.worktreeinclude` and the setup hook as for every new worktree, then HEAD `reset --soft` to the default branch's tip so the run's whole change is uncommitted (a check of what changed against HEAD, like `check:changed`, passes a clean checkout of the candidate in 1 s without checking anything), the command in bash with pipefail (Git Bash on Windows) under the setup supervisor, in the environment a session's omp gets (`shellSpawnEnv`: the login shell's PATH and exports under the app's; a Finder-launched app's own PATH is launchd's bare one, where a cycle's `bun run check:changed` was "command not found" and nothing landed over a moved main), the run's worktree path in it pointing at the temp checkout, 30 min cap; the folder is removed every time). Only that commit is pushed, as a fast-forward of the tip it merged; a default branch that moved again during the check or the push gets a new candidate, checked again, up to `LAND_ATTEMPTS` (3). Measured on this repo (21 Oct 2026, warm bun cache): worktree add 0 s, setup hook 2 s, `check:changed --no-e2e` over a 12-commit, 333-file change 57 s. Landed as a merge: the run's branch is fast-forwarded to it only while its worktree still sits clean on the cycle's commit, else the agent is told to merge; either way one note says it landed. A failed check (`LandOutcome` `red`), a conflict, a cycle without a known check, or a branch that kept moving lands nothing and the next `begin` gets a note (`#landed`: "Not landed: … Run git fetch && git merge …, fix, run the check, commit; the next green cycle lands it", what the check printed (`checkExcerpt`: its first error line and the 11 under it, then its end, within 2,000 characters; vitest lists every failing file after their shared error and the tail alone was only that list) or the conflicting files named): main never merges into the worktree, because the next turn may already work in it. A run on an existing branch ahead of the default branch lands its earlier commits with the cycle's (they are in the cycle's commit). Never a stop. Pinned by `autopilot-ship-land*.test.ts` (moved main → checked candidate → landed; red candidate; moved again during the check and during the push; a diff-scoped check; a worktree that moved on; an existing branch ahead), `autopilot-land-check.test.ts` (a tool only on the login shell's PATH runs under the app's bare PATH; the first error of a long failing output is kept) and `autopilot.test.ts`. **Protected default branch** (the push refused for any reason other than moving on, the network or the account): the run's branch is pushed and ONE pull request opened into the default branch (`#landByPr`; an existing one, "already exists", is reused; once it is open a moved default branch goes to it too, unchecked, since the pull request is merged on the host); later lands update that branch. Said once: `AutopilotShipState.landing {via: "pr", url, reason}` (overlaid by main; ShipBox's `data-ship-land` line with an open button), one notification (`autopilot.land.prTitle`/`prBody`) and one note. **Release** (cadence `agent`: the agent judges when, see Project guide) when the repository has a remote and a release procedure exists in the run's own checkout after Start committed its guide (`#releaseFor(made.path)`: a rules file's, else the guide's Release section, see `release-detect.ts`); the procedure runs on top of the landed default branch. A project whose guide says `Releases: no` only lands. The agent's `begin.ship.land` says green cycles land. Main logs the guide's source and the decision (`autopilot: guide …; ship land on <branch>, release …`). Kept: the guard (destructive git banned, agent pushes blocked), the post-cycle audit, and the sheet's Advanced levels (Commit / Push / Release) for a person who picks otherwise; an agent's `ompdesk_autopilot` start always names a level, so it never lands.
- **Every run leaves a summary** (`#summary`, `#reportStop`; the user's report, 21 Oct 2026: a run's session was deleted and its stop reason went with it): when a run ends or pauses, one `gui-runtime.jsonl` line (source `autopilot`, message `ended` | `paused`; `details` {summary, run, root, branch, reason, detail, cycles, green, commits, landed + landTo + pr, or pushed}) and the same line as its notification body (`autopilot.summary`: "<branch>: N cycles (G green), C commits; L of C landed on main | pushed to … | kept on this computer. ### Permissions
- Held only while the run lives. Arm takes `ask`/`eval`/`debug` off, adds `autopilot`, holds `tools.approvalMode = yolo` as a runtime override on the session's settings (never written to config.yml), and journals what it took off plus which were `xd://` devices (`excludedTools`, `mountedTools`). ### Restart
- **The user's rule: a restart continues the run, always** (crash, SIGKILL, normal quit, omp restart). Only Settings › General › Continue interrupted work off leaves it paused `app_closed` with Resume.
- `#onReady` sees the journal say `running` and asks `TurnResume.relaunchContinuation`: with a launch marker the run waits for TurnResume's restore of the cut-off turn (`resumeGoal`; `goalSettled` `none` continues anyway, `cancelled` or the resuming row's Stop pauses); without one (kill between turns) it continues at once. A run `#start` is still arming is no restart. Every way that continuation ends reaches `goalSettled`, a call-off while it still waits offline included (Cancel, the resuming row's Stop, a new prompt, a session or branch move: `TurnResume.#dropWait` says `cancelled`, 29 Oct 2026), or Autopilot's `#awaitingResume` would wait for ever.
- Order: stock `goal pause`, arm with `resume`, `goal resume` (`#continueAfterRestart`). Why: stock's startup reconcile reattaches the goal paused and remembers the tool set of that moment (ask, eval, debug, no `autopilot`); its `goal resume` puts that set back and its `goal pause` restores and forgets it (`RpcGoalController` `#previousTools`). Without the pause the run lost its tool set until the next turn's `ensureTools` and every later pause gave the startup set back.
- On omp 18.11.3 a killed/quitting OMPdesk closes omp's stdin and stock journals the cut turn aborted, with a `session_exit` (real SIGKILL) or without (stock test), so `goalPausedByExit` must not need one (see Interrupted work, quit and diagnostics).
- Pinned by `autopilot.test.ts` (restart), `bridge-autopilot-stock.test.ts` (third test: stdin EOF mid-turn on the real omp), `e2e/autopilot-restart.e2e.ts` (kill mid-cycle, normal quit, kill between turns, setting off), and the real-omp yolo/tool-set test.

### Project guide (`AUTOPILOT.md`)
- At a repo's root (`AUTOPILOT_GUIDE_*`, `AutopilotGuideParams` and `AutopilotEnsuredGuide` in `autopilot-contracts.ts`; rules in `modes/autopilot-guide.ts`, `modes/autopilot-release-core.ts` (pure), `modes/autopilot-release-facts.ts` (reads) + `boundGuide` in `autopilot-core.ts`): project-wide direction shared across sessions and computers (roadmap, area priorities, no-touch paths, done criteria, taste, release, ideas). OMPdesk's own is `AUTOPILOT.md` at this repo's root. It is **not** the run's follow-ups or notes (those stay in the session journal and return through `begin`); nothing ever writes them into it.
- Every `autopilot begin` reads it from the worktree root (`state.root`) and returns `begin.guide` (≤ 8 KB, `AUTOPILOT_GUIDE_MAX_BYTES`, cut on a character boundary with a marker; absent/blank leaves the field out), so an edit applies from the next cycle. The static system section stays byte-identical (says the guide exists, ranks below the rules files, never lifts the HARD LIMITS): rules files (AGENTS.md etc.) win over the guide.
- **The app owns it** (the user's decision, 21 Oct 2026): no one sees or edits it in the start sheet. At Start, while the worktree is made, main asks the bridge `modes.autopilot_guide {root, procedure, text?}` (`#guideToCommit`, `GUIDE_MS` 45 s; `procedure` = the folder's rules-file procedure, `text` = an agent's `ompdesk_autopilot` guide) and `#commitGuide` writes the answer into the new worktree and commits it (`--no-verify`, no signing) as the branch's first commit when the file differs, so it never touches the user's current branch and reaches main only on merge. `ensureGuide`: an existing guide (the agent's `text`, else the checkout's file) is kept byte for byte and only gets the facts' `## Release` section when it has none (no model request); never rewritten otherwise; one past `AUTOPILOT_GUIDE_COMMIT_MAX_BYTES` (256 KB) is left alone. A repo without one gets one built: ONE `completeOnSmol` request (`next-prompt-engine.ts`: stock's `smol` role via `resolveRoleChain`, never the main model, usage in stock's ledger as `autopilot-guide-draft`) over a bounded prompt (rules-file excerpts, README, recent commit subjects, test/build commands) writes the other sections, then the facts' Release section goes in (replacing any the model wrote); on any failure the deterministic `templateGuide`. A bridge that cannot answer means no guide commit; the run starts anyway.
- **Release facts** (`collectReleaseFacts`, read-only, no model, every read bounded, git and gh with a 10 s timeout): release/publish/deploy workflows in `.github/workflows` (triggers: a push to the default branch and its `paths`, a pushed tag, a published GitHub release, manual dispatch; what they publish (npm, crates.io, PyPI, electron-builder, GitHub release, goreleaser, …) or deploy (GitHub Pages, Vercel, Netlify, Cloudflare, Fly.io, Firebase); the secrets they read, `GITHUB_TOKEN` left out), version manifests (`package.json`, `Cargo.toml`, `pyproject.toml`, `go.mod`), local publish scripts (`package.json` scripts, `Makefile`, goreleaser), the changelog's shape (keep-a-changelog, versioned, unversioned), version tags (count, last 90 days, median gap of the latest 10, the latest tag's commit subject), GitHub releases (`gh release list`, only for a github.com remote), hosting configs whose Git integration deploys a push (`vercel.json`, `netlify.toml`, …), conventional commits (a majority of the last 30 subjects).
- **Verdict** (`releaseVerdict`): a rules-file procedure first (the section points there and adds only the cadence); else a publishing workflow (packaging alone, an electron-builder CI build, publishes nothing); else a deploy workflow or hosting config (a release is a fast-forward push of the default branch); else tags, GitHub releases or a publish script (push the release commit and a version tag; a local publish command stays the maintainer's); else **no release**. The `## Release` section starts with one marker line, `Releases: yes` or `Releases: no`, and is **always `releaseSectionTemplate` over the facts, never a model's**: the agent runs it as written, and on TokenCat (21 Oct 2026) the smol model's section added pushing the version tag before a workflow whose first job skips the release when that tag already exists, so the run would never have published; the template had it right. A `yes` section has a numbered Procedure (version bump rule from the commit kinds, where the version lives (manifests with a version, and the files a publishing workflow's push `paths` must change, e.g. TokenCat's `build.sh`), changelog section in its own shape, checks first, one release commit touching only those files and the changelog in the last release's message style, the exact push/tag/workflow, watch the run; a failed run is reported and fixed in the next cycle, never forced) and a Cadence (the history line, the newest of local tags and GitHub releases, then: release when user-visible fixes or features have gathered at about that rhythm, a breaking defect at once), within what the guard lets a release do (push `HEAD:<default>` fast-forward and version tags, `gh workflow run`, watch runs; never a publish command or `gh release create`: CI publishes).
- **Release detection reads it**: `detectReleaseProcedure` (`src/main/release-detect.ts`) takes a rules file's (AGENTS.md, CLAUDE.md, CONTRIBUTING.md), then `RELEASING.md`/`docs/release*.md`, then AUTOPILOT.md's Release section (`guideRelease`: a heading named Release/Releasing/Release procedure/릴리스/배포, never "Release cadence"; a section without a marker is a person's own procedure and counts) unless it says `Releases: no`. So a run started with the app's guide can release under Automatic shipping, and the agent's `begin.ship.releaseProcedure` names `AUTOPILOT.md › Release`. WHEN to release is decided by the content, never the clock (`propose_release`, cadence `agent`; `releaseReadiness` in `autopilot-core.ts`): the bridge reads what landed on the release target, never the run's own HEAD (`unreleasedOnTarget` in `autopilot-release-facts.ts`: `<ship remote>/<base branch>` fetched with its tags, the commits after the newest `v*` tag reachable from it; an unlanded run has nothing to release there, and a release made from another checkout is a tag on the remote, so its commits do not count again; pinned on real repos by `bridge-autopilot-release.test.ts`) and answers due for `RELEASE_BATCH` (3) user-visible ones (`feat`/`fix`/`perf` or a breaking `!`; every commit counts in a repository without conventional commits), for one the agent calls `urgent` (with why), or for one that has waited `RELEASE_WAIT_CEILING_MS` (a day); docs, tests, refactors and CI alone never are. The answer lists the user-visible subjects (newest 20) and counts the rest; a release not due opens no release scope. Replaced a time-based cadence (the user's call, 22 Oct 2026). A user's own release request (`ship`) is never held.
- Pinned by `bridge-autopilot-guide.test.ts` (kept byte for byte, a missing Release section added with no model request, a model's Release section always replaced by the facts', the agent's text first, a too-large guide left alone), `bridge-autopilot-release.test.ts` (facts on real temp repos: an npm package with tags and a tag publish workflow, an Electron app publishing on a version push to main like this repo, a repo with no releases, a Pages and a Vercel site; trigger parsing from the `on:` block only, a CI build publishing nothing, a push's `paths` as the version file, the newest release in the cadence; the section's marker and replacement), `release-detect.test.ts` (AUTOPILOT.md's Release section, `Releases: no`, a rules file wins), `autopilot.test.ts` (Start's guide request and commit, no guide call from the sheet), the sheet tests in `ComposerModes.autopilot.test.tsx`, the guide test of `e2e/autopilot-cycles.e2e.ts` (no guide box; the template guide with `Releases: no` is the branch's first commit and `begin` reads it) and the opt-in guide test of `e2e/real-autopilot.e2e.ts`.

### Cycle reports are checked, not trusted
- Why (real omp, small model: 11 of 11 cycles told the truth about their check, but the commit hash was missing in 5 of 7 reports and a second `end` overwrote the first). Pure rules in `modes/autopilot-verify.ts` (pinned by `bridge-autopilot-verify.test.ts`), wiring in `autopilot.ts`.
- **The first `end` of a turn stands**: a repeat only adds follow-ups, children, ship, commit; `shouldSteerStop` sends no stop steer once reported. Only a refused report is replaced by a second `end`.
- `observeReport` takes the commit from git (a claimed hash not in the branch history is dropped; no repo, the claim stands) and measures `change` (`AutopilotChangeStat`: files, +/−, commits, `docOnly`).
- **`end` waits for the calls beside it** (`settledBeside`): stock runs a message's tool calls side by side, so an `end` sent with its commit or check read HEAD and the ledger before they finished (cycle 90 of this repository's run: a mistyped hash, no commit recorded, the green cycle never landed). It first waits for stock's event stream to report its own start (up to 2 s; the stream lags the call, and a call listed after `end` starts after it), then until every other call of its own assistant message (stock's message list) has ended and no other call of the cycle runs (up to 5 min, `OMP_GUI_TEST_AUTOPILOT_SIBLING_WAIT_MS` in tests); a call still running then records nothing and answers `recorded: false` with the running tools, so the agent waits and calls `end` again. Pinned by "takes the commit a call beside `end` made", "takes the commit of a call listed after `end`" and "records nothing while a call beside `end` still runs" in `bridge-autopilot-stock.test.ts` (installed omp, a commit and `end` in one message).
- **A green claim needs the turn's own tool calls to show it** (ledger of `tool_execution_*`: a check-like `bash` command, or the one named in `end.check`, that did not fail and ran after the last `edit`/`write`/`ast_edit`). How each `bash` call ended is the work card's own rule (`commandStatus`, `resources/gui-bridge/command-verdict-core.ts`, read in `ledgerCall`): a check stock or the shared-checkout guard refused is no check run, a check whose own output shows failure under exit 0 failed, a backgrounded one is no failure (its result never reaches the ledger), and one the user's stop cut off while `end` waited (the tool's abort signal, `LiveState.stoppedAt`, `statusAfterStop`) is no check run, as the card reads it interrupted. Otherwise `verify` becomes `skipped` or `red` with `verifyNote` (`no_check` | `check_failed` | `edited_after`; timeline in en/ko and Markdown log); the `end` result tells the agent, which may run the check and `end` again. A cycle with a commit and no green counts red: neither pushed nor ignored. Release cycles are exempt.
- A `pick` op names the item after the audit (`now.title`; before it `now.area` is unset and the screen says "Picking an item…", never the rotation's guess) and refuses a repeat of a recent title before the work.
- **A cycle is a batch** (the user's call, 22 Oct 2026: "한 사이클에 여러개를 동시에 개선해도 되는 거 아니야?"): the static protocol's PICK step takes the highest-value item plus every other independent item (different files, none waiting on another) the cycle can finish and verify, worked side by side (the task tool's subagents in the worktree for small ones, child sessions for multi-minute ones), one commit per item, the batch named in one `pick`/`end` title joined by " · ". `beginHints`' cost hint points small items at subagents instead of child sessions (`bridge-autopilot-verify.test.ts`).
- `begin` carries `pick` and `hints` (a follow-up open ≥ 3 cycles, counted from the cycle that left it whether or not later cycles list it again (`followupAge`; counting only consecutive re-listings left a follow-up named once at 0, and the run's list only grew, the user's report of 23 Oct 2026), asks for a decision: do it, or close it in `end.resolved` with why, a docs-only last cycle, fan-out cost); all dynamic guidance rides in `begin`, the static section is unchanged. Fan-out measured: two 25–30 s items took 62 s and cost about twice as much in two children, hence "fan out only for items of several minutes".
- **A follow-up closes when a cycle says it did it** (21 Oct 2026, this repository's own run: four finished follow-ups stayed open for the whole window and `begin`'s defect hint kept sending the agent back to them, once to re-investigate a guess an earlier cycle had disproved). `openFollowups` drops a follow-up a later cycle's title names exactly (rare: a title is a short name, a follow-up a sentence) or lists under `end.resolved` (begin's exact text, case, punctuation and spacing ignored; the tool schema and the defect hint say so; a repeated `end` merges it). A cycle that lists it again in its own `followups` reopens it. Pinned by `bridge-autopilot-core.test.ts` ("resolves a follow-up"). Because a title almost never repeats a follow-up's sentence, `pick` and `end` name the open follow-ups the cycle looks like it covers (`followupsLikeCycle`: at least 2 of the follow-up's words of two or more letters, and 40 % of them, appear in the title and summary; one the report already resolved is left out) and ask for their exact text in `resolved` (a repeated `end` merges it): a run on 23 Oct 2026 carried 12 open follow-ups, its next item among them, because nothing asked the agent to close them. Only a hint, in the tool results; the static section is unchanged. Pinned by `bridge-autopilot-core.test.ts` ("followupsLikeCycle").
- **Bugs before polish** (19 Oct 2026; a real run spent 2 of 4 cycles on docs and wrote a found bug off as a "known limitation"): `BEGIN_PICK` ranks a known bug or failing behaviour first, docs and polish last, and says a fixable bug is never a limitation; `beginHints` names up to two open follow-ups whose words mark a defect (`DEFECT`); `pick` refuses a docs item right after a docs-only cycle unless it carries `reason` (`docsPickRefusal`); `end` answers a report that writes a problem off with no follow-up with `writeOff` (`writeOffNote`), and the repeated `end` merges the follow-up. Pure in `autopilot-core.ts`, pinned by `bridge-autopilot-verify.test.ts`. Real run after it: 3 bug cycles and 1 docs cycle of 4, both seeded bugs and a third one fixed, nothing written off.
- **The run's session title** (`runSessionTitle`, `#retitle` in `src/main/autopilot.ts`): stock `set_session_name` "<repo folder>" once the tab is ready, then the item of the cycle at work, renamed as each cycle's `pick` (or, for a cycle that picked nothing, its record) names it, only while the name is still the run's own (`get_state.sessionName`; renames go one after another, `Run.titling`). No "Autopilot" word in it (the user's call, 23 Oct 2026): the row's rocket mark, the title bar and the pane header say it is a run. A relaunch's run takes the naming over only when the name is still one a run gives (its folder, a cycle's item, an earlier build's "Autopilot · …") or none (`runOwnsTitle`); a typed one stays. Stock answers an RPC rename without `session_info_update`, so `SidecarPool.noteSessionName` tells the tab entry and the windows. Pinned by `autopilot.test.ts` ("titles the run's session") and the two title cases of `autopilot-restart-resume.test.ts` (restart).
- The run's board sections have no empty-state sentences: the run, the cycles and the follow-ups show only their rows, and the cycles section waits for the first cycle (`AutopilotBoard.test.tsx` "one-line rows").
