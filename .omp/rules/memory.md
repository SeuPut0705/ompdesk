## Panels, sidebar and work views

### Memory (ai-memory)

- Memory is ai-memory: `src/main/ai-memory/`, contract `src/shared/ai-memory.ts`, always on, with no off switch (see the user's rule below). Settings › Memory (`settings/memory/MemorySection.tsx`) is the ONLY memory setting, and its only switch-like control is the terminal omp button. The name in every UI string is just "Memory"/"메모리", never "ai-memory"; no link to the project's repo or docs, no credits in the UI. The licence notice lives in `THIRD_PARTY_NOTICES.txt` and `LICENSES/` only; Settings › Updates & about › This computer lists it as one of OMPdesk's own components (`settings/memory/MemoryComponentRow.tsx`: version, status, "updated with OMPdesk", no update control).
- **User's rule (29 Oct 2026, "Remove that thing itself. We decided to use only what we built, and updates are ours to do: we customised and built it.")**: (1) memory and learning are always on: the prefs `aiMemory`, `aiMemoryLearn` and `aiMemoryServiceOwned` are retired at startup (`retired-prefs.ts`; a stored `false` from an older version is ignored and deleted), `agent_power.set` has no `aiMemory`/`aiMemoryLearn` switch, `AI_MEMORY_SET_ENABLED` is gone; Delete all memory and per-page delete stay (they manage data, not the feature). (2) Only OMPdesk's own ai-memory build ever runs, from the bundled build staged as today: no PATH, `~/.local/bin`, Homebrew or Windows-script install is ever used, a foreign launchd unit or logon entry is replaced, and a foreign wiring in the terminal omp is not adopted. (3) Updates come only with OMPdesk releases: nothing in OMPdesk calls ai-memory's `upgrade`, downloads an upstream asset or touches Homebrew (audited 29 Oct 2026); the vendored binary still carries the user-run `ai-memory upgrade` subcommand (`native/memory` `commands/upgrade.rs`, only reachable from a shell, never run by the server or `setup`), and anything it replaced in the staged folder is put back at the next launch because the staged copy is trusted only by bytes (below). Do not add a path that updates, replaces or selects the memory binary or service from anywhere but the app's bundled build.
- Stock's `MemoryBackend` (`memory.backend` rows, the `memory` model role row via `HIDDEN_ROLE_IDS`, the bridge's `get_memory_report`/`memory_*` methods) is gone from OMPdesk. Stock keeps `memory.backend` `off` for RPC hosts itself (`protocolDefault: ["rpc", "acp"]`), so nothing is held as a runtime default.
- **No side panel view**: Memory lives on Settings › Memory alone (status, counts, pages by kind, handoffs, the web console); palette command `cmd.memory` ("Memory") opens it. The side panel's glance (status, the newest pages, open handoffs) was removed on 21 Oct 2026 (see Side panel).
- **OMPdesk's own source, built by OMPdesk** (ai-memory, MIT, [akitaonrails/ai-memory](https://github.com/akitaonrails/ai-memory)): it lives in `native/memory/` (a `git subtree add --squash` of upstream tag v3.1.1; tag and commit in `native/memory/UPSTREAM.md` and `native/memory/ompdesk.json`; the upstream `LICENSE` is kept; `.github/`, `companions/`, `docker/`, `nix/`, `flake.*` and its AGENTS/CLAUDE files were removed on import). Edit it like our code. No release asset of the upstream is downloaded or pinned anywhere (`sync:ai-memory`, `bump:ai-memory` and the pin file are gone).
  - `bun run build:memory` (`scripts/build-memory.ts`) runs the upstream's own release build (`cargo build --locked --release -p ai-memory-cli`, default features, Cargo.lock as committed, `native/memory/rust-toolchain.toml` = 1.95) for the host (macOS arm64 or Windows x64) and writes the gitignored `resources/ai-memory-bin/<platform>-<arch>/ai-memory[.exe]` plus `ai-memory.build.json` (binary name, **SHA-256 recorded at build time**, version, upstream tag/commit, rustc, build time and duration). Each builder config ships that directory as `<resources>/ai-memory-bin/` outside the asar. `scripts/after-pack.cjs` `checkAiMemory` (and `packaging-config.test.ts`) fail a package without the binary and its record, with another version than `native/memory/ompdesk.json`, or whose bytes differ from the record; `scripts/mac-sign.cjs` signs the nested binary with the app's certificate; the release's `Verify bundle` verifies and runs it. Without Rust, `build:memory` prints how to install it and exits 1; the app then shows the failed phase "Memory is not built", never a crash (a dev run only reports).
  - CI: release.yml's `mac` and `win` jobs first restore the built binary and its record (`actions/cache/restore`, path `resources/ai-memory-bin`, key `ai-memory-bin-<os>-<arch>-<hashFiles native/memory/** + scripts/build-memory.ts + resources/gui-bridge/memory-prompt.ts + resources/gui-bridge/redactor.ts>`; the toolchain file and Cargo.lock sit inside native/memory, and `memory-prompt.ts` and `redactor.ts` (`EMBEDDED_SOURCES` in build-memory.ts) are the files outside it the CLI compiles in: `install_hooks.rs` embeds them with `include_str!` into the omp extension it generates, so a new input outside native/memory joins every key, `EMBEDDED_SOURCES` and ci.yml's change test). A hit runs only `bun run build:memory -- --check` (the record matches native/memory/ompdesk.json, this OS/arch and the SHA-256 over the current `EMBEDDED_SOURCES` it records as `embeddedSha256`, the binary's SHA-256 is recomputed against it, its `--version` runs; after-pack checks the packaged bytes again and mac-sign.cjs signs them at packaging as on a build). A miss installs Rust 1.95 (`dtolnay/rust-toolchain`), restores `Swatinem/rust-cache` (workspace `native/memory`; dependencies only, so the 11 workspace crates compile), runs `bun run build:memory` and saves the cache right after the build, so a later failing step keeps it. A miss costs 9m23s on mac and 7m13s on win (dry run 39229484141; almost all of it the `ai-memory-cli` crate's thin-LTO link with `codegen-units = 1`; 3m41s on an M-series Mac). ci.yml's manual Windows jobs do the same, and its `memory` job (macOS) builds only when `native/memory/**`, `scripts/build-memory.ts`, `resources/gui-bridge/memory-prompt.ts` or `resources/gui-bridge/redactor.ts` changed (then also `licenses:check`) and saves under the same key, so a release after that push hits the cache.
  - **Merging upstream**: `git subtree pull --prefix native/memory https://github.com/akitaonrails/ai-memory <tag> --squash`; delete again what we removed when it comes back (`.github/`, `companions/`, `docker/`, `nix/`, `flake.*`, `AGENTS.md`, `CLAUDE.md`) and the self-update: `crates/ai-memory-cli/src/commands/upgrade.rs` and `tests/suite/upgrade_e2e.rs`, `Command::Upgrade`/`UpgradeArgs`/`commands::upgrade` in `cli.rs`, `lib.rs`, `commands/mod.rs`, `agent_plugins.rs update_claude_code`, `install_hooks.rs restage_claude_code_scripts`, `install_layout.rs shipped_binary_name`, `Config.release_base_url` (OMPdesk's binary only updates with OMPdesk: `ai-memory upgrade` is an unknown command and nothing fetches upstream releases; `src/main/ai-memory/no-self-update.test.ts` fails when any of it comes back), keep our own edits, update `UPSTREAM.md`, `ompdesk.json` and (if it moved) the version in `native/memory/Cargo.toml`. Then `bun run build:memory`, `bun scripts/gen-ai-memory-notices.ts && bun run gen:licenses` (`LICENSES/ai-memory-LICENSE` is the upstream MIT text; `LICENSES/ai-memory-dependencies.txt` lists every Rust crate linked and records the SHA-256 of `native/memory/Cargo.lock`; `licenses:check` fails when they differ), the packaged e2e and a release dry run. The binary updates only with OMPdesk (no CLI-tools updater entry). The upstream copyright and licence text appear only in `LICENSES/`, `THIRD_PARTY_NOTICES.txt` and `native/memory/LICENSE`.
  - The launchd label `com.github.akitaonrails.ai-memory`, the Windows logon value `ai-memory` and the data dir are the binary's own and stay, so an existing install keeps working: a new build replaces the macOS binary in its one staged folder (Windows: a new `<version>-<hash>` folder the logon entry is re-pointed at), `setup` restarts the server on the new bytes, the data dir is untouched, other folders are pruned.

#### The Memory page

- Settings › Memory (`settings/memory/`; Settings sub-target `memory:<tab>`, the tab is the route). `MemorySection.tsx` is the shell: tabs Overview, Search, Pages, Handoffs, Sessions, Profile, Maintenance, each one component; project selector `resolveProject` = the user's pick, else the project whose name ends with the active session's folder name, else the latest. A memory that is `unsupported` (no build for the platform, or a launch that does not set it up) shows only Overview.
  - **Overview**: status, project, its counts, last capture (7-day activity and health in the tooltip), disk size, data folder, "Open web console" (`웹 화면 열기`, only while running) and its password, terminal omp, one privacy line (full text as tooltip).
  - **Search**: full text in the project or all projects (toggle); a hit shows title, path, kind, tier, age, snippet and opens in Pages (hits carry no tier or time on the wire; main fills them from the projects' page lists).
  - **Pages**: by kind (rules, decisions, gotchas, procedures, sessions folded, notes), markdown reader, Edit (a new version through the server's write path, keeping kind, tier, tags, pin), Pin, Helpful/Not helpful, Delete (confirm) and a **Deleted** group whose Restore reads the page from the checkpoint the delete returned (`AiMemoryDeleted.rev`, in `useMemoryPageStore.deleted` and the snapshot cache). Session pages are read-only.
  - **Handoffs**: open first; the detail reads without claiming; Cancel (confirm) discards an open one. Korean says "인계". **Sessions**: recent captured sessions with observation counts; one opens its raw observations read-only, 50 a page. **Profile**: the cross-project profile, read-only; Edit opens the entry's page in Pages. **Maintenance**: rule-based lint (writes no report), retention sweep (Preview is a dry run; Run sweep enabled only after a preview that found something, then confirms), Delete all memory (typed-word confirmation).
- UI rules: lists/detail are `MasterDetail` (detail on its own screen on a phone). Rows use `SettingsRow` `tipOnly` (every description is a tooltip, never inline; `data-setting-desc` must not appear). Row actions are quiet secondary buttons (danger only in the confirm dialog). Close rows declare `--hit-gap-x/-y` (tab bar 4 px, reader's action row 4/16 px) so no touch reach covers a neighbour.
- Data: reads go through `useMemoryRead(key, read)` (`use-memory-read.ts`: last known value at the first frame via `lib/last-read.ts`, re-read in place and when `useMemoryPageStore.version` bumps; never a spinner); every write through `useMemoryAction` (`memory-ui.tsx`: toast, then `bump()`). Strings: `locales/memory/<section>.ts` (en and ko side by side, aggregated by `locales/memory/index.ts`).
- Tests: one `*.test.tsx` per tab plus shell/component row/panel on `memory-test-harness.tsx` (fake `window.omp.aiMemory`); `e2e/memory-page.e2e.ts` on the stateful fake server (palette → Overview → search → open → edit/save → delete → restore → read/cancel a handoff → session paging → side panel), rig shared with `ai-memory.e2e.ts` in `e2e/fixture/ai-memory-rig.ts`. The responsive audit covers every tab and list → detail state (`settings-memory-<tab>`, `settings-memory-<tab>-detail` in `e2e/responsive-surfaces.ts`, answered by `dev-harness/fixture-memory.ts`); run at 390 with `OMP_GUI_RESPONSIVE_ONLY=settings-memory`.

#### Client, binary, lifecycle

- **Client** (`src/main/ai-memory/client.ts`, one `AiMemoryClient`; the token is read in main, never in the renderer): reads are `/api/v1` REST routes plus `/admin/status`, `/admin/checkpoints`, `/admin/profile/*`. Writes go through the server's own write path, never its files: `/admin/write-page`, `/admin/delete-page` (returns `pre_checkpoint`; the client falls back to the head checkpoint read before the call), `/admin/restore-page`, `/admin/lint` (always `dry_run` + `no_llm`), `/admin/forget-sweep`; `memory_feedback` and `memory_handoff_cancel` (no REST route) go as MCP `tools/call` on `/mcp` (stateless JSON, `Accept: application/json, text/event-stream`).
  - Twelve IPC channels (`AI_MEMORY_OVERVIEW|PAGES|SESSIONS|OBSERVATIONS|PROFILE|LINT|SWEEP|WRITE_PAGE|DELETE_PAGE|RESTORE_PAGE|FEEDBACK|CANCEL_HANDOFF`): reads are web-`workspace`, writes `host-admin` in `IPC_POLICY`. For the agent (`app-channels.ts`) `memory.delete_page` and `memory.sweep` are `sensitive` catalog actions beside `memory.purge`; everything else is `never` (the agent has its own memory tools). `ipc.ts` validates every argument (a page path is never absolute or `..`).
- **Which binary** (`binary.ts`): the shipped file is never run in place (its path lands in a launchd unit, a Windows logon entry and omp's MCP entry, and a Windows update replaces the install folder under a running server). `stageBinary` verifies it and copies it to `<tools>/ai-memory/<stageKey>/` (atomic rename; other folders pruned after wiring): on macOS always `current` (`MAC_STAGE_KEY`), on Windows `<version>-<first 8 hex of the recorded SHA-256>` (a running server locks its .exe).
  - **Why one macOS path** (the user's report, 20 Oct 2026: Desktop, Documents, Downloads prompts came back after updates): the server is a launchd job, so it is its own responsible process for TCC, and TCC keys an unbundled program's grants by its absolute path (tccd's `AUTHREQ_SUBJECT` is the binary's path), checked against its designated requirement. The requirement never changes (`AI_MEMORY_REQUIREMENT`: identifier plus the pinned certificate; 0.42.0 and 0.43.0 binaries have different cdhashes and the same requirement), but a path per build was a new TCC client after every update. OMPdesk's own bundle keeps its grants across updates (same bundle id and requirement). Never move the macOS staged path again without a reason worth one more round of prompts for every user.
  - The unit `setup` renders names the binary's SHA-256 (`binary_line` in `native/memory` `user_service.rs`, a comment line in the plist and the systemd unit), so a binary replaced in place changes the unit and `setup` restarts the server on the new bytes instead of answering `Unchanged`. Pinned by `a_binary_replaced_in_place_restarts_the_launch_agent`, `binary.test.ts` (one macOS path across builds, one folder per Windows build), and the requirement in release.yml's `Verify bundle` by `packaging-config.test.ts`.
  - Accepted when its bytes are the build record's `binarySha256` (`readBuiltAsset`; Windows ships it unsigned; a dev build's own copy) or, on macOS only, when its signature satisfies `AI_MEMORY_REQUIREMENT` = `identifier "ai-memory" and certificate root = H"<scripts/mac-signing.json certificateSha1>"` (`codesign --verify --strict -R`, `codeRequirementProblem`). Packaging re-signs the nested binary with OMPdesk's certificate (`mac-sign.cjs`) after `after-pack.cjs` checked the build record, so a release's bytes never equal the record and any other valid signature (system binary, ad-hoc re-signed copy) fails. A package signed ad-hoc therefore has no memory, by design. `release.yml`'s `Verify bundle` checks the same requirement.
  - The staged copy is trusted only by bytes: reused when it is the recorded one or byte-identical to the shipped file verified at that launch; otherwise replaced. (0.38.0/0.38.1 compared the signed bytes with the then-pinned upstream hash, failed every launch silently, so memory never started on a Mac; pinned by `binary.test.ts`, `service.test.ts`, `e2e/packaged-ai-memory.e2e.ts`.)
  - A rebuilt binary changes the unit (its SHA-256 line; on Windows also its path), so ai-memory's `setup` restarts the service on it. Only this build ever runs (see the user's rule below): `binary.ts` no longer looks at PATH, `~/.local/bin`, Homebrew or the Windows script's folders, however new an install there is.
- **Runtime log**: `AiMemoryService` writes `<userData>/logs/gui-runtime.jsonl` lines with source `ai-memory`: `launch` {enabled, automatic, platform, arch, bundledDir, override} once per start, `binary` {source, version, bin}, `phase` {phase, step, detail, from, fromStep} on every change, `failed` {step, detail, stack} per failure (polls too). `start()` never rejects: whatever it throws becomes the `failed` phase, shown in Settings with its reason and Try again.
- **Lifecycle** (`service.ts`, `AiMemoryService`; started after the first tab). Only a packaged app or `OMP_GUI_AI_MEMORY_BIN=<binary>` changes the machine; a dev build only reports. `OMP_GUI_AI_MEMORY_NO_SERVICE=1` passes `--no-service` for tests; `OMP_GUI_AI_MEMORY_UNIT_PIDFILE=<file>` stands in for the OS service in the fake-binary e2e.
  - The server is **ai-memory's own per-user service** (launchd LaunchAgent / Windows logon entry, installed by `ai-memory setup`), not an OMPdesk child. OMPdesk owns only its own wiring and **never writes ambient configuration**: nothing goes to `~/.omp/agent`, no other agent's config is touched, `uninstall --apply` is never run (it removes every agent's wiring).
  - On: `setup --plan --json --agent omp`; on a fresh data dir `init` plus the one config change below; then `setup --yes --agent omp` with `PI_CODING_AGENT_DIR` at a scratch folder (`<userData>/ai-memory/omp-ext.setup`, deleted afterwards): `setup` cannot install the service without wiring an agent, so its omp wiring lands in the scratch folder, and the shared skills it writes to `~/.agents/skills` are taken back when this run created them (`terminal.ts removeNewSharedSkills`). A lone `problem: self-check` is not fatal; the `/healthz` poll decides.
  - Every `setup --yes` runs **isolated** (`SpawnSpec.isolated`, `setup/supervisor.ts isolatedLaunch`), still under the setup supervisor. WHY (v0.38.0): the service host outlives OMPdesk by design and on Windows a child inherits every inheritable handle of its parent, so a plain spawn gave the host the app's pipes and those of whatever launched the app, open as long as the service runs (the packaged first-launch e2e's teardown timed out). Isolated, Bun starts the command (`bun -e` with `bun:ffi` calling kernel32 `CreateProcessW`, no PowerShell) with an explicit handle list (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`: NUL stdin, a temp log file as stdout/stderr, `CREATE_NO_WINDOW`); the supervisor passes the log on once the command exited. On macOS launchd starts the server, so it inherits nothing.
  - Bun may still be installing on a fresh Windows machine, so the wiring depends on it (dep `bunPresent`, `findBun`): without Bun a pass runs no command and fails with "Waiting for Bun…"; the setup state reporting Bun present (`index.ts` calls `AiMemoryService.bunInstalled()`) re-runs the pass once, so memory sets itself up on first launch with no relaunch or Try again.
  - Then ai-memory's OWN generators fill the **app-owned extension root** `<userData>/ai-memory/omp-ext/` (`root.ts`): `install-hooks --agent omp --apply --config-file <root>/index.ts`, `install-mcp --client omp --apply --config-file <root>/.mcp.json`, `install-skills --target-dir <root>/skills`, produced next to the root and swapped in only when bytes differ (nothing hand-written, no `.bak`, nothing touched on an unchanged launch). omp reads a package root's `index.ts`, `.mcp.json`, `skills/` (stock `omp-extension-roots.ts`), like `resources/omp-builtin/rea`.
  - **The MCP entry starts through a description relay** (`resources/omp-builtin/ai-memory/memory-relay.mjs`, copied beside `.mcp.json` by `generateRoot`). The entry becomes `<bun> ${OMP_PLUGIN_ROOT}/memory-relay.mjs <ai-memory> mcp-bridge …`. `service.ts` resolves Bun by absolute path from the spawn PATH or its install directory; without Bun, the generated entry stays unchanged. Every server tool, including future tools, stays directly mounted under its original name with its original schemas and metadata. The relay only prepends a concise route summary to known tools' descriptions, retaining the full original description, order and pagination. Unknown tools' descriptors remain entirely unchanged. It has no dispatch tool or local tool schemas. `initialize.instructions` passes through entirely unchanged, byte for byte: upstream `MEMORY_INSTRUCTIONS` in `native/memory/crates/ai-memory-mcp/src/server.rs` contains scope and trust guidance both before and after its detailed tool catalog. Never discard everything after the catalog's opening delimiter. Tool calls, errors, notifications and server requests pass through without rewriting. Only list request ids are tracked, with numeric and string ids kept distinct. Client EOF closes the bridge's stdin and kills a bridge that does not exit; bridge exit drains pending stdout before the relay exits. The earlier hidden-tool dispatcher added steps to maintenance requests and was removed; its token and model timing measurements do not describe this design. `memory-relay.test.ts` covers complete instruction preservation including trailing trust text, complete descriptors and future tools, pagination, reordered ids, errors and process lifetime. Root tests cover missing and updated relay files and non-stdio entries; service tests cover the no-Bun path. Packaging must include the relay outside the asar. Never add `index.ts`, `.mcp.json` or `skills/` to `omp-builtin/ai-memory/`: that folder is not an extension root.
  - **Only OMPdesk's own service serves** (`#takeOverService`, `unit.ts`: launchd plist `com.github.akitaonrails.ai-memory` / HKCU `Run\ai-memory` runs a binary under `<tools>/ai-memory` or the binary in use = ours). A unit that runs someone else's binary (the label and the logon value are ai-memory's own, so a person's own install uses the same ones) is removed (`launchctl bootout` + plist, or the `Run` value + the PIDs in `service-host.json`) before `setup` installs OMPdesk's own; there is no stored ownership flag (`aiMemoryServiceOwned` is retired). A server that answers with NO unit (Docker, a foreground `ai-memory serve`) cannot be stopped by OMPdesk, so the pass fails with a message saying so and `setup` does not run (Try again after stopping it). `OMP_GUI_AI_MEMORY_NO_SERVICE=1` skips this (tests).
  - **No off path**: memory and learning cannot be turned off (29 Oct 2026), so there is no root removal, no "server stops when OMPdesk started it" and no `uninstall` listing of other clients. Stopping a unit exists only to replace a foreign one (above) and for Delete all memory: `launchctl bootout` + delete the plist (macOS), delete the `Run` value + `taskkill` of the PIDs in `<data>/service-host.json` (Windows; never by image name: every live omp has an `ai-memory mcp-bridge`). `uninstall --apply` is never run.
  - Delete all memory: the same stop (owned units only), then `wiki/ db/ raw/` are deleted after `/healthz` stops answering (`uninstall --purge-data` refuses while any `ai-memory` process runs), then `setup` and the generators run again (`#purgeData`, then `#enable`; a failed purge runs `#enable` again too).
  - A 60 s poll (`/healthz`, `/admin/status` for counts, the root's files) heals by re-running setup and the generators (twice down in a row, or the root gone; at most once per 10 minutes). One check runs at a time (`#check` joins a running one): on Windows a check's file reads outlasted the test's 10 ms interval, and an older check applying its answer after a newer one read a removed root back as present (ready, no heal).
  - **An update never leaves memory down or stale** (v0.41.0: the server stayed off and the extension root kept a two-versions-old build). ai-memory's `setup` restarting a changed LaunchAgent waits until the booted-out job has left the domain (`launchctl print` polled up to 30 s) and bootstraps up to 3 times (`user_service.rs` `start_launchd`): `bootout` returns while the old server drains, and a `bootstrap` sent then fails "5: Input/output error" with nothing loaded. A failed wiring pass still regenerates the extension root from the binary in use (the root follows the binary, not the service), then runs again by itself after 30 s, 2 min and 10 min (`RETRY_DELAYS_MS`, a `retry` log line each; e2e shortens them with `OMP_GUI_RETRY_DELAYS_MS`) before it stays failed for Try again. Pinned by `user_service.rs` tests, the "setup problems" cases of `service.test.ts` and the update-like relaunch in `e2e/ai-memory.e2e.ts` (`FAKE_AI_MEMORY_REFUSE_SERVICE`).
  - Defaults stay ai-memory's zero-LLM path (no provider, no dream) and its single-user cross-project profile. The one change: a **fresh** config gets `embedding_provider = "none"` (`config.ts`), since local embeddings fetch an 87 MB model from huggingface.co and hold ~355 MB resident; search stays full-text, entity and graph, and removing that line turns hybrid search on. An existing config is never touched.
- **Coverage**: every omp OMPdesk spawns gets `-e <root>` once the root is complete (`AiMemoryService.extensionArgs()`, read at each spawn: `sidecar-factory.ts` `aiMemoryExtensionArgs` for local tabs and tabs a host runs for a paired device, `schedules.ts` `ompRunLauncher` for scheduled `omp -p` runs; subagents are children of those omps). The terminal `omp` CLI is separate unless the user asks. Short-lived internal omps that pass `--no-extensions` (rename, model setup) capture nothing, on purpose. The brief is the folder's open handoff, injected as a hidden `ai-memory-handoff` custom message at a session's first prompt. A paired host's own OMPdesk wires its own.
- **Terminal omp** (Settings › Memory › "Also use in the terminal omp", `AiMemoryService.setTerminal`, pref `aiMemoryTerminal`, default off): runs ai-memory's `setup --yes --agent omp` against omp's real agent dir (MCP entry `mcp.json`, extension `extensions/ai-memory-omp.ts`; skills to the shared `~/.agents/skills`); each later launch re-runs it so the entry follows the new staged binary. ai-memory has no per-agent uninstall, so the reverse (`terminal.ts removeTerminalWiring`) removes exactly what `setup` added: the extension only when it carries ai-memory's generated header, the `mcpServers["ai-memory"]` entry only when it runs an `ai-memory` binary or the `/mcp` URL (other servers and keys stay; the file goes only when nothing is left). Shared skills stay (other agents read them). While the user connected it (pref `true`) and omp's agent dir holds the generated extension, `extensionArgs()` leaves the root out so a session never captures twice. **Kept as a switch on purpose** (29 Oct 2026): unlike memory itself it writes into the person's OWN omp config (`~/.omp/agent`), which must stay a choice; it is off by default and only the button sets it.
- **Migration** (once, in the first `enable` pass with pref `aiMemoryTerminal` unset): an earlier build wrote ai-memory's extension and MCP entry into `~/.omp/agent` with the staged binary. When the `ai-memory` MCP entry runs a binary under `<tools>/ai-memory` or the binary in use (`legacyOwned`), exactly those two entries are removed and the pref is stored `false`; wiring that runs someone else's ai-memory stays untouched and is NOT adopted as the terminal's (`wiring.terminal` and `extensionArgs()` read the pref, so such wiring neither shows as "Connected" nor hides OMPdesk's root; only the button sets the pref `true`).
