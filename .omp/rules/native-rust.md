## Rust conversion (`native/ompdesk/`)

- **The owner's order (11 Nov 2026)**: convert every part of OMPdesk that can be converted to Rust, for a lighter and faster app. It is a conversion order, not a study: a part is left in TypeScript only for a reason this file states. **A Rust unit alone never cuts a release** (the owner's rule, 12 Nov 2026, his choice among three: release now, wait for the whole conversion, or this): units land on `main` one by one, each leaving a working app, with no version bump of their own. Changes that are not Rust work release by the usual cadence (AGENTS.md › Change workflow), and such a release carries whatever Rust is on `main` by then. `gh workflow run release.yml --ref main -f dry_run=true` rehearses packaging for a unit that changes it.
- **What stays TypeScript, and why** (the owner chose both on 12 Nov 2026: the React page stays and only the main process and the shell move; omp stays the one installed on the machine, never bundled)
  - `resources/gui-bridge/**`: an omp extension, loaded by stock omp's Bun process with `-e`. omp is never forked, so its extension language is omp's.
  - The page (`src/renderer/**`, `src/shared/**` as the page uses it): the paired phone and another computer open the same UI in a browser over the web server, which only a web page can serve. The desktop window shows that same page; a second, native UI for the desktop would be a copy of 190 000 lines that the ui-parity rule forbids.
  - Tests and build scripts (`scripts/**`, `e2e/**`): tooling, not the app.
- **Target architecture**: a Rust process owns everything `src/main` does today (sidecars, bridge client, session index, control socket, web server and link, git, files, updater, memory service, terminals, preview) and a thin shell hosts the page. The page already reaches main only through `createOmpApi(transport)` (`src/shared/omp-api.ts`), so the transport is the seam: the same channel names and payloads, served by Rust.
- **Order** (a strangler on `main`, never a long-lived branch: other sessions keep changing `src/main`, and a branch would rot):
  1. The `ompdesk` CLI as a native binary. It carries the whole path once: cargo workspace, build script, staging, signing, packaging check, CI, notices. **Done** (ledger below).
  2. The core process `ompdesk-core` (crate `crates/core`: a host-agnostic library over any `AsyncRead`/`AsyncWrite`, plus its binary), spawned by Electron main on its first request with an open stdin pipe (it exits when the pipe closes, as every child here does). Main's subsystems move into it one at a time; for each one the logic is deleted from TypeScript in the same change (clean cutover) and what stays is its typed client: the exported functions other files call, now a request to the core, plus whatever needs Electron or must stay synchronous. **The subsystem's vitest file stays and runs against the real process**: it is the parity suite, so its cases are not rewritten for the port. Pure parts get Rust unit tests, with tables captured from the TypeScript before it is deleted. Order by independence from Electron: workspace files (done), git's read side (done), git's write side (done), worktrees and the rest of `local/git`'s reads (done), gh with the PR Center and the GitHub center (done), worktree care (branch standing, merge, orphan worktrees; done), disk care (sizes, the regenerable rules, saving and removing worktrees; done), the memory sampler (done), the session index's file work (done; list share stays TypeScript), the control socket server and router (done), worktree seeding (done; a worktree hook's script still runs in main and moves with setup's supervisor), the git that autopilot and the other local handlers still run through `exec.ts`, sidecar pool and RPC client, bridge client, web server and remote link, updater, setup.
     - **Wire** (`crates/core/src/wire.rs`, `src/main/core/process.ts`): one JSON object per line over stdio. Request `{id, method, params}`; response `{id, ok: true, result}` or `{id, ok: false, error: {code, message}}`; event `{event, data}`; the first frame is the event `ready` `{version, protocol: 1}`. A frame with `"bin": n` is followed by exactly n raw bytes that belong to it (file contents either way, never base64). Requests run concurrently and answer in completion order; one writer task, so frames never interleave. stdout carries frames only, stderr diagnostics. A number is read as its digits say, as `JSON.parse` reads it (serde_json's `float_roundtrip`, for the whole core crate): its default parse is best effort and returned one time in ten with sub-millisecond digits one bit off, and the core compares times with `==` (2g › Exact numbers). Base: tokio (later units bring sockets, child processes, timers and the HTTP server into this process).
     - **Client** (`CoreProcess`, `core()`): each request has a 30 s timeout (per-call override; a late answer is dropped); a process that exits rejects what is pending and starts again on the next request, at most three failed starts before a 30 s rest; `stop()` ends stdin and kills after 5 s, called in the quit teardown. `src/main/native-bin.ts` is the one place that knows where a native binary is (packaged `<resources>/ompdesk-bin/`, otherwise `resources/ompdesk-bin/<platform>-<arch>/`). `scripts/vitest-native.ts` (vitest `globalSetup`, node project) runs `ensureNative()` once per run, so every test that reaches the core finds the binary. `core.echo` is the plumbing tests' method and ships in the binary.
  3. The shell. Electron stays until a Rust shell passes the list below; the core process makes the swap small, because by then main is only windows, menus, tray, dialogs, the preview's views and the IPC relay.
  4. What the shell swap leaves in `src/preload` and `src/main` is deleted with it.
- **Batches** (the owner's call, 12 Nov 2026: "조금씩 작업하고 검사하면 하루종일하잖아"). The remaining units move in batches, not one unit per landing:
  - A batch is several units of one area (the batches of `docs/rust-remaining-units.md` §3.2) taken by one session on one branch (`omp/agent/rust-batch-<name>`), each unit still a clean cutover in its own commits. While building, run only what the unit at hand needs to compile and its own Rust tests; no per-unit full parity run, no mutation run, no formal restamp, no CI watch.
  - **The gate is before landing, once per batch**: push the branch and run `gh workflow run ci.yml --ref <branch> -f batch=true` (every job a push to main runs: static, check, build, `native` on all three OSes, `win-platform`, `mac-smoke`, `mac-native`, `memory`; pinned by `packaging-config.test.ts`). Every parity suite of the batch's units is in that run (each unit adds its parity files to `.github/actions/native-parity/action.yml` in the batch). Mutation checks and the formal restamp of every model a batch touches run once, on the branch, after the batch run is green. Only then does the batch land on `main` (rebase, push), and the branch, its worktree and local branch are deleted at once.
  - The session does not wait on the batch run: it starts the next batch on a new branch from its branch head and goes back to land the first when its run reports (`bun scripts/watch-run.ts <id>` as an async job). A red run is fixed on its branch and run again; nothing red lands.
  - The cost the owner accepted: a failure is found inside a larger change, so finding its cause takes longer.
- **The shell is chosen by measurement among three candidates** (the owner's call, 12 Nov 2026; facts read 11 Nov 2026, `tauri-runtime-cef` 3.0.0-alpha.7). The Preview panel needs Chromium (CDP from the host, input injection, capture, PDF, offscreen pages), which the system webview on macOS (WKWebView) does not give. The candidates:
  - (a) **CEF** for the whole app: Tauri 3's CEF runtime or the `cef` crate directly. Tauri 3 is alpha ("Keep production apps on 2.x") with open defects on paths OMPdesk uses: custom-scheme range requests (tauri#16479), a crash on title-bar drag (tauri#14936), no Windows title-bar overlay (tauri#9458), no Windows sandbox, transparent windows black (tauri#15718). A CEF shell is about Electron's size on disk, so its gain is the removed Node main process, not the download.
  - (b) **The system webview alone** (Tauri 2, stable): expected to fail on the Preview's needs above; it is dropped once the prototype shows which of them it cannot meet, with that evidence written here.
  - (c) **A system webview window plus a separate Chromium process for the Preview only**: the UI already runs in WebKit (a paired phone opens the same page in Safari, `docs/mobile-web.md`; e2e drives it in WebKit, `e2e/web-no-reload.e2e.ts`), and a phone already gets the Preview as a picture stream of an offscreen page (`web/preview-stream.ts`, `web/preview-input.ts`). Known costs: Chromium still ships or must be found on the device, so the download barely shrinks; the desktop e2e attaches Playwright over the window's debugging port, which a system webview has no equivalent of, so the desktop tests change; a streamed Preview may answer input more slowly (inferred, not measured).
- The order (the owner's call of 12 Nov 2026 19:4x, "너무 느리다", to shorten the chain): the shell prototype runs beside the leaf batches B1 and B2 (it shares no file with them), and the first hub batch H1 is built on its branch beside the prototype but lands only once the prototype passed (the command entry and omp's pipes are the core's under any of the three shells). The prototype runs (a) and (c), and (b) unless dropped, against one pass list on both platforms: the page loads from the custom scheme with video seek, a second webview in the window or its equivalent, CDP attach to the Preview, `capturePage`/input/PDF equivalents, the hidden title bar with drag regions, the tray, deep links, Playwright attached (over the debugging port or the candidate's replacement), plus resident memory and size on disk. The candidate that passes the list with the best measured memory and size is taken without asking the owner again; a fork only the owner can decide goes to him as a question.
- **People on the Electron app move by the ordinary automatic update** (the owner's rule, 12 Nov 2026): nobody downloads or installs again. It is on the prototype's pass list for every candidate, on both platforms, measured from the released Electron app of that day: its updater (`app-updater` rule › Install modes) finds the new version, installs it and relaunches into the new shell with nothing the person does. What the move must keep, each one checked in that run:
  - The update path itself: the same release asset names (`ompdesk-mac-arm64.dmg`, `ompdesk-windows-setup.exe`) and the `<!-- ompdesk-update … -->` metadata the Electron updater reads; macOS's relaunch swap (`stageBundleFromDmg`'s `codesign --verify`, bundle id and version checks, `SWAP_SCRIPT` with its rollback); Windows' NSIS install over the existing one. If the new shell cannot ship in that form, the last Electron release (the handoff release) learns the new form first, and only then does the new shell ship.
  - Identity: macOS the same bundle id `com.seuput.ompdesk`, signed with the same certificate (AGENTS.md › Signing: the designated requirement, so privacy grants survive) and replacing `/Applications/OMPdesk.app` in place; Windows the same app id, install folder and uninstall entry, so no second copy appears.
  - Data: the same userData folder (`ompdesk`), read as it is (prefs, tab layouts, sessions' snapshots, `deleted-sessions.json`, disk care and update state), and what Electron's `safeStorage` encrypted (the "ompdesk Safe Storage" keychain item on macOS, DPAPI on Windows: the GitHub update token, mail account passwords and the like) decrypted by the new shell, or each such secret asked for once again with the reason shown; never silently lost.
  - Failure: a move that fails leaves the Electron app installed and starting as before (the swap's rollback, the next launch's `swap result` log line).
- **Workspace** (`native/ompdesk/`): one cargo workspace, `crates/*`, toolchain pinned in `rust-toolchain.toml` (1.95, as `native/memory`), `Cargo.lock` committed, edition 2024. `unsafe_code = "deny"` for the workspace; a crate's one `sys.rs` may allow it for OS calls, each with a `// SAFETY:` line. `clippy::all` denied. Release profile: fat LTO, one codegen unit, stripped, `opt-level = "s"`, unwinding kept. Dependencies stay few and are named in the crate's `Cargo.toml` with the reason when not obvious; `native/memory` (the vendored ai-memory) is a separate workspace and is never mixed in.
- **Build and staging** (`scripts/build-native.ts`, `bun run build:native`): `cargo build --locked --release --workspace`, then each binary of `BINARIES` into the gitignored `resources/ompdesk-bin/<platform>-<arch>/` with `ompdesk.build.json` (each binary's SHA-256, the SHA-256 of the workspace's sources, rustc, when). `--check` holds the staged bytes to the record and the record to the sources; `--ensure` (and `ensureNative()` for a test) builds only when that check fails, so a run with a fresh staging never calls cargo. `bun run build` stays TypeScript-only (`out/` is one artifact for every OS); `bun run dev` builds native first. Rust is a development requirement (`scripts/cargo.ts` finds `cargo` on PATH or in `~/.cargo/bin`).
- **Packaging**: `extraResources` `resources/ompdesk-bin/<key>` → `ompdesk-bin` in both builder configs; `scripts/after-pack.cjs` `checkNative` fails the package unless every binary of `NATIVE_BINARIES` is there, executable and the bytes the record names. macOS signs it with the app (`scripts/mac-sign.cjs` signs every Mach-O in the bundle); Windows ships it unsigned like the app. Pinned by "native binaries" in `packaging-config.test.ts`.
- **CI**: `.github/actions/install` restores `resources/ompdesk-bin` from a cache keyed by the sources (`native/ompdesk/**`, `scripts/build-native.ts`, `scripts/cargo.ts`) per OS and architecture for every job that takes Electron; a miss installs the pinned toolchain, builds and saves; a hit only runs `--check`. Both `ci.yml` and `release.yml` run `native` on Linux, Windows and macOS arm64: `cargo fmt --check` on Linux once, `cargo clippy --all-targets -- -D warnings` and `cargo test --workspace` on every OS, using `rust-toolchain.toml` and the native cargo cache. `mac-native` runs the real-binary vitest parity suites for the process, lock fence, session index, memory sampler, git changes/scm/worktree/gh and every `disk/*.test.ts`. Pull requests keep the Linux-only policy. There is no per-job path filter, so these jobs run on every eligible workflow run; docs-only and release-push skips stay unchanged.
  - The macOS parity list also runs `session-processes.test.ts` (3d: `KERN_PROCARGS2` and the kill on real processes), `control-socket/{server,router,events,cli}.test.ts`, `checkout-peers*.test.ts`, `git-fingerprints*.test.ts`, `ai-memory/freshness*.test.ts` and `routines/*.test.ts`, covering the control listener and the remaining git readers as their ports land.
- **Licenses**: the crates a binary links are listed in `LICENSES/ompdesk-native-dependencies.txt` (`bun scripts/gen-crate-notices.ts`, needs cargo and the crate sources), embedded in `THIRD_PARTY_NOTICES.txt`; `bun run licenses:check` fails when `native/ompdesk/Cargo.lock` changed without regenerating.
- **A port keeps behaviour**: what a person, a script or the page can observe (output text, exit codes, wire frames, file formats and modes) is the same after a unit unless its ledger line names the difference. The TypeScript tests of the moved code are the specification; they become Rust tests of the same cases.

### Ledger

- **1. `ompdesk` CLI** (`crates/cli`, binary `ompdesk`; was `resources/cli/ompdesk.ts` run by Bun): same commands, flags, output and exit codes; it no longer needs Bun on the machine, so the launchers (`cli-install.ts`) run the binary by its absolute path. The wire contract moved to `src/shared/control-protocol.ts` (main's side) and `crates/cli/src/protocol.rs` (the CLI's); `CONTROL_PROTOCOL_VERSION` is spelled in both and `cli.test.ts` runs the built binary against main's own server.
  - Measured (11 Nov 2026): 743 invocations run through both programs against one fake server (every command and flag, stdin forms, number forms, error codes, events, the owner checks); 690 gave the same request bytes, stdout, stderr and exit code.
  - Differences kept on purpose: an interrupt during a command other than `events` ends the process at once (the TypeScript swallowed the first one); `events` stops when nobody reads its output (`ompdesk events | head`), where the TypeScript ran on; an ended `events` prints no second `OMPdesk closed the connection` line; the operating system's wording inside `OMPdesk is not running (…)`; a command named like a JavaScript object member (`toString`) is an unknown command.
  - Differences that only a fake server or hand-written JSON shows: numbers in `--json` output and in JSON a person passes (`call`, `app`, `--answers`, stdin) keep the spelling they came with (`1.0`, `1e3`, a 20-digit integer) where JavaScript rewrote them, and keys keep their order where JavaScript moved integer-like keys first; half a surrogate pair reads as U+FFFD (`json.rs`); JSON nested deeper than 128 levels is refused as input and, as an answer, ends the wait with `unavailable`.
- **2a. Workspace files** (`crates/core/src/fs/`; was the logic of `src/main/workspace-fs.ts`): the Files panel's listing, text, binary, range and image reads, the plan file, the folder picker's level, stat and the panel's writes are `fs.*` methods of the core. Main keeps argument checks and path resolution with node's `path` (`resolveWithin`, `resolveReadPath`, both synchronous for their callers), MIME sniffing (`sniffMime`, one copy; the core sends the head bytes) and the move to the trash (Electron's; the core validates and answers what to trash). `workspace-fs.test.ts` runs its 43 cases unchanged through the process.
  - Kept exactly, with tests: listing order (`Intl.Collator(undefined, {numeric: true})` is ICU4X `icu_collator` with the locale main resolves; names ICU ranks equal fall back to byte order, as libuv's scandir gives them; `workspace-fs-order.test.ts` compares 50 awkward names in seven locales), the gitignore subset (a matcher over UTF-16 units; 76 pattern/path pairs captured from the TypeScript), node's error texts (`CODE: description, syscall 'path'`), text decoding at the byte cap (16 captured sequences), `mtimeMs` as node's double.
  - Differences: a call that takes over 30 s fails where the TypeScript waited; a crashed core is a failed call with a message and no code; JSON carries no infinite number, so `maxBytes: -Infinity` reads the whole file (or is `file_too_large`) and a write's `expectedMtimeMs: ±Infinity` is `invalid_path`; a lone surrogate in a path reads as U+FFFD; `readWorkspaceImage` reads a non-image under 25 MB whole before refusing it; a folder whose name is not UTF-8 is listed on POSIX; a save in a workspace that is a volume's root (`/`, `C:\`) works, where the TypeScript refused every one as escaping (`mutate.rs` `within` compares whole path components).
  - Measured (12 Nov 2026, this repository's root, five alternating runs, load 4.45 on 10 cores): the default listing (2 000 files) 5.6 ms → 5.4 ms, no measurable difference; the full listing (5 103 files) 21.8 ms → 19.6 ms. Both walk one folder at a time, which bounds them; the first request also starts the process (26 ms).
  - CI coverage: `win-platform` runs `workspace-fs.test.ts` against the real Windows binary, including the Win32 error table, reparse points, `\\?\` in messages, mtime and `same_file`; `native` runs the Rust tests on all three OSes.
- **2b. Git's read side** (`crates/core/src/git/`; was `src/main/local/git/changes.ts` and the parsers only it used): the checkout root, `get_git_status`, `get_git_changes`, `get_git_fingerprint`, `get_git_diff` and the source-control head are `git.*` methods of the core. Main keeps how git runs: `gitRunner` (`exec.ts`) hands every request the binary (`resolveBin`/`developerGit`, cached there), the argument prefix, the whole environment (selectors dropped, login-shell PATH, `GIT_OPTIONAL_LOCKS=0`), the 60 s timeout and the 8 MiB cap, the rules main's `gitRaw` follows for the write side; the core only spawns and supervises (SIGTERM, SIGKILL 2 s later; `crates/core/src/sys.rs` is the crate's one unsafe file). Main also keeps the diff path's check (`isSafeRelativePath`), the repository-lock fence around each request (`currentStepSignal`, `trackEffect`) and the path guards its write side uses (`isInside`, the rest of `parse.ts`; `parseGitStatus` moved in 2h): the core reads porcelain v2 and lists it in v1's order. `changes.test.ts`, `git-env.test.ts`, `scm*.test.ts`, `git-fingerprints.test.ts` and `repo-lock-fence.test.ts` run through the process; the cases of `parseStatusV2`, `newFileDiff` and `parseBranchHeaders` are Rust tests.
  - Kept exactly, with tests: answers captured from the TypeScript on 12 folders (renames, copies, conflicts among changes, intent-to-add, type change, symlinks in and out, a non-UTF-8 index path, CRLF, binary, over 4 MiB, unborn, detached, rebase, upstream and stash, no repository, a missing folder) are equal but for the differences below; the timeout text (`-c timed out after 60000ms`), node's `spawn <bin> ENOENT`, git's stderr as the message.
  - Differences: a diff cut at 200 000 UTF-16 units through a surrogate pair ends in U+FFFD (the TypeScript kept the lone half); the fingerprint is a 16-hex SipHash, compared only with this app's own answers; containment is by whole components, so a changed file at the root named `..x` shows its diff; a read fails with `ompdesk-core …` when the core cannot answer and gets `rounds × 60 s` plus slack in all.
  - Measured (12 Nov 2026, this repository, 24 changed files, five alternating runs, load about 5 on 10 cores): `getGitChanges` 41.0 → 40.8 ms median, `getGitStatus` 19.4 → 19.4 ms, no measurable difference. git bounds both: `status` alone 19.1 ms; the changes read's second wave runs seven gits at once, `diff --numstat` alone 24.6 ms; `gitRunner` and the core round trip with its 4 KB environment cost 0.1 ms each.
  - CI coverage: `win-platform` exercises `git.exe` spawn, `CREATE_NO_WINDOW`, case-insensitive environment names and `\\?\` real paths in the trusted-root check. `mac-native` runs `changes.test.ts` against the macOS core; `native` runs the Rust tests on all three OSes.
- **2c. Git's write side** (`crates/core/src/git/scm.rs`; was the logic of `src/main/local/git/scm.ts` and `parseDecorations`, `remoteWebBase`): stage, unstage, discard, commit, undo, push/pull/fetch, stash, continue/abort, branches and branch actions, the log, a commit's files and diff, the history actions and the commit message's staged check are `git.*` methods, each one request that runs its whole sequence of gits in the core. Main keeps the checkout root and the repository lock around each mutation (`requireRoot`, `mutate`, `withRepoLock`), the checks of what the page sent (`checkPaths`/`isSafeRelativePath`, `checkRef`/`isValidRefName`, `checkSha`, an empty message, a reset mode) and the trim of typed text, discard's removal of the untracked paths the core answers (`fenced-fs`), the commit message's omp call with `parseGeneratedMessage`, and the timeouts (`slowMs` names a request's one slow git). Every core git request, reads included, goes through `coreGit` (`exec.ts`): a stopped lock step sends `{"cancel": id}` (`process.ts` → `server.rs`), the core ends the git it runs (SIGTERM, SIGKILL 2 s later) and starts no other, and answers only once every git of the request exited (each git's supervisor holds the request's `Scope`); main keeps that answer (`onEnded`, also after its own timeout, which now cancels too) as the step's tracked effect. The gits die with the core: on POSIX main spawns it detached (a process group and session of its own, never `unref`ed, still ending at stdin's end), and when it ends main SIGKILLs the group and settles what waited only once `kill(-pid, 0)` says the group is gone (`GROUP_GONE_MS` 3 s; past it, an error that says git processes of the dead core may still run, logged); on Windows the core joins a `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` job at start (`sys.rs`, which now also holds the crate's hand-declared kernel32 calls `CreateJobObjectW`, `SetInformationJobObject`, `AssignProcessToJobObject` and `GetCurrentProcess`; a failure is logged and the core runs on); `stop()`'s 5 s kill takes the group or the job. The core reads porcelain v2 for the conflict count and the discard (`parseGitStatus`'s last caller moved in 2h and the TypeScript parser was deleted); `git.head` is no longer a method. `scm.test.ts`, `scm-history.test.ts` and `repo-lock-fence.test.ts` run through the process; the cases of `parseDecorations` and `remoteWebBase` are Rust tests, with 32 URLs captured from the TypeScript. TLA+ model `formal/repo-lock-core` (`.omp/skills/repo-lock-core-verify`).
  - Kept exactly, with tests: 139 steps captured from the TypeScript on deterministic repositories (every read and write, each refusal and its code, conflicts, a rejected push, a conflicting and a refused pull, a fetch from a gone remote, stash pop conflicts, history moves) give the same answers, messages, codes and repository states; a stopped holder's git is ended and the next holder starts after it exited (`repo-lock-fence.test.ts` "scm commit in the core…", which fails with the cancel removed); a core killed mid-request, or by `stop()`'s kill, takes its git with it before what waited settles and before the lock's next holder starts (`process.test.ts` "a core that ends while a request runs its git", a node stand-in for git so it runs on Windows too; it failed before the process group); the remote's web base by the WHATWG URL standard (`url` crate), as node's `URL`. Probed (`formal/repo-lock-core/evidence/session-probe.log`): in the core's own session a credential helper, `GIT_ASKPASS` and `GIT_TERMINAL_PROMPT=0` answer as before.
  - Differences: between a stop in main and the cancel's arrival in the core the request may start its next git (ended at once; `execBin` refused it); a stopped read is cancelled too (2b first let its git run to its end); a dead core's requests settle once its process group is gone (up to 3 s later), and a git that survives SIGKILL that long is settled past with "git processes it started may still run"; the gits of an app started from a terminal no longer have that terminal (an ssh passphrase prompt that went to it now fails or goes to `SSH_ASKPASS`; a packaged app had none); the lock's busy message names the request (`git.commit`); a request whose concurrent gits fail answers once all of them ended; a NUL in a typed message or query fails as `spawn <git> UNKNOWN` (node: "must be a string without null bytes"); a log `limit` or `skip` that is no finite number counts as absent; an invalid base or new name of a branch action is refused before the branch list is read; a commit diff cut through a surrogate pair ends in U+FFFD; the reorder's temp folder is removed also when its request is cancelled; each core git request waits `rounds × 60 s + slow + 7 s` (2b's reads: +7 s instead of +5 s).
  - Not measured: speed (git bounds every command; one round trip replaces each command's sequence of spawns).
  - CI coverage: `win-platform` checks the job object with `process.test.ts` "a core that ends while a request runs its git" (main has no group to wait on there, so it relies on the job ending the gits before the core's `close` reaches main), `git.exe` spawn/cancel and the reorder's `cp` through Git for Windows' sh. `mac-native` runs the process-group and lock-fence cases plus `scm.test.ts`; `native` runs the Rust scm tests on all three OSes. The POSIX-only lock-fence case stays skipped on Windows.
