## Build, test, CI

### E2E

- Run: `bunx playwright test`. `playwright.config.ts` sets `OMP_GUI_HEADLESS=1`: windows are transparent, click-through, off the Dock/taskbar and never focused; the app creates no menu-bar tray item and never registers the `omp://` handler (both belong to the user's installed OMPdesk). It posts no OS notification (`holdTestNotifications`, `src/main/app-icon.ts`: `Notification.prototype.show` is a no-op, so a spec that wraps it still sees each one), because macOS files it under node_modules' Electron.app in the user's Notification Center. Tests never cover the user's screen or rewrite their LaunchServices state. Set `OMP_GUI_HEADLESS=0` only when you must watch.
- Fake vs real omp: `e2e/real-core.e2e.ts` and `e2e/deep-audit.e2e.ts` run against the real system omp (isolated agent dir, no credentials). Every other suite uses the fake omp in `e2e/sidecar-fixture.ts`, installed per test by `fixtureOmp()` (`e2e/harness.ts`; an `omp.cmd` shim on Windows) and passed as `OMP_GUI_OMP`. It speaks stock `--mode rpc-ui` and serves the gui-bridge methods those suites reach on `OMP_GUI_BRIDGE`.
- Tear apps down with `exitApp()` (same file; it kills a main process that does not act on the exit within 10 s). On Windows it then waits (`e2e/process-tree.ts`) for every process the app started (Chromium's helpers, omp, its MCP servers, git) and kills one still running after 10 s, because a process holds the folder it works in and the launcher exits before them (a following `fs.rm(profile)` failed `EBUSY`). Shortcuts in tests use `ControlOrMeta`. A path inside a CSS attribute selector goes through `cssString()` (`e2e/harness.ts`): a raw Windows path's backslashes read as CSS escapes.
- **A test app never outlives its worker**. Playwright's exit handler is the only thing that ends an app it launched; a worker that dies without running it leaves the app running under Playwright's `cmd.exe`, and stdin cannot tell (Electron's main process on Windows has an empty `process.stdin`). `playwright.config.ts` sets `OMP_GUI_TEST_LAUNCHER_PID` to each runner's and worker's own pid, `appLaunchOptions` (`e2e/harness.ts`) puts it in every `launchApp` env, and main (`src/main/test-launcher-exit.ts`) exits once a once-a-second check finds that pid gone (it removes the variable from its environment, so nothing it spawns inherits it); a spec that builds its own env keeps the variable by spreading `process.env`. Pinned by `e2e/app-lifetime.e2e.ts` (launcher dies without handler: app, helpers and omp gone).
- **A test run leaves nothing in the temp folder** (`scripts/run-temp.ts`; Vitest and Playwright, every platform), by where the run writes and not by each test remembering to delete. Each runner's config calls `claimRunTemp()` before any worker starts (`playwright.config.ts`, `vitest.config.ts`): it points TEMP, TMP and TMPDIR (and `MAC_CHROMIUM_TMPDIR`, which Chromium on macOS asks first) at a folder of the run's own, `ompdesk-run-<pid>-XXXXXX`, so every `mkdtemp` a test never removes, each spec's profile, Playwright's own files, the app's Chromium folders and whatever apps, fakes and real omps write land there by inheritance. When the runner exits, however the run went (tests that crashed, a `globalSetup` that failed, a `--list`), it ends every process whose command line names the folder (the detached fake ai-memory server included), removes it and, when tests had left something in it, says what in one `[run-temp]` line on stderr; on a hosted runner a second line counts what appeared in the real temp folder meanwhile (writers that ask the system, not the environment). A runner that was killed leaves its folder to the next runner of either kind, which clears it as it claims its own: the name carries the owner's pid, so claiming is one atomic `mkdtemp` with no ownerless moment, and a folder whose pid no longer runs is cleared; a reused pid only delays that. A run inside a run (a test that starts Playwright) inherits the outer folder and never removes it. On macOS the folders are made in `/private/tmp`, not the per-user `/var/folders/…/T`: that path takes 48 of the 103 bytes a unix socket path may have, and a run folder inside it leaves the control socket's short fallback (38) and Chromium's singleton socket (43) no room. What must outlive a run (the compiled fake `gh` launcher, opt-in evidence folders, the lock's root on Windows) and a test that needs the real temp folder (a path-length case, a rename across devices) say so with `baseTemp()`, which the real-home guard exempts. Still outside the folder: `playwright-transform-cache`, one folder Playwright makes before it loads the config and reuses in every run. `bun scripts/temp-leftovers.ts <command…>` counts what a command leaves (it gives the command a temp folder of its own, because other sessions write to the real one). Pinned by `scripts/run-temp.test.ts`.
- **The fake ai-memory server ends itself** (`e2e/fixture/fake-ai-memory.ts` `serve`): it is detached like a real service, so nothing ends it before the runner's exit does. It checks once a second and exits when its data dir is gone (the spec's teardown) or the worker that installed the fake no longer runs (`FAKE_AI_MEMORY_OWNER_PID`, baked into the launcher by `fixtureAiMemory`).
- **A fake omp ends with the test that wrote it** (`DIES_WITH_TEST`, `src/main/test-fake-omp.ts`; `exitWhenGone` in `scripts/vitest-orphan-guard.ts`). `writeFakeOmp` writes every fake omp (unit tests and `fixtureOmp` alike) as an entry `omp.ts` that arms it and only then imports the test's source from `body.ts` beside it, because in one file it ran after the source's static imports, and a source that awaits forever there (`sidecar-fixture.ts`'s `stats` and `-p` modes) never armed it. A long-lived process a unit test starts itself (an idle stand-in, a SIGTERM-ignoring child, an installer's grandchild) begins with it too. It checks every 2 s whether the process that wrote it still runs and exits once it does not, so a killed or crashed Vitest or Playwright worker leaves none behind. It watches the writer, never its own parent: an app the spec kills (SIGKILL) must still be what stops its fake through stdin, so the app's stop stays tested, and on Windows the fake's parent is the `omp.cmd` shim's cmd.exe, which outlives the test too. A process the guard cannot run in (one kept stopped with SIGSTOP) is only ended by its test's own teardown.
- Fake omp layout: `e2e/sidecar-fixture.ts` only reports the version (`fixture/version.ts`) and dispatches in stock's order: `--version`, `stats` (`fixture/stats.ts`), `update --check` (`update-check.ts`), `worktree … --json` (`worktree.ts`), `-p` (`print.ts`), then `--mode rpc-ui` (`rpc-ui.ts`: stock RPC plus every gui-bridge method the suites reach; one closure, because its fake session state is shared by every command). A new fake RPC command or bridge method goes into `rpc-ui.ts`; a new CLI invocation into its own `e2e/fixture/` module and the entry's dispatch. A fixture branch no spec uses any more goes with the spec that used it.
- With `OMP_GUI_TEST_SESSION_FILES=1` the fake's journal is a stock-shaped session file: a new session writes `sessions/fixture/fixture-<pid>.jsonl`, and a stored file that `--session` or `switch_session` opened keeps its header and takes every later entry, as stock's `SessionManager.open` does (`e2e/fixture/rpc-ui-session-file.test.ts`). Writing it elsewhere makes a relaunch's continued turn a second session the sidebar lists beside the first.
- Two shared steps a spec never re-implements (`e2e/harness.ts`): `dragTabToPane` splits by dragging a tab's sidebar row onto a pane edge, naming the tab with a `fixture:title:` shell line first, since a fresh tab has no row until something is typed into it (`unstarted`, Sidebar.tsx). `untilAnswered` waits for a tab's transcript to hold the fake's reply: never read an agent-opened child's `lastRun.reply` or last answer for it, because main asks a child whose turn ended with no `Result:` line and no report to report (`#nudgeSilent`, about a second after the turn) and the fake's "Read the note report from …" then follows; `after` waits for the reply to a later message, and an `ompdesk_compare` `final answer:` is either reply.
- **No build, no run.** Electron with a missing entry opens a native "Error launching app" dialog on the user's screen for every test, and `OMP_GUI_HEADLESS` does not stop it. `playwright.config.ts`'s `globalSetup` (`e2e/global-setup.ts`) resolves `<OMP_GUI_E2E_OUT ?? out>/main/index.js` once (`scripts/e2e-app-entry.ts`) and fails the whole run before any worker starts ("No build: … Run `bun run build` or `bun run check:changed`"). `launchApp` (`e2e/harness.ts`) asserts the same before `electron.launch` (covers a spec run with a custom config); a spec that calls `electron.launch` itself uses `assertAppBuilt()`. Pinned by `scripts/e2e-app-entry.test.ts` (empty `OMP_GUI_E2E_OUT`: fast non-zero exit, no process on that path). Never run Playwright in a fresh worktree before `bun run build`.
- Specs launch `path.resolve(process.env.OMP_GUI_E2E_OUT ?? "out", "main/index.js")` (a new spec does the same, or uses `launchApp`); see Lock and gate for why the path is a snapshot.
- Env-gated specs and helpers:
  - `e2e/performance.e2e.ts` runs only with `OMP_GUI_PERFORMANCE=1` (optional `OMP_GUI_BASELINE_DIR` compares another built checkout); CPU and compositing budgets run only with it.
  - `e2e/load-performance.e2e.ts` runs only with `OMP_GUI_LOAD_AUDIT=1`: five fake-omp tabs streaming at once (a long reply, two bash outputs, two task calls with `OMP_GUI_LOAD_AGENTS` subagents; fake omp knobs `OMP_GUI_TEST_WORK_AGENTS`, `fixture:work-ticks`), then 10 s windows watch / away (unfocused) / switch (⌃⇥ timed to the shown pane, plus scrolling) / pressure (`OMP_GUI_LOAD_BUSY` busy loops, default one per core). Reports main's event-loop delay, CPU per process, frames, IPC and omp reads per switch, the generator's ticks; `OMP_GUI_BASELINE_DIR` interleaves a built checkout, `OMP_GUI_LOAD_RUNS`, `OMP_GUI_LOAD_OUT`, `OMP_GUI_LOAD_MAIN_PROFILE` (main's CPU profile per window), what-if `OMP_GUI_LOAD_CSS` / `OMP_GUI_LOAD_AWAY_SCRIPT`.
  - `e2e/real-startup.e2e.ts` registers only with `OMP_GUI_REAL_STARTUP=<dir>`: the built app on the user's installed omp (a private copy of `~/.omp/agent`'s config, extensions and databases plus the two largest sessions written this week), per run the main startup marks (`omp-spawned` included), the window's boot skeleton, layout, first row and composer, and a session opened in a new tab with and without its transcript snapshot. `OMP_GUI_REAL_STARTUP_SUBJECTS=before=<root>,after=<root>` interleaves built checkouts, `OMP_GUI_REAL_STARTUP_RUNS` (default 5); writes `results.json` and `summary.md` (median and range) to the dir. No model is called.
  - `e2e/event-replay.e2e.ts` runs the fake omp with `OMP_GUI_TEST_REPLAY_FRAMES=1` (every message and tool frame sent again behind the next one) and main with `OMP_GUI_TEST_BATCH_INTERVAL_MS=400`, so snapshot loads overtake held frames. `src/renderer/hooks/event-replay.test.tsx` is its seeded unit counterpart. Renderer stores apply a frame for a message or call they already hold (by stock timestamp and call id) as a no-op.
  - `OMP_GUI_TEST_INSTALLER=<executable>` (when it turns on automatic setup: see machine-setup-updates › Machine setup) replaces every install plan with `<executable> <item> <method>`. `e2e/machine-setup.e2e.ts` uses it with `OMP_GUI_OMP` naming a not-yet-existing fake omp (missing omp → install fails → Retry → detected → the tab restarts ready); `OMP_GUI_SETUP_CAPTURES=<dir>` adds its captures. Real installs never run in a test against the user's profile: `scripts/setup-install-check.ts` runs the real Bun installer, PortableGit (Windows) and `bun install -g` omp in a child with a temp HOME/USERPROFILE and BUN_INSTALL, checks `omp --version` against the minimum, and deletes the temp dir.
    - A spec that keeps setup from installing an item at launch seeds its back-off with `seedSetupBackoff` (`e2e/harness.ts`), never a hand-written `setup-state.json`: the ledger counts only misses stamped with the running version (`app`), which for the built app launched as a script is Electron's own; an unstamped seed reads as an older version's miss.
  - Opt-in model audits (`OMP_GUI_REAL_WORK=1`, they spend tokens): `e2e/real-work-map.e2e.ts`, `e2e/real-work-scenarios.e2e.ts` and `e2e/real-advisor.e2e.ts` (asserts each custom message an `agent_end` commits, advisor card or background job result, carries its journal `entryId`, which the sidecar's `sessions.attach_entry_ids` stamps, and that its card is in the live transcript; `e2e/fixtures/real-advisor-frames.json` is a trimmed recording). All copy `config.yml` and `agent.db` into a private 0700 agent dir through `e2e/real-omp.ts` and run the main model on the user's `smol` role; `OMP_GUI_REAL_WORK_ARTIFACTS` picks the capture directory.
- **Tiers.** `@smoke` (the tag in a test's title) runs on every release's `mac` and `win` packaging jobs against the build they just made; it is the only e2e a release waits for. The default run (`bunx playwright test`) is the full suite: locally on demand (`bun run gate`; `check:changed` picks specs from it), on hosted runners nightly and on demand (`e2e-nightly.yml` and ci.yml's `e2e=true`, both through `e2e-shards.yml`; informational, never a release block).
- **Variants and captures are opt-in.** `variants(all, keep?)` in `e2e/harness.ts` keeps one variant (en light; for the mobile matrix one engine × device per shell mode) and does not register the rest unless `OMP_GUI_VARIANTS=1`, so they neither run nor show as skipped. `OMP_GUI_*=<dir>` capture tests register only with their dir set.
- **Rules for a new e2e.** No theme, language or size variant matrix as blocking tests (en light runs, the rest goes behind `variants()`). Prefer a unit or component test (vitest with linkedom) for anything that needs no real Electron window, Chromium layout, real processes or the wire between them; an e2e asserts a flow across those, and its header names the component tests that cover the rest. To move an e2e down, write the unit case first, confirm it fails when the behaviour breaks (break the guard, run it, put the guard back), then delete the e2e and any fixture branch only it used.
- **Parallelism.** Locally Playwright runs at most 4 workers, fewer on a machine under 32 GB of RAM or beside other runs (Lock on a small machine › **Workers**, Lock and gate; `OMP_GUI_WORKERS` overrides; 1 on GitHub's runners, `GITHUB_ACTIONS`). Every test launches its own app on `mkdtemp` userData, agent dir and fake omp, with ephemeral ports (a fresh bridge socket per spawn), so a new spec never uses a fixed path, port or shared profile. A remote spec's host and client share one free port from `makeRemoteProfile`; a parallel test may hold a successor of it, so never assert the exact successor. That port comes from `freePortRun` (`src/main/remote/test-ports.ts`), which walks a band of 500 ports per parallel worker (Playwright `TEST_PARALLEL_INDEX`, Vitest `VITEST_POOL_ID`) run by run, never at random from one shared range, because every app on the machine sees the others on 127.0.0.1 and two touching picks send a device to another test's host (`[remote_key_mismatch]` in `remote.connect`). `test-ports.test.ts` pins the bands.
  - The suite is bound by its total work, not its slowest test: all workers stay busy to the end and apps running at once slow each other down. A launch on the fake omp is cheap (about 1 s, 2 s on a hosted runner), so sharing an app between tests saves little; fewer tests is the lever. Split a long test into tests that run side by side only while it ends the run.
  - `e2e/deep-audit.e2e.ts` (`mode: "parallel"`) splits its settings rows by measured cost over `SETTINGS_SHARDS = 3` apps (more shards add work without cutting wall time). The cap stays at 4 workers, because 5 or 6 were barely faster at more load.
  - `MEASURED_SECONDS` in `scripts/e2e-shard.ts` holds per-spec costs for the shard dealer, measured on the hosted macOS runner with one worker (a nightly's per-test times summed per file), never locally with several workers, which understates a spec several times over.
- **Responsive audit.** `e2e/responsive-audit.ts` (engine), `e2e/responsive-surfaces.ts` (named surfaces), `e2e/responsive-audit.e2e.ts` (the matrix), `e2e/responsive-smoke.e2e.ts` (the default run). It visits the dev harness (`src/renderer/harness.html`; `?stress=1` overflow-prone turns, `?host=1` a fake web host so host sheets mount, `?pwa=push|ios`, `?platform=darwin|win32` paints the page as that OS's Electron window: desktop layout, no mobile shell; `window.__stores` exposes the ui/toast/extension-ui/plan/updater/host-ui stores so a surface opens the way a click would) at 48 looks: touch phones 320/360/390/412, tablets 768/834/1024 (portrait and landscape) and iPads sideways 1133/1180/1366, then desktop windows 1100/1280/1440/1920 with a mouse, once as the web client (column `W`) and once as the Electron window (`E`); en and ko, light (dark at 390 and 1280), with simulated safe areas (`--safe-*`) on touch looks. A surface that shows a panel's error boundary (`PanelErrorBoundary`, `data-panel-crashed`) or the root crash screen fails with its message.
  - Each surface reports page overflow, escaping elements, truncated controls, clipped text, off-screen popovers, hit boxes under 44 px (a list row under the shell's `--sc-row-touch`, 36 on a phone; 36 on a field or a cluster that declares `--hit-gap-*`), text under 11.5 px, overlaps, stolen taps and content under the insets; hit areas, stolen taps and insets only on touch looks. Every audit page carries the stress turns, the reply showcase (`dev-harness/reply-showcase.ts`) among them, so `session-idle` measures every reply component too.
  - Small text by meaning is not small text: a `<sub>`/`<sup>` (a footnote marker too) and a formula's script levels (KaTeX's `.mtight`) read as body text at the floor; a reply's `<kbd>` and inline code are words to read and keep the phone's 12 px floor (`mobile.css`).
  - Not measured or not a finding: anything covered by a layer (judged at the centre of its on-screen part) or scrolled out of its scroller; a popover or toast inside a scroller is judged by what the scroller lets through on each axis it scrolls (a fixed box, or an absolute one whose containing block sits above the scroller, escapes it; pinned by "a scroller lets through only what it scrolls" in `responsive-smoke.e2e.ts`); a menu, popover, sheet or toast over a control covers it rather than stealing or colliding; the drawer's edge strip is looked through (it hands taps on); a control drawn inside a field's box is the field's adornment; a list row's own actions over its title, whose ::after stretches over the row (ListRow's ⋯), are layered, not an overlap; a text editor (CodeMirror's contenteditable) is a field, its hit box its own; a checkbox or radio inside its label is measured by the label's box and reach; a point outside its clipping ancestors is no tap of the control's; a control with `pointer-events: none` is no target (a tree row's chevron on touch, `TreeView`: a row with children and no action of its own toggles them, so the whole row is the target); a point past the curve of a clipping ancestor's rounded corner (per ancestor and corner, `e2e/rounded-outline.ts`) taps nothing drawn and counts for no one, while a point inside the curve still counts.
  - **No key between surfaces.** `resetPage` closes what a surface left open by its own means (the ui store's open flags, cards, toasts, the plan, host sheets, the update banner, the draft with its `/` and `@` menus; the transcript follows its end again), sends Escape only to a layer still open, which claims it, and moves the mouse off the page (a click's hover on a control the next surface moves under it showed its tooltip); never a key to the page or the composer, where an Escape on an empty field is the composer's double Esc (`doubleEscapeAction`: the fork picker opened over the next surface and twelve surfaces were measured under it, 10 Nov 2026). `openSurface` (the matrix and the smoke) fails a surface whose `ready` part left the screen while it settled, lies under a layer it did not open (named), or sits under the dev server's compile-error overlay. The audit's and the smoke's dev servers run without hot updates (`hmr: false`): another checkout's edit saved mid-run remounted the transcript and put a scrolled surface back at its end. A surface finds a control by its words in the look's language (`say`, the locale files), sets its scroll in its own `open` (the reset re-pins the transcript), and its `when` leaves out looks where the product never shows it: `board-strip` where the board docks (`board-strip-open` covers the docked board), the host sheets in the Electron window (`WebHostUi` renders nothing there), the install steps off touch; `prompt` guidance has no sheet (the browser's own prompt opens). Text made only of zero-width characters (KaTeX's 1 px `vlist-s` strut) is no text to measure.
  - Soft-keyboard surfaces (`composer-keyboard`, `composer-keyboard-slash`, `dialog-rename-keyboard`, portrait touch looks) shrink the layout viewport as Chrome on Android does, and the home bar's inset is dropped while `html[data-kb="open"]`.
  - `OMP_GUI_AXE=<dir>` (`e2e/axe-surfaces.e2e.ts`) runs axe-core and a Tab walk (every stop must draw a focus ring; `tokens.test.ts` also refuses Tailwind 4's `outline-none` beside `focus-visible:outline-2`, which draws none) over the same surfaces on the dev harness, one test per look (`OMP_GUI_AXE_LOOKS=<width>-<theme>-<lang>,…`, 390/412 a phone and wider the Electron window; default 1280 light and dark en, 390 light ko and dark en; `_ONLY=<regex>`), writes `<look>.json` and fails a look on any violation or a surface that did not open; rules that cannot hold are listed in the file with their reason (`region`, the composer's combobox).
  - `OMP_GUI_RESPONSIVE=<dir>` (plus `_WIDTHS`, `_LANGS`, `_THEMES`, `_ORIENT`, `_DEVICE=touch|web|electron`, `_AREA`, `_ONLY=<regex>`, `_SHOTS=all|none`) writes `report.json`, `summary.md` and `shots/`. Run it one look per `bun run locked` hold (`-g "responsive 390P-light-en$"`) with `--trace off --output <private dir>`: a Playwright locator action has no default timeout (the audit sets 8 s) and a shared `test-results/` is wiped by other agents' runs.
  - The default smoke (390 + 834, en light) refuses page overflow, an escaping element, an off-screen popover and, at 390, an app chrome above 19.4 % of the screen. It also pins: at 390 and 834 no stolen tap, overlap or inset finding on fourteen key surfaces (the feedback and worktree dialogs' checkbox and radio rows, a question card and a figure header among them) and two host sheets; a question card's step tabs and a figure header's buttons as 36 px targets; whole summary figures on a work card and 36 px controls in a docked tablet sidebar; a tap on the drawer's edge strip reaches the PR row under it; a 1100 px Electron window keeps Settings › Memory's tabs clear of the project picker and cuts no Run popover choice; an Autopilot run's board (1133 docked, 390 in the strip) never scrolls sideways, its controls are 36 px targets and the goal bar's Pause, Edit and Drop keep their taps; the transcript never scrolls sideways (`overflow-sideways` covers `.omp-transcript-scroll` and names the element that widens it) on every look, and an 800 px dark and a 1280 px Electron window check it on the session and the reply showcase's text, tables and code (the showcase keeps a row of pictures whose files are gone, whose chips must not spill their path); a picture viewer (`image-viewer`: a chat pane's viewer stays inside the pane under the title bar, the full size's unlayered `100dvh` overridden, its bar's buttons 36 px targets on touch and the picture clear of the home bar) fits the screen; more toasts than a 1280×480 window holds scroll inside it (`Toast.tsx` `data-toast-scroll`, top from `--omp-toast-top`), a wheel over a toast reaching the newest. Every look emulates Reduce motion, and under it a mermaid diagram still lays out: `global.css`'s reduced-motion rule ends animations at 0.01 ms but runs no transition at all (`transition-duration: 0s`), because a 0.01 ms transition on every style change made code that styles and measures in one task (mermaid's labels) read the old size.

### Local checks

- **Local or runner** (the owner's rule, AGENTS.md › Build and the agent loop). Local: typecheck, biome on the changed files, the unit tests the change touched, `check:changed --no-e2e`. Runner (on the pushed branch): the full vitest and Playwright suites (`ci.yml` `batch=true`, `e2e-nightly.yml` `specs`), the native jobs on Linux and Windows, and the macOS jobs once, in the landing gate (`ci.yml` `batch=true mac=true`; AGENTS.md › macOS runners), a release dry run (`release.yml` `dry_run=true`). Local only because no runner can: a paired device's real link, a physical title-bar drag, a person's look at the screen. Waiting: one `gh run watch <id> --interval 120` per run, async. A landed worktree's `native/ompdesk/target`, `node_modules` and `out*/` are deleted when it lands.
- **What `check:changed` runs** (`scripts/check-changed.ts`): a smoke pass, never a verdict. It holds no lock as a whole. In a `vitest` slot it runs typecheck (whole project), biome on the changed files, the surface policy and vitest (below) side by side (in turn on 16 GB); then `bun run build` (`build` slot; reused when `out/` matches); then, in a `playwright` slot, the Playwright specs picked by name. `--list` shows the pick without taking a slot. Every pass line names the verdict, the branch's runner run (`ci.yml` `batch=true`, `e2e-nightly.yml` `specs`); a change to e2e support files picks no spec, and the run says that no e2e ran and names the full e2e run. The batch gate and the release keep the full suites.
- **Which unit tests** (`scripts/changed-tests.ts`): `vitest related` (every test that imports a changed file, transitively) while the change reaches at most `RELATED_CAP` = 40 test files; a change that reaches more runs only the tests one step away (a changed test, a test that imports a changed file) and prints one line with how many it leaves to CI's `check`, which runs every test on each push, and the `vitest related` command that runs them here. Either way it adds every test naming a changed file, CHANGELOG.md included (`scripts/changed-readers.ts`). The reach is read from import statements with one `git grep` (about half a second), type-only imports included, so it errs toward calling a file a hub.
  - **Why** (12 Nov 2026, `bun scripts/session-checks.ts`, three days of sessions on one Windows computer): 26 `check:changed` runs took 4.9 hours (842 s each; vitest was 2.0 h of the 2.3 h of steps they printed); ten failed, on 44 test files, none broken by the session's change: 14 timed out, 3 lost a temp folder Windows would not release, 7 passed when run alone with nothing edited, 11 failed in other checkouts' runs too (two of those failed on `origin/main` itself), 7 were never run again and 2 passed alone after edits elsewhere. The sessions' own runs of the tests they named (101, 99 s each) found their failures, and the CI failures they met were other platforms', the newest omp's or a cancelled run, none a test their own computer would have failed. A Rust unit that touched a file much of main imports ran 1,197 test files twice (1,577 s and 1,206 s, both red on load); the same change now runs 8 test files in 15 s. Over the last 100 commits on main the pick runs 4,165 test files where `vitest related` reached 19,571 (48 commits past the cap; median reach 20, a quarter over 369).
  - Pinned by `scripts/changed-tests.test.ts` (one step against any depth, the import spellings, the cap, tracked and untracked files through real git).
- "Changed" = working tree against HEAD (with `--base <ref>`, against where this branch left `<ref>`: their merge-base, so a branch behind `origin/main` does not count what landed there since; `changeBase` in `scripts/changed-readers.ts`) plus untracked files under `src/ e2e/ resources/ scripts/`, and the root configuration (`scripts/changed-scope.ts`: `*.config.ts`, the vitest setup files, `tsconfig*.json`, `package.json`, `bun.lock`, `bunfig.toml`, `biome.json`). Any build input (`isBuildInput` in `scripts/build-cache.ts`, the same rule as the build's own hash) also builds when no spec matched; a test-runner input (vitest's config, package.json, bun.lock) runs the whole vitest suite instead of the related tests.
- A spec is picked when it is changed itself, or its file name (for a hyphenated or camel-case name, its text) mentions a changed source file's name (`layout/work-board/WorkBoard.tsx` → `e2e/work-board.e2e.ts`; `auto-title-core.ts` → `auto-title`; a plain word such as `window.ts` matches file names only). A changed renderer file also picks every spec holding the English text it shows through a literal `t("key")` (each piece of 12 characters or more with a space, split at `{placeholders}`; `scripts/changed-specs.ts`), because specs find controls by that text. A changed renderer stylesheet counts as a change to the components that use the `omp-*` classes of the rules its changed lines touch (`touchedClasses`; a class used by more than 8 files is shared styling and names none; pinned by `scripts/changed-specs.test.ts`).
- Playwright runs with `--pass-with-no-tests` (an opt-in spec, such as the responsive audit or a capture run, registers nothing without its env) and picks from the default run only (no variants).
- Before the build it asks Playwright to start each browser a picked spec imports from `@playwright/test` (`chromium`, `webkit`; `scripts/e2e-browsers.ts`), since a Playwright upgrade leaves its versioned browsers to `bunx playwright install`. A missing one gets one warning line naming it, the specs that import it and the install command, before the specs and again after a failed run. Only a warning, because an import does not mean the spec runs: Playwright's result stays the verdict (pinned by `scripts/e2e-browsers.test.ts`).
- **Build reuse** (`scripts/build-cache.ts`). `out/` is reused when it was built from identical inputs: a SHA-256 over `src/` and `resources/` (test and bench files outside `src/renderer` excepted; Tailwind scans renderer tests for class names), the electron-vite config, `tsconfig*.json`, `package.json`, `bun.lock`, `.gitignore`, `.env*`, the build's own scripts and the build env (`NODE_ENV`, `MODE`, `NODE_PATH`, browserslist, the `*VITE_*` vars). The hash is stored with the size and mtime of every `out/` file in `out/.build-stamp.json`, written only after the build and the bundle check passed. A missing `out/` or stamp, a different hash, or a removed, added or rewritten `out/` file rebuilds; `OMPDESK_FORCE_BUILD=1` always does. CI and packaging start from a fresh checkout (no stamp), so they always build; a local `package:*` reuses only a byte-identical-input `out/`, and electron-builder leaves the stamp out of the package.
- **vitest projects** (`vitest.config.ts`; `tmp/`, gitignored scratch that can hold another repository's clone, is in neither): `renderer` (`src/renderer/**`) runs on worker threads with `lucide-react`, `linkedom` and `react-dom` pre-bundled by the deps optimizer (it stays: it saves seconds per run); `node` (everything else) keeps a child process per file, since those tests spawn processes, open sockets and edit `PATH`/env. They run one after the other (`sequence.groupOrder`), since side by side each would take every worker. Workers: as many as cores on GitHub's runners (`GITHUB_ACTIONS`; never key on `CI`, which agent shells on this Mac export too), locally `OMP_VITEST_WORKERS` or at most 8. Both keep per-file isolation; never turn `isolate` off.

### Lock and gate

- Kind slots (`DEFAULT_SLOTS` in `scripts/lock-slots.ts`; `OMPDESK_LOCK_SLOTS=playwright=3` overrides for measuring): `build` 1 (builds into `out/` never overlap), `playwright` 4 (four runs at once add no flakes beyond the solo baseline, and 4 runs × 2 workers is the fastest per run), `vitest` 1 (a full run with the static checks; `check:types` is one too; two full runs at once lose `*-stock` tests to load), `other` 1. Every hold takes a slot of the computer's heavy pool (`ompdesk heavy`) first (Lock on a small machine). A test that fails in every concurrent run is a peer's edit, not load.
- A slot is the directory `/tmp/ompdesk-locks/<kind>.<i>` (`os.tmpdir()` on Windows) with an `owner` file (first line `name HH:MM:SS pid N`; refreshed every minute; one older than 15 minutes is stale and the next waiter removes it). Waiters keep a ticket in `<kind>.queue/` and are served first come, first served; a late short job never overtakes an earlier one. A non-gate hold past 15 minutes is warned about and flagged by `lock-stats`.
- A Playwright run never reads `out/`: every `bun run build` (which takes the `build` slot itself) also publishes an immutable copy `out-<first 12 hex of the input hash>/` (an APFS clone; gitignored; deleted 30 minutes after a run last touched it; `scripts/out-snapshot.ts`), and `playwright.config.ts` pins `OMP_GUI_E2E_OUT` to the current one once per run, so a build another agent starts mid-run never changes the app under it.
- A Playwright run that finds others holding slots gets fewer workers: `OMP_GUI_WORKERS` = min(4, ⌊8 ÷ runs holding a slot⌋), both capped at one per 8 GB of RAM (`ramWorkers`); `OMP_VITEST_WORKERS` defaults under the same cap.
- `bun run gate` (`scripts/gate.ts`) holds no lock as a whole: typecheck, biome, the surface policy and the full vitest suite side by side in one `vitest` slot while the build takes the `build` slot, then, only if all passed, the full Playwright suite in a `playwright` slot on that build; its holds are exempt from the max hold.
- `bun run locked -- <command>`: the kind comes from the command, `--kind <kind>` overrides it, `--chunk <n>` runs a playwright/vitest command as `--shard=1/n … n/n`, one hold per shard. It waits for a slot (printing `[lock] waited 42.3s for <holder>` past 1 s), stops the command's whole process tree and releases the slot when interrupted; a locked command nested under another runs inside its hold (`OMPDESK_BUILD_LOCK_HELD` lists the kinds held; which nested command still takes a slot: Lock on a small machine › **Nesting never deadlocks**). The old single lock directory `/tmp/ompdesk-build.lock`, while it exists, counts as holding every slot (old `until mkdir` users keep working). Each release appends one JSON line (owner = `OMPDESK_LOCK_OWNER` or `user@checkout`, command, kind, `waitedMs`, `slot`, `via`, `heldMs`, exit code) to `/tmp/ompdesk-build.log` (`scripts/lock-log.ts`, trimmed to its newest 4000 lines past 5000); `bun run lock-stats [--since 2h]` summarizes it and shows whether agents wait more than they work and which slot each run used. `OMPDESK_LOCK_ROOT` and `OMPDESK_LOCK_POLL_MS` exist for tests, never for daily use.

### Lock on a small machine

- **One heavy hold at a time on 16 GB**, because running one of each kind together (plus typecheck and targeted vitest outside the lock) exhausted a 16 GB Mac's memory and forced a reboot.
- **What it does.** Every hold takes a slot of the computer's heavy pool first, then its kind's (`acquireHold` in `scripts/lock-slots.ts`). The pool is the product's, not this repository's: `ompdesk heavy` (`native/ompdesk/crates/checks/src/heavy.rs`, the `ompdesk` binary `bun run build:native` stages in `resources/ompdesk-bin/`), one per user and computer, so every checkout, worktree, OMPdesk session and plain script (`ompdesk run --heavy -- <cmd>`) shares one limit on heavy commands and there is one copy of the rule. The pool is the folder `$OMPDESK_HEAVY_DIR`, else `~/.cache/ompdesk/heavy` (`$XDG_CACHE_HOME` when set; `%LOCALAPPDATA%\ompdesk\heavy` on Windows) with `slot.<i>` files held by OS file locks, so a holder that dies gives its slot back at once and nothing is reclaimed by a timeout. Waiters are one FIFO for all kinds, so a stream of Playwright runs never starves a build or a larger `--all` holder. A hold spawns `ompdesk heavy hold`, waits for its `held` line and keeps it until the hold ends (its stdin closes; the child has its own process group, so a Ctrl-C reaches only the command). `ompdesk heavy status [--json]` and `bun run lock-stats` list the holders and the queue. The old `/tmp/ompdesk-build.lock` still holds every kind's slot. **CI:** GitHub's runners have one job each, so there is nothing to share, and ci.yml's `static` job (`bun run check:types`, `electron: "false"`) stages no binary (`.github/actions/install` builds or restores `resources/ompdesk-bin` only for jobs that take Electron). A hold there skips the pool when `GITHUB_ACTIONS` is set and no binary is staged; with one staged (the `check` legs) it uses the pool like any machine. Anywhere else a missing binary is built once by `ensureNative` (`bun run build:native`), and an existing one is used as it is, never rebuilt for a peer's edit in `native/`.
- **Size.** `pool_size` in heavy.rs: min(⌊(GB − 8) ÷ 8⌋, ⌊cores ÷ 2⌋), at least 1 and at most 7: 16 GB → 1, 24 → 2, 32 → 3, 64 GB with 16 cores → 7. 8 GB stay for macOS, OMPdesk and its sessions and each hold gets 8 GB (a whole-project `tsc --noEmit` alone peaks near 3 GB; vitest or Playwright workers add an app or a fork each). `OMPDESK_HEAVY_SLOTS=N` overrides it for measuring and `OMPDESK_HEAVY_DIR` moves the pool (tests that isolate the lock with `OMPDESK_LOCK_ROOT` set both). Nothing here computes the size: `heavyPoolSize` reads `ompdesk heavy status --json` (1 where no binary is staged), so `runSteps` and `lock-stats` follow the pool. `OMPDESK_LOCK_RAM_GB` stands in for RAM in the worker shares below, tests only.
- **Workers.** `ramWorkers(RAM)` = one per 8 GB (2 on 16 GB) caps Playwright's per-run default and share (`workersFor`) and vitest's default `maxWorkers` (`vitest.config.ts`); `OMP_GUI_WORKERS`/`OMP_VITEST_WORKERS` still override.
- **Typecheck is a heavy hold**: `bun run check:types` runs `tsc --noEmit` through `locked --kind vitest`; under check:changed or the gate it runs inside their vitest hold. It is incremental (`--incremental`, build info in `node_modules/.cache/tsc/check.tsbuildinfo`, gitignored). Measured 12 Nov 2026 on a 16-core Windows desktop while other sessions worked (CPU 19 to 85 % busy before a run, so not a quiet machine; three interleaved rounds, each run alone in the vitest slot; median and range): plain 36 s (34 to 46), incremental from nothing 38 s (33 to 50, no measurable difference), nothing in its scope changed since the last run 8.5 s (7 to 9), a comment added to a test file nothing imports 6.4 s (6 to 7), a comment or an export added to a module other files import 35 to 37 s (33 to 43, no gain: it checks nearly everything again). So it saves the runs between which only Rust, scripts, rules or leaf tests changed (14 of the 52 type checks in three days of sessions) and costs nothing measurable otherwise.
- **Nesting never deadlocks.** `OMPDESK_BUILD_LOCK_HELD` carries the kinds a holder has and `OMPDESK_HEAVY_HELD` the pid of the `ompdesk heavy hold` that keeps its heavy slot (a pid that is no longer alive counts for nothing; `ompdesk run --heavy` and the coming `ompdesk check` read it too, so none of them waits on its parent). A locked command nested under it runs inside it whatever its kind, except a build, which still takes the build slot (builds into out/ never overlap). The only wait a nested command makes is for the build slot, and a build holder never waits on anything, so no cycle of waits can close. Two phases of one gate in one process are not nested: each takes its own heavy slot, so on 16 GB the gate's vitest phase and its build run one after the other. Inside their one vitest hold, check:changed and the gate run typecheck, biome, the surface policy and vitest one after another when the machine has a single heavy slot (`runSteps` in `scripts/build-lock.ts`), side by side otherwise.
- **A hold never keeps its holder alive.** Once `ompdesk heavy hold` prints `held`, `acquireHeavy` unrefs the child and its pipes; the slot goes back when the holder exits (its exit handler, and the OS closing the hold's stdin). Without it a script that takes the lock and ends (`build-cache.ts`'s build path) and the hold waited on each other: on 13 Nov 2026 a measurement kept a heavy slot and the build slot for six hours.
- Pinned by `scripts/lock-slots.test.ts` ("the computer's heavy slots": FIFO across checkouts, nesting, a dead holder's slot, the GitHub-runner skip; the real `ompdesk` on a temp `OMPDESK_HEAVY_DIR`) and `scripts/build-lock.test.ts` (two locked commands serialize on one slot, a killed holder frees it, a script that takes the lock and ends exits and frees it, workers on 16 and 64 GB, nested build on one heavy slot, cross-kind nesting).

### CI

- Workflows: `.github/workflows/ci.yml`, `mac-main.yml`, `release.yml`, `formal.yml`, `e2e-shards.yml`, `e2e-nightly.yml`, and the called ones `queue-gate.yml` and `mac-checks.yml` (see The check queue below), plus `setup-assets-health.yml`, `omp-latest.yml` and `skills-bump.yml` (see Built-in skill packs stay current) and the manual `flake-probe.yml` (see Flaky tests). The repo is public, so every job runs on a GitHub-hosted runner at no cost and the layout follows wall time, not billing.
- **The check queue is held by the workflows, not by whoever dispatches** (the owner's rule, 13 Nov 2026: the account runs 5 macOS jobs at once, sessions queued 71 of them, every push to `main` kept a run of its own, and Main cancelled runs by hand all evening). Five invariants, each held by a GitHub feature that no agent has to remember or can skip; `src/main/ci-queue.test.ts` pins the shape that makes each apply.
  1. **Main has at most two runs of each kind, one going and the newest waiting, and a run that started is never cancelled.** A push to `main` is in ci.yml's group `ci-main` with `cancel-in-progress: false`: a push that finds a run going waits, and a newer push replaces the one waiting (it ends `cancelled`: a newer commit's run covers it). Nothing piles up (one group per commit, as before, kept every push's run: 69 CI watches in three days; one group per branch with cancel on killed each push's run for as long as pushes kept coming, so no commit got a verdict), and a verdict arrives every run length however fast pushes land. A push's macOS checks are a queue of their own, mac-main.yml (group `mac-main`, the same rule), because a macOS runner can be a long wait and, kept in `ci-main`, that wait held every newer push's Linux and Windows verdict behind it. The run of a `release: vX.Y.Z` commit (all its jobs skip: release.yml checks that commit) sets `cancel-in-progress` for itself in both workflows, so it ends the running and the waiting run and the runners they hold are free for release.yml.
  2. **A dispatch replaces its own older run.** Group `ci-<ref>-<inputs>` with cancel on: the newest dispatch of the same inputs on a ref wins, other inputs run beside it. e2e-nightly.yml keeps its per-ref, per-kind group; flake-probe.yml lets an identical probe finish and keeps one waiting.
  3. **Dispatched macOS work never exceeds one unit.** Every macOS job of a dispatchable workflow is in the job-level group `mac-dispatch` (`cancel-in-progress: false`), set on its calling job so the whole unit holds it: ci.yml's `mac` (mac-checks.yml: `mac-smoke`, `mac-native`, `memory` and `native` on macOS, four runners), ci.yml's `e2e` and e2e-nightly.yml's `e2e` (the five shards), `parity` and flake-probe.yml's macOS leg. GitHub keeps one running and one waiting job per group and a waiting job holds no runner (status `pending`), so branches have at most one unit's runners open (4 for the gate, 5 for the full suite) and nothing queues behind it. The nightly has `mac-nightly`, a push to main has mac-main.yml (one run at a time, four runners); release.yml has no group and is first in line.
  4. **macOS is for release-bound work.** `gate` (queue-gate.yml, the first job of every dispatchable workflow that has macOS jobs) admits a dispatch that asks for macOS (ci `mac` or `e2e`, every e2e-nightly dispatch, flake-probe `os` macos or all) only from `main` or a branch named in the repository variable `MAC_REFS` (space or comma separated; Main sets it, `gh variable set MAC_REFS --body "branch-a branch-b"`, and clears it when the release is out). From any other ref the gate job fails with the reason and the macOS jobs (`needs: gate`, `if: needs.gate.outputs.mac_ok == 'true'`) never start; the run's Linux and Windows jobs go on. Pushes to main, the nightly and release.yml are always admitted.
     - **A macOS dispatch carries an admission ticket** (check-control, design §7 criterion 1): the workflows' `ticket` input, `v1.<DEVICE>.<expiry ms>.<hex>`, an HMAC-SHA256 of the computer, repo, ref, commit and expiry under that computer's own key, which its OMPdesk's checks hub mints for each dispatch (`native/ompdesk/crates/core/src/checks/ticket.rs`; one key per computer, never synced). queue-gate.yml's `device` step names the ticket's computer; the `admit` step reads only that computer's secret `CHECKS_ADMISSION_KEY_<DEVICE>` (`secrets[format(…)]`; callers pass `secrets: inherit` and `admission-devices: vars.CHECKS_ADMISSION_DEVICES`), recomputes the mac with openssl and refuses one started by hand, main included, or from a computer `CHECKS_ADMISSION_DEVICES` does not list, with "Start it with ompdesk_checks". While that variable is empty the step only notes that tickets are off. A step cannot list secret names, so the variable is the list of computers with a key; OMPdesk's publish action writes the secret and the variable together. `ci-queue.test.ts` runs both steps on the vector `ticket.rs` pins and pins the device-to-secret mapping.
  5. **The same commit and inputs run once.** A dispatch's run name carries its inputs (`ci [batch mac ]`); `gate` cancels the run when its commit already has a successful run of that workflow under the same name (`-f force=true` runs it anyway; a re-run is never cancelled; a failed or cancelled run covers nothing; a lookup that errors lets the run go; a run still going is not a twin, the group of invariant 2 replaces it). A new `workflow_dispatch` input of ci.yml or e2e-nightly.yml goes into the run name (and ci.yml's group), or two different runs read as one; `force` and `ticket` stay out, as they change nothing that runs.
  - **The front door** is `bun scripts/ci-run.ts <workflow> --ref <branch> -f …` (workflows `ci`, `e2e-nightly`, `flake-probe`, `formal`; same fields as `gh workflow run`), a thin client of OMPdesk's checks hub (`ompdesk checks start --workflow <file> --input k=v … [--macos] --ref <branch>`; check-control › Starting, waiting and the answer): the hub's one admission queues it with every session's start (macOS only from main or a MAC_REFS branch, one macOS unit at a time held in OMPdesk instead of at GitHub, the release lane first, a newer start of the branch replacing the older, a green run of the same inputs reused) and dispatches it with its ticket. ci-run prints the hub's answer (exit 0 started, held or reused; 2 refused). When OMPdesk does not answer, a dispatch without macOS goes out directly with `gh workflow run` (an app restart never stops every CI dispatch) and one with macOS is refused with "open OMPdesk". Pure parts pinned by `scripts/ci-run.test.ts`.
  - **What the workflows cannot enforce.** **The caps are the account's, not this repo's**: 40 jobs at once and 5 of them macOS (`RUNNER_LIMITS` in `scripts/ci-run.ts`, the one place the numbers live) belong to the personal account `SeuPut0705` and are shared with any other repo of it. Today none: seuoffice, which shared them until 13 Nov 2026 (measured 15:05 UTC that day: 39 of 40 running, 29 of them seuoffice's, 114 seuoffice and 60 ompdesk jobs queued), moved to the org seuput-inc, whose limit is its own (about 5 jobs at once on 13 Nov 2026), and ompdesk stays on this account. Everything above bounds only what ompdesk adds: no policy here can reserve a slot against another repo of the account, and a job of ompdesk can still wait behind its queue if one lands here. `ci-run.ts` prints this repo's open runs before a macOS dispatch (read-only; `OMPDESK_CI_SIBLINGS` adds another repo's), so a wait is expected, not a bug in the queue; another repo's runs are never touched from here. A dispatch runs the workflow file of its ref, so a branch cut before queue-gate.yml landed runs its own old files, which hold nothing: `ci-run.ts` refuses it, a raw dispatch on it is not held until main is merged into the branch. Anyone can still `gh run cancel`, `gh variable set MAC_REFS` or push a workflow that drops a rule; ci-queue.test.ts fails in CI for the last. A request replaced while it waits in a lane is dropped, not queued (its `mac` job shows `cancelled`, "Canceling since a higher priority waiting request for 'mac-dispatch' exists"): its session dispatches again once the holder ends. A holder whose jobs wait for a macOS runner that main's pushes or a release hold keeps the lane until they start or Main cancels it (`gh run cancel <holder>`). A session watches the run of its own commit (`bun scripts/watch-run.ts <run-id>`); a run that is red because of a commit landed before it is that commit's to fix, and a `cancelled` main run was replaced by a newer commit's.

- Failures: a failed job writes its failing step and the first error lines to its job summary at once (`scripts/ci-failure.sh`, last step `if: failure()`, read-only `actions: read` token). Informational; the local `bun run gate` is the full-suite proof.

- **Flaky tests: `bun run flake`** (`scripts/flake.ts`), never a hand-made probe branch (copied cases, added delays, a push and a dispatch per guess). `bun run flake <spec> [--grep <regex>] [--repeat <n>]` (default 10) runs one test file here under the lock: an e2e spec (`*.e2e.ts`) as `bun run build`, then Playwright `--repeat-each` in a `playwright` slot, traces of failures in a private folder it names; a vitest file as `n` separate `vitest run`s, each in its own `vitest` slot so a waiter gets in between (vitest 3 has no repeat flag, only a per-test `repeats` option that needs the file edited). Retries off, every repeat runs to the end. It prints passes and failures, failures per test and the first failure's message; exit 1 on any failure, 2 when no test ran (a wrong path or `--grep`, or every test skipped, as the `*-stock` suites do without omp).
  - `--ci [--os macos|windows|ubuntu|all]` dispatches `flake-probe.yml` on the current branch through `scripts/ci-run.ts` (pushed as it is; it refuses otherwise) and prints the run's URL: one job per OS (`all` = macOS and Windows for an e2e spec, which never runs on Linux, plus ubuntu for a vitest file) runs the same script after installing the newest omp and the Playwright browsers the spec imports, writes its counts and first failure to the job summary (and `scripts/ci-failure.sh`'s log lines on a failure) and uploads `test-results/` and `playwright-report/` as `flake-<os>`. The macOS leg needs the branch in `MAC_REFS` and takes the `mac-dispatch` lane; from any other branch `--os windows` (or `ubuntu`) is the probe, and `--os all` fails its gate job and runs the other legs. Its own workflow, so a probe starts none of ci.yml's jobs and no push cancels it.
- **Captures from a runner.** The e2e shards (`e2e-shards.yml`) upload `test-results/` only when a shard failed or was cancelled, so a green `e2e-nightly.yml` run leaves no capture. A workflow file that is new on a branch cannot be dispatched until it is on `main`; put such a path into an existing workflow.

- **Public-repo trust rules.** No workflow uses `pull_request_target`. A pull request (fork or not) runs only ci.yml's Linux jobs with a read-only `GITHUB_TOKEN` and no secrets. release.yml starts only from a push to `main` that touches `package.json` or from a manual dispatch (write access). `MAC_SIGNING_P12_BASE64` and `MAC_SIGNING_PASSWORD` are read only by `mac`'s Package step and only for `main` (a dry run from another ref signs ad hoc). Every job has `permissions: contents: read` (plus `actions: read` where it lists the run's artifacts or jobs, for `ci-fetch-out.sh` and `ci-failure.sh`) except `publish` (`contents: write`), skills-bump.yml's `push` (`contents: write`, `actions: write` to dispatch ci.yml; it runs no third-party code) and the health and bump issue jobs (`issues: write`). Every action is pinned to a commit SHA. Repo settings behind this: "Require approval for all outside collaborators" and read-only workflow permissions. The former self-hosted runner (`ompdesk-mac`) is retired; its secret `RUNNER_STATUS_TOKEN` is unused.
- **Why no bun cache.** No job caches bun's install, because `actions/cache` keyed on `bun.lock` is no faster than a cold `bun install` on any OS and costs an upload per lockfile change. The caches that pay are the Rust builds': the memory build's (`Swatinem/rust-cache` and the built binary, see "Memory (ai-memory)") and OMPdesk's own native binaries' (below). A pull request's cache entries are scoped to its own ref, so a fork's run can never put a binary in front of `main` or a release.
- **OMPdesk's own Rust is built in the install action** (`native/ompdesk`, `bun run build:native`; native-rust), for every job that takes Electron, since those are the jobs that test or package it (`native: "false"` opts one out). `resources/ompdesk-bin` is restored from `actions/cache` keyed on OS, arch and a hash of `native/ompdesk/**`, `scripts/build-native.ts` and `scripts/cargo.ts`: a hit installs no Rust and runs only `bun run build:native -- --check`; a miss calls `.github/actions/native-toolchain` (the channel from `rust-toolchain.toml`, `dtolnay/rust-toolchain` and `Swatinem/rust-cache` for `native/ompdesk`), builds and saves right away. The `native` jobs use that same toolchain action but always run checks, not the staged-binary cache. release.yml's `Verify bundle` / `Verify package` run the packaged `ompdesk help` (macOS: after `codesign --verify`).
- **Electron comes from a cache, installed in one place**, because electron's postinstall download and electron-builder's fetches fail intermittently (5xx, socket hang up) and turned runs red before any test. Jobs needing JavaScript dependencies run `.github/actions/install` (a composite action; after checkout and `oven-sh/setup-bun`, whose pinned version stays in each workflow for `supply-chain.test.ts`) instead of `bun install` and an "Ensure the Electron binary" step. It installs the packages with `ELECTRON_SKIP_BINARY_DOWNLOAD=1`, then runs electron's `install.js` under bun (the Node 26 `extract-zip` hang, see AGENTS.md) with `ELECTRON_CACHE`/`electron_config_cache` in `$RUNNER_TEMP/electron-cache`, restored from `actions/cache` keyed on OS, arch and the electron version read from `bun.lock`; a miss downloads, retrying once after 30 s, and saves the cache right away (a later failing step keeps it). `electron: "false"` (types, biome, build) skips the binary and the cache; `builder: "true"` (release `mac` and `win`, ci's `installer-check` and `win-e2e`) also restores `ELECTRON_BUILDER_CACHE` (electron-builder's electron zip, winCodeSign, nsis), saved when the job ends green. The step log says `Electron <version>: cache-hit=true|false`, with `@electron/get` debug lines. Tests are never retried. A pull request or branch reads `main`'s entries and writes its own.
- **Windows packaging.** electron-builder packs the NSIS payload at `-mx=9` whatever `compression:` says, so `win`'s Package step sets `ELECTRON_BUILDER_COMPRESSION_LEVEL=4` (about half the packing time for a setup about a quarter larger; the Mac DMG is untouched; never below 4). `ELECTRON_SKIP_BINARY_DOWNLOAD` on Windows fails (gpu-fallback and sidecar tests import electron) and saves nothing. `win`'s lever is fewer `@smoke` specs, since every one guards a Windows-only failure.

### Signing

- `scripts/mac-sign.cjs` (electron-builder `mac.sign`) signs every bundle with OMPdesk's own self-signed certificate, pinned by SHA-1 in `scripts/mac-signing.json`, so the designated requirement (`identifier "com.seuput.ompdesk" and certificate root = H"…"`) is the same in every release and macOS keeps its privacy grants (folders, local network, microphone) across updates; an ad-hoc requirement is the build's cdhash and re-asks them all each update. **Never replace the certificate.**
- Identity source, in order: repo secrets `MAC_SIGNING_P12_BASE64` / `MAC_SIGNING_PASSWORD` (release.yml sets `OMPDESK_MAC_SIGNING_REQUIRED=1` on `main` and checks the requirement); the maintainer's local `~/.ompdesk-signing/` (p12 + password; the only backup: losing it means a new certificate and another round of prompts for every user); else ad-hoc with a warning.
- It is imported into a throwaway keychain passed to codesign with `--keychain`; the user's keychain search list is never touched.
- No Apple Team ID, so keychain items still bind to the cdhash (safeStorage stays untouched unless a stored token exists). Nothing is notarized: downloaded DMGs need right-click → Open once; locally built apps run without Gatekeeper prompts.
- `mac` packages an arm64 DMG, signed with the pinned certificate on `main`, and verifies codesign, the designated requirement and `gui-bridge`; `win` packages the x64 NSIS setup, because `makensis` cannot run on Apple Silicon.

### Windows

- **Test scope.** release.yml's `win-platform` job runs `bun run test:platform --shard=n/3` (`vitest run --exclude "src/renderer/**"`), the suite minus the renderer, as three shards. Anything that can behave differently on Windows (paths, PATH lookup, shells and `.cmd` shims, spawn, sockets and named pipes, file modes) lives in main, shared, the bridge or scripts, so its tests run there by default. Renderer tests never read the host platform (pass `"windows"`/`win32` explicitly); `src/main/platform-test-scope.test.ts` fails on a renderer test that checks `process.platform` and pins the script and the workflow step.
- **Windows test pitfalls the platform job found**:
  - A process holds the folder it runs in: `rm` of a child's cwd fails `EBUSY` until the child exited. A test that runs a child in a temp folder stops it and waits for it to be gone (its pid, or the product's own stop that awaits it) before removing the folder (`mcp-hub-rea.test.ts` "runs each omp's REA in that omp's folder").
  - A live worker holds the files it opened: the stock helper's SQLite databases (`history.db-shm`, `agent.db`) and the native module stock copies into a private HOME (`.omp/natives/<version>/pi_natives.*.node`). `child.kill()` returns before the process is gone, so a cleanup that removes the folder right after fails `EBUSY`/`EPERM`; await the child's `exit` first (`stock-helper-accounts.test.ts`, `stock-helper-sessions-named.test.ts`). An exited child's folder can still be refused for a few hundred ms, as `EBUSY` or `EPERM`; `removeWhenFree` (`src/main/test-folders.ts`) retries both.
  - A bound under test (a step's or drain's timeout) is reached on a fake clock at the moment the test means, never by a short wall-clock bound over real git, because a git process can take over a second on a busy runner. `vi.useFakeTimers({ toFake: ["setTimeout", "clearTimeout"] })` for the stuck part only, `vi.useRealTimers()` before the real work (`autopilot-ship-stall.test.ts`).
  - A path compared or used as a key keeps the spelling the product saw. windows-latest's `%TEMP%` is the 8.3 `C:\Users\RUNNER~1\…`: `os.tmpdir()`, `fs.realpathSync` (JS) and a child's `process.cwd()` keep it, `fs.promises.realpath` and `fs.realpathSync.native` spell it `C:\Users\runneradmin\…`. A test takes the path the product reported (a `get_state` answer, an event) instead of rebuilding it with `realpath` (`link-traffic-relaunch.test.ts`'s relaunch; see the remote-devices rule).
  - **A stock suite runs the installed omp the Windows way**. `src/main/test-bridge-probe.ts` holds the three things they share: `INSTALLED_OMP` is Bun's launcher (`omp.exe` there); `OMP_COMMAND` starts omp itself (`bun <package>/dist/cli.js`), since a signal to the `omp.exe` launcher ends only the launcher and the real omp then disposes cleanly on its stdin's end, holding its folders; `configDirName` gives `PI_CONFIG_DIR` relative to the home folder, which stock joins it to (an absolute path gives `ENOENT`). A folder a stock omp worked in is removed with `removeWhenFree` (`src/main/test-folders.ts`) once that omp exited. No `sqlite3` CLI (Windows has none: `node:sqlite`), no `:` as a PATH separator (`path.delimiter`), and a fake tool is a program the way the product starts it (a compiled `gh.exe`; Bun refuses a `.cmd` whose arguments carry cmd.exe's special characters). Skipped on Windows with the reason in the file: `bridge-ssh-diagnostics` (stock verifies no SSH login there).
- **Windows e2e** (`@smoke`, never run by a human). release.yml's `win` job runs every `@smoke` spec after packaging (not split into `--shard` halves, since a second checkout and install costs more than it saves). Tag a new spec `@smoke` only when it is worth ~10–25 s there and guards a Windows-only failure.
