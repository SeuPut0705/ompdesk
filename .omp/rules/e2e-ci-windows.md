## Build, test, CI

### E2E

- Run: `bunx playwright test`. `playwright.config.ts` sets `OMP_GUI_HEADLESS=1`: windows are transparent, click-through, off the Dock/taskbar and never focused, and the app creates no menu-bar tray item and never registers the `omp://` handler (both belong to the user's installed OMPdesk; a test's tray once stalled the main thread before the first window reached Playwright). It posts no OS notification either (`holdTestNotifications`, `src/main/app-icon.ts`: `Notification.prototype.show` is a no-op, so a spec that wraps it still sees each one): macOS filed a test's notification under node_modules' Electron.app and the user's Notification Center showed e2e's "Autopilot ended" with the Electron logo. Tests never cover the user's screen or rewrite their LaunchServices state. Set `OMP_GUI_HEADLESS=0` only when you must watch.
- Fake vs real omp: `e2e/real-core.e2e.ts` and `e2e/deep-audit.e2e.ts` run against the real system omp (isolated agent dir, no credentials). Every other suite uses the fake omp in `e2e/sidecar-fixture.ts`, installed per test by `fixtureOmp()` (`e2e/harness.ts`; an `omp.cmd` shim on Windows) and passed as `OMP_GUI_OMP`. It speaks stock `--mode rpc-ui` and serves the gui-bridge methods those suites reach on `OMP_GUI_BRIDGE`.
- Tear apps down with `exitApp()` (same file; it kills a main process that does not act on the exit within 10 s). On Windows it then waits (`e2e/process-tree.ts`) for every process the app started (Chromium's helpers, omp, its MCP servers, git) and kills one still running after 10 s: a process holds the folder it works in, and the launcher exits ~0.1 s before they do, so a spec's `fs.rm(profile)` right after found `project` busy (`real-core.e2e.ts`: `EBUSY` in 5 of 24 runs, the omp and its `npx` chain alive when `exitApp` returned; 0 of 30 after). Shortcuts in tests use `ControlOrMeta`. A path inside a CSS attribute selector goes through `cssString()` (`e2e/harness.ts`): a raw Windows path's backslashes read as CSS escapes and the locator matches nothing.
- **A test app never outlives its worker, and a run's temp files never outlive the run** (21 Oct 2026: a Windows PC held 108 test Electron processes, their fake omps and fake ai-memory servers, and 289 test profiles plus 405 WebKit profiles after a day of agent runs). Playwright's exit handler is the only thing that ends an app it launched, and a worker that dies without running it (Node 24.15's 0xC0000409, an outer `taskkill /F`) left the app running under the `cmd.exe` Playwright starts it with; stdin cannot tell, since Electron's main process on Windows has an empty `process.stdin`. `playwright.config.ts` sets `OMP_GUI_TEST_LAUNCHER_PID` to each runner's and worker's own pid and `appLaunchOptions` (`e2e/harness.ts`) puts it in every `launchApp` env, and main (`src/main/test-launcher-exit.ts`) exits once a second's check finds that pid gone (taken out of its environment, so nothing it spawns inherits it); a spec that builds its own env keeps the variable by spreading `process.env`. On Windows every run also gets its own temp folder (`e2e/run-temp.ts`: TEMP/TMP point at `<temp>/ompdesk-e2e-XXXXXX` with an `owner.json`), so every `mkdtemp` profile, Playwright's own and whatever the apps and fakes write land there; `globalTeardown` ends every process whose command line names it (the detached fake ai-memory server included) and removes it, and `globalSetup` does the same for a folder whose runner died first. What must outlive a run (the compiled fake `gh` launcher, opt-in evidence folders) uses `baseTemp()`. Pinned by `e2e/app-lifetime.e2e.ts` (launches with `appLaunchOptions`' env, whose launcher dies running no handler: the app, its helpers and its omp are gone within seconds; it fails with that wiring removed) and `e2e/run-temp.test.ts`.
- **The fake ai-memory server ends itself** (`e2e/fixture/fake-ai-memory.ts` `serve`): it is detached like a real service, so nothing above reaches it on macOS (there is no run temp folder there). It checks once a second and exits when its data dir is gone (the spec's teardown) or the worker that installed the fake no longer runs (`FAKE_AI_MEMORY_OWNER_PID`, baked into the launcher by `fixtureAiMemory`). Seen 28 Oct 2026: 49 servers (136 MB RSS) from a week of runs, every data dir already deleted; 0 after `ai-memory`, `memory-page`, `memory-sync` and `memory-upkeep` ran twice with `--repeat-each 2`.
- Fake omp layout: `e2e/sidecar-fixture.ts` only reports the version (`fixture/version.ts`) and dispatches in stock's order: `--version`, `stats` (`fixture/stats.ts`), `update --check` (`update-check.ts`), `worktree … --json` (`worktree.ts`), `-p` (`print.ts`), then `--mode rpc-ui` (`rpc-ui.ts`: stock RPC plus every gui-bridge method the suites reach; one closure, because its fake session state is shared by every command). A new fake RPC command or bridge method goes into `rpc-ui.ts`; a new CLI invocation into its own `e2e/fixture/` module and the entry's dispatch. A fixture branch no spec uses any more goes with the spec that used it.
- With `OMP_GUI_TEST_SESSION_FILES=1` the fake's journal is a stock-shaped session file: a new session writes `sessions/fixture/fixture-<pid>.jsonl`, and a stored file that `--session` or `switch_session` opened keeps its header and takes every later entry, as stock's `SessionManager.open` does (`e2e/fixture/rpc-ui-session-file.test.ts`). Writing it elsewhere makes a relaunch's continued turn a second session the sidebar lists beside the first.
- Two shared steps a spec never re-implements (`e2e/harness.ts`): `dragTabToPane` splits by dragging a tab's sidebar row onto a pane edge, naming the tab with a `fixture:title:` shell line first, since a fresh tab has no row until something is typed into it (`unstarted`, Sidebar.tsx; four inline copies dragged `[data-session-path="tab:<id>"]` of a spawned tab and found nothing once that rule landed). `untilAnswered` waits for a tab's transcript to hold the fake's reply: never read an agent-opened child's `lastRun.reply` or last answer for it, because main asks a child whose turn ended with no `Result:` line and no report to report (`#nudgeSilent`, about a second after the turn) and the fake's "Read the note report from …" then follows (viewer-family, agent-control-across's blip test and remote-host-family failed so under load); `after` waits for the reply to a later message, and an `ompdesk_compare` `final answer:` is either reply.
- **No build, no run.** Electron with a missing entry opens a native "Error launching app: Unable to find Electron app at …/main/index.js" dialog on the user's screen for every test, and `OMP_GUI_HEADLESS` does not stop it. `playwright.config.ts`'s `globalSetup` (`e2e/global-setup.ts`) resolves `<OMP_GUI_E2E_OUT ?? out>/main/index.js` once (`scripts/e2e-app-entry.ts`) and fails the whole run before any worker starts ("No build: … Run `bun run build` or `bun run check:changed`"). `launchApp` (`e2e/harness.ts`) asserts the same before `electron.launch` (covers a spec run with a custom config); a spec that calls `electron.launch` itself uses `assertAppBuilt()`. Pinned by `scripts/e2e-app-entry.test.ts` (Playwright on an empty `OMP_GUI_E2E_OUT`: fast non-zero exit, no process on that path). Never run Playwright in a fresh worktree before `bun run build`.
- Specs launch `path.resolve(process.env.OMP_GUI_E2E_OUT ?? "out", "main/index.js")` (a new spec does the same, or uses `launchApp`); see Lock and gate for why the path is a snapshot.
- Env-gated specs and helpers:
  - `e2e/performance.e2e.ts` runs only with `OMP_GUI_PERFORMANCE=1` (optional `OMP_GUI_BASELINE_DIR` compares another built checkout); CPU and compositing budgets run only with it.
  - `e2e/real-startup.e2e.ts` registers only with `OMP_GUI_REAL_STARTUP=<dir>`: the built app on the user's installed omp (a private copy of `~/.omp/agent`'s config, extensions and databases plus the two largest sessions written this week), per run the main startup marks (`omp-spawned` included), the window's boot skeleton, layout, first row and composer, and a session opened in a new tab with and without its transcript snapshot. `OMP_GUI_REAL_STARTUP_SUBJECTS=before=<root>,after=<root>` interleaves built checkouts, `OMP_GUI_REAL_STARTUP_RUNS` (default 5); writes `results.json` and `summary.md` (median and range) to the dir. No model is called.
  - `e2e/event-replay.e2e.ts` runs the fake omp with `OMP_GUI_TEST_REPLAY_FRAMES=1` (every message and tool frame sent again behind the next one) and main with `OMP_GUI_TEST_BATCH_INTERVAL_MS=400`, so snapshot loads overtake held frames. `src/renderer/hooks/event-replay.test.tsx` is its seeded unit counterpart. Renderer stores apply a frame for a message or call they already hold (by stock timestamp and call id) as a no-op.
  - `OMP_GUI_TEST_INSTALLER=<executable>` turns on automatic machine setup in a test launch and replaces every install plan with `<executable> <item> <method>`. `e2e/machine-setup.e2e.ts` uses it with `OMP_GUI_OMP` naming a not-yet-existing fake omp (missing omp → install fails → Retry → detected → the tab restarts ready); `OMP_GUI_SETUP_CAPTURES=<dir>` adds its captures. Real installs never run in a test against the user's profile: `scripts/setup-install-check.ts` runs the real Bun installer, PortableGit (Windows) and `bun install -g` omp in a child with a temp HOME/USERPROFILE and BUN_INSTALL, checks `omp --version` against the minimum, and deletes the temp dir.
  - Opt-in model audits (`OMP_GUI_REAL_WORK=1`, they spend tokens): `e2e/real-work-map.e2e.ts`, `e2e/real-work-scenarios.e2e.ts` and `e2e/real-advisor.e2e.ts` (asserts each custom message an `agent_end` commits, advisor card or background job result, carries its journal `entryId`, which the sidecar's `sessions.attach_entry_ids` stamps, and that its card is in the live transcript; `e2e/fixtures/real-advisor-frames.json` is a trimmed recording). All copy `config.yml` and `agent.db` into a private 0700 agent dir through `e2e/real-omp.ts` and run the main model on the user's `smol` role; `OMP_GUI_REAL_WORK_ARTIFACTS` picks the capture directory.
- **Tiers.** `@smoke` (the tag in a test's title) runs on every release's `mac` and `win` packaging jobs against the build they just made; it is the only e2e a release waits for. The default run (`bunx playwright test`) is the full suite: locally on demand (`bun run gate`; `check:changed` picks specs from it), on hosted runners nightly and on demand (`e2e-nightly.yml` and ci.yml's `e2e=true`, both through `e2e-shards.yml`; informational, never a release block).
- **Variants and captures are opt-in.** `variants(all, keep?)` in `e2e/harness.ts` keeps one variant (en light; for the mobile matrix one engine × device per shell mode) and does not register the rest unless `OMP_GUI_VARIANTS=1`, so they neither run nor show as skipped. `OMP_GUI_*=<dir>` capture tests register only with their dir set.
- **Rules for a new e2e.** No theme, language or size variant matrix as blocking tests (en light runs, the rest goes behind `variants()`). Prefer a unit or component test (vitest with linkedom) for anything that needs no real Electron window, Chromium layout, real processes or the wire between them; an e2e asserts a flow across those, and its header names the component tests that cover the rest. To move an e2e down, write the unit case first, confirm it fails when the behaviour breaks (break the guard, run it, put the guard back), then delete the e2e and any fixture branch only it used.
- **Parallelism.** Locally Playwright runs 4 workers (`OMP_GUI_WORKERS` overrides; 1 on GitHub's runners, `GITHUB_ACTIONS`). Every test launches its own app on `mkdtemp` userData, agent dir and fake omp, with ephemeral ports (a fresh bridge socket per spawn; a remote spec's host and client share one free port from `makeRemoteProfile`, which a parallel test may hold a successor of, so never assert the exact successor), so a new spec never uses a fixed path, port or shared profile. That remote port comes from `freePortRun` (`src/main/remote/test-ports.ts`), which walks a band of 500 ports per parallel worker (Playwright `TEST_PARALLEL_INDEX`, Vitest `VITEST_POOL_ID`) run by run, never at random from one shared range: a run is picked seconds before its app listens on it, and every app on the machine sees the others on 127.0.0.1, so two random picks that touched sent a device to another test's host, and the second device to reach it failed `[remote_key_mismatch]` in `remote.connect` (`connectHost`). Measured with the range cut to 45 ports: 2 of 24 `remote-resume` runs failed that way, each beside a pair of touching picks in the pick log (`test-ports.test.ts` pins the bands).
  - The suite is bound by its total work, not its slowest test: all workers stay busy to the end and apps running at once slow each other down. A launch on the fake omp costs about 1 s here and 2 s on a hosted runner, so sharing an app between tests saves little; fewer tests is the lever. Split a long test into tests that run side by side only while it ends the run.
  - `e2e/deep-audit.e2e.ts` (`mode: "parallel"`) splits its settings rows by measured cost over `SETTINGS_SHARDS = 3` apps (6 shards added work and left wall time unchanged). 5 or 6 workers measured only ~10 % faster than 4 at more load, so 4 stays.
  - Reference (18 Oct 2026, 15-core Mac): full default run ≈ 4 min. `MEASURED_SECONDS` in `scripts/e2e-shard.ts` holds per-spec costs for the shard dealer, measured on the hosted macOS runner with one worker (a nightly's per-test times summed per file): measured here with 4 workers, deep-audit read 184 s against 672 s on the runner, and its shard ran past the 30-minute step limit (nightly 39749113072).
- **Responsive audit.** `e2e/responsive-audit.ts` (engine), `e2e/responsive-surfaces.ts` (named surfaces), `e2e/responsive-audit.e2e.ts` (the matrix), `e2e/responsive-smoke.e2e.ts` (the default run). It visits the dev harness (`src/renderer/harness.html`; `?stress=1` overflow-prone turns, `?host=1` a fake web host so host sheets mount, `?pwa=push|ios`, `?platform=darwin|win32` paints the page as that OS's Electron window: desktop layout, no mobile shell; `window.__stores` exposes the ui/toast/extension-ui/plan/updater/host-ui stores so a surface opens the way a click would) at 48 looks: touch phones 320/360/390/412, tablets 768/834/1024 (portrait and landscape) and iPads sideways 1133/1180/1366, then desktop windows 1100/1280/1440/1920 with a mouse, once as the web client (column `W`) and once as the Electron window (`E`); en and ko, light (dark at 390 and 1280), with simulated safe areas (`--safe-*`) on touch looks. A surface that shows a panel's error boundary (`PanelErrorBoundary`, `data-panel-crashed`) or the root crash screen fails with its message (the harness once answered `getLaunchProfile` with nothing, and Settings › Projects & launch was measured as "This panel crashed" for weeks). Each surface reports page overflow, escaping elements, truncated controls, clipped text, off-screen popovers, hit boxes under 44 px (a list row under the shell's `--sc-row-touch`, 36 on a phone; 36 on a field or a cluster that declares `--hit-gap-*`), text under 11.5 px, overlaps, stolen taps and content under the insets; hit areas, stolen taps and insets only on touch looks. Anything covered by a layer (judged at the centre of its on-screen part) or scrolled out of its scroller is not measured, and a popover or toast inside a scroller is judged by what the scroller lets through on each axis it scrolls (a fixed box, or an absolute one whose containing block sits above the scroller, escapes it; pinned by "a scroller lets through only what it scrolls" in `responsive-smoke.e2e.ts`); a menu, popover, sheet or toast over a control covers it rather than stealing or colliding; the drawer's edge strip is looked through (it hands taps on); a control drawn inside a field's box is the field's adornment; a list row's own actions over its title, whose ::after stretches over the row (ListRow's ⋯ the title runs on under), are layered, not an overlap; a text editor (CodeMirror's contenteditable) is a field, its hit box its own; a checkbox or radio inside its label is measured by the label's box and reach (it carries the hit area); a point outside its clipping ancestors (a tab half scrolled out of its strip) is no tap of the control's; a control with `pointer-events: none` is no target (a tree row's chevron on touch, `TreeView`: a row with children and no action of its own toggles them, so the whole row is the target); a point past the curve of a clipping ancestor's rounded corner (a half-scrolled segmented tab; per ancestor and corner, `e2e/rounded-outline.ts`) taps nothing drawn and counts for no one, while a point inside the curve still counts. Soft-keyboard surfaces (`composer-keyboard`, `composer-keyboard-slash`, `dialog-rename-keyboard`, portrait touch looks) shrink the layout viewport as Chrome on Android does, and the home bar's inset is dropped while `html[data-kb="open"]`.
  - `OMP_GUI_AXE=<dir>` (`e2e/axe-surfaces.e2e.ts`) runs axe-core and a Tab walk (every stop must draw a focus ring: Tailwind 4's `outline-none` beside `focus-visible:outline-2` drew none on ten controls; `tokens.test.ts` also refuses that pair) over the same surfaces on the dev harness, one test per look (`OMP_GUI_AXE_LOOKS=<width>-<theme>-<lang>,…`, 390/412 a phone and wider the Electron window; default 1280 light and dark en, 390 light ko and dark en; `_ONLY=<regex>`), writes `<look>.json` and fails a look on any violation or a surface that did not open; rules that cannot hold are listed in the file with their reason (`region`, the composer's combobox). All four default looks were clean on 23 Oct 2026 (≈ 2 min a look).
  - `OMP_GUI_RESPONSIVE=<dir>` (plus `_WIDTHS`, `_LANGS`, `_THEMES`, `_ORIENT`, `_DEVICE=touch|web|electron`, `_AREA`, `_ONLY=<regex>`, `_SHOTS=all|none`) writes `report.json`, `summary.md` and `shots/`. Run it one look per `bun run locked` hold (`-g "responsive 390P-light-en$"`, ≈ 1.5–3 min) with `--trace off --output <private dir>`: a Playwright locator action has no default timeout (the audit sets 8 s) and a shared `test-results/` is wiped by other agents' runs.
  - The default smoke (390 + 834, en light) refuses page overflow, an escaping element, an off-screen popover and, at 390, an app chrome above 19.4 % of the screen. It also pins what the pass of 20 Oct 2026 fixed: at 390 and 834 no stolen tap, overlap or inset finding on fourteen key surfaces (the feedback and worktree dialogs' checkbox and radio rows, a question card and a figure header among them) and two host sheets, a question card's step tabs and a figure header's buttons as 36 px targets, whole summary figures on a work card and 36 px controls in a docked tablet sidebar; a tap on the drawer's edge strip reaches the PR row under it; a 1100 px Electron window keeps Settings › Memory's tabs clear of the project picker and cuts no Run popover choice; an Autopilot run's board (1133 docked, 390 in the strip) never scrolls sideways, its controls are 36 px targets and the goal bar's Pause, Edit and Drop keep their taps; a picture viewer (`image-viewer`: a chat pane's viewer stays inside the pane under the title bar, the full size's unlayered `100dvh` overridden, its bar's buttons 36 px targets on touch and the picture clear of the home bar) fits the screen; more toasts than a 1280×480 window holds scroll inside it (`Toast.tsx` `data-toast-scroll`, top from `--omp-toast-top`), a wheel over a toast reaching the newest. Every look emulates Reduce motion, and under it a mermaid diagram still lays out: `global.css`'s reduced-motion rule ends animations at 0.01 ms but runs no transition at all (`transition-duration: 0s`), since at 0.01 ms every element began one on any style change and code that styled and measured in one task (mermaid's labels) read the old size.

### CI

- Workflows: `.github/workflows/ci.yml`, `release.yml`, `e2e-shards.yml`, `e2e-nightly.yml` (plus `setup-assets-health.yml` and `skills-bump.yml`, see Built-in skill packs stay current). The repo is public, so every job runs on a GitHub-hosted runner at no cost and the layout follows wall time, not billing.
- **Pre-flight, every push to `main`** (ci.yml; not a `release: vX.Y.Z` push, whose checks release.yml runs; docs-only pushes are skipped via `paths-ignore`: Markdown, `docs/`, `LICENSE`, `THIRD_PARTY_NOTICES.txt`, issue templates, the health-check workflow): the release's blocking checks side by side, so a release finds nothing red that a push did not already show. Jobs: `static` (types, biome, surface policy), `check` (vitest as three jobs: `node`, `renderer 1/2`, `renderer 2/2`; `node` also runs the step "Work card verdict over real journals", the work card's real-card replay and verdict invariants by name, even when its full run failed; see the work-board rule's "One owner of the verdict"), `build`, `win-platform` (`bun run test:platform` on Windows) and `mac-smoke` (`@smoke` on macOS against a fresh build). A pull request runs only the Linux jobs (`static`, `check`, `build`).
- Failures: a failed job writes its failing step and the first error lines to its job summary at once (`scripts/ci-failure.sh`, last step `if: failure()`, read-only `actions: read` token). A failure never cancels independent jobs: `publish`'s `needs` already blocks the release, and `gh run rerun <id> --failed` reruns only what failed. ci.yml cancels a superseded run of the same ref; release.yml never cancels a running run (`cancel-in-progress: false`): a later push or dispatch waits for it, and a newer waiting run replaces an older waiting one.
- **release.yml is the release gate.** Nothing is run on this Mac first. Every job starts right after `prepare`: `build` (only `bun run build` and the `out/` upload; its end is what `win` and `mac` wait for), `static`, `check` (the three vitest jobs), `win-platform`, `mac-real` (`e2e/real-core.e2e.ts` against the latest omp, on build's `out/`), `mac` (package build's `out/`, verify, `@smoke`) and `win` (package build's `out/`, `@smoke`). `publish` needs prepare, build, static, check, `win-platform`, `mac`, `mac-real` and `win`.
  - `mac`, `mac-real` and `win` install their dependencies meanwhile and wait for build's `out/` artifact with `scripts/ci-fetch-out.sh` (polls this run's artifacts, `gh run download`, fails if build ends without one) instead of `needs: build`, which would start them only after build's job is over. None builds a second time, so the packaging tests exercise the one shared build (`out/` is byte-identical on every OS).
  - Why `win-platform` is its own job: inside `win`, `test:platform` held packaging back by ~2 min. The macOS path (package + verify + `@smoke`) is the floor for the time to `publish`; levers left are fewer or faster macOS `@smoke` specs and running `Verify bundle` beside `@smoke`.
  - vitest: the renderer project is most of the work; two renderer shards beside the node job cut the wall time from ~3 min to ~1:10, a third would save little against ~25 s of setup.
- **Full Playwright suite is not part of a release.** `e2e-nightly.yml` (03:17 UTC and on demand) and ci.yml's `e2e=true` run it in 4 `macos-latest` shards from `e2e-shards.yml`. `scripts/e2e-shard.ts` deals whole spec files by estimated cost, because `playwright --shard` counts tests that skip inside their body and leaves a shard nearly empty; `deep-audit` keeps its own `SETTINGS_SHARDS` split inside its shard; each shard installs omp with `bun install -g` (the runner is ephemeral) and Playwright `chromium webkit`. A shard's Playwright run has a 25-minute `--global-timeout` under the job's 30, so a shard that runs long still prints its failures and uploads `test-results/` (the upload also runs on a cancel). Informational; the local `bun run gate` is the full-suite proof. A public repo runs at most 5 macOS jobs at once; raise the shard count only together with that cap.
- Manual checks (`workflow_dispatch` inputs of ci.yml):
  - `install_check=true`: the `install-check` job on `windows-latest` runs `bun scripts/setup-install-check.ts --hide-system-git` (the runner's preinstalled Git for Windows hidden, so PortableGit installs) against a temp USERPROFILE and asserts omp is detected at the minimum, the PortableGit download reported byte progress, the registry PATH refresh found Bun, and stock omp's shell resolves to that Git Bash, not cmd.exe.
  - `installer_check=true`: the Windows setup is one click, per user (`electron-builder.win.yml`: `oneClick`, no `perMachine`; `resources/installer.nsh` removes an all-users copy the old assisted installer left, after one question and one UAC prompt, the only case that asks anything). The `installer-check` job packages it and runs `scripts/windows-installer-check.ps1` silently, as a double-click (it must finish with only a progress bar and start the app), and over `legacy_tag`'s (default `v0.26.0`) all-users install, checking the folder, the Start-menu and desktop shortcuts, the HKCU uninstall entry, the app's window and the uninstall.
  - `win_platform=true` runs `test:platform` on Windows (main's pushes cancel each other); `win_e2e=true` see Windows.
- **Public-repo trust rules.** No workflow uses `pull_request_target`. A pull request (fork or not) runs only ci.yml's Linux jobs with a read-only `GITHUB_TOKEN` and no secrets. release.yml starts only from a push to `main` that touches `package.json` or from a manual dispatch (write access). `MAC_SIGNING_P12_BASE64` and `MAC_SIGNING_PASSWORD` are read only by `mac`'s Package step and only for `main` (a dry run from another ref signs ad hoc). Every job has `permissions: contents: read` (plus `actions: read` where it lists the run's artifacts or jobs, for `ci-fetch-out.sh` and `ci-failure.sh`) except `publish` (`contents: write`), skills-bump.yml's `push` (`contents: write`, `actions: write` to dispatch ci.yml; it runs no third-party code) and the health and bump issue jobs (`issues: write`). Every action is pinned to a commit SHA. Repo settings behind this: "Require approval for all outside collaborators" and read-only workflow permissions. The former self-hosted runner (`ompdesk-mac`) is retired; its secret `RUNNER_STATUS_TOKEN` is unused.
- **Why no bun cache.** `actions/cache` keyed on `bun.lock` saves nothing: a cold `bun install` takes 2–10 s on Linux and ~10 s on macOS (a restore costs about as much), and on Windows restore + install measured no faster than the 28–41 s cold install, with a 42 s upload per lockfile change. So no job caches bun's install. The two caches that pay are the memory build's (`Swatinem/rust-cache` and the built binary, see "Memory (ai-memory)"). A pull request's cache entries are scoped to its own ref, so a fork's run can never put a binary in front of `main` or a release.
- **Windows packaging.** electron-builder packs the NSIS payload at `-mx=9` whatever `compression:` says (61 s of one 262 s `win` run), so `win`'s Package step sets `ELECTRON_BUILDER_COMPRESSION_LEVEL=4` (~27 s for a setup about a quarter larger, ~110 MB instead of 88 MB; the Mac DMG is untouched; never below 4). `ELECTRON_SKIP_BINARY_DOWNLOAD` on Windows fails (gpu-fallback and sidecar tests import electron) and saves nothing. `win`'s lever is fewer `@smoke` specs, since every one guards a Windows-only failure.

### Windows

- **Test scope.** release.yml's `win-platform` job runs `bun run test:platform` (`vitest run --exclude "src/renderer/**"`), the suite minus the renderer. Anything that can behave differently on Windows (paths, PATH lookup, shells and `.cmd` shims, spawn, sockets and named pipes, file modes) lives in main, shared, the bridge or scripts, so its tests run there by default. Renderer tests never read the host platform (pass `"windows"`/`win32` explicitly); `src/main/platform-test-scope.test.ts` fails on a renderer test that checks `process.platform` and pins the script and the workflow step.
- **Windows e2e** (`@smoke`, never run by a human). release.yml's `win` job runs every `@smoke` spec after packaging (~105 s; two `--shard` halves would save ~30 s of wall time but pay a second checkout and install, so they don't). Tag a new spec `@smoke` only when it is worth ~10–25 s there and guards a Windows-only failure. Current set: `machine-setup`, `split-select`, `interrupted-resume`, Model roles, `desktop-surfaces`, `window-theme`, `first-launch-window`, `source-control`, Preview, `steer-send`, `remote-devices`, `oauth-login`, `session-delete`, `autopilot-cycles`, `mobile-web`, `smoke`; macOS only: `terminal` (the Windows e2e jobs install no stock omp, whose PTY natives it runs). Pitfalls each one pins:
  - `interrupted-resume`: kill the app's own main pid; on Windows Playwright's `app.process()` is a launcher one level above it and killing that leaves the app running.
  - `desktop-surfaces`: the tray test runs without `OMP_GUI_HEADLESS` on a real desktop and returns the window with a second launch.
  - `window-theme`: `nativeTheme.themeSource`, pre-paint and the surface colors of both windows, with Playwright's color-scheme emulation off.
  - `first-launch-window`: `dist/win-unpacked/OMPdesk.exe` (or `OMP_GUI_E2E_EXE`), no `OMP_GUI_HEADLESS`, empty profile and saved maximized window; the screen pixels under the window must be one flat color. A Mica window shown maximized stayed blank while its renderer had drawn the app, so `WindowManager.createWindow` gives a window that opens maximized no Mica. A hidden window with `titleBarOverlay` never gets `ready-to-show` once its first frame is slow (electron/electron#54025, reproduced on 36.9.5: a restored window never appeared), so `showOnFirstPaint` (`window-show.ts`) also shows it at `did-finish-load`.
  - `source-control`: the smoke case uses no `gh`; the full flow's stand-in comes from `writeShellGh` (`e2e/fixture/shell-gh.ts`), see Windows e2e pitfalls in docs/windows-dev.md.
  - `steer-send`: Enter, the Send button and the platform's send chord (⌘↵, Ctrl+Enter on Windows) reach the fake omp as `steer`; only `composerFollowUpChord` in `lib/keymap.ts` (⌃↵ macOS, ⌥↵ Windows, because ⌃↵ is ⌘↵ there) sends `follow_up`. Ctrl+Enter once read as the follow-up chord on Windows, so a steer waited for the turn to end.
  - `mobile-web` (~17 s on a developer PC): the fake Tailscale is a `.cmd` shim calling bun in a folder with a space, started through cmd.exe like the fake omp, so the CLI's path and argv quoting are exercised.
- **Fake tools on Windows** (the phone, GitHub sign-in, update and remote specs run on a Windows PC). A fake is a file Windows can start the way the product looks the tool up: omp, the Tailscale CLI, the test installer, Claude Code and the bundled Codex are `.cmd` shims (`writeFakeOmp`, `fixtureTailscale`; the shim calls `bun <script>`); `gh` is a bun-compiled `gh.exe` (`e2e/fixture/fake-gh-install.ts`: `resolveBin` starts only `gh.exe` there, and bun bundles an entry with no extension as data instead of running it); a `gh` stand-in written as a shell script (PR Center, Autopilot release) is `writeShellGh` (`e2e/fixture/shell-gh.ts`): one launcher `gh.exe`, compiled once into `%TEMP%\omp-e2e-fake-gh`, runs the script with Git for Windows' `bin\sh.exe`; an npm global is `<prefix>\node_modules\<pkg>` with npm's `.cmd` shim in the prefix (`extension-update`); the bundled Codex sits under a `WindowsApps` folder, which `classifyInstall` reads as another app's copy (`cli-update`); no login-shell stand-in is written, Windows has no login-shell probe. `mobile-remote-session` plays a Windows host on POSIX with a folder named `C:\Users\admin\.omp\agent`, which cannot exist on Windows, so there the host's agent dir is an ordinary folder. Still macOS only: `github-cli-install` (Windows installs gh with winget only, `selectMethod` in `setup/plans.ts`: no archive download and no managed `tools/gh/bin`, the install it drives).
- Manual run: `gh workflow run ci.yml --ref <branch> -f win_e2e=true [-f win_e2e_grep=<regex>]` runs them, preceded by `scripts/omp-update-lock-check.ts`, on windows-latest with captures in the `e2e-windows-captures` artifact (`OMP_GUI_DESKTOP_CAPTURES`, `OMP_GUI_SETUP_CAPTURES`, `OMP_GUI_SPLIT_SELECT_CAPTURES`, `OMP_GUI_SCM_CAPTURES`, `OMP_GUI_PREVIEW_SCREENSHOTS`). Dispatch from a branch nobody pushes to (ci.yml cancels a superseded run per ref, so a push to `main` cancels a dispatch on `main`).
- The omp update lock check (manual only, 18 s, so it stays out of `win`) exercises omp's auto-update while omp runs: a fake npm registry, the real `bun install -g` into a temp BUN_INSTALL, one process holding the package's files open with a DLL loaded from it, then `SetupService.updateOmp`. On windows-latest the update goes through (Bun replaces the files; the running omp keeps its loaded code and lazy assets), so the app needs no EBUSY handling beyond the recorded failure.
- **Playwright's own Chromium.** A spec that launches it (`chromium.launch()`: `device-prefs`, `pwa-install`) is not `@smoke`. The `@smoke` jobs (ci.yml `mac-smoke`, release.yml `mac` and `win`) and `win-e2e` run `bunx playwright install chromium` (a headless shell is ~196 MB unpacked); `e2e-shards.yml` installs `chromium webkit`. A job that runs such a spec without that step fails with "chromium_headless_shell … Executable doesn't exist".
- **Playwright's WebKit.** `mobile-attach`, `mobile-composer`, `mobile-enter`, `mobile-notification-open`, `mobile-pages`, `mobile-panels`, `mobile-shell`, `mobile-work-strip`, `phone-day`, `phone-run-sheet`, `web-no-reload` and `web-perf` launch `webkit` as an iPhone. None is `@smoke`, and no Windows job installs WebKit (`win` and `win-e2e` run `bunx playwright install chromium`), so they run on macOS (`e2e-shards.yml` installs `chromium webkit`) and on a Windows dev PC, where `bunx playwright install webkit` (60 MB) comes first: without it each WebKit case fails with `browserType.launch: Executable doesn't exist at …\ms-playwright\webkit-<n>\Playwright.exe`, and a `beforeAll` launch (`mobile-shell`) fails its first case and does not run the rest of the describe. That build is not Safari. Measured on it: no `OffscreenCanvas`, no HEIC decoder, `navigator.platform` `Win32`, Korean in Malgun Gothic, and a `resize` that comes after `html[data-kb]` is set by long enough for a read to land between them (`mobile-composer`'s slash menu measures its room on `resize`, so that test waits for the menu to fit). A phone spec asks the page what the browser can do (`typeof OffscreenCanvas`, a decode) or the measured width, never the engine's name, and never skips WebKit on `win32`: everything else it asserts holds there.
- **Stopping an omp needs WMI** (`terminate`, `src/main/sidecar.ts`). `taskkill /T /F` finds the tree through WMI. During an EBUSY hunt on the user's PC WMI wedged (`Get-CimInstance` and `tasklist` failed with 0x80041032 "call cancelled"; it recovered once the leaked test apps were killed): all 94 taskkills then exited 1 and killed nothing, so a closed tab's omp ran until the app exited and every `agent-control-across` run failed `EBUSY` (before: 94 of 96 exited 0). A taskkill that exits non-zero while the child still runs now falls back to ending its stdin (omp exits when it ends) and `child.kill()`; pinned by `sidecar.test.ts` with a failing `taskkill.exe` first on PATH. Never ask WMI from tests or probes: `e2e/process-tree.ts` lists processes with `e2e/win-processes.ts` (run by bun: Toolhelp32 for pid, parent and name, `NtQueryInformationProcess` for the command line, `GetProcessTimes` for the creation time; no WMI, no PowerShell). Beside a running 4-worker suite, 223 of 542 `Get-CimInstance Win32_Process` listings failed with 0x80041032 (1069 ms each); the same 542 asked of the helper at the same moments all passed (167 ms each). A process this user may not open (system services) has no command line there; WMI gave none for them either, and every process an app or spec starts is listed in full.
