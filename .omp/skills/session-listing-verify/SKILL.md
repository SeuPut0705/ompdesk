# Session listing verification

## The promise and the harm

After any order of tab open, close and session change on the host, of changes to the index's rows (a session appears, is written to, renamed, deleted or moved), of reads, lost messages and link drops, once events settle each paired device's list in each window equals the host's current list: a row exactly when the host lists the session, `heldOnHost` exactly when a tab on the host holds it, `openedBySession` naming the opener the host knows. A session the host deleted does not come back in any receiver's copy, and no copy applies a change against a version it does not hold.

If it breaks, a device keeps showing a row as held by a tab that is gone (or hides one that is held), a deleted or moved session stays listed or comes back, a child nests under a wrong or missing opener, or a rename does not show, until something else refreshes the list.

## Bounds and assumptions

- Runs (TLC, all invariants unless noted), after the same-drain read model (F7): `MC.cfg` 2 devices (symmetry), 1 window tab, 1 hosted tab (opened by the window tab), 2 sessions, at most 3 tab changes, no index changes, no drop: deep tier, more than 18.6M states and no verdict yet (2.3M before F7); `MC_delta.cfg` 1 device, 1 hosted tab, 2 sessions (one not yet listed), 1 tab change, at most 2 index changes (create, write or rename, delete, move), 1 link drop: 9.29M states, depth 46, about 11 minutes on one worker; `MC_two.cfg` 2 devices (symmetry), 2 index changes: deep tier, 27.3M states, depth 56, 35 minutes; queues of 3 messages, a link in order, a window's two IPC paths in any order. The deep run (`MC_deep.cfg`) adds a second device that reads the list (`ForeignRead`): 22.6M states, depth 46, 24 minutes. `--tier fast` runs `MC_delta.cfg`, `MC_gap.cfg` and the sanity runs.
- Assumptions (each is a place a bug could hide), the full table is `formal/session-listing/CORRESPONDENCE.md`: the host's messages reach a computer in the order sent (one counted encrypted socket, A1: in order is not the same as a read continuing before the next frame is handled, F7; `MC_gap.cfg` is the run with a link that reorders and passes since F7's guard); a window gets events in order but a reply at any position (A2); the host's read samples rows and tabs in one block and every `sessions.list` reads again (A3); one window feed per computer and host, a read under way is that window's one ask (A4, checked by `OneAsk`); no epoch (A5); a host `emit` does not fail (A6); a handler's mutation and its `listingChanged()` call run in one synchronous block (A7).
- Not covered: a host that restarts, devices older than this build, retain/release of the feed, read errors' backoff, the optimistic hide of a window's own delete (F6), other row fields (`status`, `messageCount`, titles), the snapshot cache. `formal/session-listing/SCOPE.md` lists them.

## Run it

`<tools-dir>` is the folder of the SKILL.md that you see when you read `skill://ompdesk-formal-verify`. In CI and on machines without OMPdesk, use a copy of that folder's `scripts/` and `assets/toolchain.json` (see `references/ci-and-drift.md` there).

```bash
bun <tools-dir>/scripts/verify-all.ts formal --only session-listing
```

A full run takes over an hour on this Mac since F7 (the three heavy matrix runs, then the mutations' baseline on `MC.cfg`); `--tier fast` skips `MC.cfg`, `MC_two.cfg` and the deep run. Read the result like this:
- `PASS`, exit 0: no counterexample within the bounds above. It does not mean the code is correct.
- `FAIL`, exit 1: a property was violated, a mutation was MISSED, or an `@code` tag no longer resolves. A violation prints a trace with one row per step: the action, its `@code` location and the variables that changed.
- `DRIFT:` note under the drift line: covered files differ from the sync commit, so the model needs another look (CI adds `--strict-drift` and fails on it). A sync commit that is not in this repository fails.
- `NOT CHECKED`, exit 3: the tool could not be prepared (for example offline). Report "not checked". Never report it as a pass.

## Does my change touch this?

It does when it changes the host's list (`listingChanged`, `#listing`, `listingSignature`, `#decorated`, `sessions.list`, `#deviceList`), how it is numbered or diffed (`SessionListShare`, `diffSessionList`, `applySessionListDelta`, the version rule), what a delta carries or when it is sent (`onChange`, `emitSafely`), how a computer keeps its copy of a host's list (`HostSessionList`, the link's `state`/`event` handlers, `hostSessionsStale`), who counts as holding a session (`windowSessionFiles`, `#registerSessionFile`, `#unregisterSessionFile`, `onSessionFilesChanged`, a tab's `sessionFile`) or who opened it (`sessionOpeners`, `AGENT_CLOSED_CHILDREN_PREF`), the debounce of `sessionsChanged`, the index's delete, move and rename (`relist`, `#notifyChange`), or the window's feed (`refresh`, its `onSessionsChanged` handler, `reconcile`, `sameRow`, `deleteSession`, `renameSession`); or adds code that changes what a row says without calling `listingChanged()` or `sessionsChanged()`. Search for them: `grep -rn "listingChanged\|heldOnHost\|openedBySession\|windowSessionFiles\|sessionOpeners\|onSessionFilesChanged\|#unregisterSessionFile\|SessionListShare\|HostSessionList\|hostSessionsStale\|hostChanged\|applySessionListDelta" src`. If it does, run the check; if the check or the covered code needs to change, go to "Updating the verification for an intended change".

## A failure: real bug or modeling error?

Replay the counterexample against the real code, step by step, using the `@code` location on each trace row. If a step cannot happen in the code, the verification is wrong: fix the verification and say what was wrong. If every step can happen, it is a bug: tell the counterexample as steps in the code's own words, state the harm in one sentence, and report it; a failing test on the unchanged code is the proof (F3 started as one in `src/main/remote/host-services.test.ts`, the pool half is pinned by `sidecar-pool.test.ts` "announces every take and let-go of a session file"; F4 started as one in `src/main/remote/host-session-list.test.ts` and `session-list-share.test.ts`). Never weaken the property or the model, add a state constraint or add fairness to make the check pass. If a change to the property is intended, say so as a model change and cite the evidence.

One kind of failure is not a code bug by itself: a counterexample whose first step needs a message to overtake another that the link or the IPC paths cannot reorder (check A1 and A2 against the code) is a modeling error. A counterexample that needs only the order frames of one `#drain` and a read's continuation give is real (F7): the model lets the frames of one drain run between a reply's arrival and its read's continuation (`HostReplyArrive`, `HostReplyResume`).

## Updating the verification for an intended change

1. Change the model from the code, before you rerun: each changed part must again point to code a reviewer can open (`@code` tags in `formal/session-listing/tla/SessionListing.tla`, the table in `formal/session-listing/CORRESPONDENCE.md`). One indivisible step in the code stays one step in the model; a new `await` between a mutation and its `listingChanged()` call, or between a read's start and its publish, splits a step. `Open`, `Close` and `Switch` each stand for a hosted tab (`host-services.ts`) and a window tab (`sidecar-pool.ts`) at once; when a change touches only one of them, split the action by tab kind (`t \in WinTabs` / `t \in HostTabs`) so the model can see it. The guards of the delta path are single operators so a mutation can drop each: `BaseOk` (the computer applies a change only against the version it holds), `FeedBaseOk` (the feed does), `HslGap` and `LinkBack` (`MarkStale`: stale and tell the windows), `FeedGap` (the debounced read for a change it cannot apply), `FeedRaced` (an answer older than a named version reads again), `StaleAfterSet` (an applied change does not clear a `stale()`), `PostStale` (a request through the host marks the copy stale), `noted` in `FeedEvent` (a change while a read is under way is noted, not applied), `late` in `HostReply`.
2. Change a property only when the code's promise changed on purpose. Write down the old wording, the new wording and the evidence (doc comment, tests, changelog, commit message).
3. Keep the bounds unless the change makes them wrong. If you must reduce one, say so.
4. Update `formal/session-listing/tla/mutations.json` so each new guard or step has a mutation that breaks it, and `matrix.json` when a finding is fixed (a run that expects the violation must flip to pass, or move into a mutation as F3's and F4's did: `id-change-silent`, `delta-clears-stale`). A guard that no reachable state exercises gets a mutation with an `equivalent` reason, written from the code (`hsl-skips-reread-on-gap`, `hsl-ignores-announced-version`). Rerun. Then break the new code the way the property guards against and confirm the check catches it (the scratch break of `#closeTab` dropping its `listingChanged()` call failed the run on `HeldConverges`; see F3 in `formal/findings.session-listing.json`).

## Known findings

- F3 (fixed 28 Oct 2026): the host re-announces by comparing with the snapshot that ANY device's read last recorded, and `sessionInfoUpdate` with another session id unregistered a window tab's session file without calling `listingChanged()`. Device A listed a session as held; the window's omp reported a new session id, so the file left `windowSessionFiles()` silently; device B read the list in that gap (its snapshot had no held session); the tab closed, `listingChanged()` found the listing equal to B's snapshot and said nothing; device A kept the row as held on the host. The fix: the pool calls `onSessionFilesChanged` on every take and let-go of a session file (wired in `index.ts` to `hostServices.listingChanged()`), so every change is announced when it happens (`CORRESPONDENCE.md` A7). Property `HeldConverges`; tests `sidecar-pool.test.ts` "announces every take and let-go of a session file" and `host-services.test.ts` "a device that listed a session as held hears of it when a window's tab lets go of it" (with `control for F3`). Since the host shares one numbered list (`b53551176`) the mutation `id-change-silent` is declared equivalent: a read that finds the list changed publishes it to every device, so B's read in the gap would have told A; the pool's announce stays.
- F4 (fixed 30 Oct 2026): `SessionListShare.set()` marked the copy current at the share's latest generation, so a change applied to a copy that a `stale()` had marked stale cleared the stale. A device deleted (or renamed, or moved) a session through the host: main marked the computer's copy of the host's list stale (`hostSessionsStale`), the host had not published the change yet, and before the window's own `refresh()` another change of the held version (a turn wrote to another session) applied: `set()` made the copy current, so the window's ask was answered from the copy, which still listed the deleted session (an old title, the old path), until the host's own change arrived about 300 ms later. Property `FreshAfterRequest` (the mutation `delta-clears-stale` is the bug); evidence `formal/session-listing/evidence/F4-trace.json`, `repro-F4-vitest.txt` (failing on the unchanged code) and `repro-after-fix-F4-vitest-pass.txt`. The fix: `set()` publishes at the copy's own generation, so it is no fresher than before.
- F5 (observation, corrected by F7): `HostSessionList` applies a change of the held version while its own read of the host is under way, and the read's answer then replaced the copy. F5 held that the in-order link makes a reply never older than a change that reached the computer before it, so nothing is lost, and that only a reordering link could do it (`MC_gap.cfg`, evidence `F5-trace.json`). That was wrong for this dispatch path: see F7. The guard on the answer's version now closes both, and `MC_gap.cfg` passes (matrix run `link-reorder-is-handled`).
- F6 (observation, not reproduced in the code): the window hides a row it deleted at once (`deleteSession` filters the store) and an answer that was already on its way, computed before the delete, shows the row again until the queued read lands. It self-heals within one read and the copies never regress, so `NoReappear` is stated on the copies and `ListConverges` on the settled view. It is the same before the delta commit.
- F7 (fixed 30 Oct 2026): a read's answer older than the host version the copy holds replaced the copy. The link's `#drain` (`wire.ts`) delivers several frames in one synchronous loop and `client.ts` resolves a read's promise when its reply frame is handled; the promise's continuation (`HostSessionList.#read` resuming) runs only after the loop, so a delta right behind the reply applied BEFORE the read resumed. Device holds h.1, `stale()` (a delete through the host), `current()` starts a read, the host answers h.1 and publishes h.2 (the delete) right behind it: the delta applies and removes the session, then `#read` resumes, sets `hostVersion` back to h.1 and the share publishes h.1's rows over h.2's, `#announced` stays null (the delta was applied, not announced), and the deleted session is listed again until the next change. Reproduced by a failing test on the unchanged code (`host-session-list.test.ts` "keeps a change that applied right behind the answer of a read under way", commit `3b31d6cb9`); the model splits the reply into arrival and continuation (`HostReplyArrive`, `HostReplyResume`; `Next` lets only the frames of that drain run between them) and finds it in 15 steps (mutation `hsl-keeps-older-answer`, `NoReappear`, evidence `F7-trace.json`). The fix: `#read` compares the answer's version with `#hostVersion` (`olderSessionListVersion`, the one version rule in `session-list-delta.ts`) and returns the copy when the answer is behind it. The window's feed (`session-list.ts`) does not have the pattern (it notes a change that arrives while its read is in flight instead of applying it, so the same turn reads once more: pinned by "keeps a change pushed in the same turn as the answer of the read under way"), and `SessionListShare` has no versions of the host's to compare (the guard belongs in `HostSessionList.#read`, the one place that holds both).
