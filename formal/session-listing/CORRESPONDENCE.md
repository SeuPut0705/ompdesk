# Correspondence: session-listing

Sync commit: set by `verify-all.ts formal --only session-listing --stamp` (the same value as `syncCommit` of `session-listing` in `formal/manifest.json`; the manifest wins when they differ).

The `@code path:lines` tags in `tla/SessionListing.tla` are the machine-checked half of this map. This table records what each tag abstracts and the assumptions the model relies on.

How the code is laid out, so the table reads: the host numbers its list of sessions once (`LocalHostServices.#deviceList`, a `SessionListShare`: `epoch.n`) and sends every connected device what changed (`{base, version, set, remove}`, `SESSIONS_CHANGED`); a paired computer keeps one copy per host (`HostSessionList`) and applies a change of the version it holds; every window of that computer keeps its own numbered copy of that (the global feed in `session-list.ts`) and does the same. Whoever holds no copy or missed a version reads the whole list once.

## Assumptions

- A1: the host's messages reach a device computer in the order they were sent (`LinkMode = "fifo"`): one encrypted socket whose frames carry a counter and are refused out of order (`wire.ts` `FrameSealer`, `FrameOpener`), and the host sends the reply in the continuation of the call that took it. In order is not the same as "the reply's read continues before the next frame is handled": `#drain` delivers every frame it has read in one synchronous loop and a read's `await` continues only after it, so a change sent behind the reply can apply to the copy before the read resumes (F7, found 30 Oct 2026; F5 had assumed only a reordering link could do this, which was wrong). `HostReplyArrive`/`HostReplyResume` model it and `HostSessionList.#read` guards it by version. `LinkMode = "gap"` (a reply sent after a later event) is a run that passes with the guard (matrix run `link-reorder-is-handled`; without the guard TLC finds the older read overwriting the newer delta, as in F5).
- A2: a window gets events in order but a reply at any position (`IpcMode = "free"`): the code sends them on two IPC paths (`webContents.send`, the invoke reply) and enforces no order between them.
- A3: the host's read (`sessions.list`, or the debounce) is one block that samples what the index lists and what tabs hold when it ends; the list it awaits (`sessionIndex.list`) includes every change notified before the read began. Every `sessions.list` calls `stale()` first and waits for a read that starts after the call, so an asker sees at least everything that happened before its call. A change's own `sessionsChanged()` timer is set when the index changes, not after the index has read again (the host's read waits for that read anyway).
- A4: the generation counters of `SessionListShare` are two booleans: `dstale` (a `stale()` the copy has not served) and a read's `clean`/`dirty`. A window has at most one ask at its computer's copy (`OneAsk`: its `inFlight` makes the next one queue), so an ask that must wait for a later read than the one under way does not arise.
- A5: a host's numbers are one epoch: a host that restarts numbers from another epoch, no old copy matches it, so a change of the new epoch is a missed version (the same branch as a lost event) and the link came back anyway (`LinkUp` marks the copy stale). Epochs are not modeled.
- A6: a host's `emit` does not fail: `emitSafely` drops an event over the frame cap (16 MiB), which for a delta would mean the whole list is over it too and the read fails.
- A7: every change of what a host tab holds calls `listingChanged()` in the block that makes it (the pool's `onSessionFilesChanged` covers each window tab's take and let-go; `LocalHostServices` covers its own tabs). With that, the single shared snapshot always equals the listing at the last announce or read, so any change from what any device last read is announced; a per-device snapshot is not needed.
- A8: a row is its journal state, `heldOnHost` and `openedBySession`; the other fields (`status`, `messageCount`, titles) are not modeled. The row a window shows is the content of the last answer or applied change (`reconcile` keeps a row object only when `sameRow`).
- A9: one window feed per paired computer and host. Several windows share the computer's copy and each has its own numbered copy: they are separate instances of the same code. The windows of the host's own computer read `SessionIndex`'s copy over IPC with the same feed code; that source has no link and no tabs' overlay and is not modeled apart.
- A10: a window that is closed, or reopened (`retain`, `release`, the `generation` counter that drops an old answer), is not modeled; a feed holds its list for the whole run.

## Granularity

One action = one event handler, timer or microtask chain. Merged steps: a handler's mutation and its `listingChanged()` call (one synchronous block); a read's `#listing()`, snapshot, publish and row building; the host's reply with its delta (the delta leaves first); the reply's delivery with `accept` and `.finally`; `HostReplyResume`'s `finally` branch, its `queueMicrotask(stale)` and the publish (microtasks of one macrotask). The `await sessionIndex.list` inside `sessions.list` is the gap between a device's request and `HostRequest`; the device computer's read of the host spans request, reply and every event that arrives between. Split steps: the reply's arrival and the read's continuation (`HostReplyArrive`, `HostReplyResume`, F7): the frames of one `#drain` run between them and nothing else on that computer does (a timer, an IPC message, the socket's close are other tasks), which the model states by `Busy` (every action but `HostEvent` of that computer and the continuation is disabled while a reply waits in `rp`). The host's own steps are not blocked in reality but commute with the computer's synchronous block, so they are not interleaved inside it. The queue bound `MaxCh` is checked at the arrival; the events of the drain and the continuation may take the computer-to-window queue past it (TypeOK allows `MaxCh + 5`).
