F5 · HostSessionList lets an older read overwrite a newer change if the link ever reorders a reply behind an event

low suspected violated property: ListConverges

HostSessionList applies a change of the held version even while its own read of the host is under way (hostChanged checks the version before it checks the read). If the read's answer was taken before that change and arrives after it, #read sets the host version back and the share publishes the older rows over the newer ones; nothing names a later version (the change was applied, not announced), so no read follows and a deleted session is listed again until the next change. The link cannot do this today: it is one encrypted socket whose frames carry a counter and are refused out of order (wire.ts), and the host sends a reply in the continuation of the call that took it, so a reply is never older than a change that reached the computer before it. The model run with a link that lets a later event pass a reply (MC_gap.cfg) shows the result. Not reproduced in the code, because the code cannot reorder; kept as a finding of the model so a change that reorders (a second connection, a relay) meets it.

Model scope and assumptions

Modeled

  • the host's shared numbered list (#deviceList: changed/stale/current/publish), sessions.list, sessionsChanged and its debounce, listingChanged and the snapshot, the delta or bare event to each device
  • the index's changes as the host sees them: create, write, rename, delete, move
  • the paired computer's copy of the host's list (HostSessionList: hostChanged, #read, stale), the link state and hostSessionsStale
  • the window tabs' register/unregister/notify and the closed-child record
  • the window's feed: refresh, the onSessionsChanged handler, the answer, retries, deleteSession, renameSession, reconcile/sameRow

Abstracted

  • rows are [journal state, heldOnHost, openedBySession]; the host's read samples them in one block
  • the link is in order; the two IPC paths to a window have no order between them (a reply anywhere, events in order)
  • version numbers are integers (no epoch), generation counters are a stale flag and a clean or dirty read
  • a second paired device whose answers go elsewhere is a read that publishes (ForeignRead)

Out of scope

  • a host that restarts, devices older than this build, retain/release of the feed, read errors' backoff, the snapshot cache
  • the window's optimistic hide of its own delete (F6)
  • other row fields, the per-device filter of SESSIONS_CHANGED, several windows of one device

Assumptions

  • A1: the host's messages reach a computer in order (one counted encrypted socket); with a reordering link HostSessionList fails (F5)
  • A2: a window gets events in order and a reply at any position
  • A3: the host's read samples rows and tabs in one block, and every sessions.list reads again
  • A4: one window feed per computer and host; its read under way is its one ask (OneAsk)
  • A6: a host emit does not fail
  • A7: a handler's mutation and its listingChanged() call run in one synchronous block
