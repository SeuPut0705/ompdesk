Findings

F1 · A lower-lane Linux job can take the account's last hosted place while a release macOS job waits

medium confirmed violated property: KeepsLastAccountPlace

An outside macOS run holds the only macOS place (5 of 5 in real terms). A release macOS job arrives and waits for macOS. A land job for Linux arrives, has room in the account and is admitted: no rule is broken, because the release job could not use any free place. The account is now full (40 of 40). When the macOS run ends, the release job still cannot start until a lower-lane Linux job ends. The model reaches this at depth 5 (OutsideStarts, Start release, Start land, Admit land). It is a property of the design's rule (design 5: a free place goes to the first entry that can use it), not a code bug: there is no code. Strict head-of-line would prevent it and is shown wrong by mutation strict-head-of-line (it breaks FirstInLineCanStart). Options for the owner: accept (the 40 cap is far from today's use), reserve the account's last places for release while one waits, or count a waiting release macOS job against the account.

Model scope and assumptions

Modeled

  • start: refuse while paused, reuse a green digest, hold and supersede
  • the pump: lane then arrival, place recorded before the dispatch
  • dispatch answer, run end, cancel landing
  • leases: lapse, sweep, no late renew
  • Pause/Resume
  • outside jobs taking free places

Abstracted

  • one macOS pool and one hosted pool under the account limit, one heavy pool
  • jobs instead of runs
  • one shared key group and one shared digest group
  • no clock: a lease lapses at any moment

Out of scope

  • admission ticket
  • wait/Answer, merge-queue batching, flaky state
  • placement and disk care
  • a stale poller
  • several hubs

Assumptions

  • A1 one admission step at a time
  • A2 the place is in the ledger before the dispatch await
  • A3 outside jobs counted at once (code lags one poll)
  • A4 a dispatch is answered and a run ends
  • A5 lane, pool, key, digest fixed at start
