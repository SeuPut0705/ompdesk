repo-lock-core verification

Unit 2c moves a repository-lock holder's git into ompdesk-core. Within the bounds (one holder, one next holder, a request of 2 gits one at a time and 3 gits two at a time, the core free to die at any step) the next holder never runs beside a stopped holder's git or a git of a dead core, a cancelled request starts no git, a stopped request in flight is cancelled once the core read main's frames, and a stop always hands the lock on. The core's death was a reproduced finding and is fixed: its gits are in its process group (POSIX) or kill-on-close job (Windows), and main settles only once the group is gone. Two limits remain: a git can start between the stop and the cancel's arrival (then ended at once), and a git that survives SIGKILL past 3 s is settled past with an error that says so.

F1 · A core that died mid-write released the lock while its git still ran

medium fixed violated property: NoOverlapAfterCoreDeath

A commit runs in the core and its step is stopped (or the core dies first). The core process dies (a crash, a kill) while the commit's git waits on a hook. Main settled the request (core_exited) at the core's close, and the lock's next holder started while the git, orphaned, kept running. Before 2c the git's parent was main itself, so the same death ended every holder. Fix: The core leads its own process group on POSIX (spawned detached, never unref'ed); when it ends main SIGKILLs the group and settles what waited only once kill(-pid, 0) says ESRCH (3 s bound, then an error and a log line). F2 · A git can start between the stop in main and the cancel's arrival in the core

low confirmed violated property: NoSpawnAfterStop

The stop aborts the step in main and writes the cancel frame; until the core reads it (one pipe write and read), the request's handler may start its next git. That git is ended as soon as the cancel is read, and the next holder still waits for its exit (NoOverlapAfterStop holds). execBin refused such a spawn synchronously.

Fix: Accepted: closing it would make every git a round trip to main.. Model re-check: not-run; mutation check: not-run

Model scope and assumptions

Modeled

  • coreGit: send in a live step, the request's end as the step's effect

  • process.ts #receive and #ended; SerialChain #clearHolds
  • the core's death; main settling its requests after groupGone

Abstracted

  • a killed git is one that exits
  • timings (kill grace, drain bound, timeouts)
  • one request per step

Out of scope

  • main's own file calls in a step (fenced-fs, unchanged)
  • the chain's queue of several steps

Assumptions

  • A1: frames are FIFO both ways
  • A2: the core registers a request's cancel flag before it reads the next frame
  • A3: an answered id leaves in_flight before its frame is queued
  • A4: Windows: the job object ended the core's gits by the time main sees the core's close (not verified on Windows)
