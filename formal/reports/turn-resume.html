F1 · A scheduled retry that fires while offline leaves no `network` marker

medium confirmed violated property: MarkerNetwork

A turn ends in a transient error (a 503) while the link is up: #judge plans a scheduled retry and #arm shows its row. Before the 30 s timer fires the connection drops (report(false)). The timer runs #fire: stillHolds passes, stock retry.enabled is read, then `!network.online`, so #fire releases the row, records the attempt and calls #hold(tab, "retry"): the wait row shows (setAwaitingConnection(true)). #fire returns there and never calls sync(), so deriveMarkers has not run and the marker file has no entry for the tab: a scheduled retry writes none, and awaitingConnection is only turned into the `network` reason by a sync. Nothing syncs until some later run-state change. If OMPdesk crashes or is killed while the tab waits, the relaunch finds no marker and the turn is never continued. #verifyNetwork's own hold calls sync() with the comment "a crash during the wait still retries"; #fire's does not.

F4 · A session or branch change while the wait holds does not end it; stock retry runs in the new session

low confirmed violated property: NoRetryAfterSessionChangeWhileHeld

This is a property the verifier added, not one of the stated ones; whether the behavior is intended is a design question. While offline a turn fails on the network: #judge holds it, the wait row shows and the marker says `network`. The user switches the tab to another session or branch (noteTouched bumps `touched`, sync()). #watchScheduledRetry and #verifyNetwork's continuation compare sessionFile and `touched` and end the retry or the probe; the held wait is not looked at (#judge only ends it for a new run or Cancel). The connection returns, flush() runs #run(tab, "retry") and stock retry is sent to a tab that now shows another session or branch.

F2 · (Refuted, model error) a retry sent into a user's run through a prompt on an omp that is not ready

low refuted violated property: NoRetryIntoUserRun

The first model run ended a scheduled retry's #run waiting in whenReady (the tab's omp not ready), the omp became ready, the user's prompt started a run, and only then did the #run continue and send retry into it. Two steps cannot happen in the code: a run cannot be live on an omp that is not up, and whenReady's resolution is a microtask, so the continuation runs in the same macrotask as the status event, before any prompt. The model was wrong (it allowed a prompt on an omp that is not ready and ran the continuation as a separate step). Fixed in the model: a prompt needs a ready omp, Unready needs every tab idle, Boot continues every waiting #run. The property was not changed.

Model scope and assumptions

Modeled

  • TurnResume sync/#judge/#verifyNetwork/#hold/flush/#run/#planRetry/#arm/#fire/cancelWait/#dropWait and the marker file (deriveMarkers)
  • ConnectivityMonitor verify (one shared probe per host), #check, #reachable, the #attempt recovery loop, report, #set -> connectivityChanged -> flush
  • the pool facts the rules read: running, lastRun, stopped, session/touched, awaitingConnection, as pool events that each end in sync()

Abstracted

  • one tab, one host name, one session counter; four outcome kinds (dns, net, transient, fatal)
  • time is order only: any armed timer may fire at any moment
  • sync() and flush() are synchronous regions run as ordered micro-steps under one program counter
  • the retry RPC is one atomic send

Out of scope

  • launch markers and the relaunch continuation, stock auto-retry takeover, the wake window, hosted tabs, quit freeze, tab close, retry.enabled toggling
  • the duration of the retry RPC (a user prompt while it is in flight is stock's), two tabs at once, attempt counts above 2

Assumptions

  • A1: every pool event that changes a fact is followed by TurnResume.sync() before the next macrotask; setAwaitingConnection does not call sync()
  • A2/A3/A4: sync() and flush() run in one macrotask; a ready sidecar resolves whenReady in a microtask and Boot continues every waiting #run in that macrotask
  • A5: a run cannot be live on an omp that is not up (the F2 model fix)
  • A7: strong fairness per component, and the network eventually comes back (an assumption, not code)
