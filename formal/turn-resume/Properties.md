# Frozen properties: the connection wait

Protocol-level: any correct implementation of "a failed turn waits for the connection and continues, never on top of the user" must hold them. They are defined next to the model in `tla/TurnResume.tla` (a TLA+ property needs the model's variables; see the skill gaps in `formal/findings.json`). Do not weaken or drop one without the user's explicit OK; a change is reported as a model change.

| Name | Kind | Statement | Source |
|---|---|---|---|
| `NoRetryIntoUserRun` | invariant | Stock `retry` is never sent while the tab's live run is one the user started (it has no outcome yet). | `turn-resume.ts:511-521` ("nothing retries into the live run once online"); `turn-resume.test.ts` "a prompt sent during the wait replaces it: the waiting row goes and nothing retries into the new run"; the assignment. |
| `NoRetryAfterCallOff` | invariant | Cancel, Stop, a new prompt, or a session/branch change that happens while a failure is probed or while its scheduled retry is armed never leads to a retry of that failure. | `turn-resume.ts:572-585` ("Cancel, a new run or another failure since: whoever ended this probe also cleared its row"; "Stop, a closed tab, or another session or branch on the tab since the failure: nothing to continue"); `TOUCH_COMMANDS` doc `:139-142`; `turn-resume.test.ts` "%s while the lookup is probed ends it". |
| `WaitEnds` | liveness | Whenever the wait row shows (`awaitingConnection`), it eventually goes, under the assumption that the network eventually comes back (`SCOPE.md`). | `connectivity.ts:1-13` ("holds the state at offline until a probe confirms the way out"); `turn-resume.ts:1-4`; `turn-resume.test.ts` "waits instead of failing, and the stock retry runs once the network is back". |
| `ProbeEnds` | liveness | A probe row (`#probing`) always ends: it answers and the tab holds or plans a retry, or someone ends it. | `turn-resume.ts:560-563` ("the tab shows the wait while the probe runs"). |
| `MarkerNetwork` | invariant | While a wait holds (`awaitingConnection`), the marker file says `network`, so a crash during the wait still retries. | `turn-resume.ts:588-589` and `:706-707` ("The marker says `network` now, so a crash during the wait still retries": after the probe's hold and the scheduled retry's); `deriveMarkers` doc `:89-94`; `turn-resume.test.ts` "keeps a turn waiting for the connection, so a crash during the wait still resumes it" and "a scheduled retry that fires while offline hands over to the connection wait, and the marker file says `network`". Violated before F1's fix. |
| `OneOfWaitOrScheduled` | invariant | A tab has at most one of: a held wait, a probe, a scheduled retry. | `turn-resume.ts:400-406` (`ArmedRetry`), `#mayRetry` `!fact.awaitingConnection`, `turn-resume.ts:544-545` ("no second schedule"); `turn-resume.test.ts` "leaves a network failure the connection wait holds to that wait (no second schedule)". |
| `OneProbePerHost` | invariant | At most one probe is in flight for the host; concurrent asks share it. | `connectivity.ts:109-115` ("One probe per host answers every concurrent ask"). |
| `OfflineOnlyOnNoAnswer` | invariant | The monitor goes offline through a probe only when neither the failed host nor the default way out answered (and the link was up). | `connectivity.ts:109-112` ("Unreachable only when neither the default way out nor `host` answers (a mistyped provider URL alone is not a lost connection)"). |

## Added by the verifier, adopted as the rule (28 Oct 2026)

| Name | Statement | Why added |
|---|---|---|
| `NoRetryAfterSessionChangeWhileHeld` | A session or branch change while a wait HOLDS (after the probe, or the relaunch's offline wait) ends the wait and never leads to a retry or restore of what it held. | The probe checks the session and branch (`turn-resume.ts:585-586`) and the scheduled retry checks them (`#holds`); the held wait did not (finding F4), nor did the relaunch's wait. The user chose the same call-off for both: `#judge` ends it through `#movedSince` (`turn-resume.ts:525-529`, `:767-770`), and `launch()` records the tab's session and `touched` when it holds (`:973-985`). Pinned by `turn-resume.test.ts` "%s while the connection wait holds ends the wait" and "a relaunch held offline for %s ends the wait". |

Sanity (must FAIL, in `matrix.json`): `NeverWaits`, `NeverRetries`, `NeverArmed`, `NeverProbing`, `NeverLaunchWaits`: each interesting state is reachable, so the properties above are not vacuous.

The model has no bug toggles: it describes the code after the F1 and F4 fixes. The bugs it found stay as mutations (`mutations.json`): `fire-hold-without-sync` (F1, breaks `MarkerNetwork`), `held-wait-ignores-session-change` (F4: `#movedSince` never true, breaks `NoRetryAfterSessionChangeWhileHeld`), `launch-hold-records-no-session` (the relaunch's wait as it was, the same property), `flush-skips-recheck` (review M1, the same property) and `ready-skips-recheck` (review minor 2, breaks `NoRetryAfterCallOff`).

Model changes made after a counterexample (reported, not silent):
- F2 (refuted): the first run found `NoRetryIntoUserRun` violated through a user prompt on an omp that is not ready. A run cannot be live on an omp that is not up, and `whenReady`'s resolution is a microtask. The model was refined so a prompt needs a ready omp, `Unready` needs every tab idle, and `Boot` continues every waiting `#run` in the same macrotask. The property was not changed. Trace: `evidence/F2-refuted-retry-into-user-run.log`.
- F1 and F4 fixed (28 Oct 2026): the `FireSyncs` toggle is gone (`FireResume`'s offline hold always runs the `sync()` chain), a held wait records the session/branch it holds for (`wsg`, the code's `HeldWait.since`), and `S_NewRun` ends a held wait whose tab moved (`movedWhileHeld`). No property changed; `NoRetryAfterSessionChangeWhileHeld` joined `MC.cfg` and lost its mutation waiver.
- The relaunch's wait (28 Oct 2026): `Launch` holds the marker's continuation (outcome id `LaunchO` = 0) with `wsg` from the tab, once and offline; `movedWhileHeld` reads `sg[t] > wsg[t]` (the same as `#` for a counter that only grows) so the mutation can stand for a wait that records no session. No property changed; `MarkerNetwork` covers the launch wait through CORRESPONDENCE A9.
- The 28 Oct 2026 review of the F4 fix (M1, minor 2): `FileMoved` moves a tab's session with no `sync()`; `Moved(t)` names `#movedSince` once for `S_NewRun`, `FlushStep` (a moved wait is dropped as `flush()` lets it go) and `Boot` (the continuation looks again once the omp is up); a fired scheduled retry's continuation on its way keeps the armed session in `wsg`. The history variables now count a continuation waiting for its omp as called off by a session change (`MovedOff`, in `NoRetryAfterCallOff`: a retry not yet sent is still scheduled). No property's definition changed.
