## End conditions

`resume/hold-ends.json` is the table (`ends`: one row per end condition and the places it is checked, in precedence order; `checks`: for each place the code looks, the model action that looks) and `resume/ends.rs` applies it: `hold_end(check, since, fact, context)` finds the first row listed for `check` whose `applies` arm holds (`src/main/turn-resume-ends.ts` only re-exports the JSON for the test). `Inst::ends` calls it at each place and decides there only what the end does. The model mirrors it by name: row `x` is the operator `End_x`, check `y` is `Ends_y`, a disjunction of exactly the `End_` rows the table lists for `y`, and the action that looks at `y` uses `Ends_y` (`S_NewRun` uses `Ends_wait` and `Ends_probe`; `MayRetry` = `~Ends_armed` at the tab's own session). `turn-resume-ends.test.ts` compares the two sets exactly (and `ends.rs`'s own test, that the table and `applies` name the same rows); the rows the model keeps constant are its fixed list `OUT_OF_MODEL` (`gone`, `frozen`, `fileWritten`), which may have no `End_` operator.

| Check (`HOLD_CHECKS`) | Code | Model action | Rows |
|---|---|---|---|
| `wait` | `Inst::judge`, a held wait | `S_NewRun` (`Ends_wait`) | `personsRun`, `moved` |
| `probe` | `Inst::judge`, a probe still out | `S_NewRun` (`Ends_probe`) | `personsRun`, `stopped` |
| `probeAnswer` | `Inst::verified`, the probe's answer | `VerifyThen` (`Ends_probeAnswer`) | `gone`, `frozen`, `stopped`, `moved`, `fileWritten`, `otherOutcome` |
| `armed` | `watch_scheduled_retry`; may one be armed (`may_retry`: `S_Judge`, `PlanResume`) | `S_Watch` (`Ends_armed`; `MayRetry`) | `gone`, `frozen`, `personsRun`, `stopped`, `moved`, `otherOutcome`, `notRetryable` |
| `firing` | `fire`'s `still_holds` | `FireStart`, `FireResume` (`Ends_firing`) | the `armed` rows but `personsRun`, plus `busy` |
| `continuing` | `run`'s `stale()` | `RunGo`, `RestoreDone`, `FlushStep` (`Ends_continuing`) | `moved` (ends every hold: `#dropWait`), `personsPrompt` (ends this continuation: `pk`, `rk`) |

Rows the model keeps constant, each a place a bug could hide: `gone` (tab close, SCOPE.md), `frozen` (the quit freeze, SCOPE.md), `fileWritten` (one file per session in the model; only the probe's answer counts a first file written after it), and the `peer`/`device`/no-file parts of `notRetryable` (a `peer` tab's limit wait holds, its backoff retry does not: `HeldFor.limit`, 12 Nov 2026).

Known differences between checks, kept as the code had them and visible in the table: a move ends a held wait and a scheduled retry when `sync()` sees it, a probe only when it answers (`probe` lacks `moved`, `probeAnswer` has it); a first file written after a hold ends a probe at its answer and no held wait (`fileWritten`); Stop ends a probe and a scheduled retry and no held wait (a held wait's tab runs only stock's taken-over retry saga, out of scope).

## Assumptions

Each is a place a bug could hide.

- A1: every pool event that changes a fact (`agent_start`/`agent_end`, `noteStopped`, `noteTouched`, a held tab's session file moving) is followed by `TurnResume.sync()` before the next macrotask (`onRunningChange` in index.ts). `setAwaitingConnection` itself does not call `sync()`. The one exception the model keeps on purpose is `FileMoved`: a move with no `sync()` (a path that forgets to tell the rules), which the continuations' re-check has to catch.
- A2: `sync()` and `flush()` run in one macrotask: no IPC message, timer or event interleaves with them. Promise continuations whose awaited promise is already resolved are folded into the step that starts them. Still true after the move into the core (H2, checked in `resume/machine.rs`): `sync` is `stretch(env, sync_inner)` with the reads main made in that tick (`env`, passed in the call), and `sync_inner` and every function it reaches (`judge`, `exited`, `settle_retries`, `show_resuming`, `take_over_retry`, `plan_retry`, `verify_network`, `watch_scheduled_retry`, `hold`, `flush_prefix`, `drop_wait`, `drop_scheduled`, `start_run`, `arm`) are plain `fn`, not `async fn`: no `.await`, so no yield and no question to main inside them. `flush` is `stretch(env, flush_prefix …)` the same way; `hold` online calls `flush_started` (`flush_prefix` in place, `start(all)`). The tasks they start (`verified`, `planned`, `run`, `fire`) first run in the job's microtasks, after the whole region. A hub call is one job on one thread (A16), so nothing from main or a timer interleaves.
- A3: with a ready sidecar `whenReady` resolves in a microtask, so `flush()`'s `#run` sends `retry` in the same macrotask as the flush. The RPC itself (`await command`) takes time and is not modeled. After H2 this no longer holds as written: see A18.
- A4 (after H2 see A16, A18): `whenReady`'s listener resolves its promise in the status event handler, and `trackMove`'s `end()` resolves the movesSettled waiters, so their continuations run before the next macrotask: `Boot` and `MoveReply` hand them to `rg`, which only `RunGo` can leave and nothing interleaves with (`Idle` = no `pc` region and `rg = {}`). A `MoveReply` runs its `sync()` chain first, then the continuation, as the code does.
- A5: a run cannot be live on an omp that is not up: a prompt needs a ready omp and the omp does not go away while a run is live (`Unready` needs every tab idle).
- A6: one tab; `Tabs = {t1}` in every config. The monitor's probe sharing is checked with consecutive asks of the same tab, not two tabs.
- A7 (assumption, not code): the network eventually comes back (`ReportOnline`, `DefUp`, `HostUp` are strongly fair); each component's queued work eventually runs (strong fairness per component).
- A8: the host `retry.enabled` setting is on; an online launch's own start (`Launch` is offline-only: the online one is the same continuation `RunGo` runs after a flush, with the same `since`), the takeover and the wake window are absent (SCOPE.md).
- A9: a held launch marker is `store = "network"` in the model: the code keeps the launch marker itself (`#pending`, its reason unchanged, `sync()` writes it before the live ones), so a crash during the launch's wait continues it the same way; what `MarkerNetwork` asks ("a crash during the wait still continues") holds for it. A first launch is a fresh process: no run has started (`nStarts = 0`).
- A10: `touched` moves only with the tab's session or branch (`movesTab`: the command worked, was not cancelled, and is no `fork_from`), so `sg` growing is always a real change; a command that bumps `touched` but leaves the tab where it is would end a wait wrongly and has no model step.

- A11 (closed 29 Oct 2026): a prompt of the person's own while the launch's `restore_interrupted` runs (`restoring`) or a continuation waits for a move's answer or its omp (`runWait`) starts a run the continuation cannot tell from its own (`#judge` drops only a held wait or a probe). `SidecarPool.notePrompted` counts such prompts (`personsPrompt`; ipc.ts, a device's hosted tab and its view in host-services.ts); `#run` takes the count when it starts and, at every `stale()`, ends `cancelled` once it moved. `UserPrompt` is enabled in these windows; `NoSendAfterPersonsPrompt` checks it. The baseline is `#run`'s own start, not the hold's: a prompt during a held wait is `#judge`'s (the mutation `keep-held-wait-on-new-user-run` removes that).
- A12: a move command's send leaves `touched` (`sg`) alone; only its answer counts (`trackMove`), a timed-out command as a move (outcome unknown). Every continuation that looks at `touched` first waits for the moves in flight (`movesSettled`): `FireStart`, `FireResume`, `FlushStep`, `Boot`/`RunGo`, `RestoreDone` are disabled or deferred while `Moving(t)`.
- A13 (assumption, not code, unchecked): no second `#run` of a tab starts while one waits for its omp or a move, or its restore runs: `EndRun` needs `runWait[t] < 0` and `~restoring[t]`, so the person's run, whose failure would arm a scheduled retry, ends after the continuation. The code runs both; SCOPE.md.
- A14 (30 Oct 2026): the re-probe is one atomic step: its answer is the world (`link /\ (defOK \/ hostOK)`) as the step runs. The code's `#answers` asks the resolver and ignores the link flag (`net.isOnline()`), so it also goes online when the flag lies; the model's single `link` cannot tell the two apart and so checks the case where flag and resolver agree. A probe answered a moment before the network dropped again is a stale answer in the code and the model alike: the next failure takes the state offline once more.
- A15 (12 Nov 2026, the look's busy hold added the same day): a limit wait is the model's armed retry under the kind `limit` (`Limits = {"limit"}`; SCOPE.md › The limit wait): judged, planned, armed and fired as a `transient` failure, except that `FireStart` needs an idle tab, since `#look` holds the wait while the failed turn's background work keeps the tab running and looks again a pace later (b0c90dd3). The rest of the look (a `sync()`, an `await` on reads of the tab's omp, then the timer again or `#fire`) changes nothing the model has before `#fire` runs, which checks everything again; the `limit` marker and the launch that retries it are not modeled. The safety configs leave the kind out (`Limits = {}`): a limit wait's behaviours are transient ones without the busy drop, so every safety verdict carries over; `MC_live_limit.cfg` and `MC_sanity_limit.cfg` run with it.
- A-settle (assumption, not code, 12 Nov 2026): the failed turn's background work eventually ends (`Settle` is strongly fair in `SpecSettles`, the spec of `LimitWaitGoesOn` only). A limit wait holds while it runs, so without this the wait may rightly hold for ever. In the code a result of that work can also start a turn of its own (`agent_start` with no prompt of the person's), which ends the wait as `personsRun`; the model has no such turn.
- A16 (H2, Nov 2026, hub timing; `native/ompdesk/crates/core/src/hub/mod.rs` header): the pool, turn resume and the connectivity monitor are hub instances on one thread. A call (a pool method, `sync`, `flush`, `report`) is one job that runs to its end; the tasks it woke run after it and before the next job (JavaScript's microtasks); what the instances told main goes out after the job, with a tick. A question main answers at once (`Out::ask`: `onRunningChange` -> `turnResume.sync()`, `look`) is answered while the asking method is suspended, and what main does meanwhile is a nested job of its own (with its microtasks) before the method resumes. A question main answers with a promise (`ask_later`: `startTab`, `command`, `settled`, `verify`, `probe`, the timers) wakes its task as a job of its own, later. The model's atomic regions rest on this, and three things differ from main's single JavaScript thread, none of which changes a step the model has:
  - The woken continuations of a `sync()` that a pool method triggered (`onRunningChange` ask) now run before the rest of that pool method, which TypeScript ran after the whole stack. What the rest of `note_stopped` / `note_counter` / `register_session_file_of` does after `on_running_change` (the owner map, `on_session_files_changed`) is nothing the resume reads.
  - `verified`, `planned`, `fire`, `look_task` and `run`'s tail read the facts with one more question to main (`look`, answered at once) where the TypeScript continued in the same tick as its `await`: main reads the facts when it answers and the stretch uses that read; main's next call to the pool queues behind the answer, so no pool event falls between the read and the step. Only a timer or a later-answered promise can, macrotasks the code could always have between an `await` and its continuation. `stale()` (`settled`: main waits for the moves in flight, then reads the facts in the same tick) and `fire`'s first check keep that shape: the model's `RunGo`, `FlushStep`, `FireStart` are the stretch after the answer.
  - Not as before: see A17 and A18.
- A17 (H2, unchecked, found by the retag): `Monitor::set` no longer runs `flush()` in the same tick. It pushes `changed`; main handles it after the job (for a call such as `report` in a microtask after the call returned, so the same macrotask as before; for `attempt` and `reprobe`, woken by a probe's answer or a timer, in a macrotask of its own) and then calls `turnResume.connectivityChanged()` = `flush`. The model's `AttemptDone`, `Reprobe` and `ReportOnline` go online and start the flush chain in one step (`pc = "flush"`, nothing interleaves). In the core a pool event, a prompt or a second `changed` can run between the state going online and the flush. What it does there: `sync()` in that window finds `should_wait()` false and so does not `hold` a new failure, and a `hold` while online flushes every held tab in place (`flush_started`), so the later `flush` finds nothing; an old held wait stays held until one of the two runs. The model has no step "online, waiting continuations not yet flushed, an event comes first"; it is a modelling gap to close (a `pc`-less `FlushPending` flag), not a failing property. Settled by the integrator from the code: every wake of the monitor in the core comes from main inside one of main's macrotasks, and its `changed` reaches main in that same macrotask. A timer is main's (`schedule` asks main's `setTimeout`), whose callback makes the synchronous `timer` call; a probe's answer is a promise of main's, whose resolution sends `hub.answer` synchronously (`Hub.#answer`, no call under way), and the continuation it wakes runs in the core before that call's tick is handed back, its items in a microtask of the same macrotask. The core runs no timer of its own for the monitor, and main's thread handles no IPC, pool event or prompt until that macrotask ends. So going online and `flush` stay adjacent for main, as the model's one step says.

- A18 (H2, unchecked, found by the retag; the model's `RunGo`, `FlushStep`, `RestoreDone`, `FireStart` rest on it): in TypeScript a continuation's `await stale()` and the command it sends were adjacent in one tick (A3). In the core they are two steps with a round trip between: `stale` asks main (`settled`, answered as a promise once the moves in flight are over, with the facts read in that tick), the task wakes as a hub job, re-checks (`hold_end("continuing")`, `called_off`) and pushes the `command` question; main sends the RPC when it handles that item, in a later macrotask of main's (or inside the next blocking call into the core that main makes, which handles the frames written before its answer). A move or a prompt of the person's that main handles between the check and the send is not seen by the check that guarded that command (the next `stale` sees it). `start_tab`, `when_ready` and every command are such round trips too, so `run` has real yields where the TypeScript had microtask hops, and the model merges them into one step (Granularity, `RunGo`). Whether the window can break `NoSendWhileMoveInFlight` or `NoSendAfterPersonsPrompt` is not analysed: main's IPC path for a prompt calls the pool with a blocking call, which handles the already-written `command` item first, so the person's prompt is then sent after the continuation's command, not before it. A model that splits the check from the send (a `sendPending` flag read by `MoveSend`/`UserPrompt`) would settle it. Settled by the integrator from the code instead: the hub writes a job's lines before it runs the next job, main's blocking call handles every line written before its answer before it returns, and the `command` item's handler calls `client.command` synchronously (its lane takes messages in main's call order). So a check that passed reaches omp before anything main sends after its next call into the core. The person's prompt calls `notePrompted` (`ipc.ts` 876-879) and a move `beginMove` (`ipc.ts` 1069) before they send; `beginMove` keeps its `MovesInFlight` in main and so makes a barrier call (`hub.barrier()`, `hub.sync`) first, which it did not when the retag found this: a move sent while main had not yet handled an already written `command` could precede it. With the barrier the merged step holds as modelled.

## Granularity

One model action = one macrotask, or one promise continuation that waited on I/O or a timer (in the core: one hub job, or one task woken by an answer or a timer). `sync()` and `flush()` are regions the code runs without yielding: the model runs them as a fixed chain of micro-steps behind `pc`, which merges nothing the code performs separately.

Places where the model merges steps the code performs separately:

- `#judge`, `#watchScheduledRetry` and `deriveMarkers` run per fact in a `for` loop over all tabs; the model runs the chain for the one tab that changed. A fact for another tab does not change in the same `sync()`.
- `flush()` runs `#run` for every held tab in one `Promise.all`; the model handles all held tabs in one step.
- `Promise.all([ask(), ask(host)])` of `#reachable`: the model samples both answers at one instant.
- `#attempt`'s `isOnline()` check and the probe are sampled as `link at start` and `defOK/hostOK at end`.
- `#fire` between `FireStart` and `FireResume`: `await #stockRetryOn` is one step (the RPC's own duration is not split further).
- `RunGo` and `FlushStep` handle all of one tab's continuation in one step: the code's several `await stale()` between its commands are microtask hops while no move is in flight, and a move in flight defers the whole continuation.
- `RestoreDone` stands for everything the launch sends after its restore (stock `retry`, the unwritten prompt, the goal resume): one second command, checked like `#run`'s `send`.
