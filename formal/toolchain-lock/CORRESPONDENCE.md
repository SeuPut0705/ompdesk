Every action carries a `@code` tag with its lines (checked by `verify-all` to resolve; the ranges were read against the code at the sync commit). One action is one file-system call (or one pure decision on what was read): node's sync fs calls do not interleave inside one process, while another process can run between any two of them.

## Assumptions that could hide a bug

- A dead process's lock folder changes only through a takeover (no other writer, no pid reuse to a process that would write the same token).
- `rmSync` recursive is atomic. In the code it unlinks `owner.json` before the folder: in between, `judge` sees a folder without owner whose mtime was just updated, which counts as fresh, the same verdict as for a folder being made (and a takeover cannot judge it: it needs the guard, which the remover holds).
- Weak fairness of every process step and of `R`'s release, strong fairness of the guard waits of `release` and `R`'s release. The acquire's look (`AcqPeek`) is needed for `Termination`: without it two waiters polling a held lock take the guard in turn and every takeover finds it busy (a livelock TLC finds; mutation `acquire-without-peek`).
- A guard holder that has not stalled is not slower than 30 s and does not die while holding it (a dead one: the next waiter reclaims the guard after 30 s, modeled as the stalled holder).
- A stall is modeled as time passing under the guard; it ends the holder's right to act (`Ok` fails) and lets `Reclaim` remove the guard. What the model cannot say: a stall that starts after `Ok` returned and ends after a reclaimer removed the guard and another holder changed the lock, before the call that `Ok` guarded (`Recheck = "gap"` is that run; it fails, `matrix.json` race 8). The code narrows this window to the two adjacent statements, the check and the call, and the time bound (a third of the stale time) makes a reclaim before the check unlikely to be missed.
- `stale` is a flag, not a clock: a holder that sleeps for a minute, not five, is not modeled (it is simply not stale).
- The release of a holder on this computer matters for exclusion only through the guard's uniformity: the model finds the gap only through `R`'s release (a local live holder is never judged abandoned; mutation `local-release-skips-guard` is recorded as equivalent). The real-code test "takes the guard to release" (a peer told it is on another computer) pins the local release path.
