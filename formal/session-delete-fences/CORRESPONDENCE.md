## Assumptions and boundaries

1. A successful storage operation removes the one modeled file before the index invalidation. With no external writer, later store samples cannot contain it. The model does not prove this about the filesystem or stock.
2. No crash, tombstone eviction, or failed tombstone persistence occurs. `DeletedSessions.add` mutates memory synchronously but requests persistence through `AtomicSaver`; durability is not atomic with file deletion.
3. The paired host's reconnect invalidates its local cached list and a successful new request reaches the current numbered host source with the modeled wanted-generation rule. `HostSessionList` version comparison, delta application, announced versions, connection transport, and multiple consumers are outside the state machine. The separate `session-listing` model covers transport and ordering at its own abstraction, but its drift is not green for this candidate. There is no claimed composition or end-to-end paired-cache proof.
4. The requesting renderer's successful delete response follows the host's index notification and in-memory tombstone. This is a modeling boundary, not a guarantee for independently acting renderers.
5. No intervening synchronous callback throws in tombstone insertion, deleted listeners, or count release. A storage operation that physically removes a file and then rejects is excluded.
6. Source reads and await completions are abstract interleavings. `ReadAnswer` separates obtaining a copy from the renderer continuation to cover a pending answer; actual promise and event-loop ordering can rule out some traces. The optional kind branch and already-resolved promises are over-approximated as yields. Validate a trace before calling it a defect.
7. Shared reads start only when the copy is stale. The model allows one independent stale event and two delete notifications. It tracks one shared underlying read and two bounded feed requests per scope. It assumes the relevant listed ID is the modeled path rather than another duplicate path.

The atomicity rule is one source region between real awaits, a synchronous handler, or an external storage effect. The physical storage effect and its promise continuation are deliberately separate. The index notification and outer tombstone continuation are separate to avoid ruling out an intervening microtask, even where a concrete promise settles within the same event-loop turn. The final open check, sidecar construction, and tab-map insertion are deliberately merged because there is no await between them. `Reconnect` combines a link transition with a later feed teardown/rebuild and is a scenario abstraction, not one atomic production event.
