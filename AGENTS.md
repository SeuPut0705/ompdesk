# ompdesk — Development Rules

Read this before any edit in this repository. Every rule here and in the area rules below binds; a "user's rule" is a product decision by the user and is never undone without them.

## Area rules

This file holds what every change needs. Each area's detailed rules (its user's rules, measurements and pinning tests) live in `.omp/rules/<name>.md`; omp lists them as domain rules and serves each as `rule://<name>`. **Before changing a file an area covers, read that area's rule in full.** A cross-reference such as "see Remote devices › Gate" names a section heading inside one of them.

- `multi-viewer-web` (`.omp/rules/multi-viewer-web.md`): Tabs shared by several windows, the paired phone/web page (server, auth, threat model, reloads, PWA and push, Tailscale serve, phone preview and terminal, per-device prefs).
- `no-loading-screens` (`.omp/rules/no-loading-screens.md`): The user's no-spinner rule: snapshot cache, skeletons, preload, ghost tabs, boot shell geometry.
- `settings-layout-look` (`.omp/rules/settings-layout-look.md`): Settings layout and minimal-settings rule, figure headers, phone/tablet layout and touch targets, themes and contrast, profile and reply language, sidebar header, memory and projects.
- `composer` (`.omp/rules/composer.md`): The composer: Stop/Esc/queue, delegation strength, working cue and age slot, toolbar and Run chip, phone composer, Run sheet, input mechanics, dictation, touch Enter.
- `smart-features` (`.omp/rules/smart-features.md`): Prompt suggestions and inline completion, mojibake refusal, automatic session titles, automatic Plan/Goal choice, judge-model assists.
- `autopilot` (`.omp/rules/autopilot.md`): Autopilot runs: board, branch and target, no soft stops, start sheet and land shipping, permissions, restart, AUTOPILOT.md guide and release facts, checked cycle reports.
- `control-tools` (`.omp/rules/control-tools.md`): The ompdesk_* agent tools: safety and full control, app control, the control socket and `ompdesk` CLI, the ompdesk skill, worker contract, worktrees and review list, other windows and devices, mailbox, shared checkouts, schedules, worktree seeding and names.
- `panels-sidebar` (`.omp/rules/panels-sidebar.md`): Composer history and stats, side panel and view sheets, sidebar families and subagent titles, split view, files the conversation names, Preview (agent browsing, visuals), SSH tools.
- `memory` (`.omp/rules/memory.md`): ai-memory: the Memory page, client, binary build and staging, service lifecycle, coverage, learning, care, recall, sync between computers, privacy.
- `work-board` (`.omp/rules/work-board.md`): The work board (sections, one-line rows, money, the strip where it cannot dock), children at work, the work card's checks, findings and steps.
- `builtin-packs` (`.omp/rules/builtin-packs.md`): MCP server state and sign-in, built-in REA, pstack engineering mode, ECC skills, automatic skill-pack bumps.

- `app-updater` (`.omp/rules/app-updater.md`): OMPdesk's updater: auth, release lookup, install modes, automatic install timing, update log.

- New detail about an area goes into its rule file, never here. This file stays under 64 KB (`src/main/agents-md.test.ts`): every byte of it rides in front of every request of every session in this repository.
- A new area gets its own rule file with `description` and `globs` frontmatter and a line in the list above.

## Architecture

```
renderer (React) ── IPC ──▶ main (Electron)
                              ├─ src/main/local/*      fork-era commands served in main
                              │     (git/gh, fs, ~/.omp files, `omp` CLI, translation to stock RPC)
                              ├─ src/main/sidecar.ts   spawns `omp --mode rpc-ui -e <gui-bridge>/index.ts`
                              │                         (stock RPC over stdio)
                              └─ src/main/bridge-client.ts ◀── unix socket / named pipe ──▶
                                                         resources/gui-bridge/*  (omp extension,
                                                         live AgentSession access)
```

### Command routing and IPC

- The renderer speaks one command set. `RpcClient.command()` (`src/main/rpc-client.ts`) first looks for a **local handler** (`src/main/local/index.ts` merges `src/main/local/<area>.ts` maps; duplicate keys throw at startup). Commands without one go to stock omp unchanged.
- A local handler (`LocalHandler`, `src/main/local/types.ts`) works in main (git, gh, files, `ctx.omp.run([...])`), translates to stock RPC (`ctx.send(...)`), or calls the bridge (`ctx.bridge.request(method, params)`) for live session state.
- Main's IPC handlers register through the one `IpcRegistry` (`src/main/web/ipc-registry.ts`, created in `index.ts`), never on `ipcMain` directly: `ipc.handle(channel, (caller, …args) => …)` / `ipc.on(…)` register on `ipcMain` and in the table the web client is dispatched from. A handler finds its window as `caller.win` (`ClientWindow`, `src/main/web/client-window.ts`) and the page as `caller.sender`. Only a dialog sheet, the title-bar overlay or the preview take the native `caller.browserWindow`.
- `window.omp` is `createOmpApi(transport)` (`src/shared/omp-api.ts`): the preload hands it an `ipcRenderer` transport and adds only `fs.pathForFile`; a paired web page hands it a WebSocket one. A new API member goes in `omp-api.ts`, never the preload. Every channel is classified in `src/main/web/ipc-policy.ts` (`IPC_POLICY`, typed over the channel union: a new channel does not compile without a direction, a `WebPermission` and a web mode; `ipc-policy.test.ts` matches it against the registered handlers and the channels `createOmpApi` subscribes to). Web frames and permissions: `src/shared/web-protocol.ts`.

### Bridge

- **Bridge** (`resources/gui-bridge/`): an omp extension loaded with `-e`. Area modules export `methods` maps; `env.session()` is the live `AgentSession`, `env.pi.pi` the stock package index. Bare `@oh-my-pi/pi-coding-agent/...` subpath imports resolve through omp's resolver. These are **internal omp APIs without semver**: keep methods small, feature-detect, throw clear errors.
- A feature's pure rules (`<name>-core.ts`), runtime wiring (`<name>-engine.ts`), per-session memory (`<name>-state.ts`) and dependency-free contracts main and the renderer import (`<name>-contracts.ts`) sit in the folder of the module that registers the feature: `modes/` (auto mode, auto title, delegation, prompt suggestions, output style, profile, goal time, visuals), `extensions/`, `stock-helper/`, or the root beside a root area module (`session-recap.ts`, `reset-passes.ts`, …; `timer-core.ts` serves two). Contracts shared with the renderer live in `resources/gui-bridge/`, never outside `extraResources`.
- **Compatibility self-check**: every omp internal a bridge module uses is listed per GUI feature in `resources/gui-bridge/capabilities.ts` (`REQUIREMENTS`); add it there (and the module to `LOADERS` in `health.ts`, literal specifier) whenever a bridge method starts using one. `index.ts` loads each area module separately, `guard(feature, methods)` refuses a feature's methods with `unsupported_omp` while anything it needs is missing, and the `capabilities` method reports them. `src/main/bridge-health.ts` probes once per omp version per launch; the renderer toasts the result. `OMP_GUI_BRIDGE_PROBE_HIDE=<label>,…` (labels as `capabilities` prints them, e.g. `AgentSession.setPlanModeState`) makes the probe treat those internals as missing, to rehearse a broken omp.
- **Only the running omp's modules**: omp serves a bridge's literal `@oh-my-pi/*` import from the running omp's bundle only when the bundle registers that subpath (its legacy-pi module registry; pi-coding-agent's `./*` catch-all is not in it); any other subpath falls back to the package's source file, a **second module graph** with its own settings registry, whose setting handles read other settings' slots of the live session (omp 18.12.2: `goal.enabled` read `[]` and 333 of 557 settings read wrong through such a copy). `health.ts` reads each loader's rewritten target (`TARGETS`: `omp-legacy-pi-bundled:` = the running omp's, `file://` = a copy) and refuses a feature whose module is a copy not in capabilities.ts `COPY_SAFE` (each entry says what of that copy is used and why), labelled `<specifier> (separate copy, not this omp's module)`. Reach an unbundled internal through a bundled module instead: a setting by id with `config/registry` `lookup` (`goal.enabled`, `goal.continuationModes`), a package root (`@oh-my-pi/pi-ai` for `resolveCredentialIdentityKey`), a stock tool (`tools/security-scan` `SecurityScanTool` for the security coordinator, whose `status` also recovers stored scans' operations; `tools/manage-skill` `ManageSkillTool` for managed-skill writes, which join the session's per-skill mutation chain; `tools/tts` `resolveSpeechCandidates` for the speech chain). **Known gap**: omp's bundle has no `tts/*`, so read-aloud still uses a copy of `tts/tts-client` (its own worker, tiny-model device/dtype from the environment, not `providers.tinyModel*`) until upstream bundles it. Pinned by `bridge-stock-settings-stock.test.ts` (installed omp: config's `plan/goal/security.enabled: false` hold through auto mode, guided goal and a security scan; the copies seen equal `COPY_SAFE`), `bridge-security-stock.test.ts` (a scan an earlier process left running reads failed, scan and operation alike, on the dashboard's first read: scans are read after stock's recovery) and `bridge-capabilities.test.ts` (every extension-side stock import is a `REQUIREMENTS` module, so the check sees it).
- **Source copies stay off omp's startup path** (measured on Windows; `resources/gui-bridge/capabilities.ts` `HEAVY_COPIES`): the first import of `config`, `tts/*`, `sdk` or `skillshare/*` makes bun transpile omp's source tree on omp's only thread, ~1.1 s warm and 4 to 6 s with a cold transpiler cache (right after `omp update`), and proportionally more on a busy machine. No area module imports `config` or `tts/*` statically (`bridge-capabilities.test.ts`; `extensions/agents.ts` and `voice.ts` import on use), and the startup `capabilities` probe leaves all of them unevaluated (`probe(env, features, {evaluateHeavy: false})`: present when the file exists). A missing export of theirs therefore shows when a feature first uses it, as `unsupported_omp`, not as a startup toast; `guard` still evaluates them on a feature's first call, except `PRESENCE_ONLY` (`sdk`, `skillshare/*`: no bridge module imports them, only the stock helper loads them in its own process), which no probe evaluates in omp: `providers`' first call, which a window asks right after a tab's `ready`, held omp's thread ~1.1 s on `sdk` and every request of the tab waited behind it (macOS, omp 18.13.1: a `get_state` sent beside it answered in 1.1 s, 34 ms without). Measure a new bridge import that resolves to a source copy before it ships (`PI_DEBUG_STARTUP=1` makes omp print its phases to stderr).
- **Bun's transpiler cache is off for a session's omp on Windows** (`ompBunDefaults` in `src/main/omp-runtime.ts`, set under the user's own environment at `SidecarManager` spawn): omp's start with an empty cache (right after `omp update` or a bridge file change) was ~4 s slower than with none, and a warm cache ~0.4 s slower (measured, 18.12.3 on bun 1.4.3, `BUN_RUNTIME_TRANSPILER_CACHE_PATH=0`). macOS keeps bun's default until it is measured there.
- Composer state uses stock `get_state` (session identity, resolved thinking) and stock `cycle_model` (forward cycling); the bridge adds only missing state, backward cycling, tool provenance/mounted tools and the GUI `/copy` tree around stock `pi-tui/overlays/copy-targets`. The model pool was removed (pref `modelPool` deleted once at startup; `ompdesk.model-pool` journal entries ignored).

### omp runtime and version floor

- `src/main/omp-runtime.ts` finds omp (`OMP_GUI_OMP` override → login-shell `PATH` → `~/.bun/bin/omp`, `/opt/homebrew/bin/omp`, `/usr/local/bin/omp`; Windows `%USERPROFILE%\.bun\bin\omp.exe`, `omp.cmd`/`omp.exe` on `PATH`) and enforces `MIN_OMP_VERSION` (18.12.6, for pi-catalog `isPromptCachePersistent`, which idle compaction asks like stock; earlier 18.12.3 for the `always-ask-cached` approval mode; it only moves with a newer requirement or an audit). A bin that links to `<package>/dist/cli.js` (a bun or npm global install) is versioned from that package's `package.json` (`installedVersion`); any other layout runs `omp --version`, which cost 0.3 s of every launch in front of the first session. Every bridge feature in `capabilities.ts` is required at that version. When a feature needs a newer omp, raise `MIN_OMP_VERSION` instead of carrying an older-omp fallback. The fake omp (`e2e/sidecar-fixture.ts`) reports the minimum.
- Only an omp that runs from its package counts (`pickOmp`/`isCompiledOmp`): the bridge's `@oh-my-pi/*` imports cannot resolve in a compiled omp (Bun's standalone build), so one is passed over in the lookup and, alone, fails `compiled`; machine setup reinstalls the package, moving the compiled omp out of Bun's launcher path first (`setup/compiled-launcher.ts`: `bun install -g` alone fails EEXIST over it on POSIX and keeps a running one on Windows). The package's `engines.bun` gates the Bun its shebang would find (`bun-too-old`; setup upgrades Bun, falling back to Bun's installer). OMPdesk's omp update reads the target's `engines.bun` and upgrades Bun before stock `omp update`, whose launcher repair otherwise swaps in the compiled omp (28 Oct 2026; `.omp/rules/machine-setup-updates.md`). OMPdesk never asks the person to run a command to fix Bun or omp (the user's rule, 29 Oct 2026).

### Stock helper workers

- Main-side stock operations without a tab run in three lazy Bun workers (`src/main/stock-helper.ts`, `resources/gui-bridge/stock-helper/host.ts`, routing in `dispatch.ts`): `terminal.*`/`pty.*` → terminals worker (every request concurrent); `extensions.*` → extensions worker (own serial lane: a plugin upgrade runs `bun install` for minutes and must neither block session scans nor be recycled); everything else → the stock worker's serial lane, except the read-only probes in `stock-helper/sessions.ts` `UNQUEUED_METHODS` (`sessions.owned`), answered at once beside it: a restored tab's omp spawns only after it answers, and queued behind launch's session-list scan it waited 0.3 to 0.9 s for the scan. A hung stock call can never take a shell or a running upgrade with it. Area handlers register request names; resolve stock modules from `OMP_PACKAGE_ROOT`; never boot an agent or call a model.
- Each request has its own 30 s timeout (`stockHelperRequest(method, params, { timeoutMs })` overrides; armed before the worker starts). It fails only that request and sends `{cancel: id}`, so the worker skips it if not started (a mutation never runs after its caller was told it failed) and answers `withdrawn`. If a timed-out request still has no answer 30 s later, the lane is stuck: main logs it, fails what waits behind it, kills the stock worker and starts a fresh one on the next request. The terminals and extensions workers are never replaced for a slow request. stdin EOF and app quit stop all workers.
- The session index uses read-only `listAllSessions`/`listSessionsReadOnly` and keeps only GUI chat labels, scope filtering, duplicate-id suppression and change notifications. Changes come from one recursive `fs.watch` of the sessions tree (`SessionIndex.start`; never a watch per directory, chokidar's way: on macOS each new one recreates libuv's single FSEvents stream and drops session files written meanwhile). Picker and sidebar list no session without content (`sessionHasContent`, stock's `filterSessionsForPicker` rule). The legacy chat label is read from a session file's header once per session id (`#legacyChat`): every window lists again after each settled append while an agent streams, and re-reading every file's head was 2.4 of a list's 3.5 ms main CPU (33 sessions, 28 Oct 2026).

### Deleting a session

- Deleting never starts another session. The tab holding it closes as closing a tab does, and only then does the stock worker's `FileSessionStorage.deleteSessionWithArtifacts` remove the file (a file already gone counts as deleted, as in stock's `dropSession`). The renderer closes its own window's tab first (`closeDeletedSession` in `stores/tabs.ts`: the window's last tab gives way to the empty start tab, `placeholder`, with no sidebar row and no file until its first run; the closed-tab history forgets the session). `deleteSession` (`session-mutations.ts`) then calls `SidecarPool.closeSessionTab`, which closes a tab another window holds or a paired device's request reaches (its window hears `TAB_LIST_CHANGED` with `closed`), refuses while that tab runs a turn or compacts, and waits until the omp that had the file open has exited (`#exiting`; `LocalHostServices` waits the same way). There is no `drop_session`: stock `new_session` writes its header at once (≥ 18.11), so a leave-for-a-fresh-session delete left a "New session" row after every delete.
- A deleted session never comes back (`src/main/deleted-sessions.ts`). A successful `deleteSession` (the one path for the sidebar, `/delete`, `ompdesk_session_stop {delete}` and a paired device's `sessions.delete` on its host) records a tombstone (session path, plus the host's `device` for a remote one) in `<userData>/deleted-sessions.json` (0600, newest 2000). Every path that could revive it asks:
  - `SidecarPool.acquire` returns null (reopen from another window's closed-tab history, a child, any restore).
  - `sanitizePersistedTabLayout` drops the saved tab (desktop `tabLayouts`, web `webTabLayouts`); a missing file **without** a tombstone still becomes a fresh tab in its folder. The launch writes one `tab-layout` line to `gui-runtime.jsonl` with the windows and tabs restored and each tab left out or started fresh, by reason (`folder`, `deleted`, `duplicate`, `fresh`; `TabLayoutDrop`, `logLayoutRestore` in `index.ts`; pinned by `tab-layout.test.ts`).
  - `TurnResume.launch` drops and purges its marker.
  - A host's `tab.open` refuses `session_deleted` for a device whose layout still names it; that device's `RemoteSidecar` emits `sessionDeleted` and its pool closes the tab and records the tombstone under the host's id instead of showing an error tab.
  - `SessionIndex.list` never lists it, even if a stray writer recreated the file.
- A never-written session (first turn cut off before stock wrote its file, marker `prompt`, `#unwrittenSessionTab`) has no tombstone and still continues.
- Renderer: `sessionListFeed(...).deleteSession` drops the row from both scopes' feeds and snapshot copies (`lib/snapshot-cache.ts`), and every global list read prunes the local snapshot of rows it lacks, so a session deleted on another device never repaints after reload. Ghost tabs (`lib/tab-snapshot.ts`) become real only when the live tab list names their session.
- Pinned by the tombstone cases in `session-mutations.test.ts`, `tab-layout.test.ts`, `turn-resume.test.ts`, `sidecar-pool.test.ts`, `remote/host-services.test.ts`, `remote/remote-sidecar.test.ts`, `session-index.test.ts`, `stores/session-list.test.ts`, and the relaunch over a stale layout and marker in `e2e/session-delete.e2e.ts`.

### Packaging
- Packaged apps ship `resources/gui-bridge` **outside the asar** (`extraResources` in `electron-builder.yml` and `electron-builder.win.yml`; `src/main/packaging-config.test.ts` enforces it). The app contains no `omp` binary.
- Packaged apps keep only Electron's `en-US` and `ko` locales (`electronLanguages` in both builder configs; never `en` alone, which deletes `en-US.pak` and blanks the window, issue #12). `scripts/after-pack.cjs` fails the package unless exactly those survive. Chromium's locale is then en-US for every other system language, so `src/main/system-languages.ts` seeds the Windows spellchecker (default and Preview sessions) and the Preview's Accept-Language from `app.getPreferredSystemLanguages()`; `e2e/preview.e2e.ts` checks the header under `--lang=de`.
- All three bundles are esbuild-minified with identifiers kept (`electron.vite.config.ts`), so `scripts/check-main-bundle.ts` reads the main bundle's imports with Bun's parser (against Node's builtins; Bun's own list also names `ws` and `undici`). It also refuses axe-core in the renderer and any .woff/.ttf in `out/renderer` (Chromium loads only .woff2; the `woff2OnlyFonts` plugin drops KaTeX's and JetBrains Mono's older fallbacks).
- Vite bundles an uninstalled optional peer dependency as an empty object, not a throwing `require`, so a package's `try { require(…) } catch` fallback never runs (v0.34.0 crashed main on a paired phone's first WebSocket frame: ws's `bufferutil`). The main build `define`s `WS_NO_BUFFER_UTIL`/`WS_NO_UTF_8_VALIDATE` (`MAIN_DEFINES`); the check refuses any `__viteOptionalPeerDep_*` stand-in in `out/main` and builds `scripts/ws-bundle-probe.ts` with the main config (`ws-bundle-probe.config.ts`) for a masked-frame round trip in Node; `e2e/mobile-web.e2e.ts` pairs a phone with the built app and sends one over `/ws` (`@smoke` in en light).

### Where a new feature goes

1. Stock RPC already has it (`omp://rpc.md`) → call it; add a local handler only to reshape.
2. Stock implements it (an exported function or class in `@oh-my-pi/*`, an `omp <subcommand>`) → reuse that implementation through the bridge or the CLI; never port or re-derive its rules in OMPdesk.
3. Data the GUI can get on its own (git, files, `omp <subcommand>`) → local handler in main.
4. Needs the live session → bridge method + thin local handler.
5. Needs a change inside omp → contribute upstream; never fork.

**No duplicate of stock logic.** Before adding domain logic, search the stock packages (`~/.bun/install/global/node_modules/@oh-my-pi/`). If an implementation exists, call it, even through a bridge method, and add its internals to `capabilities.ts`. Keep an OMPdesk copy only when (a) it is measurably better and stock cannot be used as is, or (b) it must run where stock cannot: the renderer, main before omp starts, or a remote client. Say why in a comment naming the stock counterpart. A test pins the copy to stock: it compares against the stock function where importable (bridge tests on a machine with omp), otherwise uses stock's own test cases. Two OMPdesk copies of the same logic are never acceptable; merge them into one shared module.

When an omp update breaks a bridge method, fix it against the new internals and raise `MIN_OMP_VERSION` if the fix requires it.

**A file the app replaces in one step is written with `src/main/atomic-file.ts`** (`writeFileAtomicSync` when the caller needs the file now or an error, `writeFileAtomic` in async code, `writeFileAtomicDeferred` for a writer that runs on every state change and cannot block), never with a `writeFile` + `rename` of its own. On Windows the rename fails (`EPERM`, sometimes `EACCES`/`EBUSY`) while any process has the target open (a virus scan, a backup, an indexer, a poll), and a save that gives up loses the write for good: the seam retries the rename on a backoff (blocking variant under 0.6 s, the others about 5 s). Renames that move folders, downloads or the user's own files are not atomic writes and stay as they are.

### Lock and gate

- The machine-wide lock is one counting semaphore per kind of heavy work, because too much at once overloads this Mac until load-sensitive tests fail (`scripts/lock-slots.ts`, `scripts/build-lock.ts`). Slots (`DEFAULT_SLOTS`; `OMPDESK_LOCK_SLOTS=playwright=3,vitest=2` overrides for measuring): `build` 1 (builds into `out/` never overlap), `playwright` 4, `vitest` 1 (a full run with the static checks), `other` 1.
- Why those numbers (measured 18 Oct 2026, loaded 15-core Mac). Playwright: 4 runs at once add no flakes beyond the solo baseline and 4 runs × 2 workers is the fastest per run, so 4 slots share 8 workers. Full vitest: two runs at once lost `*-stock` tests (real omp subprocesses that time out under load) in half or more of the runs and fewer workers did not cure it, so 1 slot. With one lock for everything, agents waited 11 h in 6 h and one responsive-audit held it 93 min. A test that failed in every concurrent run was a peer's edit, not load.
- A slot is the directory `/tmp/ompdesk-locks/<kind>.<i>` (`os.tmpdir()` on Windows) with an `owner` file (first line `name HH:MM:SS pid N`; refreshed every minute; one older than 15 minutes is stale and the next waiter removes it). Waiters keep a ticket in `<kind>.queue/` and are served first come, first served; a late short job never overtakes an earlier one. A non-gate hold past 15 minutes is warned about and flagged by `lock-stats`.
- A Playwright run never reads `out/`: every `bun run build` (which takes the `build` slot itself) also publishes an immutable copy `out-<first 12 hex of the input hash>/` (an APFS clone; gitignored; deleted 30 minutes after a run last touched it; `scripts/out-snapshot.ts`), and `playwright.config.ts` pins `OMP_GUI_E2E_OUT` to the current one once per run, so a build another agent starts mid-run never changes the app under it.
- A Playwright run that finds others holding slots gets fewer workers: `OMP_GUI_WORKERS` = min(4, ⌊8 ÷ runs holding a slot⌋), so 4 each for one or two runs and 2 each from three (set `OMP_GUI_WORKERS` or pass `--workers` to choose). Vitest has the matching `OMP_VITEST_WORKERS`.
- `bun run gate` (`scripts/gate.ts`) is the full local check and holds no lock as a whole: typecheck, biome, the surface policy and the full vitest suite side by side in one `vitest` slot while the build takes the `build` slot, then, only if all passed, the full Playwright suite in a `playwright` slot on that build; its holds are exempt from the max hold. It is optional: the release gate is release.yml (see CI).
- Run any other build, Playwright run or full vitest run as `bun run locked -- <command>` (e.g. `bun run locked -- bunx playwright test e2e/smoke.e2e.ts --output /tmp/<you>-results`); the kind comes from the command, `--kind <kind>` overrides it, `--chunk <n>` runs a playwright/vitest command as `--shard=1/n … n/n`, one hold per shard, so a long job lets waiters in between.
- `locked` waits for a slot (printing `[lock] waited 42.3s for <holder>` past 1 s), stops the command's whole process tree and releases the slot when interrupted; a nested locked command of a kind an ancestor holds runs inside it (`OMPDESK_BUILD_LOCK_HELD` lists the kinds held). The old single lock directory `/tmp/ompdesk-build.lock`, while it exists, counts as holding every slot (old `until mkdir` users keep working). Each release appends one JSON line (owner = `OMPDESK_LOCK_OWNER` or `user@checkout`, command, kind, `waitedMs`, `slot`, `via`, `heldMs`, exit code) to `/tmp/ompdesk-build.log` (`scripts/lock-log.ts`, trimmed to its newest 4000 lines past 5000); `bun run lock-stats [--since 2h]` summarizes it. `OMPDESK_LOCK_ROOT` and `OMPDESK_LOCK_POLL_MS` exist for tests, never for daily use.
- Parallel agents: the lock lets six heavy holds run at once (4 Playwright, 1 full vitest or check run, 1 build), so run up to six agents at once, each on one disjoint slice; a seventh only queues. Iterate with targeted vitest outside the lock, run builds and e2e as short `bun run locked -- …` holds (several specs in one command, a long sweep split with `--chunk`), commit verified hunks locally as you go, and leave the full gate to CI. Waits come from full suites in front of short holds, so iterate with `check:changed`. `bun run lock-stats` shows whether agents wait more than they work (avg wait over a minute: too many at once or a hold that should be split) and which slot each run used.

### Dev rules

- Never reinstall `/Applications/OMPdesk.app` from inside the app (you may be running *inside* OMPdesk; quitting it kills this session). `scripts/reinstall-mac.sh` (`bun run package:mac -- --publish never && bash scripts/reinstall-mac.sh`) runs **only when the user explicitly asks for a local reinstall**. **Never** schedule a swap with `launchctl submit` (launchd keeps submitted jobs alive and reruns them, so the app quits and relaunches forever) or any `KeepAlive` job.
- Child processes the app spawns must not outlive it: they get an open stdin pipe and exit when it closes (see `resources/gui-bridge/stats-host.ts`), because a crash or force-kill skips the quit handlers. The one process meant to outlive the app is ai-memory's own per-user service (launchd LaunchAgent / Windows logon entry, serving the terminal omp too): it is not OMPdesk's child but the service `ai-memory setup` installs. That `setup` is supervised like any installer and dies with the app; it runs isolated (`SpawnSpec.isolated`) so the service holds no handle of the app's (see "Memory (ai-memory)"). A new command whose descendant outlives the app by design runs isolated the same way.
- A spawned omp never inherits another OMPdesk session's plumbing: `SESSION_OWNED_ENV` (`src/main/omp-launch.ts`, beside `sessionEnv`, which sets them) lists every `OMP_GUI_*` variable a spawn sets from its own launch (bridge socket, reply language, profile, judge assist, delegation, account rotation, roles file, REA root, pstack, memory), and those are removed from the app's and the login shell's environment before the spawn adds its own. Without it a dev or test run started from an OMPdesk session's shell handed its tabs the parent's bridge socket, delegation and memory file. A new per-spawn variable goes into `sessionEnv` and that list together (`omp-launch.test.ts` fails when they differ; the "never passes on the session variables" case of `shell-env.test.ts` checks a real spawn); test hooks (`OMP_GUI_TEST_*`) still pass through.
- No git command, the app's or a test's, follows a repository selector it did not set: `git bisect run` from a linked worktree, a hook or a shell inside a git operation exports `GIT_DIR` and its kin (`GIT_REPO_SELECTOR_ENV`, `src/shared/git-env.ts`), and a test's temp-repo `git init`/`git config` once set the shared checkout's `.git/config` to `core.bare = true` with a test identity. `execBin` (`local/git/exec.ts`) drops the ambient ones before the caller's own `env` (disk care's scratch `GIT_INDEX_FILE` still applies), as do `gitSync`/`initRepo` (`local/git/test-repos.ts`), both test runners' configs, `vitest.setup.ts` and e2e `launchApp`. A new spawn of git outside those builds its env with `withoutGitSelectors`. Pinned by `local/git/git-env.test.ts` (a sacrificial repository the selectors point at comes out byte-identical).

## Change workflow

Commit and push each change as it lands; release in small batches without waiting to be asked (the repo is public, CI and releases cost nothing).

1. Each finished fix or feature: run `bun run check:changed`, commit with a normal descriptive message (no version bump, no CHANGELOG release section), push to `main`. ci.yml's `check` runs on the push; a red `check` is fixed before anything else lands.
2. Release by what landed since the last release, never by the clock: three user-visible changes (`feat`, `fix`, `perf`), one urgent fix (a defect that breaks the released app, a regression of the last release) on its own, or a user-visible change that has waited a day. Docs, tests, refactors and CI alone never make a release (the user's call, 22 Oct 2026: a "once or twice a day" rule kept a batch of fixes back for hours). Every release prompts every user to update and restart, so a lone small change waits for company. No local gate: ci.yml already ran the blocking checks per push, and release.yml is the gate (types, biome, surface policy, vitest, Windows platform tests, `mac`/`win` packaging with `@smoke`, real-core). The full Playwright suite runs nightly and on demand (`e2e-nightly.yml`), not in a release.
   - A release is a cut of `main`, not a list of work to finish. It ships what `main` holds when it is cut; work still running in other sessions, a hunt for an intermittent test, a red nightly or a Windows full run ships in the next release. On 21 Oct 2026 a release held until every running session finished was the whole delay: the lock queue had waited 6.5 minutes in those 6 hours (`bun run lock-stats --since 6h`).
   - Other sessions keep pushing while a release runs, `package.json` changes included. The tag lands on the run's own commit; a later push that starts a release run waits for the running one and then finds the tag cut (it ends after `prepare`) or releases a newer version. No session holds its pushes; a release commit that finds `main` moved rebases like any push.
3. Release per the steps under Release: one dated bilingual `CHANGELOG.md` section covering every commit since the last release, one version bump, commit `release: vX.Y.Z`, push, watch the run to the end (rerun only failed jobs), tell the user it went out.

- A run takes about 6 minutes to `publish`, bound by `mac`, when the memory binary comes from the cache, and about 15 when one of its inputs (native/memory, scripts/build-memory.ts, resources/gui-bridge/memory-prompt.ts, resources/gui-bridge/redactor.ts) changed (dry runs 39240205382 and 39238195669); every blocking job starts right after `prepare`.
- Never leave an `Unreleased` section on `main`.
- Do not reinstall the local app unless asked; the in-app updater picks the release up.

## Release

- Semver `X.Y.Z`; tag `vX.Y.Z`; commit `release: vX.Y.Z`. No AI attribution trailers in commit messages.

### Steps

1. Pick the version from commits since the last tag (features → minor, fixes only → patch). Bump `package.json` `version`; add `## [X.Y.Z] - YYYY-MM-DD` to `CHANGELOG.md`: Korean summary, a line holding only `<!-- en -->`, then the English summary. release.yml turns the marker into `---`, so the GitHub notes carry both, Korean first; the What's new and changelog windows show the UI language's part and fall back to Korean (`changelogSection`/`changelogReleases` in `src/renderer/lib/whats-new.ts`).
   - **Open each section with one plain sentence.** `layout/WhatsNewCard.tsx` (one in-flow row under the title bar, mounted by `AppShell`; never over a composer, transcript or side panel; once per new version; never during the setup takeover, first run or tour) shows that first paragraph (`changelogSummary`); "자세히 보기" opens the section in the dialog. After skipped versions one card names the newest and the dialog lists every release since the last seen (`changelogSince`). The card stays until dismissed or opened, and hides after 60 s of focused, unhovered time (`WHATS_NEW_AUTO_HIDE_MS`).
   - Update README version mentions. Confirm `MIN_OMP_VERSION` (`src/main/omp-runtime.ts`) is current.
2. `git commit -am "release: vX.Y.Z" && git push origin main`. Do not tag. The tag lands on the commit the run starts from, and that commit's diff must not touch `.github/workflows/*`: `publish` tags with the run's `GITHUB_TOKEN`, which never has the `workflows` permission, so GitHub refuses with HTTP 403 "Resource not accessible by integration" (v0.35.1). Ship a workflow change in its own commit, then an ordinary commit (the release commit, or an empty `chore: release point …`) before dispatching the release.
3. `release.yml` does the rest; every job starts right after `prepare`:
   - `prepare` reads version and notes; `build` builds `out/` once and uploads it (byte-identical on any OS); `static` runs types, biome, surface policy; `check` runs vitest as three jobs (node project + two renderer shards); `win-platform` runs `bun run test:platform`; `mac-real` runs `e2e/real-core.e2e.ts` on `out/`.
   - `mac` and `win` install while `build` runs, wait for `out/` (`scripts/ci-fetch-out.sh` polls the run's artifacts; `needs: build` would wait for the whole job), package it and run `@smoke` on the fake omp. `mac`: arm64 DMG, signed with the pinned certificate on `main`, codesign + designated requirement + `gui-bridge` verified. `win`: x64 NSIS setup (`makensis` cannot run on Apple Silicon).
   - Only if all passed, `publish` creates tag `vX.Y.Z` and the Release (title `vX.Y.Z`) with exactly two version-free assets, `ompdesk-mac-arm64.dmg` and `ompdesk-windows-setup.exe` (so `/releases/latest/download/<name>` stays stable). Notes = changelog section + minimum omp version + `<!-- ompdesk-update {"version","releaseDate","files":{"mac"|"windows":{"name","size","sha512"}}} -->` (sha512 base64), appended by the "Append update metadata" step; GitHub does not render it.
   - No `latest*.yml`, ZIP, blockmap or portable exe. An existing tag or an `Unreleased` heading makes the run a no-op. Package artifacts expire after 1 day (7 on a dry run); the Release keeps the assets.
   - **Legacy feed switch**: `LEGACY_UPDATE_FEED` at the top of release.yml, `"false"` since v0.18.1 (v0.18.0 carried the bridge). Installs up to v0.17.x updated from `latest-mac.yml`/`latest.yml`, fetching `ompdesk-X.Y.Z-arm64-mac.zip`, `ompdesk-X.Y.Z-arm64.dmg` and `ompdesk-X.Y.Z-setup.exe` by exact name. `"true"`: the mac job also builds the ZIP (`electron-builder --mac dmg zip`) and both jobs add the yml plus every file it lists. While `"false"`, `publish` refuses any release without exactly the two assets.
4. Watch: `gh run watch <run-id> --exit-status`. A failure the code didn't cause (runner, network, flaky test): `gh run rerun <run-id> --failed`, never a whole new run. Otherwise fix on `main` and re-run with `gh workflow run release.yml`. Rehearse from any branch: `gh workflow run release.yml --ref <branch> -f dry_run=true` (artifacts kept 7 days).

- Manual fallback: `bun run package:mac -- --publish never` on a Mac, `bun run package:win -- --publish never` on Windows; copy `dist/ompdesk-X.Y.Z-arm64.dmg` → `ompdesk-mac-arm64.dmg` and `dist/ompdesk-X.Y.Z-setup.exe` → `ompdesk-windows-setup.exe`; append the metadata comment to the notes as that step does (a release without it is not offered as an update); `gh release create vX.Y.Z --target main --title vX.Y.Z --notes-file <notes> ompdesk-mac-arm64.dmg ompdesk-windows-setup.exe`.

### Signing

- `scripts/mac-sign.cjs` (electron-builder `mac.sign`) signs every bundle with OMPdesk's own self-signed certificate, pinned by SHA-1 in `scripts/mac-signing.json`. The designated requirement (`identifier "com.seuput.ompdesk" and certificate root = H"…"`) is then the same in every release, so macOS keeps its privacy grants (folders, local network, microphone) across updates; an ad-hoc requirement is the build's cdhash and re-asked them all each update.
- Identity source, in order: repo secrets `MAC_SIGNING_P12_BASE64` / `MAC_SIGNING_PASSWORD` (release.yml sets `OMPDESK_MAC_SIGNING_REQUIRED=1` on `main` and checks the requirement); the maintainer's local `~/.ompdesk-signing/` (p12 + password; the only backup, losing it means a new certificate and another round of prompts for every user); else ad-hoc with a warning.
- It is imported into a throwaway keychain passed to codesign with `--keychain`; the user's keychain search list is never touched. **Never replace the certificate.**
- No Apple Team ID, so keychain items still bind to the cdhash (safeStorage stays untouched unless a stored token exists). Nothing is notarized: downloaded DMGs need right-click → Open once; locally built apps run without Gatekeeper prompts.

## Code conventions

- **UI is built from the shared components** (`src/renderer/components/common`). Read its catalog, `src/renderer/components/common/README.md` (which component for which need, container policy, the rules every component keeps), before writing UI. A need none covers gets a new component there, never a private copy in a feature folder. `scripts/lint-controls.mjs` (run by `lint-surfaces.mjs`) fails a renderer `.tsx` outside `components/common` that adds a raw `<button>`, a raw checkbox or radio (`Checkbox`, `Radio`) or a hand-made `role="dialog"`; the raw ones that were there are frozen per file in `scripts/lint-controls-baseline.json`, which only goes down (`--update` lowers it), and a deliberate one says why with `controls-ok: <reason>`. Pinned by `scripts/lint-controls.test.mjs`.
- TypeScript: no `any`, no inline `import("…")` types, `#private` fields, Bun APIs where cleaner.
- **A layer over the window cuts itself out of the drag area.** The 48px top bars are `-webkit-app-region: drag`, and Chromium builds the window's drag area from every element that declares a region, whatever is drawn over it: a dialog reaching into those bars (the picture viewer's own bar, a tall model picker) had its clicks taken as a window drag. `global.css` gives every overlay layer (`.omp-dialog-overlay`, `.omp-action-sheet-overlay`, a `Sheet`'s `[data-sheet-placement]`, `.omp-pop-in` popovers and menus) `no-drag`; a new floating layer that can reach the top bars wears one of those or `no-drag` itself. Pinned by the model picker case of `e2e/responsive-smoke.e2e.ts`.
- **Main's `fs` over a user's folders is `original-fs`.** Electron patches `fs` so a path through a `*.asar` is a folder: stat, lstat, access, exists, realpath, open, read or copy of one opens the archive and keeps it for the life of the process (measured on Windows, Electron 36.9.5, Restart Manager naming the holder; `readdir` alone holds nothing, `original-fs` holds nothing in any call), and Windows cannot delete a file another process holds. Every Electron project's `node_modules/electron/dist/resources/default_app.asar` is one: the installed app's launch disk-care run walked `~/.omp/wt`, and then its main pid was named for the archive of every worktree under it and `rd /s /q` was refused until OMPdesk quit. `src/main/disk/*`, `worktree-orphans.ts`, `worktree-removals.ts`, `workspace-fs.ts`, `open-path.ts`, `web/host-actions.ts` and `local/git/{changes,scm,session-worktree,worktree,worktree-seed}.ts` import `promises as fs` from `original-fs`; a module that walks, stats, copies or removes a user's folder does too. `process.noAsar` stays unset (main's own code is read from `app.asar`). Pinned by `e2e/disk-care-asar.e2e.ts` and, for the modules that spec does not reach, `src/main/user-folder-fs.test.ts` (a source check: plain Node has no asar, and `vitest.config.ts` aliases `original-fs` to `node:fs`).
- i18n: English and Korean only (`UI_LANGUAGES` in `src/shared/ui-language.ts`). Every user-visible string goes through `useT()` with the same key in `src/renderer/locales/en.ts` and `ko.ts` (`locales.test.ts` enforces identical key sets). Settings-schema text: `src/renderer/components/settings/schema-ko.ts` and `schema-option-ko.ts`; main-process strings: `src/main/i18n.ts` and `tray-labels.ts`.
- Model output renders through `MarkdownRenderer` (`src/renderer/lib/markdown.tsx`, rehype-sanitize), never `dangerouslySetInnerHTML` with model text. Text a person typed (prompt bubbles) passes `userText`: single-dollar math stays literal, HTML tags show as typed (`remark-html-text.ts`), and every newline is a line break, as typed with Shift+Enter (`remark-soft-breaks.ts`; Markdown would read one as a space, so a multi-line prompt showed as one run-on line).
- A path a reply or tool card links is never given to `shell.openPath` when opening could run something. `openLocalPath` (`src/main/open-path.ts`) reveals launcher types in Finder/Explorer instead: `.app .command .sh .jar .exe .bat .cmd .ps1 .lnk .url .msi`; interpreter scripts (`.py .pyw .pyz .pl .rb`; python.org's launcher runs `.py` on macOS); Windows script, scriptlet, shortcut, help, add-in and theme types (`.chm .xll .wsc .sct .theme .settingcontent-ms` and the like); macOS `.terminal .workflow .pkg .dmg .scpt .webloc` and the like; anything an executable bit marks on POSIX; any symlink to either. A new caller that opens a model-supplied path goes through it.
- Tool-rendered text uses `src/renderer/lib/format.ts`; preview ceilings come from `src/renderer/lib/preview.ts`; subprocess output renders through `AnsiText` (`src/renderer/lib/ansi.tsx`).
- Component tests use the linkedom harness (see `src/renderer/components/chat/ThinkingBlock.test.tsx`): mount through `I18nProvider`, reset zustand stores in `afterEach` via `reset()`/setters; never `mock.module()`.
