# ompdesk — Development Rules

Read this before any edit in this repository. Every rule here and in the area rules below binds; a "user's rule" is a product decision by the user and is never undone without them.

This codebase is yours: how it is built is your call, and you will keep building on it. So merge repeated code instead of adding a copy beside it, and fix a defect you find next to your change instead of only reporting it. What the product does for the person stays the user's: a user's rule or an existing feature's behavior changes only when the task asks for it. Name every change beyond the task in your report, small ones too.

## Architecture

```
renderer (React) ── IPC ──▶ main (Electron)
                              ├─ src/main/local/*      fork-era commands served in main
                              │     (git/gh, fs, ~/.omp files, `omp` CLI, translation to stock RPC)
                              ├─ src/main/sidecar.ts   spawns `omp --mode rpc-ui -e <gui-bridge>/index.ts`
                              │                         (stock RPC over stdio)
                              └─ src/main/bridge-client.ts ◀── unix socket / named pipe ──▶
                                                         resources/gui-bridge/*  (omp extension,
                                                         live AgentSession access)
```

### Command routing and IPC

- The renderer speaks one command set. `RpcClient.command()` (`src/main/rpc-client.ts`) first looks for a **local handler** (`src/main/local/index.ts` merges `src/main/local/<area>.ts` maps; duplicate keys throw at startup). Commands without one go to stock omp unchanged.
- A local handler (`LocalHandler`, `src/main/local/types.ts`) works in main (git, gh, files, `ctx.omp.run([...])`), translates to stock RPC (`ctx.send(...)`), or calls the bridge (`ctx.bridge.request(method, params)`) for live session state.
- Main's IPC handlers register through the one `IpcRegistry` (`src/main/web/ipc-registry.ts`, created in `index.ts`), never on `ipcMain` directly: `ipc.handle(channel, (caller, …args) => …)` / `ipc.on(…)` register on `ipcMain` and in the table the web client is dispatched from. A handler finds its window as `caller.win` (`ClientWindow`, `src/main/web/client-window.ts`) and the page as `caller.sender`. Only a dialog sheet, the title-bar overlay or the preview take the native `caller.browserWindow`.
- `window.omp` is `createOmpApi(transport)` (`src/shared/omp-api.ts`): the preload hands it an `ipcRenderer` transport and adds only `fs.pathForFile`; a paired web page hands it a WebSocket one. A new API member goes in `omp-api.ts`, never the preload. Every channel is classified in `src/main/web/ipc-policy.ts` (`IPC_POLICY`, typed over the channel union: a new channel does not compile without a direction, a `WebPermission` and a web mode; `ipc-policy.test.ts` matches it against the registered handlers and the channels `createOmpApi` subscribes to). Web frames and permissions: `src/shared/web-protocol.ts`.

### Bridge

- **Bridge** (`resources/gui-bridge/`): an omp extension loaded with `-e`. Area modules export `methods` maps; `env.session()` is the live `AgentSession`, `env.pi.pi` the stock package index. Bare `@oh-my-pi/pi-coding-agent/...` subpath imports resolve through omp's resolver. These are **internal omp APIs without semver**: keep methods small, feature-detect, throw clear errors.
- A feature's pure rules (`<name>-core.ts`), runtime wiring (`<name>-engine.ts`), per-session memory (`<name>-state.ts`) and dependency-free contracts main and the renderer import (`<name>-contracts.ts`) sit in the folder of the module that registers the feature: `modes/` (auto mode, auto title, delegation, prompt suggestions, output style, profile, goal time, visuals), `extensions/`, `stock-helper/`, or the root beside a root area module (`session-recap.ts`, `reset-passes.ts`, …; `timer-core.ts` serves two). Contracts shared with the renderer live in `resources/gui-bridge/`, never outside `extraResources`.
- **Compatibility self-check**: every omp internal a bridge module uses is listed per GUI feature in `resources/gui-bridge/capabilities.ts` (`REQUIREMENTS`); add it there (and the module to `LOADERS` in `health.ts`, literal specifier) whenever a bridge method starts using one. `index.ts` loads each area module separately, `guard(feature, methods)` refuses a feature's methods with `unsupported_omp` while anything it needs is missing, and the `capabilities` method reports them. `src/main/bridge-health.ts` probes once per omp version per launch; the renderer toasts the result. `OMP_GUI_BRIDGE_PROBE_HIDE=<label>,…` (labels as `capabilities` prints them, e.g. `AgentSession.setPlanModeState`) makes the probe treat those internals as missing, to rehearse a broken omp.
- **Only the running omp's modules**: omp serves a bridge's literal `@oh-my-pi/*` import from the running omp's bundle only when the bundle registers that subpath (its legacy-pi module registry; pi-coding-agent's `./*` catch-all is not in it); any other subpath falls back to the package's source file, a **second module graph** with its own settings registry, whose setting handles read the wrong slots of the live session. `health.ts` reads each loader's rewritten target (`TARGETS`: `omp-legacy-pi-bundled:` = the running omp's, `file://` = a copy) and refuses a feature whose module is a copy not in capabilities.ts `COPY_SAFE` (each entry says what of that copy is used and why), labelled `<specifier> (separate copy, not this omp's module)`. Reach an unbundled internal through a bundled module instead: a setting by id with `config/registry` `lookup` (`goal.enabled`, `goal.continuationModes`), a package root (`@oh-my-pi/pi-ai` for `resolveCredentialIdentityKey`), a stock tool (`tools/security-scan` `SecurityScanTool` for the security coordinator, whose `status` also recovers stored scans' operations; `tools/manage-skill` `ManageSkillTool` for managed-skill writes, which join the session's per-skill mutation chain; `tools/tts` `resolveSpeechCandidates` for the speech chain). **Known gap**: omp's bundle has no `tts/*`, so read-aloud still uses a copy of `tts/tts-client` (its own worker, tiny-model device/dtype from the environment, not `providers.tinyModel*`) until upstream bundles it. Pinned by `bridge-stock-settings-stock.test.ts` (disabled plan/goal/security stay off; copies seen equal `COPY_SAFE`), `bridge-security-stock.test.ts` (a scan left running reads failed) and `bridge-capabilities.test.ts` (every extension-side stock import is a `REQUIREMENTS` module).
- **Source copies stay off omp's startup path** (`resources/gui-bridge/capabilities.ts` `HEAVY_COPIES`): the first import of `config`, `tts/*`, `sdk` or `skillshare/*` makes bun transpile omp's source tree on omp's only thread (seconds with a cold transpiler cache). No area module imports `config` or `tts/*` statically (`bridge-capabilities.test.ts`; `extensions/agents.ts` and `voice.ts` import on use), and the startup `capabilities` probe leaves all of them unevaluated (`probe(env, features, {evaluateHeavy: false})`: present when the file exists), so a missing export of theirs shows as `unsupported_omp` when a feature first uses it, not as a startup toast. `guard` still evaluates them on a feature's first call, except `PRESENCE_ONLY` (`sdk`, `skillshare/*`: only the stock helper loads them, in its own process), which no probe evaluates in omp, because evaluating `sdk` on a `providers` call held every request of the tab behind it. Measure a new bridge import that resolves to a source copy before it ships (`PI_DEBUG_STARTUP=1` makes omp print its phases to stderr).
- **Area modules load at the bridge's first use, not while omp starts** (`index.ts` `guiBridge`): main's first connection, the first prompt or a subagent's rebind starts `loadMethods`; only the thinking default, delegation strength and OMPdesk roles apply in the factory, because loading at startup cost every omp `ready` time and memory. A prompt sent before the load waits for it in the `input`/`before_agent_start` gates, so its hooks still run (`bridge-first-use-stock.test.ts`). An area's `install` never sees the boot `session_start`; one that needs the live session attaches itself (`turn-stages.ts`).
- **Bun's transpiler cache is off for a session's omp on Windows** (`ompBunDefaults`, `src/main/omp-runtime.ts`; why: machine-setup-updates).
- Composer state uses stock `get_state` (session identity, resolved thinking) and stock `cycle_model` (forward cycling); the bridge adds only missing state, backward cycling, tool provenance/mounted tools and the GUI `/copy` tree around stock `pi-tui/overlays/copy-targets`. The model pool was removed (pref `modelPool` deleted once at startup; `ompdesk.model-pool` journal entries ignored).

### omp runtime and version floor

- `src/main/omp-runtime.ts` finds omp (`OMP_GUI_OMP` override → login-shell `PATH` → `~/.bun/bin/omp`, `/opt/homebrew/bin/omp`, `/usr/local/bin/omp`; Windows `%USERPROFILE%\.bun\bin\omp.exe`, `omp.cmd`/`omp.exe` on `PATH`) and enforces `MIN_OMP_VERSION` (18.18.9, for stock's prompt sources, `session.systemPromptSources` and pi-tui's `claimPromptSources`, which the context inspector reads; it only moves with a newer requirement or an audit). A bin that links to `<package>/dist/cli.js` (a bun or npm global install) is versioned from that package's `package.json` (`installedVersion`), because any other layout runs `omp --version` in front of the first session. Every bridge feature in `capabilities.ts` is required at that version. When a feature needs a newer omp, raise `MIN_OMP_VERSION` instead of carrying an older-omp fallback; when an omp update breaks a bridge method, fix it against the new internals and raise `MIN_OMP_VERSION` if the fix requires it. The fake omp (`e2e/sidecar-fixture.ts`) reports the minimum.
- Only an omp that runs from its package counts (`pickOmp`/`isCompiledOmp`): the bridge's `@oh-my-pi/*` imports cannot resolve in a compiled omp (Bun's standalone build), so one is passed over in the lookup and, alone, fails `compiled`; machine setup reinstalls the package, moving the compiled omp out of Bun's launcher path first (`setup/compiled-launcher.ts`: `bun install -g` alone fails EEXIST over it on POSIX and keeps a running one on Windows). The package's `engines.bun` gates the Bun its shebang would find (`bun-too-old`; setup upgrades Bun, falling back to Bun's installer). OMPdesk's omp update reads the target's `engines.bun` and upgrades Bun before stock `omp update`, whose launcher repair otherwise swaps in the compiled omp (machine-setup-updates). OMPdesk never asks the person to run a command to fix Bun or omp (the user's rule).

### Stock helper workers

- Main-side stock operations without a tab run in three lazy Bun workers (`src/main/stock-helper.ts`, `resources/gui-bridge/stock-helper/host.ts`, routing in `dispatch.ts`): `terminal.*`/`pty.*` → terminals worker (every request concurrent); `extensions.*` → extensions worker (own serial lane: a plugin upgrade runs `bun install` for minutes and must neither block session scans nor be recycled); everything else → the stock worker's serial lane, except the read-only probes in `stock-helper/sessions.ts` `UNQUEUED_METHODS` (`sessions.owned`), answered at once beside it, because a restored tab's omp spawns only after it answers. A hung stock call can never take a shell or a running upgrade with it. Area handlers register request names; resolve stock modules from `OMP_PACKAGE_ROOT`; never boot an agent or call a model.
- Each request has its own 30 s timeout (`stockHelperRequest(method, params, { timeoutMs })` overrides; armed before the worker starts). It fails only that request and sends `{cancel: id}`, so the worker skips it if not started (a mutation never runs after its caller was told it failed) and answers `withdrawn`. If a timed-out request still has no answer 30 s later, the lane is stuck: main logs it, fails what waits behind it, kills the stock worker and starts a fresh one on the next request. The terminals and extensions workers are never replaced for a slow request. The extensions worker holds no state, so it ends 60 s after its last answer (`EXTENSIONS_IDLE_EXIT_MS`) to give its memory back, and the next request starts it again. stdin EOF and app quit stop all workers.
- The session index uses read-only `listAllSessions`/`listSessionsReadOnly` and keeps only GUI chat labels, scope filtering, duplicate-id suppression and change notifications. Changes come from one recursive `fs.watch` of the sessions tree (`SessionIndex.start`), never a watch per directory, because on macOS each new one recreates libuv's single FSEvents stream and drops session files written meanwhile. Picker and sidebar list no session without content (`sessionHasContent`, stock's `filterSessionsForPicker` rule). The legacy chat label is read from a session file's header once per session id (`#legacyChat`), not on every list.
- **A computer's session list is read once per change and shared** (`SessionListShare`; versions and diff in `src/shared/session-list-delta.ts`): every ask answers from one numbered copy or joins the read under way, and `SESSIONS_CHANGED` carries what changed, so a window holding that version reads nothing. A paired host sends a device the same (`slimSessionLists`); the device keeps one copy for all its windows (`HostSessionList`). Details: no-loading-screens › What is cached.

### Deleting a session

- Deleting never starts another session. The tab holding it closes as closing a tab does, and only then does the stock worker's `FileSessionStorage.deleteSessionWithArtifacts` remove the file (a file already gone counts as deleted, as in stock's `dropSession`). The renderer closes its own window's tab first (`closeDeletedSession` in `stores/tabs.ts`: the window's last tab gives way to the empty start tab, `placeholder`, with no sidebar row and no file until its first run; the closed-tab history forgets the session). `deleteSession` (`session-mutations.ts`) then calls `SidecarPool.closeSessionTab`, which closes a tab another window holds or a paired device's request reaches (its window hears `TAB_LIST_CHANGED` with `closed`), refuses while that tab runs a turn or compacts, and waits until the omp that had the file open has exited (`#exiting`; `LocalHostServices` waits the same way). There is no `drop_session`, because stock `new_session` writes its header at once, so leaving for a fresh session would leave a "New session" row after every delete.
- A deleted session never comes back (`src/main/deleted-sessions.ts`). A successful `deleteSession` (the one path for the sidebar, `/delete`, `ompdesk_session_stop {delete}` and a paired device's `sessions.delete` on its host) records a tombstone (session path, plus the host's `device` for a remote one) in `<userData>/deleted-sessions.json` (0600, newest 2000). Every path that could revive it asks:
  - `SidecarPool.acquire` returns null (reopen from another window's closed-tab history, a child, any restore).
  - `sanitizePersistedTabLayout` drops the saved tab (desktop `tabLayouts`, web `webTabLayouts`); a missing file **without** a tombstone still becomes a fresh tab in its folder. The launch writes one `tab-layout` line to `gui-runtime.jsonl` with the windows and tabs restored and each tab left out or started fresh, by reason (`folder`, `deleted`, `duplicate`, `fresh`; `TabLayoutDrop`, `logLayoutRestore` in `index.ts`; pinned by `tab-layout.test.ts`).
  - `TurnResume.launch` drops and purges its marker.
  - A host's `tab.open` refuses `session_deleted` for a device whose layout still names it; that device's `RemoteSidecar` emits `sessionDeleted` and its pool closes the tab and records the tombstone under the host's id instead of showing an error tab.
  - `SessionIndex.list` never lists it, even if a stray writer recreated the file.
- A never-written session (first turn cut off before stock wrote its file, marker `prompt`, `#unwrittenSessionTab`) has no tombstone and still continues.
- Renderer: `sessionListFeed(...).deleteSession` drops the row from both scopes' feeds and snapshot copies (`lib/snapshot-cache.ts`), and every global list read prunes the local snapshot of rows it lacks, so a session deleted on another device never repaints after reload. Ghost tabs (`lib/tab-snapshot.ts`) become real only when the live tab list names their session.
- Pinned by the tombstone cases in `session-mutations.test.ts`, `tab-layout.test.ts`, `turn-resume.test.ts`, `sidecar-pool.test.ts`, `remote/host-services.test.ts`, `remote/remote-sidecar.test.ts`, `session-index.test.ts`, `stores/session-list.test.ts`, and the relaunch over a stale layout and marker in `e2e/session-delete.e2e.ts`.

### Packaging

- Packaged apps ship `resources/gui-bridge` **outside the asar** (`extraResources` in `electron-builder.yml` and `electron-builder.win.yml`; `src/main/packaging-config.test.ts` enforces it). The app contains no `omp` binary.
- Packaged apps keep only Electron's `en-US` and `ko` locales (`electronLanguages` in both builder configs; never `en` alone, which deletes `en-US.pak` and blanks the window). `scripts/after-pack.cjs` fails the package unless exactly those survive. Chromium's locale is then en-US for every other system language, so `src/main/system-languages.ts` seeds the Windows spellchecker (default and Preview sessions) and the Preview's Accept-Language from `app.getPreferredSystemLanguages()`; `e2e/preview.e2e.ts` checks the header under `--lang=de`.
- All three bundles are esbuild-minified with names kept (`electron.vite.config.ts`; renderer locals shortened), so `scripts/check-main-bundle.ts` reads the main bundle's imports with Bun's parser (against Node's builtins; Bun's list also names `ws` and `undici`). It also refuses axe-core in the renderer and any .woff/.ttf in `out/renderer` (Chromium loads only .woff2; `woff2OnlyFonts` drops KaTeX's and JetBrains Mono's older fallbacks).
- Vite bundles an uninstalled optional peer dependency as an empty object, not a throwing `require`, so a package's `try { require(…) } catch` fallback never runs (ws's `bufferutil` once crashed main on a paired phone's first frame). The main build `define`s `WS_NO_BUFFER_UTIL`/`WS_NO_UTF_8_VALIDATE` (`MAIN_DEFINES`); the check refuses any `__viteOptionalPeerDep_*` stand-in in `out/main` and builds `scripts/ws-bundle-probe.ts` with the main config (`ws-bundle-probe.config.ts`) for a masked-frame round trip in Node; `e2e/mobile-web.e2e.ts` pairs a phone with the built app and sends one over `/ws` (`@smoke` in en light).

### Where a new feature goes

1. Stock RPC already has it (`omp://rpc.md`) → call it; add a local handler only to reshape.
2. Stock implements it (an exported function or class in `@oh-my-pi/*`, an `omp <subcommand>`) → reuse that implementation through the bridge or the CLI; never port or re-derive its rules in OMPdesk.
3. Data the GUI can get on its own (git, files, `omp <subcommand>`) → local handler in main.
4. Needs the live session → bridge method + thin local handler.
5. Needs a change inside omp → contribute upstream; never fork.

**No duplicate of stock logic.** Before adding domain logic, search the stock packages (`~/.bun/install/global/node_modules/@oh-my-pi/`). If an implementation exists, call it, even through a bridge method, and add its internals to `capabilities.ts`. Keep an OMPdesk copy only when (a) it is measurably better and stock cannot be used as is, or (b) it must run where stock cannot: the renderer, main before omp starts, or a remote client. Say why in a comment naming the stock counterpart. A test pins the copy to stock: it compares against the stock function where importable (bridge tests on a machine with omp), otherwise uses stock's own test cases. Two OMPdesk copies of the same logic are never acceptable; merge them into one shared module.

**A file the app replaces in one step is written with `src/main/atomic-file.ts`** (`writeFileAtomicSync` when the caller needs the file now or an error, `writeFileAtomic` in async code, `writeFileAtomicDeferred` for a writer that runs on every state change and cannot block), never with a `writeFile` + `rename` of its own. On Windows the rename fails (`EPERM`, sometimes `EACCES`/`EBUSY`) while any process (a virus scan, a backup, an indexer) has the target open, and a save that gives up loses the write for good: the seam retries the rename on a backoff (blocking variant under 0.6 s, the others about 5 s). Renames that move folders, downloads or the user's own files are not atomic writes and stay as they are.

## Build, test, CI

### Checks

- Typecheck `bun run check:types`. Lint/format `bunx biome check src e2e resources scripts`. Surface policy (the SURFACE POLICY block in `src/renderer/styles/global.css`) `node scripts/lint-surfaces.mjs`. That script also runs the rules below, each in `scripts/lint-<name>.mjs` and tested by its `scripts/lint-<name>.test.mjs`; each exception says why with its marker comment.
  - `lint-ime`: a renderer `.ts`/`.tsx` function that tests a key for `"Enter"` uses the shared IME guard (`isImeKeyEvent`, `src/renderer/lib/ime.ts`), so the Enter that commits a Korean composition never submits. Marker `// ime-ok: <reason>` (a handler that can never see a text field).
  - `lint-unhandled`: a renderer `void window.omp.…(…)` or `void tabRpc.…(…)` call ends its chain with `.catch(…)` or a two-argument `.then`, because on a paired phone page each is a WebSocket call a dropped link fails, and an unhandled one is a page error and a click that silently does nothing. Links go through `lib/open-external.ts`, update buttons through `stores/updater.ts` `runUpdaterAction`. Marker `unhandled-ok: <reason>`.
  - `lint-controls`: see Code conventions › UI is built from the shared components. Marker `controls-ok: <reason>`.
  - `lint-locale`: no renderer number or date formatted in the OS locale (`toLocaleString()`, `toLocaleDateString()` or `toLocaleTimeString()` with no locale), because the English UI then shows a German grouping; pass `uiLocale()` (`lib/format.ts`). Marker `locale-ok: <reason>`.
  - `lint-prompt-sections`: no gui-bridge `before_agent_start` handler returns its own `systemPrompt`, because stock's restore of a continued turn and the context inspector build the prompt from the registered sections only, so that text would be missing from every revived subagent's first request. Register a section (`registerPromptSection`, models-accounts). Marker `prompt-section-ok: <reason>`.
  - `lint-duplicate-rules`: no rule spelled on two sides of src/main, src/renderer, src/shared and resources/gui-bridge (a regex bound to a top-level `const` whose pattern another side repeats, or an exported constant with the same name and value): import the one copy. Known ones sit in `scripts/lint-duplicate-rules-allow.json` with their files and reason; a copy in one more file fails, and so does a stale entry. Narrow on purpose (a literal match, no clone detection).
- A commit whose subject is a fix (`fix:`, `fix(scope):`, `fix!:`) changes a test file (`*.test.*`, `*.e2e.*`, `*.spec.*`, anything under `e2e/`; in Rust a line at or after the file's `#[cfg(test)]` mark, or a crate's `tests/` folder) or says why not in its body with a line `no-test: <reason>`. `scripts/lint-fix-tests.mjs` (run by bun; its git ignores the repository selectors an enclosing hook or bisect sets) checks the branch's unpublished commits in `check:changed` and the pushed range in ci.yml's `static`; tested by `scripts/lint-fix-tests.test.mjs`.
- Supply chain: `bunfig.toml` sets `[install] minimumReleaseAge = 259200` (Bun skips a version published less than 3 days ago when it resolves; `bun.lock` pins are untouched; a fresher `bun add`/`bun update` waits or needs `minimumReleaseAgeExcludes`). Every workflow's `oven-sh/setup-bun` pins one exact `bun-version` (never `latest`; bump all together). `src/main/supply-chain.test.ts` pins both.

### Tests

- Unit/component tests: `bunx vitest run`. The full suite must stay green.
- `vitest.setup.ts` pins `navigator.language` to en-US and `navigator.platform` to MacIntel, so keymap defaults and shortcut labels are the macOS ones on every runner; Windows behavior is tested by passing `"windows"` to the `lib/keymap.ts` functions. `vitest.renderer-setup.ts` (renderer project only) gives linkedom's documents standards mode (`compatMode`), as the app's doctype does, so KaTeX does not warn about quirks mode.
- `scripts/vitest-real-home-guard.ts` makes any fs write under the **real** home (from `os.userInfo().homedir`, so a faked `HOME` does not hide it; only this checkout and the OS temp dir are exempt, never another `~/.omp/wt` worktree) throw and fail the test even when the code swallows the error. Give the test a temp HOME, or set `OMP_GUI_ALLOW_REAL_HOME=1` in a suite that runs a real omp on purpose. Child processes and reads are outside the guard: on Windows `os.homedir()` reads `USERPROFILE`, not `HOME`, so a test that fakes the home sets both, and one whose code measures bun's cache also points `BUN_INSTALL` at it and drops CI's `BUN_INSTALL_CACHE_DIR`.
- `scripts/vitest-orphan-guard.ts` (from `vitest.setup.ts`, every worker of both projects) ends a test worker whose parent is gone, checked every 2 s (`ppid` changed, or the parent no longer runs, which is what Windows shows), because an orphaned `forks` worker keeps its test file and memory going and has stalled this machine. Never cut a test run off with a pipe into `head`; stop it through its own process (`bun run locked` stops the whole tree). Pinned by `scripts/vitest-orphan-guard.test.ts`.
- Two projects, `renderer` (`src/renderer/**`, worker threads) and `node` (everything else, a child process per file), run one after the other (`vitest.config.ts`; e2e-ci-windows › Local checks). Never key worker counts on `CI` (agent shells here export it; GitHub's runners are `GITHUB_ACTIONS`), and never turn `isolate` off.
- A test waits on an event, a promise or fake timers, never on wall-clock time. The `*-stock` files (`bridge-autopilot-stock`, `stock-helper-extensions`, `bridge-accounts-stock`) run real stock omp and stay ungated; they are the ones that time out under load.
- A test that needs a git repository takes it from `initRepo` / `initRepoWithRemote` (`src/main/local/git/test-repos.ts`): a copy of a template each test process builds once (in the run's folder from `scripts/vitest-test-repos.ts`, deleted when the run ends), with `maintenance.auto` and the remote's `receive.autogc` off. A git process is slow on a busy Windows runner, so a file whose cases each run git dozens of times is split so its cases run side by side, its shared world in a `*-test-rig.ts` (or `*-fixture.ts`) the parts import (`disk/disk-care*.test.ts`, `autopilot*.test.ts`, `autopilot-ship*.test.ts`, `agent-control/branches*.test.ts`, `worktree-orphans*.test.ts`). Find the next one in the Windows platform job's log: each file's line ends with its milliseconds. On Windows the node project's hooks get the tests' 20 s, since they run git too.

### Build and the agent loop

- Build: `bun run build` (`scripts/build-cache.ts`: electron-vite → `out/`, then `scripts/check-main-bundle.ts`). It reuses `out/` built from identical inputs and says so in one `[build] reusing …` / `[build] building out/: <reason>` line; `OMPDESK_FORCE_BUILD=1` always builds (inputs and stamp: e2e-ci-windows › Local checks).
- Native: `bun run build:native` (`scripts/build-native.ts`) builds OMPdesk's own Rust (`native/ompdesk`: the `ompdesk` CLI and the core process `ompdesk-core`, where main's subsystems move one by one) into the gitignored `resources/ompdesk-bin/<platform>-<arch>/`; it needs Rust (rustup; the toolchain is pinned in `native/ompdesk/rust-toolchain.toml`). Every vitest run of the node project ensures the binaries first (`scripts/vitest-native.ts`), packaging fails without them (native-rust).
- Dev: `bun run dev` (builds native first; HMR against the system omp; opens a visible window).
- Fresh worktrees install through the repo's `.ompdesk/worktree-setup` (`.cmd` on Windows; OMPdesk runs it after `worktree add`, run it yourself after a plain `git worktree add`): `bun install --frozen-lockfile`, then `bun scripts/ensure-electron.ts` (the `postinstall` script runs it on every `bun install`), because bun runs electron's `install.js` with the `node` on PATH, and on Node 26 `extract-zip@2` never settles, so the binary is never unpacked ("Electron failed to install correctly"); `ensure-electron.ts` re-runs the installer under bun's runtime from the `~/Library/Caches/electron` zip. Never copy `node_modules` or `dist` from another checkout.
- Default agent loop: `bun run check:changed [--base <ref>] [--no-e2e] [--list]` (`scripts/check-changed.ts`), not the gate: typecheck, biome on the changed files, the surface policy and `vitest related`, then the build, then the Playwright specs whose file name or shown English text matches the change (e2e-ci-windows › Local checks). It is a name match, not a dependency graph: a change whose specs find it neither by name nor by its text, or one in e2e support files, needs `bun run locked -- bunx playwright test <spec>` by hand. Neither the full vitest nor the full Playwright suite is needed between edits.
- Never drive the app with synthetic OS input (osascript keystrokes etc.); use Playwright.

### Lock and gate

- The machine-wide lock is one counting semaphore per kind of heavy work (`build` 1, `playwright` 4, `vitest` 1, `other` 1) plus one `heavy` semaphore every hold takes first, sized from RAM (1 on 16 GB), because too much at once overloads the machine (`scripts/lock-slots.ts`, `scripts/build-lock.ts`). Slots, queue, snapshots, workers, log: e2e-ci-windows › Lock and gate, › Lock on a small machine.
- `bun run gate` (`scripts/gate.ts`) is the full local check (static checks and full vitest, then the full Playwright suite on that build). It is optional: the release gate is release.yml (see CI).
- Run any other build, Playwright run or full vitest run as `bun run locked -- <command>` (e.g. `bun run locked -- bunx playwright test e2e/smoke.e2e.ts --output /tmp/<you>-results`); `--chunk <n>` splits a playwright/vitest command into shards, one hold each, so a long job lets waiters in between.
- Parallel agents: on a big machine the lock lets up to seven heavy holds run at once, on 16 GB one; past that, agents only queue. Give each agent one disjoint slice; iterate with targeted vitest outside the lock, run builds and e2e as short `bun run locked -- …` holds (several specs in one command, a long sweep split with `--chunk`), commit verified hunks locally as you go, and leave the full gate to CI.

### Dev rules

- Never reinstall `/Applications/OMPdesk.app` from inside the app (you may be running *inside* OMPdesk; quitting it kills this session). `scripts/reinstall-mac.sh` (`bun run package:mac -- --publish never && bash scripts/reinstall-mac.sh`) runs **only when the user explicitly asks for a local reinstall**. **Never** schedule a swap with `launchctl submit` (launchd keeps submitted jobs alive and reruns them, so the app quits and relaunches forever) or any `KeepAlive` job.
- Child processes the app spawns must not outlive it: they get an open stdin pipe and exit when it closes (see `resources/gui-bridge/stats-host.ts`), because a crash or force-kill skips the quit handlers. The one process meant to outlive the app is ai-memory's own per-user service (launchd LaunchAgent / Windows logon entry, serving the terminal omp too): not OMPdesk's child but the service `ai-memory setup` installs. That `setup` is supervised like any installer and dies with the app; it runs isolated (`SpawnSpec.isolated`) so the service holds no handle of the app's (memory). A new command whose descendant outlives the app by design runs isolated the same way.
- A test run closes what it opened (apps, windows, unsaved documents, dev servers); what was open before stays.
- A spawned omp never inherits another OMPdesk session's plumbing: `SESSION_OWNED_ENV` (`src/main/omp-launch.ts`, beside `sessionEnv`, which sets them) lists every `OMP_GUI_*` variable a spawn sets from its own launch (bridge socket, reply language, profile, judge assist, delegation, account rotation, roles file, REA root, pstack, memory), and those are removed from the app's and the login shell's environment before the spawn adds its own, so a run started from an OMPdesk session's shell never hands its tabs the parent's plumbing. A new per-spawn variable goes into `sessionEnv` and that list together (`omp-launch.test.ts` fails when they differ; `shell-env.test.ts` checks a real spawn); test hooks (`OMP_GUI_TEST_*`) still pass through.
- No git command, the app's or a test's, follows a repository selector it did not set: `git bisect run` from a linked worktree, a hook or a shell inside a git operation exports `GIT_DIR` and its kin (`GIT_REPO_SELECTOR_ENV`, `src/shared/git-env.ts`), and a test's temp-repo `git init`/`git config` would then rewrite the shared checkout's `.git/config`. `execBin` and `gitRunner` (`local/git/exec.ts`; the core process's git reads take their whole environment from it) drop the ambient ones before the caller's own `env` (disk care's scratch `GIT_INDEX_FILE` still applies), as do `gitSync`/`initRepo` (`local/git/test-repos.ts`), both test runners' configs, `vitest.setup.ts` and e2e `launchApp`. A new spawn of git outside those builds its env with `withoutGitSelectors`. Pinned by `local/git/git-env.test.ts`.

## Change workflow

Commit and push each change as it lands; release in small batches without waiting to be asked (the repo is public, CI and releases cost nothing).

1. Each finished fix or feature: run `bun run check:changed`, commit with a normal descriptive message (no version bump, no CHANGELOG release section), push to `main`. ci.yml's `check` runs on the push; a red `check` is fixed before anything else lands.
2. Release by what landed since the last release, never by the clock (the user's rule): three user-visible changes (`feat`, `fix`, `perf`), one urgent fix (a defect that breaks the released app, a regression of the last release) on its own, or a user-visible change that has waited a day. Docs, tests, refactors and CI alone never make a release. Every release prompts every user to update and restart, so a lone small change waits for company. No local gate: ci.yml already ran the blocking checks per push, and release.yml is the gate (e2e-ci-windows › CI). The full Playwright suite runs nightly and on demand (`e2e-nightly.yml`), not in a release.
   - A release is a cut of `main`, not a list of work to finish. It ships what `main` holds when it is cut; work still running in other sessions, a hunt for an intermittent test, a red nightly or a Windows full run ships in the next release.
   - Other sessions keep pushing while a release runs, `package.json` changes included. The tag lands on the run's own commit; a later push that starts a release run waits for the running one and then finds the tag cut (it ends after `prepare`) or releases a newer version. No session holds its pushes; a release commit that finds `main` moved rebases like any push.
3. Release per the steps under Release: one dated bilingual `CHANGELOG.md` section covering every commit since the last release, one version bump, commit `release: vX.Y.Z`, push, watch the run (step 4; rerun only failed jobs), tell the user it went out.

- Never leave an `Unreleased` section on `main`.

## Release

- Semver `X.Y.Z`; tag `vX.Y.Z`; commit `release: vX.Y.Z`. No AI attribution trailers in commit messages.

### Steps

1. Pick the version from commits since the last tag (features → minor, fixes only → patch). Bump `package.json` `version`; add `## [X.Y.Z] - YYYY-MM-DD` to `CHANGELOG.md`: Korean summary, a line holding only `<!-- en -->`, then the English summary. release.yml turns the marker into `---`, so the GitHub notes carry both, Korean first; the What's new and changelog windows show the UI language's part and fall back to Korean (`changelogSection`/`changelogReleases` in `src/renderer/lib/whats-new.ts`).
   - **Open each section with one plain sentence.** `layout/WhatsNewCard.tsx` (one in-flow row under the title bar, mounted by `AppShell`; never over a composer, transcript or side panel; once per new version; never during the setup takeover, first run or tour) shows that first paragraph (`changelogSummary`); "자세히 보기" opens the section in the dialog. After skipped versions one card names the newest and the dialog lists every release since the last seen (`changelogSince`). The card stays until dismissed or opened, and hides after 60 s of focused, unhovered time (`WHATS_NEW_AUTO_HIDE_MS`).
   - Update README version mentions. Confirm `MIN_OMP_VERSION` (`src/main/omp-runtime.ts`) is current.
2. `git commit -am "release: vX.Y.Z" && git push origin main`. Do not tag. The tag lands on the commit the run starts from, and that commit's diff must not touch `.github/workflows/*`, because `publish` tags with the run's `GITHUB_TOKEN`, which never has the `workflows` permission (HTTP 403 "Resource not accessible by integration"). Ship a workflow change in its own commit, then an ordinary commit (the release commit, or an empty `chore: release point …`) before dispatching the release.
3. `release.yml` does the rest (its jobs: e2e-ci-windows › CI). Only if all passed, `publish` creates tag `vX.Y.Z` and the Release (title `vX.Y.Z`) with exactly two version-free assets, `ompdesk-mac-arm64.dmg` and `ompdesk-windows-setup.exe`, so `/releases/latest/download/<name>` stays stable. Notes = changelog section + minimum omp version + `<!-- ompdesk-update {"version","releaseDate","files":{"mac"|"windows":{"name","size","sha512"}}} -->` (sha512 base64), appended by the "Append update metadata" step; GitHub does not render it.
   - No other assets; an existing tag or an `Unreleased` heading makes the run a no-op (e2e-ci-windows › CI › Release assets).
4. Watch: `bun scripts/watch-run.ts <run-id>` (a release push's run: `--release --sha <pushed commit>`) as a bash `async: true` job, then `wait`, never a foreground poll or `gh run watch --exit-status` (e2e-ci-windows › CI). It exits 1 at the first failed job with its failed step and first error lines, 0 when the run succeeds. A failure the code didn't cause (runner, network, flaky test): `gh run rerun <run-id> --failed`, never a whole new run. Otherwise fix on `main` and re-run with `gh workflow run release.yml`. Rehearse from any branch: `gh workflow run release.yml --ref <branch> -f dry_run=true`.

- Manual fallback: `bun run package:mac -- --publish never` on a Mac, `bun run package:win -- --publish never` on Windows; copy `dist/ompdesk-X.Y.Z-arm64.dmg` → `ompdesk-mac-arm64.dmg` and `dist/ompdesk-X.Y.Z-setup.exe` → `ompdesk-windows-setup.exe`; append the metadata comment to the notes as that step does (a release without it is not offered as an update); `gh release create vX.Y.Z --target main --title vX.Y.Z --notes-file <notes> ompdesk-mac-arm64.dmg ompdesk-windows-setup.exe`.

### Signing

- Mac builds are signed with OMPdesk's own self-signed certificate (`scripts/mac-sign.cjs`, pinned by SHA-1 in `scripts/mac-signing.json`), so the designated requirement stays the same in every release and macOS keeps its privacy grants across updates. **Never replace the certificate.** Identity sources, keychain and notarization: e2e-ci-windows › Signing.

## Code conventions

- **Never hold agent work back** (the owner's rule). An agent's open or message, a scheduled run and a relaunch continuation start at once: no count cap, no queue, no wait for memory. Only idle release, which gives a quiet hidden session's omp back while memory is short, acts on memory (control-tools › Memory and idle release).
- **UI is built from the shared components** (`src/renderer/components/common`). Read its catalog, `src/renderer/components/common/README.md` (which component for which need, container policy, the rules every component keeps), before writing UI. A need none covers gets a new component there, never a private copy in a feature folder. `scripts/lint-controls.mjs` (run by `lint-surfaces.mjs`; `node scripts/lint-controls.mjs` runs it alone) fails a renderer `.tsx` outside `components/common` that holds a raw `<button>`, a raw checkbox or radio (`Checkbox`, `Radio`), a hand-made `role="dialog"`, a hand-made `role="tab"`/`role="tablist"` (`Tabs`, `SegmentedChoice`), a hand-made `role="progressbar"` (`ProgressBar`) or a turning lucide loader (`Loader2` with `animate-spin`; `Spinner`); a deliberate one says why on its line or the line above with `controls-ok: <reason>`, and there is no other allow-list. Pinned by `scripts/lint-controls.test.mjs`.
- TypeScript: no `any`, no inline `import("…")` types, `#private` fields, Bun APIs where cleaner.
- **A layer over the window cuts itself out of the drag area.** The 48px top bars are `-webkit-app-region: drag`, and Chromium builds the window's drag area from every element that declares a region, whatever is drawn over it, so a click on a dialog reaching into those bars is taken as a window drag. `global.css` gives every overlay layer (`.omp-dialog-overlay`, `.omp-action-sheet-overlay`, a `Sheet`'s `[data-sheet-placement]`, `.omp-pop-in` popovers and menus) `no-drag`; a new floating layer that can reach the top bars wears one of those or `no-drag` itself. Pinned by the model picker case of `e2e/responsive-smoke.e2e.ts`.
- **Main's `fs` over a user's folders is `original-fs`.** Electron's patched `fs` treats a path through a `*.asar` as a folder, and stat, lstat, access, exists, realpath, open, read or copy of one keeps the archive open for the life of the process (`readdir` alone and every `original-fs` call hold nothing), so Windows cannot delete it while OMPdesk runs; every Electron project's `node_modules/electron/dist/resources/default_app.asar` is one. `src/main/disk/*`, `worktree-orphans.ts`, `worktree-removals.ts`, `open-path.ts`, `web/host-actions.ts` and `local/git/{scm,worktree,worktree-seed}.ts` import `promises as fs` from `original-fs`; a module that walks, stats, copies or removes a user's folder does too (the workspace files the Files panel reads are the core process's, which has no asar). `process.noAsar` stays unset (main's own code is read from `app.asar`). Pinned by `e2e/disk-care-asar.e2e.ts` and, for the modules that spec does not reach, `src/main/user-folder-fs.test.ts` (a source check: plain Node has no asar, and `vitest.config.ts` aliases `original-fs` to `node:fs`).
- i18n: English and Korean only (`UI_LANGUAGES` in `src/shared/ui-language.ts`). Every user-visible string goes through `useT()` with the same key in `src/renderer/locales/en.ts` and `ko.ts` (`locales.test.ts` enforces identical key sets). Settings-schema text: `src/renderer/components/settings/schema-ko.ts` and `schema-option-ko.ts`; main-process strings: `src/main/i18n.ts` and `tray-labels.ts`.
- Model output renders through `MarkdownRenderer` (`src/renderer/lib/markdown.tsx`, rehype-sanitize), never `dangerouslySetInnerHTML` with model text. Text a person typed (prompt bubbles) passes `userText`: single-dollar math stays literal, HTML tags show as typed (`remark-html-text.ts`), and every newline is a line break, as typed with Shift+Enter (`remark-soft-breaks.ts`), where Markdown would read one as a space.
- A path a reply or tool card links is never given to `shell.openPath` when opening could run something. `openLocalPath` (`src/main/open-path.ts`) reveals launcher types in Finder/Explorer instead: `.app .command .sh .jar .exe .bat .cmd .ps1 .lnk .url .msi`; interpreter scripts (`.py .pyw .pyz .pl .rb`; python.org's launcher runs `.py` on macOS); Windows script, scriptlet, shortcut, help, add-in and theme types (`.chm .xll .wsc .sct .theme .settingcontent-ms` and the like); macOS `.terminal .workflow .pkg .dmg .scpt .webloc` and the like; anything an executable bit marks on POSIX; any symlink to either. A new caller that opens a model-supplied path goes through it.
- Tool-rendered text uses `src/renderer/lib/format.ts`; preview ceilings come from `src/renderer/lib/preview.ts`; subprocess output renders through `AnsiText` (`src/renderer/lib/ansi.tsx`).
- Component tests use the linkedom harness (see `src/renderer/components/chat/ThinkingBlock.test.tsx`): mount through `I18nProvider`, reset zustand stores in `afterEach` via `reset()`/setters; never `mock.module()`.
