# ompdesk — Development Rules

Read this before any edit in this repository.

## Repository identity

- Product: **OMPdesk** (`OMP` capitals, `desk` lowercase) is the display name in every user-visible string, the bundle (`OMPdesk.app`, `productName`), menus, tray, and window title. An unofficial desktop app for the omp agent. Identifiers stay lowercase: the package name, the bundle id `com.seuput.ompdesk`, `app.setName("ompdesk")` (which picks userData `~/Library/Application Support/ompdesk` (`%APPDATA%\ompdesk`) and the "ompdesk Safe Storage" keychain item), the repo, and the two release asset names `ompdesk-mac-arm64.dmg` / `ompdesk-windows-setup.exe` (README download links and the updater fetch them by exact name; `packaging-config.test.ts` pins them). The first launch moves the pre-rename profile from its sibling directory into userData before anything reads it (`src/main/legacy-user-data.ts`, skipped under `--user-data-dir`). Say "omp" only for the agent/CLI (`omp update`, "omp 18.7+"). The mark (an omp-style π: top bar and two legs, the shorter left leg ending in an accent-colored foot; full and ≤48px pixel-grid forms) is defined once in `src/shared/brand-mark.ts`; `bun run gen:icons` writes the SVGs in `resources/icon-source*.svg` and `resources/brand/` from it (`scripts/brand-svgs.ts`; never hand-edit them, `brand-mark.test.ts` fails on drift; the hand-made README buttons `resources/brand/download-*.svg` are exempt) and regenerates `icon.png`/`icon.icns`/`icon.ico`, the tray PNGs and the favicon. The in-app mark is `components/common/BrandMark.tsx`.
- Product repo: [`SeuPut0705/ompdesk`](https://github.com/SeuPut0705/ompdesk) (`origin`). All code, tags, and releases live here.
- The agent is **stock omp** ([`can1357/oh-my-pi`](https://github.com/can1357/oh-my-pi)) installed on the user's machine. It is never built, vendored, or forked here. Users get agent updates with `omp update`.
- Platforms: **macOS and Windows only.**

## Architecture

```
renderer (React) ── IPC ──▶ main (Electron)
                              ├─ src/main/local/*      fork-era commands served in main
                              │     (git/gh, fs, ~/.omp files, `omp` CLI, translation to stock RPC)
                              ├─ src/main/sidecar.ts   spawns `omp --mode rpc-ui -e <gui-bridge>/index.ts`
                              │                         (stock RPC over stdio)
                              └─ src/main/bridge-client.ts ◀── unix socket / named pipe ──▶
                                                         resources/gui-bridge/*  (omp extension,
                                                         live AgentSession access)
```

- The renderer speaks one command set. `RpcClient.command()` (`src/main/rpc-client.ts`) first looks for a **local handler** (`src/main/local/index.ts` merges `src/main/local/<area>.ts` maps; duplicate keys throw at startup). Commands without a local handler go to stock omp unchanged.
- A local handler (`LocalHandler`, `src/main/local/types.ts`) either does the work in main (git, gh, files, `ctx.omp.run([...])`), translates to stock RPC (`ctx.send(...)`), or calls the bridge (`ctx.bridge.request(method, params)`) when it needs live session state.
- **Bridge** (`resources/gui-bridge/`): an omp extension loaded with `-e`. Area modules export `methods` maps; `env.session()` is the live `AgentSession`, `env.pi.pi` the stock package index. Bare `@oh-my-pi/pi-coding-agent/...` subpath imports resolve through omp's own resolver. These are **internal omp APIs without semver** — keep methods small, feature-detect, and throw clear errors.
- **Compatibility self-check**: every omp internal a bridge module uses is listed per GUI feature in `resources/gui-bridge/capabilities.ts` (`REQUIREMENTS`); add the new internal there (and its module to `LOADERS` in `health.ts`, literal specifier) whenever a bridge method starts using one. `index.ts` loads each area module separately, `guard(feature, methods)` refuses a feature's methods with `unsupported_omp` while anything it needs is missing, and the `capabilities` method reports them; `src/main/bridge-health.ts` probes once per omp version per launch and the renderer toasts the result. `OMP_GUI_BRIDGE_PROBE_HIDE=<label>,…` (labels as `capabilities` prints them, e.g. `AgentSession.setPlanModeState`) makes the probe treat those internals as missing, to rehearse a broken omp.
- Settings layout (`settings-catalog.ts` `SETTINGS_NAV`, one name per section in en/ko and the native menu): App — General (language, notifications, profile, window, Sidebar shortcuts, GitHub account; proxy under Advanced), Appearance & input, Keyboard shortcuts; Agent — Models & accounts, Agent behavior, Tools & extensions, Permissions & security, Projects & launch, Schedules; System — Devices & connections, Updates & about (versions plus This computer, the machine setup list), Other settings. Each section shows its curated rows first; rare or raw stock rows (non-curated schema rows, launch profile, reset passes, account pools, model overrides, the proxy) fold under one closed `SettingsAdvanced` disclosure at its end, and `SettingsPage` opens it before scrolling to a search hit or deep link inside — so every row stays reachable and searchable. Models & accounts reads top to bottom as connection, then models: Providers & accounts (accounts, live quota, rotation), Custom endpoints, then Model (the setup assistant, Model roles, Defaults, Compare models). "This device" / "Selected host" scope lines show only while the focused tab runs on a paired host. Sidebar shortcuts (prefs `sidebar.railPins`) are off by default; Help › Customize sidebar… opens their switches. Older paths below ("Models & providers", "General › This computer", "Settings › SSH") mean these sections.
- Reply language: Settings › General › Conversation language stores prefs `replyLanguage` (`auto` default | a curated English name | `off`; `src/shared/reply-language.ts`). `auto` is the device language's English name (first usable `app.getPreferredSystemLanguages()` entry, then `app.getLocale()`; not the UI language). Each spawn passes the result as `OMP_GUI_REPLY_LANGUAGE`, and a pref change (or a bridge connect) pushes it to every live local sidecar and every tab this machine hosts through the bridge's `reply_language_set {language: string | null}`; a paired host's tabs follow the host's own pref. The bridge's `modes/reply-language.ts` keeps the value as module state and appends one instruction through `before_agent_start` from the next turn (nothing when off, unset or English, so the prompt stays stock). Never inject GUI text with `--append-system-prompt`: it collides with the launch profile's flag and turns off omp's fork prompt-cache key.
- Compact settings rows (`settings/SettingsLayout.tsx`): `SettingsRow`/`SettingsSwitchRow` are one dense line (`--sc-control-md` high) — optional `icon` (a lucide glyph, or `ProviderMark` for a provider, model or vendor CLI; decorative, `data-setting-icon`), label, a muted `description` and the control at the right. A string description up to `INLINE_DESCRIPTION_MAX` (56) characters reads inline; a longer one moves behind a `SettingInfo` glyph (tooltip on hover/focus, the text stays in the DOM as `sr-only`, `data-setting-info`); a node description (a cost, a warning) stays a visible small muted note. Group titles are small, the same split applies to a titled `SettingsSection` description, and collections (accounts, CLIs, devices, schedules, MCP servers, shortcuts) are dense list rows with their secondary actions behind an overflow `MenuButton`. New rows reuse these, never a boxed card or a full-width description paragraph. `e2e/settings-captures.e2e.ts` (`OMPDESK_SETTINGS_SHOTS=<dir>`) captures every section in light/dark × en/ko, wide and narrow.
- Profile: Settings › General › Profile stores prefs `userProfile` (`{name, experience}`; contracts and prompt text in dependency-free `resources/gui-bridge/user-profile-contracts.ts`; levels beginner, vibe-coder, junior, expert). It rides the reply-language path: `OMP_GUI_USER_PROFILE` (JSON) at spawn, `user_profile_set` on change and on bridge connect to every live local sidecar and every hosted tab, and `modes/user-profile.ts` appends one `<user-profile>` section through `before_agent_start` (nothing for an empty profile). Stock has no such setting.
- Prompt suggestions (built in, Settings › Agent behavior, prefs `nextPromptSuggestions` default **on** and the sub-switch `nextPromptInline` default on; `resources/gui-bridge/next-prompt-contracts.ts`, rules in `next-prompt-core.ts`, behaviour in `next-prompt-engine.ts` behind `modes/next-prompt.ts`): same plumbing as the reply language (`OMP_GUI_NEXT_PROMPT` JSON at spawn, `next_prompt_set` on change and on bridge connect to every live local sidecar and hosted tab; a paired host's tab follows the host's pref). Stock's `ComposerPredictionController` runs only in its TUI and `runEphemeralTurn` can only use the session model, so the engine calls stock `completeSimple` on the model stock's `smol` role resolves to (`resolveRoleChain` over `roleCandidatePool`, the session's credentials through `modelRegistry.resolver`; reasoning off, ≤ 512 output tokens, one retry without the cap when a transport refuses it) and never falls back to the main model: no model / no credentials / refused / offline become `unavailable` frames, shown as a muted `role=status` line under the composer plus a bridge debug log, never a toast. One request per finished turn (`agent_end`), regenerated (debounced 800 ms, gated by `gateSuggestion`: enabled, idle, main agent, empty composer, a reply exists, state key moved) after a compaction, a finished user `!` command (renderer `refresh_next_prompt`), a session switch and an emptied draft; typing (`set_next_prompt_draft`, reported by `use-idle-compaction-draft.ts`), a new run or the switch going off aborts the request, and an answer whose moment moved while the model answered (new messages, running work that ended or started) is dropped and asked for again. The prompt carries the transcript tail (the reply being followed up clipped to 1800 characters, older ones to 700) plus a compact `<app-state>` (last failed tool/command and exit, files changed this turn, open plan/todos, a question answered this turn, the main agent's running subagents and background jobs as `running-now` — stock `getAsyncJobSnapshot`, a subagent with the intent of the `task` call that spawned it —, goal, whether tests ran and failed, the user's `!` command, compaction) read from the live session. Its rules take the voice and follow-up lines of stock's `prompts/system/composer-prediction-user.md`, ask for exactly 3 different next steps (asked for "up to 3", the cheap model often wrote one, so no chips showed) and forbid anything already done, started, planned or handed to a subagent. Running work does not suppress suggestions: a delegating session has jobs running at almost every turn end, so suppression would switch the feature off where it is used most; instead the model is told the work is underway and suggests waiting for it, checking or steering it, or something unrelated. The best of up to 3 ranked one-line candidates is the placeholder (Tab/→), the rest are chips (↓ from an empty composer enters them, ←/→, Enter/click fills; Alt+1..3 fills directly); the per-session memory in `stores/next-prompt.ts` is unchanged (submit or a run clears it, a deleted draft brings it back, so an accepted-then-sent suggestion is simply the submit). Inline completion (`complete_inline` → `next_prompt_inline`, same cheap model, ≤ 160 tokens, `InlineScheduler`): ghost text after the caret for a single-line draft of ≥ 8 characters with the caret at its end, 600 ms after the last keystroke, at most one request start per 2 s (so ≤ 30 a minute, answers cached per draft; `e2e/next-prompt.e2e.ts` scripts 10 typing bursts with pauses in a minute and sees 10 requests), aborted on every keystroke, never during IME composition, with a slash/`@` menu or paste choice open, for drafts starting `/`, `!`, `$`, `->`/`=>`, or a draft stock's `shouldSkipHistory` calls secret; Tab accepts, Esc dismisses. `next_prompt_state.requests` counts both kinds. The user's own `next-prompt` extension is found through stock's loaded-extension list (`legacyExtension`); while the built-in is on the renderer ignores its widget (its own request cannot be stopped from here), and with the built-in off or unsupported the widget path works as before. Pinned on the real omp by `src/main/bridge-next-prompt-stock.test.ts` (smol resolution, legacy detection, reply cleaning against stock's `parseComposerPrediction`) and, opt-in with `OMP_GUI_REAL_WORK=1`, by `e2e/real-next-prompt.e2e.ts`; the loaders are `config/model-roles`, `config/model-resolver`, `modes/controllers/input-controller` and `pi-ai` in `capabilities.ts` / `health.ts`.
- Automatic session titles (built in, Settings › Agent behavior › Session titles, prefs `autoTitle` and the sub-switch `autoTitleEvolve` "keep the title up to date as work changes", both default **on**; dependency-free contracts in `resources/gui-bridge/auto-title-contracts.ts`, rules in `auto-title-core.ts`, behaviour in `auto-title-engine.ts` behind `modes/auto-title.ts`, capability `autoTitle`): same plumbing as the prompt suggestions (`OMP_GUI_AUTO_TITLE` JSON at spawn, `auto_title_set` on change and on bridge connect to every live local sidecar and hosted tab; a paired host's tab follows the host's pref). **Stock machinery only, never the session model for a first title**: `AgentSession.generateTitle` (stock's `generateSessionTitle`, models from the `tiny`, then `commit`, then `smol` role chain; the session model only as stock's own retry fallback after those failed) names the operator's first message (`operatorTitleText`), `renameTitle(title)` adds the card per `title.icons`, a message the title model declines (a greeting) is retried from the conversation after the turn with `renameTitle()` (stock's `/rename` without a title), the main agent only (subagents are excluded). **Origin is stock's own record**: `SessionManager.titleSource` and the journal's `title_change` entries (`source`, `trigger`); the one case stock cannot say, "a fresh automatic title over a typed one" (`setSessionName(…,"auto")` is refused over source `user`), is written as source `user` with `trigger: "ompdesk-auto"` (`TITLE_TRIGGER`) and read back by `titleIsAuto` (`auto-title-core.ts`), so nothing lives in a GUI-only file. **Evolving** (sub-switch): after a terminal `agent_end` while the title is automatic, `EvolveGate` (cheap, no model call: at least 2 terminal turns and 60 s since the title was set or last considered, and the work moved — a file edited/written 1, the todo plan changed 2, the goal changed 3, threshold 3 — or 6 turns regardless) asks stock `renameTitle()` once per window; the result is applied only when it is not a reword of the current title (`isRewordedTitle`: normalized word overlap ≥ 0.6 or character-trigram overlap ≥ 0.55), and every write re-checks the session id, the name and `titleRevision` it started from, so a typed name wins over any request in flight and ends the evolving. Cost: 1 title-model request for the first title plus 1 for its card (none with `title.icons: boring`), then at most 1 request per two finished turns and minute, only after files/plan/goal moved or six quiet turns (counted in `auto_title_set`'s `requests`). The editors' ✨ auto button (title bar, rename dialog, sidebar row; `hooks/use-auto-title.ts`, `common/AutoTitleButton.tsx`) sends `regenerate_session_title` → local handler → bridge `regenerate_title` (`renameTitle()` on the live session, saved by the bridge as an automatic title even over a typed name; failure is one inline `role="alert"` sentence, never a toast); a stored session no tab has open has no omp to ask, so its button is aria-disabled with a tooltip (the origin tracking lives in that omp, and a short-lived `omp` per click could neither keep it nor be cancelled); a paired host's tab answers on the host (the command is in `quota-commands.ts`' model list). A changed title eases in (`common/SwapText.tsx`, `.omp-title-swap`; the global reduced-motion rule shortens it). e2e: `e2e/auto-title.e2e.ts` on the fake omp (`OMP_GUI_TEST_AUTO_TITLE`).
- Delegation strength: the composer chip (`layout/DelegationControl.tsx`) sets Your settings / Solo / Assisted / Collaborative / Swarm per tab through `get_delegation`/`set_delegation` → bridge `modes/delegation.ts` (rules `delegation-core.ts`, presets `delegation-contracts.ts`). Each strength is stock `task.eager`, `task.maxConcurrency` and (Solo) `task.maxRecursionDepth = 0` held as runtime overrides, never written to config.yml; stock's own listeners rebuild the prompt and drop or restore the task tool. The last pick is prefs `delegationMode`, passed as `OMP_GUI_DELEGATION` on every spawn and applied inside the extension factory like the thinking default; a Settings write of one of those settings releases the strength.
- Account rotation: Settings › Models & providers stores prefs `accountRotation` (`quota` default = stock omp's usage ranking | `even`; `src/shared/account-rotation.ts`, control `providers/RotationModeControl.tsx`). Stock has no switch for it, so each spawn passes `OMP_GUI_ACCOUNT_ROTATION` plus the shared ledger `<userData>/account-rotation.json` (`OMP_GUI_ACCOUNT_ROTATION_STATE`), and a change (or a bridge connect) pushes `account_rotation_set {mode}` to every live local sidecar and every tab this machine hosts (`LocalMachine.setAccountRotation`, `src/main/account-rotation.ts`). In even mode the bridge's `account-rotation.ts` (`before_agent_start`) gives a session without an account the unblocked one handed out least recently across all local omps, as an automatic warm pin (`authStorage.sessions.pin(…, {restoredAtMs})`); a session keeps its account until it is blocked (an idle pin is renewed, not re-ranked), and stock's 429 blocking/failover is untouched. A paired host's tabs follow the host's pref, which Settings reads and writes through `host.accountRotation.get|set`.
- Provider sign-in (Settings › Models, first run; `providers/ProviderLogin.tsx`) runs stock `login` on the tab's omp. Its `open_url`, `input` and info `notify` requests that arrive while a sign-in is in flight belong to the panel (`loginRequestIds` in `stores/extension-ui.ts`; the kinds are `isSignInRequest` in `shared/rpc-types.ts`) and never render as chat cards, even after the panel unmounts, the page reloads or a paired host's link comes back: main counts the `login` commands in flight per tab with their providers (`SidecarPool.noteSignIn`; for a paired host's tab also what the host reports through its `signIn` tab event — sent as `login` starts and ends and on every `tab.open`, a new tab's included (`{active: []}`) and ahead of `openAsks` on a re-attach — because the host's login runs on when this window's `login` call fails with the link; a status the host reports (not the link) that leaves `ready` drops the host's list, since its logins died with that omp) and marks every request `isSignInRequest` accepts while one runs (`IpcSignIn`: `active`, provider, the browser page it opened) on the live `EXTENSION_UI` frame, in `EXTENSION_UI_OPEN` and in a host's re-sent `openAsks`. All of them reach the page through `pushTabExtensionUiRequest`, so one rule applies: a marked request is never a card. While `login` runs (`active`) it goes into `loginRequestIds` and the page adopts the sign-in (`adoptedLogin`, also counted as in flight), so the panel shows it again when opened ("Sign-in in progress…", the browser link, the paste fallback, Cancel) until main sends `SIGN_IN_ENDED` (`endTabSignIn`: answers the leftover, the panel reloads the providers or shows the failure; the outcome is unseen when a host's login ended while the link was down or its omp went away); once `login` has answered it is a leftover and is answered `cancelled` at once. A browser sign-in finishes through stock's loopback callback; stock also races a code paste against it ("Paste the authorization code…") and never closes it, so the panel shows the paste as a collapsed fallback (open on a paired host's tab) and answers the leftover request with `cancelled` once `login` returns — an empty answer before that only re-asks. Stock's RPC `login` takes no cancel and holds omp's serial command queue (up to its 5-minute callback timeout), so Cancel sends `login_cancel` (`src/main/local/settings.ts`), which ends it through the callback's own denial (`error=access_denied` with the flow's `state`, what a provider's Deny button sends). A relaunched client has lost the browser page of a host's login (the Cancel of its adopted panel then answers the paste instead).
- Held stock defaults: sessions OMPdesk spawns (local tabs and the tabs a host runs) differ from stock in the settings of `GUI_THINKING_DEFAULTS` (`resources/gui-bridge/thinking-default-core.ts`, wired by `thinking-default.ts`) unless some layer (config.yml, a project config, `--config` overlay, env) sets them. Each is held as a runtime override applied inside the extension factory (stock loads `-e` extensions after `Settings.init` and before createAgentSession builds the tools and the advisor and picks the first thinking level); never written to config.yml (the omp CLI keeps stock), reported by Settings with `runtime` provenance, released by a Settings write first (so the user's value persists and wins), taken up again by a reset, and inherited by subagents through stock's `createSubagentSettings` snapshot. Pinned on the real omp by `src/main/bridge-omp-defaults-stock.test.ts` and `bridge-goal-continuation-stock.test.ts`, rules in `bridge-thinking-default.test.ts`. The list:
  - `defaultThinkingLevel` = `auto` (stock `high`) and `providers.autoThinkingMaxEffort` = `max` (stock `xhigh`), so `auto` may resolve every effort the model supports up to its top tier. The advisor role is written with `:auto` when picked without a level (`resources/gui-bridge/role-values.ts`), because stock runs an unsuffixed advisor at a fixed `medium`; pickers show it without the suffix.
  - `goal.continuationModes` = `["interactive", "rpc"]` (stock continues a goal between turns over RPC only with `"rpc"` listed); the loader is `goals/settings` in `capabilities.ts` / `health.ts`.
  - `display.showTokenUsage` on (the GUI's usage row follows it unless a GUI display preference overrides), `lsp.diagnosticsOnEdit` on (a language-server pass per edit), `lsp.formatOnWrite` on (rewrites a written code file with its formatter).
  - `astGrep.enabled` on (`astEdit.enabled` is on in stock already). Both tools are the `@oh-my-pi/pi-natives` addon every omp ships, not a separate binary; `applyGuiThinkingDefault` feature-detects the export (`NATIVE_DEFAULTS`), and an omp without it keeps stock's value with a Settings note (`SettingEntry.note`, `settings.note.native`).
  - `advisor.enabled` on: a second model (the `advisor` role; unset it follows `slow`, then stock's slow chain) reviews every turn, which costs another model call per turn. Stock pins it off for RPC hosts (`protocolDefault: ["rpc", "acp"]`, `applyProtocolDefaults` in `main.ts` before the extensions load) as a soft runtime override that reads as configured; `PROTOCOL_PINNED` lets the override replace such a pin while nothing but the pin sets the value (provenance `runtime`, value equal to the schema default, no persisted layer). The advisor's other pinned tuning (`advisor.syncBacklog`, …) keeps stock's defaults. OMPdesk already renders advisor cards.
  - OTLP telemetry export off (the user's decision; not a setting): `telemetry.otlpExportEnabled` is read by `initTelemetryExport` in `main.ts` before the extensions load, so no runtime override reaches it; instead every omp OMPdesk runs a session in gets `OTEL_SDK_DISABLED=true` (`OMP_TELEMETRY_OFF` in `omp-runtime.ts`, spread last over the user's environment: local and hosted tabs through `SidecarManager`, scheduled runs, benchmarks, model setup and `omp` CLI calls through `runtime.run`), on which stock's only exporter (`telemetry-export.ts`) returns at once, whatever `OTEL_*` endpoints the user's environment names. The stats server and the stock helper never call it; `omp --version`/`update` exit before it. Pinned by `shell-env.test.ts`.
  - Not held, on evidence from stock 18.11.1: `display.showTurnTime` and `read.toolResultPreview` are read only by the TUI renderer (`modes/utils/ui-helpers.ts`) and the GUI has no consumer for them (it hides `display.showTurnTime`); `retry.usageAwareFallback` and `retry.waitForUsageReset` stay stock's, since account rotation and the interrupted-turn resume cover them.
  - Automatic session titles on (not a stock setting: stock's `autoTitle` is a session option that `main.ts` sets for the TUI only, and `main.ts` sets `PI_NO_TITLE` for `--mode rpc-ui`, so a GUI session stayed "New session"; prefs `autoTitle` and the sub-switch `autoTitleEvolve`, both default on, Settings › Agent behavior › Session titles). Not a runtime override of a setting: the bridge (`modes/auto-title.ts`, behaviour in `auto-title-engine.ts`) runs stock's own title machinery from the live session's events, so `PI_NO_TITLE` cannot reach it. The user's own `PI_NO_TITLE` is still respected: main reads it from the environment it hands omp (`titleSuppressedByEnv`) and passes `suppressed` in `OMP_GUI_AUTO_TITLE`/`auto_title_set`. Pinned by `bridge-auto-title*.test.ts` and `shell-env.test.ts`.
- Model roles (Settings › Models & accounts › Model roles; `ModelRolesSection.tsx`, `ModelRoleRow.tsx`; contracts in dependency-free `resources/gui-bridge/model-role-contracts.ts`): stock owns the roles (ids, names, `accepts`, empty-role fallbacks, `@role` resolution in `config/model-roles.ts` / `config/model-resolver.ts`); OMPdesk only groups them by purpose — Conversation (default, slow, smol, plan), Agent work (task, advisor, commit, memory, tiny), Input & output (vision, image, web, speech, dictation, judge), Custom roles — and writes a localized one-line "when it is used" (`modelRoles.use.<id>`, grounded in the stock call site, e.g. `commit/model-selection.ts`, `utils/image-question.ts`, `auto-thinking/classifier.ts`) and the empty-role fallback text (`modelRoles.fallback.<id>`) per role. `get_model_roles` adds `effective` to every role (`role-effective.ts`: the model it really runs on, resolved through stock `resolveModelOverride` / `resolveRoleSelection` over the role's own `roleCandidatePool`, with `source` configured / fallback / session / none and `via` the role that answered; the per-role selector lists copy the stock call sites and are pinned by `src/main/bridge-model-roles-stock.test.ts` against `resolveRoleChain` and `resolveAdvisorRoleSelection` on the real omp). A row also shows the provider's account state and the tightest live quota (`useLiveUsage`, `inUseReport`, `tightestLimit` from `lib/usage-reports.ts`), the thinking level the resolved selector names (else "follows session"), and a picker over stock's candidate pool. The model setup assistant proposes per group (its prompt and review table use the same groups) but assigns only stock's built-in roles; a custom role keeps the user's model.
- Custom roles (`modelRoles.<id>`, selected as `@id`): stock treats `@id` as a role only while `modelRoles.<id>` holds a value, and otherwise leaves it in an agent's `model:` list as a pattern that matches nothing, so resolution moves to the next entry (`getModelRoleAlias`, `resolveConfiguredRolePattern`, `resolveModelOverride`). An agent therefore lists the role first and the built-ins it follows while empty (`["@review", "@slow", "@task"]`) and needs nothing assigned. Consumers stock reads: an agent definition's `model:` (`resolveAgentModelSelection` in `task/executor.ts`, `structured-subagent.ts`), `task.agentModelOverrides`, `/model` and `--model` (`resolveCliModel`, only configured roles), and `cycleOrder` (a role needs a value to join it). OMPdesk ships six preset roles in `PRESET_ROLES` — explore, review, debug, docs, test, design — and never a role nothing consumes: `AGENT_TEMPLATES` (`src/shared/agent-templates.ts`) carry `role` and a `model` of `roleSelectors(role)` (code-explorer, code-reviewer, debugger, docs-writer, test-writer, ui-polisher), and `agent-templates.test.ts` fails on a preset without a template or a template naming a role outside the preset. - Interrupted turns continue by themselves (`src/main/turn-resume.ts`, `src/main/connectivity.ts`, Settings › General › Continue interrupted work after relaunch, pref `resumeInterrupted`, default on). **Two paths, one coordinator (`TurnResume`), driven by `SidecarPool.onRunningChange` (pool facts via `resumeFacts()`).** ① Relaunch: eligibility is a marker file `<userData>/interrupted-turns.json` ({window, tab, peer, sessionPath, cwd, kind, startedAt, reason}) rewritten atomically on every run-state transition — never in a quit hook, because SIGKILL/crash runs none. It exists while a turn runs (`running`), is cleared on normal completion and on the user's Stop (`SidecarPool.noteStopped`, called by the RPC dispatcher for `STOP_COMMANDS` `abort`/`abort_and_prompt`/`abort_and_restore_queue`, so a kill before the run's end event still leaves no marker), and a turn blocked on an ask/approval keeps it as `asking` (the relaunch re-runs the cut-off call, which reopens the card; it is not counted as "continuing"). An omp that exits or restarts takes its open asks/approvals with it: the pool forgets their owners on any non-ready status, so no `asking` outlives its process. A quit (`quitApproved()`) freezes writes: tearing the tabs down must not read as the turns ending. Closing the last shown window on Windows (close-to-tray off) is such a quit, asked for before the window goes (`lastWindowCloseAction` in `quit-guard.ts`): the confirmation runs and the markers stay, instead of the window's tabs ending first and `window-all-closed` quitting afterwards. At launch (`TurnResume.launch()`, after the saved windows exist) each marker finds its tab by session path — a deferred/background tab is started with `SidecarPool.startTab`, a tab missing from the layout is opened — and continues through stock: `restore_interrupted` (local handler → bridge `composer.restore_interrupted` → stock `restoreSession`, the code behind `omp --restore`, which is TUI-only as a flag) for a cut-off turn, `retry` (`/retry`, the quota-resume path) for a failed one. A killed OMPdesk's omp usually closes the turn itself before it exits (stdin EOF: a pending ask/approval fails with "RPC client disconnected before extension UI response completed" and the run is journaled aborted), so `restoreSession` finds nothing unfinished; the relaunch then runs stock `retry`, which replays that failed tool batch (the card reopens) or the aborted reply, and does nothing for a turn that really ended. A continuation waits for its tab's omp to be ready (at most `RESUME_READY_TIMEOUT_MS`; an omp that already failed drops the marker at once), and the toast's Stop, the waiting row's Cancel and a new prompt on a held tab call it off even during that wait (a per-tab generation it checks before every command). **The host owns the turns it runs for a paired device.** On the device (A) a remote tab (`device`) is skipped entirely: no marker, no judging, no takeover by A's connectivity. On the host (B) `index.ts` composes `TurnResume`'s pool from `SidecarPool` and `LocalHostServices` (`resumeFacts`/`startTab`/`setAwaitingConnection`/`noteStopped`/`tabForSession`, ids `peer:<deviceId>:<rtab>`, kept when the tab is re-keyed; run bookkeeping shared through `trackRunEvent` in `sidecar-run-state.ts`; asks tracked from the tab's `extensionUi` and the device's `extension_ui_response`; the device's Stop through `tab.command`), so B writes the marker (with `peer`), continues the turn after its own crash or quit — the marker revives the hosted tab, unstarted and waiting for its device in the grace period (`RemoteDevices.reviveHostTab`, only while hosting is on) — and judges a network failure by B's connectivity. That grace period (`HOST_TAB_GRACE_MS`, 10 min from the device's link loss, `LocalHostServices.#startGrace`) closes only an idle hosted tab: one that runs out while the tab runs a turn (a revived one included) or holds it for B's connection starts another, so the turn runs to its end and keeps its marker until then. A turn blocked on an ask that waits for the device therefore keeps its omp until the device answers or B quits; there is no overall cap. A only mirrors that wait (the `awaitingConnection` tab event, emitted ahead of the failing events and re-sent on every `tab.open`; the row reads "Waiting for {device}'s internet connection…") and sends its Cancel to B (`RemoteSidecar.cancelHostWait` → `tab.cancelWait`). A relaunched device reopens its tabs under new rtabs: `tab.open` with a session path takes over the tab an earlier connection of that device left on it (`#adopt`), so no second omp starts on the same session. The first window to load takes the "Continuing N interrupted tasks" notice (`resume.takeNotice`) with a Stop (`resume.stop`). The quit and update confirmations (`confirmQuit(restart)`) say the work continues rather than stops. ② Connectivity: `ConnectivityMonitor` (net.isOnline() sampled by edge, the windows' `online`/`offline` events via `resume.reportOnline`, `powerMonitor` suspend/resume with a DNS probe until the wake is real, and `RESUME_WINDOW_MS` after a wake) decides `shouldWait()`. A turn that ends with a network-class error (`isNetworkError`, a subset of stock's retryable pattern) while `shouldWait()` is held, not failed: the tab shows `awaitingConnection` (TurnStatusRow's calm "Waiting for the internet connection…" row with Cancel → `resume.cancelWait`; TurnErrorNotice stays hidden), keeps a `network` marker, and runs stock `retry` once online; a new run on the held tab (a prompt sent meanwhile, not the taken-over retry saga still ending) replaces the wait. ### Where a new feature goes

1. Stock RPC already has it (`omp://rpc.md`) → call it; add a local handler only to reshape.
2. Stock implements it (an exported function or class in `@oh-my-pi/*`, an `omp <subcommand>`) → reuse that implementation through the bridge or the CLI; never port or re-derive its rules in OMPdesk.
3. Data the GUI can get on its own (git, files, `omp <subcommand>`) → local handler in main.
4. Needs the live session → bridge method + thin local handler.
5. Needs a change inside omp → contribute upstream; never fork.

**No duplicate of stock logic.** Before adding domain logic, search the stock packages (`~/.bun/install/global/node_modules/@oh-my-pi/`) for an implementation. If one exists, call it, even when that means a bridge method, and add its internals to `capabilities.ts`. Keep an OMPdesk copy only in two cases, and say why in a comment that names the stock counterpart:
- the copy is measurably better and stock cannot be used as is;
- it must run where stock cannot: the renderer, main before omp starts, or a remote client.

A test pins such a copy to stock behaviour: it compares against the stock function where the test can import it (bridge tests on a machine with omp), and otherwise uses the same cases stock's own tests use. Two OMPdesk copies of the same logic are never acceptable; merge them into one shared module.

When an omp update breaks a bridge method, fix the method against the new internals and raise `MIN_OMP_VERSION` if the fix requires it.

## Change workflow

Changes accumulate as local commits on `main` and ship together only when the user asks:

1. Each finished fix or feature: run its own checks, then commit it locally (a normal descriptive message; no version bump, no CHANGELOG release section). Do not push.
2. When the user asks to release ("배포해줘"): `bun run gate` (types, biome, surface policy, vitest and build, then the full Playwright suite) — all green. CI runs only part of the e2e suite, so the full suite on this Mac is the release gate.
3. Then release with the steps below: one dated `CHANGELOG.md` section (Korean summary plus English summary) covering every local commit since the last release, bump the version once, commit `release: vX.Y.Z`, push everything to `main` in one push, and watch the release run to the end.

Exception: a defect in the released version that makes the app unusable ships right away on its own.

Every release run bills about 17 weighted minutes (6-7 Linux minutes plus 5 Windows minutes weighted 2×; the `mac` job runs free on the maintainer's Mac, or adds about 20 on GitHub's macOS runner), which is why releases are batched; unpushed commits live only on this Mac, so tell the user when several are waiting. Never leave an `Unreleased` section behind on `main`. Do not reinstall the local app unless the user asks — the in-app updater picks the release up.

## Release

- Version `X.Y.Z` semver; tag `vX.Y.Z`; release commit `release: vX.Y.Z`. Commit messages carry no AI attribution trailers.
1. Pick the version from the commits since the last release tag (features → minor, fixes only → patch). Bump `package.json` `version`, add a dated `## [X.Y.Z] - YYYY-MM-DD` section to `CHANGELOG.md`: the Korean summary first, then a line holding only `<!-- en -->`, then the English summary of the same content (release.yml turns the marker into a `---` rule, so the GitHub notes carry both, Korean first; the What's new window and the changelog window show the part for the UI language and fall back to Korean when a release has no English part — `changelogSection`/`changelogReleases` in `src/renderer/lib/whats-new.ts`). Update README version mentions. Confirm `MIN_OMP_VERSION` is current.
2. `git commit -am "release: vX.Y.Z" && git push origin main`. Do not tag.
3. `.github/workflows/release.yml` does the rest; each packaging job runs its e2e on the `out/` it packaged: `build` on Linux builds the app bundle `out/` once and uploads it (the bundle is byte-identical whichever OS builds it), then runs types, biome and the surface policy; `check` on Linux runs vitest; `mac` builds and packages the arm64 DMG (signed with the pinned certificate, codesign + designated requirement + `gui-bridge` verified), then runs `@smoke` and `e2e/real-core.e2e.ts`; `win-test` runs `bun run test:platform` (the Windows test scope above); `win` installs while `build` runs, takes its `out/` (it polls the run's artifacts instead of `needs: build`, which would also wait for build's checks), packages it as the x64 NSIS setup (`makensis` cannot run on Apple Silicon), then `@smoke`. Only if everything passed, `publish` creates tag `vX.Y.Z` and the GitHub Release (title `vX.Y.Z`) with exactly two assets, `ompdesk-mac-arm64.dmg` and `ompdesk-windows-setup.exe` (version-free, so `/releases/latest/download/<name>` links stay stable); notes = changelog section + minimum omp version + the update metadata comment `<!-- ompdesk-update {"version","releaseDate","files":{"mac"|"windows":{"name","size","sha512"}}} -->` (sha512 in base64), which the "Append update metadata" step computes from the files it uploads and GitHub does not render. No `latest*.yml`, ZIP, blockmap or portable exe. An existing tag or an `Unreleased` heading makes the run a no-op. The package run artifacts only carry the files to `publish` and expire after 1 day (7 on a dry run); the Release keeps the assets.
   - **Legacy feed switch**: `LEGACY_UPDATE_FEED` at the top of release.yml, `"false"` since v0.18.1. Installs up to v0.17.x updated from electron-updater's `latest-mac.yml`/`latest.yml`, fetching `ompdesk-X.Y.Z-arm64-mac.zip` (relaunch), `ompdesk-X.Y.Z-arm64.dmg` (manual) and `ompdesk-X.Y.Z-setup.exe` by exact name. Set to `"true"`, the mac job also builds the ZIP (`electron-builder --mac dmg zip`) and both jobs add the yml plus every file it lists, so such installs update once into the new updater; v0.18.0 carried that bridge. While it is `"false"`, `publish` refuses any release that does not have exactly the two assets.
4. Watch it to the end: `gh run watch <run-id> --exit-status`. A failure the code didn't cause (runner, network, flaky test): `gh run rerun <run-id> --failed` reruns only the failed jobs — never start a whole new run for it. Otherwise fix the cause on `main` and re-run with `gh workflow run release.yml` (on main). Rehearse without releasing from any branch: `gh workflow run release.yml --ref <branch> -f dry_run=true` (packages land as run artifacts for 7 days).

Manual fallback: `bun run package:mac -- --publish never` on a Mac, `bun run package:win -- --publish never` on Windows, copy `dist/ompdesk-X.Y.Z-arm64.dmg` to `ompdesk-mac-arm64.dmg` and `dist/ompdesk-X.Y.Z-setup.exe` to `ompdesk-windows-setup.exe`, append the metadata comment to the notes the way the "Append update metadata" step does (a release without it is not offered as an update), then `gh release create vX.Y.Z --target main --title vX.Y.Z --notes-file <notes> ompdesk-mac-arm64.dmg ompdesk-windows-setup.exe`.

The repo is private, so the in-app updater authenticates as the user (`src/main/update-auth.ts`: `GH_TOKEN`/`GITHUB_TOKEN` → `gh auth token` → a safeStorage-encrypted token from Settings › Updates). Each check reads the latest release (`/releases/latest`, or `/releases` with pre-releases on) through the authenticated API, and `src/main/update-release.ts` validates the metadata comment with zod against the release itself (tag = version, asset present with that size). A missing or malformed comment, or one that contradicts the release, means no update and an error state ("no valid update information"); a release without this platform's file reports a missing installer. `src/main/update-provider.ts` hands electron-updater a custom provider (`setFeedURL({ provider: "custom", updateProvider })`) whose UpdateInfo points at the API asset endpoint plus the token; differential download is off (no blockmaps). Never bundle a token. Exercise it unpackaged with `OMP_DEV_UPDATE_CHECK=1 OMP_DEV_UPDATE_MODE=manual` (plus `OMP_DEV_UPDATE_PRERELEASE=1` to accept a throwaway pre-release), launching Electron on the repo root so the version is `package.json`'s. `OMP_DEV_UPDATE_MODE=relaunch OMP_DEV_UPDATE_BUNDLE=<writable copy of OMPdesk.app>` runs the relaunch path instead, staging the release against that stand-in bundle and swapping it on quit (unpackaged only).

Install modes (`src/main/updater.ts`): Windows uses electron-updater's NSIS flow (background download, SHA-512 checked, applied on restart or quit). Every macOS build, ad-hoc or certificate-signed, avoids Squirrel, which would need the ZIP the release no longer ships. When the bundle sits in a writable location it runs **relaunch** mode: download `ompdesk-mac-arm64.dmg` in the background into `<userData>/updates/ompdesk-X.Y.Z-arm64.dmg`, verify its SHA-512, `hdiutil attach -nobrowse -readonly` it, copy the `.app` out with `ditto`, detach, check the bundle's `codesign --verify --deep --strict`, bundle id and version (`stageBundleFromDmg` in `updater-state.ts`), then on "Restart & install" (or any approved quit) a detached `/bin/bash` helper (`SWAP_SCRIPT`) waits for the app to exit, swaps the bundle with rollback, and reopens it on restart. Read-only locations (DMG, App Translocation) fall back to the same DMG, verified and opened in Finder from Downloads (**manual** mode).

macOS signing: `scripts/mac-sign.cjs` (electron-builder `mac.sign`) signs every bundle with OMPdesk's own self-signed certificate, pinned by SHA-1 in `scripts/mac-signing.json`, so the designated requirement (`identifier "com.seuput.ompdesk" and certificate root = H"…"`) is the same in every release and macOS keeps its privacy grants (folders, local network, microphone) across updates; an ad-hoc signature's requirement is the build's cdhash, so each update re-asked them all. The identity comes from the repository secrets `MAC_SIGNING_P12_BASE64` / `MAC_SIGNING_PASSWORD` (release.yml sets `OMPDESK_MAC_SIGNING_REQUIRED=1` and checks the requirement), else the maintainer's local copy in `~/.ompdesk-signing/` (p12 + password; the only backup — losing it means a new certificate and one more round of prompts for every user), else an ad-hoc fallback with a warning. It is imported into a throwaway keychain passed to codesign with `--keychain`; the user's keychain search list is never touched. Never replace the certificate. Builds carry no Apple Team ID, so keychain items still bind to the cdhash (hence safeStorage stays untouched unless a stored token exists), and nothing is notarized: downloaded DMGs need right-click → Open once, locally built apps run without Gatekeeper prompts.

## Code conventions

- TypeScript: no `any`, no inline `import("…")` types, `#private` fields, Bun APIs where cleaner.
- i18n: the UI ships English and Korean only (`UI_LANGUAGES` in `src/shared/ui-language.ts`). Every user-visible string goes through `useT()` with the same key in `src/renderer/locales/en.ts` and `ko.ts` (`locales.test.ts` enforces identical key sets). Settings-schema text lives in `src/renderer/components/settings/schema-ko.ts` and `schema-option-ko.ts`; main-process strings in `src/main/i18n.ts` and `tray-labels.ts`.
- Model output renders through `MarkdownRenderer` (`src/renderer/lib/markdown.tsx`, rehype-sanitize) — never `dangerouslySetInnerHTML` with model text. Text a person typed (prompt bubbles) passes `userText`: single-dollar math stays literal and HTML tags show as typed (`remark-html-text.ts`).
- A path a reply or tool card links is never handed to `shell.openPath` when opening it would run something: `openLocalPath` (`src/main/open-path.ts`) reveals launcher types (`.app .command .sh .jar .exe .bat .cmd .ps1 .lnk .url .msi`, scripts an interpreter's install may run on open on either platform — `.py .pyw .pyz .pl .rb`, python.org's Python Launcher runs a `.py` on macOS —, the Windows script, scriptlet, shortcut, help, add-in and theme types (`.chm .xll .wsc .sct .theme .settingcontent-ms` and the like), macOS `.terminal .workflow .pkg .dmg .scpt .webloc` and the like), anything an executable bit marks on POSIX, and any symlink to either, in Finder/Explorer instead. A new caller that opens a model-supplied path goes through it.
- Tool-rendered text uses the helpers in `src/renderer/lib/format.ts`; preview ceilings come from `src/renderer/lib/preview.ts`; subprocess output renders through `AnsiText` (`src/renderer/lib/ansi.tsx`).
- Component tests use the linkedom harness (see `src/renderer/components/chat/ThinkingBlock.test.tsx`): mount through `I18nProvider`, reset zustand stores in `afterEach` via their `reset()`/setters — never `mock.module()`.
