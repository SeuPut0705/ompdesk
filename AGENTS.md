# ompdesk — Development Rules

Read this before any edit in this repository.

## Repository identity

- Product: **OMPdesk** (`OMP` capitals, `desk` lowercase) is the display name in every user-visible string, the bundle (`OMPdesk.app`, `productName`), menus, tray, and window title. An unofficial desktop app for the omp agent. Identifiers stay lowercase: the package name, the bundle id `com.seuput.ompdesk`, `app.setName("ompdesk")` (which picks userData `~/Library/Application Support/ompdesk` (`%APPDATA%\ompdesk`) and the "ompdesk Safe Storage" keychain item), the repo, and the two release asset names `ompdesk-mac-arm64.dmg` / `ompdesk-windows-setup.exe` (README download links and the updater fetch them by exact name; `packaging-config.test.ts` pins them). The first launch moves the pre-rename profile from its sibling directory into userData before anything reads it (`src/main/legacy-user-data.ts`, skipped under `--user-data-dir`). Say "omp" only for the agent/CLI (`omp update`, "omp 18.7+"). The mark (an omp-style π: top bar and two legs, the shorter left leg ending in an accent-colored foot; full and ≤48px pixel-grid forms) is defined once in `src/shared/brand-mark.ts`; `bun run gen:icons` writes the SVGs in `resources/icon-source*.svg` and `resources/brand/` from it (`scripts/brand-svgs.ts`; never hand-edit them, `brand-mark.test.ts` fails on drift; the hand-made README buttons `resources/brand/download-*.svg` are exempt) and regenerates `icon.png`/`icon.icns`/`icon.ico`, the tray PNGs and the favicon. The in-app mark is `components/common/BrandMark.tsx`.
- Product repo: [`SeuPut0705/ompdesk`](https://github.com/SeuPut0705/ompdesk) (`origin`). All code, tags, and releases live here.
- The agent is **stock omp** ([`can1357/oh-my-pi`](https://github.com/can1357/oh-my-pi)) installed on the user's machine. It is never built, vendored, or forked here. Users get agent updates with `omp update`.
- Platforms: **macOS and Windows only.**

## Architecture

```
renderer (React) ── IPC ──▶ main (Electron)
                              ├─ src/main/local/*      fork-era commands served in main
                              │     (git/gh, fs, ~/.omp files, `omp` CLI, translation to stock RPC)
                              ├─ src/main/sidecar.ts   spawns `omp --mode rpc-ui -e <gui-bridge>/index.ts`
                              │                         (stock RPC over stdio)
                              └─ src/main/bridge-client.ts ◀── unix socket / named pipe ──▶
                                                         resources/gui-bridge/*  (omp extension,
                                                         live AgentSession access)
```

- The renderer speaks one command set. `RpcClient.command()` (`src/main/rpc-client.ts`) first looks for a **local handler** (`src/main/local/index.ts` merges `src/main/local/<area>.ts` maps; duplicate keys throw at startup). Commands without a local handler go to stock omp unchanged.
- A local handler (`LocalHandler`, `src/main/local/types.ts`) either does the work in main (git, gh, files, `ctx.omp.run([...])`), translates to stock RPC (`ctx.send(...)`), or calls the bridge (`ctx.bridge.request(method, params)`) when it needs live session state.
- **Bridge** (`resources/gui-bridge/`): an omp extension loaded with `-e`. Area modules export `methods` maps; `env.session()` is the live `AgentSession`, `env.pi.pi` the stock package index. Bare `@oh-my-pi/pi-coding-agent/...` subpath imports resolve through omp's own resolver. These are **internal omp APIs without semver** — keep methods small, feature-detect, and throw clear errors.
- **Compatibility self-check**: every omp internal a bridge module uses is listed per GUI feature in `resources/gui-bridge/capabilities.ts` (`REQUIREMENTS`); add the new internal there (and its module to `LOADERS` in `health.ts`, literal specifier) whenever a bridge method starts using one. `index.ts` loads each area module separately, `guard(feature, methods)` refuses a feature's methods with `unsupported_omp` while anything it needs is missing, and the `capabilities` method reports them; `src/main/bridge-health.ts` probes once per omp version per launch and the renderer toasts the result. `OMP_GUI_BRIDGE_PROBE_HIDE=<label>,…` (labels as `capabilities` prints them, e.g. `AgentSession.setPlanModeState`) makes the probe treat those internals as missing, to rehearse a broken omp.
- Reply language: Settings › General › Conversation language stores prefs `replyLanguage` (`auto` default | a curated English name | `off`; `src/shared/reply-language.ts`). `auto` is the device language's English name (first usable `app.getPreferredSystemLanguages()` entry, then `app.getLocale()`; not the UI language). Each spawn passes the result as `OMP_GUI_REPLY_LANGUAGE`, and a pref change (or a bridge connect) pushes it to every live local sidecar and every tab this machine hosts through the bridge's `reply_language_set {language: string | null}`; a paired host's tabs follow the host's own pref. The bridge's `modes/reply-language.ts` keeps the value as module state and appends one instruction through `before_agent_start` from the next turn (nothing when off, unset or English, so the prompt stays stock). Never inject GUI text with `--append-system-prompt`: it collides with the launch profile's flag and turns off omp's fork prompt-cache key.
- Profile: Settings › General › Profile stores prefs `userProfile` (`{name, experience}`; contracts and prompt text in dependency-free `resources/gui-bridge/user-profile-contracts.ts`; levels beginner, vibe-coder, junior, expert). It rides the reply-language path: `OMP_GUI_USER_PROFILE` (JSON) at spawn, `user_profile_set` on change and on bridge connect to every live local sidecar and every hosted tab, and `modes/user-profile.ts` appends one `<user-profile>` section through `before_agent_start` (nothing for an empty profile). Stock has no such setting.
- Delegation strength: the composer chip (`layout/DelegationControl.tsx`) sets Your settings / Solo / Assisted / Collaborative / Swarm per tab through `get_delegation`/`set_delegation` → bridge `modes/delegation.ts` (rules `delegation-core.ts`, presets `delegation-contracts.ts`). Each strength is stock `task.eager`, `task.maxConcurrency` and (Solo) `task.maxRecursionDepth = 0` held as runtime overrides, never written to config.yml; stock's own listeners rebuild the prompt and drop or restore the task tool. The last pick is prefs `delegationMode`, passed as `OMP_GUI_DELEGATION` on every spawn and applied inside the extension factory like the thinking default; a Settings write of one of those settings releases the strength.
- Account rotation: Settings › Models & providers stores prefs `accountRotation` (`quota` default = stock omp's usage ranking | `even`; `src/shared/account-rotation.ts`, control `providers/RotationModeControl.tsx`). Stock has no switch for it, so each spawn passes `OMP_GUI_ACCOUNT_ROTATION` plus the shared ledger `<userData>/account-rotation.json` (`OMP_GUI_ACCOUNT_ROTATION_STATE`), and a change (or a bridge connect) pushes `account_rotation_set {mode}` to every live local sidecar and every tab this machine hosts (`LocalMachine.setAccountRotation`, `src/main/account-rotation.ts`). In even mode the bridge's `account-rotation.ts` (`before_agent_start`) gives a session without an account the unblocked one handed out least recently across all local omps, as an automatic warm pin (`authStorage.sessions.pin(…, {restoredAtMs})`); a session keeps its account until it is blocked (an idle pin is renewed, not re-ranked), and stock's 429 blocking/failover is untouched. A paired host's tabs follow the host's pref, which Settings reads and writes through `host.accountRotation.get|set`.
- Provider sign-in (Settings › Models, first run; `providers/ProviderLogin.tsx`) runs stock `login` on the tab's omp. Its `open_url`, `input` and info `notify` requests that arrive while a sign-in is in flight belong to the panel (`loginRequestIds` in `stores/extension-ui.ts`) and never render as chat cards, even after the panel unmounts. A browser sign-in finishes through stock's loopback callback; stock also races a code paste against it ("Paste the authorization code…") and never closes it, so the panel shows the paste as a collapsed fallback (open on a paired host's tab) and answers the leftover request with `cancelled` once `login` returns — an empty answer before that only re-asks. Stock's RPC `login` takes no cancel and holds omp's serial command queue (up to its 5-minute callback timeout), so Cancel sends `login_cancel` (`src/main/local/settings.ts`), which ends it through the callback's own denial (`error=access_denied` with the flow's `state`, what a provider's Deny button sends).
- Thinking default: sessions OMPdesk spawns (local tabs and the tabs a host runs) start on stock's `auto` thinking level unless some layer (config.yml, a project config, `--config` overlay, env) sets `defaultThinkingLevel`. `resources/gui-bridge/thinking-default.ts` (rules in `thinking-default-core.ts`) holds `auto` as a runtime override, applied inside the extension factory because stock loads `-e` extensions after `Settings.init` and before createAgentSession picks the first level; it is never written to config.yml (the omp CLI keeps stock `high`), Settings reports it with `runtime` provenance, a Settings write releases it first so the user's value persists and wins, a reset takes it up again, and subagents inherit it through stock's `createSubagentSettings` snapshot.
- Thinking range: the same mechanism holds `providers.autoThinkingMaxEffort` = `max` (stock `xhigh`), so `auto` may resolve every effort the model supports up to its top tier; an explicit user value wins. The advisor role is written with `:auto` when picked without a level (`resources/gui-bridge/role-values.ts`), because stock runs an unsuffixed advisor at a fixed `medium`; pickers show it without the suffix. The model setup assistant assigns only stock's built-in roles; custom roles (`modelRoles.<name>`) keep the user's model.
- Idle compaction: stock's `compaction.idleEnabled` / `idleThresholdTokens` / `idleTimeoutSeconds` (Settings › Agent › Context, `/autoclear on [delay] | off`) only had a timer in the TUI, so `resources/gui-bridge/idle-compaction.ts` (rules in `idle-compaction-core.ts`, a copy of the TUI's `#scheduleIdleCompaction`) arms it on the live session after a terminal `agent_end` and calls stock `runIdleCompaction()`. The renderer (`hooks/use-idle-compaction-draft.ts`) reports each tab's draft empty ⇄ non-empty through `set_idle_compaction_draft`, because stock skips a session whose input holds text.
- Context inspector (Insights › This session › Inspect, `components/insights/ContextInspector.tsx`): the bridge's `context.inspect` (`resources/gui-bridge/context-inspect.ts`, rules in `context-inspect-core.ts`) keeps stock `getContextBreakdown()`'s anchored totals, splits the tool schemas by source (built-in / MCP / extension, counted per tool with stock `estimateToolSchemaTokens`) and reads the context files back out of the rendered `<repo-rules>` block; `context.entry` returns one entry's provider text (tool schema via stock `toolWireSchema`, messages via `convertToLlm`), capped at 32k characters.
- Prompt origins (A85, `resources/gui-bridge/prompt-origin.ts`, contracts `prompt-origin-contracts.ts`): a host passes the device a tab runs for (and its own name) as `OMP_GUI_PROMPT_ORIGIN` at spawn; that omp journals one `ompdesk.prompt-origin` custom entry per user message (public `message_end` hook, keyed by the message timestamp), and `sessions.transcript` sets `promptFrom` on the prompts typed on another device than the viewing one once a session holds prompts from two devices (MessageBubble shows "from {device}"). Each device's tab is its own omp, so no prompt or approval is ever cancelled or answered from another device.
- `src/main/omp-runtime.ts` finds omp (`OMP_GUI_OMP` override → login-shell `PATH` → `~/.bun/bin/omp`, `/opt/homebrew/bin/omp`, `/usr/local/bin/omp`; Windows `%USERPROFILE%\.bun\bin\omp.exe`, `omp.cmd`/`omp.exe` on `PATH`) and enforces `MIN_OMP_VERSION` (18.8.7). Every bridge feature in `capabilities.ts` is required at that version; when a feature needs a newer omp, raise `MIN_OMP_VERSION` instead of carrying an older-omp fallback.
- Machine setup (`src/main/setup/`, contract `src/shared/setup.ts`): at launch main detects Bun, omp (through `resolveOmp`, so `MIN_OMP_VERSION` gates it), Git, GitHub CLI and Node.js (through the REA probe) and installs what is missing **on its own** — no install button, no consent click. Required, in order: Bun (`curl -fsSL https://bun.sh/install | bash` / `irm bun.sh/install.ps1 | iex`, user-level), on Windows Git for Windows (an existing install with `bin\bash.exe` is reused; otherwise the PortableGit pinned in `plans.ts` with its published SHA-256, extracted without admin into `%LOCALAPPDATA%\ompdesk\tools\git`; never WSL), then omp (`<abs bun> install -g @oh-my-pi/pi-coding-agent`, or `omp update` below the minimum). Optional, in the background once omp works: Git on macOS (`xcode-select --install`, Apple's dialog), gh and Node (Homebrew on macOS, else the official archive checked against its published SHA-256 into the managed tools dir `<userData>/tools`; `winget … --accept-source-agreements --accept-package-agreements` on Windows, else `unavailable`). Main downloads the PortableGit and archive files itself (`download.ts`: streamed to `<tools>/.downloads`, SHA-256 checked, removed after the install) before their script re-checks and unpacks them, so a running item's `progress` carries real bytes against the announced size; every running item also carries its place in its run (`step`/`steps`) and `startedAt`, and the view shows a determinate bar only for those bytes, an indeterminate one otherwise, plus "Step n of m" and the elapsed time. `paths.ts` appends the managed bin dirs to `process.env.PATH` and sets `GIT_INSTALL_ROOT` (which stock `resolveWindowsShell` checks after the Git for Windows roots) at startup and after each install, so every later spawn inherits them; after an install it re-reads the login-shell PATH (macOS) or the registry PATH (Windows), re-detects, and when omp became usable restarts every local tab in `error`/`exited` and the stats server — no app restart. Each item is tried automatically once per launch; after three automatic misses only once a day (`<userData>/setup-state.json`); the user's Retry always runs. Every install runs under `supervisor.ts` (the app binary as Node via `ELECTRON_RUN_AS_NODE`), which kills the installer's process tree when its stdin closes: Cancel (which aborts main's download too), quit (`SetupService.dispose`) or a crash. IPC (`setup:get-state`, `setup:retry`, `setup:cancel`, push `setup:state`) takes item ids only and refuses anything else; no handler accepts a command. Automatic installs run only in a packaged app outside `OMP_GUI_HEADLESS=1`, or with `OMP_GUI_TEST_INSTALLER` (plus `OMP_GUI_TEST_DOWNLOAD`/`_SHA256`, a file every test plan downloads first); dev and test launches only detect. The renderer shows the required steps as the first first-run step (`components/onboarding/`) whenever a local tab's omp is unusable, and every item in Settings › General › This computer; remote tabs never show it. Claude Code CLI and Codex CLI are never installed: omp signs in to Anthropic and OpenAI itself. `.github/workflows/setup-assets-health.yml` downloads every one of those files weekly through `download.ts` (`scripts/setup-assets-health.ts`, `gh workflow run setup-assets-health.yml` to run it now) and keeps one issue open while any fails.
- Composer history uses stock `HistoryStorage` through guarded `history_recent`, `history_search`, and `history_record` bridge methods. Local tabs share history with this machine's terminal omp; remote tabs use the paired host's history and never import client prefs. Legacy `inputHistory` prefs migrate oldest-first on the first successful local bridge load and are then deleted. Stock `shouldSkipHistory` keeps secrets out of SQLite; renderer-only transient recall and Up/Down draft restore remain local. Compaction-limit commit/prefill uses stock `config/compaction-threshold` helpers through `compaction_limits`; typing never waits for bridge validation.
- Stats: `resources/gui-bridge/stats-host.ts` runs the user's omp-stats server (stock `omp stats` always opens a browser) and adds the paginated `/api/stats/requests` route stock lacks.
- Main-side stock operations without a tab share one lazy Bun worker (`src/main/stock-helper.ts`, `resources/gui-bridge/stock-helper/host.ts`). Area handlers register request names; resolve stock modules from `OMP_PACKAGE_ROOT`, never boot an agent or call a model. The session index uses read-only `listAllSessions`/`listSessionsReadOnly` and preserves only GUI chat labels, scope filtering, duplicate-id suppression and chokidar notifications. Stored deletion uses stock `FileSessionStorage.deleteSessionWithArtifacts`; live `drop_session` first succeeds at `new_session`, then the guarded bridge refuses to delete the new active file. stdin EOF and app quit stop the helper.
- Scheduled runs (Settings › Schedules; contract `src/shared/schedules.ts`, service `src/main/schedules.ts`): main checks every 30 s and starts stock `omp -p [--model] [--yolo]` in the schedule's folder, only while OMPdesk is open; times missed while it was closed are skipped, a start due while the previous run still goes is recorded as skipped. Stock omp has no scheduler. Each run goes through the setup supervisor (`spawnSupervised`, the prompt file as omp's stdin), so a Stop, a quit or a crash kills omp's whole tree. Schedules and the last 200 runs live in `<userData>/schedules.json`, run output in `<userData>/schedule-runs/<runId>.log`.
- Right panel (`components/layout/PanelContainer.tsx`): header = view title, Terminal/Changes/Preview/Files icons, ⋮ View options (Background tasks, Plan, Logs, Queue, Tree), close; a view's own actions sit in its toolbar row, never in the header. The terminal reuses stock `@oh-my-pi/pi-natives` `PtySession` inside the stock helper worker (`resources/gui-bridge/stock-helper/terminals.ts`, `src/main/terminal/`): no second native addon, stdin EOF kills every PTY; a paired host's tab gets the host's terminals (`terminal.request`/`terminal.shells` in `remote/host-services.ts`, disposed with the host tab). The agent reads a tab's terminals through the read-only `gui_terminal_read` host tool, registered with stock `set_host_tools` on every ready sidecar and answered in ipc.ts (`src/main/terminal/agent-tool.ts`). The preview is a main-managed `WebContentsView` (`src/main/preview/`) on a non-persistent partition with sandbox/contextIsolation, no preload, http(s) only, permissions/downloads/new windows refused, and remote-tab loopback URLs blocked. Background tasks read stock `inspectAsyncJob`/`cancelAsyncJob` through the bridge.
- Side panel Subagent view (`panels/SubagentPanel.tsx`): a sidebar subagent row dragged onto a session pane (`omp:subagent-drag`, taken by `SplitWorkspace`) or its menu's "Open in side panel" sets `useUiStore.panelTab = "subagent"` + `panelSubagent {tabId, agentId}`; the view reads the transcript and steers through the owning tab's runtime. It is not in `PANEL_TABS` (default-view setting, `panel.*` shortcuts); panes stay main-owned omp tabs.
- Agent browsing in the preview (Preview toolbar robot button, local tabs only, off until the user clicks it): the tab's bridge (`resources/gui-bridge/browser-relay.ts`) starts stock's own `omp browser-relay` server (`tools/browser/relay/server.ts`) on a free 127.0.0.1 port with a random extension token and holds `browser.relay`/`browser.relayUrl` as session runtime overrides, so stock's browser tool runs in relay mode. Main joins as the relay's "Chrome extension" (`src/main/preview/agent-relay.ts`, stock's `relay/protocol.ts`) over the preview page's `webContents.debugger`, offering that one page — never the app window, which keeps no remote-debugging port. It refuses `Page.navigate` off http(s)/about:blank, `Browser.*`, downloads and new or closed targets; the page keeps its partition, sandbox and no-preload rules. A banner shows the agent's last CDP method; Take over (or a tab switch, closing the panel, the session ending) detaches the debugger, closes the socket and stops the relay. `e2e/preview-agent.e2e.ts` drives it with stock's relay server and puppeteer-core from the installed omp.
- Built-in MCP: `resources/omp-builtin/.mcp.json` starts the dependency-free Node `rea-relay.mjs` via stock's `${OMP_PLUGIN_ROOT}` substitution, outside asar, as a second directory `-e` on every eligible spawn. The relay runs pinned REA (`rea-config.json` is the sole version pin), exposes 15 unchanged entry-tool schemas plus `rea_catalog` / `rea_call`, and keeps the full catalog available on demand instead of adding 207 xd:// mount-notice lines to each session. The same root carries REA's own `reverse-engineer-anything` skill in `skills/` (stock loads an extension root's `skills/`), so the skill comes and goes with the server; it is vendored from the pinned release plus an OMPdesk section (mounted vs `rea_call` tools, no `rea setup`) by `bun run sync:rea-skill`, which every version bump runs (`packaging-config.test.ts` fails on a stale copy). Node/npx must satisfy REA's engines; prefs `builtinMcp.rea` (default on) governs tabs this machine spawns or hosts. stdin EOF kills the child process tree; never write the user's MCP config.
- Remote devices (`src/main/remote/`): OMPdesk on a host (B) runs tabs for paired clients (A). Pairing is an 8-char code shown on B (10 min, single use, 5 wrong guesses rotate it) proved through an X25519 + HKDF handshake; later connections authenticate both long-term keys (Noise-KK-like) and run AES-256-GCM frames over TCP. Keys and peers live in `<userData>/remote-*.json` (mode 0600, no safeStorage). The pool holds a `SidecarLike` per tab: a `RemoteSidecar` (A) proxies `tab.*` requests to B's `LocalHostServices`, which runs real SidecarManagers from `sidecar-factory.ts` and forwards their events; ipc.ts routes every handler that touches the omp machine (sessions, fs reads, launch profiles, project switches) by the tab's `device`, and F-OWN keys are device + path. Settings, Usage and Stats follow the focused tab's `device`: tab RPC already reaches the host, and models.yml providers, the stats server and `omp bench` go through `machine-services.ts` (`LocalMachine` here, `host.*` calls on B), while app prefs, the updater and remote-devices stay this device's (`SECTION_SCOPE`, `components/remote/HostScope.tsx`). Host tool calls (`gui_open_url`, notify, clipboard) always run on A. `OMP_GUI_REMOTE_PORT` (TCP, default 47821, `0` = ephemeral) and `OMP_GUI_REMOTE_DISCOVERY_PORT` (UDP beacon, default 47822) let parallel instances coexist.
- Packaged apps ship `resources/gui-bridge` **outside the asar** (`extraResources` in `electron-builder.yml` and `electron-builder.win.yml`; `src/main/packaging-config.test.ts` enforces it). The app contains no `omp` binary.
- Composer state uses stock `get_state` for session identity and resolved thinking, and stock `cycle_model` for forward cycling; the bridge adds only missing state, backward cycling, tool provenance/mounted tools and the GUI `/copy` tree around stock `pi-tui/overlays/copy-targets` extraction. Model-pool contracts live in dependency-free `resources/gui-bridge/pool-contracts.ts`, so renderer imports and the packaged bridge use the same normalization, roles and member cap without reaching outside `extraResources`.

### Where a new feature goes

1. Stock RPC already has it (`omp://rpc.md`) → call it; add a local handler only to reshape.
2. Stock implements it (an exported function or class in `@oh-my-pi/*`, an `omp <subcommand>`) → reuse that implementation through the bridge or the CLI; never port or re-derive its rules in OMPdesk.
3. Data the GUI can get on its own (git, files, `omp <subcommand>`) → local handler in main.
4. Needs the live session → bridge method + thin local handler.
5. Needs a change inside omp → contribute upstream; never fork.

**No duplicate of stock logic.** Before adding domain logic, search the stock packages (`~/.bun/install/global/node_modules/@oh-my-pi/`) for an implementation. If one exists, call it, even when that means a bridge method, and add its internals to `capabilities.ts`. Keep an OMPdesk copy only in two cases, and say why in a comment that names the stock counterpart:
- the copy is measurably better and stock cannot be used as is;
- it must run where stock cannot: the renderer, main before omp starts, or a remote client.

A test pins such a copy to stock behaviour: it compares against the stock function where the test can import it (bridge tests on a machine with omp), and otherwise uses the same cases stock's own tests use. Two OMPdesk copies of the same logic are never acceptable; merge them into one shared module.

When an omp update breaks a bridge method, fix the method against the new internals and raise `MIN_OMP_VERSION` if the fix requires it.

## Build, test

- Typecheck: `bun run check:types`. Lint/format: `bunx biome check src e2e resources scripts`. Surface policy (the SURFACE POLICY block in `src/renderer/styles/global.css`): `node scripts/lint-surfaces.mjs`.
- Unit/component tests: `bunx vitest run` (full suite must stay green; `vitest.setup.ts` pins `navigator.language` to en-US and `navigator.platform` to MacIntel, so keymap defaults and shortcut labels are the macOS ones on every runner — Windows behavior is tested by passing `"windows"` to the `lib/keymap.ts` functions).
- Vitest has two projects (`vitest.config.ts`): `renderer` (`src/renderer/**`) runs on worker threads with `lucide-react`, `linkedom` and `react-dom` pre-bundled by the deps optimizer; `node` (everything else) keeps a child process per file, since those tests spawn processes, open sockets and edit `PATH`/env. They run one after the other (`sequence.groupOrder`; side by side each would take every worker), with as many workers as cores on GitHub's runners (`GITHUB_ACTIONS`; never key on `CI`, which agent shells on this Mac export too) and at most 8 locally (as fast as 14 here). Both keep per-file isolation; never turn `isolate` off.
- Windows test scope: release.yml's `win-test` job runs `bun run test:platform`, the suite minus `src/renderer/**`. Anything that can behave differently on Windows (paths, PATH lookup, shells and `.cmd` shims, spawn, sockets and named pipes, file modes) lives in main, shared, the bridge or scripts, so its tests run there by default. Renderer tests never read the host platform (pass `"windows"`/`win32` explicitly instead); `src/main/platform-test-scope.test.ts` fails on a renderer test that checks `process.platform` and pins the script and the workflow step.
- Build: `bun run build` (`scripts/build-cache.ts`: electron-vite → `out/`, then `scripts/check-main-bundle.ts`). It reuses `out/` when it was built from identical inputs: a SHA-256 over `src/` and `resources/` (test and bench files outside `src/renderer` excepted; Tailwind scans renderer tests for class names), the electron-vite config, `tsconfig*.json`, `package.json`, `bun.lock`, `.gitignore`, `.env*`, the build's own scripts and the build env (`NODE_ENV`, `MODE`, `NODE_PATH`, browserslist and the `*VITE_*` vars) is stored with the size and mtime of every `out/` file in `out/.build-stamp.json`, written only after the build and the bundle check passed (about 20 ms to check against ~8 s to build). A missing `out/` or stamp, a different hash, or a removed, added or rewritten `out/` file rebuilds; `OMPDESK_FORCE_BUILD=1` always does. It prints one `[build] reusing …`/`[build] building out/: <reason>` line. CI and packaging start from a fresh checkout (no stamp), so they always build; a local `package:*` reuses only a byte-identical-input `out/`, and electron-builder leaves the stamp out of the package.
- E2E: `bunx playwright test`. `playwright.config.ts` sets `OMP_GUI_HEADLESS=1`: windows are transparent, click-through, off the Dock/taskbar, and never focused, and the app creates no menu-bar tray item and never registers the `omp://` handler (both belong to the user's installed OMPdesk; a test's tray once stalled the main thread before the first window reached Playwright), so tests never cover the user's screen or rewrite their LaunchServices state. Set `OMP_GUI_HEADLESS=0` only when you must watch. `e2e/real-core.e2e.ts` and `e2e/deep-audit.e2e.ts` run against the real system omp (isolated agent dir, no credentials); the other suites use the fake omp in `e2e/sidecar-fixture.ts`, installed per test by `fixtureOmp()` (`e2e/harness.ts`: an `omp.cmd` shim on Windows) and passed as `OMP_GUI_OMP`; it speaks stock `--mode rpc-ui` and serves the gui-bridge methods those suites reach on `OMP_GUI_BRIDGE`. Tear apps down with `exitApp()` (same file; it kills a main process that does not act on the exit within 10 s); shortcuts in tests use `ControlOrMeta`. `e2e/performance.e2e.ts` only runs with `OMP_GUI_PERFORMANCE=1` (optional `OMP_GUI_BASELINE_DIR` compares another built checkout). `e2e/event-replay.e2e.ts` runs the fake omp with `OMP_GUI_TEST_REPLAY_FRAMES=1` (every message and tool frame sent again behind the next one) and main with `OMP_GUI_TEST_BATCH_INTERVAL_MS=400`, so snapshot loads overtake held frames; `src/renderer/hooks/event-replay.test.tsx` is its seeded unit counterpart. Renderer stores apply a frame for a message or call they already hold (by stock timestamp and call id) as a no-op. `OMP_GUI_TEST_INSTALLER=<executable>` turns on automatic machine setup in a test launch and replaces every install plan with `<executable> <item> <method>` (archive installs skip their release lookup); `e2e/machine-setup.e2e.ts` uses it with `OMP_GUI_OMP` naming a not-yet-existing fake omp (missing omp → automatic install fails → Retry → detected → the tab restarts ready), and `OMP_GUI_SETUP_CAPTURES=<dir>` adds its light/dark × en/ko and narrow captures. Real installs never run in a test against the user's profile: `scripts/setup-install-check.ts` runs the real Bun installer, PortableGit (Windows) and `bun install -g` omp through the same runner in a child with a temp HOME/USERPROFILE and BUN_INSTALL, checks `omp --version` against the minimum, and deletes the temp dir.
- E2E parallelism: locally Playwright runs 4 workers (`playwright.config.ts`; 1 on GitHub's runners). Every test launches its own app on `mkdtemp` userData, agent dir and fake omp, with ephemeral ports (`OMP_GUI_REMOTE_PORT=0`, a fresh bridge socket per spawn), so a new spec never uses a fixed path, port or shared profile. The full suite (~90 s, three runs of 88–92 s in Oct 2026) is bound by its total work, not its slowest test: all four workers stay busy to the end, and apps running at once slow each other down. Split a long test into tests that run side by side only while it ends the run; each split adds a launch (~8 s on the system omp). `e2e/deep-audit.e2e.ts` (`mode: "parallel"`) splits its settings rows by measured cost over `SETTINGS_SHARDS` = 3 apps (~43 s each); 6 shards ran ~24 s each but added ~26 s of work and left the wall time unchanged. 5 workers measured ~9% faster than 4 (80–84 s vs 88–92 s, three runs each) and 6 ~10%, at more load, so 4 stays.
- Build lock and release gate: one build, Playwright run or full vitest run at a time across every checkout and agent on this Mac, because several at once overload it until load-sensitive tests fail. `scripts/build-lock.ts` holds the lock directory `/tmp/ompdesk-build.lock` (owner file refreshed every minute; one older than 15 minutes counts as stale). `bun run gate` (`scripts/gate.ts`) is the release gate inside that lock: typecheck, biome, the surface policy, the full vitest suite and the build (`bun run build`, so an unchanged `out/` is reused) side by side, then, only if all passed, the full Playwright suite on that build. Run any other build, Playwright run or full vitest run as `bun run locked -- <command>` (e.g. `bun run locked -- bunx playwright test e2e/smoke.e2e.ts --output /tmp/<you>-results`); it waits for the lock (printing `[lock] waited 42.3s for <holder>` past 1 s), stops the command's whole process tree and releases the lock when interrupted, and a nested locked command runs inside its ancestor's lock and logs nothing. Each release appends one JSON line (owner = `OMPDESK_LOCK_OWNER` or `user@checkout`, command, kind, cwd, `waitedMs`, `heldMs`, exit code, ISO time) to `/tmp/ompdesk-build.log` (Windows: the temp dir; `scripts/lock-log.ts`, trimmed to its newest 4000 lines past 5000); `bun run lock-stats [--since 2h]` (default 24h, `all`) prints totals and p50/p90 of wait and hold per owner and per kind (build / playwright / vitest / gate).
- Parallel agents: since every heavy step waits on that one lock, run at most three agents at once on this repo, each on one disjoint slice. Agents iterate with targeted vitest outside the lock, batch their builds and e2e into one short `bun run locked -- …` hold, commit their verified hunks locally as they go, and leave the full gate to whoever releases. `bun run lock-stats` shows whether agents are waiting more than working.
- Opt-in model audits (`OMP_GUI_REAL_WORK=1`, they spend tokens): `e2e/real-work-map.e2e.ts` (two parallel subagents, records frames) and `e2e/real-work-scenarios.e2e.ts` (edit, todos, failing command, silent command then stop, detached agent then stop, 20 commands, text only; light/dark captures plus a Korean relaunch). Both copy `config.yml` and `agent.db` into a private 0700 agent dir through `e2e/real-omp.ts` and run the main model on the user's `smol` role; `OMP_GUI_REAL_WORK_ARTIFACTS` picks the capture directory.
- CI (`.github/workflows/ci.yml`): `check` (types, biome, surface policy, vitest, build) on Linux only for every push/PR that touches more than Markdown, except a `release: vX.Y.Z` push, whose checks release.yml runs instead. Billing drives the layout: a private repo bills macOS minutes at 10× Linux and Windows at 2×, and every job rounds up to a whole minute. The full Playwright suite is manual only (`gh workflow run ci.yml -f e2e=true`); the release workflow runs the `@smoke` subset (`e2e/smoke.e2e.ts`, `--grep @smoke`, fake omp) on macOS and Windows and `e2e/real-core.e2e.ts` on macOS. The real Windows install of machine setup is manual only too (`gh workflow run ci.yml -f install_check=true`): the `install-check` job on `windows-latest` runs `bun scripts/setup-install-check.ts --hide-system-git` (the runner's preinstalled Git for Windows hidden, so PortableGit installs) against a temp USERPROFILE and asserts omp is detected at the minimum, the PortableGit download reported byte progress, the registry PATH refresh found Bun, and stock omp's shell resolves to that Git Bash, not cmd.exe. The Windows setup itself is one click, per user (`electron-builder.win.yml`: `oneClick`, no `perMachine`; `resources/installer.nsh` removes an all-users copy the old assisted installer left, after one question and one UAC prompt — the only case that asks anything), checked by hand with `gh workflow run ci.yml -f installer_check=true`: the `installer-check` job packages it and runs `scripts/windows-installer-check.ps1` silently, as a double-click (it must finish with only a progress bar and start the app), and over `legacy_tag`'s all-users install, checking the folder, the Start-menu and desktop shortcuts, the HKCU uninstall entry, the app's window and the uninstall.
- macOS jobs on `main` run on the maintainer's own Mac: a self-hosted runner (label `ompdesk-mac`, installed in `~/actions-runner-ompdesk`, a login LaunchAgent without KeepAlive; `./svc.sh stop|start|uninstall` there). It acts as the maintainer's login account, so it serves only release.yml's `mac` job and ci.yml's manual e2e, never push or PR jobs; those jobs must not change the account's environment (no `setup-bun`, which writes `~/.bun/bin`; no global omp install — real-core runs against the installed omp), and every action in both workflows is pinned to a commit SHA. Other refs, and `gh workflow run release.yml -f hosted_mac=true` when that Mac is off or asleep, use GitHub's macOS runner (about 20 billed minutes). A queued `mac` job means that Mac is offline.
- Never drive the app with synthetic OS input (osascript keystrokes etc.); use Playwright.
- Dev: `bun run dev` (HMR against the system omp; opens a visible window).
- Never reinstall `/Applications/OMPdesk.app` from inside the app (you may be running *inside* OMPdesk; quitting it kills this session). `scripts/reinstall-mac.sh` (`bun run package:mac -- --publish never && bash scripts/reinstall-mac.sh`) runs **only when the user explicitly asks for a local reinstall**. **Never** schedule a swap with `launchctl submit` (launchd keeps submitted jobs alive and reruns them, so the app quits and relaunches forever) or any `KeepAlive` job.
- Child processes the app spawns must not outlive it: they get an open stdin pipe and exit when it closes (see `resources/gui-bridge/stats-host.ts`), because a crash or force-kill skips the quit handlers.

## Change workflow

Changes accumulate as local commits on `main` and ship together only when the user asks:

1. Each finished fix or feature: run its own checks, then commit it locally (a normal descriptive message; no version bump, no CHANGELOG release section). Do not push.
2. When the user asks to release ("배포해줘"): `bun run gate` (types, biome, surface policy, vitest and build, then the full Playwright suite) — all green. CI runs only part of the e2e suite, so the full suite on this Mac is the release gate.
3. Then release with the steps below: one dated Korean `CHANGELOG.md` section covering every local commit since the last release, bump the version once, commit `release: vX.Y.Z`, push everything to `main` in one push, and watch the release run to the end.

Exception: a defect in the released version that makes the app unusable ships right away on its own.

Every release run bills about 17 weighted minutes (6-7 Linux minutes plus 5 Windows minutes weighted 2×; the `mac` job runs free on the maintainer's Mac, or adds about 20 on GitHub's macOS runner), which is why releases are batched; unpushed commits live only on this Mac, so tell the user when several are waiting. Never leave an `Unreleased` section behind on `main`. Do not reinstall the local app unless the user asks — the in-app updater picks the release up.

## Release

- Version `X.Y.Z` semver; tag `vX.Y.Z`; release commit `release: vX.Y.Z`. Commit messages carry no AI attribution trailers.
1. Pick the version from the commits since the last release tag (features → minor, fixes only → patch). Bump `package.json` `version`, add a dated `## [X.Y.Z] - YYYY-MM-DD` section to `CHANGELOG.md` with a Korean summary (it becomes the release notes), update README version mentions. Confirm `MIN_OMP_VERSION` is current.
2. `git commit -am "release: vX.Y.Z" && git push origin main`. Do not tag.
3. `.github/workflows/release.yml` does the rest; each packaging job runs its e2e on the `out/` it packaged: `build` on Linux builds the app bundle `out/` once and uploads it (the bundle is byte-identical whichever OS builds it), then runs types, biome and the surface policy; `check` on Linux runs vitest; `mac` builds and packages the arm64 DMG (signed with the pinned certificate, codesign + designated requirement + `gui-bridge` verified), then runs `@smoke` and `e2e/real-core.e2e.ts`; `win-test` runs `bun run test:platform` (the Windows test scope above); `win` installs while `build` runs, takes its `out/` (it polls the run's artifacts instead of `needs: build`, which would also wait for build's checks), packages it as the x64 NSIS setup (`makensis` cannot run on Apple Silicon), then `@smoke`. Only if everything passed, `publish` creates tag `vX.Y.Z` and the GitHub Release (title `vX.Y.Z`) with exactly two assets, `ompdesk-mac-arm64.dmg` and `ompdesk-windows-setup.exe` (version-free, so `/releases/latest/download/<name>` links stay stable); notes = changelog section + minimum omp version + the update metadata comment `<!-- ompdesk-update {"version","releaseDate","files":{"mac"|"windows":{"name","size","sha512"}}} -->` (sha512 in base64), which the "Append update metadata" step computes from the files it uploads and GitHub does not render. No `latest*.yml`, ZIP, blockmap or portable exe. An existing tag or an `Unreleased` heading makes the run a no-op. The package run artifacts only carry the files to `publish` and expire after 1 day (7 on a dry run); the Release keeps the assets.
   - **Legacy feed switch**: `LEGACY_UPDATE_FEED` at the top of release.yml, `"false"` since v0.18.1. Installs up to v0.17.x updated from electron-updater's `latest-mac.yml`/`latest.yml`, fetching `ompdesk-X.Y.Z-arm64-mac.zip` (relaunch), `ompdesk-X.Y.Z-arm64.dmg` (manual) and `ompdesk-X.Y.Z-setup.exe` by exact name. Set to `"true"`, the mac job also builds the ZIP (`electron-builder --mac dmg zip`) and both jobs add the yml plus every file it lists, so such installs update once into the new updater; v0.18.0 carried that bridge. While it is `"false"`, `publish` refuses any release that does not have exactly the two assets.
4. Watch it to the end: `gh run watch <run-id> --exit-status`. A failure the code didn't cause (runner, network, flaky test): `gh run rerun <run-id> --failed` reruns only the failed jobs — never start a whole new run for it. Otherwise fix the cause on `main` and re-run with `gh workflow run release.yml` (on main). Rehearse without releasing from any branch: `gh workflow run release.yml --ref <branch> -f dry_run=true` (packages land as run artifacts for 7 days).

Manual fallback: `bun run package:mac -- --publish never` on a Mac, `bun run package:win -- --publish never` on Windows, copy `dist/ompdesk-X.Y.Z-arm64.dmg` to `ompdesk-mac-arm64.dmg` and `dist/ompdesk-X.Y.Z-setup.exe` to `ompdesk-windows-setup.exe`, append the metadata comment to the notes the way the "Append update metadata" step does (a release without it is not offered as an update), then `gh release create vX.Y.Z --target main --title vX.Y.Z --notes-file <notes> ompdesk-mac-arm64.dmg ompdesk-windows-setup.exe`.

The repo is private, so the in-app updater authenticates as the user (`src/main/update-auth.ts`: `GH_TOKEN`/`GITHUB_TOKEN` → `gh auth token` → a safeStorage-encrypted token from Settings › Updates). Each check reads the latest release (`/releases/latest`, or `/releases` with pre-releases on) through the authenticated API, and `src/main/update-release.ts` validates the metadata comment with zod against the release itself (tag = version, asset present with that size). A missing or malformed comment, or one that contradicts the release, means no update and an error state ("no valid update information"); a release without this platform's file reports a missing installer. `src/main/update-provider.ts` hands electron-updater a custom provider (`setFeedURL({ provider: "custom", updateProvider })`) whose UpdateInfo points at the API asset endpoint plus the token; differential download is off (no blockmaps). Never bundle a token. Exercise it unpackaged with `OMP_DEV_UPDATE_CHECK=1 OMP_DEV_UPDATE_MODE=manual` (plus `OMP_DEV_UPDATE_PRERELEASE=1` to accept a throwaway pre-release), launching Electron on the repo root so the version is `package.json`'s. `OMP_DEV_UPDATE_MODE=relaunch OMP_DEV_UPDATE_BUNDLE=<writable copy of OMPdesk.app>` runs the relaunch path instead, staging the release against that stand-in bundle and swapping it on quit (unpackaged only).

Install modes (`src/main/updater.ts`): Windows uses electron-updater's NSIS flow (background download, SHA-512 checked, applied on restart or quit). Every macOS build, ad-hoc or certificate-signed, avoids Squirrel, which would need the ZIP the release no longer ships. When the bundle sits in a writable location it runs **relaunch** mode: download `ompdesk-mac-arm64.dmg` in the background into `<userData>/updates/ompdesk-X.Y.Z-arm64.dmg`, verify its SHA-512, `hdiutil attach -nobrowse -readonly` it, copy the `.app` out with `ditto`, detach, check the bundle's `codesign --verify --deep --strict`, bundle id and version (`stageBundleFromDmg` in `updater-state.ts`), then on "Restart & install" (or any approved quit) a detached `/bin/bash` helper (`SWAP_SCRIPT`) waits for the app to exit, swaps the bundle with rollback, and reopens it on restart. Read-only locations (DMG, App Translocation) fall back to the same DMG, verified and opened in Finder from Downloads (**manual** mode).

macOS signing: `scripts/mac-sign.cjs` (electron-builder `mac.sign`) signs every bundle with OMPdesk's own self-signed certificate, pinned by SHA-1 in `scripts/mac-signing.json`, so the designated requirement (`identifier "com.seuput.ompdesk" and certificate root = H"…"`) is the same in every release and macOS keeps its privacy grants (folders, local network, microphone) across updates; an ad-hoc signature's requirement is the build's cdhash, so each update re-asked them all. The identity comes from the repository secrets `MAC_SIGNING_P12_BASE64` / `MAC_SIGNING_PASSWORD` (release.yml sets `OMPDESK_MAC_SIGNING_REQUIRED=1` and checks the requirement), else the maintainer's local copy in `~/.ompdesk-signing/` (p12 + password; the only backup — losing it means a new certificate and one more round of prompts for every user), else an ad-hoc fallback with a warning. It is imported into a throwaway keychain passed to codesign with `--keychain`; the user's keychain search list is never touched. Never replace the certificate. Builds carry no Apple Team ID, so keychain items still bind to the cdhash (hence safeStorage stays untouched unless a stored token exists), and nothing is notarized: downloaded DMGs need right-click → Open once, locally built apps run without Gatekeeper prompts.

## Code conventions

- TypeScript: no `any`, no inline `import("…")` types, `#private` fields, Bun APIs where cleaner.
- i18n: the UI ships English and Korean only (`UI_LANGUAGES` in `src/shared/ui-language.ts`). Every user-visible string goes through `useT()` with the same key in `src/renderer/locales/en.ts` and `ko.ts` (`locales.test.ts` enforces identical key sets). Settings-schema text lives in `src/renderer/components/settings/schema-ko.ts` and `schema-option-ko.ts`; main-process strings in `src/main/i18n.ts` and `tray-labels.ts`.
- Model output renders through `MarkdownRenderer` (`src/renderer/lib/markdown.tsx`, rehype-sanitize) — never `dangerouslySetInnerHTML` with model text.
- Tool-rendered text uses the helpers in `src/renderer/lib/format.ts`; preview ceilings come from `src/renderer/lib/preview.ts`; subprocess output renders through `AnsiText` (`src/renderer/lib/ansi.tsx`).
- Component tests use the linkedom harness (see `src/renderer/components/chat/ThinkingBlock.test.tsx`): mount through `I18nProvider`, reset zustand stores in `afterEach` via their `reset()`/setters — never `mock.module()`.
