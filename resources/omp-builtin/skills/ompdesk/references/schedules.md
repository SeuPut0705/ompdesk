# Schedules

## `ompdesk_schedule`

Puts a prompt on a computer's Schedules service: a fresh print-mode session started in a folder, only while OMPdesk is open on that computer, on a timer, once, or when an event happens. `action` is `create`, `list`, `update`, `pause`, `resume`, `run`, `runs` or `cancel`; `device` picks the computer (a paired device by name or id, `"local"` = this computer; default the one your own session runs on), and each computer keeps and runs its own schedules.

- `action: "create"` needs `name`, `prompt` and exactly one start: `every_minutes` (at least 5), `daily_at` (`HH:MM`, optional `days` 0-6), `at` (once, an ISO moment with its offset) or `in_minutes` (once, from now), or `on` (an event, below); optional `folder` (absolute on that computer; default your own folder, required when `device` is not the one your session runs on) and `model`. The prompt has no memory of this conversation, so write it self-contained with the brief template. No card by default; the user confirms a new one only if they turned off both full control and "Let agents manage other sessions". It never runs with auto-approve; that computer's Settings › Schedules marks agent-made ones `[agent]`. A once schedule turns itself off after its run; a new one never runs on creation.
- `on` starts it on an event instead of a clock; an event run is also told what fired it:
  - `{"source": "webhook"}`: `POST /hooks/<id>` with `Authorization: Bearer <key>` on that computer's OMPdesk web server (it runs while Mobile web is on); the answer gives the id and key, and the request body reaches the run.
  - `{"source": "github", "repo": "owner/name", "events": [...]}` with `pull_request`, `issue`, `ci_failure`, `release`, `push`: news the user's `gh` sees, asked every 5 minutes.
  - `{"source": "files", "path": "/abs"}`: a file, or anything under a folder, created, changed or removed.
  - `{"source": "git", "repo": "/abs", "branch": "main"}`: new commits on a local branch (`repo` defaults to your folder).
  - `{"source": "session", "events": [...], "folder": "text"}` with `done`, `failed`, `waiting`: another session on that computer finished a turn, failed one, or waits for the user (only folders containing `folder`). Never the bot's own session or one it opened.
  - `{"source": "email", "account": "Work", "from": "text", "subject": "text", "to": "owner+bot@"}`: new mail in a mailbox the user added in that computer's Settings › Schedules › Email accounts (named by its label), checked every 2 minutes; `from`, `subject` and `to` are optional text the mail must contain (`to` matches any recipient, so a plus-address gives you a mailbox of your own). The run gets the sender, recipients, subject and the start of the text. A reply sent from that mailbox and automatic mail never start it. You never see or need the password; if no account has the label, ask the user to add it.
  - What changed while OMPdesk was closed (commits, GitHub events, mail, files) fires once when it starts again; nothing that happened while the routine was off or paused ever does. A trigger that cannot watch what it names shows as a failed run ("Its trigger failed: …") in `runs`.
  - Events that come while it runs start one more run after it with all of them; a routine whose own work keeps firing it is turned off after 10 such runs in a row, and its history says why.
- `action: "list"` shows every schedule of that computer; `action: "runs"` with `id` shows one's recent runs (running, succeeded, failed, stopped, skipped; what fired each; why one failed or was skipped; the newest 20 per schedule). `update` (any of `name`, `prompt`, `model` and one start), `pause`, `resume`, `run` (a test run now) and `cancel` take `id` (and the same `device`) and change only the ones agents made, never the user's.
- A device whose link is down is waited for about 15 seconds (a blip reconnects in that time); one that stays away is refused: it has to be on and reachable first.
- `target: "self"` (with `create`) is a routine of your own session, not a fresh run: at each start the prompt is delivered into this session as a message that starts a turn (the session is opened in the background when no tab holds it), so you keep this conversation and the prompt can be a note to yourself ("check the build; tell the owner only if it failed"). The run lasts as long as the turn it starts and fails with that turn's error. It takes no `folder`, `model` or `device` and works only for this computer's sessions. Use `in_minutes` or `at` for one follow-up you decide on yourself (it turns itself off), a timer or `on` for a standing routine; cancel a standing one once it is no longer needed.

Use it for recurring orchestration ("every morning, review the open PRs") and for work that should answer an event ("when CI fails on main, find the cause"), not for work that can run now.

## Keeping something durable

To keep a lesson or decision for later sessions, use ai-memory's own tools (see its `ai-memory-durable-pages` skill); OMPdesk has no tool for it.
